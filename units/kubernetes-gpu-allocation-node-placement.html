핵심 질문: GPU 총량이 충분해도 왜 Pod가 배치되지 않는가? 개념·실습 흐름 GPU 1·2·4개 요청 및 Multi-GPU Pod 하나와 1-GPU Replica 여러 개를 비교한다. 서로 다른 Node에 남은 GPU를 한 Pod가 합칠 수 없는 사례를 만들고 Label·Affinity·Taint를 변경한다. 집중/분산 배치가 이후 큰 요청에 미치는 영향, 자원 반환, Event 기반 Pending 원인을 재현한다. 실험과 달성 기준 연결 요청 크기·Replica·파편화 비교는 달성 기준 1~3, Node 선택·Taint·집중/분산 비교는 4~6, 반환·진단·재현은 7~8과 연결한다.

GPU 개수 요청과 배치 확인

미충족

CPU용 Mock 컨테이너의 limits에 nvidia.com/gpu 1·2·4를 각각 지정한다. requests를 함께 명시하면 limits와 같아야 함을 확인하고, 각 Pod의 nodeName·상태·Event와 Node별 예약 자원 합계를 비교한다.

○

Multi-GPU Pod와 여러 Replica 구분

미충족

한 컨테이너가 GPU 4개를 요청하는 Pod 하나와 GPU 1개를 요청하는 Replica 네 개를 비교한다. 한 Pod는 한 Node에 배치됨을 확인하고, Replica 증가가 모델 하나의 Tensor Parallel 설정을 대신하지 않음을 설명한다.

○

자원 부족과 단편화 재현

미충족

Fake GPU가 각각 2개인 Node 두 대에서 GPU 4개를 요청한 Pod가 Pending되는 상황을 만든다. 클러스터 총량 부족과 단일 Node의 연속된 요청 수량을 확보할 수 없는 상황을 구분하고, 요청 또는 배치 구성을 바꾼 뒤 결과를 검증한다.

○

GPU 종류와 Node 선택 조건

미충족

서로 다른 GPU 종류를 나타내는 Node Label을 사용해 nodeSelector·required nodeAffinity의 일치·불일치 사례를 실행한다. 지정한 Label은 하드웨어 성능 검증 결과가 아니라 가상 장치 속성임을 표시한다.

○

전용 GPU Node의 배치 제어

미충족

GPU Node에 NoSchedule Taint를 적용하고 Toleration 유무에 따른 배치 차이를 확인한다. Toleration은 배치를 허용할 뿐 해당 Node를 선택하도록 강제하지 않으므로 필요 시 Affinity와 조합한다.

○

집중 배치와 분산 배치 비교

미충족

지원되는 Scheduler 정책·Affinity·Pod Anti-affinity·Topology Spread 설정 중 선택한 방법을 기록하고 동일 Fake 자원과 Replica 수에서 집중·분산 배치를 비교한다. Node별 잔여 GPU와 이후 큰 GPU 요청의 배치 가능성을 설명한다.

○

Pending 진단과 자원 반환

미충족

자원 부족·선택 조건 불일치·Taint로 인한 Pending을 Event로 구분한다. GPU 요청 Pod를 삭제한 뒤 대기 Pod가 배치되는지 확인하고 Node Allocatable 총량과 Pod별 예약량·남은 배치 여유를 혼동하지 않는다.

○

GPU 배치 실험 재현 자료

미충족

각 실험의 Manifest·Fake GPU Topology·Scheduler 설정·Event·배치 결과표를 저장하고 같은 조건에서 성공·Pending 사례를 재현한다.

목표 문맥별 선택 이유

쿠버네티스 GPU 클러스터와 Multi-GPU Serving 학습에서 선택한 이유

Fake GPU 환경에서 쿠버네티스의 GPU 자원 등록·할당·Node 및 그룹 배치와 LLM Serving 운영을 먼저 익힌다. 이후 실제 Multi-GPU 환경에서 분산 추론의 계산·통신·메모리·성능을 검증하고 Kubernetes의 자원 관리와 Runtime의 GPU 사용·통신 책임을 구분한다.
