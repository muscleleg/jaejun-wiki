GPU 자원 등록과 Pod 할당

짧은 제목 · GPU 등록·Pod 할당

완료달성 기준 11 / 11

학습 후 할 수 있는 일GPU 게시부터 Pod 요청·배치·Pending까지 추적하고 실제 구성요소와 Fake 대체 범위를 설명한다.

학습 안내

이 학습이 필요한 이유
GPU를 사용하는 Kubernetes의 출발점은 실제 연산보다 장치 게시·요청·배치의 책임을 구분하는 것이다.
완료 후 이어지는 일
GPU 요청 크기·Node 조건·자원 부족을 바꾸는 배치 실험을 수행한다.
학습 내용 자세히 보기

핵심 질문: GPU는 어떻게 Kubernetes 자원이 되어 Pod에 할당되는가? 개념·실습 흐름 구성요소의 역할을 먼저 배우고 멀티노드 Minikube·Fake GPU Node Pool을 만든다. GPU 게시 → Capacity/Allocatable → Pod 요청 → 배치 → 자원 소진 시 Pending을 추적한다. Fake GPU Metric과 실제 하드웨어 관측의 차이를 설명한다. Allocatable이 예약 후 남은 GPU 수처럼 자동 감소한다고 해석하지 않는다. 실험과 달성 기준 연결 구성요소 설명과 Fake/실제 경계는 달성 기준 10~11, 멀티노드·Pool 구성은 1~6, GPU 게시·요청·소진 실험은 7~9와 연결한다. 실행 조건과 검증 경계 Apple Silicon에서는 Docker Driver와 ARM64 이미지를 사용하고 기존 프로필과 분리한 학습용 프로필을 선택한다. 단일 노드는 예비 실습일 뿐이며 이 학습 단원의 완료에는 Control Plane 1개와 Worker 2개 이상, 서로 다른 Fake GPU Pool이 필요하다. CUDA 연산 대신 CPU 컨테이너를 실행한다. Allocatable 총량을 예약 후 남은 수량으로 해석하지 않는다.

    Docker Driver로 Minikube Control Plane 1개와 Worker 2개를 구성하고 모든 Node의 Ready 상태와 동일 Mac에서 실행되는 Node Container 구조를 확인했다. ARM64 Image 호환성을 검사한 뒤 Fake GPU Operator v0.2.0을 설치하고, gpu-lab-m02에는 A100 40GB 2개, gpu-lab-m03에는 T4 16GB 1개를 서로 다른 Node Pool로 설정했다. Fake Device Plugin이 각 Node의 kubelet에 등록되는 Log와 nvidia.com/gpu Capacity·Allocatable 2개·1개 게시 결과를 확인했다. BusyBox Pod에 nvidia.com/gpu: 1을 요청해 Scheduler의 Node 배치와 Device Plugin의 논리 장치 할당을 확인했고, 세 GPU를 모두 예약한 뒤 네 번째 Pod에서 Insufficient nvidia.com/gpu FailedScheduling과 Pending을 재현했다. 실행 중인 Pod 하나를 삭제하자 예약이 반환되고 Pending Pod가 다시 배치되는 과정도 확인했다. Fake Metric의 GPU Utilization과 Framebuffer 값은 Annotation과 가상 Topology에서 만든 합성값이며 실제 CUDA 연산·VRAM·DCGM Hardware Metric의 근거가 아님을 구분했다. 실제 환경에서는 물리 GPU·Driver·NVML·NVIDIA Device Plugin·kubelet·API Server·Scheduler·Container Runtime이 이어지고, Fake 환경은 물리 장치 발견과 실제 Container GPU 주입을 대체한다는 책임 경계를 설명했다.
