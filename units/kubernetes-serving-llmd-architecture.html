Controller Reconcile과 Serving 복구

짧은 제목 · Reconcile·복구

완료달성 기준 9 / 9

학습 후 할 수 있는 일원하는 상태와 실제 상태의 차이를 Controller가 복구하는 과정을 HTTP 상태와 분리해 설명한다.

학습 안내

이 학습이 필요한 이유
실제로 배포한 서버를 변경·삭제해 보아야 Controller의 관리 흐름과 요청 처리 흐름의 차이를 설명할 수 있다.
완료 후 이어지는 일
그룹 복구와 요청 경로를 제어 흐름·데이터 흐름으로 구분한다.
학습 내용 자세히 보기

핵심 질문: 선언한 서버 수와 실제 상태가 다르면 누가 어떻게 복구하는가? 개념·실습 흐름 Controller·Control/Data Plane과 Reconcile(원하는 상태와 실제 상태를 맞추는 과정)을 설명하고 관리 흐름과 요청 흐름을 각각 그린다. Controller가 감시·생성하는 리소스, Replica 수 결정 주체를 확인한다. Pod를 제거하고 Desired/Current/Ready·Restart·Metric/Event/Log·복구를 관찰한다. 관리 리소스의 정상 상태와 HTTP 응답 성공을 따로 검증한다. 실험과 달성 기준 연결 Controller 책임과 관리/요청 흐름 설명은 달성 기준 4~7, Pod 삭제 전후 상태·복구 관측은 1~3 및 8, Reconcile과 HTTP 상태의 교차 비교는 9와 연결한다. 실행 조건과 검증 경계 여기서는 배포한 서버의 최소 HTTP 요청 흐름과 관리 흐름을 비교한다. Gateway·EPP를 실제 연결한 뒤 요청 경로 학습 단원에서 전체 흐름을 확장한다.
