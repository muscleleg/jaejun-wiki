    `diffs`·`times`가 같은 인덱스의 순서 있는 퍼즐 목록이고, 숙련도는 입력이 아니라 제한 시간 안에 끝내기 위해 찾아야 할 최소 후보임을 다시 해석했다. 현재 퍼즐 실패 뒤 이전 퍼즐을 다시 푸는 벌칙과 마지막 성공에는 이전 시간이 붙지 않는 순서를 풀어 쓰고, `diff-level`이 문제에서 직접 정의한 실패 횟수임을 확인했다. 후보 숙련도마다 전체 시간을 Simulation하고 `total<=limit`이면 더 낮은 숙련도를 찾는 경계를 구현했으며, `total==limit`을 실패로 처리한 조건을 수정해 프로그래머스 제출에 통과했다. 두 문제의 자료 없는 재구현과 복잡도 설명은 지연 복습으로 등록했다. `n=6`, `times=[7,10]`에서 후보 시간마다 `sum(T // time)`으로 처리 인원을 계산하고, 판정이 `불가능 → 가능`으로 단조롭게 변하는 경계를 추적했다. 중간값은 심사관 수가 아니라 남은 시간 후보 범위를 나누는 값이며, 폐구간에서 `mid - 1`·`mid + 1`은 이미 검사한 정수 후보를 제외하는 이동이라고 정리했다. 반복 중 `left`보다 작은 값은 불가능하고 `right`보다 큰 값은 가능하다는 의미를 연결해, 교차 뒤 `left`가 최초 가능 시간으로 남는 코드를 다시 구현하고 프로그래머스 제출에 통과했다. 같은 패턴의 독립 전이와 복잡도 재설명은 다음 확인으로 남겼다. 마지막 위치 Logit의 전체 Vocabulary에서 `torch.topk()`로 점수가 큰 후보 10개와 그 후보의 실제 Token ID를 함께 가져왔다. `softmax(top_values)`는 이 10개 안에서만 선택 비중을 다시 만들고, `torch.multinomial()`은 실제 Token ID가 아니라 Top-k 목록 안의 임시 위치를 반환한다. 따라서 `torch.gather(top_token_ids, ..., selected_top_positions)`로 그 임시 위치에 대응하는 실제 Vocabulary Token ID를 꺼낸다는 흐름을 설명했다. `top_token_pieces`는 사람이 후보를 읽기 위한 표시용이며 생성 계산에는 필요하지 않다고 구분했다. Token 선택 부분만 Top-k로 바꾸고, 선택한 ID를 `torch.cat()`으로 기존 입력 뒤에 붙여 다시 Forward하는 자기회귀 반복 구조는 Temperature Sampling과 같다고 확인했다. Temperature는 전체 후보의 격차를 조절하지만, Top-k는 그 전에 후보 수를 상위 `k`개로 제한한다는 차이를 실제 생성 루프에 연결했다. Vocabulary 선택 비중을 큰 순서로 정렬하고 누적합이 `top_p`를 넘는 위치를 제거 Mask로 만들었다. `remove_mask[:, 1:] = remove_mask[:, :-1].clone()`은 기존 Mask를 오른쪽으로 한 칸 밀어 임계값을 처음 넘게 만든 경계 후보까지 남기기 위한 처리라고 이해했다. 이 이동이 없으면 누적합을 임계값 위로 처음 올려 준 후보까지 제거될 수 있으므로 단순히 한 칸만 뒤집는 방식보다 Batch마다 다른 경계를 동일한 Tensor 연산으로 처리하는 이유를 설명했다. `masked_fill(remove_mask, 0.0)`으로 제외 후보의 선택 비중을 0으로 만들고, 남은 값들을 합으로 나눠 전체 합이 다시 1이 되도록 조정했다. `multinomial()`이 정렬된 후보 목록 안의 위치를 뽑고 `gather(sorted_token_ids, ...)`가 실제 Token ID로 바꾸는 순서를 설명했다. `(~remove_mask).sum(dim=-1)`은 제거 여부를 반전한 뒤 각 Batch에서 남은 후보 수를 세는 진단값이라고 확인했다. Causal LM의 Logit `[B,S,V]`와 Shift된 Target은 각 Batch의 각 다음 Token 위치를 하나의 분류 문제로 만든다. 각 위치에서 정답 Token에 배정된 선택 비중 `p`의 Loss는 `-ln(p)`이고, 전체 `B×(S-1)`개 Token Loss를 평균한 scalar 하나가 기본 `CrossEntropyLoss`와 `outputs.loss`라는 점을 다시 연결했다. Accuracy처럼 최댓값 ID의 일치만 보는 것이 아니라 정답 칸에 얼마나 강한 비중을 주었는지를 연속적인 값으로 채점한다고 구분했다. MSE의 `(출력-정답)²`과 Cross Entropy의 `-Σ(yᵢ×ln(pᵢ))`를 분리했다. 정답 Token ID가 7이면 One-hot Target에서 7번만 1이고 나머지는 0이므로 모든 0 항이 사라져 `-ln(p₇)`만 남는다. `p₇=0.4509`이면 Loss가 약 `0.7966`이며, PyTorch는 이 계산을 위해 One-hot 전체 대신 정답 열을 가리키는 Token ID를 받는다고 이해했다. `Perplexity = exp(평균 Token Cross Entropy)`이므로 Loss가 0이면 1이고 Loss가 커질수록 Perplexity도 커진다고 확인했다. `"I study."`에서는 첫 Token 자체를 채점하는 것이 아니라 `I→study`, `I study→.`처럼 다음 Token 두 위치를 채점한다. 실행한 평균 Token Loss `10.831886`을 지수 변환해 Perplexity `50609.078`을 얻었으며, 이 한 문장 결과만으로 모델 전체 품질을 단정하지 않는 해석 경계도 남겼다. `save_pretrained()`로 Tokenizer의 문자열↔Token ID 규칙과 Model의 설정·Embedding·Transformer·LM Head Weight를 각각 저장하고, 별도 객체에서 `local_files_only=True`로 복원했다. 이번에는 파인튜닝하지 않은 원본을 그대로 저장했다가 불러온 비교이므로 Token ID `[[40,2050,13]]`, Logit Shape `[1,3,50257]`, Loss와 Perplexity가 동일한 것이 정상이라고 설명했다. 저장은 현재 학습 성과를 과장하기 위한 것이 아니라 이후 로컬·오프라인·RunPod 환경에서 같은 Artifact를 재사용하고 비교하기 위한 기반이라고 구분했다. Tokenizer·동적 Padding·Attention Mask, 사전학습 Model Forward, Batch별 마지막 실제 Token Logit, Greedy·Temperature·Top-k·Top-p 수동 생성, Cross Entropy·Perplexity 평가, Model·Tokenizer 저장·복원까지 직접 실행하고 핵심 Shape과 선택 과정을 설명했다. 이 증거로 사전학습 Causal LM 적용 관문을 완료했고, 다음 관문은 같은 모델·Prompt 조건에서 No-cache와 KV Cache, Batch 1과 Batch N을 비교하는 PyTorch 추론 Baseline이다. 같은 활동에 관해 기존 복습 기록에 남아 있던 검증 요약 (새 활동·추가 시간 아님) 입국심사와 퍼즐 게임 챌린지에서 후보별 가능 판정과 최초 가능 경계를 구현해 프로그래머스 제출에 통과했으며, 문제 독해와 등호 경계는 설명을 받아 교정했습니다. Top-k·Top-p 생성 루프를 실행하고 후보 내부 위치를 gather로 실제 Token ID로 복원했습니다. p=0.4509의 Loss 약 0.7966을 계산하고 고정 텍스트의 평균 Loss 10.831886·Perplexity 50609.078을 실행했습니다. Tokenizer와 Model을 저장한 뒤 별도 프로세스에서 로컬 전용으로 복원해 Token ID·Logit Shape·Loss 일치를 확인했습니다.
