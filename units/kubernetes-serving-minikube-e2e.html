핵심 질문: 부하 증가부터 Queue 회복까지 인과관계를 입증할 수 있는가? 개념·실습 흐름 전체 Architecture·Resource 관계·Request Sequence·통합 Dashboard를 구성하고 모든 계층의 Metric 수집을 확인한다. Request Rate·Endpoint Health·EPP Endpoint Selection을 같은 시간축에서 대조해 요청량과 후보 상태 변화가 선택에 어떻게 연결되는지 관찰한다. 부하 → Queue → EPP 선택 → Autoscaling → Scheduling → Running/Ready → Endpoint 등록 → Reject/Failure → 회복을 같은 시간축으로 기록하고 운영 병목 가설 하나를 검증한다. 상위 Multi-GPU 설정부터 요청 성공까지 추적하며 자원 단편화 또는 배치 조건 실패까지 통합한다. 실험과 달성 기준 연결 Architecture·리소스·요청 관계, 계층별 Metric 수집, Request Rate·Health·선택의 동시 관측, 부하·과부하·병목 가설, GPU 요청→배치→응답 및 배치 실패를 각 달성 기준과 연결한다. 실행 조건과 검증 경계 낮은 Replica와 부하를 사용해도 요청·라우팅·수용 제어·확장·배치·관측의 연결은 실제 유지한다. 구성요소를 따로 실행한 결과의 합으로 통합 실험을 완료하지 않는다. 자원이 부족하면 검증 가능한 환경을 확보할 때까지 해당 기준을 미충족으로 둔다.

    한쪽 대기열 0/17을 확인한 뒤, 모델 Pod 직접 부하 경로 18081과 Gateway·EPP 선택 경로 18080을 구분해 후속 비교를 진행했다. Deployment뿐 아니라 Service 포트포워딩도 한 세션은 Pod 하나에 고정되며, Gateway 포워딩은 그 이후 EPP를 거쳐 모델 목적지가 선택된다는 점을 확인했다. 시뮬레이터 동시 처리 제한 1개·첫 토큰 지연 5초와 Queue 단독 정책에서, 같은 약 105초 관측 구간에 hdzml의 Queue 0·jv57n의 Queue 4가 유지되는 동안 성공 선택 카운터는 hdzml 4→10, jv57n 6→6이었다. 부하가 작은 후보의 선택 증가를 대기열과 같은 구간에서 대조했다. 직접 경로와 Gateway 경로에 각각 병렬 5개·순차 8회의 부하를 동시에 주었을 때 양쪽 Queue 4/4도 확인했다. 정확한 반반 분배나 서버 처리 능력 증가로 해석하지 않았다. 단일 HTTP 200과 선택 Counter 증가가 있어도 짧은 요청은 Queue Gauge에 포착되지 않을 수 있고, Endpoint 라벨은 HTTP 경로가 아니라 모델 Pod라는 점을 구분했다. Request Rate·Endpoint Health·선택의 세 시계열을 같은 시간축에 모두 대조한 자료는 남기지 않았다.

    Ready는 후보 자격이고 후보 간 우선순위를 정하지 않는다는 점에서 출발해, 기존 두 모델 서버를 유지하며 Queue와 Prefix를 바꾸어 요청 목적지가 달라지는 흐름을 설명했다. 일반 Round Robin의 순번 선택과 EPP의 서버 상태·요청 재사용 가능성 기반 선택을 구분했다. 일반 부하분산에도 부하 기반 정책은 있으므로 LLM-aware만 부하를 본다고 일반화하지 않았다. Kubernetes Scheduler는 Pod의 Node 배치를, EPP는 이미 배치된 Endpoint 중 요청 목적지를, 추론 엔진은 받은 요청의 Batch·Token 실행을 결정한다. 시뮬레이터 인수 변경으로 ReplicaSet과 Pod가 교체된 Deployment 롤아웃과, 같은 후보 안에서 요청 선택 Counter가 증가한 라우팅을 구분했다. 앞서 두 Ready Pod의 Node 기준선을 확인했고 이후 Pod 교체와 후보 선택은 관찰했지만, 의도적인 Node 재배치 전후의 리소스·Log와 동일 부하를 통제한 대조는 완결하지 않았다. Mock Endpoint 선택 결과를 실제 GPU 재할당·계산 성능 개선으로 해석하지 않는다.
