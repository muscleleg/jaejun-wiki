과부하·Admission과 두 종류의 대기

선수 대기달성 기준 0 / 12

학습 후 할 수 있는 일HTTP 요청 대기와 GPU Scheduling 대기를 구분하고 Admission 전후 성공·거부·실패를 비교한다.

학습 안내

이 학습이 필요한 이유
정상 요청 전달을 확인한 다음 수용 한계와 대기를 만들어야 Admission·Queue·Scheduling의 책임을 구분할 수 있다.
완료 후 이어지는 일
Cancellation·Retry와 Autoscaling 신호를 대기 계층별로 검증한다.
학습 내용 자세히 보기

핵심 질문: 요청을 받을지 결정하는 것과 어디로 보낼지 결정하는 것은 어떻게 다른가? 개념·실습 흐름 인증 → Admission(요청 수용 제어) → Queue → Endpoint 선택 → Runtime을 연결하고 각 계층의 대기를 구분한다. 부하 및 Queue/Admission Limit을 바꾸며 Running/Waiting/Queue/Reject·Status와 성공/Reject/Failure/Timeout 기반 Goodput을 비교한다. 추가 서버가 GPU 부족으로 Pending일 때 기존 서버를 과부하시켜 Pod Scheduling 대기와 HTTP 요청 대기를 같은 시간축에서 관찰한다. 실험과 달성 기준 연결 계층·요청 흐름 설명은 달성 기준 1·3·9, 부하·Queue·제한 유무 비교는 2·4~7, Goodput·시간축·모의 경계는 8·10~11, GPU Pending과 HTTP 대기의 결합 실험은 12와 연결한다. 실행 조건과 검증 경계 Admission과 Queue의 구현 위치를 명시하고 Mock이 지원하지 않는 상태를 있다고 가정하지 않는다. 필요한 부하·지연·거부 조건을 구현한 테스트 구성으로 검증하되 Synthetic 값임을 표시한다.

미충족

Fake GPU 환경에서 쿠버네티스의 GPU 자원 등록·할당·Node 및 그룹 배치와 LLM Serving 운영을 먼저 익힌다. 이후 실제 Multi-GPU 환경에서 분산 추론의 계산·통신·메모리·성능을 검증하고 Kubernetes의 자원 관리와 Runtime의 GPU 사용·통신 책임을 구분한다.
