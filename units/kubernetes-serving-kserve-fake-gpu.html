KServe 배포와 GPU 요청 전달

KServe 설정에서 Pod GPU 요청·Node 배치·HTTP 응답까지 추적하고 조건 불일치를 복구한다.

학습 안내

짧은 제목 · KServe 배포·GPU 요청

완료달성 기준 14 / 14
이 학습이 필요한 이유
GPU 배치와 기본 관측을 HTTP 응답하는 서버에 연결해야 추상적인 Serving 리소스 관계를 실제 상태로 확인할 수 있다.
완료 후 이어지는 일
Controller Reconcile과 서버 복구를 실제 Pod·HTTP 응답으로 관찰한다.
학습 내용 자세히 보기

핵심 질문: Serving 설정은 어떻게 GPU를 요청하는 Pod와 응답하는 API가 되는가? 개념·실습 흐름 KServe·CRD·Controller의 최소 역할부터 설명하고 Mock API와 Synthetic Metric 노출·수집을 준비한다. Deployment와 InferenceService를 비교해 배포하고, HTTP 응답·Request Rate·Status와 상위 CRD부터 Pod까지 관계를 확인한다. 상위 InferenceService에 선언한 GPU 요청이 생성된 Deployment와 Pod까지 전달되는지 추적한다. GPU 부족 또는 Taint 불일치로 Pending이 발생하면 상위 Status와 Pod Event를 함께 해석하고, GPU를 점유하던 Workload의 종료처럼 실제 원인을 해소한 뒤 재배치되는 과정까지 확인한다. Mock 지연의 해석 한계도 기록한다. 실험과 달성 기준 연결 Mock·Deployment·KServe 배포는 달성 기준 1~5, HTTP 응답·관측은 6~7 및 14, CRD→Pod 관계는 8~9, 모의 성능 경계는 10~11, GPU 요청 전달과 Pending 진단·복구는 12~13과 연결한다. 실행 조건과 검증 경계 모델 가중치 없이 CPU에서 실제 HTTP 요청을 처리하는 ARM64 Mock을 사용한다. 선택한 버전의 지원 기능을 확인하고 후속 Queue·Streaming·취소 실습에 필요한 동작을 갖춘다. Pod 상태만 모의하는 노드로 HTTP 실행을 대신하지 않는다.
