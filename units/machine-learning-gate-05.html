    AI·ML·딥러닝, LLM 응용, 데이터 엔지니어링·MLOps, Knowledge Graph·GraphRAG·Ontology·Agent Harness 커리큘럼을 현재 1차 학습 순환과 대조했다. 기본 ML·PyTorch·Transformer, CV·시계열·이상탐지·추천 후보는 기존 로드맵에 이미 포함되어 있어 중복 추가하지 않았다. 독립적인 결과물과 완료 조건이 필요한 [MLOps·모델 운영](roadmaps/roadmap_mlops.html)과 [Knowledge Graph·GraphRAG·Agent Harness](roadmaps/roadmap_knowledge_agents.html)만 1차 순환 이후 선택할 확장 로드맵으로 분리했다. 이번 기록은 학습 방향 설계이며 해당 확장 역량을 완료했다는 뜻은 아니다. 표 데이터 파이프라인에서 `Churn` 라벨 정렬(`No=0, Yes=1`) 후 `ColumnTransformer`로 수치형/범주형을 통합 전처리해 NumPy `(5634,45)`·`(1409,45)`를 Tensor화했고, `TensorDataset` + `DataLoader`로 Batch 학습을 구성했다. `Linear(45,16) → ReLU → Linear(16,1)` 모델에서 Batch는 64명 단위이며 Batch Loss는 각 샘플 BCE의 평균으로 계산한다는 점, 에포크마다 모든 배치 누적 후 평균을 기준으로 진척을 봄을 확인했다. 모델 출력 `logits`는 제한이 없고, 학습/해석 단계에서 `sigmoid`를 통과해 `0~1` 구간 score로 본다는 흐름을 정리했다. 사용자와 함께 BCE 식을 샘플 단위로 추적해 보며, MSE와 BCE의 차이를 구분했고(둘 다 평균이지만 계산 항이 다름), 현재는 이진 분류의 기본 관점(임계값 0.5 기준)으로 `Yes/No` 판정을 다루었다. `SGD(model.parameters(), lr=0.1)` 루프에서 `zero_grad → forward → BCE → backward → step` 순서를 직접 확인했고, 한 번의 step 후 loss가 내려가는 모습을 봤다. `loss.backward()`는 현재 배치 기준 기울기(.grad)를 쌓고, `step()`에서만 weight·bias가 실제 이동한다는 연결을 유지했다. 또한 `valid`에서 손실/accuracy를 함께 보고 과적합 가능성 판단을 준비했다. 학습된 모델 파라미터는 `state_dict`로 저장·복원 가능하고, 로드 후 동일 입력에 대해 `torch.allclose`로 출력 일치 체크를 해서 복원 신뢰성을 점검했다. 단일 고객 추론 시에도 동일 전처리 기준을 `transform` 후 텐서화해 `sigmoid`까지 확인하면서 배치 학습/단일 예측 경로의 일관성을 맞췄다.

    회원 이탈 데이터에서 고정 Batch를 외우는 실험과 전체 데이터를 학습하는 실험을 분리했다. 별도의 overfit_model을 같은 Batch로 10,000번 수정해 Loss를 0.6944166422에서 0.0006966530까지 낮췄다. 같은 Batch의 Accuracy는 100%였지만 Validation Accuracy는 71.19%였다. 같은 입력을 잘 외운 결과를 전체 고객에 대한 일반화로 판단하지 않았다. 새 train_model을 만들어 전체 Train DataLoader를 20 Epoch, 총 1,780번 수정했다. 마지막 Epoch의 평균 Loss는 0.4128111020이었다. 학습에 사용한 45개 Feature 전처리와 Train/Validation 분할을 유지하고, 가중치를 수정하지 않는 평가에서 Validation 1,409명 중 1,113명을 맞혀 Accuracy 78.99%를 얻었다. 실제 이탈자 374명 중 133명을 찾아 Yes Recall은 35.56%였으며, 놓친 이탈자는 241명이었다. 같은 데이터 분할·전처리 기준의 Logistic Regression Accuracy 80.55%·Yes Recall 55.88%보다 낮았다. 모델이 복잡해져도 성능이 자동으로 좋아지지 않으며, 전체 정답 비율과 이탈자를 놓치는 문제를 따로 비교해야 한다. 고정 Batch 암기용 모델과 전체 학습·평가용 모델은 서로 다른 객체로 실험했다. 이 수치는 Notebook에 저장된 실행 결과이며, 초기화 Seed를 고정하지 않아 재실행 시 정확히 같은 수치를 보장하지 않는다.

    `decision_function()`의 제한 없는 원시 점수에 sigmoid를 적용하면 `predict_proba()`의 Yes 확률과 같아지는 것을 확인했다. 기본 Threshold `0.5`에서는 Yes 318명, `0.3`에서는 Yes 543명을 예측했으며, 기준을 낮추면 Yes Recall은 `55.88% → 75.40%`로 오르고 Precision은 `65.72% → 51.93%`로 내려가는 trade-off를 읽었다. `y=df["Churn"]`은 No·Yes 정답을 가진 Pandas Series이고, `fit(X_train,y_train)`이 이 정답 클래스를 모델에 전달한다는 점을 확인했다. Pipeline은 Tree가 전처리까지 스스로 하는 모델이 아니라 `원본 X → 전처리기 → 모델` 호출 순서를 묶는 관리자이며, `named_steps["model"]`은 그 안에서 학습된 모델 객체를 꺼내는 문법이다. 각 노드는 현재까지 같은 답을 따라온 고객 묶음이고, 45개 Feature는 45개의 트리가 아니라 각 노드에서 시험할 질문 후보임을 정리했다. 숫자 경계 질문마다 No·Yes가 얼마나 덜 섞이는지 Gini로 비교해 하나를 고르고, 더 나누지 않는 잎에서는 다수 Label을 최종 No·Yes로 낸다. `get_depth()`는 가장 긴 질문 경로, `get_n_leaves()`는 깊이가 달라도 모든 최종 잎의 개수다. 제한 없는 Tree는 깊이 22·잎 1,106개, Train `99.8048%`·Validation `72.8886%`로 Train을 거의 외운 과적합 상태였다. `max_depth=3`은 Validation `78.2115%`, 깊이 5는 `79.8439%`, 깊이 7은 `78.6373%`, `min_samples_leaf=10`은 `76.7211%`였다. Train 점수가 내려가더라도 Validation이 오르면 처음 보는 데이터에는 더 나아진 모델일 수 있음을 확인했다. Logistic Regression은 Feature의 가중합으로 경계를 만들고 Tree는 조건 질문을 이어 비선형 구간을 만든다는 차이를 정리했다. 같은 Split과 Metric에서 시험한 Tree 중 깊이 5가 가장 좋았지만 Logistic Validation `80.5536%`보다 낮았다. 또한 깊이 5 Tree의 Yes Recall은 약 `0.57`이므로 Accuracy만 보면 실제 이탈자를 많이 놓치는 문제를 숨길 수 있다는 점을 확인했다. 데이터 품질·분할·Dummy·One-Hot과 StandardScaler·Logistic 평가·Threshold·DecisionTree 과적합과 제한 비교까지 완료했다. 다음 활성 학습은 PyTorch `nn.Module`과 Optimizer로 `y=3x+2` 학습 루프를 구현하는 것이며, 그 뒤 Tiny Decoder LM으로 복귀한다. 같은 활동에 관해 기존 복습 기록에 남아 있던 검증 요약 (새 활동·추가 시간 아님) Threshold 0.5→0.3에서 Yes Recall 55.88%→75.40%, Precision 65.72%→51.93% 변화를 읽고 비용 기준을 설명했습니다.
