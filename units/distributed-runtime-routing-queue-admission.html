    Routing은 목적지를, Queue는 지금 전달할 자리가 없을 때의 기다림을, Admission은 더 받아들일지를 결정한다. 기본 구성에서는 별도 실험용 서버 연결 한도 없이 동시 8·32·128개를 처리했다. 이후 서버별 maxconn=2로 전체 전달 자리 4개를 제한하고 12개를 동시에 보내 설정된 처리 자리의 포화를 재현했다. A/B 연결은 2개씩 유지되고 HAProxy 공통 Queue는 8→4→0으로 줄며 요청 네 개씩 약 3.2·6.4·9.6초에 완료됐다. 이는 GPU의 물리적 포화점을 찾은 실험이 아니라 프록시가 정한 수용 용량 초과 실험이다. timeout queue를 60초에서 1초로 바꾸자 4개는 약 3.2초에 200, 대기 요청 8개는 약 1초에 503이었다. IP별 10초 유입량 기준 Admission에서는 0.1초 간격의 12개 중 4개가 200, 8개가 약 1~2ms에 429였다. 유입률 제한은 동시성 한도나 GPU 부하 기반 제어가 아니다. 대기 후 실패와 즉시 거절을 비교했고 두 실험의 유입 조건이 달라 동일 부하 성능 우열로 해석하지 않았다. Queue Depth·E2E·Throughput과 성공·거절 수를 보존했다. Queue Time은 완료 패턴으로 해석했으며 요청별 직접 측정과 TTFT 측정은 하지 않았다. Goodput은 지연 목표까지 만족한 정상 완료 수를 측정 구간으로 나누며 거절을 성공에 포함하지 않는다는 점을 정리했다. 다만 거절을 포함한 실측 Goodput 수치는 계산하지 않았다.

A/B 연결은 2개씩 유지되고 HAProxy 공통 Queue는 8→4→0으로 줄며 요청 네 개씩 약 3.2·6.4·9.6초에 완료됐다. 이는 GPU의 물리적 포화점을 찾은 실험이 아니라 프록시가 정한 수용 용량 초과 실험이다. timeout queue를 60초에서 1초로 바꾸자 4개는 약 3.2초에 200, 대기 요청 8개는 약 1초에 503이었다. IP별 10초 유입량 기준 Admission에서는 0.1초 간격의 12개 중 4개가 200, 8개가 약 1~2ms에 429였다. 유입률 제한은 동시성 한도나 GPU 부하 기반 제어가 아니다. 대기 후 실패와 즉시 거절을 비교했고 두 실험의 유입 조건이 달라 동일 부하 성능 우열로 해석하지 않았다. Queue Depth·E2E·Throughput과 성공·거절 수를 보존했다. Queue Time은 완료 패턴으로 해석했으며 요청별 직접 측정과 TTFT 측정은 하지 않았다. Goodput은 지연 목표까지 만족한 정상 완료 수를 측정 구간으로 나누며 거절을 성공에 포함하지 않는다는 점을 정리했다. 다만 거절을 포함한 실측 Goodput 수치는 계산하지 않았다.

    긴 Streaming 요청의 첫 내용 수신 후 클라이언트 연결을 닫았다. 처리 서버의 Running이 1에서 종료 후 첫 2초 표본에 0으로 내려가고 이후 10초까지 양쪽 Running·Waiting이 0임을 확인했다. 생성 중 취소 전파는 관측했지만 프록시 Queue 대기 중 취소 제거는 실험하지 않았다. 다른 Streaming 요청에서 첫 내용을 받은 뒤 선택된 서버 A를 SIGINT로 중단하자 HTTP 200으로 시작한 응답이 finish_reason과 [DONE] 없이 TimeoutError로 끝났다. HAProxy는 A를 DOWN/L4CON, B를 UP/L7OK로 판정했고 새 요청 네 개는 B에서 정상 완료됐다. A를 재시작해 두 서버가 UP/L7OK가 된 뒤 새 요청 네 개는 B,A,B,A에서 완료됐다. 신규 요청 가용성 회복은 기존 Stream 복구가 아니다. 의도적으로 닫힌 목적지와 정상 B를 후보로 두고 재시도 없음/연결 실패 1회 재시도를 비교했다. 전자는 503 2개와 200 2개, 후자는 200 4개였으며 재분배 카운터가 4 증가했다. 재시도 카운터 0을 복구 없음으로 해석하지 않고 같은 서버 재시도와 다른 서버 재분배의 집계 경로를 구분했다. 연결 수립 전 실패와 이미 생성이 시작된 실패의 재시도 위험이 다르며, 무조건 재전송하면 중복 생성과 Stream 연속성 문제가 생긴다는 경계를 설명했다.
