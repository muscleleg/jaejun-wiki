    이전 풀이를 보지 않고 양방향 인접 리스트, `distance` 무한대 초기화와 `distance[1]=0`, Heap 반복, 낡은 후보 확인, 거리 완화와 `K` 이하 개수 계산까지 다시 구성했다. 처음에는 Heap Tuple 순서와 다음 후보에 전달할 도로 하나의 비용·누적 비용을 혼동했지만, `heapq`가 Tuple의 첫 값부터 비교하므로 표준 다익스트라는 `(new_cost, next_village)`를 저장해야 한다고 교정했다. 누적 비용을 보존한 채 마을 번호를 첫 값으로 두면 반복 완화로 수렴할 수 있어도 비용 우선 탐색과 효율성 보장을 잃는다는 차이도 설명했다. `heapq.heappop(heap)` 호출과 변수명 오타를 함께 수정했다. 제시한 제출 화면에서 같은 표준 코드의 프로그래머스 정확성 `100점`과 전체 `32개` 테스트 통과를 확인했다. 화면의 성공 제출 시각은 이전 날짜로 표시되므로 이번 학습일의 새 제출 시각으로 기록하지 않는다. 일반 BFS는 이동 단계만 최소화하므로 서로 다른 도로 비용의 최소 누적 비용을 보장하지 못한다는 점, 더 비싼 후보는 이후 양수 비용을 더해도 유리해질 수 없어 다시 넣지 않는다는 점을 설명했다. 시간 복잡도에서는 마을 수 `V`와 도로 수 `E`가 서로 다른 기준이며, Heap 삽입과 삭제는 각각 `O(E log V)`로 더한다는 점을 확인했다. 일반식 `O((V+E) log V)`에서 모든 마을이 거의 연결된 경우에만 `E≈V²`를 대입해 `O(V² log V)`가 된다고 자기 말로 정리했다. 핵심 Tuple 상태는 힌트로 교정했으므로 힌트 재구현 성공으로 기록하고, 9월 3일 무자료 복습은 유지한다. 처음에는 각 행의 최댓값 하나를 고르는 그리디와 모든 경로를 Queue에 넣는 BFS를 생각했지만, 같은 열을 연속 선택할 수 없어 현재의 최댓값 하나만 남기면 이후 선택을 보장할 수 없다고 교정했다. 같은 도착 열의 여러 경로는 이후 선택 조건이 같으므로 최고 누적점수 하나로 압축하고, 네 열의 상태는 모두 유지하는 DP로 전환했다. `ac_value`를 이전 행 열별 최고 누적점수, `next_value`를 현재 행 열별 최고 누적점수로 구분했다. 각 열 `i`에서 `ac_value[:i] + ac_value[i+1:]`로 이전 행의 같은 열을 제외하고 `row[i] + max(...)`를 새 배열에 넣은 뒤, 행 계산이 끝난 시점에만 `ac_value = next_value`로 교체하는 코드를 직접 완성했다. 처음처럼 현재 `row`를 필터링하거나 누적 배열을 계산 도중 갱신하면 이전 행과 현재 행의 상태가 섞인다는 점을 자기 말로 설명했다. 프로그래머스에서 정확성 `59.8`, 효율성 `40.2`, 합계 `100/100`으로 정확성 18개와 효율성 4개 테스트를 모두 통과했다. 처음에는 중첩 반복문을 보고 `O(N²)`로 판단했지만 열이 항상 4개라 본문 실행 횟수가 약 `4N`이고 시간 복잡도는 `O(N)`이라고 교정했다. `land[1:]`가 새 바깥 List를 만들어 추가 공간 `O(N)`을 쓸 수 있다는 점을 확인하고, `range(1, len(land))` 인덱스 순회로 바꿔 길이 4의 두 DP 배열과 길이 3 후보만 남기면 추가 공간 `O(1)`이 된다고 설명·적용했다. 상태 설계·제출·복잡도 증거를 확인해 첫 학습은 완료했지만 자료 없는 재구현과 후속 DP 문제는 남아 통합 관문을 진행 중으로 유지한다. 문제를 읽고 첫 행을 누적값으로 시작하며, 다음 행의 왼쪽 끝은 이전 행 `0`번, 가운데는 이전 `i-1`번과 `i`번 중 큰 값, 오른쪽 끝은 이전 `i-1`번을 더하고 마지막 행의 최댓값을 반환한다고 바로 설명했다. 이 상태 전이를 직접 구현했고, 최초 코드의 `i == len(row)`가 유효한 마지막 Index에서 절대 참이 되지 않는 문제를 `i == len(row)-1`로 교정했다. 가운데 위치의 두 부모 최댓값 계산, 행 완료 뒤 `ac_value = new_value` 교체, 한 행 입력에서도 정의되지 않은 `new_value`를 참조하지 않는 `return max(ac_value)`를 반영했다. 프로그래머스 정확성 10개와 효율성 10개, 총 20개 테스트를 모두 통과했다. 각 칸 계산은 `O(1)`이지만 땅따먹기의 고정 4열과 달리 행별 칸 수가 `1..N`으로 증가하므로 전체 칸 합과 중첩 반복 상한에서 시간복잡도는 `O(N²)`이라고 설명했다. `ac_value`와 `new_value`가 각각 최대 `N`개를 저장하고 약 `2N`개를 함께 보유해도 추가 공간은 `O(N)`이라고 답했다. 제출·상태 전이·복잡도 증거를 확인해 첫 학습은 완료했지만 자료 없는 재구현과 등굣길은 남아 통합 관문을 진행 중으로 유지한다. Batch 1과 Batch 4의 Prompt를 같은 모델에 넣어 첫 Layer Key Cache가 각각 `[1,2,2,1]`과 `[4,2,2,1]`이 되는 것을 실행했다. 이 Shape을 `[Batch,Head,Token,Head dimension]`으로 읽고, KV Cache는 Attention Head별로 이미 분리된 K·V를 Layer마다 보관하므로 마지막 Token의 Multi-Head Attention에서 바로 재사용할 수 있다고 설명했다. 일반 Python 타입만으로는 Tensor의 dtype·축 의미가 보이지 않는 문제를 줄이기 위해 `Int64[Tensor, "batch prompt_token"]`처럼 변수 옆에 `jaxtyping`을 제한적으로 적용했고, 실제 `.shape` 출력으로 표기와 실행 결과를 대조했다. 런타임 타입 검사는 아직 적용하지 않았다. 모델 호출 한 번에는 여러 문장을 행으로 가진 하나의 Batch Tensor가 들어가며, Token ID 단계는 `[문장 수, 문장별 Token 수]`, Embedding 뒤는 `[문장 수, 문장별 Token 수, Token 정보 차원]`이라고 정리했다. Batch 4는 Batch가 네 개라는 뜻이 아니라 한 Batch Tensor의 행이 네 개라는 점을 교정했다. Latency는 문장 하나의 시간이 아니라 그 호출에서 모든 행의 생성을 처리한 평균 전체 시간이고, Throughput은 `Batch 크기 × 생성 Token 수 ÷ 평균 전체 시간`으로 계산하는 초당 전체 Token 수라고 구분했다. `input_ids.to(device)`와 `attention_mask.to(device)`는 Tensor를 선택한 장치 메모리로 옮기는 코드이며, 이 호출 자체가 병렬 연산을 직접 작성하는 명령은 아니라고 구분했다. 모델과 입력이 CUDA 장치에 있으면 PyTorch가 연산 종류와 장치를 보고 CUDA Kernel로 디스패치하고, Kernel 내부에서 Batch·Token·행렬 원소의 작업을 GPU Thread에 나누어 실행한다는 흐름을 연결했다. 이번 실행 장치는 CPU였으므로 GPU 병렬 성능을 확인한 것은 아니며, H2D·D2H 복사·CUDA 비동기 실행·`synchronize` Timing은 이후 검증 항목으로 남겼다. 길이 2와 6인 문장을 하나의 Tensor로 만들기 위해 `padding_side="left"`와 EOS Padding을 사용하고, 짧은 문장 앞의 Padding 위치가 Attention Mask `0`이 되는 것을 확인했다. `attention_mask.cumsum(dim=-1)-1`은 실제 Token을 만날 때만 위치를 증가시키고, Padding에서 생기는 `-1`은 `masked_fill(attention_mask==0,0)`으로 보정한다고 설명했다. 새 Token 하나가 생성될 때는 문장마다 실제 Token을 뜻하는 `1`을 가진 `[B,1]` Mask를 만들어 기존 Mask 오른쪽에 붙이고, 누적합의 마지막 열 `[:, -1:]`로 다음 Position ID `[[2],[6]]`만 구했다. 첫 Forward에는 Prompt 전체를 넣어 Cache를 만들고, 후속 Forward에는 새 Token `input_ids [B,1]`과 그 Token의 `position_ids [B,1]`만 전달하되, 새 Query가 과거 K·V까지 조회할 수 있도록 `attention_mask [B,past+new]`는 전체 길이를 유지한다고 설명했다. `use_cache=False`이면 재사용할 `past_key_values`가 반환되지 않으며, Cache와 함께 새 Token을 두 개 이상 전달하는 것도 가능하고 그 구간의 K·V는 현재 Forward에서 순서대로 계산된다고 구분했다. 저장된 실습에서는 Forward 전후 Cache가 같은 `DynamicCache` 객체였고 새 Token의 K·V Tensor가 Token 축에 이어 붙은 결과 Sequence 길이가 `7→8`로 증가했다. 이는 길이 숫자만 바꾸는 동작이 아니라 K·V 내용의 확장임을 현재 설치 버전의 구현과 함께 확인했다. 길이가 다른 두 문장을 대상으로 첫 Forward에는 `[2,6]` Prompt 전체를 넣고, 이후에는 직전에 선택한 새 Token `[2,1]`과 Cache만 넣는 5-Step Greedy 생성 루프를 완성했다. `generated_ids`는 최종 Decode용 전체 ID를 누적하고 `step_input_ids`는 이번 Forward의 새 Token만 보관하도록 역할을 분리했으며, Cache 길이가 `6→10`으로 늘어나는 것을 확인했다. 수동 결과와 라이브러리의 `generate()` Token 생성 메서드가 Padding부터 새 Token 5개까지 전체 ID Tensor에서 `torch.equal(...)=True`임을 검증했다. 마지막으로 CPU tiny GPT-2에서 No-cache·KV Cache와 Batch 1·4를 조합해 출력 일치를 확인했고, Batch 1은 `23.082 ms/866.48 tokens/sec` 대 `15.488 ms/1291.32 tokens/sec`, Batch 4는 `26.701 ms/2996.09 tokens/sec` 대 `25.023 ms/3197.07 tokens/sec`로 측정했다. 이 수치는 작은 CPU 실험의 기준선이며 일반적인 GPU 향상률로 확장하지 않는다. 같은 활동에 관해 기존 복습 기록에 남아 있던 검증 요약 (새 활동·추가 시간 아님) 첫 행에서 시작해 왼쪽 끝·가운데·오른쪽 끝의 서로 다른 이전 후보를 누적 최댓값으로 전이하는 구조를 직접 설명·구현했습니다. 경계 Index, 가운데 max, 행 상태 교체와 한 행 입력 반환을 교정한 뒤 프로그래머스 정확성 10개·효율성 10개, 총 20개 테스트를 모두 통과했습니다. 행 길이가 1부터 N까지 증가해 시간 O(N²), 이전·현재 두 행 상태가 각각 최대 N개라 추가 공간 O(N)임을 설명했습니다. 자료 없는 재구현은 아직 남았습니다. 같은 도착 열의 경로를 최고 누적점수 하나로 압축하고 네 열 상태를 모두 유지하는 DP로 교정했습니다. 이전 행 배열에서 같은 열을 제외해 새 배열을 만든 뒤 교체하는 코드를 직접 완성했고, 프로그래머스 정확성 59.8·효율성 40.2로 합계 100점과 22개 테스트 전체 통과를 확인했습니다. 열이 4개로 고정되어 시간 O(N)이며 land[1:] 대신 인덱스로 순회하면 추가 공간 O(1)이라는 점을 설명·적용했습니다. 자료 없는 재구현은 아직 남았습니다. 배달 문제를 안내에 따라 처음 구현한 뒤 이전 코드를 보지 않고 인접 리스트·distance·Heap 반복·거리 완화·결과 계산을 다시 구성했습니다. Tuple 순서와 누적 new_cost 전달은 힌트로 교정했고, 표준 코드의 프로그래머스 정확성 100점·전체 32개 테스트 통과 증거와 BFS 비교·갱신 조건·복잡도 설명을 확인했습니다. 이전 코드를 보지 않고 인접 리스트·distance·Heap 반복·거리 완화·결과 계산을 다시 구성했습니다. Heap의 Tuple 순서와 누적 new_cost 전달은 힌트로 교정했으며, 표준 코드로 정확성 100점·32개 테스트 통과 증거를 확인했습니다. 일반 BFS와 가중치 최단경로의 차이, 개선되지 않은 경로를 다시 넣지 않는 이유, V·E 기준과 Heap 삽입·삭제를 합친 O((V+E) log V), 빽빽한 그래프에서 E≈V²를 대입한 O(V² log V)를 설명했습니다.
