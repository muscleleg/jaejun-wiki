    LLM을 실행하는 것과 여러 요청을 서비스하는 것은 다른 문제이며, Scheduler가 매 Engine Iteration마다 Waiting·Running 요청과 Token 작업을 다시 선택한다는 구조를 정리했다. Prefill과 Decode는 Scheduler 상태와 다른 계산 단계이고, 여러 요청의 Decode Token을 하나의 Batch로 묶어 GPU에서 함께 처리할 수 있음을 확인했다. Static Batching은 Batch 구성원을 고정하지만 Continuous Batching은 요청이 Finished되면 다음 Iteration에 Waiting 요청을 투입한다. 요청별 KV Cache가 Scheduler가 관리하는 GPU 자원이며 Prefix Caching과 Chunked Prefill이 각각 중복 Prefill과 긴 Prompt의 독점을 줄이는 방식도 정리했다. 표준 /metrics는 Running·Waiting 수와 Iteration Token 통계를 보여주지만 Request ID별 Iteration Batch 구성은 직접 증명하지 못하므로 학습용 Scheduler Trace가 필요하다는 관찰 경계를 구분했다. 실제 A·B·C 요청의 상태·시간축·Iteration별 Batch 기록은 다음 실습에서 확인할 범위로 남겼다.

TTFT는 전송 전 Client 대기를 제외하므로 전체 시간축과 함께 해석해야 함을 확인했다. 동일 서버 Session의 세 Run을 분리한 총 1,800줄 Trace와 코드·출력 포함 Notebook을 로컬에 보존했다.     같은 vLLM 서버와 같은 A·B·C 요청 조건에서 Client가 A·B를 하나의 Submission Group으로 먼저 제출하고 Future.result()로 두 요청의 완료를 기다린 뒤 C를 제출하는 Static-like 방식과, A·B·C를 동시에 제출하는 Continuous 방식의 차이를 비교했다. 두 경우 모두 Server 자체는 Continuous Batching이며 Client 제출 시점만 달랐다. Static-like에서는 C 첫 내용 6.808초, 전체 완료 10.177초였고 Continuous에서는 C 첫 내용 1.756초, 전체 완료 6.811초였다. executor.submit()은 그룹의 요청을 모두 병렬 제출하고, 그룹의 각 Future.result()를 확인한 뒤 다음 그룹으로 넘어가므로 (A,B)→C 순서가 실제로 보장된다. Trace에서도 Static-like는 A·B 완료 뒤 C 최초 배정, Continuous는 B 완료 보고와 C 최초 배정이 겹치는 것을 확인했다. 이 결과는 한 번의 비교에서 제출 시점과 Queue 대기 차이를 증명하며 모든 부하에서의 일반적인 성능 우위를 의미하지 않는다.
