    LLM을 실행하는 것과 여러 요청을 서비스하는 것은 다른 문제이며, Scheduler가 매 Engine Iteration마다 Waiting·Running 요청과 Token 작업을 다시 선택한다는 구조를 정리했다. Prefill과 Decode는 Scheduler 상태와 다른 계산 단계이고, 여러 요청의 Decode Token을 하나의 Batch로 묶어 GPU에서 함께 처리할 수 있음을 확인했다. Static Batching은 Batch 구성원을 고정하지만 Continuous Batching은 요청이 Finished되면 다음 Iteration에 Waiting 요청을 투입한다. 요청별 KV Cache가 Scheduler가 관리하는 GPU 자원이며 Prefix Caching과 Chunked Prefill이 각각 중복 Prefill과 긴 Prompt의 독점을 줄이는 방식도 정리했다. 표준 /metrics는 Running·Waiting 수와 Iteration Token 통계를 보여주지만 Request ID별 Iteration Batch 구성은 직접 증명하지 못하므로 학습용 Scheduler Trace가 필요하다는 관찰 경계를 구분했다. 실제 A·B·C 요청의 상태·시간축·Iteration별 Batch 기록은 다음 실습에서 확인할 범위로 남겼다.

긴 Prompt 요청과 Decode 중인 요청을 함께 실행하고 Chunked Prefill이 긴 Prefill을 여러 Iteration으로 나누는 이유를 설명한다. ON·OFF와 max_num_batched_tokens를 한 번에 하나씩 바꾸고 긴·짧은 Prompt 혼합 Workload의 TTFT·TPOT·Queue 변화로 Prefill·Decode Token Budget 경쟁을 설명한다.

    Qwen2.5-1.5B-Instruct 고정 Revision을 단일 RTX 2000 Ada 16GB GPU에서 실행하고, 먼저 전송해 800Token을 생성 중인 A와 796Token의 긴 Prompt B, 135Token의 짧은 Prompt C를 함께 사용해 Chunked Prefill과 Iteration Token Budget 경쟁을 검증했다. A의 첫 Content가 도착해 Decode가 시작된 뒤 B와 C를 제출했으며, Prefix Caching을 끄고 FCFS·float16·max_model_len=1024·max_num_seqs=3·Block Size 16을 고정했다. 각 조건에서 Warm-up 1회를 통계에서 제외하고 본 측정 5회를 수행했다. OFF·Budget 1024와 ON·Budget 1024에서는 B의 Prefill이 모두 [796]으로 한 Iteration에 배정되어 A TPOT p50은 15.41/15.42ms·A의 Prefill 구간 최대 Content 간격 p50은 82.14/79.75ms·B TTFT p50은 112.73/113.78ms·C TTFT p50은 111.52/113.05ms로 거의 같았다. Chunked Prefill을 켜도 Decode를 먼저 배정한 뒤 남은 Token Budget에 긴 Prefill 전체가 들어가면 실제 분할은 발생하지 않는다고 설명했다. ON·Budget 256에서는 B가 [255, 255, 255, 31]로 네 Iteration에 나뉘고 각 Iteration에 A Decode 1Token이 먼저 배정됐다. 그 결과 A 최대 Content 간격 p50은 28.59ms로 ON·1024보다 51.16ms, 64.15% 감소했지만 B TTFT는 135.02ms로 21.25ms, C TTFT는 134.56ms로 21.51ms 증가했다. C는 FCFS에서 B 뒤에 제출되어 B의 마지막 Chunk와 함께 네 번째 Prefill Iteration에 배정됐다. A의 전체 TPOT p50은 세 조건 모두 약 15.4ms/token이어서 평균 TPOT만으로 한 번의 긴 Streaming 정지를 찾기 어렵고, Prefill 관찰 구간과 겹친 Content 간격을 함께 봐야 함을 확인했다. 초기 최대 간격 집계가 구간의 끝 시각만 비교해 ON·1024의 약 78ms 간격을 누락한 것을 발견해 두 시간 구간의 겹침 조건으로 원본 Content 시각을 재계산하고 수정 결과를 별도 비교 JSON에 보존했다. 최종 측정 파일에는 /metrics Running·Waiting 표본이 없으므로 Queue 수치를 측정했다고 주장하지 않고 Scheduler Trace의 요청별 prefill·decode scheduled_tokens와 Client TTFT·TPOT·Content 간격만 판정 근거로 사용했다. Chunked Prefill은 총 Prefill 계산량을 줄이는 기능이 아니라 긴 Prefill을 여러 Scheduler Iteration으로 나누어 기존 Decode에 중간 실행 기회를 주는 방식이며, 작은 Budget은 기존 Streaming의 긴 멈춤을 줄이는 대신 새 요청의 TTFT를 늘릴 수 있다고 결론지었다. Budget 256은 이 GPU·모델·Workload의 비교 조건일 뿐 운영 권장값이 아니며 실제 설정은 Prompt 길이 분포, 동시 Decode 수, TTFT와 최대 Token 간격 SLO로 다시 측정해야 한다.
