    `[[3,7,2,9],[4,1,6,8]]`에서 `tokens[:, :-1]`을 모든 행의 마지막 열 전까지, `tokens[:, 1:]`을 모든 행의 두 번째 열부터 끝까지로 해석했다. 입력 `[[3,7,2],[4,1,6]]`과 Target `[[7,2,9],[1,6,8]]`의 Shape이 모두 `[2,3]`임을 실행 결과로 확인하고, 각 행에서 입력의 마지막 Token `9·8`과 Target의 첫 Token `3·4`가 빠진다고 자기 말로 설명해 이전 보강 항목을 완료했다. 모델 Logit `[B,T,V]=[1,3,10]`을 `reshape(-1,10)`으로 `[3,10]`에 펼친 왼쪽 입력은 위치별 후보 점수이고, Target `[1,3]`을 `reshape(-1)`으로 `[3]`에 펼친 오른쪽 입력은 각 행에서 채점할 Token ID `[7,2,9]`라고 구분했다. Accuracy는 최댓값 인덱스가 Target과 같은지만 보지만, Cross Entropy는 Target 칸의 Log-Softmax 값을 사용하므로 최댓값이 정답이어도 정답 칸이 충분히 강하지 않으면 Loss가 남는다는 차이를 확인했다. 입력 `[3,7,2]`과 Target `[7,2,9]`은 단순 배열 변환 하나가 아니라 Causal Mask로 `[3]→7`, `[3,7]→2`, `[3,7,2]→9` 세 Prefix 문제를 만든다고 이해했다. 세 위치를 따로 세 번 학습한 것이 아니라 한 Forward에서 세 위치 Logit을 병렬 계산하고, 세 Token Loss의 평균으로 한 번에 `backward()`해 전체 모델을 조정한다는 구조를 설명했다. 저장된 실행에서 `d_model=2`·Head 2개 모델을 300번 수정했을 때 Loss가 `0.462389`에서 정체되고 예측이 `[9,2,9]`로 남았다. 학습된 모델의 첫 위치와 마지막 위치 Softmax 행이 같고 Token 7·9가 약 `0.4999`씩 나뉜 것이 직접 관찰한 사실이다. `d_model=4`·`d_ff=16`으로 넓혀 새로 초기화한 모델은 같은 저장 실행에서 50번에 Loss `3.3378e-06`, 300번에 `2.5829e-06`까지 감소해 작은 수열을 사실상 완전히 암기했다. Seed를 고정하지 않아 세부 숫자는 재실행마다 달라질 수 있지만, 새 커널에서도 `d_model=2`의 약 `0.462` 정체와 `d_model=4`의 Loss `0.001` 미만·동일 생성 결과를 재현했다. 이를 표현 병목으로 해석하되, 차원 변경과 재초기화가 함께 일어났으므로 LayerNorm 하나만의 영향으로 단정하지 않았다. 입력을 실수로 `[7,2,9]`로 두고 같은 Target `[7,2,9]`을 재사용하면 Loss가 0에 가까워져도 다음 Token 관계가 아니라 입력과 같은 ID를 내는 잘못된 목표를 학습한다. 그 상태에서 `[3,7,2]`를 생성해 `[3,7,2,2]`가 나온 원인을 추적했고, 입력 `[3,7,2]`과 Target `[7,2,9]`을 같은 셀에 다시 선언해 학습한 뒤 `[3,7,2,9]`로 수정했다. 화면의 수정 Source·디스크 저장 Source·cached output을 서로 다른 시점의 근거로 읽으면 전제가 엇갈릴 수 있으므로, 최종 저장본의 Source와 Output을 함께 확인하고 다시 실행해야 한다는 디버깅 기준도 남겼다. `logits[:, -1, :]`이 모든 Batch의 마지막 Token 위치에서 Vocabulary 후보 전체를 가져와 `[B,T,V] → [B,V]`로 만드는 슬라이싱임을 확인했다. `argmax(dim=-1)`는 최댓값 자체가 아니라 그 값이 있던 Vocabulary 인덱스, 즉 Token ID를 반환하고, `keepdim=True`는 결과를 `[B,1]`로 유지해 기존 Token ID Tensor 뒤에 붙일 수 있게 한다고 설명했다. Token ID Tensor가 `[Batch,Token]`인 2차원이므로 현재 코드에서는 `dim=1`과 `dim=-1`이 같은 마지막 Token 축이라는 점을 확인했다. `dim=1`은 Token 축이라는 역할을, `dim=-1`은 마지막 축이라는 위치를 강조하며, 새 Token이 뒤에 붙는 것은 `[prompt_tokens,next_token]` 목록 순서 때문이라고 정리했다. `[B,T,D]` 3차원에서는 `dim=1`과 `dim=-1`이 서로 다른 축이라는 경계도 함께 남겼다. 학습된 모델에 `[3]`을 넣고 마지막 위치의 Token ID를 선택해 다시 입력 뒤에 붙이는 과정을 세 번 반복했다. 실제 출력은 `[3] → [3,7] → [3,7,2] → [3,7,2,9]`였고, 학습에서 병렬로 만든 세 Prefix 관계를 생성에서 순차적으로 사용한다는 연결을 설명했다. 이 결과로 Target shift·Causal Mask·Cross Entropy·Optimizer 학습·실패 수정·Autoregressive Generation까지 Tiny Decoder LM 필수 관문을 완료했다. `sshleifer/tiny-gpt2`의 Tokenizer를 모델 이름으로 불러와 문자열을 Token ID와 Token 조각으로 변환했다. 길이가 3·7인 두 문장을 `padding=True`로 묶어 `input_ids`와 `attention_mask` Shape `[2,7]`을 확인했고, 짧은 문장 뒤의 PAD 위치가 Mask 0이 되는 것을 실행했다. 한 문장만 넣으면 그 Batch의 최장 길이 3까지만 만들어지고, 길이가 다른 여러 문장을 Padding 없이 하나의 Tensor로 묶으려 하면 오류가 나는 이유도 확인했다. `AutoModelForCausalLM`으로 실제 `GPT2LMHeadModel`을 불러와 `input_ids`와 `attention_mask`를 전달했다. 입력 `[2,7]`이 Logit `[2,7,50257]`이 되는 것을 확인하고, Logit은 정답과 비교해 얻는 Loss가 아니라 각 Batch·Token 위치에서 Vocabulary 전체에 준 원시 점수라고 구분했다. `attention_mask.sum(dim=1)`으로 실제 Token 수 `[3,7]`을 구하고 1을 빼 마지막 실제 위치 `[2,6]`을 얻었다. `logits[batch_indices,last_real_positions,:]`는 `(0,2)`와 `(1,6)`을 짝지어 각 문장의 마지막 실제 Token 위치에서 Vocabulary 열 전체를 가져오는 고급 인덱싱이며, `[2,7,50257] → [2,50257]`이 된다고 설명했다. 전체 고급 인덱싱 실습은 현재 흐름을 끊지 않고 Batch inference 직전 보강 항목으로 남겼다. Tokenizer는 문자열을 Token ID로 바꾸고, 모델의 `nn.Embedding`은 그 ID를 행 주소로 사용해 학습된 벡터를 조회하는 서로 다른 객체라고 구분했다. Tokenizer가 만들 수 있는 ID 수, Embedding의 `num_embeddings`, LM Head의 Vocabulary 출력 수가 같은 ID 체계에 맞아야 하며 연속 ID의 경우 행 수는 최대 ID보다 1 커야 한다고 설명했다. `type(model)`과 `inspect.getfile(type(model))`로 실제 GPT-2 구현 파일에 들어가 `self.wte = nn.Embedding(...)` 선언과 Forward의 `inputs_embeds = self.wte(input_ids)`를 직접 찾아, 전체 소스 대신 생성 줄과 입력 사용 줄을 연결해 보는 분석법을 익혔다. 현재 `last_real_logits` Shape `[2,50257]`까지 만들었다. 다음에는 각 문장의 Vocabulary 축에서 다음 Token ID를 선택하고 문자열로 복원한 뒤, 선택한 Token을 입력 뒤에 반복해서 붙이는 `generate()` 없는 수동 Greedy 생성 루프를 완성한다. 원래 인덱스를 보존하며 Queue 회전과 실제 실행 횟수를 구분하고 O(n²) 구현을 완성했습니다. heap[0]만 최솟값을 보장하는 성질과 heappop·heappush·원소 부족 종료 조건을 적용해 풀이했습니다. 타겟 넘버의 +·- 이진 선택을 DFS 재귀로 구현해 모든 경로의 정답 개수를 계산했습니다. 이전 풀이를 보지 않고 Counter 방식으로 다시 풀고, 순회 중 음수 조기 종료와 마지막 0 검사를 설명했습니다. 같은 활동에 관해 기존 복습 기록에 남아 있던 검증 요약 (새 활동·추가 시간 아님) 길이 3·7의 동적 Padding에서 실제 마지막 위치 [2,6]을 구하고 GPT-2 Logit [2,7,50257]에서 [2,50257]을 선택했습니다. 세 개의 다음 Token 문제를 한 Forward에서 학습하는 구조와 마지막 Logit을 이어 붙이는 반복 생성을 실행했습니다. 2-Batch에서 Target shift를 자료 없이 구성하고 [B,T,V]·[B,T]를 평탄화해 Cross Entropy로 채점했습니다.     하루 전 풀이와 학습 기록을 보지 않고 `left=1`, `right=min(times)×n`의 시간 후보 범위, `sum(mid//time)` 가능 판정과 폐구간 경계 이동을 다시 구현해 프로그래머스 전체 테스트에 통과했다. 종료 시 `right=27`은 불가능하고 `left=28`은 최초 가능인 경계로 교차한다는 점을 자기 말로 설명했다. 범위를 절반씩 줄이는 `O(log R)`회마다 심사관 `m`명을 확인하므로 전체 시간 복잡도가 `O(m log R)`임을 교정했으며, 이 증거로 이분 탐색 경계 설계 관문을 완료했다. 인접 행렬 `computers[current]`의 각 열을 이웃 연결 여부로 읽고, 방문하지 않은 컴퓨터를 시작점으로 잡아 DFS를 수행했다. DFS가 하나의 연결 요소를 모두 `visited` 처리하므로 바깥 반복에서 아직 방문하지 않은 시작점을 만날 때만 `answer += 1`이 실행되어 네트워크 수가 된다는 점을 설명했다. 각 컴퓨터는 DFS에 한 번만 들어가지만, 그때 길이 `n`인 연결 행을 확인하므로 전체 시간 복잡도는 `O(n²)`임을 연결해 프로그래머스 제출에 통과했다. `deque`에 `(현재 단어, 변환 횟수)`를 넣고, 꺼낸 직후 목표 단어이면 현재 `count`를 반환하는 BFS 흐름을 구현했다. 후보 단어는 글자 차이가 정확히 하나일 때만 다음 상태가 되며, `visited = {begin}`은 값만 저장하는 `set`으로 이미 큐에 넣은 단어의 재방문과 순환을 막는다. 방문한 단어는 글자 비교 전 건너뛰고, 새 단어는 큐에 넣는 순간 방문 처리하도록 정리했으며 프로그래머스 제출에 통과했다. 프로그래머스 배달 문제에서 출발 마을 1부터 모든 마을까지의 최소 누적 비용을 `distance`에 저장하고, 비용이 `K` 이하인 마을 수를 세는 문제로 해석했다. `distance[1]=0`, 나머지는 무한대로 시작하며 양방향 도로를 인접 리스트에 넣고, 최소 Heap에서 가장 작은 누적 비용을 꺼내 `new_cost < distance[next_village]`일 때만 거리 갱신과 다음 탐색을 수행하는 흐름을 따라 구현했다. 일반 Queue와 달리 비용이 작은 후보부터 꺼내야 하는 이유, 더 비싼 경로는 최단거리 후보가 아니므로 확장하지 않는 이유, 오래된 Heap 후보를 건너뛰는 조건이 정답보다 중복 탐색을 줄이는 최적화라는 점까지 설명했다. 전체 정답은 안내를 받아 완성했으므로 가중치 최단경로 관문은 아직 완료하지 않고, 다음 코딩 테스트 세션에서 자료 없이 다시 구현해 제출하는 과제로 남겼다. Token 수·Transformer Layer 수·Attention Head 수를 서로 다른 축으로 구분하고, 같은 Token도 이전 Layer의 출력과 Layer별 Projection Weight가 다르므로 각 Layer에서 서로 다른 Q·K·V가 만들어진다고 설명했다. GPT-2의 합쳐진 QKV Projection Weight를 역할별 열 구간으로 나누어 이해하고, `past_key_values[layer][0/1]`이 Layer별 Key·Value Tensor를 가리킨다는 점을 `[Batch,Head,Token,Head dim]` Shape과 연결했다. 과거 Query는 이미 출력을 만드는 역할을 마쳤고, 다음 Step에 다시 필요한 과거 K·V만 Cache한다는 이유도 정리했다. No-cache에서는 생성할 때마다 전체 Prefix가 다시 입력되어 과거 Token의 Q·K·V까지 반복 계산되는 반면, Cache 경로는 첫 Prompt 전체 이후 새 Token `[1,1]`과 과거 `past_key_values`만 전달한다는 차이를 실행했다. Layer 0 Key Cache의 Token 축이 `2 → 3 → 4 → 5 → 6`으로 증가하는 것을 확인했고, 같은 Prompt·Greedy·생성 길이에서 두 방식의 Token ID와 Decode 문장이 같아 `torch.equal(...)=True`가 되는 기능적 기준선을 확보했다. 각 생성 함수를 3회 Warm-up한 뒤 10회 반복 측정해 No-cache 평균 `74.1009 ms`, KV Cache 평균 `11.6883 ms`를 얻었고, 같은 로컬 조건에서 Cache 경로가 약 `6.34배` 빠르다고 계산했다. `time.perf_counter()`는 Python Singleton이 계속 증가시키는 값이 아니라 운영체제·하드웨어 시계를 호출 순간 읽은 Snapshot이며, 저장된 두 Counter의 차이만 경과시간으로 사용한다고 이해했다. 기준점이 Unix Epoch가 아니므로 UTC로 직접 변환할 수 없고, 실제 시각이 필요하면 별도 시계를 기록하거나 두 시계를 함께 찍어 근사 대응해야 한다고 구분했다. 같은 활동에 관해 기존 복습 기록에 남아 있던 검증 요약 (새 활동·추가 시간 아님) 입국심사를 기존 코드 없이 다시 구현해 전체 테스트에 통과하고, left·right 교차가 최초 가능 경계를 남기는 이유와 O(m log R) 판정 비용을 설명했습니다.
