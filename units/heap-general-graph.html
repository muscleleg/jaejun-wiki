    하루 전 풀이와 학습 기록을 보지 않고 `left=1`, `right=min(times)×n`의 시간 후보 범위, `sum(mid//time)` 가능 판정과 폐구간 경계 이동을 다시 구현해 프로그래머스 전체 테스트에 통과했다. 종료 시 `right=27`은 불가능하고 `left=28`은 최초 가능인 경계로 교차한다는 점을 자기 말로 설명했다. 범위를 절반씩 줄이는 `O(log R)`회마다 심사관 `m`명을 확인하므로 전체 시간 복잡도가 `O(m log R)`임을 교정했으며, 이 증거로 이분 탐색 경계 설계 관문을 완료했다. 인접 행렬 `computers[current]`의 각 열을 이웃 연결 여부로 읽고, 방문하지 않은 컴퓨터를 시작점으로 잡아 DFS를 수행했다. DFS가 하나의 연결 요소를 모두 `visited` 처리하므로 바깥 반복에서 아직 방문하지 않은 시작점을 만날 때만 `answer += 1`이 실행되어 네트워크 수가 된다는 점을 설명했다. 각 컴퓨터는 DFS에 한 번만 들어가지만, 그때 길이 `n`인 연결 행을 확인하므로 전체 시간 복잡도는 `O(n²)`임을 연결해 프로그래머스 제출에 통과했다. `deque`에 `(현재 단어, 변환 횟수)`를 넣고, 꺼낸 직후 목표 단어이면 현재 `count`를 반환하는 BFS 흐름을 구현했다. 후보 단어는 글자 차이가 정확히 하나일 때만 다음 상태가 되며, `visited = {begin}`은 값만 저장하는 `set`으로 이미 큐에 넣은 단어의 재방문과 순환을 막는다. 방문한 단어는 글자 비교 전 건너뛰고, 새 단어는 큐에 넣는 순간 방문 처리하도록 정리했으며 프로그래머스 제출에 통과했다. 프로그래머스 배달 문제에서 출발 마을 1부터 모든 마을까지의 최소 누적 비용을 `distance`에 저장하고, 비용이 `K` 이하인 마을 수를 세는 문제로 해석했다. `distance[1]=0`, 나머지는 무한대로 시작하며 양방향 도로를 인접 리스트에 넣고, 최소 Heap에서 가장 작은 누적 비용을 꺼내 `new_cost < distance[next_village]`일 때만 거리 갱신과 다음 탐색을 수행하는 흐름을 따라 구현했다. 일반 Queue와 달리 비용이 작은 후보부터 꺼내야 하는 이유, 더 비싼 경로는 최단거리 후보가 아니므로 확장하지 않는 이유, 오래된 Heap 후보를 건너뛰는 조건이 정답보다 중복 탐색을 줄이는 최적화라는 점까지 설명했다. 전체 정답은 안내를 받아 완성했으므로 가중치 최단경로 관문은 아직 완료하지 않고, 다음 코딩 테스트 세션에서 자료 없이 다시 구현해 제출하는 과제로 남겼다. Token 수·Transformer Layer 수·Attention Head 수를 서로 다른 축으로 구분하고, 같은 Token도 이전 Layer의 출력과 Layer별 Projection Weight가 다르므로 각 Layer에서 서로 다른 Q·K·V가 만들어진다고 설명했다. GPT-2의 합쳐진 QKV Projection Weight를 역할별 열 구간으로 나누어 이해하고, `past_key_values[layer][0/1]`이 Layer별 Key·Value Tensor를 가리킨다는 점을 `[Batch,Head,Token,Head dim]` Shape과 연결했다. 과거 Query는 이미 출력을 만드는 역할을 마쳤고, 다음 Step에 다시 필요한 과거 K·V만 Cache한다는 이유도 정리했다. No-cache에서는 생성할 때마다 전체 Prefix가 다시 입력되어 과거 Token의 Q·K·V까지 반복 계산되는 반면, Cache 경로는 첫 Prompt 전체 이후 새 Token `[1,1]`과 과거 `past_key_values`만 전달한다는 차이를 실행했다. Layer 0 Key Cache의 Token 축이 `2 → 3 → 4 → 5 → 6`으로 증가하는 것을 확인했고, 같은 Prompt·Greedy·생성 길이에서 두 방식의 Token ID와 Decode 문장이 같아 `torch.equal(...)=True`가 되는 기능적 기준선을 확보했다. 각 생성 함수를 3회 Warm-up한 뒤 10회 반복 측정해 No-cache 평균 `74.1009 ms`, KV Cache 평균 `11.6883 ms`를 얻었고, 같은 로컬 조건에서 Cache 경로가 약 `6.34배` 빠르다고 계산했다. `time.perf_counter()`는 Python Singleton이 계속 증가시키는 값이 아니라 운영체제·하드웨어 시계를 호출 순간 읽은 Snapshot이며, 저장된 두 Counter의 차이만 경과시간으로 사용한다고 이해했다. 기준점이 Unix Epoch가 아니므로 UTC로 직접 변환할 수 없고, 실제 시각이 필요하면 별도 시계를 기록하거나 두 시계를 함께 찍어 근사 대응해야 한다고 구분했다. 같은 활동에 관해 기존 복습 기록에 남아 있던 검증 요약 (새 활동·추가 시간 아님) 입국심사를 기존 코드 없이 다시 구현해 전체 테스트에 통과하고, left·right 교차가 최초 가능 경계를 남기는 이유와 O(m log R) 판정 비용을 설명했습니다.
