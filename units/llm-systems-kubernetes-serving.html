Kubernetes LLM Serving

짧은 제목 · Kubernetes Serving

선수 대기완료 조건 0 / 4

학습 후 할 수 있는 일vLLM을 Kubernetes GPU 환경에 재현 가능하게 배포하고 관측·Replica 확장의 효과를 Serving Metric으로 검증한다.

학습 안내

이 학습이 필요한 이유
단일 프로세스와 Multi-GPU에서 확인한 성능 특성을 실제 배포·운영 경계로 이전해야 Serving 시스템 역량을 완성할 수 있다.
완료 후 이어지는 일
KServe·LLMInferenceService·HPA 또는 KEDA·고급 Routing을 후속 선택 과제로 확장할 수 있다.
학습 내용 자세히 보기

앞에서 검증한 vLLM Serving 계약을 Kubernetes GPU Workload로 이전한다. Manifest와 Helm으로 재현 가능한 배포를 만들고, Prometheus·Grafana 관측과 Replica 확장 실험으로 Queue·Latency·Throughput 변화를 검증한다. Kubernetes 전체 플랫폼 학습이 아니라 LLM Serving 배포의 통합 실습에 집중한다.

완료 조건

충족한 조건 0 / 4

○

vLLM GPU Deployment

미충족

Kubernetes Deployment·Service와 GPU Resource Request를 구성해 vLLM을 실행한다. 환경에 필요한 Model Cache용 PVC 또는 지속 스토리지와 인증용 Secret을 연결하고 Startup·Readiness Probe를 설정한다. Manifest·Pod 상태·Event·Log·GPU 할당 상태·API Request와 Response를 남겨 정상 Serving을 확인하면 완료된다.

○

Helm을 이용한 재현 가능한 배포

미충족

Model·dtype·max_model_len·gpu_memory_utilization·GPU와 Memory Resource·Service·Probe·Monitoring 설정을 Chart와 values.yaml로 분리한다. Helm Install 또는 Upgrade 명령과 Rendered Manifest를 기록하고 재배포 후 동일 Configuration과 정상 API 응답이 복원되는지 확인하면 완료된다.

○

Kubernetes Observability

미충족

vLLM /metrics를 Prometheus가 수집하도록 구성하고 Grafana에서 확인한다. 14번에서 사용한 Running·Waiting·Queue·Preemption·KV Cache·TTFT·TPOT 패널에 Pod 상태와 GPU Metric을 같은 시간축으로 연결하고, 부하 수행 중 Metric 변화를 남기면 완료된다.

○

Replica 확장 효과 검증

미충족

GPU 2개 이상을 사용할 수 있는 환경에서 동일 Workload를 Replica 1개와 2개 이상에 실행한다. Replica 1개에서 Queue 증가를 확인한 뒤 Replica를 늘리고 Request 분배·Throughput·Queue Time·TTFT·GPU Utilization 변화를 비교한다. Replica 증가가 선형 확장을 보장하지 않는 이유와 병목을 설명하면 완료된다.

목표 문맥별 선택 이유

AI 엔지니어 역량에서 선택한 이유
