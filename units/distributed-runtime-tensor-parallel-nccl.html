Tensor Parallel과 NCCL Collective

짧은 제목 · TP·NCCL

선수 대기달성 기준 0 / 21

학습 후 할 수 있는 일vLLM Engine·Executor·GPU Worker의 실행 구조와 KV Cache 예산을 설명하고, TP=1·2·4를 실행해 Tensor 분할과 실제 vLLM Collective, NCCL 통신, 메모리와 성능 변화를 검증한다.

학습 안내

이 학습이 필요한 이유
단일 GPU 기준선 이후에 모델과 요청 계산을 여러 GPU로 분할할 때 생기는 통신 비용을 분리해 봐야 한다.
완료 후 이어지는 일
Prefill·Decode 분리, 동일 GPU Budget 비교, 고속 Interconnect와 Cross-node 통신 실험을 수행할 수 있다.
학습 내용 자세히 보기

[런파드 - L4 x 4] 동일한 L4 4장 호스트에서 활성 GPU를 1·2·4장으로 바꾸며 Tensor Parallel의 Tensor 분할, Collective, 통신 비용과 Scaling을 연결한다. 먼저 API Server·Engine Core·Executor·GPU Worker의 역할과 실제 Process·Rank·GPU 대응을 확인한다. Worker의 초기 메모리 프로파일링이 KV Cache 예산으로 연결되는 과정과 Engine이 그 예산 안에서 요청·Token을 스케줄링하는 과정을 구분한다. Kubernetes의 Leader·Worker Pod 구분과 Runtime 내부 GPU Worker Process를 같은 단위로 취급하지 않는다.

○

vLLM Engine·Executor·GPU Worker의 역할과 실행 경로

미충족

설치한 vLLM Version과 Backend를 기준으로 API Server → Engine Core의 요청·Token 스케줄링 → Executor의 실행 지시 → GPU Worker의 모델 계산 → 결과 반환을 도식화한다. Process Tree와 시작 Log 또는 해당 Version의 소스로 역할·Process·Rank·GPU 대응을 확인한다. Worker에도 vLLM 코드와 모델의 담당 Shard가 필요하며 별도의 독립 Serving Replica는 아니라는 점, Leader가 로컬 GPU Worker도 포함할 수 있다는 점, Kubernetes Leader·Worker Pod와 Runtime GPU Worker Process의 단위가 다르다는 점을 설명한다.

○

Worker 초기 메모리 예산과 Engine 요청 스케줄링의 구분

미충족

모델 로딩·Worker 메모리 프로파일링·KV Cache 용량 설정을 시작 Log와 Version별 구현으로 확인하고, 그 예산 안에서 Engine이 Cache Block 할당·회수와 요청·Token Budget을 관리하는 흐름을 설명한다. TP Worker들은 독립 요청을 GPU 사용률에 따라 나눠 받는 서버가 아니라 같은 모델 실행에 참여한다는 점을 구분한다. 외부 Process의 GPU 부하·메모리 사용을 Engine이 항상 직접 감지하고 예산을 자동 재산정하는 것으로 해석하지 않으며, 초기 용량 결정과 실행 중 내부 상태 추적의 경계를 기록한다.

목표 문맥별 선택 이유

쿠버네티스 GPU 클러스터와 Multi-GPU Serving 학습에서 선택한 이유

Fake GPU 환경에서 쿠버네티스의 GPU 자원 등록·할당·Node 및 그룹 배치와 LLM Serving 운영을 먼저 익힌다. 이후 실제 Multi-GPU 환경에서 분산 추론의 계산·통신·메모리·성능을 검증하고 Kubernetes의 자원 관리와 Runtime의 GPU 사용·통신 책임을 구분한다.
