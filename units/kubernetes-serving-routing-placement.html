LLM-aware Routing과 GPU 배치의 구분

Endpoint 부하·Prefix에 따른 요청 선택을 관찰하고, EPP의 요청 라우팅과 Kubernetes의 Pod·GPU 배치 책임을 구분한다.

학습 안내

짧은 제목 · Routing·배치 구분

완료달성 기준 5 / 5
이 학습이 필요한 이유
요청 경로가 연결돼도 어느 Ready 서버를 고를지와 Pod를 어느 Node에 배치할지는 별개의 결정이다. 실제 선택 변화와 Pod 상태를 연결해야 두 책임을 혼동하지 않는다.
완료 후 이어지는 일
과부하·확장·복구를 관찰할 때 요청 목적지 변화와 Pod·GPU 배치 변화를 구분하고, 통합 시간축의 병목 분석으로 확장한다.
학습 내용 자세히 보기

핵심 질문: 이미 배치된 Ready 모델 서버 중 어떤 서버로 요청을 보내며, 이 선택은 GPU 배치와 어떻게 다른가? 개념·실습 흐름 Pod의 Node 배치와 Ready 후보를 확인한 뒤, Endpoint 부하와 Mock Prefix Locality를 바꾸어 EPP의 요청 선택 변화를 관찰한다. Queue·KV Cache 사용 비율·Prefix 재사용 가능성을 평가하는 기준과 weight를 구분하고, 일반 Load Balancing과 LLM-aware Selection의 차이를 설명한다. 같은 후보 안의 요청 선택과 Deployment 롤아웃에 따른 Pod 교체를 구분한다. Kubernetes Scheduler의 Pod·GPU 배치, EPP의 Endpoint 선택, 추론 엔진의 Batch·Token 실행이 서로 다른 결정임을 연결한다. 검증 경계 Mock Locality를 실제 KV Cache 적중률이나 GPU 성능 근거로 사용하지 않는다. 책임 구분을 확인하기 위해 의도적인 Node 재배치 대조 실험까지 요구하지 않는다. Request Rate·Endpoint Health·EPP 선택을 같은 시간축에서 종합하는 관측은 Serving 전체 흐름과 병목 통합 검증에서 다룬다.

    llm-d Router v0.9.0의 설명과 구현을 바탕으로 EPP가 KV 텐서 대신 Prefix 블록과 선택 Endpoint의 관계를 메모리 인덱스에 유지하며 재사용 가능성을 추정한다는 점을 이해했다. 선택 후 PreRequest 경로의 인덱스 기록은 실제 엔진 처리 성공·캐시 잔존 보장이 아니며 EPP 재시작으로 사라질 수 있다. 문자열을 주어 기록 유무를 읽기 전용으로 조회하는 공개 API와 집계 적중 메트릭은 다른 기능이고, 직접 조회 API를 구현한 실습은 하지 않았다. 엔진 Prefix Cache의 사용자 격리는 messages.role=user와 무관하며 vLLM 확장 cache_salt 같은 캐시 키 구분값을 사용할 수 있다는 원리를 확인했으나 실제 Salt 격리 실험은 하지 않았다.
