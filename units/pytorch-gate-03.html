  • Head별 Attention 결과를 `transpose()`와 `reshape()`로 이어 붙인 `multi_head_output`은 여러 관점의 결과를 나열한 상태라고 이해했다…

    Head별 Attention 결과를 `transpose()`와 `reshape()`로 이어 붙인 `multi_head_output`은 여러 관점의 결과를 나열한 상태라고 이해했다. 이어 붙이는 연산만으로는 Head 정보가 섞이지 않으므로, `W_O` Linear가 각 특징을 학습된 비율로 다시 조합해 다음 블록에서 사용할 `d_model` 벡터로 만든다는 역할을 정리했다. 포지셔널 인코딩은 입력 `x`에 이미 더해져 Q·K·V Projection을 통과하므로 Head 계산 중 사라지는 값이 아니라는 점도 확인했다. `multi_head_output[0,0]`이 `[0,0,:]`와 같은 0번째 Batch·0번째 Token의 전체 벡터임을 확인했다. 이 벡터를 `W_O.T`에 직접 곱한 결과와 `nn.Linear`의 `projected_output[0,0]`을 `torch.allclose()`로 비교해 동일함을 검증했다. `assert d_model % num_heads == 0`으로 특징 차원이 Head 수로 나누어지는지 검사하고, `head_dim=d_model//num_heads`에서 `//`가 몫 나눗셈임을 확인했다. Q·K·V Projection은 모두 `nn.Linear(d_model,d_model,bias=False)`로 등록했다. 클래스 밖에서 `self.num_heads`를 사용해 생긴 `NameError`를 통해 `self`는 인스턴스 메서드 안에서만 사용할 수 있다는 점도 바로잡았다. Q·K·V Projection 직후 Shape은 모두 `[1,2,2]`였고, `view()`와 `transpose(1,2)`를 거쳐 `[batch,head,token,head_dim]=[1,2,2,1]`이 됐다. Head를 나누는 것은 Token을 늘리는 것이 아니라 Token마다 가진 특징 차원을 Head별로 나누는 것임을 다시 확인했다. 현재 `head_dim=1`에서는 `√1=1`이므로 Score Scaling 전후 숫자가 같은 것도 정상이다. 평균 0인 512차원 벡터에서 원소 제곱합의 기댓값을 1로 두면 각 원소의 제곱 기댓값이 `1/512`, 분산이 `1/512`, 표준편차가 `1/√512`로 이어지는 흐름을 자신의 분산 정의와 연결했다. 임베딩에 `√d_model`을 곱하는 작업과 Score를 `√head_dim`으로 나누는 작업은 서로를 취소하는 한 쌍이 아니라 목적이 다른 별도 Scaling임을 구분했다. AGI를 향한 연구를 하나의 알고리즘 이름으로 보지 않고 모델 구조·학습·메모리·계획·도구 사용·검증·서빙이 연결된 기술 지도로 살펴봤다. Agent Loop에서는 계획 → 실행 → 검증 이후 문제가 발견되면 결과를 다음 계획에 다시 반영하는 반복 구조와 코드 단위 검증의 역할을 읽었다.

    Hidden State `[1,2,4]`에서 Token별 Feature 평균을 `dim=-1, keepdim=True`로 구하면 평균을 낸 마지막 축이 길이 `1`로 남아 `[1,2,1]`이 되고, 이 평균을 원래 Tensor에서 뺄 때 크기 `1`인 축이 Feature 길이 `4`에 맞춰 Broadcasting된다고 자기 말로 설명했다. Broadcasting은 오른쪽 축부터 크기를 비교하며, 크기가 같거나 한쪽이 `1`이면 계산할 수 있고, 차원이 짧은 `[4]`는 부족한 Batch·Token 축이 왼쪽에 생략된 것으로 보아 `[1,2,4]`의 Feature 축에 대응한다고 이해했다. 반면 같은 위치의 축이 `4`와 `2`처럼 다르고 어느 쪽도 `1`이 아니면 연산할 수 없다는 경계도 구분했다.

    같은 tiny GPT-2와 `I study.` 입력을 CPU와 RunPod CUDA GPU에서 각각 실행하고, 양쪽 Logit dtype이 `float32`임을 확인했다. GPU Logit을 CPU로 옮겨 비교한 결과 `torch.equal(...)=False`, `torch.allclose(rtol=1e-5, atol=1e-5)=True`였고, 전체 `[1,3,50257]` Logit의 최대 절댓값 차이는 `1.4901161193847656e-08`이었다. `(cpu_logits-gpu_logits).abs().max().item()`을 부호 제거, 전체 원소 중 최대 차이 Scalar Tensor 선택, Python `float` 변환의 순서로 설명했으며 Shape이 `[1,3,50257] → [] → float`로 바뀐다고 정리했다. CPU와 GPU의 다음 Token ID는 모두 `5087`이어서, 미세한 부동소수점 차이가 이번 입력의 `argmax` 선택에는 영향을 주지 않았음을 검증했다. 진행률 표시 비활성화는 계산에 영향 없는 UI 제어이고, 여러 줄 괄호는 Tuple이 아니며 쉼표가 Tuple을 만든다는 Python 문법도 함께 확인했다. 또한 `gpu_model(...)`의 Python 반환과 GPU 물리 계산 완료는 같은 시점이 아닐 수 있지만, 이번 기본 `.to("cpu")` D2H 복사는 선행 CUDA 작업을 기다린 뒤 완성된 CPU 값을 반환하므로 직후 정확성 비교는 안전하다고 구분했다. 반면 `perf_counter()`로 호출만 감싸면 GPU 완료 전에 종료 시각이 기록될 수 있어, GPU Timing에는 `torch.cuda.synchronize()` 또는 CUDA Event 같은 명시적 측정 경계가 필요하다고 정리했다. 이어서 입력 `[1,3]`인 tiny GPT-2를 Warm-up 10회 뒤 200회 실행해, 모든 Python `model()` 호출 반환까지 `1335.146ms`, 동기화로 GPU 작업이 모두 끝날 때까지 `1335.274ms`, 반환 뒤 남은 대기는 `0.128ms`임을 측정했다. `model_calls_returned_ms`는 순수 CPU 시간이 아니고 `gpu_work_completed_ms`도 순수 Kernel 시간이 아니라, CPU의 준비·등록과 GPU 계산이 겹친 전체 벽시계 구간이라고 교정해 해석했다. Benchmark 함수는 전역 `model`·`device` 대신 `model: GPT2LMHeadModel`을 직접 받고, `next(model.parameters()).device`와 `prompt_ids.device`가 다르면 Forward 전에 `ValueError`를 내도록 리팩터링했다. 처음에는 `next()`가 두 번째 Parameter를 꺼낸다고 생각했지만, 새 Iterator의 커서가 첫 원소 앞에 있어 최초 호출이 첫 Parameter로 이동하며 값을 반환한다고 JDBC ResultSet 경험과 연결해 교정했다. 같은 Iterator에 두 번 호출해야 두 번째 Parameter가 나오며, 호출마다 새 Iterator를 만드는 `next(model.parameters())`는 항상 첫 Parameter라는 점과 이 검사가 단일 장치 모델에만 대표성을 가진다는 범위까지 확인했다. 최종적으로 PAD Token `<|endoftext|>`·ID `50256`를 설정하고 RTX 2000 Ada에서 tiny GPT-2, Prompt 2 Token, 새 Token 20개, Warm-up 3회, 동기화된 20회 측정으로 No-cache·KV Cache × Batch 1·4를 비교했다. 두 Batch 모두 출력이 `torch.equal=True`였고, Batch 1은 `48.395ms/413.26 tokens/sec → 42.857ms/466.66 tokens/sec`, Batch 4는 `49.180ms/1626.66 tokens/sec → 43.671ms/1831.89 tokens/sec`로 Cache 사용 시 Latency가 각각 약 `11.44%`·`11.20%` 줄었다. No-cache의 개념적 Token-position `230`과 Cache의 `21` 차이보다 시간 차이가 작았던 이유를 tiny 모델·짧은 Sequence에서 Python 생성 반복·Kernel Launch·argmax·Tensor 연결 같은 고정 비용의 비중이 크기 때문이라고 한정했으며, 다른 로컬 CPU 수치와 직접 우열을 비교하지 않았다. 이 단계 뒤에 Peak VRAM과 Profiler 분석을 이어서 수행했다.

    RunPod에서 tiny GPT-2에 `I study`를 넣은 한 번의 GPU Forward를 PyTorch Profiler로 기록했다. `key_averages()` 표의 `Self`는 해당 연산 자체, `Total`은 하위 연산을 포함한 비용이고, `# of Calls`와 평균 시간·CPU/CUDA 비율·연산별 메모리의 계산 기준을 실제 수치로 읽었다. `aten::mm`의 `Self CUDA 18.655us`와 `ampere_sgemm_128x32_tn`의 `18.655us`는 두 번의 계산이 아니라 같은 행렬 곱셈을 PyTorch ATen 연산과 실제 CUDA Kernel이라는 서로 다른 계층에서 본 결과라고 설명했다. ATen은 Attention이 아니라 Tensor 연산의 공통 표현이며, CPU Tensor면 CPU 구현이 계산하고 CUDA Tensor면 CPU가 CUDA Kernel 실행을 등록해 GPU가 계산한다고 자기 말로 정리했다. `aten::mm`의 CUDA 메모리 `393KB`가 Logit Shape `[1,2,50257]`와 float32 4Byte 계산값 약 `393KiB`에 대응함을 확인했고, 전체 `Self CPU 6.267ms`와 `Self CUDA 137.439us` 차이는 작은 모델·Batch 1·Prompt 2의 Kernel 계산이 짧고 CPU 준비·등록 비용 비중이 컸던 결과이지 CPU가 모델 계산 대부분을 대신했다는 뜻은 아니라고 구분했다. Tokenizer가 만든 CPU 입력 `[1,2]`를 `.to("cuda")`로 옮기고, tiny GPT-2 Forward로 GPU Logit `[1,2,50257]`을 만든 뒤 `.to("cpu")`로 되가져오는 전체 구간을 PyTorch Profiler로 기록했다. H2D는 Host인 CPU 메모리에서 Device인 GPU 메모리로, D2H는 그 반대 방향으로 복사한다는 뜻이며, `.to()`가 원본 Tensor를 변신시키는 것이 아니라 대상 장치에 복사본을 만든다는 점을 연결했다. 장치 이동은 `aten::to → aten::_to_copy → aten::copy_`와 `cudaMemcpyAsync`로, GPU 계산은 `aten::embedding`·`aten::native_layer_norm`·`aten::addmm`·`aten::bmm`·`aten::mm`과 실제 CUDA Kernel로 나타났다. `non_blocking=False`여도 내부에서 비동기 복사 API로 등록한 뒤 `cudaStreamSynchronize`로 완료를 기다릴 수 있다고 구분했다. 최신 실행에서 `Memcpy DtoH (Device -> Pageable) 31.424us`, `ampere_sgemm_128x32_tn 18.432us`, 전체 `Self CUDA time total 187.968us`를 확인했다. H2D 입력은 `int64` 2개인 16Byte라 CUDA 시간 상위 40행에서 `Memcpy HtoD` 장치 이벤트가 보이지 않았고, Kernel 재시작 직후의 Lazy Loading 가능성과 작은 단일 Forward 조건 때문에 이 수치를 일반 성능 Benchmark로 해석하지 않는 한계를 남겼다.
