Batch는 GPU 사용 여부가 아니라 데이터를 묶어 전달하는 단위이고, 실제 계산은 선택한 device에서 수행된다고 구분했다. 각 Batch의 zero_grad → prediction → loss → backward → step을 100 Epoch 반복해 학습 전 전체 Loss 38.047859가 1.64 × 10⁻¹⁰까지 줄고 예측이 [2,5,8]에 가까워짐을 확인했다. 한 Epoch를 마친 뒤 출력하면서 epoch: 0이라고 쓰던 로그는 실제 1회 학습 뒤 값이므로 epoch + 1로 고쳤다.

MLP의 Batch·Feature 차원과 ReLU·Logit 구분

ChurnMLP를 [batch,45] → Linear(45,16) → ReLU → Linear(16,1) → [batch,1]로 만들었다. 64는 바뀔 수 있는 Batch 고객 수이고 45는 고정 입력 Feature 수이며, 16은 고객 한 명의 45개 값을 학습 가능한 중간 조합 16개로 바꾼 개수라고 설명했다. ReLU는 음수를 정확히 0으로 만들지만 양수를 1 이하로 제한하지 않고, 마지막 Linear의 Logit은 음수·1보다 큰 수를 포함한 임의의 실수가 될 수 있음을 구분했다.

Sigmoid 출력과 BCE Loss 이해 진행

Sigmoid가 제한 없는 Logit을 0~1 사이로 압축하며, 현재 학습 전 값은 과하게 해석하지 않고 학습 전 sigmoid 출력값이라고 부르기로 했다. 첫 고객의 z=-0.2608에서 p=0.4352, 정답 y=0이므로 개별 BCE가 -log(1-p)=-log(0.5648)≈0.571임을 따라 계산했다. 고객별 Loss 64개를 기본 reduction="mean"으로 평균내 초기 Batch Loss 0.6564000844955444가 되는 흐름을 확인했다. 출력값 0.8에서는 정답 0의 -log(0.2)가 정답 1의 -log(0.8)보다 크며, e-x가 더 작은 값이 되려면 x가 더 커야 한다는 관계로 설명했다. 분산은 값에서 평균을, MSE는 예측에서 정답을 빼는 방식이며 BCE는 정답 쪽 sigmoid 출력값에 -log를 적용하는 별도 Loss임을 구분했다. 전체 BCE 계산을 자료 없이 다시 구성하는 확인은 남아 있다. 자세한 내용은 회원 이탈 MLP와 BCE 문서에 정리했다.

회원 이탈 MLP의 SGD 한 Step 실행

SGD(model.parameters(),lr=0.1)를 연결하고 한 Batch에서 zero_grad → forward → BCE → backward → step을 한 번 실행했다. 같은 Batch를 no_grad()에서 다시 계산했을 때 Loss가 0.6564000844955444 → 0.6511512994766235로 내려갔다. 사용자는 optimizer.step() 한 번마다 Gradient와 learning rate를 기준으로 weight·bias가 조금 조정되고, 이번 한 번의 수정에서는 Loss가 소폭 감소한 것이라고 자기 말로 설명했다. SGD 한 Step의 원리는 확인했지만 한 Batch 과적합이나 전체 Train·Validation 루프 완료로 표시하지 않는다.

nn.Linear 파라미터와 다차원 입력 질문 진행

Linear(45,16)의 weight [16,45] 720개와 bias 16개, Linear(16,1)의 weight 16개와 bias 1개로 전체 학습 파라미터가 753개라는 계산을 설명 중이다. Linear weight는 [out,in]인 2차원 행렬이지만 입력 Tensor는 3차원 이상일 수 있고 마지막 Feature 축만 바뀐다는 점도 현재 질문으로 남아 있다. nn.Linear(45,33,16)의 세 번째 값은 새 출력 차원이 아니라 bias 위치 인자이며, 45 → 33 → 16에는 Linear 두 계층이 필요하다. 이 내용은 아직 자료 없이 Shape·파라미터 수를 다시 설명한 증거가 없어 완료로 기록하지 않는다.

nn.Linear의 구조·파라미터·예측 출력 구분

print(model)은 Linear(in_features=1,out_features=1,bias=True)라는 구조를, model.parameters()는 실제 학습 대상인 weight·bias Tensor를, model(x)는 입력으로 만든 실제 예측값을 보여 준다는 차이를 확인했다. weight는 기울기, bias는 절편이며 무작위 초기값에서 학습을 시작한다.

MSE Loss와 순간변화율의 연결

MSE는 분산의 value−mean이 아니라 prediction−target을 제곱해 평균내며 음수가 될 수 없다는 점을 구분했다. loss.backward()는 weight를 조금 움직였을 때의 Loss 순간변화율과 bias를 조금 움직였을 때의 순간변화율을 각각 계산한다는 흐름을 작은 숫자로 다시 연결했다.

동일한 수정 전 상태에서 두 Gradient 계산

한 Step에서 ∂L/∂weight는 현재 bias를 고정한 관점으로, ∂L/∂bias는 현재 weight를 고정한 관점으로 계산하지만 한쪽을 먼저 수정한 값으로 다른 쪽을 계산하지 않는다는 점을 확인했다. 두 Gradient는 같은 수정 전 (weight,bias) 상태에서 만들어지고 optimizer.step()이 함께 적용하며, 새 값의 상호 영향은 다음 Epoch부터 반영된다.

SGD·학습률·Gradient 누적

SGD(model.parameters(),lr=0.1)은 수정 대상과 규칙을 등록할 뿐 즉시 값을 바꾸지 않으며, 학습률 0.1은 고정 0.1이 아니라 각 Gradient 크기의 10%를 적용한다는 뜻이다. Loss를 계산하는 Forward에서는 Gradient가 쌓이지 않고 backward()에서 기존 .grad에 누적되므로, 매 Step의 현재 Gradient만 쓰려면 zero_grad()가 필요하다는 점을 구분했다.

데이터 식별 조건과 no_grad()

x=3,y=11 하나만으로는 3×weight+bias=11을 만족하는 조합이 여러 개라 두 파라미터를 유일하게 정할 수 없고, 서로 다른 입력 데이터가 추가 조건을 제공해야 한다는 점을 확인했다. no_grad()는 기존 Gradient를 지우는 기능이 아니라 추론 시 backward에 필요할 연산 경로와 중간값을 저장하지 않아 큰 모델의 메모리 부담을 줄이는 기능으로 정리했다.

nn.Module·Optimizer 챕터 완료

y=3x+2를 101 Epoch 학습해 Loss를 9.36×10⁻⁸까지 줄였다. 최종 weight 2.9996803, bias 2.0004435, 새 입력 x=3의 예측 10.999484와 정답 11을 검증했다. Epoch 20부터 절대 오차가 이미 작았고, 실제 학습에서는 Validation 개선이 멈추는 시점을 Early Stopping 기준으로 삼는다는 점도 연결했다. 다음 챕터는 Dataset·DataLoader와 Batch 학습이다.

범주형 Feature 전체를 One-Hot Encoding

문자열 범주형 Feature들을 OneHotEncoder로 숫자 열로 바꾸고, 각 범주를 별도의 자리로 표현하는 흐름을 확인했다. ColumnTransformer의 한 작업이 (작업 이름, 실행할 변환기, 적용할 컬럼 목록)으로 구성된다는 점도 코드와 연결했다.

Train에 맞추고 Validation에는 같은 기준 적용

전처리기는 Train 데이터로 fit해 범주별 자리를 정하고, Validation에는 새로 자리를 만들지 않고 Train에서 정한 자리를 그대로 사용해 transform해야 한다고 이해했다. 전체 변환 결과 Shape은 Train [5634,45], Validation [1409,45]였고 두 데이터의 Feature 수가 45개로 일치했다.

LayerNorm을 실제 숫자와 연결

첫 Residual 결과의 Token별 평균을 빼고 표준편차로 나누면 각 Token의 마지막 특징 차원이 평균 0, 분산 1에 가까워진다는 흐름을 확인했다. 2.9802e-08은 정확한 0을 Float로 계산하면서 생긴 매우 작은 오차이므로 사실상 0으로 해석했다. 두 번째 Residual 뒤에도 같은 이유로 별도의 nn.LayerNorm(d_model)이 필요하다고 먼저 예측하고 실행 결과로 검증했다.

FFN의 확장·GELU·축소 의미

nn.Linear(2,4)는 층을 만드는 것이고, expanded_output = ffn_expand(normalized_output)은 그 층에 실제 Tensor를 넣어 실행하는 것임을 구분했다. 첫 Linear는 Token마다 더 넓은 중간 특징 공간을 만들고, GELU는 음수를 곧바로 노이즈로 판정하는 것이 아니라 학습된 중간 반응의 전달 정도를 부드럽게 조절하며, 두 번째 Linear는 4 → 2로 돌아오면서 현재 표현에 더할 수정값을 만든다고 이해했다.

두 번째 Residual과 Dropout

x + Attention을 정돈한 normalized_output에 FFN이 만든 contracted_output을 다시 더해 현재 표현이 사라지지 않게 한다고 설명했다. Dropout은 훈련 중 일부 원소를 확률적으로 0으로 만들고 살아남은 값을 보정하지만 Shape은 유지하며, eval()에서는 무작위 제거가 꺼져 같은 입력에 같은 결과가 나오는 것을 확인했다.

TransformerBlock.forward() 완성

Attention → Attention Dropout → 첫 Residual → LayerNorm → FFN 확장 → GELU → 축소 → FFN Dropout → 두 번째 Residual → LayerNorm을 하나의 클래스에 연결했다. 입력과 최종 출력 Shape이 모두 [1,2,2]로 유지되고, 최종 Token별 평균은 사실상 0, unbiased=False 분산은 1임을 확인했다.

Score 분산과 √head_dim Scaling의 연결 완성

head_dim=2인 한 Score를 Score=A+B로 두고, (A+B)²=A²+2AB+B²를 여러 Score에 걸쳐 평균내는 과정을 따라갔다. 평균 0·분산 1·독립이라는 전제에서는 A²와 B²의 평균이 각각 1이고 AB의 평균이 0에 가까워져 Score 분산이 2, 표준편차가 √2가 된다는 점을 확인했다.

Score 평균의 제곱과 Score 제곱의 평균 구분

Score=[2,0,0,-2]에서 Score 평균의 제곱은 0이지만, 각 Score를 먼저 제곱한 값은 [4,0,0,4]이고 그 평균은 2다. Score 평균이 0일 때 분산 공식의 (Score-평균)²가 Score²가 되므로 Score 제곱의 평균 2가 곧 분산이고, 표준편차는 √2가 된다는 중간 단계를 명확히 연결했다.

통계적 전제와 개별 Score의 구분

모든 원소가 같은 방향이거나 서로 강하게 연관된 경우에도 항상 √head_dim이 나오는 것은 아니다. 각 Score 하나의 값이 반드시 커진다는 뜻도 아니며, 평균 0에 가까운 독립적인 곱을 여러 개 합산한 Score 집단의 전체적인 퍼짐이 커진다는 통계적 분석임을 구분했다.

Q·K·V Projection부터 Head 분리, Score·Scaling·Softmax, Value 가중합, Token 기준 재정렬, d_model 병합과 Output Projection W_O까지 하나의 nn.Module.forward()로 연결했다. 최종 projected_output의 Shape이 [batch,token,d_model]=[1,2,2]로 유지되는 것을 실행 결과로 확인했다.

[1,2,3,1] Tensor에서 Head A의 [0,1,2]와 Head B의 [3,4,5]가 transpose(1,2) 뒤 Token별 [[0,3],[1,4],[2,5]] 묶음으로 바뀔 것을 먼저 주석으로 예측했다. 실제 Shape [1,3,2,1]과 값이 예상과 일치했다.

테이블의 Row는 Page에 저장되고, Heap은 우선순위 자료구조가 아니라 여기서는 Row가 특정 정렬 순서를 보장받지 않는 테이블 저장 구조를 뜻한다는 점을 구분했다. Index는 검색 값에서 실제 Row 위치로 이동하기 위한 별도 탐색 구조이고, B-tree의 Leaf와 연결된 위치 정보를 통해 모든 Page를 순차 검색하는 비용을 줄인다는 흐름을 정리했다.

Q·K·V Projection과 nn.Linear 내부 계산 확인

입력 x=[1, 2, 2]를 서로 다른 nn.Linear(2, 2, bias=False)에 통과시켜 Q·K·V를 만들었다. Linear가 마지막 벡터 차원만 변환하므로 Shape은 유지되지만, 각 Projection이 별도의 가중치를 사용해 값과 역할은 달라진다는 점을 확인했다. 또한 x @ weight.T를 직접 계산하고 torch.allclose()가 True임을 확인해 Linear의 결과와 직접 행렬곱이 같다는 것을 검증했다.

Score Scaling에서 평균 0과 분산의 연결 복습

QKᵀ로 [1,2,2] Score를 만들고 현재 d_k=2임을 확인했다. 분산은 Var(X)=E[(X-E[X])²]이며, 초기화 분포의 기댓값을 0으로 두었기 때문에 Var(X)=E[X²]로 단순화된다는 빠졌던 연결고리를 바로잡았다. 각 곱의 평균 0·분산 1과 독립성을 근사하면 Score의 실제 값이 d_k가 아니라 분산이 d_k, 표준편차가 √d_k가 되므로 이를 나누어 약 1 규모로 맞춘다는 점을 정리했다.

Softmax와 dim=-1의 의미 확인

scaled_scores에 마지막 차원 Softmax를 적용해 attention_weights를 만들었다. Shape [1,2,2]에서 각 행은 하나의 Query가 두 Key를 참고하는 비율이고, dim=-1은 Key 방향으로 행별 정규화하므로 각 행의 합이 1이 된다. 실제 결과 [0.5084,0.4916], [0.4306,0.5694]를 통해 Query1은 Key1을, Query2는 Key2를 조금 더 참고한다는 것을 확인했다.

attention_weights @ value를 실제 숫자로 검산

Attention weight의 Shape이 3차원인 이유는 맨 앞의 Batch 차원 때문이며, value[0,0]은 Token1의 한 좌표가 아니라 Value 벡터 전체라는 점을 구분했다. 첫 번째 Query에 대해 0.5084×Value1 + 0.4916×Value2를 직접 계산해 [-0.0971,0.0557]을 얻고 output[0,0]과 일치함을 확인했다. Attention은 Value들의 가중합이므로 두 항 사이에는 뺄셈이 아니라 덧셈을 사용한다. 또한 Attention weight 행렬을 [[a1,a2],[a3,a4]]로 놓았을 때 두 번째 행은 Q2→K1과 Q2→K2의 비율이며, Output2=a3×V1+a4×V2로 두 번째 Token이 첫 번째 Token의 정보도 가져온다는 점을 연결했다.

현재 Attention 코드는 Q와 K의 실제 평균이나 분산을 측정하지 않고 마지막 차원 크기만 사용한다. 따라서 모든 입력에서 Score 표준편차를 정확히 1로 만드는 연산이 아니라, Q·K 원소가 중심 0 근처이고 비슷한 분산을 가지며 독립적이라는 일반적인 통계적 전제에서 차원이 커질 때 생기는 Score 규모 증가를 완화하는 고정 Scaling임을 바로잡았다.
