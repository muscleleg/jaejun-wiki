Score 분산과 √head_dim Scaling의 연결 완성

head_dim=2인 한 Score를 Score=A+B로 두고, (A+B)²=A²+2AB+B²를 여러 Score에 걸쳐 평균내는 과정을 따라갔다. 평균 0·분산 1·독립이라는 전제에서는 A²와 B²의 평균이 각각 1이고 AB의 평균이 0에 가까워져 Score 분산이 2, 표준편차가 √2가 된다는 점을 확인했다.

Score 평균의 제곱과 Score 제곱의 평균 구분

Score=[2,0,0,-2]에서 Score 평균의 제곱은 0이지만, 각 Score를 먼저 제곱한 값은 [4,0,0,4]이고 그 평균은 2다. Score 평균이 0일 때 분산 공식의 (Score-평균)²가 Score²가 되므로 Score 제곱의 평균 2가 곧 분산이고, 표준편차는 √2가 된다는 중간 단계를 명확히 연결했다.

통계적 전제와 개별 Score의 구분

모든 원소가 같은 방향이거나 서로 강하게 연관된 경우에도 항상 √head_dim이 나오는 것은 아니다. 각 Score 하나의 값이 반드시 커진다는 뜻도 아니며, 평균 0에 가까운 독립적인 곱을 여러 개 합산한 Score 집단의 전체적인 퍼짐이 커진다는 통계적 분석임을 구분했다.

Head 병합과 Output Projection W_O

Head별 Attention 결과를 transpose()와 reshape()로 이어 붙인 multi_head_output은 여러 관점의 결과를 나열한 상태라고 이해했다. 이어 붙이는 연산만으로는 Head 정보가 섞이지 않으므로, W_O Linear가 각 특징을 학습된 비율로 다시 조합해 다음 블록에서 사용할 d_model 벡터로 만든다는 역할을 정리했다. 포지셔널 인코딩은 입력 x에 이미 더해져 Q·K·V Projection을 통과하므로 Head 계산 중 사라지는 값이 아니라는 점도 확인했다.

Output Projection을 수동 행렬곱으로 검증

multi_head_output[0,0]이 [0,0,:]와 같은 0번째 Batch·0번째 Token의 전체 벡터임을 확인했다. 이 벡터를 W_O.T에 직접 곱한 결과와 nn.Linear의 projected_output[0,0]을 torch.allclose()로 비교해 동일함을 검증했다.

MultiHeadAttention(nn.Module) 구현

assert d_model % num_heads == 0으로 특징 차원이 Head 수로 나누어지는지 검사하고, head_dim=d_model//num_heads에서 //가 몫 나눗셈임을 확인했다. Q·K·V Projection은 모두 nn.Linear(d_model,d_model,bias=False)로 등록했다. 클래스 밖에서 self.num_heads를 사용해 생긴 NameError를 통해 self는 인스턴스 메서드 안에서만 사용할 수 있다는 점도 바로잡았다.

Projection과 Head별 Shape 검증

Q·K·V Projection 직후 Shape은 모두 [1,2,2]였고, view()와 transpose(1,2)를 거쳐 [batch,head,token,head_dim]=[1,2,2,1]이 됐다. Head를 나누는 것은 Token을 늘리는 것이 아니라 Token마다 가진 특징 차원을 Head별로 나누는 것임을 다시 확인했다. 현재 head_dim=1에서는 √1=1이므로 Score Scaling 전후 숫자가 같은 것도 정상이다.

임베딩 초기화와 Score Scaling을 분리해 다시 보기

평균 0인 512차원 벡터에서 원소 제곱합의 기댓값을 1로 두면 각 원소의 제곱 기댓값이 1/512, 분산이 1/512, 표준편차가 1/√512로 이어지는 흐름을 자신의 분산 정의와 연결했다. 임베딩에 √d_model을 곱하는 작업과 Score를 √head_dim으로 나누는 작업은 서로를 취소하는 한 쌍이 아니라 목적이 다른 별도 Scaling임을 구분했다.

AGI 기술 지도와 Agent Loop 아티클

AGI를 향한 연구를 하나의 알고리즘 이름으로 보지 않고 모델 구조·학습·메모리·계획·도구 사용·검증·서빙이 연결된 기술 지도로 살펴봤다. Agent Loop에서는 계획 → 실행 → 검증 이후 문제가 발견되면 결과를 다음 계획에 다시 반영하는 반복 구조와 코드 단위 검증의 역할을 읽었다.

LLM 정밀도 형식과 Tensor 원소의 bytes

7B는 입력 Token 수나 만들 수 있는 벡터 종류가 아니라 Embedding·QKV Projection·Output Projection·FFN 등 모델 전체에 학습되어 저장된 숫자가 약 70억 개라는 뜻임을 구분했다. 각 Linear는 입력을 변환하는 가중치 행렬이라는 숫자 표를 가지고 있으며, 70억 개는 이러한 모든 가중치 원소를 합친 수다.

Multi-Head Attention의 Head 분리부터 병합까지

view()를 같은 원소를 유지한 채 Shape을 다시 해석하는 reshape 계열 연산으로 이해했다. [batch,token,d_model]을 [batch,head,token,head_dim]으로 바꾸어 Q·K·V를 Head별로 계산하고, Head마다 [query_token,key_token] Score와 Softmax 비율을 만든 뒤 Value의 가중합을 구했다. dim=-1 합은 각 Query에서 Key 방향 확률을 더해 1이 되는지 검사하는 연산임을 실제 Shape과 연결했다.

각 위치의 Token에는 차원 전체에 걸쳐 서로 다른 sin·cos 파형 모양의 위치 벡터가 더해진다. 따라서 같은 Token이라도 위치마다 다른 벡터가 되고, 모델은 이 서로 다른 파형 패턴을 통해 위치 관계를 학습할 수 있다는 직관을 그림과 함께 정리했다.

테이블의 Row는 Page에 저장되고, Heap은 우선순위 자료구조가 아니라 여기서는 Row가 특정 정렬 순서를 보장받지 않는 테이블 저장 구조를 뜻한다는 점을 구분했다. Index는 검색 값에서 실제 Row 위치로 이동하기 위한 별도 탐색 구조이고, B-tree의 Leaf와 연결된 위치 정보를 통해 모든 Page를 순차 검색하는 비용을 줄인다는 흐름을 정리했다.

Q·K·V Projection과 nn.Linear 내부 계산 확인

입력 x=[1, 2, 2]를 서로 다른 nn.Linear(2, 2, bias=False)에 통과시켜 Q·K·V를 만들었다. Linear가 마지막 벡터 차원만 변환하므로 Shape은 유지되지만, 각 Projection이 별도의 가중치를 사용해 값과 역할은 달라진다는 점을 확인했다. 또한 x @ weight.T를 직접 계산하고 torch.allclose()가 True임을 확인해 Linear의 결과와 직접 행렬곱이 같다는 것을 검증했다.

Score Scaling에서 평균 0과 분산의 연결 복습

QKᵀ로 [1,2,2] Score를 만들고 현재 d_k=2임을 확인했다. 분산은 Var(X)=E[(X-E[X])²]이며, 초기화 분포의 기댓값을 0으로 두었기 때문에 Var(X)=E[X²]로 단순화된다는 빠졌던 연결고리를 바로잡았다. 각 곱의 평균 0·분산 1과 독립성을 근사하면 Score의 실제 값이 d_k가 아니라 분산이 d_k, 표준편차가 √d_k가 되므로 이를 나누어 약 1 규모로 맞춘다는 점을 정리했다.

Softmax와 dim=-1의 의미 확인

scaled_scores에 마지막 차원 Softmax를 적용해 attention_weights를 만들었다. Shape [1,2,2]에서 각 행은 하나의 Query가 두 Key를 참고하는 비율이고, dim=-1은 Key 방향으로 행별 정규화하므로 각 행의 합이 1이 된다. 실제 결과 [0.5084,0.4916], [0.4306,0.5694]를 통해 Query1은 Key1을, Query2는 Key2를 조금 더 참고한다는 것을 확인했다.

attention_weights @ value를 실제 숫자로 검산

Attention weight의 Shape이 3차원인 이유는 맨 앞의 Batch 차원 때문이며, value[0,0]은 Token1의 한 좌표가 아니라 Value 벡터 전체라는 점을 구분했다. 첫 번째 Query에 대해 0.5084×Value1 + 0.4916×Value2를 직접 계산해 [-0.0971,0.0557]을 얻고 output[0,0]과 일치함을 확인했다. Attention은 Value들의 가중합이므로 두 항 사이에는 뺄셈이 아니라 덧셈을 사용한다. 또한 Attention weight 행렬을 [[a1,a2],[a3,a4]]로 놓았을 때 두 번째 행은 Q2→K1과 Q2→K2의 비율이며, Output2=a3×V1+a4×V2로 두 번째 Token이 첫 번째 Token의 정보도 가져온다는 점을 연결했다.
