Rook-Ceph 기반 Kubernetes 스토리지 구성 및 Cinder CSI 비교 — 보류 백로그 보류 이유와 현재 선택 현재 우선순위는 vLLM·llm-d와 챗봇 UI 구성이다. Cinder CSI로 테스트 PVC 생성, VM 디스크 연결, Pod의 파일 읽기·쓰기를 확인했으므로 우선 cinder-ssd StorageClass를 사용한다. Ceph는 저장소 운영 자체를 학습할 때 별도 실습으로 재개한다. Ceph용 VM·디스크·Helm 리소스는 아직 설치하지 않는다. 학습 목적 미리 VM에 할당한 데이터 디스크로 Kubernetes 저장소를 운영하는 구조를 이해한다. Ceph는 여러 노드의 디스크에 데이터를 분산·복제하는 저장소이고, Rook은 Kubernetes에서 Ceph의 배포·운영을 관리하며, Ceph CSI는 PVC와 Ceph 볼륨을 연결한다. 애플리케이션 워커마다 전용 Ceph 서버 하나가 필요한 구조가 아니라 여러 워커가 공통 Ceph 클러스터를 이용하는 구조를 실습한다. RBD 블록 볼륨과 CephFS 공유 파일시스템의 차이를 구분한다. 재개 전 결정할 배치 기존 애플리케이션 워커에 Ceph를 함께 배치하는 방법, 같은 Kubernetes 클러스터에 전용 스토리지 노드를 추가하는 방법, 외부 Ceph 클러스터를 사용하는 방법을 비교한다. 처음부터 전용 VM 세 대 추가로 확정하지 않는다. 기존 일반 워커 두 대를 활용하고 세 번째 일반 워커를 추가하는 선택지도 검토한다. GPU 워커의 추론 부하와 control plane의 안정성을 고려해 저장소 배치를 결정한다. 자원·장애 범위 점검 실제 호스트·VM의 CPU, 메모리, 디스크 여유와 OpenStack 쿼터를 조회한다. Nova가 보고하는 로컬 디스크 용량과 Cinder 백엔드의 여유 용량을 구분한다. 노드별 MON·MGR·OSD 자원과 복구 중 I/O 예산을 산정한다. 3복제 학습 구성은 원시 용량의 약 1/3에서 추가 여유 공간을 제외한 사용 가능 용량을 예상한다. 모든 VM이 하나의 물리 호스트와 공통 SSD 백엔드에 있으므로 VM 장애 복구 실습은 가능해도 물리 서버 장애에 대한 고가용성을 확보했다고 주장하지 않는다. 실행 순서 1. MON·MGR·OSD, Pool, 복제 수, failure domain, RBD·CephFS, CSI의 역할을 정리한다. 2. 세 노드에 복제본을 분산하는 학습 배치를 설계하고 필요한 VM 및 빈 데이터 디스크를 Terraform으로 선언한다. 루트 디스크와 데이터 디스크를 확실히 식별하고 기존 데이터 디스크를 초기화하지 않는다. 필요한 노드만 Kubespray로 합류시킨다. 3. 재개 시점 Kubernetes와 호환되는 Rook·Ceph 버전 및 Helm values를 고정한다. 명시적으로 선택한 노드·디스크만 사용하며 모든 디스크를 자동 선택하는 설정을 피한다. 4. Rook Operator, CephCluster, Ceph CSI 상태를 확인하고 CephBlockPool과 별도의 ceph-rbd StorageClass를 만든다. 기존 cinder-ssd와 공존시키고 기본 StorageClass는 무심코 변경하지 않는다. 5. 테스트 PVC와 Pod로 파일 쓰기·읽기를 확인한다. Pod 재생성 후 데이터 유지, 다른 노드로의 안전한 볼륨 재연결, RWO 제약을 확인한다. 6. 테스트 데이터로 OSD 또는 스토리지 VM 한 대의 중단·복구를 실습하고 Ceph 상태, 복제·재동기화, 애플리케이션 I/O 영향을 기록한다. 복제 수와 최소 복제 수 조건을 확인하며 무중단을 전제하지 않는다. 7. Cinder CSI와 Ceph CSI의 PVC 생성 경로, 용량 할당 단위, 복제 비용, 장애 범위, 운영 부담을 비교한다. 필요할 때 CephFS의 RWX를 별도 확장 실습으로 진행한다. 8. reclaimPolicy, 백업·복구, PVC·Pool·클러스터 제거 순서를 정리한다. 데이터 보존 여부를 확인한 뒤 정리한다. 중요한 경계 Ceph용 데이터 디스크를 Cinder 볼륨으로 한 번 할당할 수 있다. 이후 Ceph PVC는 그 디스크 위의 Ceph Pool에서 생성된다. 이것은 매 PVC마다 Cinder 볼륨을 직접 생성하는 현재 구성과 관리 경계가 다르지만, 물리 호스트의 자원 소비와 장애 의존성이 없어지는 것은 아니다. OpenStack Cinder 백엔드 자체를 Ceph로 교체하는 작업은 이번 실습 범위에 넣지 않는다. 재개 조건과 완료 기준 현재 모델 서빙·UI 구성을 먼저 마친 뒤, 별도 저장소 운영을 학습할 시간과 충분한 자원을 확보했을 때 재개한다. 완료 시 설치 재현 자료, PVC 영속성 확인 결과, 단일 VM 장애·복구 관찰 결과, Cinder 대비 선택 기준과 단일 물리 호스트의 한계를 남긴다. 지금은 설치 완료나 학습 완료로 처리하지 않는다.
