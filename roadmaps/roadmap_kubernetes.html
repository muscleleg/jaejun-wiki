Kubernetes 플랫폼 심화

객체 이름과 kubectl 명령을 넓게 외우지 않는다. Desired State가 Control Loop를 통해 실제 Pod·Network·Storage·권한·배포 상태로 수렴하는 과정을 관찰하고, 장애를 Application·Kubernetes·Container·Linux·Cloud 계층으로 좁히는 역량을 만든다.

활성화 경계

완전한 초보 로드맵이 아니다Control Plane·Workload·RBAC·Network·Storage·Helm·GitOps 관련 문서와 Kubernetes 운영 관측 AI, Function Calling 개인 프로젝트가 이미 있다. 다만 과거 메모와 프로젝트 범위를 Kubernetes 플랫폼 전체 이해로 자동 환산하지 않는다.
관심은 보존하고 현재 집중은 유지한다Kubernetes를 더 깊게 파고 싶은 방향은 보존하지만 Road to LLM inference의 현재 관문, PyTorch 추론 Baseline → vLLM → Multi-GPU 순서나 AI 코어 진행률을 바꾸지 않는다.
언제 시작하는가핵심 여정을 완료했거나 사용자가 별도 Kubernetes 세션을 명시적으로 선택했을 때 시작한다. 핵심 여정의 LLM Serving·GPU Workload에서 Scheduling·Network·Storage 문제가 실제 blocker가 되면 필요한 진단만 수행하고 즉시 원래 관문으로 돌아간다.

플랫폼 역량 경로

1 · Container와 Cluster 기반Linux Namespace·cgroup·Process·Filesystem·Network를 Container 경계와 연결한다. Control Plane과 Worker의 구성 요소, API Server·etcd·Scheduler·Controller Manager·kubelet·Container Runtime의 책임과 통신 경계를 설명한다.
2 · API·Desired State·Control LoopManifest가 API Object로 저장되고 Controller가 현재 상태와 원하는 상태의 차이를 반복 조정하는 흐름을 추적한다. Deployment 변경에서 ReplicaSet·Pod 생성, Condition·Event·Status 변화와 Rollout을 실제 객체로 확인한다.
3 · Workload·Scheduling·ResourcePod·Deployment·StatefulSet·DaemonSet·Job의 책임을 Workload 요구로 선택한다. Request·Limit, QoS, Probe, Affinity·Taint·Toleration, Priority와 Eviction을 연결하고 Pending·OOMKilled·CrashLoopBackOff를 서로 다른 증거로 진단한다.
4 · Network와 요청 경로Pod IP, CNI, Service·EndpointSlice, DNS, kube-proxy 또는 대체 Data Plane, Ingress·Gateway와 Network Policy를 한 요청 경로로 연결한다. DNS 실패, Endpoint 부재, Route·MTU·Policy 문제를 Packet과 객체 상태로 구분한다.
5 · Storage와 Stateful WorkloadVolume, PV·PVC·StorageClass, CSI, Access Mode와 Reclaim Policy를 실제 Mount·Block I/O 흐름에 연결한다. StatefulSet의 안정된 Identity, 데이터 보존, Backup·Restore와 Node 장애 뒤 재연결 조건을 검증한다.
6 · Security와 Multi-tenancyAuthentication·Authorization, ServiceAccount·RBAC, Secret, Security Context, Pod Security, Network Policy와 Image 신뢰 경계를 구분한다. 최소 권한의 조회·배포 권한을 만들고 허용·거절 요청과 Audit 증거를 확인한다.
7 · Delivery·Observability·운영Manifest·Helm·GitOps의 Desired State 원본과 Rollout·Rollback 경계를 비교한다. Metric·Log·Event·Trace를 요청 ID와 Resource 상태에 연결하고 Health·Readiness·Liveness, SLO와 Alert가 어떤 실패를 감지하는지 설명한다.
8 · Failure Lab와 AI Workload 전이Image Pull, Scheduling, Probe, Network, Storage, 권한 또는 Node Resource 실패 중 하나씩 작은 장애를 주입해 가설 → 관찰 → 반증 → 복구 → 재검증 기록을 만든다. 이후 필요할 때만 GPU Scheduling·Device Plugin·Node Label·Autoscaling과 LLM Inference Routing을 같은 운영 계약에 연결한다.

완료 조건

Control Loop 설명
Manifest 적용부터 실제 Pod가 Running·Ready가 될 때까지 참여 구성 요소와 상태 변화를 자료 없이 설명한다.
요청과 데이터 경로 추적
외부 요청이 Service를 거쳐 Pod에 도달하는 경로와 Stateful Pod의 I/O가 Storage Backend에 도달하는 경로를 각각 추적한다.
안전한 변경과 복구
배포 변경 전후의 객체·Metric을 비교하고 실패 조건에서 Rollback 또는 원상 복구를 실제로 검증한다.
계층적 장애 진단
Application, Kubernetes Object, Container Runtime, Linux, Network·Storage 중 어느 계층의 실패인지 증거로 좁힌다.
새 Workload로 전이
처음 보는 API 또는 AI Workload의 요구에서 Resource·Network·Storage·Security·관측 구성을 도출하고 선택 이유를 설명한다.
