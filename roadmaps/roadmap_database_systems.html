Database 시스템 심화

SQL 문법을 넓게 외우는 데서 멈추지 않는다. 한 Query와 Transaction이 Parser·Planner·Executor를 거쳐 Buffer와 Page·Index를 읽고, Lock·MVCC와 WAL을 통해 동시성·일관성·복구를 보장하는 흐름을 관찰한다. PostgreSQL을 대표 실험 대상으로 삼되 특정 제품의 명령만 암기하지 않고 다른 관계형 Database에도 전이할 원리를 만든다.

활성화 경계

데이터 엔지니어링과 역할을 분리한다데이터 엔지니어링 로드맵은 여러 원천에서 검증된 Dataset을 반복 생성하는 흐름에 집중한다. 이 로드맵은 그 Pipeline이 읽고 쓰는 Database 내부에서 저장·조회·동시성·복구가 어떻게 성립하는지 깊게 파고든다.
기존 경험을 출발점으로 쓴다SQL CRUD, JDBC 실행, PostgreSQL 구조와 Index 문서는 기초 증거다. 문서가 존재한다는 이유로 완료 처리하지 않고, Query Plan·동시 Transaction·Crash Recovery를 직접 예측하고 관찰한 관문만 닫는다.
언제 시작하는가Road to LLM inference를 완료했거나 사용자가 별도 Database 세션을 명시적으로 선택했을 때 시작한다. 현재 핵심 관문에서 Query 성능·정합성·Lock·복구가 실제 blocker가 되면 필요한 최소 실험만 수행하고 즉시 핵심 여정으로 돌아간다.
첫 검증은 한 Query로 시작한다작은 PostgreSQL Table에 충분한 Row를 넣고 Index 전후의 EXPLAIN ANALYZE, 읽은 Page와 실행 시간을 비교한다. 결과를 보기 전에 Sequential Scan과 Index Scan 선택 조건을 먼저 예측한다.

3 · Query Planner와 실행Parse·Rewrite·Plan·Execute 단계, Cardinality Estimation과 Cost를 읽는다. Sequential·Index·Bitmap Scan, Nested Loop·Hash·Merge Join, Sort·Aggregate 중 선택된 Operator를 EXPLAIN ANALYZE의 예상·실제 Row, Buffer와 시간으로 검증한다.

완료 조건

Schema와 Query 결과 예측
요구사항에서 Key·관계·제약을 도출하고 Join 전후 Row 수, 중복과 Null이 생기는 조건을 자료 없이 설명한다.
실행 계획으로 병목 진단
느린 Query 하나에서 실제·예상 Cardinality, Scan·Join Operator와 Buffer를 읽어 원인을 좁히고 변경 전후를 같은 조건으로 비교한다.
동시성 현상 재현
두 Transaction의 실행 순서를 직접 제어해 Blocking·Conflict 또는 Deadlock을 재현하고 Isolation·Lock·MVCC 관점에서 결과를 설명한다.
실패 뒤 데이터 복구
Backup과 WAL을 사용해 지정 시점 또는 마지막 일관된 상태로 복원하고 Schema·Row 수·핵심 제약과 Query 결과를 다시 검증한다.
확장 선택 근거
Query·Write·Connection·Storage·가용성 중 실제 병목을 측정한 뒤 Index, Partition, Replica, Pool 또는 Cache 중 가장 작은 해결책을 선택한다.

첫 통합 결과물

관찰 대상관계와 제약이 있는 작은 서비스 Schema를 PostgreSQL에 만들고 재현 가능한 Seed Data와 대표 읽기·쓰기 Query를 준비한다.
성능 실험데이터 분포와 조건을 고정한 뒤 Index 전후, Join 방식과 Transaction 범위 변화가 Plan·Buffer·Latency에 미치는 영향을 비교한다.
동시성 실험두 Session에서 같은 Row 또는 범위를 읽고 변경하면서 Isolation Level별 결과, Lock Wait와 Deadlock 탐지·해소 과정을 기록한다.
복구 실험변경 전 Backup과 WAL 경계를 확보하고 의도적인 잘못된 변경 또는 중단 뒤 원하는 시점으로 복원해 데이터 계약을 다시 검증한다.
