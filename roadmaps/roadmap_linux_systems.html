Linux 시스템 심화

활성화 경계

관심은 보존하고 의무는 만들지 않는다Linux를 깊게 배우고 싶은 방향을 장기 계획에 남긴다. 현재 AI·ML과 코딩 테스트의 다음 행동을 교체하거나 별도의 진도 압박으로 사용하지 않는다.
언제 시작하는가CS 운영체제 기반을 검증한 뒤 Linux 구현으로 더 깊게 들어가고 싶을 때, 또는 Container·Kubernetes·GPU Worker의 실제 자원 문제를 Linux 수준에서 진단해야 할 때 시작 준비 상태로 올린다.

심화 경로

1 · Boot·Kernel·User SpaceBootloader 이후 Kernel 초기화와 User Space의 init·service 시작을 큰 흐름으로 구분하고, Application이 System Call을 통해 Kernel 자원을 사용하는 경계를 설명한다.
2 · Process·Thread·SignalProcess 생성·상태·부모와 자식, File Descriptor, Environment, Signal과 종료 코드를 관찰한다. 실행 중인 서비스 하나를 Process Tree와 열린 자원 기준으로 설명한다.
3 · CPU·Memory 관찰Load Average, CPU 사용률, Context Switch, RSS·Virtual Memory, Page Cache, Swap과 OOM을 구분한다. CPU Bound와 Memory Pressure 상황을 각각 만들고 관찰값으로 병목을 판정한다.
4 · Filesystem·Block I/OPath, inode, File Descriptor, Mount, Buffer·Page Cache와 Block Device를 연결한다. 용량 부족, inode 부족, 권한, 느린 I/O를 서로 다른 증거로 구분한다.
5 · Namespace·cgroup·ContainerPID·Mount·Network Namespace와 cgroup의 자원 제한을 직접 비교한다. Container가 별도 Kernel을 가진 VM이 아니라 격리된 Process라는 점을 Process·Mount·Network·Resource 관찰로 검증한다.
6 · 장애 진단 결과물느린 API, Memory 증가, File Descriptor 고갈 또는 Container OOM 중 하나를 재현한다. 현상 → 가설 → 관찰 명령 → 반증 → 원인 → 수정 → 재검증 순서의 공개 가능한 진단 기록을 만든다.

완료 조건

Process 실행 경로
Service 하나의 Process Tree, 열린 File·Socket, Memory와 종료 신호를 자료 없이 설명한다.
자원 병목 구분
CPU, Memory, Disk I/O와 File Descriptor 문제를 같은 “느림”으로 뭉치지 않고 서로 다른 지표로 판정한다.
Container 격리 검증
Namespace와 cgroup이 각각 무엇을 분리하고 제한하는지 Host와 Container 관찰값으로 비교한다.
재현 가능한 진단
실패 하나를 다시 만들고 수정 전후의 같은 지표로 원인 제거를 확인한다.
