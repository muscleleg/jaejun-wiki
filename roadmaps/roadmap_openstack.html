현재 상태와 활성화 경계

관심 보관 · 처음부터 시작하지 않음Kolla-Ansible AIO에서 VM·Network·Floating IP·Volume을 종단 간 실행한 증거가 있으므로 빈 계획이 아니다. 다만 범용 OpenStack 역량 전체를 활성 학습 중인 것은 아니며 현재 AI 코어 진행률에는 포함하지 않는다.
언제 다시 활성화하는가Private Cloud 설계·운영을 다시 결과물로 선택하거나, Compute·Network·Storage 내부의 실제 장애를 서비스와 Linux 계층까지 추적해야 할 때 관심 보관에서 시작 준비 상태로 올린다.
다음 시작점새 기능을 넓게 설치하기 전에 기존 AIO 기록을 보지 않고 VM 생성, 외부 Packet, Volume 연결 중 한 경로를 먼저 재구성한 뒤 실제 상태와 비교한다.

여기서 “잘 안다”의 의미

사용할 수 있다Project 안에서 Compute·Network·Storage·Identity 자원을 조합하고 수명주기와 제약을 다룬다.
구조를 설명할 수 있다사용자 요청이 API·Message Queue·Database·Agent·Hypervisor·가상 네트워크·Storage Backend로 이어지는 경로를 설명한다.
설계할 수 있다요구사항을 자원 토폴로지와 Network·Storage·권한·가용성 경계로 바꾸고 대안의 장단점을 비교한다.
구축하고 운영할 수 있다배포 방식과 설정의 의미를 이해하고 상태·로그·Metric을 관찰하며 변경·Backup·Upgrade를 안전하게 수행한다.
문제를 추적할 수 있다증상을 서비스, Control/Data Plane, Linux Network·Storage, Hypervisor 계층으로 좁혀 원인과 복구를 검증한다.

이 다섯 역량이 함께 목표다. 특정 직무 하나를 먼저 고르는 로드맵이 아니며, 약한 영역을 프로젝트와 실습으로 보강한다.

고정 순서가 아니라 반복하는 학습 방식

단계매 주제에서 남길 증거
개념그 구성 요소가 왜 존재하고 무엇을 책임지며 무엇은 책임지지 않는지 자기 말로 설명한다.
자원 실습CLI나 API로 정상 흐름을 실행하고 입력·출력·상태 전이를 확인한다.
내부 관찰관련 Service·Agent·Log·Namespace·Process·Backend 상태에서 실제 증거를 찾는다.
실패 실험설정·정책·서비스·경로 하나를 의도적으로 바꾸고 나타날 증상을 먼저 예측한 뒤 확인한다.
설계 적용실제 요구사항에 그 기능을 포함하거나 제외한 이유와 대안을 비교한다.
재현·설명다른 이름·주소·환경에서도 다시 만들고, 처음 보는 사람에게 구조와 진단 순서를 설명한다.

현재 프로젝트가 증명한 것과 남은 것

역량 영역현재 상태다음 검증
사용자 자원Image·Flavor·VM·Network·Router·Floating IP·Volume 종단 간 실행 증거가 있다.자료 없이 수명주기를 재구성하고 Project·Quota·Snapshot·Backup까지 확장한다.
서비스 구조실제 핵심 서비스를 배포하고 요청 결과를 확인했다.VM 생성과 Volume 연결의 서비스 호출·상태·실패 지점을 직접 추적한다.
Network·Storage 내부Provider 경로와 Cinder LVM Guest I/O 증거가 있다.Packet Trace와 Block I/O 계층을 다른 주소·자원으로 재현한다.
배포Kolla-Ansible AIO를 완료했다.설정값의 영향, Reconfigure와 Clean Rebuild 재현성을 확인한다.
설계학습용 싱글노드 구성의 선택과 한계를 기록했다.Workload 인프라와 Multinode Private Cloud 설계를 각각 요구사항에서 도출한다.
운영·장애 분석설치 중 일부 실패·수정 기록은 있으나 체계적인 장애 실험은 미완료다.Compute·Network·Storage에서 장애 하나씩을 예측·관찰·복구한다.
자동화·보안·확장 서비스OpenStack 배포 자동화 경험 외에는 미검증이다.Workload IaC와 최소 권한 구성을 만든 뒤 필요 서비스 하나를 선택한다.
프로젝트의 위치
현재 저장소는 “OpenStack을 배웠다”의 완결본이 아니라, 여러 범용 역량을 실제 환경에서 확인하기 시작한 첫 통합 실습이다. 원본 실행 기록은 보존하고, 여기서 드러난 개념은 주제별 문서로 계속 추출한다.

보강 메모 · 자료를 덮고 경계 5개 설명하기

추가한 이유
구축을 완료한 뒤 시간이 지나면 명령 이름은 보여도 “어느 계층을 바꾸는 명령인지”와 “어디까지 확인해야 성공인지”가 흐려질 수 있다. 아래 항목은 현재 다음 행동을 대체하지 않는 회상 연습이며, 범용 완료 조건과 로드맵 진행률에도 포함하지 않는다.
배포와 자원 생성의 경계
kolla-ansible deploy는 OpenStack 서비스를 배포하고, openstack server create는 이미 배포된 API를 사용해 Project의 VM 자원을 만든다는 차이를 자료 없이 설명한다.
VM 외부 통신의 두 단계 SNAT
SNAT(출발지 네트워크 주소 변환)이 Tenant VM 주소를 Provider 쪽 주소로 한 번, Provider 주소를 물리 LAN의 호스트 주소로 다시 한 번 바꾸는 이유와 각 변환 지점을 주소 변환 그림 없이 그린다.
같은 LAN PC에서 FIP로 가지 못하는 첫 막힘
FIP(Floating IP, 유동 IP)인 172.24.4.130으로 가는 경로를 LAN PC와 공유기가 알지 못한다는 첫 번째 막힘을 먼저 말하고, 이후 필요한 호스트 Forward 규칙과 Security Group을 구분한다.
in-use와 Guest 쓰기 성공의 경계
Cinder Volume의 in-use는 제어 계층의 연결 상태이고, Guest에서 Block Device·Filesystem·실제 파일 쓰기를 확인해야 데이터 경로까지 검증한 것임을 5분 회상 점검을 보지 않고 설명한다.
재부팅 뒤 Network와 Storage의 독립 복구
Network의 veth·Route·Forward/NAT 규칙과 Storage의 loop·LVM·Cinder Backend는 서로 다른 복구 조건을 가지므로 한쪽 성공이 다른 쪽 성공을 보장하지 않는다고 설명하고, 각각 확인할 상태를 말한다.

완료 증거: 문서를 덮고 다섯 경계를 자기 말로 설명한 뒤, 구축 기록의 그림과 5분 회상 점검을 다시 열어 빠진 계층을 수정한다.

추천하는 다음 학습 묶음

요청 하나를 깊게 추적

새 VM 하나를 만들며 Keystone → Nova → Placement → Neutron → Glance → Hypervisor의 상태와 로그를 연결한다.

Network 하나를 깊게 추적

VM에서 외부까지 Port·Security Group·Router·NAT·Provider Interface와 실제 Packet을 연결한다.

Volume 하나를 깊게 추적

Cinder 요청부터 LVM Backend·Attach·Guest Block Device·Filesystem I/O까지 연결한다.

작은 인프라 하나를 설계

Public Web과 Private Data 요구를 OpenStack 자원 토폴로지로 만들고 검증·자동화한다.

이 네 묶음은 하나의 관점을 고르는 선택지가 아니라 서로 연결되는 첫 순환이다. 이후 부족한 역량 영역으로 다시 들어간다.

핵심 자원을 CLI·API로 다루고 관계·수명주기·제약을 설명한다.
Explain
Compute·Network·Storage 요청의 참여 서비스와 Control/Data Plane을 그린다.
Trace
API 상태부터 Linux·Hypervisor·Backend까지 실제 실행 경로를 추적한다.
Design
요구사항을 Workload와 Private Cloud 토폴로지로 바꾸고 대안을 비교한다.
Deploy·Operate
구축·설정 변경·관찰·Backup·Upgrade의 절차와 위험을 이해하고 검증한다.
Troubleshoot
처음 보는 장애를 계층별 가설과 증거로 좁히고 복구·재발 방지를 설명한다.
Automate·Secure
반복 가능한 구성과 최소 권한·Secret·Network·Image 보안 기준을 적용한다.
Transfer
새 서비스나 새 환경에서도 공식 문서와 관찰 증거를 이용해 스스로 학습·판단한다.
