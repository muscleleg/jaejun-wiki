적용 학습 정책

세션 재개와 학습 컨텍스트

  • focusedSessionId가 가리키는 세션이 있으면 그 세션의 첫 pending 단계부터 재개한다.
  • 로드맵·백로그에 소속된 여러 세션을 열어 둘 수 있지만 한 번에 하나만 active로 두며, 사용자의 선택이나 명시적인 session.focus 작업 없이 다른 세션으로 초점을 바꾸지 않는다.
  • 대화 중 한 번 다룬 독립 주제는 날짜별 학습 기록에만 남길 수 있다. 다음 대화에서도 이어갈 필요가 생기면 먼저 백로그 항목으로 승격한 뒤 backlog 세션으로 연다.
  • 학습을 시작하거나 재개할 때는 responseBrief를 사용해 현재까지 확인된 기록, 로드맵 또는 백로그에서의 위치, 현재 학습 단위와 목적, 왜 지금 필요한지, 지금 할 가장 작은 단계와 관찰·완료 근거, 다음에 열리는 결과 순서로 설명한다.
  • Notebook·소스 코드·테스트·CLI·화면·대화 등 현재 매체에서 실행 결과와 사용자 이해를 확인한 뒤, 파일 위치가 아니라 이해·검증·남은 질문·다음 행동을 Markdown 학습 컨텍스트로 기록한다.
  • 학습 컨텍스트는 특정 파일의 현재 존재 여부에 의존하지 않으며, 직접 확인하지 않은 내용은 완료 근거로 기록하지 않는다.
  • 모든 필수 단계의 학습 컨텍스트가 확인되기 전에는 현재 학습 단위를 완료하지 않는다.
  • 모든 단계의 완료와 각 단계의 검증된 학습 컨텍스트가 확인되면 LLM이 해당 sessionId의 범위와 현재 progressionMode·관문 관계를 근거로 다음 작은 학습 단위를 만들고 session.advance-current-unit으로 전환한다. 관문이나 백로그 단계도 끝났다면 같은 Plan에 해당 진행 상태 변경을 별도 작업으로 기록한다.
  • 학습 세션을 마감할 때 LLM은 대화의 실제 학습 구간을 근거로 그날의 하루 총 학습시간을 분 단위로 판정하고 history.set-study-time에 절대값과 추정 여부만 전달한다. 근거가 부족하면 시간을 꾸며내지 않는다.

대화형 손코딩 학습

  • 사용자가 코드를 직접 입력한다.
  • 개념과 필요성을 설명한 뒤 독립 실행 가능한 작은 코드 셀과 예상 Shape·값을 제공하고 저장된 실행 결과를 검증한다.
  • 한 번에 새로운 핵심 개념 하나를 다루며 완료되지 않은 단계를 건너뛰지 않는다.
  • 새로운 클래스·메서드·API·모델 객체는 사용 전에 역할과 입력·출력을 먼저 설명한다.
  • 추상적인 용어보다 현재 코드의 실제 숫자와 Shape을 우선한다.
  • 연습 셀은 필요한 작은 입력·Target·상수를 다시 선언해 독립 실행 가능하게 만들고, 상태를 재사용해야 할 때는 이유를 설명한다.
  • 사용자가 자료 없는 재구현을 선택한 검증 단계가 아니라면 과제 순서만 주고 샘플 코드를 생략하지 않는다.
  • 외부 강의·교재는 출처로 사용하되 학습 단위를 개념 설명·예측·손코딩·실행 증거·자기 말 설명 순서로 재구성한다.

이해도와 완료 판정

  • 설명을 듣거나 코드를 따라 입력한 사실만으로 완료 처리하지 않는다.
  • 자기 말 설명·조건 변경 결과 예측·자료 없는 재구현·의도적 변경 설명 중 하나 이상의 증거를 확인한다.
  • 대표 실습은 입력과 정답 설명·핵심 Shape 예상·Metric 평가·조건 변경 설명·핵심 코드 재구현을 확인한다.
  • 완료 기준을 충족하면 선택 심화보다 먼저 완료 사실과 남은 필수 단계 수를 명확히 알린다.
  • 캐시된 출력만 믿지 않고 필요한 import·변수·모델·입력이 포함된 상태에서 커널 재시작 후 재현되는지 확인한다.

학습 설명과 피드백

  • 처음 소개하거나 다시 묻는 영문 약어와 모델명은 한국어 뜻을 함께 설명한다.
  • 질문한 대상과 코드 줄을 먼저 특정하고 질문을 다른 개념으로 바꾸어 답하지 않는다.
  • 막힘을 수학·Python 문법·PyTorch 객체 모델·Tensor Shape 등 실제 원인으로 분류한다.
  • 진도는 나이·전공·감정이 아니라 실행 결과·설명 능력·재구현 증거로 판단한다.

로드맵 안내

  • 선택 경계: 언제 시작하는가 Road to LLM inference 를 완료했거나 사용자가 별도 Knowledge Graph·Agent 세션을 명시적으로 선택했을 때 시작한다. Graph 경로는 단순 Keyword 또는 Vector RAG의 한계가 실제 평가로 확인됐을 때, Agent Harness 경로는 도구 실행·실패 복구·운영 검증이 필요한 작은 LLM 애플리케이션을 정했을 때만 연다. 두 진입 경로 문서 관계 검색이 목적이면 기존 Vector RAG → GraphRAG 경로로 들어간다. 도구를 안전하게 실행하는 LLM 애플리케이션이 목적이면 Function Calling → Agent Harness 경로로 들어가며, 이 경우 Graph를 선수지식으로 요구하지 않는다. Graph를 목적처럼 만들지 않는다 Entity 관계를 여러 단계 따라가야 하거나 Schema·권한·규칙 검증이 답의 핵심일 때 Knowledge Graph를 사용한다. 단순 문서 유사도 검색으로 충분하면 Vector RAG를 유지한다. 프로젝트 범위 공개 문서 묶음 하나를 사용해 Baseline과 Graph 확장을 같은 질문 세트로 비교한다. 여러 도메인 Agent를 동시에 만들지 않는다.
  • 결과물 중심 학습 경로: 1 · 문서 계약과 검색 Baseline 문서 ID·출처·제목·Section·Tag·갱신 시각 같은 Metadata를 정하고 Parsing 결과를 JSONL 등 확인 가능한 형식으로 저장한다. Keyword 또는 Vector RAG로 질문·근거·응답 Baseline을 먼저 측정한다. 2 · Knowledge Graph Schema 현재 질문에 필요한 Entity Type, Relation Type, Triple과 고유 식별 규칙을 먼저 설계한다. 원문 근거와 연결되지 않는 추출 정보는 Graph에 넣지 않는다. 3 · 정보 추출과 정규화 Entity·Relation을 추출하고 표기 차이를 정규화하며 중복 Entity를 병합한다. 자동 병합의 Threshold와 보류·거절 이유를 남겨 잘못된 관계가 조용히 퍼지지 않게 한다. 4 · Graph 저장과 Query Graph Database에 Node·Edge와 출처를 적재하고 Cypher 같은 Query로 한 단계·다단계 관계를 직접 조회한다. Text-to-Query를 붙이기 전에 고정 Query의 정답과 실행 비용을 검증한다. 5 · GraphRAG 비교 질문에서 필요한 Entity와 관계 경로를 찾아 Graph Context를 구성한다. 같은 질문 세트에서 Vector RAG와 GraphRAG의 검색 성공, 근거 적합성, 다단계 질문 성공과 지연·비용을 비교한다. 6 · Ontology와 Semantic Validation 허용하는 Entity·Relation·Vocabulary와 Constraint를 명시한다. Schema 위반, 의미적으로 금지된 관계, 권한 없는 요청을 구분해 통과·보류·거절과 구체적인 Reject reason을 만든다. 7 · Agent Tool과 Routing docs_search , graph_query , ontology_check 처럼 역할과 입력·출력이 분리된 도구를 만들고, 어떤 질문에서 어떤 도구를 호출할지 Router의 규칙과 실패 조건을 시험한다. 8 · Agent Harness 안정성 Structured output Schema, Timeout, Retry 가능 오류, Fallback, 최대 반복 횟수와 Human review 조건을 둔다. Retry가 같은 잘못을 무한 반복하지 않도록 Evidence와 실패 이유를 다음 시도에 전달한다. 9 · 평가와 증분 갱신 검색 성공·근거 충실성·최종 답·도구 선택·Schema 준수·latency·비용을 분리해 평가한다. 문서가 바뀌면 영향받은 Chunk·Entity·Relation만 갱신하고 삭제·충돌·버전 변경을 재평가한다.
  • 하나의 프로젝트로 묶는 방법: 권장 문제 공개 기술 문서처럼 출처와 구조를 확인할 수 있는 작은 Corpus에서 단일 문서 질문 → 여러 문서 관계 질문 → 규칙 위반 질문 세 종류를 만든다. 비교 순서 검색 없는 LLM → Vector RAG → Graph Query를 포함한 GraphRAG → Ontology 검증과 Tool Router를 포함한 Agent Harness 순서로 한 기능씩 추가한다. 각 단계는 이전 Baseline 대비 무엇이 좋아지고 어떤 비용과 실패가 생겼는지 기록한다. 현재 프로젝트와의 연결 기존 RAG 지식 비서의 문서 수집·검색·근거 응답 흐름은 Vector RAG Baseline으로 재사용할 수 있다. Graph와 Ontology는 기존 평가에서 관계 탐색 또는 규칙 검증의 부족이 확인된 뒤에만 추가한다.
  • 선택 실습 · Agent Application Engineering: Claude Code 워크숍에서 재사용 가치가 높은 부분만 제품 독립적인 실습으로 다시 구성했다. 설치법·CLI 명령 암기·특정 모델 가격은 제외하고, 현재 공식 API와 MCP 사양으로 직접 검증한다. 아래 실습은 1차 순환 진행률에 포함하지 않는다. 1 · Tool 계약 읽기 전용 도구 두 개를 JSON Schema로 정의하고, 모델이 만든 Tool name·arguments가 실행 명령이 아니라 검증 대상인 제안임을 설명한다. 정상 입력, 필수값 누락, 잘못된 enum을 각각 예측하고 서버에서 통과·거절을 확인한다. 2 · Tool Loop user → model(tool call) → handler → tool result → model 흐름을 작은 반복문으로 직접 연결한다. 한 응답의 여러 Tool Call, Tool 실행 오류, end_turn ·길이 제한 같은 종료 이유를 구분하고 최대 반복 횟수에서 반드시 멈추게 한다. 3 · 안전 경계와 Prompt Injection 읽기·쓰기·삭제 도구의 권한을 분리하고, Side Effect가 있는 호출에는 사용자 승인과 Idempotency Key를 둔다. 사용자 입력·검색 문서·웹페이지·Tool 결과의 지시를 신뢰 경계별로 구분하고, Prompt Injection이 System 정책·Tool Schema·권한·승인을 우회하지 못하게 한다. 허용되지 않은 도구명, Schema 위반, 권한 부족과 중복 요청을 Handler 전에 차단하는지 테스트한다. 4 · 실패 복구 Validation Error처럼 고쳐 다시 시도할 오류와 인증 실패처럼 즉시 중단할 오류를 구분한다. Timeout, 지수 Backoff, Retry 상한, Fallback, Circuit Breaker를 한꺼번에 붙이지 말고 실패 하나씩 주입해 호출 횟수와 최종 상태를 검증한다. 5 · Streaming SSE 또는 WebSocket 하나를 선택해 시작·Delta·Tool Call·완료·오류 이벤트를 명시한다. 느린 Consumer를 만들어 Queue 크기, Backpressure, 취소와 연결 종료가 Producer와 서버 자원을 어떻게 정리하는지 확인한다. 6 · 운영 증거 API를 Mock한 단위 테스트와 실제 Tool Handler를 연결한 통합 테스트를 분리한다. 요청 ID·Tool name·latency·retry count·token usage를 구조화 로그와 Metric으로 남기고, Health와 Readiness가 외부 의존성 실패를 어떻게 다르게 표현하는지 설명한다. 7 · MCP 비교 앞에서 만든 읽기 전용 도구 하나를 MCP Tool로 다시 노출한다. Tools·Resources·Prompts의 책임, Client와 Server의 경계, 입력·출력 Schema와 권한을 비교하고 직접 Function Calling한 경우와 MCP를 사용한 경우의 코드 책임·재사용성·실패 지점을 표로 정리한다. 8 · Multi-agent 단일 Agent Baseline을 먼저 측정한 뒤 서로 독립적인 두 작업만 Worker로 병렬화한다. Main과 Worker의 Context, 전달한 입력, 반환 요약, 전체 token·latency를 기록하고 병렬화가 실제로 유리한 조건과 오히려 비용만 늘린 조건을 설명한다. 통합 결과물 읽기 전용 Tool Agent 하나에 Schema 검증·권한·종료 조건·Timeout·관측·테스트를 연결한다. Streaming, MCP, Multi-agent는 같은 결과물의 필요가 확인될 때 하나씩 비교하며, 기능을 붙인 개수가 아니라 실패를 의도적으로 만들고 복구 결과를 설명한 증거로 완료한다. 자료 사용 원칙 워크숍의 코드와 수치는 정답으로 복사하지 않는다. 구조를 실습 아이디어로 사용하고, 변하기 쉬운 SDK·모델·MCP 세부 문법은 구현 시점의 공식 문서로 다시 확인한다.
  • GraphRAG 경로 완료 조건: Graph 경로를 선택했을 때만 아래 증거를 확인한다. 재현 가능한 Corpus와 Baseline 문서 출처·Parser·Chunk·Metadata와 고정 질문 세트를 재생성하고 Vector RAG 결과를 보존한다. 근거가 있는 Graph Entity·Relation·Triple의 원문 근거와 Schema를 확인하고 중복·오류 사례를 설명한다. Vector RAG와 GraphRAG 비교 다단계 질문에서 좋아진 사례와 오히려 복잡도·지연만 늘어난 사례를 같은 평가표로 분석한다. Ontology 검증 허용·보류·거절 예제를 만들고 각 판단의 Constraint와 Reject reason을 재현한다. Tool Router와 실패 복구 도구 선택, Structured output, Timeout·Retry·Fallback과 최대 반복 제한을 테스트한다. End-to-End 평가 검색·근거·답·도구·안전·지연·비용을 분리한 실패 분석과 증분 갱신 결과를 문서화한다.
  • Agent Harness 경로 완료 조건: Agent Application Engineering 경로를 선택했을 때만 아래 증거를 확인한다. Tool 계약과 Loop 정상·Schema 위반·Tool 오류·여러 Tool Call·종료 이유를 재현하고 최대 반복 제한에서 멈춘다. 권한·Prompt Injection·Side Effect 사용자 입력이나 검색·Tool 결과에 권한 상승·비밀 노출·임의 도구 실행 지시를 넣고, 허용·승인 필요·거절 경계와 중복 요청이 실행 전에 차단되거나 Idempotent하게 처리되는지 확인한다. 실패 복구와 운영 증거 Retry 가능 오류와 즉시 중단 오류를 구분하고 테스트·로그·Metric·Health/Readiness로 결과를 설명한다. 선택 확장 판정 Streaming·MCP·Multi-agent 중 실제 문제에 필요한 하나만 비교하거나, 필요하지 않다면 Baseline 근거로 선택하지 않은 이유를 기록한다.
  • 연결 로드맵과 프로젝트: Transformer 손코딩·적용 텍스트 모델과 사전학습 모델 적용의 선행 관문 LLM 시스템·최적화 서빙 비용·평가 계약과 Agent 실행의 시스템 관점 RAG 개인 지식 비서 문서 수집·Vector 검색·근거 응답을 재사용할 Baseline Function Calling과 도구 계약 Tool Schema·서버 검증·Agent Loop의 현재 학습 기록 Claude Code Deep Dive Workshop Tool Use·Streaming·MCP·Production·Subagent 실습 아이디어를 선별한 공개 출처 핵심 여정 이후 보관함 Road to LLM inference 완료 뒤에만 확장 후보를 검토하는 기준

학습 관문

1 · 문서 계약과 검색 Baseline

문서 ID·출처·제목·Section·Tag·갱신 시각 같은 Metadata를 정하고 Parsing 결과를 JSONL 등 확인 가능한 형식으로 저장한다. Keyword 또는 Vector RAG로 질문·근거·응답 Baseline을 먼저 측정한다.

예정

2 · Knowledge Graph Schema

현재 질문에 필요한 Entity Type, Relation Type, Triple과 고유 식별 규칙을 먼저 설계한다. 원문 근거와 연결되지 않는 추출 정보는 Graph에 넣지 않는다.

예정

3 · 정보 추출과 정규화

Entity·Relation을 추출하고 표기 차이를 정규화하며 중복 Entity를 병합한다. 자동 병합의 Threshold와 보류·거절 이유를 남겨 잘못된 관계가 조용히 퍼지지 않게 한다.

예정

4 · Graph 저장과 Query

Graph Database에 Node·Edge와 출처를 적재하고 Cypher 같은 Query로 한 단계·다단계 관계를 직접 조회한다. Text-to-Query를 붙이기 전에 고정 Query의 정답과 실행 비용을 검증한다.

예정

5 · GraphRAG 비교

질문에서 필요한 Entity와 관계 경로를 찾아 Graph Context를 구성한다. 같은 질문 세트에서 Vector RAG와 GraphRAG의 검색 성공, 근거 적합성, 다단계 질문 성공과 지연·비용을 비교한다.

예정

6 · Ontology와 Semantic Validation

허용하는 Entity·Relation·Vocabulary와 Constraint를 명시한다. Schema 위반, 의미적으로 금지된 관계, 권한 없는 요청을 구분해 통과·보류·거절과 구체적인 Reject reason을 만든다.

예정

7 · Agent Tool과 Routing

docs_search , graph_query , ontology_check 처럼 역할과 입력·출력이 분리된 도구를 만들고, 어떤 질문에서 어떤 도구를 호출할지 Router의 규칙과 실패 조건을 시험한다.

예정

8 · Agent Harness 안정성

Structured output Schema, Timeout, Retry 가능 오류, Fallback, 최대 반복 횟수와 Human review 조건을 둔다. Retry가 같은 잘못을 무한 반복하지 않도록 Evidence와 실패 이유를 다음 시도에 전달한다.

예정

9 · 평가와 증분 갱신

검색 성공·근거 충실성·최종 답·도구 선택·Schema 준수·latency·비용을 분리해 평가한다. 문서가 바뀌면 영향받은 Chunk·Entity·Relation만 갱신하고 삭제·충돌·버전 변경을 재평가한다.
