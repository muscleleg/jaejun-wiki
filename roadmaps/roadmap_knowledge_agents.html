Knowledge Graph·GraphRAG·Agent Harness

문서를 단순 Vector 검색하는 Baseline에서 출발해 Entity·Relation·Ontology를 명시하고, 필요한 도구를 선택하며 실패를 검증할 수 있는 지식 Agent 결과물로 확장한다.

선택 경계

언제 시작하는가Tiny Decoder LM과 사전학습 텍스트 모델 적용을 완료한 뒤 선택한다. Graph 경로는 단순 Keyword 또는 Vector RAG의 한계가 실제 평가로 확인됐을 때 시작하고, Agent Harness 경로는 도구 실행·실패 복구·운영 검증이 필요한 작은 LLM 애플리케이션을 정했을 때 시작한다.
두 진입 경로문서 관계 검색이 목적이면 기존 Vector RAG → GraphRAG 경로로 들어간다. 도구를 안전하게 실행하는 LLM 애플리케이션이 목적이면 Function Calling → Agent Harness 경로로 들어가며, 이 경우 Graph를 선수지식으로 요구하지 않는다.
Graph를 목적처럼 만들지 않는다Entity 관계를 여러 단계 따라가야 하거나 Schema·권한·규칙 검증이 답의 핵심일 때 Knowledge Graph를 사용한다. 단순 문서 유사도 검색으로 충분하면 Vector RAG를 유지한다.
프로젝트 범위공개 문서 묶음 하나를 사용해 Baseline과 Graph 확장을 같은 질문 세트로 비교한다. 여러 도메인 Agent를 동시에 만들지 않는다.

결과물 중심 학습 경로

1 · 문서 계약과 검색 Baseline문서 ID·출처·제목·Section·Tag·갱신 시각 같은 Metadata를 정하고 Parsing 결과를 JSONL 등 확인 가능한 형식으로 저장한다. Keyword 또는 Vector RAG로 질문·근거·응답 Baseline을 먼저 측정한다.
2 · Knowledge Graph Schema현재 질문에 필요한 Entity Type, Relation Type, Triple과 고유 식별 규칙을 먼저 설계한다. 원문 근거와 연결되지 않는 추출 정보는 Graph에 넣지 않는다.
3 · 정보 추출과 정규화Entity·Relation을 추출하고 표기 차이를 정규화하며 중복 Entity를 병합한다. 자동 병합의 Threshold와 보류·거절 이유를 남겨 잘못된 관계가 조용히 퍼지지 않게 한다.
4 · Graph 저장과 QueryGraph Database에 Node·Edge와 출처를 적재하고 Cypher 같은 Query로 한 단계·다단계 관계를 직접 조회한다. Text-to-Query를 붙이기 전에 고정 Query의 정답과 실행 비용을 검증한다.
5 · GraphRAG 비교질문에서 필요한 Entity와 관계 경로를 찾아 Graph Context를 구성한다. 같은 질문 세트에서 Vector RAG와 GraphRAG의 검색 성공, 근거 적합성, 다단계 질문 성공과 지연·비용을 비교한다.
6 · Ontology와 Semantic Validation허용하는 Entity·Relation·Vocabulary와 Constraint를 명시한다. Schema 위반, 의미적으로 금지된 관계, 권한 없는 요청을 구분해 통과·보류·거절과 구체적인 Reject reason을 만든다.
7 · Agent Tool과 Routingdocs_search, graph_query, ontology_check처럼 역할과 입력·출력이 분리된 도구를 만들고, 어떤 질문에서 어떤 도구를 호출할지 Router의 규칙과 실패 조건을 시험한다.
8 · Agent Harness 안정성Structured output Schema, Timeout, Retry 가능 오류, Fallback, 최대 반복 횟수와 Human review 조건을 둔다. Retry가 같은 잘못을 무한 반복하지 않도록 Evidence와 실패 이유를 다음 시도에 전달한다.
9 · 평가와 증분 갱신검색 성공·근거 충실성·최종 답·도구 선택·Schema 준수·latency·비용을 분리해 평가한다. 문서가 바뀌면 영향받은 Chunk·Entity·Relation만 갱신하고 삭제·충돌·버전 변경을 재평가한다.

하나의 프로젝트로 묶는 방법

권장 문제공개 기술 문서처럼 출처와 구조를 확인할 수 있는 작은 Corpus에서 단일 문서 질문 → 여러 문서 관계 질문 → 규칙 위반 질문 세 종류를 만든다.
비교 순서검색 없는 LLM → Vector RAG → Graph Query를 포함한 GraphRAG → Ontology 검증과 Tool Router를 포함한 Agent Harness 순서로 한 기능씩 추가한다. 각 단계는 이전 Baseline 대비 무엇이 좋아지고 어떤 비용과 실패가 생겼는지 기록한다.
현재 프로젝트와의 연결기존 RAG 지식 비서의 문서 수집·검색·근거 응답 흐름은 Vector RAG Baseline으로 재사용할 수 있다. Graph와 Ontology는 기존 평가에서 관계 탐색 또는 규칙 검증의 부족이 확인된 뒤에만 추가한다.

선택 실습 · Agent Application Engineering

Claude Code 워크숍에서 재사용 가치가 높은 부분만 제품 독립적인 실습으로 다시 구성했다. 설치법·CLI 명령 암기·특정 모델 가격은 제외하고, 현재 공식 API와 MCP 사양으로 직접 검증한다. 아래 실습은 1차 순환 진행률에 포함하지 않는다.

1 · Tool 계약읽기 전용 도구 두 개를 JSON Schema로 정의하고, 모델이 만든 Tool name·arguments가 실행 명령이 아니라 검증 대상인 제안임을 설명한다. 정상 입력, 필수값 누락, 잘못된 enum을 각각 예측하고 서버에서 통과·거절을 확인한다.
2 · Tool Loopuser → model(tool call) → handler → tool result → model 흐름을 작은 반복문으로 직접 연결한다. 한 응답의 여러 Tool Call, Tool 실행 오류, end_turn·길이 제한 같은 종료 이유를 구분하고 최대 반복 횟수에서 반드시 멈추게 한다.
3 · 안전 경계읽기·쓰기·삭제 도구의 권한을 분리하고, Side Effect가 있는 호출에는 사용자 승인과 Idempotency Key를 둔다. 허용되지 않은 도구명, Schema 위반, 권한 부족, 중복 요청이 Handler에 도달하기 전에 차단되는지 테스트한다.
4 · 실패 복구Validation Error처럼 고쳐 다시 시도할 오류와 인증 실패처럼 즉시 중단할 오류를 구분한다. Timeout, 지수 Backoff, Retry 상한, Fallback, Circuit Breaker를 한꺼번에 붙이지 말고 실패 하나씩 주입해 호출 횟수와 최종 상태를 검증한다.
5 · StreamingSSE 또는 WebSocket 하나를 선택해 시작·Delta·Tool Call·완료·오류 이벤트를 명시한다. 느린 Consumer를 만들어 Queue 크기, Backpressure, 취소와 연결 종료가 Producer와 서버 자원을 어떻게 정리하는지 확인한다.
6 · 운영 증거API를 Mock한 단위 테스트와 실제 Tool Handler를 연결한 통합 테스트를 분리한다. 요청 ID·Tool name·latency·retry count·token usage를 구조화 로그와 Metric으로 남기고, Health와 Readiness가 외부 의존성 실패를 어떻게 다르게 표현하는지 설명한다.
7 · MCP 비교앞에서 만든 읽기 전용 도구 하나를 MCP Tool로 다시 노출한다. Tools·Resources·Prompts의 책임, Client와 Server의 경계, 입력·출력 Schema와 권한을 비교하고 직접 Function Calling한 경우와 MCP를 사용한 경우의 코드 책임·재사용성·실패 지점을 표로 정리한다.
8 · Multi-agent단일 Agent Baseline을 먼저 측정한 뒤 서로 독립적인 두 작업만 Worker로 병렬화한다. Main과 Worker의 Context, 전달한 입력, 반환 요약, 전체 token·latency를 기록하고 병렬화가 실제로 유리한 조건과 오히려 비용만 늘린 조건을 설명한다.
통합 결과물
읽기 전용 Tool Agent 하나에 Schema 검증·권한·종료 조건·Timeout·관측·테스트를 연결한다. Streaming, MCP, Multi-agent는 같은 결과물의 필요가 확인될 때 하나씩 비교하며, 기능을 붙인 개수가 아니라 실패를 의도적으로 만들고 복구 결과를 설명한 증거로 완료한다.
자료 사용 원칙
워크숍의 코드와 수치는 정답으로 복사하지 않는다. 구조를 실습 아이디어로 사용하고, 변하기 쉬운 SDK·모델·MCP 세부 문법은 구현 시점의 공식 문서로 다시 확인한다.

GraphRAG 경로 완료 조건

Graph 경로를 선택했을 때만 아래 증거를 확인한다.

재현 가능한 Corpus와 Baseline
문서 출처·Parser·Chunk·Metadata와 고정 질문 세트를 재생성하고 Vector RAG 결과를 보존한다.
근거가 있는 Graph
Entity·Relation·Triple의 원문 근거와 Schema를 확인하고 중복·오류 사례를 설명한다.
Vector RAG와 GraphRAG 비교
다단계 질문에서 좋아진 사례와 오히려 복잡도·지연만 늘어난 사례를 같은 평가표로 분석한다.
Ontology 검증
허용·보류·거절 예제를 만들고 각 판단의 Constraint와 Reject reason을 재현한다.
Tool Router와 실패 복구
도구 선택, Structured output, Timeout·Retry·Fallback과 최대 반복 제한을 테스트한다.
End-to-End 평가
검색·근거·답·도구·안전·지연·비용을 분리한 실패 분석과 증분 갱신 결과를 문서화한다.

Agent Harness 경로 완료 조건

Agent Application Engineering 경로를 선택했을 때만 아래 증거를 확인한다.

Tool 계약과 Loop
정상·Schema 위반·Tool 오류·여러 Tool Call·종료 이유를 재현하고 최대 반복 제한에서 멈춘다.
권한과 Side Effect
허용·승인 필요·거절 호출과 중복 요청을 만들고 실행 전 차단 또는 Idempotent 결과를 확인한다.
실패 복구와 운영 증거
Retry 가능 오류와 즉시 중단 오류를 구분하고 테스트·로그·Metric·Health/Readiness로 결과를 설명한다.
선택 확장 판정
Streaming·MCP·Multi-agent 중 실제 문제에 필요한 하나만 비교하거나, 필요하지 않다면 Baseline 근거로 선택하지 않은 이유를 기록한다.
