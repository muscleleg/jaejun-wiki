목표 문맥별 선택 이유

쿠버네티스 GPU 클러스터와 Multi-GPU Serving 학습 문맥

Fake GPU 환경에서 쿠버네티스의 GPU 자원 등록·할당·Node 및 그룹 배치와 LLM Serving 운영을 먼저 익힌다. 이후 실제 Multi-GPU 환경에서 분산 추론의 계산·통신·메모리·성능을 검증하고 Kubernetes의 자원 관리와 Runtime의 GPU 사용·통신 책임을 구분한다.

선택된 하위 로드맵

Kubernetes GPU 클러스터 운영

[Minikube 멀티노드·Fake GPU] GPU 자원 등록·할당·Node 배치에서 시작해 DRA, Multi-node 워크로드 그룹과 토폴로지 기반 배치, LLM Serving 배포·Routing·확장·장애 복구를 검증한다. GPU 장치는 가상으로 구성하고 Kubernetes API·Scheduler·Controller와 CPU용 Mock Server는 실제 실행한다. Device Plugin과 DRA는 호환 버전과 설정을 고정해 분리 검증하며 Fake 장치·Synthetic Metric을 실제 GPU 연산·통신·하드웨어 격리의 증거로 사용하지 않는다. 실제 Multi-GPU Runtime 학습과 독립된 로드맵이다. 학습은 GPU 등록·배치 → 기본 관측 → DRA 비교 → Serving 배포·복구·그룹 → 요청 경로·Routing·과부하·Streaming → 확장·장애·업데이트 → 통합 부하·재현 순서의 개념+실습 묶음으로 진행한다. 이 권장 순서와 필수 선수 관계는 구분하며 DRA 전체 완료로 기본 Serving 배포를 막지 않는다. Apple Silicon에서는 ARM64 이미지와 호환 API 버전을 고정한 별도 Minikube Docker 프로필을 사용한다. 메모리가 제한되면 필요한 구성부터 단계적으로 실행하되 Control Plane 1개·Worker 2개 이상 조건과 최종 통합 검증은 축소하지 않는다. 단일 노드는 예비 실습으로만 사용한다. 한 실험의 관측을 여러 달성 기준에 재사용하되 각 원문 요구를 별도로 판정한다.

일부 완료 직접 학습 단원 완료 9 / 16

현재 목표에서 선택한 하위 학습 단원 (16)
  1. GPU 자원 등록과 Pod 할당 · 완료한 단일 GPU Serving 경험을 Kubernetes의 GPU 게시·요청·배치 책임으로 연결하기 위해 먼저 등록과 Pod 할당을 실험한다.
  2. GPU 요청 형태·Node 선택·자원 단편화 · 등록·할당에 이어 GPU 총량과 Node별 배치 가능성의 차이를 요청 크기·선택 조건·자원 반환으로 확인한다.
  3. GPU 클러스터 관측 · GPU 배치 결과를 Prometheus·kube-state-metrics·Grafana에서 함께 관찰하고, 이후 Serving 계층의 Gateway·EPP·Mock Server 메트릭을 추가할 기준선을 마련한다.
  4. DRA 장치 선택·수명주기와 GPU 공유 · 개수 기반 배치 뒤에 장치 속성 선택·Claim 수명주기·공유 경계를 비교한다. DRA 전체 완료를 기본 KServe 배포의 강제 선수로 삼지는 않는다.
  5. KServe 배포와 GPU 요청 전달 · GPU 배치와 관측을 실제 HTTP API에 연결한다. Controller 상세 분석보다 먼저 실행할 서버와 상위 리소스를 만든다.
  6. Controller Reconcile과 Serving 복구 · 실행 중인 KServe 서버를 대상으로 상태 차이와 Pod 삭제를 관찰해 Reconcile·복구를 설명한다.
  7. Multi-node 실행 그룹과 Gang·Topology 배치 · 개별 Pod와 Controller 복구를 이해한 뒤 여러 Node에 걸친 그룹·Gang·Topology와 GPU 예산을 확장한다.
  8. llm-d 요청 경로와 Gateway 연결 · 서버·Controller·그룹 관계 다음에 Gateway와 EPP를 연결하고 관리 흐름과 HTTP 요청 흐름을 통합해서 그린다.
  9. LLM-aware Routing과 GPU 배치의 구분 · 정상 요청 경로에서 부하·Prefix에 따른 Endpoint 선택을 관찰하고, 이미 배치된 서버 중 요청 대상을 고르는 일과 Pod·GPU를 배치하는 일의 책임을 구분한다.
  10. 과부하·Admission과 두 종류의 대기 · 정상 요청 전달과 Routing을 본 다음 과부하를 주입해 HTTP 대기와 GPU 부족으로 인한 Pod 대기를 비교한다.
  11. Streaming 요청 수명주기와 안전한 종료 · Queue와 실행 중 요청을 구분한 상태에서 취소·재시도·수동 Scale-in·Drain을 하나의 요청 수명주기로 실험한다.
  12. Autoscaling 신호·GPU 예산·Ready 지연 · 과부하 신호와 그룹 GPU 예산을 연결해 자동 확장 결정부터 GPU 확보·Startup·Ready까지 측정한다. 직전 안전한 종료 학습은 권장 순서이지 확장의 필수 선수는 아니다.
  13. 장애 전파와 GPU 자원 기반 복구 · 정상 확장·안전한 종료와 대비해 각 계층의 비계획 장애, 대체 GPU 부족과 복구를 관찰한다.
  14. Rolling Update·Rollback과 그룹 GPU 여유 · 장애·종료·그룹 복구 다음에 업데이트의 여분 GPU 요구와 Rollback을 비교하며 앞의 장애 관측 근거를 함께 사용한다.
  15. Serving 전체 흐름과 병목 통합 검증 · 개별 Routing·대기·확장·장애 실험을 하나의 관측 환경에 연결해 부하 증가부터 회복까지 병목 가설을 검증한다.
  16. 장애·DRA·그룹 통합 재현과 운영 인수 · 통합 부하 실험 뒤 동일 자료에서 장애·Drain·Rollout·DRA·그룹을 재현해 Kubernetes 운영 구간을 마무리하고 실제 GPU 실험으로 넘어간다.
