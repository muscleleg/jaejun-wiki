    `axis=0`은 행, `axis=1`은 열에서 삭제 대상을 찾는다는 뜻을 확인했다. `inplace=False`는 원본을 유지하고 새 DataFrame을 반환하며, `inplace=True`는 원본을 수정하고 반환값이 `None`이므로 결과를 다시 `df`에 대입하면 안 된다는 점을 정리했다. 테이블의 Row는 Page에 저장되고, Heap은 우선순위 자료구조가 아니라 여기서는 Row가 특정 정렬 순서를 보장받지 않는 테이블 저장 구조를 뜻한다는 점을 구분했다. Index는 검색 값에서 실제 Row 위치로 이동하기 위한 별도 탐색 구조이고, B-tree의 Leaf와 연결된 위치 정보를 통해 모든 Page를 순차 검색하는 비용을 줄인다는 흐름을 정리했다. 입력 `x=[1, 2, 2]`를 서로 다른 `nn.Linear(2, 2, bias=False)`에 통과시켜 Q·K·V를 만들었다. Linear가 마지막 벡터 차원만 변환하므로 Shape은 유지되지만, 각 Projection이 별도의 가중치를 사용해 값과 역할은 달라진다는 점을 확인했다. 또한 `x @ weight.T`를 직접 계산하고 `torch.allclose()`가 `True`임을 확인해 Linear의 결과와 직접 행렬곱이 같다는 것을 검증했다. `QKᵀ`로 `[1,2,2]` Score를 만들고 현재 `d_k=2`임을 확인했다. 분산은 `Var(X)=E[(X-E[X])²]`이며, 초기화 분포의 기댓값을 0으로 두었기 때문에 `Var(X)=E[X²]`로 단순화된다는 빠졌던 연결고리를 바로잡았다. 각 곱의 평균 0·분산 1과 독립성을 근사하면 Score의 실제 값이 `d_k`가 아니라 분산이 `d_k`, 표준편차가 `√d_k`가 되므로 이를 나누어 약 1 규모로 맞춘다는 점을 정리했다. `scaled_scores`에 마지막 차원 Softmax를 적용해 `attention_weights`를 만들었다. Shape `[1,2,2]`에서 각 행은 하나의 Query가 두 Key를 참고하는 비율이고, `dim=-1`은 Key 방향으로 행별 정규화하므로 각 행의 합이 1이 된다. 실제 결과 `[0.5084,0.4916]`, `[0.4306,0.5694]`를 통해 Query1은 Key1을, Query2는 Key2를 조금 더 참고한다는 것을 확인했다. Attention weight의 Shape이 3차원인 이유는 맨 앞의 Batch 차원 때문이며, `value[0,0]`은 Token1의 한 좌표가 아니라 Value 벡터 전체라는 점을 구분했다. 첫 번째 Query에 대해 `0.5084×Value1 + 0.4916×Value2`를 직접 계산해 `[-0.0971,0.0557]`을 얻고 `output[0,0]`과 일치함을 확인했다. Attention은 Value들의 가중합이므로 두 항 사이에는 뺄셈이 아니라 덧셈을 사용한다. 또한 Attention weight 행렬을 `[[a1,a2],[a3,a4]]`로 놓았을 때 두 번째 행은 `Q2→K1`과 `Q2→K2`의 비율이며, `Output2=a3×V1+a4×V2`로 두 번째 Token이 첫 번째 Token의 정보도 가져온다는 점을 연결했다.

  • Head별 Attention 결과를 `transpose()`와 `reshape()`로 이어 붙인 `multi_head_output`은 여러 관점의 결과를 나열한 상태라고 이해했다…

    Head별 Attention 결과를 `transpose()`와 `reshape()`로 이어 붙인 `multi_head_output`은 여러 관점의 결과를 나열한 상태라고 이해했다. 이어 붙이는 연산만으로는 Head 정보가 섞이지 않으므로, `W_O` Linear가 각 특징을 학습된 비율로 다시 조합해 다음 블록에서 사용할 `d_model` 벡터로 만든다는 역할을 정리했다. 포지셔널 인코딩은 입력 `x`에 이미 더해져 Q·K·V Projection을 통과하므로 Head 계산 중 사라지는 값이 아니라는 점도 확인했다. `multi_head_output[0,0]`이 `[0,0,:]`와 같은 0번째 Batch·0번째 Token의 전체 벡터임을 확인했다. 이 벡터를 `W_O.T`에 직접 곱한 결과와 `nn.Linear`의 `projected_output[0,0]`을 `torch.allclose()`로 비교해 동일함을 검증했다. `assert d_model % num_heads == 0`으로 특징 차원이 Head 수로 나누어지는지 검사하고, `head_dim=d_model//num_heads`에서 `//`가 몫 나눗셈임을 확인했다. Q·K·V Projection은 모두 `nn.Linear(d_model,d_model,bias=False)`로 등록했다. 클래스 밖에서 `self.num_heads`를 사용해 생긴 `NameError`를 통해 `self`는 인스턴스 메서드 안에서만 사용할 수 있다는 점도 바로잡았다. Q·K·V Projection 직후 Shape은 모두 `[1,2,2]`였고, `view()`와 `transpose(1,2)`를 거쳐 `[batch,head,token,head_dim]=[1,2,2,1]`이 됐다. Head를 나누는 것은 Token을 늘리는 것이 아니라 Token마다 가진 특징 차원을 Head별로 나누는 것임을 다시 확인했다. 현재 `head_dim=1`에서는 `√1=1`이므로 Score Scaling 전후 숫자가 같은 것도 정상이다. 평균 0인 512차원 벡터에서 원소 제곱합의 기댓값을 1로 두면 각 원소의 제곱 기댓값이 `1/512`, 분산이 `1/512`, 표준편차가 `1/√512`로 이어지는 흐름을 자신의 분산 정의와 연결했다. 임베딩에 `√d_model`을 곱하는 작업과 Score를 `√head_dim`으로 나누는 작업은 서로를 취소하는 한 쌍이 아니라 목적이 다른 별도 Scaling임을 구분했다. AGI를 향한 연구를 하나의 알고리즘 이름으로 보지 않고 모델 구조·학습·메모리·계획·도구 사용·검증·서빙이 연결된 기술 지도로 살펴봤다. Agent Loop에서는 계획 → 실행 → 검증 이후 문제가 발견되면 결과를 다음 계획에 다시 반영하는 반복 구조와 코드 단위 검증의 역할을 읽었다.
