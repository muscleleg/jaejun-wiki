Road to LLM inference의 고정 후속 경로

우선순위 잠금 · 현재 관문과 후속 순서
사전학습 Causal LM 적용을 완료했으며, 이제 PyTorch 추론 Baseline → Benchmark 계약 → vLLM 서빙·관측 → Multi-GPU Scaling 순서로 이동한다. 기존 MTP Acceptance 실험과 GPU 측정 항목은 이 고정 경로 안에서 필요한 시점에 재사용하며 별도 다음 행동을 만들지 않는다.

1. PyTorch Causal LM 추론 Baseline

입력
Tiny Decoder LM의 Forward·학습·생성 완료 결과와 로컬에서 실행 가능한 최소 사전학습 Causal LM을 사용한다. 특정 Parameter 규모를 강제하지 않고 현재 장치에 들어가는 가장 작은 모델로 흐름을 먼저 검증한다.

실행 순서 A · 생성
Hugging Face Model의 Forward 출력에서 마지막 위치 Logits를 꺼내 Token 하나를 선택하고 입력 뒤에 직접 붙이는 Loop를 만든다. Greedy 생성까지 확인한 뒤 고정한 Logits와 Seed에서 Temperature·Top-k·Top-p를 하나씩 적용하여 후보 제한, 남은 확률의 재정규화와 출력 다양성을 비교한다.

실행 순서 B·C · Cache와 Batch
No-cache와 KV Cache 생성을 같은 Prompt에서 비교하고 Token마다 늘어나는 Cache Shape을 기록한다. Sequence Length를 바꾸며 latency·memory 변화를 본 뒤 Batch 1/N으로 확장하여 Padding·Attention Mask와 Batch 출력 Shape을 확인한다.

실행 순서 D · GPU 실행 경계
RunPod의 단일 CUDA GPU에서 모델·입력·Logit의 Device를 확인하고 CPU↔GPU H2D·D2H 이동을 구분한다. 같은 입력의 CPU·GPU 출력 일치를 확인한 뒤 CUDA의 비동기 실행과 torch.cuda.synchronize()를 적용한 Timing 경계를 비교한다. PyTorch Profiler에서 메모리 복사와 CUDA Kernel을 구분하되, Grid·Block·Thread·Warp와 직접 Kernel 최적화는 실제 병목이 확인될 때만 조건부 백로그에서 꺼낸다. 개념 연결은 Device에서 CUDA 병렬 실행까지의 문서를 사용한다.

실행 순서 E · 작은 구조 모듈
현재 LayerNorm+FFN Decoder Block은 같은 d_model과 입력 Shape의 RMSNorm+SwiGLU Block과 비교해 출력 Shape, Parameter와 연산 차이를 계산한다. Attention·MHA에서 GQA·RoPE로 확장하며 Query Head와 KV Head 공유 Shape, Q/K 회전 전후 Shape을 검증한다.

실행 순서 F · Baseline 고정
위 흐름을 하나의 Naive PyTorch 추론 경로로 연결하고 동일 Prompt·정답 세트에서 latency·peak VRAM·task accuracy 또는 Loss·perplexity를 기록한다. 속도만 좋아지고 품질이 무너지는 변경은 성공으로 보지 않는다.

완료 증거
마지막 위치 Logits→Token Append 추적, Sampling별 후보·재정규화·다양성 표, Sequence Length별 No-cache/KV-cache 결과, Batch Shape, CPU·GPU 출력 일치와 Device·H2D/D2H·동기화 Timing·Profiler 근거, 두 Decoder Block과 GQA·RoPE의 Shape·Parameter·연산 비교, 재현 가능한 PyTorch Baseline을 남긴다.

2. vLLM 전에 고정하는 Benchmark 계약

입력
1단계 Naive PyTorch Baseline과 Prompt·Output 길이별 작은 Load Generator를 사용한다.

계약 고정
Model 이름과 Revision, dtype, Prompt Token 수, Output Token 수, Concurrency, Warmup 횟수, 반복 횟수를 먼저 기록한다. Tokenization 포함 여부와 요청 시작·첫 Token·마지막 Token의 Timing 경계를 정하고, CUDA 비동기 실행을 재는 구간에서는 시작·종료 전후의 Synchronization 위치를 고정한다.

최소 Metric
TTFT, TPOT 또는 ITL, End-to-end latency, throughput 또는 tokens/sec, peak VRAM을 같은 정의로 계산한다. P50·P95·P99 같은 Tail Percentile은 각 Percentile을 해석할 만큼 충분한 Sample을 모았을 때만 보고하고, Sample 수를 결과 옆에 남긴다.

측정 비교
Concurrency와 Prompt·Output 길이를 바꾸며 Cache·Batch 효과를 비교하되 한 번에 조건 하나만 바꾼다. 평균값과 Tail을 섞지 않고, Metric 정의와 측정 시작·종료 지점을 유지한다.

완료 증거
Benchmark 계약표, 재실행 가능한 설정, PyTorch 결과표와 Timing 경계 설명을 남긴다. 이 계약을 바꾸지 않고 다음 단계 vLLM에 적용한다.

3. vLLM 서빙과 스케줄러

입력
1단계의 Naive PyTorch Baseline과 2단계의 동일한 Model·Revision·dtype·Prompt·Output 길이·Concurrency·Warmup·반복·Timing 계약을 사용한다.

작은 구현
vLLM Server를 띄우고 Continuous Batching, Paged KV Cache, Prefix Caching, Chunked Prefill을 하나씩 켜며 Scheduler의 요청 합류와 Prefill·Decode 처리를 관찰한다. max_num_seqs, max_num_batched_tokens, gpu_memory_utilization을 한 번에 하나씩 바꾼다.

측정 비교
같은 Benchmark 계약에서 Naive PyTorch와 vLLM의 TTFT·TPOT/ITL·End-to-end latency·throughput·peak VRAM을 비교하고, 각 설정이 KV Cache 사용량에 미친 효과와 역효과를 분리한다.

완료 증거
기본값과 튜닝값의 재현 가능한 설정표, 요청 수·길이별 결과, 가장 나은 설정이 어떤 Workload에서만 유효한지 설명한다.

4. Observability와 병목 분석

입력
같은 계약으로 재현된 PyTorch·vLLM 결과와 충분한 요청 Sample을 사용한다.

작은 구현
GPU 사용률·VRAM·KV Cache utilization을 Prometheus·Grafana·DCGM으로 연결하여 TTFT·TPOT·ITL·End-to-end latency·throughput과 같은 시간축에서 본다. 병목이 코드 내부에 있을 때만 PyTorch Profiler 또는 Nsight로 범위를 좁힌다.

측정 비교
평균값만이 아니라 충분한 Sample에서 P50·P95·P99와 자원 사용률을 함께 비교하고, Sample이 적으면 개별 측정값과 범위만 보고한다.

완료 증거
Metric 정의표, 관측 Dashboard와 재실행 설정, Tail latency와 GPU·VRAM·KV 사용량이 같은 시간축에서 병목을 설명하는 결과를 남긴다.

5. Multi-GPU Scaling

입력
단일 GPU에서 재현된 vLLM·Benchmark Baseline과 GPU Topology 정보를 사용한다.

작은 구현
Tensor Parallel(TP)과 Pipeline Parallel(PP)의 통신 경계를 작은 Shape으로 확인한 뒤 TP 1·2·4를 실행한다. nccl-tests로 통신 Baseline을 만들고 NVLink·PCIe, AllReduce와 NCCL 경로를 실제 Topology에 연결한다.

측정 비교
GPU 수별 latency·throughput·GPU당 VRAM을 측정하고 scaling efficiency = throughput_N / (N × throughput_1)로 이상적인 배수와의 차이를 계산한다. PP는 모델 크기나 메모리 제약이 실제 blocker일 때 비교한다.

완료 증거
Topology·NCCL 대역폭 결과, TP 1/2/4 Scaling 표와 그래프, 통신 때문에 효율이 떨어지는 구간을 근거와 함께 설명한다.

6. 선택 심화 · Prefill/Decode 분리와 KV 이동

입력
4·5단계에서 긴 Prompt의 Prefill과 Decode가 서로 다른 자원 병목을 만든다는 측정 증거가 있을 때만 시작한다.

작은 구현
먼저 한 프로세스의 Prefill·Decode 구간을 분리 측정하고, 필요하면 Disaggregated Prefill의 두 역할과 KV Transfer 최소 경로를 만든다. NIXL·UCX·RDMA·InfiniBand·RoCE는 전부 나열해 설치하지 않고, 선택한 전송 경로를 설명하는 데 필요한 구성만 검증한다.

측정 비교
통합 배치와 분리 배치를 같은 긴 Prompt 부하에서 비교하며 TTFT·TPOT·throughput·KV 전송량·네트워크 지연을 함께 본다.

완료 증거
KV가 어느 장치·프로세스 사이를 이동하는지, 전송 비용보다 분리 이득이 커지는 조건, 이득이 없는 조건까지 기록한다. 이 단계는 필수 완료 조건이 아니다.

Baseline 뒤의 독립 비교 · LoRA와 Quantization
LoRA는 추론 기능이 아니라 작은 데이터로 모델을 적응시키는 Fine-tuning 실험으로 분리하고, Base와 LoRA의 Task accuracy 또는 Loss·perplexity를 먼저 비교한 뒤 latency·VRAM을 함께 기록한다. Quantization은 FP16/BF16 PyTorch Baseline이 재현된 뒤 적용하는 모델 최적화 실험으로 분리하여 정밀도·VRAM·latency·품질 변화를 비교한다. 둘 다 vLLM 시작의 선행 완료 조건은 아니다.
기본 GPU 실험 환경 후보 · RunPod
Tiny Decoder LM과 최소 사전학습 모델의 Forward·마지막 위치 Logits·직접 Token Append·Greedy·Sampling까지는 현재 로컬 흐름으로 먼저 확인한다. 실제 CUDA 모델에서 KV Cache·Sequence Length·Batch의 latency와 memory를 측정해야 할 때부터 RunPod를 2차 심화의 기본 환경 후보로 사용한다. 1B~8B 같은 크기를 목표로 강제하지 않고 실험 목적과 VRAM에 맞는 가장 작은 모델부터 시작한다. 먼저 단일 GPU에서 모델·입력·출력의 Device, H2D·D2H 이동, CPU·GPU 출력 일치, CUDA 비동기 실행과 동기화된 Timing을 확인한 뒤 Container·CUDA/PyTorch/vLLM Version, Seed와 Workload를 고정해 Baseline을 만든다. Multi-GPU 단계에서는 같은 계열의 2·4 GPU 구성을 비교하고 nvidia-smi topo -m과 nccl-tests 결과를 함께 기록한다. 인스턴스 종료 전에는 코드·설정·측정 결과만 지속 저장소로 내보내고, Model Cache와 Data는 Volume 보존 또는 재다운로드 절차를 미리 정한다. 특정 계정·Pod에 종속된 값은 로드맵 증거로 사용하지 않는다.
조건부 후순위 · Kubernetes Inference 운영
KServe·LLMInferenceService·LeaderWorkerSet·Envoy AI Gateway·InferencePool/EPP·KEDA는 기존 Kubernetes 경험을 활용할 수 있지만, Inference Core와 단일·Multi-GPU Benchmark가 재현된 뒤에만 활성화한다. 3·4단계의 안정된 Server와 Metric을 입력으로 삼고, 실제 병목에 필요한 Routing·Model 배치·Autoscaling 구성 하나를 작게 구현한다. 로컬 Baseline 대비 배포 시간, 요청 분산, Scale-out 반응, 충분한 Sample에서의 P95/P99와 GPU utilization을 비교하고 장애·복구까지 재현했을 때만 운영 단계 증거로 남긴다. 제품 이름을 모두 설치하는 것은 완료 조건이 아니다.
