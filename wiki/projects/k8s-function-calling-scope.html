1. 이 프로젝트의 책임 경계

한국어 사용자 요청
        ↓
Qwen3-1.7B Function Calling 라우터
        ↓
도구명 + arguments를 담은 tool_calls 후보
        ↓
서버의 allowlist·JSON Schema·권한 검증
        ↓
실제 Kubernetes handler (이번 프로젝트에서는 연결하지 않음)

모델이 Kubernetes를 조회한 것이 아니다. 모델은 아래 계약에 맞는 호출 후보를 생성하는 부분까지만 담당했다. 서버 실행과 보안 경계의 일반 원리는 Function Calling과 도구 계약에서 설명한다.

2. 제공한 다섯 도구

다섯 도구의 원본 계약은 schemas/kubernetes_tools.json에 있고, 학습 데이터와 평가 요청에서 동일한 전체 도구 목록을 사용했다.

도구목적인자정답에 넣는 기준
list_pods네임스페이스의 파드 목록 조회namespace?, label_selector?사용자가 말한 namespace·label만 포함
get_pod특정 파드의 상세 상태 조회pod_name, namespace?pod_name은 필수
get_pod_logs특정 파드의 로그 조회pod_name, namespace?, container?, tail_lines?, previous?말한 옵션만 포함하고 기본값은 임의로 추가하지 않음
list_deployments네임스페이스의 Deployment 목록 조회namespace?, label_selector?Deployment와 selector 의미를 구분
get_eventsKubernetes 이벤트 조회namespace?, resource_kind?, resource_name?, event_type?Pod/Deployment, Normal/Warning enum 준수
물음표(?)의 의미
Schema에서 선택적인 필드라는 뜻이다. 사용자가 말하지 않은 선택 필드를 모델이 마음대로 채우면 실행 결과가 같아도 이 프로젝트의 strict exact match에서는 실패할 수 있다.

3. 모델이 만들어야 하는 출력

OpenAI-compatible 응답에서 애플리케이션이 읽는 핵심은 choices[0].message.tool_calls다. 이번 프로젝트의 정답은 한 요청당 도구 호출 하나였다.

{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": null,
      "tool_calls": [{
        "type": "function",
        "function": {
          "name": "list_pods",
          "arguments": "{\"namespace\":\"production\"}"
        }
      }]
    },
    "finish_reason": "tool_calls"
  }]
}

학습 데이터 안에서는 arguments를 객체로 보관하고, API 응답을 평가할 때는 JSON 문자열을 다시 파싱한다. 따라서 출력 검사는 “함수명이 맞는가 → JSON인가 → Schema인가 → 정답 인자와 같은가” 순서로 나뉜다.

4. 호출하지 않아야 하는 출력

제공한 도구가 조회 전용이므로 삭제·재시작·스케일 변경·일반 개념 질문에는 도구를 호출하지 않는 것이 정답이다.

{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": "지원하지 않는 변경 작업입니다.",
      "tool_calls": null
    },
    "finish_reason": "stop"
  }]
}

이 no-call 예시가 있어야 모델이 모든 Kubernetes 문장에 가장 가까운 조회 도구를 억지로 호출하지 않는지도 평가할 수 있다.

범위 밖이유다음 확장
