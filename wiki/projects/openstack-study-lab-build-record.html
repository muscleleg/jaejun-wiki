1. 무엇을 만들려고 했는가

목표는 단순히 OpenStack 설치 명령을 한 번 성공시키는 것이 아니다. 먼저 물리 Ubuntu 호스트에 일상적으로 사용할 수 있는 싱글노드 개인 클라우드를 만들고, 장기적으로는 그 클라우드가 제공하는 VM을 서버처럼 사용해 두 번째 멀티노드 OpenStack까지 직접 배포·운영하는 것이다.

장기 목표: OpenStack 위에 다시 OpenStack을 배포한다

L0: 현재 물리 호스트 (Ubuntu)
└─ 외부 OpenStack: Kolla-Ansible All-in-One
   ├─ 평소 사용할 개인 클라우드
   ├─ Nova / Neutron / Glance / Cinder / Horizon
   └─ OpenStack 인스턴스 3대
      ├─ deploy01             멀티노드 배포 도구
      ├─ control-network01    Controller + Network
      └─ compute01            내부 OpenStack Compute
         └─ L2: 내부 OpenStack 인스턴스

물리 PC에 먼저 하나의 완전한 OpenStack을 설치한다. 이후 일반 KVM 명령으로 별도의 실습 VM을 만드는 것이 아니라, 외부 OpenStack의 Nova API로 VM을 생성하고 그 VM들을 새 서버처럼 사용해 두 번째 OpenStack을 배포한다.

1 · 가상화와 VM 실행Nova · Hypervisor · libvirt · QEMU · KVM
Host · Guest

Host는 CPU·메모리를 실제로 제공하는 바깥 컴퓨터이고, Guest는 그 위에서 독립 서버처럼 실행되는 VM이다. 이 랩에서는 Ubuntu 물리 PC가 Host, test-vm이 Guest다.

Hypervisor

여러 VM의 CPU·메모리·장치를 격리하고 실행하는 가상화 계층을 통칭한다. 여기서는 QEMU/KVM 조합이 실제 VM 실행을 맡고 Nova는 그 위의 클라우드 관리 계층이다.

KVM

Kernel-based Virtual Machine. Linux 커널이 CPU의 가상화 확장을 사용하도록 하는 기능이다. VM의 vCPU 코드를 하드웨어에 가깝게 빠르게 실행하지만, 가상 디스크·NIC 모델 전체를 혼자 제공하지는 않는다.

QEMU

VM마다 실행되는 프로세스이자 가상 하드웨어 모델이다. 디스크·NIC·펌웨어 같은 장치를 Guest에 보여주며, 이 랩에서는 KVM 가속과 함께 사용된다.

libvirt

Nova가 QEMU/KVM 같은 Hypervisor를 일관된 방식으로 제어하게 해 주는 API·daemon·도구 계층이다. Nova가 정책과 수명주기를 결정하고, libvirt가 실제 VM 정의·시작·중지를 전달한다.

Nova · nova-compute

Nova는 OpenStack의 VM 수명주기 서비스다. 그중 nova-compute는 선택된 Compute Host에서 libvirt에 VM 생성·삭제·연결 작업을 실제로 요청하는 작업자다.

Server · Image · Flavor

Server는 OpenStack API에서 관리하는 VM 자원, Image는 Root Disk의 부팅 원본, Flavor는 vCPU·RAM·임시 Disk 크기를 묶은 가상 하드웨어 사양이다.

Keypair · cloud-init

Keypair 자원의 공개키가 VM 생성 때 Guest에 전달되고 사용자는 개인키로 SSH 인증한다. cloud-init은 Cloud Image가 이 키·Hostname·초기 설정을 첫 부팅에 적용하는 도구다.

QCOW2 · Cloud Image

QCOW2는 QEMU가 사용하는 Copy-on-write Disk Image 형식이다. Cloud Image는 일반 설치 ISO와 달리 클라우드에서 바로 부팅하고 cloud-init으로 초기화하도록 준비된 OS Disk 원본이다.

vCPU

Guest에 보이는 가상 CPU 실행 단위다. 물리 CPU 코어와 항상 1:1로 고정되는 것은 아니며, Nova Flavor가 VM에 몇 개를 보여줄지 정한다.

Nested Virtualization

VM 안에서 다시 VM을 실행하는 중첩 가상화다. 장기 목표의 L1 OpenStack VM 안에 L2 OpenStack 인스턴스를 만들려면 compute01 Guest까지 KVM 가속이 전달돼야 한다.

2 · Linux와 OVS 네트워크veth pair · Bridge · br-int · br-tun · br-ex · NAT
NIC · Interface

NIC는 네트워크 장치이고 Interface는 Linux가 그 장치를 다루는 접점이다. wlo1은 물리 Wi-Fi NIC, veth-ex는 소프트웨어로 만든 가상 Interface다.

L2 · Frame / L3 · Packet

L2는 MAC 주소와 Ethernet Frame을 기준으로 같은 망 안에서 전달한다. L3는 IP Packet과 Route를 기준으로 서로 다른 망 사이를 넘긴다. Bridge는 주로 L2, Router는 L3 역할이다.

Bridge

여러 Interface를 하나의 L2 구간으로 잇는 소프트웨어 스위치다. 어느 Port에서 배운 MAC 주소가 있는지 보고 Ethernet Frame을 전달한다.

OVS · Open vSwitch

OpenStack이 가상 네트워크를 만들 때 사용하는 프로그래밍 가능한 가상 스위치다. 단일 장치 이름이 아니라 여러 Bridge·Port·Flow 규칙을 관리하는 스위칭 시스템이다.

OVS Port · Patch Port

OVS Port는 Interface를 OVS Bridge에 붙이는 접점이다. Patch Port는 두 OVS Bridge를 내부에서 직접 잇는 가상 케이블 같은 Port다.

br-int

integration bridge. VM의 Neutron Port가 먼저 연결되는 OVS의 중심 통합 Bridge다. Security Group과 논리 네트워크 처리가 시작되는 내부 접점으로 보면 된다.

br-tun

tunnel bridge. VXLAN 같은 Overlay Tunnel을 처리하는 OVS Bridge다. 멀티노드에서는 다른 호스트의 Tenant Network로 Frame을 보낼 때 중요하고, AIO에서도 같은 논리 구조가 배포된다.

br-ex

external bridge. Neutron의 Provider Network를 OpenStack 바깥 네트워크 경계로 내보내는 OVS Bridge다. 이 랩에서는 veth-ex가 Port로 붙어 Ubuntu의 Provider Gateway 쪽과 이어진다.

veth pair

항상 두 끝이 한 쌍으로 생기는 Linux 가상 Ethernet 케이블이다. 한쪽으로 들어간 Frame이 다른 쪽으로 나온다. 스위칭·Routing·NAT를 스스로 하지는 않는다.

veth-ex · veth-host

이 랩에서 만든 veth pair의 두 이름이다. veth-ex는 IP 없는 br-ex L2 Port, veth-host는 172.24.4.1/24를 가진 Ubuntu L3 Gateway다.

Network Namespace

한 Linux 커널 안에서 Interface·Route·방화벽을 서로 분리해 보이게 하는 네트워크 공간이다. Neutron Router와 DHCP Agent는 Namespace를 사용해 프로젝트별 논리 장비처럼 동작한다.

ARP · MAC Learning

ARP는 같은 L2 망에서 대상 IPv4 주소에 대응하는 MAC 주소를 묻는다. MAC Learning은 Bridge가 어느 Port 뒤에 어떤 MAC이 있는지 기억하는 과정이다.

Route · Default Gateway · Next Hop

Route는 목적지 대역별 출구 규칙이다. 일치하는 구체적 Route가 없을 때 Default Gateway로 보내며, 그때 다음으로 전달할 Router 주소가 Next Hop이다.

IP Forwarding

Linux가 자기에게 온 패킷을 다른 Interface로 다시 전달하도록 허용하는 커널 기능이다. Host가 veth-host와 wlo1 사이 Router 역할을 하려면 필요하다.

NAT · SNAT · DNAT · Masquerade

NAT는 주소 변환 전체, SNAT는 출발지, DNAT는 목적지 변환이다. Masquerade는 나가는 Interface의 현재 주소를 사용하는 SNAT 방식이다.

conntrack

Linux가 연결의 원래 주소·변환된 주소·상태를 기억하는 기능이다. NAT를 거친 응답 패킷을 역변환해 원래 VM이나 클라이언트로 돌려보낼 수 있게 한다.

VXLAN · Overlay

Overlay는 기존 물리 IP망 위에 논리 L2망을 겹쳐 만드는 방식이다. VXLAN은 Ethernet Frame을 UDP Packet 안에 넣어 호스트 사이 Tenant Network를 운반한다.

MTU

한 Interface가 분할 없이 보낼 수 있는 최대 Packet 크기다. VXLAN은 바깥 Header를 추가하므로 Overlay MTU가 너무 크면 일부 통신만 끊기는 문제가 생길 수 있다.

3 · Neutron 자원과 주소Provider · Tenant · Port · Fixed IP · Floating IP
Provider Network

OpenStack 바깥의 물리·호스트 네트워크와 연결되는 Neutron Network다. 이 랩의 public은 Resource 이름일 뿐 인터넷에 직접 공개됐다는 뜻이 아니며, 172.24.4.0/24가 br-ex를 통해 Ubuntu 경계로 이어진다.

Tenant Network · Private Network

Project의 VM이 사용하는 논리 사설망이다. 이 랩의 private은 10.0.0.0/24 VXLAN이며 공유기 LAN과는 별개다.

Subnet · Allocation Pool

Subnet은 주소 대역·Gateway·DNS·DHCP 규칙을 담는다. Allocation Pool은 그 대역 중 Neutron이 실제 자원에 나눠 줄 수 있는 주소 범위다.

Neutron Port

Network에 연결되는 가상 NIC 접점이자 API Resource다. MAC·Fixed IP·Security Group·장치 소유 정보를 묶으며 VM NIC, Router Interface, DHCP Port가 모두 이 자원으로 표현된다.

Fixed IP

Neutron Port가 Subnet에서 배정받는 내부 주소다. test-vm의 10.0.0.236이 여기에 해당하며 VM NIC에서 직접 보인다.

Floating IP · FIP

Provider Network에서 빌려 특정 Neutron Port의 Fixed IP에 NAT로 매핑하는 외부용 주소다. VM NIC에 두 번째 IP로 직접 붙는 것이 아니다.

Neutron Router

Tenant Subnet 사이와 Tenant↔Provider 경계를 잇는 논리 L3 Router다. 내부 Gateway, 외부 Gateway, SNAT, Floating IP DNAT를 담당한다.

Security Group

VM 자체가 아니라 Neutron Port에 적용되는 상태 추적 방화벽 정책이다. Floating IP와 Route가 있어도 ICMP·SSH 허용 규칙이 없으면 해당 트래픽은 차단된다.

physnet · Bridge Mapping

physnet은 실제 연결 영역에 붙인 논리 이름이다. physnet1:br-ex Mapping은 physnet1 Provider Network를 OVS br-ex로 내보내라는 뜻이다.

Agent

Neutron Server의 결정을 각 노드에 실제로 반영하는 프로세스다. OVS Agent는 Port·Flow, L3 Agent는 Router/NAT, DHCP Agent는 VM 주소 배포를 담당한다.

4 · OpenStack 제어와 Kolla 배포AIO · API · VIP · Endpoint · Service · Agent · Container
AIO · All-in-One

Controller·Network·Compute 역할을 한 노드에 함께 배치한 구성이다. 역할이 없어진 것이 아니라 이 랩의 물리 Ubuntu Host 하나가 모두 맡는 것이다.

Controller · Network · Compute Node

Controller는 API·DB·Scheduler, Network는 Router·DHCP·외부 연결, Compute는 VM 실행을 주로 맡는다. 멀티노드에서는 이 역할을 여러 서버로 나눈다.

Control Plane · Data Plane

Control Plane은 요청을 인증하고 배치·상태를 결정한다. Data Plane은 결정 뒤 vCPU가 실행되고 실제 Packet과 Block I/O가 흐르는 경로다.

API · Endpoint

API는 서비스에 자원을 요청하는 규칙이고, Endpoint는 그 API를 호출할 URL이다. Service Catalog가 Keystone·Nova·Neutron 등의 Endpoint를 알려준다.

VIP · HAProxy

VIP는 여러 서비스 앞의 안정적인 대표 IP다. HAProxy는 VIP의 요청을 해당 API Backend로 전달한다. Kolla VIP는 VM의 Floating IP와 전혀 다른 주소다.

Keystone · Token · Project · Role

Keystone이 사용자를 인증해 Token을 발급한다. Project는 자원 소유 경계, Role은 그 안에서 허용된 권한 묶음이다.

Service · Agent · Container

Service는 Nova 같은 책임 단위, Agent는 노드에서 현장 작업을 반영하는 프로세스, Container는 Kolla가 그 프로세스를 격리해 실행하는 상자다.

Database · Message Queue

Database는 자원과 작업 상태를 저장한다. Message Queue는 API·Scheduler·Agent가 비동기 작업을 주고받게 한다. API 성공과 실제 현장 작업 완료 사이를 이어 주는 제어면 구성이다.

Kolla-Ansible · Ansible

Ansible은 원하는 호스트 상태를 Task로 반복 적용하는 자동화 도구다. Kolla-Ansible은 이를 이용해 Docker Container 형태의 OpenStack을 배포·설정한다.

Inventory · Playbook · globals.yml

Inventory는 어느 Host가 어떤 역할인지, Playbook은 수행할 Task 순서, globals.yml은 Kolla 배포에서 원하는 Network·Service·Backend 설정을 선언한다.

bootstrap-servers · prechecks

bootstrap은 호스트의 사용자·패키지·Runtime 기반을 준비한다. prechecks는 NIC·VIP·Port·설정·Storage가 배포 가능한지 변경 전에 검사한다.

pull · deploy · post-deploy · reconfigure

pull은 Image 준비, deploy는 최초 서비스 구성, post-deploy는 관리자 CLI 인증 파일 생성, reconfigure는 변경한 설정 재적용이다.

Idempotency · 멱등성

같은 선언을 여러 번 적용해도 결과가 같은 원하는 상태로 수렴하는 성질이다. Ansible의 중요한 원칙이지만, 외부 상태나 비멱등 명령 때문에 언제나 무조건 안전하다는 뜻은 아니다.

5 · Cinder와 Linux 블록 저장소Block Device · loop · LVM · thin pool · iSCSI · /dev/vdb
Block Device

데이터를 번호가 붙은 Block 단위로 읽고 쓰는 장치다. 파일 이름과 디렉터리는 제공하지 않으며, Guest의 /dev/vdb는 Cinder Volume이 보이는 Block Device다.

Filesystem · Mount

Filesystem은 Block Device 위에 파일·디렉터리 구조를 만든다. Mount는 그 Filesystem을 Guest의 특정 경로에 연결한다. Volume Attach만으로 파일을 바로 쓸 수 있는 것은 아니다.

Backing File · loop Device

Backing File은 실제 NVMe Filesystem 안의 cinder_data.img다. loop Device는 이 일반 파일을 LVM이 사용할 수 있는 Block Device처럼 보이게 한다. 자기 자신 통신용 Network Interface인 lo·loopback과는 다르다.

LVM · PV · VG · LV

PV는 LVM 사용 대상으로 초기화한 Block Device, VG는 PV를 묶은 저장 Pool, LV는 그 Pool에서 잘라 상위에 새 Block Device처럼 제공하는 논리 Volume이다. PV의 P는 Physical이지만 이 랩의 PV는 물리 Disk가 아니라 loop Device다.

Thin Pool · thin LV

논리 크기를 먼저 크게 약속하고 실제로 쓴 Block만 Backend에서 할당하는 방식이다. 1GB Cinder Volume을 만들었다고 즉시 backing file에 1GB가 기록되는 것은 아니다.

Cinder Backend

Cinder가 실제 Volume을 만드는 저장 구현이다. 이 랩은 cinder-volumes LVM VG를 Backend로 사용하지만, 다른 환경은 Ceph 같은 Backend를 사용할 수 있다.

iSCSI · Target · Initiator

SCSI Block I/O를 IP Network로 전달하는 Protocol이다. Cinder 쪽 Target이 Volume을 제공하고 Compute Host의 Initiator가 연결한 뒤 libvirt가 Guest에 디스크로 보여 준다.

Attachment · /dev/vdb

Attachment는 Cinder Volume과 Server의 연결 관계다. 같은 Volume이 Backend·Compute Host·Guest에서 서로 다른 장치 이름으로 보일 수 있으며 이 VM 안에서는 /dev/vdb였다.

available · in-use

available은 연결 가능한 Volume, in-use는 Server Attachment가 있다는 API 상태다. 둘 다 Guest에서 Filesystem 생성·Mount·파일 쓰기 성공을 대신 증명하지 않는다.

Persistent Volume

VM의 Root Disk 수명과 분리해 유지할 수 있는 Cinder Volume을 뜻한다. 다만 데이터 보존 여부는 삭제 정책·Backend·백업·복구 설계까지 함께 확인해야 한다.

여유 공간은 별도 미할당 파티션이 아니라 루트 ext4 파일시스템 안에 있다. Docker 컨테이너, Glance 이미지, Nova 임시 디스크는 이 공간을 바로 사용한다. Cinder LVM에는 별도 블록 장치가 필요하므로 파일 기반 loop 장치를 만들기로 했다.

4. Cinder와 파일 기반 가상 디스크의 의미

Cinder는 OpenStack VM에 영구 데이터 디스크를 제공하는 블록 스토리지 서비스다. Nova의 기본 인스턴스 디스크는 VM 수명과 밀접하게 연결되지만, Cinder 볼륨은 VM에서 분리하여 다른 VM에 연결하거나 VM 삭제 후에도 유지할 수 있다. AWS의 EBS와 유사하다.

4.1 우리가 만들 저장 계층

Ubuntu ext4 파일시스템
└─ /var/lib/cinder_data.img (계획: 100GB)
   └─ /dev/loopN              파일을 블록 장치로 표현
      └─ LVM PV               LVM이 사용할 물리 볼륨
         └─ VG cinder-volumes 저장 공간 풀
            ├─ LV volume-A    사용자 Cinder 볼륨
            ├─ LV volume-B
            └─ LV snapshot-...
  1. cinder_data.img는 Ubuntu 파일시스템 안의 큰 파일이다.
  2. losetup은 이 파일을 디스크처럼 보이는 /dev/loopN 장치로 연결한다.
  3. pvcreate는 해당 loop 장치를 LVM 물리 볼륨으로 초기화한다.
  4. vgcreate cinder-volumes는 Cinder가 사용할 저장 공간 풀을 만든다.
  5. Cinder는 사용자가 요청한 크기만큼 LVM 논리 볼륨을 만들고 iSCSI로 VM에 연결한다.
핵심: Windows SSD나 실제 Ubuntu 파티션을 Cinder PV로 초기화하지 않는다. 오직 명시적인 이미지 파일에 연결된 loop 장치만 LVM 대상으로 사용한다.

4.2 장점과 한계

장점한계
별도 SSD 없이 Cinder 생성·연결·분리·스냅샷 실습 가능파일시스템 위에 LVM을 중첩하므로 실제 전용 디스크보다 느림
Windows 디스크를 건드리지 않음Ubuntu 루트 디스크 장애가 Cinder 장애로 이어짐
파일을 백업 대상으로 식별하기 쉬움진짜 프로덕션 스토리지나 HA 구성이 아님
나중에 별도 SSD 또는 Ceph로 학습 확장 가능재부팅 후 loop 연결과 VG 활성화를 자동화해야 함

4.3 재부팅 안전성

단순히 한 번 losetup을 실행하면 재부팅 후 loop 번호가 달라지거나 연결이 사라질 수 있다. 따라서 설치 시 systemd unit을 만들어 다음 순서를 보장한다.

  1. 이미지 파일 존재 확인
  2. 사용 가능한 loop 장치에 이미지 파일 연결
  3. cinder-volumes VG 활성화
  4. 그 뒤 Docker/Kolla Cinder 서비스 시작

Kolla의 storage 그룹에 이 호스트를 포함하고 이름이 정확히 cinder-volumes인 VG를 제공한다. Cinder LVM 백엔드는 iSCSI target/client 컨테이너를 통해 볼륨을 Nova 인스턴스에 연결한다.

7. OpenStack 네트워크 기초와 현재 랩 호스트의 설계

이 절은 물리 NIC, 가상 NIC, Bridge, Open vSwitch, br-ex, Neutron Router의 관계를 먼저 설명한 뒤 Wi-Fi 환경에서 사용할 실제 네트워크 계획을 정리한다.

7.1 NIC와 가상 NIC

NIC(Network Interface Card)는 장비가 네트워크에 연결되는 포트다. 이 PC의 wlo1은 Wi-Fi NIC이고 enp42s0은 실제 RJ45 단자에 대응하는 유선 Ethernet NIC다. enp42s0은 내부 스위치가 아니며 현재 랜선이 없어 DOWN 상태다. VM에도 소프트웨어로 만든 가상 NIC가 있고, 호스트에서는 보통 tap 계열 인터페이스로 연결된다.

물리 PC
├─ wlo1       Wi-Fi NIC
├─ enp42s0    유선 물리 NIC
├─ VM 1 ─ tap0  가상 NIC의 호스트 측 연결
└─ VM 2 ─ tap1

7.2 Switch와 Bridge

스위치는 목적지 MAC 주소를 보고 Ethernet 프레임을 올바른 포트로 전달하는 L2 장치다. Linux Bridge는 이 기능을 소프트웨어로 구현한 가상 스위치다.

VM 1 tap0 ─┐
           ├─ br0 (Linux Bridge) ─ 물리 NIC ─ 물리 스위치
VM 2 tap1 ─┘

브리지에 가상 NIC와 물리 NIC를 함께 꽂으면 VM이 물리 네트워크에 연결된 것처럼 통신할 수 있다.

7.3 Open vSwitch

Open vSwitch(OVS)는 클라우드 환경을 위해 VLAN, VXLAN/Geneve 터널, OpenFlow 규칙, 포트·통계 자동 관리 기능을 강화한 가상 스위치다. OVS 안에서도 가상 스위치 하나를 bridge라고 부른다.

  • br-int: VM 포트와 OpenStack 내부 논리 네트워크가 만나는 integration bridge
  • br-tun: 일부 OVS 배포에서 VXLAN/Geneve 터널을 처리하는 bridge
  • br-ex: OpenStack과 외부 물리 네트워크가 만나는 external bridge

이 이름과 정확한 구성은 Neutron 백엔드에 따라 달라진다. OVN 기반 배포에서는 별도 br-tun이 없을 수도 있다.

7.4 br-ex와 Neutron Router의 관계

중요: br-ex는 Neutron Router 내부 구성요소가 아니다. Neutron Router의 외부 포트와 외부로 나가는 물리 또는 가상 NIC가 함께 연결되는 별도의 L2 가상 스위치다.
Neutron Router (L3 라우팅/NAT)
└─ 외부 포트
       │ 가상 연결
       ▼
   br-ex (L2 가상 스위치)
       │
       ▼
enp42s0 (물리 유선 NIC)
       │ 물리 랜선
       ▼
물리 공유기

VM이 외부로 나갈 때는 VM → Tenant network → Neutron Router → Router 외부 포트 → br-ex → enp42s0 → 공유기 순으로 이동한다. 외부에서 Floating IP로 들어오는 패킷은 반대 방향으로 이동한다. 그림은 포함 관계가 아니라 양방향 연결 관계다.

7.5 Wi-Fi에서 직접 브리징이 어려운 이유

유선 Ethernet은 한 물리 포트 뒤의 여러 MAC 주소를 자연스럽게 전달한다. 일반 Wi-Fi 클라이언트는 AP에 wlo1의 MAC 하나로 연결되므로, 뒤에서 Neutron Router와 여러 VM의 MAC이 나오면 AP나 무선 드라이버가 프레임을 받아주지 않을 수 있다.

  • VM의 DHCP·ARP가 외부 LAN까지 전달되지 않을 수 있다.
  • Floating IP가 같은 LAN의 다른 PC에서 보이지 않을 수 있다.
  • wlo1을 br-ex에 직접 넣으면 호스트 Wi-Fi 연결이 끊길 수 있다.
  • macvlan/macvtap도 여러 MAC 전달 문제를 근본적으로 해결하지 않는다.
  • 4-address/WDS는 AP와 드라이버가 모두 지원해야 하므로 기본 설계로 사용하지 않는다.

7.5.1 Ethernet은 한 포트 뒤의 여러 MAC을 어떻게 처리하는가?

Ethernet 프레임에는 출발지 MAC과 목적지 MAC이 있다. 물리 스위치는 들어오는 프레임의 출발지 MAC을 보고 “이 MAC은 이 포트 뒤에 있다”라고 학습한다. 한 스위치 포트 뒤에 또 다른 스위치나 가상화 호스트가 있을 수 있으므로 여러 MAC이 같은 물리 포트를 가리키는 것은 정상이다.

VM 1 MAC ─┐
VM 2 MAC ─┼─ br-ex ─ enp42s0 ─ 물리 스위치의 포트 5
Router MAC┘

물리 스위치 MAC 테이블:
VM 1 MAC   → 포트 5
VM 2 MAC   → 포트 5
Router MAC → 포트 5

VM 1이 보낸 프레임은 br-ex와 enp42s0을 지나도 출발지 MAC이 VM 1의 MAC으로 유지된다. 유선 NIC와 스위치는 이를 자연스럽게 전달하고 학습한다.

7.5.1.1 “이 포트 뒤에 있다”의 정확한 의미

스위치는 다른 스위치의 존재나 전체 네트워크 지도를 아는 것이 아니다. 각 MAC 주소로 프레임을 보내려면 자신의 어느 포트로 내보내야 하는지만 기억한다. 따라서 “MAC A가 포트 5 뒤에 있다”는 말은 “MAC A에 도달하려면 내 포트 5로 보내라”는 뜻이다.

스위치 1 포트 5 ─ 스위치 2
                   ├─ 포트 2 ─ 컴퓨터 A
                   └─ 포트 3 ─ 컴퓨터 B

스위치 1의 판단:
컴퓨터 A MAC → 포트 5
컴퓨터 B MAC → 포트 5

스위치 2의 판단:
컴퓨터 A MAC → 포트 2
컴퓨터 B MAC → 포트 3

스위치 1은 포트 5에 다른 스위치가 있는지, 컴퓨터가 직접 연결됐는지, 장비까지 몇 단계를 거치는지 모른다. A와 B가 보낸 프레임이 자신의 포트 5로 들어왔다는 사실을 관찰했을 뿐이다. 각 스위치는 자신의 포트 기준으로 독립적인 MAC address table을 만든다.

7.5.1.2 출발지 MAC을 이용한 학습

프레임이 들어오면 스위치는 출발지 MAC과 프레임이 들어온 포트를 연결해 기록한다.

출발지 MAC = AA:AA
들어온 포트 = 5
        ↓
학습 결과:
AA:AA로 보내려면 포트 5 사용

목적지 MAC을 전달할 때 이 테이블을 조회한다. 하나의 하위 스위치나 가상화 호스트 뒤에 여러 장비가 있으면 여러 MAC이 동일한 상위 스위치 포트를 가리키는 것이 정상이다.

7.5.1.3 아직 목적지 MAC을 모를 때: flooding

MAC 테이블에 목적지 주소가 아직 없다면 스위치는 프레임이 들어온 포트를 제외한 같은 네트워크의 다른 포트들로 프레임을 복제해 보낸다. 이를 unknown unicast flooding이라고 한다. 목적지 장비가 응답하면 응답의 출발지 MAC을 보고 해당 포트를 학습하고, 이후에는 그 포트로만 전달한다.

목적지 BB:BB의 포트를 모름
→ 다른 포트들로 flooding
→ B가 포트 5 방향에서 응답
→ BB:BB → 포트 5 학습
→ 다음부터 포트 5로만 전달

7.5.1.4 OpenStack 호스트에 적용

VM 1 ─┐
VM 2 ─┼─ br-ex ─ enp42s0 ─ 물리 스위치 포트 5
Router┘

물리 스위치의 MAC 테이블:
VM 1 MAC          → 포트 5
VM 2 MAC          → 포트 5
Neutron Router MAC → 포트 5

물리 스위치는 VM, br-ex, Neutron을 이해하지 않는다. 세 MAC에 도달하려면 자신의 포트 5로 보내면 된다는 사실만 학습한다.

7.5.1.5 일반적인 물리 스위치 환경 예제

컴퓨터 A                  컴퓨터 B
IP  192.168.1.10           IP  192.168.1.20
MAC AA:AA                  MAC BB:BB
    │ 포트 1                   │ 포트 2
    └───────── 물리 스위치 ────┘
                    │ 포트 8
                 공유기
                 IP  192.168.1.1
                 MAC RR:RR

처음에는 스위치의 MAC 테이블이 비어 있다고 가정한다. A가 같은 LAN의 B에게 통신하려면 먼저 ARP broadcast로 “192.168.1.20의 MAC이 무엇인가?”라고 묻는다.

A의 ARP 요청:
출발지 MAC = AA:AA
목적지 MAC = FF:FF:FF:FF:FF:FF (broadcast)
들어온 포트 = 1

스위치 학습:
AA:AA → 포트 1

broadcast 전달:
포트 1을 제외한 같은 LAN의 다른 포트로 복제

B가 “내 MAC은 BB:BB”라고 응답하면 응답은 포트 2로 들어온다. 스위치는 BB:BB → 포트 2를 학습하고, 이미 알고 있는 AA:AA → 포트 1을 조회해 응답을 포트 1로만 전달한다.

MAC스위치가 학습한 포트
AA:AA (컴퓨터 A)포트 1
BB:BB (컴퓨터 B)포트 2
RR:RR (공유기)포트 8

이후 A가 B에게 보내는 프레임은 출발지 MAC AA:AA, 목적지 MAC BB:BB다. 스위치는 목적지 테이블을 조회해 포트 2로만 전달한다.

7.5.1.6 인터넷으로 보낼 때의 IP와 MAC

A가 8.8.8.8로 보낼 때 이 주소는 같은 192.168.1.0/24 LAN에 없으므로 A는 외부 서버의 MAC을 찾지 않는다. 대신 기본 게이트웨이 192.168.1.1의 MAC RR:RR을 ARP로 알아낸다.

IP 패킷:
출발지 IP = 192.168.1.10
목적지 IP = 8.8.8.8

현재 LAN의 Ethernet 프레임:
출발지 MAC = AA:AA
목적지 MAC = RR:RR (공유기)

스위치 판단:
RR:RR → 포트 8

IP 목적지는 최종 서버지만 MAC 목적지는 현재 L2 구간에서 다음으로 전달받을 공유기다. 공유기는 기존 Ethernet 프레임을 벗기고 IP 목적지를 확인한 다음, 인터넷 쪽 다음 장비의 MAC을 사용해 새 Ethernet 프레임을 만든다. 라우터를 지날 때마다 L2 프레임과 MAC은 바뀌지만 IP 패킷의 최종 목적지는 유지된다(NAT가 있으면 출발지 IP 등은 추가로 변환된다).

7.5.1.7 물리 스위치가 두 대인 경우

컴퓨터 A
  │
스위치 1 포트 1
  │
스위치 1 포트 24 ─ 스위치 2 포트 24
                         │
                    스위치 2 포트 3
                         │
                      컴퓨터 B

스위치 1의 테이블:
A MAC → 포트 1
B MAC → 포트 24

스위치 2의 테이블:
A MAC → 포트 24
B MAC → 포트 3

스위치 1은 B가 스위치 2의 포트 3에 있다는 사실을 모른다. B에게 도달하려면 자신의 포트 24로 보내면 된다는 것만 안다. 스위치 2도 A의 정확한 위치 대신 자신의 포트 24 방향으로 보내야 한다는 것만 안다. 스위치들은 전체 토폴로지나 MAC 테이블을 서로 교환하지 않고, 각자 들어오는 프레임의 출발지 MAC을 관찰해 독립적으로 학습한다.

7.5.1.8 단계별 실습: 서로 다른 네트워크의 A와 C

다음은 대화에서 한 개념씩 확인한 순서를 보존한 학습 기록이다.

1단계 — 같은 네트워크인지 판단

컴퓨터 A: 192.168.1.10/24
목적지 B: 192.168.1.20
목적지 C: 192.168.2.20

A와 B: 192.168.1이 같음 → 같은 네트워크
A와 C: 192.168.1과 192.168.2가 다름 → 다른 네트워크

컴퓨터는 목적지 IP와 서브넷 마스크를 사용해 목적지가 자신과 같은 네트워크인지 먼저 판단한다.

2단계 — 같은 네트워크라면 목적지 MAC을 ARP로 확인

A와 B가 같은 네트워크라면 A는 “192.168.1.20의 MAC 주소를 알려 달라”는 ARP 요청을 보낸다. B가 자신의 MAC BB:BB를 응답하면 A는 다음 프레임을 만든다.

출발지 MAC = A의 MAC
목적지 MAC = B의 MAC

같은 네트워크에서는 상대 장비의 MAC을 알아내 직접 전달한다.

3단계 — 다른 네트워크라면 기본 게이트웨이 MAC 사용

A: 192.168.1.10/24
C: 192.168.2.20
A의 기본 게이트웨이: 192.168.1.1

A는 다른 네트워크에 있는 C의 MAC을 직접 찾지 않는다. ARP로 기본 게이트웨이의 MAC R1:R1을 알아낸다.

IP 목적지  = 192.168.2.20 (최종 목적지 C)
MAC 목적지 = R1:R1        (현재 전달할 게이트웨이)

4단계 — 라우터가 목적지 IP를 라우팅 테이블에서 검색

라우터는 목적지 MAC이 자신인 Ethernet 프레임을 받고, 그 안의 목적지 IP 192.168.2.20을 확인한다.

라우팅 테이블:
192.168.1.0/24 → 첫 번째 인터페이스
192.168.2.0/24 → 두 번째 인터페이스

판단:
192.168.2.20은 두 번째 인터페이스 방향

스위치는 목적지 MAC으로 포트를 선택하고, 라우터는 목적지 IP로 다음 인터페이스를 선택한다.

5단계 — 라우터가 목적지 네트워크에서 C의 MAC 확인

라우터 두 번째 인터페이스: 192.168.2.1
C:                         192.168.2.20

둘은 같은 네트워크이므로 라우터가 ARP로 C의 MAC CC:CC을 알아낸다. 라우터는 기존 Ethernet 프레임을 그대로 넘기지 않고 다음 구간에 맞는 새 프레임을 만든다.

출발지 MAC = 라우터의 두 번째 인터페이스 MAC
목적지 MAC = C의 MAC

6단계 — 새 프레임으로 C에게 전달

새 프레임의 IP:
192.168.1.10 → 192.168.2.20

새 프레임의 MAC:
라우터 두 번째 인터페이스 → C

두 번째 네트워크의 스위치는 목적지 MAC을 보고 C가 연결된 포트로 전달한다. C는 Ethernet 목적지 MAC과 IP 목적지가 모두 자신임을 확인해 데이터를 받는다.

핵심: 라우터를 지나면 각 L2 구간에 맞게 MAC 주소가 변경된다. NAT가 없는 일반 라우팅에서는 최종 출발지와 목적지 IP는 유지된다.

7단계 — 응답은 반대 방향

C는 A가 다른 네트워크에 있음을 판단하고 자신의 기본 게이트웨이로 응답을 보낸다.

C → 라우터:
IP 목적지  = A의 IP
MAC 목적지 = 라우터 두 번째 인터페이스 MAC

라우터 → A:
IP 목적지  = A의 IP
MAC 목적지 = A의 MAC

응답에서도 각 네트워크 내부는 MAC으로 전달되고, 네트워크 사이는 라우터가 목적지 IP를 보고 연결한다.

7.5.1.9 새 Ethernet 프레임: IP 편지와 MAC 봉투

Ethernet 프레임은 IP 패킷을 담는 구간별 봉투로 생각할 수 있다. A가 다른 네트워크의 C로 보낼 때, 편지의 최종 목적지는 C의 IP지만 첫 봉투의 목적지는 바로 다음 장비인 라우터의 MAC이다.

첫 번째 네트워크:

Ethernet 봉투
├─ 출발지 MAC = A
├─ 목적지 MAC = 라우터 R1
└─ IP 패킷
   ├─ 출발지 IP = A
   └─ 목적지 IP = C

라우터는 목적지 MAC이 자신인 프레임을 받아 기존 Ethernet 헤더를 제거한다. 목적지 IP를 라우팅 테이블에서 검색해 다음 인터페이스를 결정한다. 이것은 방화벽·NAT 규칙을 다루는 iptables와 다른 개념이다.

기존 프레임의 목적지 MAC은 라우터 자신이므로 다음 네트워크에서 그대로 사용할 수 없다. 라우터는 ARP로 C의 MAC을 확인한 뒤 다음 L2 구간에 맞는 새 Ethernet 프레임을 만든다.

두 번째 네트워크:

새 Ethernet 봉투
├─ 출발지 MAC = 라우터 R2
├─ 목적지 MAC = C
└─ 기존 IP 패킷
   ├─ 출발지 IP = A
   └─ 목적지 IP = C
구간MAC 주소IP 주소
A → 라우터A MAC → 라우터 R1 MACA IP → C IP
라우터 → C라우터 R2 MAC → C MACA IP → C IP
핵심: 일반 라우팅에서 출발지·목적지 IP는 종단 간 유지되고, MAC은 현재 L2 구간에서 바로 다음 장비로 전달하기 위해 라우터를 지날 때마다 바뀐다.
A ─── Router 1 ─── Router 2 ─── C

IP:
A ─────────────────────────────→ C

MAC:
A → R1      R1 → R2      R2 → C

정확히는 라우터가 IP 패킷의 TTL을 감소시키고 관련 헤더 값을 갱신한다. NAT가 적용되면 출발지 또는 목적지 IP도 바뀔 수 있지만, 이 절에서는 NAT가 없는 일반 라우팅을 설명한다.

7.5.2 Wi-Fi association과 MAC 주소

Wi-Fi에서는 wlo1이 자신의 MAC 주소로 AP에 인증하고 association을 맺는다. AP는 wlo1의 MAC을 연결된 무선 클라이언트로 알고 있지만, 그 뒤에 있는 VM 1·VM 2·Neutron Router의 MAC은 AP와 직접 association을 맺지 않았다.

AP에 등록됨: wlo1 MAC
AP에 직접 등록되지 않음:
├─ VM 1 MAC
├─ VM 2 MAC
└─ Neutron Router MAC

7.5.3 일반 3-address Wi-Fi 프레임의 제약

VM 프레임을 Wi-Fi로 투명하게 넘길 때는 원래 출발지, 원래 목적지, 현재 무선 송신자, 현재 무선 수신자인 AP를 모두 표현해야 한다. 일반적인 클라이언트 모드의 3-address 프레임은 이 네 관계를 유선 브리지처럼 모두 유지하기 어렵다.

표현할 관계:
1. 원래 출발지       VM 1
2. 원래 목적지       외부 장비
3. 무선 송신자       wlo1
4. 무선 수신자       AP

그 결과 드라이버가 VM MAC을 출발지로 한 프레임을 거부하거나, AP가 association되지 않은 MAC을 학습하지 못하거나, VM MAC으로 돌아오는 응답을 올바르게 전달하지 못할 수 있다.

7.5.3.1 왜 “선만 무선으로 바뀐 것”이 아닌가?

wlo1은 Ethernet 프레임을 그대로 전파로 보내는 단순한 무선 케이블이 아니다. 호스트가 받은 Ethernet 프레임을 Wi-Fi 규격의 802.11 프레임으로 다시 포장해 AP로 송신하는 무선 종단이다.

VM이 만든 Ethernet 프레임
├─ 원래 출발지 = VM 1 MAC
└─ 목적지      = 외부 장비 MAC
          │
          ▼ wlo1에서 802.11 형식으로 재포장
일반 Wi-Fi 클라이언트 프레임
├─ 프레임을 받을 AP
├─ 현재 무선 송신자 = wlo1
└─ 최종 목적지

VM 프레임을 유선 브리지처럼 투명하게 전달하려면 다음 네 관계를 모두 표현해야 한다.

1. 무선 수신자       = AP
2. 현재 무선 송신자  = wlo1
3. 원래 출발지       = VM 1
4. 원래/최종 목적지  = 외부 장비

일반 Wi-Fi 클라이언트의 3-address 방식에는 현재 송신자인 wlo1과 원래 송신자인 VM의 MAC을 별도로 모두 보존할 자리가 없다. 그래서 AP는 wlo1 뒤의 VM MAC을 유선 스위치처럼 투명하게 학습하기 어렵다.

핵심: 유선 NIC는 VM이 만든 Ethernet 프레임의 출발지 MAC을 그대로 내보낼 수 있지만, Wi-Fi NIC는 이를 802.11 프레임으로 변환해야 하며 일반 3-address 모드에서는 VM 원본 MAC과 wlo1 MAC을 동시에 표현하기 어렵다.

4-address/WDS 모드는 이 네 주소 관계를 표현할 수 있지만 AP와 Wi-Fi NIC, Linux 드라이버, 보안 설정이 모두 지원해야 한다.

7.5.4 DHCP에서 나타날 수 있는 증상

VM 1 DHCP 요청
→ br-ex
→ wlo1
→ AP

가능한 실패:
├─ 무선 드라이버가 프레임을 거부
├─ AP가 VM MAC을 받아들이지 않음
├─ 요청은 나가지만 응답 경로를 학습하지 못함
└─ VM이 DHCP 주소를 받지 못함

유선에서는 VM MAC이 그대로 유지되고 물리 스위치가 해당 MAC을 호스트 포트 뒤에서 학습하므로 요청과 응답이 정상적으로 왕복할 수 있다.

7.5.5 4-address/WDS

4-address 모드는 원래 출발지·목적지와 현재 무선 송신자·수신자를 모두 표현하여 무선 브리지를 가능하게 한다. 하지만 Wi-Fi NIC, Linux 드라이버, AP, 암호화 설정이 모두 호환되어야 하므로 일반 가정용 환경의 기본 전제로 사용하지 않는다.

7.5.6 NAT가 문제를 피하는 원리

NAT 구성은 VM의 Ethernet 프레임을 Wi-Fi에 투명하게 흘리지 않는다. Ubuntu가 L3 라우터 역할을 하며 외부로 나가는 패킷을 새 Ethernet 프레임으로 만들고, Wi-Fi에 보이는 출발지 IP와 MAC을 호스트의 것으로 바꾼다.

OpenStack 쪽:
출발지 IP/MAC = VM 또는 Neutron 쪽 주소
          │ Ubuntu 라우팅/NAT
          ▼
Wi-Fi 쪽:
출발지 IP  = 192.168.50.217
출발지 MAC = wlo1 MAC
          │
          ▼
AP에는 association된 wlo1 하나만 보임

응답이 돌아오면 Ubuntu는 NAT 연결 상태를 조회해 원래 OpenStack VM으로 전달한다. 즉, 여러 VM의 대외 통신을 wlo1이 대리하므로 AP가 VM별 MAC을 알 필요가 없다.

7.5.6.1 현재 랩 호스트에서 선택한 극복 방법

Wi-Fi로 VM의 MAC 주소를 투명하게 전달하지 않는다. OpenStack 외부망과 Wi-Fi망을 서로 다른 L2 네트워크로 분리하고, Ubuntu 호스트가 그 사이의 L3 라우터 및 NAT 역할을 맡는다.

Wi-Fi 쪽 프레임:
출발지 IP  = Ubuntu 192.168.50.217
출발지 MAC = wlo1 MAC

br-ex와 Ubuntu 호스트의 라우터 경계는 veth pair로 연결한다. veth pair는 호스트 내부의 가상 Ethernet 케이블로, 한쪽 veth-ex를 br-ex에 연결하고 다른 쪽 veth-host에 OpenStack 외부망의 게이트웨이 주소를 둔다.

Neutron Router
      │
    br-ex
      │
   veth-ex
      ║ 가상 Ethernet 케이블
  veth-host
      │ Ubuntu 라우팅/NAT
    wlo1
      │
   Wi-Fi AP
해결 원리: VM의 Ethernet 프레임을 Wi-Fi로 브리지하지 않는다. Ubuntu가 IP 패킷을 라우팅/NAT하고, wlo1이 자신의 MAC으로 정상적인 Wi-Fi 프레임을 만들어 전송한다. AP에는 association된 wlo1 하나만 보인다.

7.5.6.2 통합 정리: Wi-Fi 제약과 우리가 선택한 해결책

VM이 3-address 통신을 못 하는 것이 아니다. 문제는 wlo1이 VM의 Ethernet 프레임을 일반적인 3-address Wi-Fi 프레임으로 바꿀 때 VM의 원래 MAC을 추가로 보존하기 어렵다는 점이다.

VM 프레임을 Wi-Fi로 그대로 전달할 때

VM이 만든 Ethernet 프레임에는 원래 출발지와 목적지 MAC이 있다.

1. VM의 MAC
2. 목적지 MAC

wlo1이 이를 무선으로 보내려면 일반적인 Wi-Fi 3-address 형식으로 다시 포장해야 한다.

1. Wi-Fi 공유기(AP)
2. 실제 무선 송신자 wlo1
3. 최종 목적지

VM의 원래 MAC까지 투명하게 유지하려면 주소 관계가 하나 더 필요하다.

1. Wi-Fi 공유기(AP)
2. 실제 무선 송신자 wlo1
3. 최종 목적지
4. 원래 출발지 VM

따라서 일반적인 Wi-Fi 클라이언트 연결에서는 VM의 Ethernet 프레임을 원래 MAC 그대로 AP 너머로 전달하는 투명 브리징이 어렵다.

대안 질문: VM마다 가상 Wi-Fi를 만들면 되지 않을까?

이론적으로는 가능하지만 일반적인 가상 Ethernet처럼 간단하지 않다. 가상 Wi-Fi마다 다음 상태가 독립적으로 필요하다.

VM 1의 가상 Wi-Fi
├─ 별도 MAC
├─ AP association
├─ 인증 및 암호화 키
└─ 무선 연결 상태

VM 2의 가상 Wi-Fi
├─ 별도 MAC
├─ AP association
├─ 인증 및 암호화 키
└─ 무선 연결 상태

물리 Wi-Fi 장치 하나가 이를 제공하려면 Wi-Fi 칩셋, Linux 드라이버, 장치 펌웨어, AP, 가상 인터페이스 조합, 채널과 암호화 설정이 모두 지원되어야 한다. 일부 장치는 가상 무선 인터페이스를 지원하지만 여러 VM에 독립적인 Wi-Fi 클라이언트를 안정적으로 제공하는 기능은 일반적으로 보장되지 않는다.

PCI/USB passthrough로 물리 Wi-Fi 장치를 VM에 직접 넘길 수도 있지만, 일반적으로 해당 VM이 장치를 독점하므로 Ubuntu 호스트와 여러 VM이 함께 사용할 수 없다.

선택한 해결책: 가상 Ethernet + Ubuntu 라우터/NAT

VM에는 표준 가상 Ethernet NIC를 제공하고 VM의 MAC을 Wi-Fi까지 전달하지 않는다. Ubuntu 호스트가 VM들의 외부 통신을 받아 실제 wlo1으로 대신 보낸다.

VM들
→ 가상 Ethernet
→ Neutron Router
→ Ubuntu 라우터/NAT
→ wlo1
→ Wi-Fi 공유기

Ubuntu는 VM 쪽 Ethernet 프레임을 종료하고, NAT로 출발지 IP를 Ubuntu Wi-Fi IP로 변환한 다음, wlo1 MAC을 사용하는 새 Wi-Fi 프레임을 만들어 공유기로 전송한다.

Ubuntu 통과 전:
IP  = OpenStack 외부 IP
MAC = Neutron/OpenStack 쪽 MAC

Ubuntu 통과 후:
IP  = Ubuntu Wi-Fi IP
MAC = wlo1 MAC

결과적으로 AP에는 association된 wlo1 하나만 보이고, 내부 VM들의 MAC 주소를 알 필요가 없다.

한 문장 요약: 일반 Wi-Fi의 3-address 프레임에는 AP, wlo1, 최종 목적지 관계가 사용되어 VM의 원래 MAC까지 유지하기 어렵고, VM별 가상 Wi-Fi 역시 하드웨어·드라이버·AP 제약이 크다. 따라서 VM에는 가상 Ethernet을 제공하고 Ubuntu가 라우터/NAT 역할을 하며 VM들의 외부 통신을 wlo1의 IP와 MAC으로 대신 전달한다.

7.5.6.3 실제 동작만 본 요약

현재 환경에서는 VM마다 독립적인 가상 wlo를 만들어 각각 Wi-Fi에 연결하는 구성을 사용하지 않는다. 가상 Wi-Fi가 이론적으로 불가능한 것은 아니지만, 현재 Wi-Fi 칩셋·드라이버·AP가 여러 VM용 독립 Wi-Fi 연결을 안정적으로 지원한다고 전제할 수 없기 때문이다.

VM별 가상 wlo를 사용하지 않음

          ↓

동작 관점의 결론: VM들은 실제 wlo1을 직접 사용하지 않는다. Ubuntu가 NAT를 통해 여러 VM의 외부 통신을 모아 자신의 IP와 실제 wlo1으로 대신 내보낸다.

7.6.1 veth pair에서 한쪽만 IP를 갖는 이유

Ubuntu 호스트에 라우터/NAT를 만들 때 veth-ex와 veth-host는 서로 연결된 가상 랜선의 양쪽 끝이다.

veth-ex ═════════ veth-host
        가상 Ethernet 랜선
인터페이스역할IP
veth-exOpenStack의 br-ex에 꽂는 L2 스위치 포트/랜선 끝없음
veth-hostUbuntu 호스트 라우터의 L3 인터페이스172.24.4.1/24
 
Neutron Router 외부 포트
예: 172.24.4.100
        │
      br-ex
        │
     veth-ex        UP, IP 없음
        ║
     veth-host      UP, 172.24.4.1/24
        │
 Ubuntu 라우터/NAT
        │
      wlo1

veth-ex는 IP 통신의 종착점이 아니라 br-ex에 연결되는 L2 포트다. 물리 환경에서 랜선이나 스위치 포트 자체에 IP가 필요하지 않은 것과 같다. IP는 랜선 끝에 연결된 컴퓨터 또는 라우터의 L3 인터페이스가 가진다.

Kolla는 neutron_external_interface를 br-ex의 포트로 넣으므로 해당 인터페이스가 활성화돼 있으면서 IP는 없어야 한다. 미리 IP를 설정하면 브리지에 넣는 과정에서 IP 위치와 호스트 라우팅이 꼬일 수 있다.

배포 전:
veth-ex → UP, IP 없음

Kolla 배포 후:
br-ex
└─ veth-ex → L2 포트

반대편 veth-host는 Ubuntu 라우터의 게이트웨이이므로 172.24.4.1/24를 가진다. OpenStack의 Neutron Router는 외부망 주소에서 인터넷으로 나갈 때 이 주소를 게이트웨이로 사용한다.

Neutron Router 172.24.4.100
→ br-ex
→ veth-ex
→ veth-host 172.24.4.1
→ Ubuntu NAT
→ wlo1
검증 문구의 의미: “veth-ex가 IP 없이 UP”은 오류가 아니라 Kolla 외부 브리지용 포트가 의도한 상태로 준비됐다는 뜻이다. 동시에 veth-host가 172.24.4.1/24를 갖는지 함께 확인해야 한다.

7.7.1 DHCP 주소와 정적 VIP의 차이

IP 주소는 반드시 DHCP로만 설정되는 것이 아니다. DHCP는 장치가 공유기에게 주소를 요청하고 공유기가 풀에서 임대하는 자동 설정 방법이다. 정적 IP는 장치가 DHCP 요청 없이 자신의 인터페이스에 직접 설정하는 방법이다.

DHCP: 장치가 공유기에 주소를 요청하고 임대받음
정적 IP: 장치가 미사용 주소를 인터페이스에 직접 설정
주소역할
192.168.50.1ASUS 공유기
192.168.50.2 - 192.168.50.253DHCP 자동 할당 범위
192.168.50.217DHCP 범위 안에서 PC Wi-Fi MAC에 예약된 호스트 주소
192.168.50.254DHCP 풀 밖의 Kolla API 정적 VIP
192.168.50.255브로드캐스트 주소로 사용 불가

Kolla의 Keepalived는 배포 시 wlo1에 VIP를 추가한다.

wlo1
├─ 192.168.50.217  호스트 관리 주소
└─ 192.168.50.254  Kolla API VIP

다른 LAN 장비가 .254를 찾는 ARP 요청을 보내면 이 호스트가 wlo1 MAC으로 응답한다. 가정용 LAN에서는 같은 서브넷의 유효하고 중복되지 않은 주소를 장치가 직접 설정할 수 있다.

DHCP 풀에서 .254를 제외한 이유: Kolla가 직접 사용할 주소를 공유기가 다른 DHCP 클라이언트에게 임대해 IP 충돌이 생기지 않도록 하기 위해서다.

정적 주소는 같은 서브넷의 유효한 주소이고 다른 장비가 사용하지 않아야 하며 DHCP 자동 할당 대상에서도 제외해야 한다.

12. 바로 다음 작업

  1. 기존 Docker/container runtime, 방화벽, 네트워크 설정과 사용 중인 포트를 읽기 전용으로 조사한다.
  2. 외부 API VIP와 NAT/provider 네트워크에 사용할 충돌 없는 IP 대역을 결정한다.
  3. Kolla-Ansible 버전과 설치 경로를 고정한다.
  4. 그 다음 Cinder 100GB loopback LVM을 생성하고 재부팅 자동화를 검증한다.
현재 결론: 이 PC는 목표한 2계층 OpenStack 랩을 구성할 수 있다. Windows 1TB SSD는 완전히 제외하고 Ubuntu 512GB SSD의 여유 공간만 사용한다. Cinder는 100GB 파일 기반 LVM으로 시작하며, 이는 학습용으로 적합하지만 장기적으로는 별도 SSD 또는 Ceph로 이전하는 것이 바람직하다.

  • /var/lib/cinder_data.img는 아직 존재하지 않음.

  • pvcreate/vgcreate가 없어 LVM2 패키지 설치가 필요하며 기존 PV/VG/LV도 확인되지 않음.

CMD-019 — Cinder용 LVM2 설치 및 버전 확인

실행 명령(원문 그대로):

목적: Cinder가 블록 볼륨을 만들 때 사용할 LVM의 PV(Physical Volume), VG(Volume Group), LV(Logical Volume) 관리 도구를 설치한다.

결과: 종료 코드 0. lvm2 2.03.16과 의존 패키지 5개가 새로 설치되었으며, LVM 관련 systemd 링크가 생성되었다.

주의해서 해석할 출력: 패키지 설치는 관리자 권한으로 성공했다. 다만 뒤의 세 버전 확인 명령은 일반 사용자로 실행되어 /dev/mapper/control: Permission denied 경고가 출력되었다. 버전 문자열은 정상 출력됐고 전체 명령도 성공했지만, 실제 device-mapper 접근 여부는 다음 명령에서 관리자 권한으로 다시 확인한다.

변경 사항: Ubuntu 루트 파일시스템에 약 9 MB의 LVM 패키지가 추가되었다. 아직 Cinder 이미지 파일, loop 장치, PV, VG, LV는 만들지 않았으며 Windows 디스크에는 접근하지 않았다.

되돌리기: 아직 LVM 저장소를 만들지 않았으므로 필요 시 pkexec apt-get remove lvm2로 패키지를 제거할 수 있다. 단, 이후 Cinder VG를 만든 뒤에는 먼저 해당 VG/PV를 안전하게 해제해야 한다.

CMD-020 — Cinder 저장소 생성 직전 관리자 안전 검증

목적: 실제 파일 및 LVM 생성 전에 device-mapper가 관리자 권한으로 동작하는지 확인하고, 동일한 파일·VG가 없어 덮어쓸 위험이 없는지 검사하며, 대상 Ubuntu SSD와 Windows SSD를 다시 구분한다.

결과: 종료 코드 0. LVM 드라이버 버전 4.49.0이 정상 확인됐다. /var/lib/cinder_data.img와 cinder-volumes VG는 모두 없었다. Ubuntu 루트(/dev/nvme1n1p2)에는 425GB가 남아 있었다.

디스크 안전성: 작업 대상은 Ubuntu가 설치된 /dev/nvme1n1p2의 파일시스템 내부 파일이다. Windows가 있는 /dev/nvme0n1과 그 파티션에는 읽기 목록 확인 외의 작업을 하지 않았다.

변경 사항: 읽기 전용 검증만 했으므로 없음.

CMD-021 — Cinder용 100GB 파일 생성

실행 명령(원문 그대로):

목적: 별도 물리 디스크 대신 Ubuntu 파일시스템 안에 Cinder LVM의 기반이 될 100GB 파일을 만든다. 첫 번째 test는 기존 파일을 실수로 덮어쓰지 않도록 막는 안전장치다.

현재 의미: 아직은 일반 파일이다. 다음 단계에서 loop 장치에 연결해야 Linux가 이 파일을 디스크처럼 보고, 그 위에 LVM PV와 cinder-volumes VG를 만들 수 있다.

Windows 안전성: 작업 경로는 Ubuntu의 /var/lib이며 /dev/nvme0n1에는 접근하지 않았다.

되돌리기: 현재 단계에서만 되돌릴 경우 이 파일 하나를 제거하면 된다. 이후 loop/PV/VG를 만든 뒤에는 VG·PV·loop 순으로 먼저 해제해야 한다.

CMD-022 — Cinder 파일을 loop 장치에 연결

실행 명령(원문 그대로):

pkexec losetup --find --show /var/lib/cinder_data.img

목적: 일반 파일을 Linux가 블록 디스크처럼 사용할 수 있도록 현재 비어 있는 loop 장치에 연결한다.

결과: 종료 코드 0. 이 부팅 세션에서 /var/lib/cinder_data.img가 /dev/loop13에 연결됐다.

중요: /dev/loop13 번호는 영구 고정값이 아니며 재부팅 후 달라질 수 있다. 따라서 영구 설정에서는 번호를 하드코딩하지 않고 이미지 파일을 기준으로 빈 loop 장치를 찾게 해야 한다.

변경 사항: 파일과 loop 장치 사이의 런타임 연결만 생성했다. 아직 PV나 VG는 생성하지 않았다.

되돌리기: PV/VG 생성 전에는 pkexec losetup -d /dev/loop13으로 분리할 수 있다.

CMD-023 — loop 장치 대상과 기존 서명 읽기 전용 검증

실행 명령(원문 그대로):

목적: 파괴적일 수 있는 pvcreate 전에 명시한 장치가 Cinder 파일을 가리키는지, 크기가 맞는지, 기존 서명이 없는지 읽기 전용으로 검증한다.

결과: 종료 코드 0. /dev/loop13의 backing file은 정확히 /var/lib/cinder_data.img였고 크기는 107,374,182,400바이트(100GiB)였다. wipefs -n 출력이 없어 기존 파일시스템/LVM 서명도 없었다.

변경 사항: 없음. 세 명령 모두 조회만 수행했다.

CMD-024 — Cinder LVM PV와 VG 생성

실행 명령(원문 그대로):

pkexec /usr/sbin/pvcreate /dev/loop13 && pkexec /usr/sbin/vgcreate cinder-volumes /dev/loop13 && pkexec /usr/sbin/pvs -o pv_name,vg_name,pv_size,pv_free && pkexec /usr/sbin/vgs cinder-volumes -o vg_name,vg_size,vg_free,pv_count,lv_count

목적: 검증된 loop 장치를 LVM Physical Volume으로 초기화하고, Kolla Cinder LVM 백엔드가 찾는 이름인 cinder-volumes Volume Group을 만든다.

결과: 종료 코드 0. PV /dev/loop13과 VG cinder-volumes가 생성됐다. VG 크기는 약 100GB이며 현재 LV가 0개라 전체 공간이 비어 있다.

개념: 파일 → loop 블록 장치 → LVM PV → cinder-volumes VG 순으로 감쌌다. OpenStack 사용자가 Cinder 볼륨을 만들면 이후 이 VG 안에 LV가 생성된다.

변경 사항: /dev/loop13 처음 부분에 LVM 메타데이터가 기록됐다. 명령 대상은 앞 단계에서 Cinder 파일로 확인한 loop 장치뿐이다.

되돌리기 순서: Cinder 서비스 중지 → 모든 Cinder LV 제거 확인 → vgremove cinder-volumes → pvremove /dev/loop13 → loop 분리 → 이미지 파일 제거 순서가 필요하다. 데이터가 생긴 뒤에는 파괴적이므로 자동으로 수행하지 않는다.
