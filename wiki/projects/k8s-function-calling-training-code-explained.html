1. 1–55행 · 진입점과 설정 읽기

원본 코드의 1–55행으로 돌아가기 ↗ 
def parse_args() -> argparse.Namespace:
    parser = argparse.ArgumentParser()
    parser.add_argument("--config", type=Path, ...)
    parser.add_argument("--resume", default="auto")
    parser.add_argument("--validate-only", action="store_true")
    return parser.parse_args()

def load_config(path: Path) -> dict[str, Any]:
    with path.open(encoding="utf-8") as handle:
        config = yaml.safe_load(handle)
    if not isinstance(config, dict):
        raise ValueError(...)
    return config

parse_args()는 터미널 문자열을 Python 객체로 바꾼다. config는 모델·데이터·LoRA 수치를 담고, resume은 중단된 checkpoint에서 이어갈지 정한다. 설정을 코드에서 분리했기 때문에 같은 학습 로직으로 다른 실험 조건을 실행할 수 있다.

코드실제 의미
Path문자열 경로를 운영체제에 맞는 경로 객체로 다룬다.
yaml.safe_loadYAML 문서를 Python dict로 읽되 임의 코드를 실행하지 않는다.
--validate-only모델 가중치를 올리기 전에 환경·데이터·템플릿만 검사한다.

2. 58–104행 · 데이터 한 행 검증

원본 코드의 58–104행으로 돌아가기 ↗ 
def validate_record(record, path, line_number):
    messages = record.get("messages")
    tools = record.get("tools")
    if not isinstance(messages, list) or len(messages) < 2:
        raise ValueError(...)
    if messages[-1].get("role") != "assistant":
        raise ValueError(...)
    assistant = messages[-1]
    if not assistant.get("tool_calls") and not assistant.get("content"):
        raise ValueError(...)

def load_jsonl(path):
    for line_number, line in enumerate(handle, 1):
        record = json.loads(line)
        validate_record(record, path, line_number)
        records.append(record)

한 줄을 단순히 JSON으로 읽는 데서 끝나지 않고, 마지막 메시지가 assistant인지, 도구 목록이 있는지, assistant가 tool call 또는 no-call content를 갖는지 확인한다. 학습 도중에야 데이터가 깨졌다는 사실을 발견하지 않도록 입력 단계에서 실패시킨다.

이 검증은 모델의 예측을 평가하는 코드가 아니다. “학습 정답이 계약에 맞는가”를 검사하는 전처리 단계다. 데이터 한 행의 구조는 데이터셋 상세에서 이어 본다.

3. 107–142행 · CUDA와 BF16 확인

원본 코드의 107–142행으로 돌아가기 ↗ 
if not torch.cuda.is_available():
    raise RuntimeError("CUDA is unavailable...")
if not torch.cuda.is_bf16_supported():
    raise RuntimeError("...native BF16 support")

free_bytes, total_bytes = torch.cuda.mem_get_info()
torch.cuda.memory_allocated()
torch.cuda.memory_reserved()
torch.cuda.max_memory_allocated()

이 실험은 RunPod NVIDIA GPU에서 BF16으로 학습하도록 정했기 때문에 CPU나 BF16을 지원하지 않는 GPU에서는 시작하지 않는다. memory_allocated와 memory_reserved는 학습을 수행하는 코드가 아니라 어느 단계에서 GPU 메모리가 증가했는지 기록하는 관측 코드다.

BF16과 양자화는 다른 선택이다.
여기서 dtype=torch.bfloat16은 가중치와 연산을 BF16으로 준비한다는 뜻이다. INT4·INT8처럼 표현 가능한 값을 줄이는 양자화를 적용한 것이 아니다. 정밀도 형식 문서에서 둘을 비교한다.

4. 145–185행 · Assistant-only loss의 안전장치

원본 코드의 145–185행으로 돌아가기 ↗ 
rendered = tokenizer.apply_chat_template(
    row["messages"],
    tools=row["tools"],
    tokenize=True,
    return_dict=True,
    return_assistant_tokens_mask=True,
)
mask = rendered.get("assistant_masks")
if not mask or sum(mask) == 0:
    raise RuntimeError(...)
if len(mask) != len(rendered["input_ids"]):
    raise RuntimeError(...)

모델 입력에는 system·도구 Schema·user 질문·assistant 정답이 모두 들어간다. 하지만 학습 loss는 assistant 정답 토큰에만 계산해야 한다. 이 함수는 tool-call 예제와 no-call 예제를 각각 골라 템플릿이 assistant 위치를 표시했는지 먼저 검사한다.

mask의 길이는 전체 input_ids와 같아야 하고, 합계가 0이면 학습할 정답 위치가 하나도 없다는 뜻이다. 이 검사를 통과하지 못하면 900개 예제를 GPU에 넣기 전에 즉시 중단한다. 입력과 출력의 계약은 Function Calling 계약 문서와 연결된다.

5. 188–274행 · checkpoint·revision·tokenizer·template

모델 ID만 기록하면 나중에 같은 이름이 다른 revision을 가리킬 수 있다. 그래서 Hugging Face commit SHA를 확정하고 모델과 tokenizer를 같은 revision에서 읽는다. Jinja chat template은 구조화된 messages와 tools를 Qwen이 학습할 문자열로 직렬화하는 규칙이다.

마지막 길이 검사는 template 적용 후 token 수가 max_length=1152를 넘는지 확인한다. 길이를 초과하면 assistant 정답이 잘릴 수 있으므로 학습 전에 중단한다.

6. 276–301행 · Qwen 로딩과 LoRA 장착 규칙

원본 코드의 276–301행으로 돌아가기 ↗ 
model = AutoModelForCausalLM.from_pretrained(
    config["model_id"],
    revision=resolved_revision,
    dtype=torch.bfloat16,
    device_map={"": 0},
)
model.config.use_cache = False

peft_config = LoraConfig(
    task_type="CAUSAL_LM",
    r=int(config["lora_r"]),
    lora_alpha=int(config["lora_alpha"]),
    lora_dropout=float(config["lora_dropout"]),
    target_modules=config["lora_target_modules"],
    bias="none",
)

AutoModelForCausalLM은 Qwen 설정을 읽어 decoder-only 다음 토큰 예측 모델을 구성한다. use_cache=False는 추론용 KV cache를 학습 중에는 끄는 설정이다.

LoraConfig를 만드는 순간 가중치가 바뀌지는 않는다. “어떤 Linear에 rank 16의 A/B adapter를 붙일지”를 적은 규칙이며, 실제 장착은 SFTTrainer가 만든다. 원본 Qwen 가중치는 동결하고 adapter만 업데이트한다. 행렬 흐름은 Qwen과 LoRA 문서에서 자세히 설명한다.

8. 335–369행 · SFTConfig로 학습 행동 지정

원본 코드의 335–369행으로 돌아가기 ↗ 
training_args = SFTConfig(
    num_train_epochs=1.0,
    per_device_train_batch_size=1,
    gradient_accumulation_steps=16,
    learning_rate=2e-4,
    max_length=1152,
    assistant_only_loss=True,
    gradient_checkpointing=True,
    bf16=True,
    fp16=False,
    eval_strategy="steps",
    save_strategy="steps",
    ...
)

GPU batch 1에서 16개의 gradient를 모은 뒤 optimizer를 한 번 업데이트하므로 유효 batch 크기는 16에 가깝다. learning rate는 LoRA A/B 가중치를 움직이는 보폭이고, assistant_only_loss는 입력이 아니라 assistant 정답만 loss 대상이 되게 한다.

Gradient checkpointing은 중간 activation을 모두 저장하지 않고 backward 때 일부를 다시 계산해 메모리를 줄인다. bf16=True와 fp16=False는 이 실험을 BF16으로 고정한다. 세부 수치의 의미는 원본 페이지의 설정 해설에서 다시 본다.

9. 371–389행 · SFTTrainer에 데이터·LoRA 연결

원본 코드의 371–389행으로 돌아가기 ↗ 
trainer = SFTTrainer(
    model=model,
    args=training_args,
    train_dataset=Dataset.from_list(train_records),
    eval_dataset=Dataset.from_list(valid_records),
    processing_class=tokenizer,
    peft_config=peft_config,
    callbacks=[GpuMemoryCallback()],
)
train_result = trainer.train(
    resume_from_checkpoint=resume_checkpoint
)

Dataset.from_list는 Python dict 목록을 Trainer가 읽는 Dataset으로 변환한다. processing_class는 tokenizer와 chat template, peft_config는 LoRA 장착 규칙을 Trainer에 전달한다. 이 생성 시점에 PEFT가 대상 Linear에 adapter를 붙이고 원본 파라미터를 동결한다.

실제 forward, assistant-only loss, backward, gradient accumulation, AdamW update는 trainer.train() 내부에서 반복된다. 따라서 이 파일에서 우리가 직접 작성한 것은 학습 알고리즘 자체가 아니라 라이브러리에 입력 계약과 설정을 연결하는 부분이다.

10. 390–412행 · adapter와 지표 저장

원본 코드의 390–412행으로 돌아가기 ↗

tokenizer.save_pretrained(str(output_dir / "final_adapter"))

final_adapter에는 Qwen 전체 가중치가 아니라 LoRA A/B와 설정이 저장된다. tokenizer도 함께 저장해 PAD·EOS·chat template이라는 입력 계약을 보존한다. validation loss는 모델 확률의 학습 지표이고, 실제 tool call 성공률은 별도의 평가 코드가 계산한다.

학습 완료와 서비스 가능은 다른 단계다.
저장된 adapter를 원본과 실행 중 장착하거나 merge_and_unload()로 BF16 merged 모델을 만든 뒤 vLLM에 올려야 최종 Function Calling 평가를 할 수 있다.
