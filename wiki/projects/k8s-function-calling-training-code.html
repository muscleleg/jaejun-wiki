중요한 점은 이 파일 하나가 Kubernetes API를 실행하는 코드가 아니라는 것이다. 이 스크립트는 모델이 한국어 요청을 도구 호출로 변환하는 확률을 학습하고, 그 결과물을 저장하는 역할만 담당한다.

3. 프로그램 진입점과 설정

main()은 정의와 실행이 다르다

def main() -> None:
    ...

if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO, ...)
    main()

def main()은 할 일을 함수로 등록할 뿐이고, 파일을 직접 실행했을 때 마지막 main()이 호출되며 실제 학습 절차가 시작된다. -> None은 반환값이 없다는 타입 힌트다.

로그 설정

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s",
)

logging은 Python 표준 라이브러리 모듈이다. 시간·등급·로거 이름·메시지를 일정한 형식으로 출력해 RunPod 실행 기록을 다시 읽을 수 있게 한다.

CLI와 YAML

args = parse_args()
config = load_config(args.config)

python scripts/train_runpod_bf16_lora.py \
  --config configs/runpod_bf16_lora.yaml \
  --resume auto

parse_args()는 --config, --resume, --validate-only를 객체로 묶고, load_config()는 YAML을 Python 딕셔너리로 바꾼다. 학습률·LoRA rank·데이터 경로를 코드에 하드코딩하지 않고 설정 파일에서 읽는 구조다.

if args.validate_only:
    LOGGER.info("validation complete; BF16 model weights were not loaded")
    return

--validate-only는 CUDA·의존성·데이터·tokenizer·mask·길이만 확인하고 큰 Qwen 가중치는 올리지 않는다. RunPod에서 학습을 시작하기 전에 빠르게 설정 오류를 찾는 안전한 분기다.

경로 객체

path = Path(value)
return path if path.is_absolute() else PROJECT_DIR / path

Path / "파일명"은 나눗셈이 아니라 경로 연결이다. 상대 경로를 프로젝트 기준 경로로 바꿔 RunPod에서 어느 작업 디렉터리에서 실행해도 같은 파일을 찾게 한다.

4. PyTorch 환경·데이터·재현성

PyTorch와 GPU 검사

require_cuda_bf16()
set_seed(int(config["seed"]))
log_gpu("startup")

import torch는 모델·텐서·CUDA·BF16·기울기 계산을 사용할 수 있게 하는 것이며, 그 자체로 학습을 시작하지 않는다. require_cuda_bf16()는 CUDA가 있고 native BF16을 지원하는지 확인한다. 이 프로젝트는 RunPod NVIDIA GPU에서만 실행하도록 의도했다.

set_seed(42)는 의사 난수의 시작점을 고정해 셔플과 일부 초기 조건을 재현하기 쉽게 한다. GPU 연산 특성 때문에 모든 비결정성이 사라진다는 뜻은 아니다.

GPU 관측 로그

free_bytes, total_bytes = torch.cuda.mem_get_info()
gib = 1024**3
torch.cuda.memory_allocated()
torch.cuda.memory_reserved()
torch.cuda.max_memory_allocated()

log_gpu(stage)는 학습 함수가 아니라 관측 함수다. stage에 startup, model_loaded, finished를 넣어 어느 시점에 메모리가 늘었는지 비교한다. 바이트를 1024**3으로 나눠 GiB로 기록한다.

JSONL 로딩과 검증

data_dir = resolve_path(config["data_dir"])
train_records = load_jsonl(data_dir / "train.jsonl")
valid_records = load_jsonl(data_dir / "valid.jsonl")

load_jsonl()은 한 줄씩 JSON을 파싱하고 validate_record()로 메시지·도구·assistant 정답을 검사한다. Train 800건과 Validation 100건은 학습 중 사용하고, test.jsonl 100건은 이 단계에서 읽지 않고 최종 holdout으로 보존한다.

데이터의 messages와 tools

row = {
  "messages": [
    {"role": "user", "content": "default의 파드 목록을 보여줘"},
    {"role": "assistant", "tool_calls": [{
      "function": {
        "name": "list_pods",
        "arguments": {"namespace": "default"}
      }
    }]}
  ],
  "tools": ["전체 다섯 도구의 Schema"]
}

messages는 질문과 정답 assistant 응답이고, tools는 모델이 고를 수 있는 전체 후보 목록이다. tool_calls가 없는 no-call 행에도 전체 도구 목록은 주어진다. 도구로 처리할 수 없는 삭제·재시작 요청에 억지로 도구를 만들지 않는 것도 학습 대상이다.

일반 Chat Completions에서 모델이 이전 대화를 영구 기억하는 것은 아니다. 애플리케이션이 기존 messages에 새 user·tool 결과를 추가해 전체 기록을 다시 보내야 다음 호출과 최종 답변이 이어진다. 이번 프로젝트의 학습 예제는 이 중 한 번의 호출만 고정한다.

5. 모델이 볼 문자열 만들기: revision·tokenizer·Jinja

모델 revision 고정

resolved_revision = HfApi().model_info(
    config["model_id"],
    revision=config["model_revision"],
).sha

Qwen/Qwen3-1.7B 같은 model ID만으로는 시간이 지나 가리키는 내용이 달라질 수 있다. 그래서 Hugging Face 커밋 SHA를 고정한다. Docker의 latest와 이미지 digest를 구분하는 것과 같은 재현성 장치다. 모델과 tokenizer는 같은 revision으로 불러온다.

Tokenizer와 PAD·EOS

tokenizer = AutoTokenizer.from_pretrained(
    config["model_id"],
    revision=resolved_revision,
    use_fast=True,
)
if tokenizer.pad_token is None:
    tokenizer.pad_token = tokenizer.eos_token

문자열은 곧바로 벡터가 되지 않고 문자열 → 토큰 ID → embedding → 벡터 순서로 변환된다. 배치의 길이를 맞출 전용 PAD가 없으면 EOS 토큰 ID를 패딩 위치에 재사용한다. EOS를 문장마다 새로 추가한다는 뜻은 아니다.

Chat template을 등록하는 이유

chat_template_path = resolve_path(config["chat_template_path"])
tokenizer.chat_template = chat_template_path.read_text(encoding="utf-8")

rendered = tokenizer.apply_chat_template(
    row["messages"],
    tools=row["tools"],
    tokenize=True,
    return_dict=True,
)

JSON 형태의 messages와 tools를 Qwen이 익힌 대화 문자열로 조립하는 규칙이 Jinja template이다. 이 파일은 토큰 사전·토큰 번호·가중치를 바꾸지 않고, 토큰화 전에 구조화된 입력을 어떤 문자열로 만들지만 결정한다.

<|im_start|>system
<tools> ... 도구 Schema ... </tools>
<|im_end|>
<|im_start|>user
사용자 요청
<|im_end|>
<|im_start|>assistant
<tool_call>{"name":"list_pods","arguments":{...}}</tool_call>
<|im_end|>

Jinja의 {% if %}, {% for %}는 실행문이고 {{ value }}는 출력문이다. tool | tojson은 도구 딕셔너리를 JSON 문자열로 삽입한다. 실제 학습과 서빙에서 같은 형식을 사용해야 한다.

{% generation %}과 assistant-only loss

{% generation %}
assistant 모범 답안
{% endgeneration %}

generation 블록은 전체 토큰 중 assistant 정답 위치를 표시한다. system·tools·user는 모델이 참고할 입력이고, assistant 답안 토큰만 loss를 계산할 대상이다.

6. 학습 전에 실패하게 만드는 검증

Assistant mask smoke test

tool_rows = [row for row in records
             if row["messages"][-1].get("tool_calls")]
no_call_rows = [row for row in records
                if not row["messages"][-1].get("tool_calls")]

rendered = tokenizer.apply_chat_template(
    row["messages"],
    tools=row["tools"],
    tokenize=True,
    return_dict=True,
    return_assistant_tokens_mask=True,
)
mask = rendered.get("assistant_masks")

전체 800건을 도는 학습 루프가 아니라, tool-call 2건과 no-call 1건만 골라 템플릿이 assistant 정답을 제대로 표시하는지 확인한다. mask가 없거나 합계가 0이면 학습을 시작하지 않는다.

if len(mask) != len(rendered["input_ids"]):
    raise RuntimeError("assistant mask length mismatch")

토큰마다 마스크 값이 하나씩 있어야 한다. 0은 system·tools·user 입력, 1은 assistant 정답을 뜻한다. 이 검사는 정답의 의미가 아니라 “어느 토큰을 학습할지” 표시가 올바른지를 검사한다.

전체 token length 검사

lengths = [
    len(tokenizer.apply_chat_template(row["messages"], tools=row["tools"]))
    for row in train_records + valid_records
]
too_long = sum(length > config["max_length"] for length in lengths)

Train 800 + Validation 100, 총 900건을 검사한다. Python에서 True는 1이므로 초과 여부를 합하면 초과 예제 수가 된다. 이번 max_length=1152를 넘으면 assistant 답안이 잘릴 수 있어 오류로 중단한다.

7. Qwen 로딩과 LoRA 장착

Qwen3-1.7B BF16 로딩

model = AutoModelForCausalLM.from_pretrained(
    config["model_id"],
    revision=resolved_revision,
    dtype=torch.bfloat16,
    device_map={"": 0},
)
model.config.use_cache = False

AutoModelForCausalLM은 Qwen 설정을 읽어 decoder-only CausalLM 구조를 자동 선택한다. Causal은 앞의 토큰만 보고 다음 토큰을 예측한다는 뜻이다. dtype=torch.bfloat16은 이번 로딩 자료형을 BF16으로 정하는 것이며 4·8비트 양자화가 아니다. device_map={"": 0}은 모델 전체를 첫 번째 CUDA GPU에 올린다.

추론에서는 과거 Key·Value를 저장하는 KV cache가 유리하지만, 학습에서는 전체 토큰 역전파와 gradient checkpointing을 사용하므로 use_cache=False로 끈다. vLLM 서빙 시에는 추론용 KV cache를 서버가 다시 관리한다.

LoRA 설정은 “장착 규칙”이다

peft_config = LoraConfig(
    task_type="CAUSAL_LM",
    r=16,
    lora_alpha=32,
    lora_dropout=0.05,
    target_modules="all-linear",
    bias="none",
)

LoraConfig를 만드는 순간 학습이 시작되는 것은 아니다. 어떤 Linear에 어느 크기의 adapter를 붙일지 적는 설정표이며, 실제 장착은 뒤의 SFTTrainer 생성 때 PEFT가 수행한다. 원본 Qwen 가중치는 고정하고 A·B adapter만 업데이트한다.

LoRA를 행렬로 보기

입력 x [1, 2048]

원본 경로: x × W[2048,2048] → [1,2048]
LoRA 경로: x × A[2048,16] → [1,16]
           [1,16] × B[16,2048] → [1,2048]

최종 출력 = 원본 출력 + (alpha / r) × LoRA 보정 출력

같은 입력이 원본과 LoRA 경로로 병렬 통과하고 두 출력이 더해진다. r=16은 16비트가 아니라 저랭크 중간 차원이다. alpha/r = 32/16 = 2이므로 개념적으로 Wx + 2 × B(Ax)가 된다.

구분설명용 행렬PyTorch Linear 저장 모양
A[2048, 16]lora_A.weight [16, 2048]
B[16, 2048]lora_B.weight [2048, 16]

PyTorch가 [out_features, in_features]로 저장하기 때문에 설명용 곱셈 표기와 shape가 전치되어 보일 수 있다. 이는 다른 가중치가 아니라 저장 방향의 차이다.

dropout·target modules·bias

lora_dropout=0.05학습 중 LoRA 경로의 일부 입력을 무작위로 끄는 정규화다. 추론 시에는 dropout을 적용하지 않는다.
target_modules="all-linear"특정 q_proj 하나만이 아니라 모델의 Linear 계층 전체에 LoRA를 붙인다. 그래서 trainable parameter가 늘지만 도구 호출 행동을 여러 projection에서 보정할 수 있다.
bias="none"기존 Linear의 bias는 학습하지 않는다. 이번 실험의 추가 학습 대상은 LoRA A/B로 제한한다.

이 설정들은 “정답률을 보장하는 마법값”이 아니다. r=16, alpha=32, dropout 0.05와 all-linear는 이 데이터 크기와 GPU에서 시작한 실험 설정이며, 다른 rank·target 조합과 비교해 최적이라고 증명한 값은 아니다.

왜 trainable parameter가 작은가

새 2048×2048 보정 행렬 직접 학습: 4,194,304개
LoRA A: 2048×16 = 32,768개
LoRA B: 16×2048 = 32,768개
LoRA 합계:          65,536개

큰 원본 W 계산을 없애는 것이 아니라, 학습할 보정 파라미터와 gradient·optimizer state를 저랭크 A/B로 줄이는 방법이다. 이번 실행은 대상 Linear 전체에 adapter를 붙여 17,432,576개, 전체의 1.003%만 trainable이었다.

8. 학습 수치가 코드에서 의미하는 것

설정값의미
num_train_epochs1800개 Train을 한 번 순회
per_device_train_batch_size1한 번에 GPU에 넣는 예제 수
gradient_accumulation_steps1616개 예제의 gradient를 모은 뒤 한 번 optimizer update
learning_rate2e-4LoRA A/B가 이동하는 기본 보폭
warmup_ratio0.05초반 약 5% step 동안 learning rate를 서서히 증가
lr_scheduler_typecosine초기 peak 이후 learning rate를 점차 감소
max_grad_norm0.3gradient가 너무 크면 방향을 유지하며 크기 제한
max_length1152chat template 적용 후 허용할 최대 token 수

현재 설정에서 약 800/16 = 50회의 optimizer update가 발생한다. learning rate는 원본 출력과 LoRA 출력의 혼합 비율이 아니라, 학습 중 A/B 가중치를 움직이는 폭이다. 학습 종료 후 추론에서는 learning rate를 사용하지 않는다.

Loss·gradient·optimizer가 하는 일

정답 토큰의 모델 확률 p 계산
→ loss = -log(p)
→ backward()로 A/B의 gradient 계산
→ 16개 예제의 gradient 누적
→ AdamW가 learning rate를 적용해 A/B 업데이트

정답 토큰의 확률이 높으면 -log(p)가 작고, 확률이 낮으면 loss가 커진다. gradient는 현재 위치에서 loss를 줄이는 방향을 알려줄 뿐 최적 위치를 직접 알려주지 않는다. 따라서 작은 learning rate로 이동하고 다시 forward·loss·backward를 반복한다.

optim="adamw_torch"는 단순 SGD가 아니라 이전 gradient의 평균과 크기를 참고해 update를 만드는 AdamW를 사용한다. weight_decay=0.0으로 별도의 0 방향 규제는 사용하지 않고, max_grad_norm=0.3으로 지나치게 큰 gradient의 전체 크기만 제한한다.

메모리와 정밀도 옵션

assistant_only_loss=True
gradient_checkpointing=True
gradient_checkpointing_kwargs={"use_reentrant": False}
packing=False
bf16=True
fp16=False

assistant-only loss는 입력 전체를 보되 assistant 정답만 loss를 계산한다. Gradient checkpointing은 중간 activation을 덜 저장하고 backward에서 재계산해 GPU 메모리를 줄인다. packing=False는 여러 예제를 한 덩어리로 이어 붙이지 않고 경계를 유지한다. BF16은 모델·학습 자료형이고, TF32은 Ampere GPU의 일부 FP32 행렬 연산을 빠르게 허용하는 옵션이지 모델 가중치를 TF32로 저장한다는 뜻이 아니다.

def validate_record(record: dict[str, Any], path: Path, line_number: int) -> None:
    messages = record.get("messages")
    tools = record.get("tools")
    location = f"{path}:{line_number}"
    if not isinstance(messages, list) or len(messages) < 2:
        raise ValueError(f"{location}: messages must contain user and assistant turns")
    if not isinstance(tools, list) or not tools:
        raise ValueError(f"{location}: tools must be a non-empty list")
    if messages[-1].get("role") != "assistant":
        raise ValueError(f"{location}: final message must have assistant role")
    assistant = messages[-1]
    if not assistant.get("tool_calls") and not assistant.get("content"):
        raise ValueError(f"{location}: assistant needs a tool call or no-call content")
    for call in assistant.get("tool_calls", []):
        function = call.get("function", {})
        if not function.get("name"):
            raise ValueError(f"{location}: tool call is missing function.name")
        arguments = function.get("arguments")
        if not isinstance(arguments, (dict, str)):
            raise ValueError(f"{location}: function.arguments must be an object or JSON string")
        if isinstance(arguments, str):
            json.loads(arguments)


def load_jsonl(path: Path) -> list[dict[str, Any]]:
    records: list[dict[str, Any]] = []
    with path.open(encoding="utf-8") as handle:
        for line_number, line in enumerate(handle, 1):
            if not line.strip():
                raise ValueError(f"{path}:{line_number}: blank line")
            try:
                record = json.loads(line)
            except json.JSONDecodeError as exc:
                raise ValueError(f"{path}:{line_number}: invalid JSON: {exc}") from exc
            validate_record(record, path, line_number)
            records.append(record)
    if not records:
        raise ValueError(f"empty dataset: {path}")
    return records


def file_sha256(path: Path) -> str:
    digest = hashlib.sha256()
    with path.open("rb") as handle:
        for chunk in iter(lambda: handle.read(1024 * 1024), b""):
            digest.update(chunk)
    return digest.hexdigest()

def validate_assistant_masks(tokenizer, records: list[dict[str, Any]]) -> None:
    # 각 데이터의 마지막 메시지는 assistant 모범 답안이다. 그 답안에 tool_calls가
    # 있으면 도구 호출 예제, 없으면 도구를 호출하지 않는 no-call 예제로 분류한다.
    tool_rows = [row for row in records if row["messages"][-1].get("tool_calls")]
    no_call_rows = [row for row in records if not row["messages"][-1].get("tool_calls")]
    # 두 종류의 대표 예제를 검사할 수 없으면 학습을 시작하지 않고 중단한다.
    if len(tool_rows) < 2 or not no_call_rows:
        raise ValueError("mask validation requires at least two tool-call and one no-call examples")
    # 800개 전체를 검사하는 학습 루프가 아니다. 도구 호출 2건과 no-call 1건을
    # 골라 채팅 템플릿의 assistant 마스킹 기능을 빠르게 점검하는 스모크 테스트다.
    for category, row in (
        ("tool", tool_rows[0]),
        ("tool", tool_rows[1]),
        ("no_call", no_call_rows[0]),
    ):
        # 한 row에는 messages(질문과 모범 답안)와 tools(전체 도구 후보)가 있다.
        # 템플릿으로 Qwen 대화 형식을 만들고 토큰 ID와 assistant 위치 마스크를 받는다.
        rendered = tokenizer.apply_chat_template(
            row["messages"],
            tools=row["tools"],
            # 템플릿 결과 문자열을 바로 정수 토큰 ID로 변환한다.
            tokenize=True,
            # ID 목록만 받지 않고 input_ids와 각종 마스크를 딕셔너리로 받는다.
            return_dict=True,
            # 전체 토큰 중 assistant 모범 답안 위치를 1로 표시한 배열도 요청한다.
            return_assistant_tokens_mask=True,
        )
        mask = rendered.get("assistant_masks")
        # 마스크가 없거나 모두 0이면 assistant 정답 토큰이 학습 대상으로 표시되지 않았다.
        if not mask or sum(mask) == 0:
            raise RuntimeError(f"assistant mask is empty for {category} example")
        # 모든 입력 토큰에는 대응하는 마스크 값이 정확히 하나씩 있어야 한다.
        if len(mask) != len(rendered["input_ids"]):
            raise RuntimeError(f"assistant mask length mismatch for {category} example")
        # 이진 마스크의 길이는 전체 토큰 수, 합계는 assistant 정답 토큰 수다.
        LOGGER.info(
            "assistant_mask category=%s total_tokens=%d assistant_tokens=%d",
            category,
            len(mask),
            sum(mask),
        )

def resolve_resume(output_dir: Path, requested: str) -> str | None:
    from transformers.trainer_utils import get_last_checkpoint

    normalized = requested.strip().lower()
    if normalized in {"", "none", "false", "0"}:
        return None
    if normalized == "auto":
        checkpoint = get_last_checkpoint(str(output_dir)) if output_dir.exists() else None
        LOGGER.info("automatic resume checkpoint=%s", checkpoint)
        return checkpoint
    checkpoint = resolve_path(requested)
    if not checkpoint.is_dir():
        raise ValueError(f"resume checkpoint does not exist: {checkpoint}")
    return str(checkpoint)

    class GpuMemoryCallback(TrainerCallback):
        def on_log(self, args, state, control, logs=None, **kwargs):
            if logs is not None and torch.cuda.is_available():
                gib = 1024**3
                free_bytes, _ = torch.cuda.mem_get_info()
                logs["gpu_allocated_gib"] = round(torch.cuda.memory_allocated() / gib, 3)
                logs["gpu_reserved_gib"] = round(torch.cuda.memory_reserved() / gib, 3)
                logs["gpu_peak_allocated_gib"] = round(torch.cuda.max_memory_allocated() / gib, 3)
                logs["gpu_free_gib"] = round(free_bytes / gib, 3)
