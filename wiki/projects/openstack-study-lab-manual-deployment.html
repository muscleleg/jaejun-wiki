1. 무엇을 배포하는가

왜 먼저 구조를 알아야 하는가? OpenStack은 하나의 프로그램이 아니다. 인증, 이미지, 계산, 네트워크, 스토리지 서비스가 API로 협업하는 시스템이다. 어떤 서비스가 어떤 책임을 갖는지 알아야 오류가 났을 때 무작정 재설치하지 않고 문제 영역을 좁힐 수 있다.

Kolla-Ansible은 OpenStack 서비스를 Docker 컨테이너로 배포하고 Ansible로 설정을 반복 적용한다. All-in-One 인벤토리는 한 호스트가 Controller, Network, Compute, Storage 역할을 모두 맡게 한다.

Ubuntu 물리 호스트
├─ Kolla-Ansible: 배포 자동화
├─ Docker: OpenStack 서비스 실행
├─ Keystone / Glance / Nova / Neutron / Horizon
├─ Open vSwitch: br-int, br-tun, br-ex
├─ Cinder LVM: /var/lib/cinder_data.img → loop → cinder-volumes
└─ Wi-Fi 외부 경로
   VM → Neutron Router → br-ex → veth-ex ↔ veth-host
      → Ubuntu nftables NAT → wlo1 → 공유기 → 인터넷

Wi-Fi NIC를 br-ex에 직접 넣지 않는다. OpenStack 외부망은 사설 provider 대역 172.24.4.0/24을 사용하고 Ubuntu가 이를 Wi-Fi로 masquerade한다.

1.1 Horizon에서 VM 생성 버튼을 누르면

flowchart LR U[사용자 / Horizon] --> K[Keystone<br/>인증·토큰] U --> N[Nova API<br/>VM 생성 요청] N --> S[Nova Scheduler<br/>실행 호스트 선택] N --> G[Glance<br/>부팅 이미지 제공] N --> Q[Neutron<br/>포트·IP·보안그룹] N --> C[Cinder<br/>영구 볼륨] S --> L[Nova Compute + libvirt<br/>KVM VM 실행] Q --> O[Open vSwitch<br/>가상 L2 연결] G --> L C --> L O --> L
  • Keystone은 누구인지 확인하고 다른 API가 신뢰할 토큰을 발급한다.
  • Glance는 VM의 원본 디스크 이미지를 저장한다.
  • Nova는 VM의 생명주기와 스케줄링을 담당하지만 네트워크나 영구 볼륨을 직접 만들지는 않는다.
  • Neutron은 논리 네트워크·포트·IP·라우터·보안그룹을 만들고 OVS가 실제 프레임을 전달하게 한다.
  • Cinder는 VM과 독립적으로 유지되는 블록 볼륨을 만든다.

1.2 제어 경로와 데이터 경로는 다르다

Horizon이나 CLI가 API에 “VM을 만들어라”라고 보내는 것은 제어 경로다. 생성된 VM의 실제 패킷과 디스크 I/O가 흐르는 것은 데이터 경로다. API가 정상이어도 OVS나 NAT가 잘못되면 VM 인터넷은 실패할 수 있고, 반대로 실행 중 VM 통신이 되더라도 Nova API가 죽으면 새 VM을 만들 수 없다.

1.3 현재 랩의 네트워크 데이터 경로

flowchart LR VM[VM<br/>10.0.0.x] --> TN[private VXLAN] TN --> NR[Neutron Router<br/>SNAT/Floating IP] NR --> BX[OVS br-ex] BX --> VE[veth-ex] VE <--> VH[veth-host<br/>172.24.4.1] VH --> NAT[Ubuntu nftables<br/>masquerade] NAT --> WL[wlo1<br/>호스트 Wi-Fi IP/MAC] WL --> AP[Wi-Fi 공유기] AP --> NET[인터넷]

첫 번째 NAT는 Neutron Router가 tenant IP를 provider IP로 바꾸는 과정이고, 두 번째 NAT는 Ubuntu가 provider IP를 호스트 Wi-Fi IP로 바꾸는 과정이다. 두 NAT 모두 conntrack에 변환 상태를 기록하므로 응답을 원래 VM까지 역변환해 돌려보낼 수 있다.

1.4 현재 랩의 스토리지 데이터 경로

flowchart LR API[Cinder API<br/>1GB 볼륨 요청] --> SCH[Cinder Scheduler] SCH --> VOL[Cinder Volume<br/>LVM driver] VOL --> LV[LVM thin LV] LV --> VG[VG cinder-volumes] VG --> LOOP[loop device] LOOP --> IMG["/var/lib/cinder_data.img"] IMG --> EXT4[Ubuntu root ext4] LV --> ISCSI[iSCSI target] ISCSI --> VM[VM /dev/vdb]

파일을 바로 VM 디스크로 쓰는 것이 아니다. 파일을 loop 장치로 보이게 하고 그 위에 LVM 저장 풀을 만든 뒤, Cinder가 논리 볼륨을 생성해 iSCSI로 VM에 제공한다. 이 계층을 알면 loop가 사라졌을 때 Cinder가 왜 실패하는지 이해할 수 있다.

2. 환경값과 안전 규칙

왜 값을 먼저 확정하는가? Kolla는 NIC 이름과 VIP를 그대로 호스트 네트워크에 적용하고, LVM은 지정한 블록 장치에 메타데이터를 쓴다. 잘못된 값은 단순 설치 실패가 아니라 관리 연결 단절이나 데이터 손실을 만들 수 있다. 따라서 변경 전에 주소·NIC·디스크를 사실로 확정한다.
항목현재 랩 값다른 PC에서 할 일
관리 NICwlo1ip -brief address로 실제 이름 확인
관리망/VIP192.168.50.0/24, 192.168.50.254DHCP 풀 밖의 미사용 주소를 예약
외부 provider망172.24.4.0/24호스트·관리 LAN과 겹치지 않는 대역 선택
provider 게이트웨이172.24.4.1veth-host에 설정
Windows 디스크/dev/nvme0n1절대 쓰기 작업 금지
Ubuntu 디스크/dev/nvme1n1루트 여유 공간 확인

주소 역할 상세: DHCP 풀에서 제외한 192.168.50.254가 Kolla VIP로 쓰이는 과정과 호스트 Wi-Fi IP 192.168.50.217, provider gateway 172.24.4.1의 차이를 확인한다.

절대 금지: 장치 이름을 추측해 pvcreate, mkfs, fdisk를 실행하지 않는다. 이 구성에서 pvcreate 대상은 backing file을 확인한 loop 장치뿐이다.

3. 호스트 준비

왜 호스트를 먼저 준비하는가? 컨테이너 안의 Nova가 KVM을 사용하고, Ansible이 호스트 패키지와 Docker를 제어해야 한다. CPU 가상화, 메모리, 디스크, Python 의존성이 부족하면 OpenStack 서비스 설정이 맞아도 VM을 실행할 수 없다.

3.1 하드웨어와 주소 확인

이 명령들이 답하는 질문: “이 CPU가 KVM VM을 실행할 수 있는가?”, “메모리와 루트 디스크가 충분한가?”, “어느 NIC가 관리망인가?”, “어느 디스크가 Windows인가?”를 배포 전에 증명한다. 조회만 하므로 시스템은 바뀌지 않는다.

lscpu | grep -E 'Model name|Virtualization'
grep -Eoc '(vmx|svm)' /proc/cpuinfo
test -c /dev/kvm && ls -l /dev/kvm
free -h
lsblk -e7 -o NAME,PATH,TYPE,SIZE,FSTYPE,MOUNTPOINTS,MODEL
df -hT /
ip -brief address
ip route
nmcli device status

3.1.1 lscpu | grep -E 'Model name|Virtualization'

lscpu는 커널이 인식한 CPU 구조, 코어·스레드 수, 가상화 기능 등을 사람이 읽기 쉬운 형태로 출력한다. 뒤의 |는 앞 명령의 출력을 다음 명령의 입력으로 넘기는 파이프다. grep은 필요한 줄만 고르며, -E는 |를 “또는”으로 사용하는 확장 정규식을 활성화한다.

Model name:      AMD Ryzen 9 5900X 12-Core Processor
Virtualization: AMD-V
확인할 것: Virtualization 행이 존재하고 AMD에서는 AMD-V, Intel에서는 VT-x 계열 값이 보이는지 확인한다. CPU 모델명은 용량 판단에 참고하지만 이 단계의 필수 통과값은 가상화 기능이다.

여기서 확인하려는 것은 CPU 이름 자체보다 Virtualization 항목이다. AMD는 AMD-V/SVM, Intel은 VT-x/VMX가 보여야 Nova가 QEMU 소프트웨어 에뮬레이션이 아니라 KVM 하드웨어 가상화를 사용할 수 있다. 항목이 없으면 BIOS/UEFI의 SVM 또는 Intel Virtualization Technology 설정부터 확인한다.

3.1.2 grep -Eoc '(vmx|svm)' /proc/cpuinfo

/proc/cpuinfo는 디스크 파일이 아니라 커널이 현재 CPU 정보를 노출하는 가상 파일이다. CPU 논리 스레드마다 한 묶음의 정보가 있고, flags에 Intel은 vmx, AMD는 svm 기능을 표시한다.

  • -E: vmx|svm의 OR 표현을 사용한다.
  • -o: 일치한 부분만 결과로 취급한다.
  • -c: 일치 문자열을 출력하지 않고 개수만 센다.

현재 랩 호스트의 샘플 출력:

24
확인할 것: 결과가 0보다 큰지 확인한다. 보통 가상화 플래그가 보이는 논리 CPU 수만큼 나오므로 PC마다 숫자가 다르다. 24라는 숫자 자체가 요구사항은 아니며 0이면 가상화 플래그가 커널에 노출되지 않은 것이다.

결과가 0보다 크면 커널이 하드웨어 가상화 플래그를 보고 있다는 뜻이다. 현재 Ryzen 5900X는 여러 논리 CPU 각각에 svm이 있으므로 큰 양수가 나온다. 이것은 “지원 여부” 검사이고, 실제 KVM 장치를 사용할 수 있는지는 다음 명령으로 별도 확인한다.

3.1.3 test -c /dev/kvm && ls -l /dev/kvm

test -c는 경로가 문자 장치(character device)인지 검사한다. /dev/kvm은 사용자 공간의 QEMU가 커널 KVM 모듈에 가상 CPU 실행을 요청하는 장치 인터페이스다. 일반 파일이 아니다.

&&는 왼쪽 명령이 성공할 때만 오른쪽을 실행한다. 따라서 KVM 장치가 있을 때만 ls -l로 종류, 소유자, 그룹, 권한을 보여준다.

crw-rw---- 1 root kvm ... /dev/kvm
확인할 것: 출력이 실제로 나타나고 첫 글자가 문자 장치를 뜻하는 c인지 확인한다. 경로는 /dev/kvm, 일반적인 소유 그룹은 kvm이다. 아무 출력도 없고 종료 코드가 실패라면 Nova를 KVM 모드로 배포하기 전에 원인을 해결한다.

첫 글자 c는 문자 장치, 일반적으로 그룹 kvm은 사용 권한의 주체다. 파일이 없다면 BIOS 기능, kvm_amd/kvm_intel 모듈, 가상 머신 안이라면 nested virtualization 노출 여부를 확인한다.

3.1.4 free -h

free는 물리 메모리와 swap 사용량을 보여주고 -h는 바이트 대신 GiB/MiB처럼 읽기 쉬운 단위를 사용한다.

현재 랩 호스트의 샘플 출력:

               total        used        free      shared  buff/cache   available
Mem:            46Gi       3.0Gi        32Gi       200Mi        11Gi        41Gi
Swap:          8.0Gi          0B       8.0Gi

사용량은 실행 시점에 따라 바뀌므로 위 숫자는 구조를 읽기 위한 예시다.

열의미
total커널이 사용할 수 있는 전체 RAM
used현재 실제 사용량
buff/cache성능을 위해 캐시 중이며 필요하면 회수 가능한 메모리
available새 프로세스가 swap 없이 현실적으로 사용할 수 있는 추정량
확인할 것: Mem: 행의 total과 특히 available을 본다. 이 랩에서는 약 46GiB total과 배포 전 약 41GiB available이 확인돼 싱글노드 서비스와 소형 VM 실습이 가능하다고 판단했다. free 열만 보고 부족하다고 판단하지 않는다.

Linux에서는 free 열이 작다고 곧바로 메모리 부족이 아니다. 판단에는 available을 본다. 이 랩은 호스트가 약 46GiB를 인식하며 OpenStack 컨테이너와 이후 실습 VM이 나누어 쓰므로, Flavor 합계가 호스트 여유를 과도하게 넘지 않도록 해야 한다.

3.1.5 lsblk -e7 -o NAME,PATH,TYPE,SIZE,FSTYPE,MOUNTPOINTS,MODEL

lsblk는 block device의 부모·자식 관계를 트리로 보여준다. 디스크, 파티션, loop 장치, LVM 장치의 관계를 확인하는 가장 중요한 안전 명령이다.

  • -e7: major number 7인 loop 장치를 목록에서 제외해 실제 SSD 식별을 쉽게 한다. loop가 필요할 때는 이 옵션을 빼고 다시 본다.
  • -o: 표시할 열을 명시한다.
  • TYPE: disk, part, lvm 등 장치 종류다.
  • FSTYPE: ext4, vfat, ntfs, LVM2_member처럼 장치에 기록된 형식이다.
  • MOUNTPOINTS: 현재 어느 디렉터리에서 사용되는지 보여준다.
  • MODEL: 물리 디스크 모델명으로 비슷한 용량의 장치를 구분한다.

현재 랩 호스트의 핵심만 줄인 샘플 출력:

NAME        PATH              TYPE   SIZE FSTYPE MOUNTPOINTS MODEL
nvme0n1     /dev/nvme0n1     disk 931.5G                   Lexar SSD
├─nvme0n1p1 /dev/nvme0n1p1   part   100M vfat
├─nvme0n1p3 /dev/nvme0n1p3   part 465.1G ntfs
└─nvme0n1p5 /dev/nvme0n1p5   part 465.8G ntfs
nvme1n1     /dev/nvme1n1     disk 476.9G                   Lexar NM620
├─nvme1n1p1 /dev/nvme1n1p1   part     1G vfat   /boot/efi
└─nvme1n1p2 /dev/nvme1n1p2   part 475.9G ext4   /
확인할 것: 먼저 MOUNTPOINTS=/인 Ubuntu 루트 파티션을 찾고 그 부모 디스크를 확인한다. 그다음 NTFS와 Windows EFI/MS 파티션이 있는 디스크를 별도 보호 대상으로 기록한다. 현재는 nvme1n1p2 → /가 Ubuntu이고 nvme0n1 전체가 Windows 보호 대상이다.

현재 랩 호스트에서는 /dev/nvme0n1이 Windows NTFS 디스크이고 /dev/nvme1n1p2가 Ubuntu 루트 /다. 이 확인 때문에 Cinder PV를 실제 NVMe가 아니라 명시적으로 만든 loop 장치에만 생성한다.

3.1.5.1 loop 장치란 무엇인가?

별도 학습 문서에서 보기: Linux 저장장치 기초 — 블록 장치, 파일시스템, loop, LVM, Cinder 전체 관계

loop 장치는 일반 파일을 디스크처럼 보이게 만드는 Linux의 가상 블록 장치다. 일반 파일은 경로와 바이트의 연속으로 다루지만, LVM과 파일시스템 도구는 섹터·블록 단위로 접근할 수 있는 block device를 기대한다. loop 드라이버가 두 인터페이스 사이를 연결한다.

일반 파일
/var/lib/cinder_data.img
        │
        │ losetup: 파일을 블록 장치에 연결
        ▼
가상 블록 장치
/dev/loop13
        │
        ├─ pvcreate 사용 가능
        ├─ LVM VG/LV 생성 가능
        └─ mkfs 같은 블록 장치 도구 사용 가능

cinder_data.img가 실제 데이터가 저장되는 backing file이고, /dev/loop13은 그 파일을 디스크 방식으로 읽고 쓰기 위한 장치 인터페이스다. LVM이 loop 장치의 특정 블록에 쓰면 Linux loop 드라이버가 이를 backing file의 대응 위치에 기록한다.

LVM이 /dev/loop13의 블록에 쓰기
              ↓
Linux loop 드라이버가 파일 위치로 변환
              ↓
/var/lib/cinder_data.img에 기록
              ↓
파일을 보관하는 Ubuntu ext4에 기록
              ↓
결국 Ubuntu NVMe SSD에 실제 저장
RAM 디스크와의 차이: loop 장치는 데이터를 메모리에만 보관하는 RAM disk가 아니다. 실제 데이터는 연결된 backing file에 남는다. 이 랩에서는 backing file이 Ubuntu SSD의 ext4 파일시스템 위에 있으므로 재부팅 후에도 파일 내용은 유지된다.

현재 Cinder 저장 경로 전체는 다음과 같다.

Ubuntu NVMe SSD (/dev/nvme1n1)
└─ Ubuntu ext4 루트 파일시스템
   └─ /var/lib/cinder_data.img       100GB backing file
      └─ /dev/loopN                  파일을 표현하는 가상 디스크
         └─ LVM PV
            └─ VG cinder-volumes
               └─ Cinder가 만든 thin LV
                  └─ iSCSI를 통해 VM의 /dev/vdb로 연결
왜 이름이 loop13이었는가?

13은 Cinder 전용으로 정해진 번호가 아니다. 연결 당시 loop0부터 다른 용도로 사용 중이었고, 사용 가능한 첫 장치가 loop13이어서 선택된 것이다. 연결 상태나 부팅 순서가 바뀌면 다음 재부팅에서는 다른 번호가 될 수 있다.

그래서 자동화에서 /dev/loop13을 고정해서 쓰지 않고 다음처럼 빈 loop 장치를 찾는다.

sudo losetup --find --show /var/lib/cinder_data.img
  • --find: 현재 사용하지 않는 loop 장치를 자동으로 찾는다.
  • --show: 연결 후 선택된 /dev/loopN 경로를 출력한다.
그렇다면 lsblk -e7에서 왜 숨겼는가?

Linux 장치에는 종류를 나타내는 major number가 있고 loop 장치 종류의 번호가 7이다. lsblk -e7은 major number 7인 모든 loop 장치를 출력에서만 제외한다.

lsblk                 lsblk -e7
├─ loop0              ├─ nvme0n1
├─ loop1              └─ nvme1n1
├─ loop13
├─ nvme0n1
└─ nvme1n1

이 옵션은 loop 장치를 삭제하거나 연결 해제하지 않는다. 설치 전 실제 Windows SSD와 Ubuntu SSD를 보기 쉽게 하려고 잠시 숨긴 것이다. Cinder loop 연결을 확인할 때는 -e7을 빼거나 다음 명령으로 backing file에 연결된 장치만 조회한다.

sudo losetup -j /var/lib/cinder_data.img
핵심: cinder_data.img는 실제 저장 파일이고, /dev/loopN은 그 파일을 LVM이 사용할 수 있는 디스크 형태로 보여주는 입구다. -e7은 이 가상 디스크들을 목록에서 잠시 숨길 뿐이다.

3.1.6 df -hT /

df는 마운트된 파일시스템의 용량을 확인한다. -h는 읽기 쉬운 단위, -T는 파일시스템 종류를 추가하며 마지막 /는 루트 파일시스템만 조회하라는 뜻이다.

배포 전 샘플 출력:

Filesystem        Type  Size  Used Avail Use% Mounted on
/dev/nvme1n1p2   ext4  468G   18G  427G   5% /
확인할 것: Filesystem이 앞에서 찾은 Ubuntu 파티션과 같은지, Mounted on이 /인지, Avail이 계획한 Cinder 100GB와 Docker·Glance·Nova 공간을 제외하고도 충분한지 확인한다. 이 랩은 약 427GB가 남아 있어 진행했다.

lsblk의 SIZE는 장치·파티션 크기이고, df의 Avail은 파일시스템에서 실제로 새 파일이 쓸 수 있는 여유 공간이다. Cinder 이미지 100GB, Glance 이미지, Nova 인스턴스 디스크, Docker image가 모두 Ubuntu 루트를 사용하므로 Avail이 더 중요한 배포 판단값이다.

3.1.7 ip -brief address

ip는 Linux 커널 네트워크 상태를 조회·변경하는 도구다. address는 인터페이스 주소를, -brief는 이름·상태·주소를 한 줄씩 간결하게 보여준다.

lo       UNKNOWN  127.0.0.1/8
wlo1     UP       192.168.50.217/24
enp42s0  DOWN
확인할 것: 인터넷과 관리망에 실제로 연결된 인터페이스가 UP이고 IPv4 주소/prefix를 갖는지 확인한다. 현재 선택은 wlo1 = 192.168.50.217/24다. lo는 자기 자신과 통신하는 loopback이며 관리 NIC로 선택하지 않는다.

여기서 Kolla의 network_interface로 사용할 실제 관리 NIC와 그 IP prefix를 찾는다. 현재는 wlo1이 UP이고 관리망 주소를 가지며, enp42s0은 내부 스위치가 아니라 랜선이 연결되지 않은 물리 Ethernet NIC다.

3.1.8 ip route

IP 주소가 “내 인터페이스가 누구인가”를 말한다면 routing table은 “목적지별로 어느 다음 홉과 인터페이스를 사용할 것인가”를 말한다.

default via 192.168.50.1 dev wlo1
192.168.50.0/24 dev wlo1 proto kernel scope link src 192.168.50.217
확인할 것: default 행에서 다음 홉(via 192.168.50.1)과 출력 장치(dev wlo1)를 확인한다. 연결된 관리망 경로에서는 src가 앞에서 본 호스트 IP와 일치해야 한다. 이 정보가 Ubuntu NAT의 외부 출력 인터페이스를 결정한다.

default via는 더 구체적인 경로가 없는 인터넷 목적지를 공유기 192.168.50.1로 보낸다는 뜻이다. NAT 규칙의 출력 인터페이스로 wlo1을 선택하는 근거가 된다. 관리 NIC에 주소가 있어도 default route가 없으면 호스트와 VM은 인터넷으로 나갈 수 없다.

3.1.9 nmcli device status

nmcli는 NetworkManager의 CLI다. ip가 현재 커널 상태를 보여주는 데 비해, NetworkManager는 재부팅 후 다시 적용할 connection profile을 관리한다.

현재 랩 호스트의 샘플 출력:

DEVICE   TYPE      STATE                   CONNECTION
wlo1     wifi      connected               Wi-Fi-프로필명
enp42s0  ethernet  disconnected            --
lo       loopback  connected (externally)  lo
확인할 것: 관리 NIC wlo1의 TYPE이 wifi, STATE가 connected이고 CONNECTION 열에 적용 중인 프로필이 있는지 확인한다. 이는 NetworkManager가 현재 연결과 이후 만들 veth 영구 프로필을 관리할 수 있다는 근거다. 프로필 이름은 PC마다 다르다.

device status에서는 장치 이름, Ethernet/Wi-Fi/veth 같은 TYPE, connected/disconnected 상태, 적용 중인 프로필을 확인한다. 이후 veth pair를 단순 ip link add가 아니라 nmcli connection add로 만드는 이유는 재부팅 후에도 자동으로 복원하기 위해서다.

3.1의 전체 논리: lscpu와 /proc/cpuinfo가 CPU 기능을, /dev/kvm이 실제 가속 인터페이스를, free와 df가 수용 능력을, lsblk가 디스크 안전 경계를, ip가 현재 네트워크를, nmcli가 재부팅 후 지속될 네트워크 관리를 증명한다.

통과 기준: AMD-V/Intel VT-x와 /dev/kvm이 있고, 관리 NIC가 UP이며, Windows와 Ubuntu 디스크를 명확히 구분할 수 있어야 한다.

3.2 기본 패키지와 Python 가상환경

왜 venv인가? Kolla-Ansible, Ansible, Docker SDK와 OpenStack CLI는 Python 패키지 버전에 민감하다. 전용 venv는 Ubuntu 시스템 Python을 오염시키지 않고, 같은 도구 집합을 다음 실행에서도 재사용하게 한다. LVM·nftables·NetworkManager는 컨테이너 밖 호스트 자원을 준비하므로 OS 패키지로 설치한다.

sudo apt-get update
sudo apt-get install -y git python3-dev libffi-dev gcc libssl-dev python3-venv python3-pip lvm2 nftables network-manager wget
mkdir -p "$HOME/.venvs" "$HOME/openstack-deploy/logs"
python3 -m venv "$HOME/.venvs/kolla-2026.1"
"$HOME/.venvs/kolla-2026.1/bin/python" -m pip install --upgrade pip
"$HOME/.venvs/kolla-2026.1/bin/python" -m pip install 'git+https://opendev.org/openstack/kolla-ansible@stable/2026.1'
"$HOME/.venvs/kolla-2026.1/bin/pip" install docker dbus-python python-openstackclient
"$HOME/.venvs/kolla-2026.1/bin/kolla-ansible" --version

venv는 시스템 Python 패키지와 Kolla 의존성을 분리한다. 이후 문서에서 $VENV는 이 경로를 뜻한다.

export VENV="$HOME/.venvs/kolla-2026.1"
export INVENTORY="$HOME/openstack-deploy/all-in-one"
export PATH="$VENV/bin:$PATH"

4. Wi-Fi 외부망 준비

왜 별도 외부망을 만드는가? 일반 Wi-Fi station은 VM과 Neutron Router의 여러 MAC을 AP까지 투명하게 전달하는 브리지로 쓰기 어렵다. 그래서 OpenStack에는 Ethernet 형태의 사설 provider망을 제공하고, Ubuntu가 그 망의 라우터/NAT가 되어 자신의 wlo1 연결로 대신 송신한다.

개념 상세: Provider 네트워크의 일반적 의미, 이번 Wi-Fi 랩에서 별도 사설망을 사용한 이유, 172.24.4.0/24와 172.24.4.1의 선택 기준 및 다른 가능한 주소 예를 별도 네트워크 기초 문서에서 확인한다.

별도 학습 문서: IP 없는 veth-ex, veth-host gateway, br-ex, routing과 NAT의 전체 패킷 흐름을 먼저 공부한다.

4.1 veth pair

무엇이 바뀌는가? 호스트 내부에 양끝이 연결된 가상 Ethernet 케이블이 생긴다. IP 없는 veth-ex는 Kolla가 br-ex에 꽂을 스위치 포트이고, veth-host는 Ubuntu 라우터의 L3 인터페이스다. 이 경계가 없으면 br-ex와 호스트 NAT 사이에 프레임을 전달할 길이 없다.

sudo nmcli connection add type veth ifname veth-ex con-name kolla-veth-ex veth.peer veth-host ipv4.method disabled ipv6.method disabled connection.autoconnect yes
sudo nmcli connection add type ethernet ifname veth-host con-name kolla-veth-host ipv4.method manual ipv4.addresses 172.24.4.1/24 ipv4.never-default yes ipv6.method disabled connection.autoconnect yes
sudo nmcli connection up kolla-veth-ex
sudo nmcli connection up kolla-veth-host
ip -brief address show veth-ex
ip -brief address show veth-host

명령 상세 해설: NetworkManager와 nmcli의 관계, 장치와 연결 프로필의 차이, 모든 옵션의 의미와 예상 확인 결과를 별도 네트워크 기초 문서 11장에서 확인한다.

veth-ex는 IP 없이 UP이어야 한다. Kolla가 이를 br-ex의 L2 포트로 사용한다. 반대쪽 veth-host만 Ubuntu 라우터 주소 172.24.4.1/24를 갖는다.

4.2 IPv4 forwarding

왜 필요한가? Linux는 기본적으로 자신에게 온 패킷만 처리하고 한 인터페이스에서 다른 인터페이스로 라우팅하지 않는다. 이 값을 1로 해야 veth-host에서 받은 패킷을 wlo1으로 넘길 수 있다. 생략하면 NAT 규칙이 있어도 패킷이 중간에서 멈춘다.

printf 'net.ipv4.ip_forward = 1\n' | sudo tee /etc/sysctl.d/99-kolla-router.conf
sudo sysctl --system
sysctl net.ipv4.ip_forward

4.2.1 이 세 명령이 하는 일

첫 번째 명령은 재부팅 후에도 사용할 설정을 파일에 저장하고, 두 번째 명령은 저장된 설정을 현재 커널에 적용하며, 세 번째 명령은 실제 적용 결과를 확인한다.

설정 파일에 저장 → 현재 커널에 적용 → 적용 결과 확인

첫 번째 명령: 설정 파일에 기록

printf 'net.ipv4.ip_forward = 1\n' | sudo tee /etc/sysctl.d/99-kolla-router.conf
구성의미
printf뒤에 지정한 문자열을 출력한다.
net.ipv4.ip_forward = 1Linux 커널의 IPv4 forwarding 기능을 활성화할 설정값이다. 1은 활성화, 0은 비활성화다.
\nnewline을 뜻하며 문자열 마지막에 줄바꿈 하나를 출력한다. 긴 명령을 다음 줄까지 잇는 줄 끝의 \와는 용도가 다르다.
|파이프다. 왼쪽 printf의 출력을 오른쪽 tee의 입력으로 전달한다.
sudo일반 사용자가 쓸 수 없는 /etc 아래에 파일을 만들기 위해 관리자 권한을 사용한다.
tee입력받은 내용을 화면에 보여 주면서 지정한 파일에도 저장한다.
/etc/sysctl.d/99-kolla-router.conf재부팅 시 다시 읽을 커널 설정 파일이다.

첫 번째 명령을 실행하면 파일의 내용은 다음 한 줄이 된다.

net.ipv4.ip_forward = 1
이 단계의 범위: 현재 커널에 즉시 적용하는 단계가 아니라, 지속적으로 사용할 설정을 파일에 기록하는 단계다.

두 번째 명령: 현재 커널에 적용

sudo sysctl --system

sysctl은 실행 중인 Linux 커널의 설정값을 조회하거나 적용하는 도구다. --system은 /etc/sysctl.d/ 등의 시스템 설정 파일을 읽어 현재 커널에 적용한다. 따라서 방금 저장한 net.ipv4.ip_forward = 1도 이 시점에 실제로 활성화된다.

세 번째 명령: 적용 결과 확인

sysctl net.ipv4.ip_forward

현재 커널이 가진 net.ipv4.ip_forward 값을 조회한다. 정상적인 예상 결과는 다음과 같다.

net.ipv4.ip_forward = 1

이 결과는 Ubuntu가 자신이 최종 목적지가 아닌 IPv4 패킷을 다른 interface로 전달할 수 있는 상태라는 뜻이다. 어느 interface로 전달할지는 이 설정이 아니라 별도의 routing table이 결정한다.

세 명령 요약: printf | sudo tee는 영구 설정 파일을 만들고, sudo sysctl --system은 그 설정을 현재 커널에 적용하며, 마지막 sysctl은 값이 1인지 검증한다.

4.3 nftables NAT

왜 masquerade인가? 공유기는 172.24.4.0/24로 돌아가는 경로를 모르고 Wi-Fi는 VM 측 MAC을 직접 쓰지 않는다. masquerade는 외부로 나가는 출발지 IP를 wlo1의 현재 IP로 바꾸며 conntrack이 응답의 원래 목적지를 기억한다. systemd unit은 재부팅 뒤 이 규칙을 다시 만든다.

sudoedit /etc/kolla/kolla-lab-nat.nft로 파일을 열고 다음 내용을 저장한다.

table ip kolla_lab_nat {
  chain forward {
    type filter hook forward priority filter; policy accept;
    iifname "veth-host" oifname "wlo1" accept
    iifname "wlo1" oifname "veth-host" ct state established,related accept
  }
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    ip saddr 172.24.4.0/24 oifname "wlo1" masquerade
  }
}

sudoedit /etc/systemd/system/kolla-lab-nat.service로 unit을 만들고 다음 내용을 저장한다.

[Unit]
Description=NAT for the OpenStack external lab network over Wi-Fi
Wants=network-online.target
After=network-online.target NetworkManager.service
Before=kolla.target

[Service]
Type=oneshot
ExecStartPre=-/usr/sbin/nft delete table ip kolla_lab_nat
ExecStart=/usr/sbin/nft -f /etc/kolla/kolla-lab-nat.nft
ExecReload=/usr/sbin/nft -f /etc/kolla/kolla-lab-nat.nft
ExecStop=-/usr/sbin/nft delete table ip kolla_lab_nat
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
sudo nft -c -f /etc/kolla/kolla-lab-nat.nft
sudo systemctl daemon-reload
sudo systemctl enable --now kolla-lab-nat.service
sudo nft list table ip kolla_lab_nat

5. 파일 기반 Cinder LVM

선행 개념: PV·VG·thin pool·LV가 낯설다면 Linux 저장장치 기초 문서의 LVM 장부터 읽는다.

왜 Cinder에 별도 블록 계층이 필요한가? Cinder LVM driver는 파일이 아니라 PV/VG/LV를 다루는 블록 장치를 기대한다. 별도 SSD가 없으므로 Ubuntu 파일을 loop 장치로 변환해 학습용 블록 저장소를 만든다. 이 방식은 단일 장애점이므로 프로덕션 스토리지의 대체품은 아니다.

5.1 이미지, loop, PV, VG 생성

계층별 의미: fallocate는 저장공간을 예약하고, losetup은 파일에 블록 장치 인터페이스를 주며, pvcreate는 LVM 관리 대상으로 초기화하고, vgcreate는 Cinder가 볼륨을 잘라 쓸 저장 풀을 만든다. VG 이름은 Kolla 기본 LVM backend가 찾는 cinder-volumes여야 한다.

df -h /
test ! -e /var/lib/cinder_data.img
sudo fallocate -l 100G /var/lib/cinder_data.img
sudo chown root:root /var/lib/cinder_data.img
sudo chmod 0600 /var/lib/cinder_data.img
LOOP_DEVICE=$(sudo losetup --find --show /var/lib/cinder_data.img)
echo "$LOOP_DEVICE"
sudo losetup -j /var/lib/cinder_data.img
sudo wipefs -n "$LOOP_DEVICE"
sudo pvcreate "$LOOP_DEVICE"
sudo vgcreate cinder-volumes "$LOOP_DEVICE"
sudo vgs cinder-volumes
중지 지점: losetup -j가 정확히 /var/lib/cinder_data.img를 가리키지 않거나 wipefs -n에서 예상하지 못한 서명이 보이면 pvcreate를 실행하지 않는다.

5.2 재부팅 후 loop/VG 자동 활성화

왜 부팅 순서를 고정하는가? loop 번호는 재부팅마다 달라질 수 있고 파일 연결이 사라지면 VG도 보이지 않는다. Docker보다 먼저 backing file을 임의의 빈 loop에 연결하고 VG를 활성화해야 cinder-volume이 정상 backend를 발견한다.

sudoedit /usr/local/sbin/kolla-cinder-loop로 스크립트를 만들고 다음 내용을 저장한다.

#!/bin/sh
set -eu
IMAGE=/var/lib/cinder_data.img
VG=cinder-volumes
test -f "$IMAGE"
if ! /usr/sbin/losetup -j "$IMAGE" | /usr/bin/grep -q '^/dev/loop'; then
  /usr/sbin/losetup --find "$IMAGE"
fi
/usr/bin/udevadm settle
/usr/sbin/pvscan --cache
/usr/sbin/vgchange -ay "$VG"

sudoedit /etc/systemd/system/kolla-cinder-loop.service로 unit을 만들고 다음 내용을 저장한다.

[Unit]
Description=Attach and activate the file-backed Cinder LVM volume group
RequiresMountsFor=/var/lib/cinder_data.img
After=local-fs.target
Before=docker.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/kolla-cinder-loop
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
sudo chmod 0755 /usr/local/sbin/kolla-cinder-loop
sudo systemctl daemon-reload
sudo systemctl enable --now kolla-cinder-loop.service
systemctl is-enabled kolla-cinder-loop.service
systemctl is-active kolla-cinder-loop.service
sudo vgs cinder-volumes

6. Kolla-Ansible 설정

왜 Kolla-Ansible인가? OpenStack 서비스를 패키지로 하나씩 설치하면 수십 개의 설정 파일, DB migration, 메시지 큐 계정, endpoint와 서비스 시작 순서를 직접 맞춰야 한다. Kolla는 서비스별 컨테이너 이미지를 사용하고 Ansible이 그 관계를 선언적으로 반복 적용한다. 학습자는 자동화가 숨기는 구성요소를 이해하되, 오타가 많은 설치 작업은 재현 가능한 playbook에 맡긴다.

6.1 예제 복사와 의존성

각 파일의 역할: inventory는 “어느 호스트가 어떤 역할인가”, globals.yml은 “무슨 서비스와 네트워크 방식을 쓸 것인가”, passwords.yml은 “서비스들이 서로 인증할 비밀값”을 정의한다. All-in-One은 모든 핵심 그룹에 localhost를 넣는다.

sudo mkdir -p /etc/kolla
sudo cp -a "$VENV/share/kolla-ansible/etc_examples/kolla/." /etc/kolla/
cp "$VENV/share/kolla-ansible/ansible/inventory/all-in-one" "$INVENTORY"
kolla-ansible install-deps
sudo chmod 0600 /etc/kolla/passwords.yml
sudo "/bin/kolla-genpwd"

kolla-genpwd가 서비스 비밀번호를 생성한다. Horizon 관리자는 admin이고 암호 키는 keystone_admin_password다. 실제 값을 문서나 Git에 저장하지 않는다.

6.2 /etc/kolla/globals.yml

설정이 연결되는 곳: network_interface는 API/VIP 관리망, neutron_external_interface는 br-ex의 외부 포트, OVS는 Neutron 데이터 평면, KVM은 Nova 가상화 backend, LVM은 Cinder backend를 선택한다. 서로 이름이 비슷해도 역할을 바꿔 쓸 수 없다.

sudoedit /etc/kolla/globals.yml로 기존 예제를 열고, 이 랩에서는 파일 내용을 다음의 최소 설정으로 교체한다.

---
kolla_base_distro: "ubuntu"
openstack_release: "2026.1"
kolla_internal_vip_address: "192.168.50.254"
network_interface: "wlo1"
neutron_external_interface: "veth-ex"
neutron_plugin_agent: "openvswitch"
enable_neutron_provider_networks: "yes"
enable_horizon: "yes"
enable_cinder: "yes"
enable_cinder_backend_lvm: "yes"
enable_cinder_backup: "no"
nova_compute_virt_type: "kvm"

VIP는 관리 NIC와 같은 서브넷의 미사용 주소여야 한다. enable_cinder_backup: no는 Ceph backup 저장소가 없는 이 랩에서 불필요한 backup 서비스를 막으며 Cinder 볼륨 기능은 유지한다.

7. 배포 실행

왜 다섯 단계로 나누는가? bootstrap은 호스트를 준비하고, prechecks는 전제조건을 검사하며, pull은 이미지 다운로드 실패를 실제 배포와 분리한다. deploy가 DB·설정·컨테이너를 만들고, post-deploy가 사람과 CLI가 API에 로그인할 인증 파일을 만든다. 단계 분리는 실패 지점을 명확하게 한다.

각 단계는 실패하면 다음으로 넘어가지 않는다. 전체 출력을 로그로 보존한다.

  1. bootstrap-servers: Docker, 호스트 설정, Kolla 디렉터리를 준비한다.
  2. prechecks: VIP 충돌, 포트, KVM, 인터페이스, Cinder VG 등 deploy가 의존하는 조건을 읽기 중심으로 검사한다.
  3. pull: 필요한 컨테이너 이미지를 미리 받아 네트워크/registry 문제를 분리한다.
  4. deploy: 데이터베이스, 메시지 큐, API endpoint, 설정과 컨테이너를 실제 생성한다.
  5. post-deploy: clouds.yaml과 OpenRC를 만들어 관리자 CLI의 인증 경로를 제공한다.
sudo -E env PATH="$VENV/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin" ANSIBLE_COLLECTIONS_PATH="$HOME/.ansible/collections" \
  kolla-ansible bootstrap-servers -i "$INVENTORY" |& tee "$HOME/openstack-deploy/logs/bootstrap.log"

sudo -E env PATH="$VENV/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin" ANSIBLE_COLLECTIONS_PATH="$HOME/.ansible/collections" \
  kolla-ansible prechecks --use-test-images -i "$INVENTORY" |& tee "$HOME/openstack-deploy/logs/prechecks.log"

sudo -E env PATH="$VENV/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin" ANSIBLE_COLLECTIONS_PATH="$HOME/.ansible/collections" \
  kolla-ansible pull -i "$INVENTORY" |& tee "$HOME/openstack-deploy/logs/pull.log"

sudo -E env PATH="$VENV/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin" ANSIBLE_COLLECTIONS_PATH="$HOME/.ansible/collections" \
  kolla-ansible deploy -i "$INVENTORY" |& tee "$HOME/openstack-deploy/logs/deploy.log"

sudo -E env PATH="$VENV/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin" ANSIBLE_COLLECTIONS_PATH="$HOME/.ansible/collections" \
  kolla-ansible post-deploy -i "$INVENTORY" |& tee "$HOME/openstack-deploy/logs/post-deploy.log"
옵션 주의: 이 버전에서는 --use-test-images를 prechecks에만 사용한다. pull과 deploy에는 붙이지 않는다. 하위 명령은 kolla-ansible deploy -i ...처럼 먼저 쓴다.

7.1 관리자 CLI

sudo stat -c '%a %U:%G %n' /etc/kolla/clouds.yaml
export OS_CLIENT_CONFIG_FILE=/etc/kolla/clouds.yaml

8. 첫 네트워크, 라우터, VM

왜 배포 후 리소스를 따로 만드는가? Kolla deploy는 클라우드 제어판을 만들 뿐 사용자의 네트워크·이미지·Flavor·VM은 정책에 따라 달라서 자동 생성하지 않는다. 이 단계는 설치된 API를 사용해 실제 클라우드 자원을 만들며, 서비스 간 연동을 처음으로 종단 간 시험한다.

아래에서는 반복을 줄이기 위해 root 인증 파일을 읽을 수 있는 openstack 래퍼 변수를 사용한다.

리소스 관계: public은 인터넷 전체가 아니라 br-ex에 붙는 172.24.4.0/24 provider L2 구간이다. private은 VM이 DHCP 주소를 받는 격리된 VXLAN tenant망이다. lab-router가 두 서브넷에 각각 포트를 두고 L3 라우팅과 SNAT/Floating IP 변환을 수행한다.
OSC="sudo env OS_CLIENT_CONFIG_FILE=/etc/kolla/clouds.yaml $VENV/bin/openstack --os-cloud kolla-admin"

$OSC network create --external --share --provider-network-type flat --provider-physical-network physnet1 public
$OSC subnet create --network public --subnet-range 172.24.4.0/24 --allocation-pool start=172.24.4.100,end=172.24.4.200 --gateway 172.24.4.1 --no-dhcp public-subnet
$OSC network create private
$OSC subnet create --network private --subnet-range 10.0.0.0/24 --gateway 10.0.0.1 --dns-nameserver 1.1.1.1 private-subnet
$OSC router create lab-router
$OSC router add subnet lab-router private-subnet
$OSC router set --external-gateway public lab-router

$OSC security group rule create --ingress --ethertype IPv4 --protocol icmp --remote-ip 0.0.0.0/0 default
$OSC security group rule create --ingress --ethertype IPv4 --protocol tcp --dst-port 22 --remote-ip 0.0.0.0/0 default
$OSC flavor create --vcpus 2 --ram 4096 --disk 20 lab.small

8.1 이미지와 키페어

왜 둘 다 필요한가? Glance 이미지는 VM 루트 디스크의 원본이고 Flavor는 Nova가 할당할 vCPU·RAM·로컬 디스크 크기다. Cloud Image는 기본 비밀번호 대신 metadata로 공개키를 받아 로그인하므로, Nova에 공개키를 등록하고 개인키는 사용자만 읽도록 0600으로 보호한다. SHA-256 검증은 다운로드 손상이나 다른 파일 사용을 막는다.

mkdir -p "$HOME/openstack-deploy/images"
cd "$HOME/openstack-deploy/images"
wget -c -O noble-server-cloudimg-amd64.img https://cloud-images.ubuntu.com/noble/current/noble-server-cloudimg-amd64.img
wget -O SHA256SUMS https://cloud-images.ubuntu.com/noble/current/SHA256SUMS
sha256sum --check --ignore-missing SHA256SUMS
$OSC image create --disk-format qcow2 --container-format bare --file noble-server-cloudimg-amd64.img --public ubuntu-24.04
$OSC keypair create --private-key "$HOME/openstack-deploy/lab-key.pem" lab-key
sudo chown "$USER:$USER" "$HOME/openstack-deploy/lab-key.pem"
chmod 0600 "$HOME/openstack-deploy/lab-key.pem"

8.2 VM과 Floating IP

주소가 두 개인 이유: VM의 10.0.0.x fixed IP는 private망에서 계속 유지된다. 172.24.4.x Floating IP는 Neutron Router가 외부 요청을 fixed IP로 DNAT하고 응답을 다시 Floating IP로 SNAT하기 위한 별도 매핑이다. 보안그룹은 라우터가 아니라 VM port에 적용되는 상태 추적 방화벽이다.

$OSC server create --wait --flavor lab.small --image ubuntu-24.04 --network private --security-group default --key-name lab-key test-vm
$OSC floating ip create public
$OSC server add floating ip test-vm FLOATING_IP
ping -c 4 FLOATING_IP
ssh -i "$HOME/openstack-deploy/lab-key.pem" ubuntu@FLOATING_IP

FLOATING_IP는 바로 앞 명령의 출력값으로 바꾼다. Cloud Image의 기본 사용자는 ubuntu이며 기본적으로 비밀번호 대신 키로 로그인한다.

8.3 Cinder 볼륨

무엇을 검증하는가? volume create는 Cinder API→scheduler→LVM backend 경로를, server add volume은 Cinder→Nova→libvirt→iSCSI 연결을 검증한다. 게스트의 /dev/vdb 확인은 제어 DB의 성공 표시가 아니라 실제 블록 장치가 VM까지 도달했음을 증명한다.

$OSC volume create --size 1 test-volume
$OSC volume show test-volume
$OSC server add volume --device /dev/vdb test-vm test-volume
$OSC volume show test-volume
ssh -i "$HOME/openstack-deploy/lab-key.pem" ubuntu@FLOATING_IP 'lsblk /dev/vdb'

9. 완료 검증과 운영

왜 Horizon 접속만으로 완료가 아닌가? Horizon 200은 웹과 일부 인증 경로만 증명한다. Nova scheduler/compute, Neutron agent/OVS/NAT, Cinder LVM/iSCSI는 실제 VM·패킷·볼륨을 만들어야 검증된다. 제어 경로와 데이터 경로를 모두 확인해야 한다.
sudo docker ps --filter health=unhealthy
$OSC compute service list
$OSC network agent list
$OSC volume service list
$OSC server list
$OSC floating ip list
$OSC volume list
systemctl is-enabled kolla-cinder-loop.service kolla-lab-nat.service
systemctl is-active kolla-cinder-loop.service kolla-lab-nat.service
sudo docker exec openvswitch_db ovs-vsctl show
sudo lvs -a cinder-volumes -o lv_name,lv_size,pool_lv,data_percent,metadata_percent

정상 기준: unhealthy 컨테이너가 없고 Nova 서비스와 Neutron agent가 up, Cinder scheduler/volume이 up이어야 한다. Ceph를 쓰지 않으므로 cinder-backup은 disabled/down이어도 의도한 상태다.

Horizon은 http://192.168.50.254/, 사용자 이름은 admin이다. 암호 확인:

sudo grep '^keystone_admin_password:' /etc/kolla/passwords.yml

9.1 설정을 바꾼 뒤

sudo systemctl daemon-reload
sudo -E env PATH="$VENV/bin:$PATH" ANSIBLE_COLLECTIONS_PATH="$HOME/.ansible/collections" kolla-ansible prechecks --use-test-images -i "$INVENTORY"
sudo -E env PATH="$VENV/bin:$PATH" ANSIBLE_COLLECTIONS_PATH="$HOME/.ansible/collections" kolla-ansible reconfigure -i "$INVENTORY"

globals를 바꿨다고 컨테이너가 자동으로 갱신되지는 않는다. prechecks 후 reconfigure를 실행한다. systemd unit을 바꾸면 먼저 daemon-reload가 필요하다.

10. 장애 확인표

왜 증상별로 나누는가? 모든 실패에 deploy를 다시 실행하면 원인을 가리고 상태를 더 복잡하게 만든다. 증상이 API, 네트워크, 컴퓨트, 스토리지 중 어디에 속하는지 정한 뒤 해당 서비스의 상태·로그·데이터 경로를 따라간다.
증상확인주요 원인

11. 기억해야 할 핵심

  1. Kolla-Ansible은 OpenStack 구성요소를 직접 하나씩 설치하는 대신 컨테이너와 설정을 일관되게 배포한다.
  2. 관리 NIC, VIP, 외부 NIC, provider 대역은 서로 다른 역할이며 값을 추측하면 안 된다.
  3. Wi-Fi 환경에서는 VM MAC을 AP까지 브리지하지 않고 Ubuntu NAT가 wlo1의 IP/MAC으로 대신 송신한다.
  4. Cinder 파일은 블록 장치가 아니므로 loop → LVM PV → VG 단계를 거친다.
  5. prechecks가 통과하지 않으면 deploy하지 않고, 설정 변경 후에는 reconfigure한다.
  6. 완료는 Horizon 화면이 뜨는 것이 아니라 VM 부팅, 양방향 네트워크, Cinder 쓰기까지 검증해야 한다.
