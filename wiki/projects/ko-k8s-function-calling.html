1. 문제 정의

소형 모델도 한국어 요청을 읽고, 여러 도구 가운데 올바른 함수를 선택해 정확한 인자를 만들 수 있을까?

한국어 요청 → 허용된 도구 선택 → 필요한 인자 생성 → tool_calls 또는 no-call

원본 Qwen3-1.7B는 호출 여부와 도구명은 비교적 잘 판단했지만, 필수 인자를 빠뜨리거나 사용자가 말하지 않은 값을 추가하고 Schema를 위반하는 경우가 있었다. 그래서 목표를 Kubernetes 자동 운영이 아니라 Function Calling 출력 계약을 안정적으로 지키는 라우터로 한정했다.

3. 학습

원본 모델의 실패 양상을 먼저 측정하고, 같은 도구 계약의 정답 데이터로 LoRA adapter만 학습했다.

학습 전Full success 36%인자 exact match 29.41%
학습BF16 + LoRATrain 800 · Validation 100
학습 후Full success 96%같은 Holdout 100건

정답은 한국어 요청, 전체 도구 목록, assistant의 tool call 또는 no-call로 구성했다. Qwen 원본 가중치는 동결하고 Attention·MLP Linear 계층의 LoRA adapter만 1 epoch 학습했다. 주요 설정은 gradient accumulation 16, learning rate 2e-4, rank 16·alpha 32였다.

4. 평가 결과

Base와 Tuned를 같은 100건 holdout과 동일한 추론·채점 조건으로 비교했다.

지표Base BF16Tuned BF16변화
Full success36.00% (36/100)96.00% (96/100)+60.00%p
Call decision96.00%99.00%+3.00%p
Schema validity83.15%100.00%+16.85%p
Argument exact match29.41%95.29%+65.88%p
No-call accuracy73.33%100.00%+26.67%p

평가 조건은 BF16, temperature=0, tool_choice="auto", thinking 비활성화로 고정했다. Full success는 호출 여부만 보는 지표가 아니라 도구명·JSON·Schema·정확한 인자와 no-call을 모두 통과해야 성공한다. 가장 큰 개선은 인자 exact match의 29.41% → 95.29%였다.
