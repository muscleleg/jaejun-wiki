Kubernetes 운영 데이터를
근거와 함께 요약하는 AI

Pod의 Metrics·Logs·Events를 한곳에 모으고, AI가 현재 상태와 이상 신호를 원문 근거와 함께 정리하는 운영 관측 웹 애플리케이션입니다. 단순한 차트 요약이 아니라 운영자가 AI의 해석을 실제 메트릭·로그·이벤트와 직접 대조할 수 있도록 설계했습니다.

운영자는 Pod를 선택한 뒤 Metrics·Logs·Events 탭에서 서로 다른 운영 신호를 확인합니다. FastAPI가 Kubernetes와 메트릭 소스에서 필요한 데이터를 모으고, LangGraph가 탭별 분석 흐름을 실행해 요약·직접 관측 신호·가능한 해석·근거를 일정한 구조로 반환합니다.

프로젝트 형태React·FastAPI·LangGraph로 구현한 1인 개발 웹 애플리케이션입니다. Pod 조회·터미널·YAML 확인과 AI Summary를 한 화면 흐름으로 연결했으며, 장애를 자동 해결하거나 운영자의 결정을 대신하는 시스템은 아닙니다.

개인 프로젝트 목록

개발 배경

Pod 상태를 판단하려면 CPU·Memory 차트, 여러 컨테이너의 로그와 시간순 이벤트를 따로 확인한 뒤 하나의 상황으로 연결해야 했습니다.

메트릭은 사용량의 변화를 보여 주지만 원인을 직접 말해 주지 않고, 로그는 양이 많아 중요한 줄을 찾는 데 시간이 걸립니다. 이벤트는 상태 변화의 단서를 제공하지만 메트릭·로그와 함께 보지 않으면 현재 문제가 계속되는지 판단하기 어렵습니다.

그래서 같은 Pod에서 나온 세 종류의 운영 데이터를 함께 수집하고, AI가 무엇을 관측했는지와 무엇을 추론했는지, 어떤 원문을 근거로 사용했는지를 구분해 보여 주는 흐름을 만들었습니다.

기존 확인 방식차트·로그·이벤트를 각각 열어 직접 연결합니다.

운영자가 많은 원문을 읽고 시간 순서와 이상 신호의 관계를 스스로 조합해야 합니다.

개선한 방식한 Pod의 운영 신호를 요약과 근거로 함께 봅니다.

AI가 핵심 신호를 먼저 정리하고, 운영자는 같은 화면에서 사용된 원문을 대조합니다.

핵심 목표

운영 데이터를 대신 판단하는 것이 아니라, 여러 신호를 빠르게 연결하고 그 해석을 검증할 수 있는 출발점을 제공하는 데 초점을 맞췄습니다.

  1. 01
    Pod 중심의 운영 맥락 통합

    Pod 목록·Metrics·Logs·Events·터미널·YAML을 하나의 상세 화면 흐름으로 연결합니다.

  2. 02
    서로 다른 관측 신호의 연결

    CPU·Memory 변화와 컨테이너 로그, Kubernetes 이벤트를 같은 분석 문맥에서 확인합니다.

  3. 03
    관측과 추론의 분리

    데이터에서 직접 확인된 사실과 가능한 원인 해석을 서로 다른 필드로 보여 줍니다.

  4. 04
    원문 근거를 남기는 요약

    대표 메트릭·로그·이벤트를 Evidence로 제공해 운영자가 결론을 직접 검토할 수 있게 합니다.

주요 기능

하나의 Pod를 선택해 기본 운영 정보를 확인하고, Metrics·Logs·Events를 각 데이터의 성격에 맞는 AI Summary로 읽는 순서로 구성했습니다.

  1. 01
    Pod 운영 화면Pod 목록과 상태를 확인하고 Metrics·Logs·Events·터미널·YAML로 이어갑니다.
  2. 02
    Metrics 통합 분석CPU·Memory 변화에 로그·이벤트와 Spike 정보를 연결해 현재 상태를 요약합니다.
  3. 03
    Logs 컨테이너별 분석긴 로그를 컨테이너별 핵심 패턴·발견 사항·대표 원문으로 나누어 보여 줍니다.
  4. 04
    Events 상태 변화 분석Warning·Normal 흐름과 최신 변화, Reason과 원문 메시지를 함께 정리합니다.
기능 01

Pod 운영 화면

클러스터의 Pod를 찾고, 선택한 Pod의 운영 데이터와 직접 확인 도구를 한 화면 흐름에서 이어갑니다.

Pod 기준 통합운영 데이터의 출발점을 하나의 Pod로 고정합니다.

Pod 목록에서 대상을 선택하면 같은 상세 화면 안에서 Metrics·Logs·Events를 확인하고, 필요할 때 터미널과 YAML로 더 깊게 들어갈 수 있습니다.

직접 확인
AI Summary만으로 판단하지 않습니다.

원본 탭과 터미널, YAML을 함께 제공해 운영자가 요약과 실제 리소스 상태를 대조할 수 있게 했습니다.

탐색 유지
대상을 다시 찾지 않고 같은 Pod의 신호를 이동합니다.

Metrics·Logs·Events가 동일한 Pod 맥락을 공유하므로 서로 다른 화면에서 리소스를 다시 선택하는 과정을 줄였습니다.

사용자가 얻는 변화리소스와 확인 도구가 흩어지지 않아, 한 Pod의 상태를 살피는 동안 현재 대상을 잃지 않고 관측과 직접 점검을 이어갈 수 있습니다.

보조 운영 화면 보기Metrics·Logs·Events 원본 탭·터미널·YAML
기능 02

Metrics 통합 분석

CPU·Memory 시계열만 요약하지 않고, 같은 Pod의 로그·이벤트와 Spike 정보를 함께 읽어 현재 상태와 판단 근거를 제공합니다.

신호 연결사용량 변화와 그때 함께 나타난 운영 신호를 연결합니다.

Metrics Graph가 CPU·Memory 시계열과 Spike, Pod 로그와 이벤트를 모아 하나의 분석 문맥을 만듭니다. 화면은 현재 상태를 먼저 보여 주고, 직접 확인된 신호와 가능한 해석을 분리합니다.

상태 요약
CPU와 Memory의 현재 상태와 변화를 먼저 확인합니다.

차트를 전부 읽기 전에 중요한 변화와 Spike 여부를 요약 카드에서 파악할 수 있습니다.

근거 대조
요약에 사용한 메트릭·로그·이벤트를 다시 확인합니다.

Evidence를 데이터 종류별로 나누어 AI의 설명이 어떤 관측값에서 시작했는지 추적할 수 있습니다.

사용자가 얻는 변화메트릭 변화만 보고 원인을 짐작하지 않고, 같은 시점의 로그와 이벤트까지 연결된 근거를 바탕으로 다음 확인 대상을 좁힐 수 있습니다.

Metrics 처리 흐름 보기CPU·Memory·Logs·Events·Spike 수집과 structured output

AI 분석 설계

입력 데이터
시계열·로그·이벤트를 하나의 Context로 묶습니다.

기본 30분 구간의 CPU·Memory 시계열과 같은 Pod의 컨테이너별 로그, Kubernetes 이벤트를 병렬로 수집합니다.

사전 계산
Spike 판정은 LLM에 맡기지 않습니다.

Python 코드가 60초 비교 구간에서 시작값보다 50% 이상 증가한 점이 두 개 이상 연속되는지를 검사하고, 시작·평균·최저·최고·종료값과 심각도를 계산합니다. 프롬프트에는 컨테이너마다 최대 20줄, 한 줄 240자까지의 로그만 전달합니다.

판단 제한
관측 사실과 가능한 해석을 분리합니다.

주어진 데이터만 사용하고, 특정 로그나 이벤트를 최종 원인으로 단정하지 않으며, 직접 근거가 없는 설정·네트워크·애플리케이션 원인까지 확장하지 않도록 지시합니다.

출력 계약
화면이 바로 사용할 수 있는 구조로 응답합니다.

Pydantic 스키마를 통해 CPU·Memory 상태, 핵심 발견, Direct Signal, Inference와 Metrics·Logs·Events Evidence를 정해진 구조로 반환합니다.

  1. Metrics 요청에 맞는 Pod Metric Analysis Graph를 실행합니다.
  2. CPU·Memory 시계열, Pod 로그, 이벤트와 Spike를 수집·가공합니다.
  3. 관측 데이터를 Prompt Context로 만들고 JSON Schema에 맞춘 응답을 생성합니다.
  4. Frontend가 요약·Analysis·Evidence를 각각의 UI 영역에 렌더링합니다.

초기 포트폴리오의 Metrics 생성 아키텍처 슬라이드는 제목과 내부 흐름이 어긋난 부분이 있어, 실제 Log Analysis 흐름에 해당하는 설명은 아래 Logs 처리 흐름에 보존했습니다.

기능 03

Logs 컨테이너별 분석

긴 Pod 로그를 컨테이너별로 나누고, 현재 상태와 핵심 패턴·발견 사항·대표 원문을 빠르게 확인할 수 있게 정리합니다.

컨테이너 분리Pod 전체 로그를 하나의 설명으로 뭉개지 않습니다.

최근 로그를 컨테이너별로 정리하고 정상 동작, 설정 로드, 포트 리스닝, 재로드와 오류처럼 판단에 필요한 패턴을 요약합니다. 대표 로그 원문도 같은 컨테이너 기준으로 남깁니다.

위치 좁히기
어느 컨테이너에서 신호가 나타났는지 먼저 구분합니다.

여러 컨테이너가 있는 Pod에서도 상태와 발견 사항을 컨테이너 단위로 확인할 수 있습니다.

원문 확인
요약에 사용한 대표 로그를 함께 읽습니다.

전체 로그를 다시 훑기 전에 핵심 원문을 대조하고, 필요하면 원본 Logs 탭으로 돌아갑니다.

사용자가 얻는 변화긴 로그에서 중요한 줄을 처음부터 찾는 대신, 컨테이너와 패턴이 정리된 요약을 출발점으로 삼아 확인 범위를 좁힐 수 있습니다.

Logs 처리 흐름 보기최근 로그 수집·컨테이너 분리·Findings·Evidence

AI 분석 설계

입력 데이터
분석 범위와 컨테이너별 로그를 함께 전달합니다.

최근 로그 수, 지정한 시작·종료 시각 또는 두 조건의 조합을 분석 기준으로 만들고, 수집한 로그를 컨테이너 이름별로 나누어 프롬프트에 넣습니다.

분석 범위
Logs 탭은 로그에서 확인할 수 있는 내용만 다룹니다.

현재 서브그래프는 Metrics와 Events를 결합하지 않습니다. 로그가 없으면 없다고 기록하고, 정상 기동·설정 로드·재시작·반복 패턴처럼 실제 로그에 나타난 정보만 분석 대상으로 삼습니다.

판단 제한
로그에서 보이지 않는 장애 원인을 단정하지 않습니다.

컨테이너별 상태를 먼저 정리하고 Direct Signal과 Inference를 분리하며, 불확실한 내용은 가능성 수준으로 표현하도록 지시합니다. 대표 원문 몇 줄도 Evidence로 함께 선택합니다.

출력 계약
컨테이너별 요약과 근거의 위치를 고정합니다.

Pydantic 스키마를 통해 컨테이너별 로그 유무·요약·핵심 발견, 전체 Analysis와 컨테이너별 Evidence를 정해진 구조로 반환합니다.

  1. Logs 요청 시 Pod Log Analysis Graph를 실행합니다.
  2. 최근 Pod 로그를 수집하고 컨테이너별 분석 Context로 정리합니다.
  3. LLM이 JSON Schema에 맞춘 Summary·Analysis·Findings·Evidence를 생성합니다.
  4. Frontend가 컨테이너별 카드와 대표 로그 영역에 응답을 렌더링합니다.

기능 04

Events 상태 변화 분석

Kubernetes 이벤트를 Warning·Normal 흐름과 최신 상태 변화로 정리하고, Reason·Timestamp·source와 원문 메시지를 근거로 제공합니다.

시간 흐름이벤트 한 건보다 반복과 최신 변화를 중심으로 읽습니다.

전체 이벤트 수와 Warning·Normal 수, 최신 이벤트를 먼저 보여 주고, 반복된 Warning 패턴과 주요 상태 변화를 Findings로 정리합니다.

변화 파악
최근에 무엇이 바뀌었는지 먼저 확인합니다.

이벤트 목록을 시간순으로만 읽지 않고 Warning·Normal 비율과 최신 발생 시각을 함께 봅니다.

사유 확인
Reason과 메시지, 발생 주체를 원문으로 남깁니다.

AI의 설명 아래에서 Timestamp와 source를 포함한 대표 이벤트를 직접 대조할 수 있습니다.

사용자가 얻는 변화반복되는 Warning과 최근 상태 변화를 먼저 파악한 뒤, 관련 Reason과 원문 메시지를 확인해 다음 점검 대상을 구체화할 수 있습니다.

Events 처리 흐름 보기이벤트 수집·Warning 분류·최신 변화·Evidence

AI 분석 설계

입력 데이터
선택한 Pod와 직접 연결된 이벤트 원문을 사용합니다.

각 이벤트의 발생 시각, Normal·Warning 타입, Reason, Source, 반복 횟수와 Message를 하나의 이벤트 목록으로 구성해 프롬프트에 전달합니다.

분석 범위
Events 탭은 상태 변화의 흐름에 집중합니다.

현재 서브그래프는 Metrics와 Logs를 함께 해석하지 않습니다. 이벤트 전체 수와 Warning·Normal 구분, 가장 최근 발생 시각과 반복된 Reason을 먼저 정리하도록 합니다.

판단 제한
이벤트 한 건을 장애의 최종 원인으로 확정하지 않습니다.

주어진 이벤트만 사용하고 Direct Signal과 Inference를 분리하며, 구체 원인을 확인하려면 Metrics와 Logs가 더 필요하다는 경계를 유지하도록 지시합니다.

출력 계약
요약과 대표 이벤트 원문을 함께 반환합니다.

Pydantic 스키마를 통해 Event Overview, 핵심 발견, Analysis와 Timestamp·Type·Reason·Message·Source를 보존한 Evidence 객체를 정해진 구조로 반환합니다.

  1. Events 요청 시 Pod Event Analysis Graph를 실행합니다.
  2. Pod 이벤트를 수집해 Warning·Normal·Latest와 주요 Reason을 정리합니다.
  3. LLM이 JSON Schema에 맞춘 Summary·Analysis·Findings·Evidence를 생성합니다.
  4. Frontend가 Event Overview와 대표 이벤트 영역에 응답을 렌더링합니다.

초기 포트폴리오의 Event Overview 화면은 서로 다른 범위를 보여 주므로 모두 보존했습니다. 별도 Evidence 슬라이드가 Analysis 화면을 다시 사용한 부분은 중복 이미지를 반복하지 않고 evidence.events 설명으로 보존했습니다.

AI Summary 생성 흐름

세 분석 기능은 서로 다른 데이터를 다루지만, 사용자의 요청을 탭별 Graph로 분기하고 관측 데이터를 구조화된 응답으로 돌려주는 공통 흐름을 사용합니다.

  1. 운영자가 Pod 상세 화면에서 Metrics·Logs·Events 중 하나의 AI Summary를 요청합니다.
  2. FastAPI가 요청 종류에 맞는 LangGraph 서브그래프를 실행합니다.
  3. 서브그래프가 Kubernetes API와 메트릭 소스에서 필요한 관측 데이터를 수집·가공합니다.
  4. LLM이 JSON Schema에 맞춘 요약·분석·근거를 생성하고 Frontend가 해당 탭에 렌더링합니다.

프롬프트와 출력 스키마

LLM에 운영 데이터를 단순히 “요약해 달라”고 요청하지 않았습니다. 프롬프트에는 무엇을 관찰하고 어디까지 추론할지를 적고, Pydantic 모델에는 각 결과를 어느 필드에 어떤 의미로 담을지를 선언했습니다. 두 계약을 with_structured_output으로 결합해 분석 결과를 Frontend까지 일정한 형태로 전달합니다.

이때 스키마는 프론트가 받을 타입만 정의한 것이 아닙니다. 각 필드의 Field(description=...)에는 LLM이 그 칸에 작성해야 할 내용과 판단 경계를 적고, examples에는 기대하는 표현의 예를 넣었습니다. 프롬프트가 분석 방법을 정한다면, 스키마의 설명은 분석 결과를 담을 자리와 의미를 정합니다.

  1. 01 · Input운영 데이터 수집Metrics·Logs·Events
  2. 02 · Prompt판단 범위 지정관측과 추론의 경계
  3. 03 · Schema응답 구조 고정Pydantic model
  4. 04 · Output화면 필드 전달Summary·Analysis·Evidence

Metrics 적용 예시

실제 코드의 핵심만 줄여 보면 역할이 더 분명합니다. 왼쪽 프롬프트가 전체 분석 규칙을 지시하고, 오른쪽 스키마의 필드 설명이 각 결과의 목적과 표현 범위를 다시 구체화합니다.

01 · 분석 프롬프트

관찰 범위와 판단 규칙

역할: Kubernetes Pod 관측 데이터 분석가

입력:
- 메트릭 분석 문맥
- 컨테이너별 로그
- Kubernetes 이벤트

규칙:
- CPU·Memory Spike를 먼저 요약
- 주어진 데이터만 사용
- 관측 사실과 추론을 분리
- 불확실한 원인은 단정하지 않음
- 스키마 밖의 필드는 만들지 않음
02 · Output Schema

필드마다 값의 의미까지 지정

class PodMetricAnalysisSummary(BaseModel):
    title: str = Field(
        description="프론트 상단에 표시할 짧은 제목",
        examples=["Readiness probe 실패 감지"],
    )
    summary: str = Field(
        description="전체 분석 결과를 한두 문장으로 요약한 한국어 문장"
    )
    analysis: AnalysisSection = Field(
        description="직접 관측된 신호와 보수적 추정을 구분한 분석 결과"
    )
    evidence: EvidenceSection = Field(
        description="메트릭, 로그, 이벤트별 근거 묶음"
    )

class AnalysisSection(BaseModel):
    direct_signal: str = Field(
        description="직접 관측된 이상 신호 또는 안정 상태"
    )
    inference: str = Field(
        description="관측 사실을 바탕으로 한 보수적인 추정. 원인을 단정하지 않음"
    )

class EvidenceSection(BaseModel):
    metrics: list[str] = Field(
        description="메트릭 기반 근거 문장 목록"
    )
    logs: list[LogEvidenceItem] = Field(
        description="컨테이너별 로그 상태 요약 목록"
    )
    events: list[str] = Field(
        description="Kubernetes 이벤트 기반 근거 문장 목록"
    )

탭별 확장 Logs와 Events도 같은 결합 방식을 사용합니다. Logs는 컨테이너별 요약과 대표 로그를, Events는 Warning·Normal·Latest와 Timestamp·Reason·Message를 담는 전용 Pydantic 모델을 사용합니다.

시스템 구성

React 화면, FastAPI 애플리케이션, Kubernetes 운영 데이터와 LangGraph 분석 책임을 분리했습니다.화면은 Pod 선택과 결과 확인을 담당하고, Backend가 데이터 조회와 분석 Graph 실행을 연결합니다.

Interface
React

Pod 목록·상세, 원본 관측 데이터와 AI Summary, 터미널과 YAML 화면을 제공합니다.

Application
FastAPI

클러스터 연결 설정을 읽고 Kubernetes API·메트릭 조회와 탭별 Summary 요청을 연결합니다.

Observability
Kubernetes API·metrics.k8s.io·Prometheus

Pod·Logs·Events와 CPU·Memory 시계열을 분석 Graph에 제공합니다.

AI workflow
LangGraph·OpenAI API

탭별 데이터 수집과 Context 생성을 분리하고 JSON Schema에 맞춘 응답을 생성합니다.

Configuration
SQLite

클러스터 접속 정보와 애플리케이션 설정을 Backend가 조회할 수 있도록 보관합니다.

역할과 프로젝트 범위

기획부터 React 화면, FastAPI API와 Kubernetes 연동, LangGraph 분석 흐름과 structured output UI까지 1인 개발로 구현했습니다.

운영자가 결정하는 일

  • 확인할 클러스터와 Pod, 분석 탭을 선택합니다.
  • AI Summary와 Evidence를 실제 원본 데이터에 대조합니다.
  • 터미널과 YAML을 통해 추가 확인 범위를 결정합니다.
  • 운영 조치의 필요성과 실행 여부를 최종 판단합니다.

애플리케이션이 처리하는 일

  • Pod의 Metrics·Logs·Events를 탭 목적에 맞게 수집합니다.
  • LangGraph로 데이터 준비와 Summary 생성을 연결합니다.
  • 관측 신호·가능한 해석·Evidence를 구조화합니다.
  • 같은 응답 계약을 React 화면의 카드에 렌더링합니다.

현재 구현 범위화면과 기능 흐름, 직접 신호·추론·근거의 분리까지 구현했지만 장애 유형별 정답셋을 이용한 Summary 정확도·재현율, 근거 충실도 자동 채점, 권한 분리·민감 로그 마스킹·다중 클러스터 운영 정책은 추가 검증이 필요합니다. 이 프로젝트는 장애를 자동 해결하는 Agent가 아니라 운영 관측 데이터를 근거와 함께 해석 가능한 AI Summary로 제공하는 시스템입니다.
