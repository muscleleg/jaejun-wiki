1. 이 관문에서 알고자 하는 것

수동 생성에서 매 Step마다 전체 Prefix를 다시 모델에 넣으면 이전 Token의 Attention Key·Value도 반복 계산합니다. 먼저 이 동작을 그대로 계측해 기준선을 만들고, 이어 past_key_values를 다음 Forward에 전달해 새 Token에 필요한 계산만 수행하는 흐름과 비교합니다.

현재의 가장 작은 다음 행동
같은 tiny GPT-2, 같은 Prompt, 같은 생성 Token 수로 Cache를 쓰지 않는 Greedy 반복 생성의 입력 Shape과 Step별 시간을 기록합니다.

2. 비교 조건을 먼저 고정합니다

고정할 값Model·dtype·Device·Prompt Token 수·생성 Token 수·선택 방식·Seed·Warm-up 횟수를 동일하게 둡니다.
기록할 값Step별 입력 Shape, 전체 생성 시간, Token당 시간, 출력 Token ID, Cache 사용 시 Layer별 Key·Value Shape을 기록합니다.
해석 기준출력이 같은지 먼저 확인한 뒤 속도 차이를 비교합니다. Cache 외의 조건이 함께 바뀌면 성능 차이의 원인을 Cache라고 단정하지 않습니다.

3. No-cache 기준선

현재 사전학습 Causal LM 관문에서 작성한 전체 입력 → 마지막 위치 Logit → 다음 Token ID → 입력 뒤 연결 루프를 그대로 재사용합니다. 생성할 때마다 Prefix 길이가 하나씩 늘고 모델에는 전체 Prefix가 다시 들어갑니다.

아직 검증 전
이 문서는 새 관문의 시작점입니다. 실제 Step별 Shape·시간·출력은 노트북 실행을 확인한 뒤 추가합니다.

4. KV Cache 비교

No-cache 기준선을 얻은 뒤 첫 Forward가 반환한 past_key_values를 보존하고, 다음 Step부터는 새 Token ID 하나와 이전 Cache를 전달합니다. Sequence 축에 과거 Key·Value가 누적되는 Shape과 모델 입력 길이의 차이를 직접 확인합니다.

5. Batch 1과 Batch N

단일 문장의 Cache 흐름을 확인한 다음 길이가 다른 여러 문장을 Batch로 묶습니다. Padding 위치, 문장별 종료 조건, Batch별 Cache Shape과 실제 처리량을 분리해 기록합니다.

6. 완료 증거

  • ○ 같은 입력에서 No-cache와 KV Cache의 출력 Token ID가 일치합니다.
  • ○ 두 방식의 Step별 입력 Shape과 past_key_values Shape을 설명합니다.
  • ○ 조건을 고정한 Latency와 Token당 시간을 비교합니다.
  • ○ Batch 1과 Batch N에서 처리량·메모리 차이를 기록합니다.
  • ○ Model·dtype·Token 길이·장치·Warm-up·측정 경계를 함께 남깁니다.
