학습 목적 비교 조건 모델 구조 No-cache KV Cache 생성 원리 Latency Batch 추론 완료 증거

1. 이 관문에서 알고자 하는 것

수동 생성에서 매 Step마다 전체 Prefix를 다시 모델에 넣으면 이전 Token의 Attention Key·Value도 반복 계산합니다. 먼저 이 동작을 그대로 계측해 기준선을 만들고, 이어 past_key_values를 다음 Forward에 전달해 새 Token에 필요한 계산만 수행하는 흐름과 비교합니다.

현재의 가장 작은 다음 행동
단일 문장의 No-cache·KV Cache 출력과 Latency 기준선을 확보했습니다. 다음에는 같은 모델에서 Batch 1과 Batch N의 입력·Cache Shape, 처리량과 메모리 차이를 비교합니다.

2. 비교 조건을 먼저 고정합니다

고정할 값Model·dtype·Device·Prompt Token 수·생성 Token 수·선택 방식·Seed·Warm-up 횟수를 동일하게 둡니다.
기록할 값Step별 입력 Shape, 전체 생성 시간, Token당 시간, 출력 Token ID, Cache 사용 시 Layer별 Key·Value Shape을 기록합니다.
해석 기준출력이 같은지 먼저 확인한 뒤 속도 차이를 비교합니다. Cache 외의 조건이 함께 바뀌면 성능 차이의 원인을 Cache라고 단정하지 않습니다.

3. Token 수와 Transformer Layer 수를 먼저 구분합니다

손코딩한 TinyDecoderLM과 현재 사용하는 sshleifer/tiny-gpt2는 모두 Head가 2개이지만 Transformer Layer 수가 다릅니다. 손코딩 모델은 클래스 안에 self.block을 단수로 선언하고 Forward에서도 한 번만 호출했으므로 Transformer Layer가 1개입니다. 반면 현재 tiny GPT-2는 Transformer Layer가 2개이고, 각 Layer 안에 Head가 2개 있습니다.

손코딩 TinyDecoderLM
Token Embedding + Position Embedding
  ↓
Transformer Layer 0  # Head 2개
  ↓
LM Head

sshleifer/tiny-gpt2
Token Embedding + Position Embedding
  ↓
Transformer Layer 0  # Head 2개
  ↓
Transformer Layer 1  # Head 2개
  ↓
LM Head

여기서 Layer와 Head, Token은 서로 다른 축입니다. Layer는 Transformer Block을 몇 층 쌓았는지, Head는 한 Layer의 Attention을 몇 갈래로 나누는지, Token은 입력 Sequence의 위치가 몇 개인지를 뜻합니다. 따라서 “Token이 3개라서 Layer도 3개”가 아니라, 현재 입력은 Token 3개이고 모델은 그 Token들을 Layer 2개에 차례로 통과시킵니다.

같은 Token이라도 Layer 0과 Layer 1의 Key·Value는 같지 않습니다. Layer 0이 입력 표현을 바꾼 뒤 Layer 1은 그 바뀐 표현에 자신의 Projection Weight를 적용해 새로운 Query·Key·Value를 만들기 때문입니다. 그래서 KV Cache도 Layer마다 따로 필요합니다.

4. No-cache에서는 전체 Prefix의 Q·K·V를 다시 계산합니다

손코딩한 TinyDecoderLM에는 KV Cache를 구현하지 않았습니다. 현재 사전학습 Causal LM에서 작성한 No-cache 생성도 전체 입력 → 마지막 위치 Logit → 다음 Token ID → 입력 뒤 연결 흐름입니다. 새 Token을 하나 붙일 때마다 늘어난 Prefix 전체를 다시 모델에 넣으므로, 각 Layer는 과거 Token을 포함한 전체 Token의 Query·Key·Value를 다시 계산합니다.

실제로 확인한 모델 입력 Shape
[1,3] → [1,4] → [1,5] → … → [1,12]

Batch는 계속 1이고, 생성할 때마다 Token 축만 3에서 12까지 한 칸씩 늘었습니다. 이는 이전 Token의 Key·Value도 매 Step 반복 계산하는 No-cache 기준선의 동작을 실제 입력 Shape으로 확인한 결과입니다.

5. past_key_values에는 Layer·Head·Token별 K·V가 모입니다

KV Cache는 Projection Weight나 연산 자체가 아니라, 각 Layer의 Hidden State가 Projection을 거친 뒤 Head별로 나뉜 과거 Token의 K·V 결과값을 저장합니다. GPT-2의 합쳐진 QKV Projection과 역할별 Gradient까지 이어지는 원리는 KV Cache와 GPT-2 QKV Projection 문서에서 분리해 설명합니다.

Prompt "I study."는 Token ID [40,2050,13]의 3개 Token이었고, 모델 출력 Logit Shape은 [1,3,50257]이었습니다. 여기서 1은 Batch, 3은 Token 위치, 50,257은 각 위치의 Vocabulary 후보 수입니다. 같은 첫 Forward를 use_cache=True로 실행해 past_key_values를 확인했습니다.

past_key_values[0][0]  # Layer 0의 Key Tensor
past_key_values[0][1]  # Layer 0의 Value Tensor
past_key_values[1][0]  # Layer 1의 Key Tensor
past_key_values[1][1]  # Layer 1의 Value Tensor

즉 바깥쪽 첫 Index는 Transformer Layer를 고르고, 안쪽 Index 0은 Key, 1은 Value를 고릅니다. 한 Layer에는 Key Tensor 하나와 Value Tensor 하나가 있지만, 여기서 “하나”는 값이나 벡터 하나가 아니라 모든 Head와 모든 Token의 값을 모은 Tensor 하나라는 뜻입니다.

Layer 0 Key   Shape = [1,2,3,1]
Layer 0 Value Shape = [1,2,3,1]

[Batch, Head, Token, Head dim]
[     1,    2,     3,        1]

예를 들어 past_key_values[0][0][0,0,1,:]은 Layer 0·Batch 0·Head 0에서 Token 1의 Key 벡터입니다. Value도 같은 위치 규칙을 사용합니다. 정리하면 각 Layer × Head × Token 조합마다 K 벡터와 V 벡터가 있고, 이를 Layer별 Key Tensor와 Value Tensor로 묶어 저장합니다.

6. Cache 생성에서는 과거 K·V를 재사용하고 새 K·V를 뒤에 붙입니다

첫 Forward는 Prompt 전체의 Query·Key·Value를 계산하고 Layer별 Key·Value를 Cache로 반환합니다. 다음 Step부터는 새 Token 하나의 Query·Key·Value만 계산하고, 새 Query가 과거 K Cache + 새 Token의 K를 조회한 뒤 그 Attention 비율로 과거 V Cache + 새 Token의 V를 섞습니다. 새 Token의 K·V는 각 Layer Cache의 Token 축 뒤에 추가되어 다음 Step에서 다시 사용됩니다.

새 Token의 Q
  × [과거 K Cache + 새 Token의 K]
  → Attention Score와 Weight
  × [과거 V Cache + 새 Token의 V]
  → 새 Token의 Attention 출력

이 흐름을 Prompt "I study"로 한 Step 직접 확인했습니다. 마침표가 없는 이 Prompt의 입력 Shape은 [1,2]였고, 첫 Forward의 Layer 0 Key Cache는 [1,2,2,1]이었습니다. 마지막 위치 Logit에서 Greedy로 고른 새 Token ID는 [[16046]]이었습니다.

Prompt 입력 Shape       = [1,2]
처음 Layer 0 Key Cache = [1,2,2,1]
선택한 새 Token ID     = [[16046]]

새 Token 입력 Shape    = [1,1]
갱신된 Layer 0 Key Cache = [1,2,3,1]

두 번째 Forward에는 과거 input_ids 전체를 다시 넣지 않았습니다. 새 Token ID 하나와 첫 Forward의 past_key_values만 전달했습니다. 모델 입력의 Token 축은 1이었지만 반환된 Key Cache의 Token 축은 과거 2개와 새 Token 1개를 합쳐 2 → 3, 즉 S → S+1이 되었습니다. 이 결과로 과거 K·V가 재사용되고 새 Token의 K·V가 Cache 뒤에 추가되는 한 Step을 실제 Shape으로 확인했습니다. 과거 ID를 다시 넣지 않아도 전체 문맥을 사용하는 인과 흐름은 KV Cache와 input_ids 전달 문서에서 A·B → C → D 예제로 이어 봅니다.

과거 Token의 Query는 그 Token의 출력을 만들 때 이미 역할을 마쳤습니다. 다음 Step에서는 새 Token의 Query만 있으면 과거를 조회할 수 있으므로 과거 Query를 저장하지 않습니다. Attention Score·Weight·최종 출력도 현재 Query와 K·V로 다시 만들어지는 중간 결과라 Cache하지 않습니다. 다음 생성에 다시 필요한 과거 정보인 K와 V만 보존합니다.

이후 Cache 반복 루프를 5개 새 Token까지 확장했습니다. 첫 Step에는 Prompt 전체 [1,2]를 넣고, 두 번째 Step부터는 직전에 선택한 새 Token만 [1,1]로 전달했습니다. Layer 0 Key Cache의 Token 축은 생성 순서에 맞춰 2 → 3 → 4 → 5 → 6으로 한 칸씩 증가했습니다.

Cache 반복 생성
1회 입력 [1,2] · Key Cache [1,2,2,1]
2회 입력 [1,1] · Key Cache [1,2,3,1]
3회 입력 [1,1] · Key Cache [1,2,4,1]
4회 입력 [1,1] · Key Cache [1,2,5,1]
5회 입력 [1,1] · Key Cache [1,2,6,1]

같은 sshleifer/tiny-gpt2, Prompt "I study", Greedy argmax, 새 Token 5개 조건에서 No-cache 함수와 KV Cache 함수를 각각 실행했습니다. 두 결과는 모두 Token ID [40,2050,16046,16046,16046,16046,16046]이었고, Decode 결과도 "I study stairs stairs stairs stairs stairs"로 같았습니다. torch.equal(no_cache_ids, cache_ids)가 True였으므로 Cache는 계산 경로를 바꾸지만 같은 Greedy 조건의 생성 의미를 바꾸지 않는다는 기능적 기준선을 확보했습니다.

현재 검증 경계
여러 Token의 Cache 반복 생성과 No-cache·KV Cache 출력 일치까지 실행으로 검증했습니다. 이어지는 첫 로컬 Latency 기준선은 아래에서 별도로 기록합니다.

7. Warm-up 뒤 함수 전체 Latency를 비교했습니다

time.perf_counter()는 달력의 현재 시각을 주는 함수가 아니라, 기준점이 공개되지 않은 고해상도 단조 증가 Counter를 초 단위 float으로 읽습니다. Python의 Singleton 객체나 변수가 계속 증가하는 것이 아니라, 운영체제와 하드웨어 쪽 시계가 독립적으로 흐르고 함수 호출 때마다 그 순간의 Snapshot 숫자를 받습니다. 변수에 저장된 값은 이후 변하지 않으므로 시작 직전 값과 종료 직후 값의 차이만 실행시간으로 사용합니다.

start = time.perf_counter()
result = generation_function(...)
end = time.perf_counter()

elapsed_seconds = end - start
UTC로 직접 바꿀 수 없는 이유
perf_counter()의 숫자는 Unix Epoch 기준 Timestamp가 아니므로 UTC(협정 세계시)로 직접 변환할 수 없습니다. UTC 로그가 필요하면 time.time() 또는 UTC datetime을 별도로 기록합니다. 두 시계를 같은 순간에 함께 찍어 utc_anchor + (later_perf - perf_anchor)로 근사 대응할 수는 있지만, 이것은 기준점이 정의된 직접 변환이 아닙니다. 범용 원리와 주의점은 LLM 추론 측정 문서에 정리했습니다.

첫 실행의 메모리 할당과 내부 준비 비용이 측정값을 왜곡하지 않도록 No-cache와 KV Cache 함수를 같은 입력으로 각각 3회 먼저 실행했고, 이 Warm-up 결과는 측정 표본에 포함하지 않았습니다. 이후 각 함수를 10회 실행해 초 단위 표본을 목록에 모은 뒤 평균을 구하고 × 1000으로 Millisecond로 변환했습니다.

고정 조건sshleifer/tiny-gpt2 · CPU · float32 · Prompt "I study" 2 Token · Greedy · 새 Token 20개
Warm-up·반복각 방식 Warm-up 3회 뒤 측정 10회
측정 경계Tokenizer와 최종 문자열 Decode는 제외하고, Python 생성 반복·Model Forward·argmax·torch.cat·Cache 처리를 포함한 함수 전체
방식평균 전체 시간새 Token당 단순 평균
No-cache74.1009 ms3.7050 ms
KV Cache11.6883 ms0.5844 ms

74.1009 ÷ 11.6883 = 6.3397이므로 이 로컬 조건에서는 KV Cache 경로가 약 6.34배 빠르게 측정되었습니다. 출력 Token ID도 계속 일치했으므로 기능 결과를 유지한 채 중복 계산을 줄인 비교입니다.

해석 한계
이 값은 tiny GPT-2·CPU·짧은 단일 Prompt·고정된 실행 순서에서 얻은 첫 기준선입니다. 다른 모델·GPU·Prompt 길이·동시 요청으로 일반화하지 않습니다. 여기의 “새 Token당 단순 평균”은 함수 전체 시간을 20으로 나눈 값이며, Prefill을 분리하는 vLLM의 TPOT와 동일한 지표가 아닙니다.

8. Batch 1과 Batch N

단일 문장의 Cache 흐름을 확인한 다음 길이가 다른 여러 문장을 Batch로 묶습니다. Padding 위치, 문장별 종료 조건, Batch별 Cache Shape과 실제 처리량을 분리해 기록합니다.

9. 완료 증거

  • ● 손코딩 Tiny Decoder와 tiny GPT-2의 Layer·Head 수 차이를 설명했습니다.
  • ● No-cache 모델 입력이 [1,3] → … → [1,12]로 늘어나는 것을 확인했습니다.
  • ● Prompt Token ID [40,2050,13], Logit [1,3,50257], 첫 Layer K·V [1,2,3,1]을 확인하고 각 축을 설명했습니다.
  • ● 새 Token 입력 [1,1]과 과거 Cache를 전달해 Layer 0 Key Cache가 [1,2,2,1] → [1,2,3,1]로 갱신되는 한 Step을 확인했습니다.
  • ● 같은 Prompt·Greedy·생성 길이에서 No-cache와 KV Cache가 동일한 Token ID와 문장을 생성했습니다.
  • ● Cache 반복 루프에서 첫 입력은 [1,2], 이후 입력은 [1,1]이고 Key Cache Token 축이 2 → 6으로 늘어나는 것을 확인했습니다.
  • ● CPU·float32·Prompt 2 Token·새 Token 20개·Warm-up 3회·측정 10회 조건에서 No-cache 74.1009 ms와 KV Cache 11.6883 ms를 비교했습니다.
  • ○ Batch 1과 Batch N에서 처리량·메모리 차이를 기록합니다.
  • ● Model·dtype·Token 길이·장치·Warm-up·측정 경계와 첫 로컬 결과의 일반화 한계를 함께 남겼습니다.
