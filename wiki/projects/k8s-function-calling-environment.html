1. 각 구성 요소의 역할

구성 요소이 프로젝트에서 한 일하지 않는 일
RunPod원격 GPU Pod와 persistent workspace 제공모델 자체나 Function Calling 규칙을 제공하지 않음
NVIDIA RTX A5000 24GBBF16 LoRA 학습과 BF16 추론을 수행도구를 선택하거나 응답을 생성하지 않음
vLLM 0.17.0base·tuned 모델을 메모리에 올리고 HTTP 추론 서버로 제공Kubernetes handler를 실행하지 않음
OpenAI-compatible APIOpenAI SDK가 같은 형식으로 chat.completions.create() 요청을 보냄OpenAI의 외부 호스팅 모델을 사용한다는 뜻이 아님
BF16양자화 없이 모델 행동 변화와 정밀도 손실을 분리LoRA adapter 자체가 아님

2. 요청이 흐르는 경로

RunPod GPU Pod
  ├─ Qwen3-1.7B BF16 base 또는 merged tuned model
  └─ vLLM server
       ↓ OpenAI-compatible HTTP API
OpenAI SDK 평가 코드
       ↓
message.tool_calls 추출
       ↓
score_case() → JSON·Schema·도구명·인자 채점

OpenAI-compatible은 모델 이름이 아니라 API의 요청·응답 모양이다. 따라서 클라이언트 코드는 OpenAI SDK를 사용하지만, 실제 모델 가중치는 RunPod에 올라간 Qwen 모델이다.

3. RunPod에서의 실행 순서

단계실행산출물
검증Schema·데이터·학습 설정 확인검증 통과 로그
Baseline원본 Qwen BF16을 vLLM으로 서빙해 평가base summary와 case별 응답
학습BF16 base를 동결하고 LoRA adapter 학습adapter checkpoint
병합base와 adapter를 BF16 merged model로 결합서빙 가능한 tuned 모델
Tuned같은 holdout·추론 조건으로 재평가tuned summary와 비교 지표
python scripts/validate_training_data.py
python scripts/train_runpod_bf16_lora.py --config configs/runpod_bf16_lora.yaml
python scripts/merge_peft_adapter.py ...
bash scripts/run_runpod_bf16_eval.sh

평가 스크립트는 vLLM의 /health를 확인한 뒤 요청을 보내고, 평가가 끝나면 해당 서버 프로세스를 종료한다. Pod 자체를 중지하는 것과 모델 서버를 종료하는 것은 다른 동작이다.

4. 이 환경을 선택한 이유

로컬과 분리M1 Pro의 메모리·가속기 제약과 학습 환경을 분리하고, 로컬은 문서와 클라이언트 테스트에 집중했다.
같은 APIBase와 Tuned를 동일한 OpenAI SDK·채점 코드로 호출해 모델 변화만 비교했다.
양자화 제외첫 실험에서는 BF16을 사용해 LoRA 효과와 양자화 오차를 섞지 않았다.
재현 가능성모델 revision, Schema, 데이터 checksum, 추론 옵션과 GPU 정보를 함께 기록했다.
