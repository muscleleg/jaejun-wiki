1. 가장 아래에는 바이트가 있다

컴퓨터 저장장치에는 결국 0과 1이 저장된다. 운영체제는 이를 8비트씩 묶은 바이트(byte) 단위로 다룬다. 하지만 수백 GB 디스크 전체를 매 요청마다 처음부터 검색할 수는 없으므로 위치를 번호로 지정해야 한다.

0번째 바이트  1번째 바이트  2번째 바이트  3번째 바이트 ...
00000000      01000001      11110000      00110101
핵심: 저장장치에는 처음부터 파일 이름이나 디렉터리가 새겨져 있는 것이 아니다. 먼저 위치와 데이터만 있다.

2. 블록은 번호가 붙은 저장 위치다

디스크를 일정 크기의 칸들로 나누고 각 칸에 번호를 붙였다고 생각하면 된다. 설명을 단순화하기 위해 한 칸이 4KiB라고 가정한다.

디스크
┌────────────┬────────────┬────────────┬────────────┐
│ 블록 0     │ 블록 1     │ 블록 2     │ 블록 3     │
│ 최대 4KiB  │ 최대 4KiB  │ 최대 4KiB  │ 최대 4KiB  │
└────────────┴────────────┴────────────┴────────────┘

프로그램과 커널은 개념적으로 다음과 같은 요청을 주고받는다.

읽기: “100번 위치부터 일정량을 읽어라.”
쓰기: “500번 위치부터 이 데이터를 기록하라.”

실제 하드웨어 sector, 커널 block, 파일시스템 block은 크기와 의미가 조금씩 다를 수 있다. 지금 단계에서 중요한 것은 디스크가 번호로 지정할 수 있는 위치들의 집합을 제공한다는 점이다.

3. 블록 장치와 /dev

블록 장치는 프로그램이 디스크의 위치를 읽고 쓰도록 Linux가 제공하는 장치 인터페이스다.

/dev/nvme1n1  # NVMe 디스크
/dev/sda      # SCSI/SATA/iSCSI 계열 디스크
/dev/vdb      # VM에 보이는 virtio 디스크
/dev/loop13   # 파일을 디스크처럼 표현하는 loop 장치

/dev/nvme1n1은 사진이나 문서를 담는 일반 파일이라기보다, 프로그램이 NVMe 드라이버에 읽기·쓰기 요청을 전달하는 입구다.

프로그램
  │ “이 위치부터 데이터를 읽어 줘”
  ▼
/dev/nvme1n1
  │ Linux NVMe 드라이버
  ▼
물리 NVMe SSD

3.1 왜 /dev 아래에 파일처럼 보이는가?

Unix는 장치도 파일과 비슷한 open/read/write 인터페이스로 다룬다. 그래서 경로가 있지만 일반 파일과 종류가 다르다. ls -l 첫 글자로 구분할 수 있다.

-rw-r--r-- ... report.txt    # - : 일반 파일
brw-rw---- ... /dev/sda     # b : block device
crw-rw---- ... /dev/kvm     # c : character device
확인할 것: 디스크 장치는 첫 글자가 b다. /dev/kvm처럼 스트림·명령 중심의 장치는 c로 표시될 수 있다.

3.2 major와 minor number

장치 파일의 두 번호 중 major는 어느 커널 드라이버·장치 종류가 처리할지, minor는 그 종류 안의 개별 장치를 구분한다.

brw-rw---- ... 7, 13 ... /dev/loop13
                 │   └─ minor 13: loop 종류 안의 개별 번호
                 └───── major 7: loop 장치 드라이버

lsblk -e7은 major 7인 loop 장치를 출력에서 제외한다. 7번 “한 장치”를 지우는 뜻이 아니다.

4. 파일시스템이 블록을 파일로 바꿔 보여준다

블록 장치 자체는 photo.jpg라는 이름을 모른다. ext4 같은 파일시스템이 디렉터리, 파일 이름, 권한, 시간, 그리고 파일 데이터가 어느 블록에 있는지를 관리한다.

블록 장치의 번호 있는 저장공간
          ↓ ext4가 관리
파일 이름 / 디렉터리 / 권한 / 데이터 위치
          ↓ mount
$HOME/photo.jpg처럼 사용자에게 표시

예를 들어 파일 하나의 데이터가 떨어진 여러 블록에 저장될 수 있다.

photo.jpg
├─ 앞부분 → 블록 100
├─ 중간   → 블록 101
└─ 뒷부분 → 블록 350

ext4 metadata:
“photo.jpg의 데이터는 100, 101, 350에 있다.”

프로그램이 파일을 읽으면 VFS와 ext4가 경로를 해석하고, 해당 블록들을 하위 블록 장치에서 읽어 순서대로 돌려준다.

4.1 프로그램이 파일을 읽을 때 실제로 벌어지는 일

프로그램은 일반적으로 디스크 블록 번호를 알지 못한다. 프로그램이 아는 것은 파일 경로와 파일 내부에서 읽고 싶은 위치다.

open("$HOME/photo.jpg")
read(파일의 현재 위치부터 4096바이트)

개념적으로 프로그램은 다음처럼 요청한다.

“$HOME/photo.jpg를 열어 줘.”
“그 파일의 처음 4KiB를 읽어 줘.”

이 요청은 다음 계층을 순서대로 내려간다.

sequenceDiagram participant P as 프로그램 participant V as Linux VFS participant F as ext4 participant B as Block layer participant D as NVMe driver participant S as 물리 SSD P->>V: open("$HOME/photo.jpg") V->>F: 이 mount의 파일 경로 해석 F->>F: 디렉터리·inode·extent 조회 P->>V: 파일 처음 4096바이트 read V->>F: 파일 offset 0~4095 읽기 F->>B: 대응하는 디스크 위치 읽기 요청 B->>D: block I/O 전달 D->>S: NVMe read 명령 S-->>D: 데이터 반환 D-->>B: 완료된 데이터 B-->>F: 블록 데이터 F-->>V: 파일 내용 V-->>P: 요청한 4096바이트

1단계: 프로그램은 파일 경로를 요청한다

프로그램은 photo.jpg가 SSD의 몇 번째 블록에 있는지 알 필요가 없다. open(), read() 같은 공통 파일 API를 사용한다. 파일의 실제 저장 위치가 바뀌어도 경로와 파일 내용이 같으면 프로그램 코드는 바뀌지 않는다.

2단계: VFS가 담당 파일시스템을 찾는다

VFS(Virtual File System)는 Linux가 프로그램에 제공하는 공통 파일 인터페이스다. 경로가 어느 mount에 속하고 그 mount를 ext4, XFS, NFS 중 어떤 파일시스템이 담당하는지 찾는다.

프로그램의 공통 요청: open(), read(), write()
                  ↓
                 VFS
       ┌──────────┼──────────┐
      ext4       XFS         NFS

그래서 프로그램은 아래 저장소가 ext4인지 네트워크 NFS인지에 따라 완전히 다른 API를 사용할 필요가 없다.

3단계: ext4가 경로와 inode를 찾는다

ext4는 경로를 구성하는 디렉터리를 순서대로 찾고 photo.jpg에 대응하는 inode를 확인한다. inode에는 파일 종류, 크기, 권한, 시간과 데이터 위치를 찾는 metadata가 있다.

$HOME/photo.jpg
  │
  ├─ / 디렉터리에서 home 찾기
  ├─ home에서 dev 찾기
  ├─ dev에서 photo.jpg 이름 찾기
  └─ photo.jpg의 inode 확인

4단계: 파일 내부 위치를 디스크 위치로 변환한다

프로그램은 “파일의 처음 4KiB”처럼 파일 기준 위치(file offset)를 요청한다. ext4는 inode의 extent 정보를 이용해 이 위치가 파일시스템의 어느 블록 범위에 있는지 변환한다.

프로그램 요청
photo.jpg의 offset 0~4095
             ↓ ext4 extent 조회
파일시스템 블록 100에 있음
             ↓
하위 블록 장치의 대응 위치 읽기

여기서 예시의 블록 100은 이해를 위한 가상 번호다. 실제 ext4는 연속 블록 범위를 효율적으로 표현하는 extent와 다양한 metadata 구조를 사용한다.

5단계: block layer와 드라이버가 SSD에 요청한다

ext4가 만든 읽기 요청은 Linux block layer로 내려간다. block layer는 요청을 병합·정렬하거나 장치 queue로 전달하고, NVMe driver는 이를 실제 NVMe 명령으로 변환한다.

ext4의 블록 읽기 요청
        ↓
Linux block layer
        ↓
NVMe driver
        ↓
물리 SSD controller와 flash storage

블록 장치는 데이터가 사진인지, 어느 디렉터리에 속하는지 모른다. 지정된 위치와 길이의 데이터를 읽는 역할만 수행한다.

6단계: 읽은 데이터가 역순으로 돌아온다

물리 SSD
  → NVMe driver
  → block layer
  → ext4
  → VFS
  → 프로그램

ext4는 필요한 블록이 여러 곳에 있다면 읽은 내용을 파일 순서에 맞게 제공한다. 프로그램은 최종적으로 요청한 파일 내용만 받고 아래에서 사용된 블록 번호는 보지 않는다.

핵심 역할 분담:
프로그램은 파일 이름과 파일 내부 위치를 요청한다.
파일시스템은 이를 실제 저장 블록 위치로 변환한다.
블록 계층과 장치 드라이버는 지정된 위치에서 데이터를 읽거나 쓴다.

4.2 파일 쓰기도 같은 구조로 반대로 진행된다

새 데이터를 쓸 때 ext4는 사용 가능한 공간을 찾아 파일의 논리 위치와 실제 블록 위치를 연결하고 inode·extent·여유 공간 metadata를 갱신한다.

프로그램: “photo.jpg에 데이터를 써 줘”
        ↓
VFS와 ext4
        ↓
ext4: 빈 블록 선택 + 파일 metadata 갱신
        ↓
block layer: 선택된 위치에 쓰기 요청
        ↓
드라이버와 SSD: 실제 데이터 기록

따라서 “파일시스템이 몇 번 블록의 데이터를 달라고 한다”는 설명은 개념적으로 맞다. 다만 실제 커널에서는 함수 호출, page cache, block I/O request, 장치 queue 등의 구조가 함께 사용된다.

4.3 한 문장으로 정리

프로그램은 파일시스템 계층에 파일 경로와 파일 내부 위치를 요청하고, 파일시스템은 이를 실제 디스크 위치로 변환해 하위 블록 장치에 읽기·쓰기를 요청한다.

5. 일반 파일은 이미 파일시스템 안에 있다

우리의 cinder_data.img는 처음에는 100GB짜리 일반 파일이다.

물리 Ubuntu NVMe
└─ /dev/nvme1n1p2              블록 장치/파티션
   └─ ext4                      파일시스템
      └─ /                      mount 지점
         └─ var/lib/cinder_data.img  일반 파일

따라서 이 파일에 기록된 데이터는 결국 ext4를 거쳐 Ubuntu NVMe에 저장된다. 하지만 LVM은 보통 일반 파일 경로가 아니라 블록 장치를 입력으로 기대한다.

6. loop 장치: 파일에 블록 장치 입구를 붙인다

loop 드라이버는 일반 파일을 backing store로 삼아 /dev/loopN이라는 블록 장치 인터페이스를 제공한다.

flowchart LR P[프로그램 / LVM] -->|블록 읽기·쓰기| L["/dev/loop13"] L --> D[Linux loop driver] D -->|파일 offset 읽기·쓰기| F["/var/lib/cinder_data.img"] F --> E[ext4] E --> N[Ubuntu NVMe SSD]

loop13에 쓴 데이터가 별도 공간에 복제되는 것은 아니다. loop 드라이버가 블록 위치를 backing file의 offset으로 변환해 같은 파일에 기록한다.

6.1 연결과 확인

sudo losetup --find --show /var/lib/cinder_data.img
sudo losetup -j /var/lib/cinder_data.img
lsblk -o NAME,PATH,TYPE,SIZE,FSTYPE,MOUNTPOINTS
  • --find: 비어 있는 loop 장치를 찾는다.
  • --show: 선택된 /dev/loopN을 출력한다.
  • -j FILE: 해당 backing file에 연결된 loop 장치를 조회한다.

번호를 고정하면 안 된다. 당시 loop0~12가 Snap에 사용돼 loop13이 선택됐지만 다음 부팅에서는 달라질 수 있다.

6.2 loop는 RAM disk가 아니다

구분loop 장치RAM disk/tmpfs
실제 저장 위치backing file이 있는 디스크주로 메모리
재부팅 후 데이터backing file은 유지일반적으로 사라짐
목적파일을 블록 장치처럼 제공메모리를 임시 저장공간으로 제공

7. Snap 때문에 loop 장치가 많은 이유

Snap 패키지는 애플리케이션과 의존 파일을 SquashFS 이미지로 묶는다. snapd는 각 이미지 파일을 loop 장치로 연결하고 읽기 전용으로 마운트한다.

/var/lib/snapd/snaps/firefox_6565.snap
        ↓ /dev/loop3으로 연결
SquashFS 파일시스템
        ↓ mount
/snap/firefox/6565

업데이트 전 revision을 rollback용으로 보관하거나 서로 다른 GNOME runtime을 여러 앱이 요구하면 loop 장치가 여러 개 보인다. 이는 여러 물리 디스크가 생긴 것도, 그 크기만큼 RAM을 항상 점유하는 것도 아니다.

loop0~loop12 → Snap 이미지, 읽기 전용 SquashFS
loop13        → 우리의 Cinder 100GB backing file, LVM PV
주의: Snap이 관리하는 loop를 임의로 losetup -d 하지 않는다. 패키지와 mount 상태를 정리하려면 Snap의 관리 명령을 사용한다.

8. LVM은 블록 장치를 유연한 저장 풀로 만든다

LVM은 물리·가상 블록 장치를 저장 풀로 묶고, 필요한 크기의 논리 장치를 잘라 제공한다.

flowchart LR LOOP["/dev/loop13 100GB"] --> PV[PV
LVM 사용 대상으로 초기화] PV --> VG[VG cinder-volumes
저장공간 풀] VG --> TP[thin pool 약 95GB] TP --> V1[volume UUID
thin LV 1GB] TP --> V2[다른 Cinder volume]
계층의미이 랩의 예
PVLVM이 사용할 수 있게 표시한 블록 장치/dev/loop13
VG하나 이상의 PV를 묶은 저장 풀cinder-volumes
thin pool요청 시 실제 사용량만 할당하는 공간cinder-volumes-pool
LV상위 프로그램에 새 블록 장치처럼 제공되는 논리 볼륨volume-e51a...

1GB thin LV를 만들었다고 즉시 1GB의 실제 데이터가 기록되는 것은 아니다. 논리 크기는 1GB지만, 실제 pool 데이터는 게스트가 쓴 블록만큼 증가한다.

8.1 tmeta, tdata, tpool

  • _tmeta: 어느 블록이 어느 thin LV에 속하는지 기록하는 관리 정보다.
  • _tdata: 실제 사용자 데이터 블록이 저장되는 공간이다.
  • -tpool: metadata와 data를 결합한 LVM 내부 thin pool 장치다.

lsblk 트리에서 동일 pool과 volume이 tmeta와 tdata 아래에 반복돼도 두 벌의 데이터가 생긴 것이 아니다. 하나의 장치가 두 부모 구성요소에 의존하는 관계를 각각 그린 것이다.

호스트 장치 이름과 VM 내부 장치 이름은 관점이 달라서 일치할 필요가 없다. 동일한 Cinder volume이 compute 호스트에서는 /dev/sda로 보이고 VM에는 virtio 장치 /dev/vdb로 전달될 수 있다.

11. 스스로 설명해 보기

  1. 왜 cinder_data.img를 LVM이 바로 사용하지 않고 loop에 연결했는가?
  2. /dev/loop13에 쓴 데이터는 최종적으로 어디에 저장되는가?
  3. lsblk -e7의 7은 장치 번호인가, 장치 종류의 major number인가?
  4. Snap loop와 Cinder loop의 공통점과 차이점은 무엇인가?
  5. 호스트의 /dev/sda와 VM의 /dev/vdb 이름이 달라도 되는 이유는 무엇인가?
최종 핵심: 블록 장치는 번호가 있는 저장 위치에 접근하는 인터페이스이고, 파일시스템은 그 블록을 파일과 디렉터리로 조직한다. loop는 이미 파일시스템 안에 있는 일반 파일에 다시 블록 장치 인터페이스를 붙인다. LVM과 Cinder는 그 인터페이스 위에 저장 풀과 VM용 볼륨을 만든다.
