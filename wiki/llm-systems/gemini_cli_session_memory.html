Gemini CLI는 대화를
어떻게 기억하는가

모델이 스스로 과거를 기억하는 것이 아니다. CLI가 대화와 도구 실행을 기록하고, 현재 유효한 턴을 다음 요청의 contents에 다시 넣기 때문에 작업이 이어지는 것처럼 보인다.

편입 범위와 버전
사용자가 제공한 발표 자료를 읽는 문서로 재구성했다. 분석 기준은 google-gemini/gemini-cli v0.55.1, commit 1ac337739, 2026-08-18이다. 경로·필드·상수·기록 순서는 버전에 따라 바뀔 수 있으며, 원문에 파일·행 단위 출처가 없으므로 현재 버전 사실로 일반화하지 않는다. 공개 문서에서는 사용자 홈 경로를 제품 데이터 디렉터리라는 중립 표기로 바꿨다.

1. 기억하는 주체는 모델이 아니라 CLI다

모델 호출은 각각 독립적이다. Gemini CLI가 이전의 유효한 대화 턴과 도구 결과를 다음 호출에 다시 전달해 연속성을 만든다. 이때 하나의 대화는 목적이 다른 세 구조로 유지된다.

AgentChatHistoryGemini API의 contents에 보낼 현재 대화. 유효한 메시지와 도구 왕복만 추린 모델 입력용 투영이다.
cachedConversation실행 중 CLI가 즉시 조회하는 세션의 현재 상태. 메시지 외에 세션 ID·수정 시각·토큰 사용량·요약 같은 관리 정보도 가진다.
JSONL종료 뒤에도 남는 추가 전용 이벤트 로그. 메시지·메타데이터·$set·$rewindTo를 시간순으로 보존한다.
JSONL                       cachedConversation              AgentChatHistory               Gemini API
무슨 일이 있었나?    →      현재 상태는 무엇인가?    →      모델에 무엇을 보낼까?   →      contents로 다음 응답 생성
디스크 이벤트 로그          로그를 재생한 결과               필요한 턴만 추출

은행 기록에 비유하면 JSONL은 거래 내역, cachedConversation은 거래를 모두 반영한 현재 잔액, AgentChatHistory는 이번 판단에 필요한 부분만 뽑은 자료다. 세 구조는 단순 복사본이 아니라 저장·현재 조회·모델 입력이라는 역할을 나눈다.

2. 세션은 이어서 할 수 있는 하나의 작업 단위다

채팅 한 번이 세션은 아니다. 예를 들어 프로젝트 구조와 인증 코드를 조사하고, 로그인 오류를 수정하고, 테스트까지 실행한 전체가 하나의 세션이다. 종료 뒤 같은 작업을 재개할 수 있도록 대화보다 넓은 범위를 기록한다.

개념범위예시
세션하나의 작업 전체로그인 오류를 찾고 수정하고 테스트한 작업
대화 기록그 작업의 요청·응답·도구 기록작업 중 오간 모든 턴
컨텍스트이번 모델 요청에 실제 전달되는 부분“그럼 수정해줘”를 이해하는 데 필요한 이전 턴
세션 파일종료 뒤 복원에 사용하는 디스크 기록session-….jsonl

세션에는 사용자·모델 메시지와 고유 ID, 도구 이름·인수·상태·결과·호출 ID, 세션 ID·프로젝트·시각, 토큰 사용량·모델·요약·작업 디렉터리 같은 부가 상태가 포함될 수 있다. 대화 전체가 매번 모델에게 전달되는 것은 아니며, 현재 유효하고 필요한 부분만 모델 입력이 된다.

3. 도구 요청은 모델과 CLI의 왕복으로 처리된다

1. CLI가 현재 요청과 이전 대화를 모델에 전달
2. 모델이 functionCall: read_file(auth.ts) 반환
3. CLI가 실제 파일 읽기를 실행하고 결과를 기록
4. functionResponse를 모델에 다시 전달
5. 모델이 실행 결과를 보고 최종 답변 생성

사용자는 한 번 요청했어도 Gemini API 호출은 여러 번 일어날 수 있다. 모델은 필요한 행동을 판단하지만 파일 읽기나 명령 실행을 직접 수행하지 않는다. CLI가 도구 결과를 대화에 추가해 다시 호출해야 모델이 다음 판단을 할 수 있다.

요청 구성역할
contents현재 사용자 턴과 AgentChatHistory에서 가져온 유효한 이전 대화·도구 결과
systemInstructionCLI 역할, 행동 규칙, 프로젝트 환경
tools사용 가능한 도구 이름과 인수 Schema
contents:          [ user: "로그인 오류를 찾아줘" ]
systemInstruction: "코드베이스를 분석하고 안전하게 수정하라…"
tools:             [ read_file, write_file, run_shell, … ]

새 메시지는 먼저 JSONL에 영구 기록되고, cachedConversation에 반영된 뒤, 같은 메시지 ID를 가진 턴이 AgentChatHistory에 추가된다.

msg-001  user    "로그인 오류를 찾아줘"
msg-002  model   functionCall: read_file(auth.ts)
msg-003  user    functionResponse: 파일 내용
msg-004  model   "세션 만료 처리에서 원인을 찾았습니다."
user 역할의 의미
도구 결과가 user 역할인 것은 여기서 user가 반드시 사람만 뜻하지 않기 때문이다. 모델 외부에서 들어온 입력이라는 의미로, functionCall은 model 턴이고 functionResponse는 user 턴이다. 메시지 ID와 호출 ID가 세 구조의 대응 항목을 연결한다.

4. JSONL은 현재 상태가 아니라 발생한 일을 쌓는다

일반 JSON으로 세션 전체를 하나의 완성된 객체로 저장하면 메시지가 추가될 때마다 파일 전체를 다시 써야 한다. JSONL은 한 줄마다 독립된 JSON 객체를 두고 새 메시지나 상태 변경을 파일 끝에 추가한다. 쓰기가 단순하고 중간 이력을 보존하지만, 현재 상태를 알려면 처음부터 끝까지 재생해야 한다.

메타데이터세션 ID·프로젝트·시각
메시지사용자·Gemini·도구 기록
$set일부 필드나 현재 유효한 메시지 목록을 덮어쓰는 체크포인트
$rewindTo지정한 메시지는 유지하고 그 뒤를 현재 대화에서 제외

자료에 제시된 저장 구조를 공개 문서용 중립 경로로 나타내면 다음과 같다.

<Gemini 데이터 디렉터리>/tmp/<프로젝트 식별자>/chats/session-<timestamp>-<id>.jsonl
{"sessionId":"session-123","projectHash":"project-abc","kind":"main"}
{"id":"msg-001","type":"user","content":[{"text":"로그인 오류를 찾아줘"}]}
{"$set":{"lastUpdated":"<timestamp>"}}
{"id":"msg-002","type":"gemini","toolCalls":[{"id":"call-001","name":"read_file","status":"success"}]}
{"id":"msg-003","type":"user","content":[{"functionResponse":{"id":"call-001"}}]}
{"id":"msg-004","type":"gemini","content":[{"text":"원인을 찾았습니다…"}]}

도구 결과는 msg-003의 functionResponse와 msg-002의 toolCalls 결과에 각각 들어가며 call-001 같은 호출 ID로 연결된다. 경로 이름에 tmp가 포함되어도 이 자료의 기준 버전에서는 CLI 종료 뒤 기록이 유지된다.

물리적 기록과 논리적 상태

1줄  msg-001 추가
2줄  msg-002 추가
3줄  msg-003 추가
4줄  {"$set":{"messages":[msg-001, msg-002]}}  ← 현재 유효 목록

물리적 기록:  msg-001 · msg-002 · msg-003 · $set
논리적 상태:  msg-001 · msg-002

파일 중간을 삭제하면 뒷부분을 다시 써야 하고 쓰는 도중 장애에도 취약하다. 그래서 기존 줄을 지우기보다 끝에 상태 변경을 추가한다. 과거 이력은 남아 있어도 현재 대화에서의 유효 여부는 달라질 수 있다.

되감기 기록

1줄  세션 생성
2줄  msg-001
3줄  msg-002
4줄  msg-003
5줄  {"$rewindTo":"msg-002"}  ← msg-002 이후를 무효화
6줄  msg-004                    ← 되감은 지점부터 새 대화

$rewindTo: "msg-002"는 msg-002를 유지하고 그 뒤를 제외한다. 이후 새 메시지는 되감은 지점에서 다른 방향으로 이어진다.

5. 세션 재개는 JSONL을 재생해 메모리 구조를 복원한다

파일 검색
  → 메시지·$set·$rewindTo를 위에서 아래로 재생
  → ConversationRecord 현재 상태 계산
  → cachedConversation 복원
  → 현재 유효한 턴으로 AgentChatHistory 복원
자료에 제시된 명령동작
gemini --resume / latest가장 최근 세션 재개
gemini --resume 5목록 번호로 선택
--session-id <uuid>세션 ID로 직접 지정
--session-file <path>세션 파일로 지정

자료의 기준 버전에서는 resume, session-id, session-file 플래그를 함께 쓰지 않는다. 대상을 하나 선택하면 다음 규칙으로 재생한다.

  1. 세션 ID와 프로젝트 같은 메타데이터로 기본 상태를 구성한다.
  2. 메시지를 ID를 키로 누적하고, 같은 ID가 나오면 최신 내용으로 갱신한다.
  3. $set이 나오면 필드를 덮어쓰고, messages라면 현재 유효 목록을 다시 구성한다.
  4. $rewindTo가 나오면 지정된 메시지 이후를 현재 상태에서 제외한다.

따라서 재개는 단순히 메시지 줄만 모으는 파일 읽기가 아니다. 상태 변경을 시간순으로 적용하는 재생이며, 파일에는 전체 이력이 남아도 복원 결과에는 현재 유효한 메시지만 남는다.

6. 도구 오류는 기록하고, 완성되지 않은 모델 응답은 롤백한다

실패대응대화 상태
모델 응답이 끊김재시도 뒤 해당 요청 턴 롤백이전 상태에서 계속
도구가 오류 반환오류도 모델이 판단할 실행 결과로 전달오류를 포함해 계속
디스크 기록 실패메모리 대화는 가능하지만 재개 기록이 빠질 수 있음주의 필요
재개 중 파일 읽기 실패원본을 보존한 채 복구 경로 시도복구 필요
트랜잭션 경계
대화 롤백은 대화 상태만 되돌린다. 이미 수행된 파일 수정, 셸 명령, 외부 시스템 변경까지 원상복구하는 트랜잭션은 아니다.

모델 응답 최종 실패의 롤백

  1. 요청 전 히스토리 길이와 토큰을 기준점으로 저장한다.
  2. 사용자 턴을 기록한 뒤 모델을 호출한다.
  3. 일시 오류에 대해 재시도한다.
  4. 최종 실패하면 메모리에서 실패한 요청을 제거해 이전 길이로 돌아간다.
  5. JSONL 끝에는 $set을 추가해 실패 전의 유효 메시지 목록을 다시 선언한다.
7줄  user 메시지 msg-005 "그럼 수정해줘"
8줄  {"$set":{"messages":[msg-001, msg-002, msg-003, msg-004]}}
      ↑ 실패 뒤 추가된 체크포인트

이 $set은 기존 줄을 삭제하지 않는다. 현재 유효한 대화가 msg-001~004라고 다시 선언하므로 msg-005는 물리적 이력에는 남지만 재생 결과와 이후 모델 입력에서는 빠진다.

되감기와 롤백

구분되감기롤백
발생 원인사용자가 명시적으로 이전 지점을 선택모델 응답이 끝내 실패
JSONL 표현$rewindTo$set 메시지 체크포인트
목적이전 지점에서 다른 방향의 대화 시작불완전한 요청 턴을 현재 대화에서 제거

예를 들어 세션 만료 문제라고 가정해 조사와 수정까지 했지만 실제 원인이 OAuth 콜백이라면, 잘못된 가정 전으로 되감아 “OAuth 콜백 문제인지 다시 확인해줘”라고 시작할 수 있다. 반면 “그럼 수정해줘”를 기록한 뒤 모델 응답이 최종 실패해 자동으로 요청 전 상태로 돌아가는 것은 롤백이다.

7. 긴 대화는 같은 세션 안에서 압축한다

자료의 기준 커밋에서는 모델 컨텍스트 사용량이 기본 50%에 도달하면 자동 압축을 시도한다. 오래된 약 70%를 하나의 state_snapshot 요약으로 바꾸고 최근 약 30%는 원문으로 유지한다. 다시 기준에 도달하면 기존 요약까지 새 요약에 합쳐 반복한다.

요약 목표 크기는 고정되어 있지 않으며, 새 히스토리가 원래보다 커지면 압축 결과를 적용하지 않는다. /compress는 같은 과정을 수동으로 실행하지만 새 세션을 만들지는 않는다. 세션 ID와 기록 파일은 유지되고 모델 입력만 줄어든다.

구분도구 출력 축약대화 압축
대상50KB를 넘는 도구 출력 한 건오래된 대화 구간
방식원문은 별도 파일, 대화에는 경로 안내과거 대화를 요약으로 대체
목적특정 결과의 크기 제한전체 컨텍스트 크기 제한
여기서 마스킹은 개인정보 비식별화가 아니다.
큰 도구 출력의 원문을 별도 파일로 옮기고, 대화에는 짧은 파일 안내만 남기는 크기 관리다.

8. 서브에이전트는 긴 조사를 별도 세션에서 수행한다

메인 에이전트가 “로그인 오류의 원인을 조사해줘”라고 위임
  → 서브에이전트가 별도 세션에서 인증 파일·로그 조사와 도구 실행
  → “OAuth 콜백의 state 검증 누락이 원인”이라는 요약 반환
  → 메인 에이전트가 요약을 바탕으로 수정과 테스트 계속

메인 에이전트는 사용자와의 핵심 대화와 전체 작업 흐름을 유지한다. 서브에이전트는 긴 조사 과정을 별도 기록에 남기고 작업을 이어가는 데 필요한 결론만 메인 컨텍스트로 돌려준다.

<Gemini 데이터 디렉터리>/tmp/<프로젝트>/chats/
└── <메인 에이전트 세션 ID>/
    └── <서브에이전트 세션 ID>.jsonl

자료의 기준 구현에서는 서브에이전트 세션이 메인 세션 아래에 저장되며, 메인 세션을 삭제하면 연결된 서브에이전트 세션 디렉터리도 함께 정리된다.

9. 전체 생명주기와 운영 경계

생성                    실행                    관리                 종료                  재개·삭제
세션 ID·프로젝트 연결 → 대화·도구 결과 기록 → 압축·자식 세션 → 메모리는 사라짐 → JSONL 재생 또는 명시적 정리
                                                                    JSONL은 유지

종료 뒤 JSONL이 남고, 재개하면 이를 재생해 cachedConversation과 AgentChatHistory를 다시 만든다. JSONL은 프로세스 종료 전과 재개 후를 잇는 연결 고리다.

디스크 사용량JSONL과 큰 도구 출력 파일이 여러 프로젝트에 누적될 수 있다.
민감한 정보입력·응답·도구 인수·결과가 로컬 기록에 남을 수 있으므로 별도 정리·보호 정책이 필요하다.
버전 의존성경로·필드·상수·기록 순서는 Gemini CLI 구현 버전에 따라 달라질 수 있다.

여기서 “영구 저장”은 CLI 프로세스가 끝나도 디스크에 남는다는 의미이지 삭제할 수 없다는 의미가 아니다. 자료에서 확인한 범위에는 자동 삭제 정책이 없으며, 삭제는 세션 파일·연결 산출물·자식 세션을 명시적으로 정리한다. 파일 권한·암호화·비밀값 필터링 정책은 원자료의 조사 범위 밖이므로 보호 수준을 단정하지 않는다.

10. 세 가지 질문으로 정리

누가 기억하는가?모델이 아니라 CLI가 대화와 도구 기록을 관리하고, 다음 호출 때 필요한 내용을 다시 전달한다.
어디에 저장되는가?실행 중에는 AgentChatHistory와 cachedConversation, 종료 뒤에는 JSONL에 남는다.
어떻게 이어지는가?세션을 재개하면 JSONL을 순서대로 재생해 현재 상태와 모델 입력용 대화를 다시 만든다.
Gemini CLI의 기억은 “대화를 저장하고 → 상태 변경을 적용해 현재 상태를 계산하고 → 필요한 내용을 모델에게 다시 전달하는 과정”이다.
