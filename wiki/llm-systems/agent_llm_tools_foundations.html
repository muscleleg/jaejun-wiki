ChatCompletion · n · Sampling · Temperature 정리

1️⃣ ChatCompletion이란?

  • LLM에게 메시지 구조(system/user/assistant) 형태로 질의를 보내는 방식이다.
  • 모델은 “다음에 올 말을 완성”하는 방식으로 응답을 생성한다.

2️⃣ n의 의미

  • n은 생성 결과 개수를 의미한다.
  • 같은 입력에 대해 생성 과정을 n번 수행한다.
  • response.choices 배열 길이 = n

중요:

  • n은 sampling을 켜는 옵션이 아니다.
  • sampling 여부는 temperature(및 top_p)가 결정한다.

3️⃣ LLM이 답변을 생성하는 과정

모델 내부 흐름:

  1. 각 토큰 후보에 대해 logits(점수) 계산
  2. softmax를 통해 확률 분포 생성
  3. 그 확률 분포에서 다음 토큰 선택
  4. 문장이 끝날 때까지 반복

4️⃣ Sampling vs Greedy

🔹 Greedy 방식

  • 가장 높은 확률 토큰을 선택
  • 항상 동일한 결과

🔹 Sampling 방식

  • 확률 비율대로 랜덤 선택
  • 결과가 달라질 수 있음

ChatCompletion은 기본적으로 확률 기반 생성 구조이며,

temperature 설정에 따라 greedy처럼도, sampling처럼도 동작할 수 있다.

5️⃣ Temperature의 역할

공식:

P(token) = softmax(logits / T)

🔹 T = 1

  • 기본 확률 분포 유지

🔹 T → 0 (0에 가까울수록)

  • logits 값 차이가 크게 반영됨
  • 확률 분포가 뾰족해짐
  • 거의 greedy처럼 동작

🔹 T > 1

  • logits 값 차이가 완화됨
  • 확률 분포가 평평해짐
  • 다양성 증가

중요:

  • temperature는 확률 자체를 곱하는 게 아니라
  • softmax 전에 logits를 스케일링하는 역할을 한다.
  • 확률의 “순위”를 바꾸는 것이 아니라
  • 확률 “격차”를 조절하는 것이다.

15.2 조건부 엣지 기반 청크 요약 그래프

수정 목적

  • 긴 전사문을 여러 청크로 나눠 요약하는 구조를 만듭니다.
  • LangGraph의 add_conditional_edges와 Send를 이용한 동적 분기를 학습합니다.

핵심 개념

  • Send: 같은 노드를 여러 번 호출하도록 작업 단위를 전달합니다.
  • add_conditional_edges: 상태에 따라 다음 노드 수를 동적으로 결정합니다.
  • Annotated[list[str], operator.add]: 여러 청크 요약 결과를 summaries에 누적합니다.

핵심 변경사항 요약

  1. summaries reducer 필드를 상태에 추가했습니다.
  2. 전사문을 500자 단위로 나누는 dispatch_summarizers를 만들었습니다.
  3. summarize_chunk와 조건부 엣지로 동적 요약 그래프를 완성했습니다.

시스템 구조

video.mp4
  ↓
extract_audio
  ↓
transcribe_audio
  ↓
dispatch_summarizers
  ↓
summarize_chunk x N
  ↓
summaries 누적

전체 코드(최종본)

import operator, textwrap
from langgraph.graph import END, START, StateGraph
from langgraph.types import Send
from typing import TypedDict
from typing_extensions import Annotated
from langchain.chat_models import init_chat_model

llm = init_chat_model("openai:gpt-4o-mini")

class State(TypedDict):
    video_file: str
    audio_file: str
    transcription: str
    summaries: Annotated[list[str], operator.add]

def dispatch_summarizers(state: State):
    transcription = state["transcription"]
    chunks = []
    for i, chunk in enumerate(textwrap.wrap(transcription, 500)):
        chunks.append({"id": i + 1, "chunk": chunk})
    return [Send("summarize_chunk", chunk) for chunk in chunks]

def summarize_chunk(chunk):
    response = llm.invoke(f"Please summarize the following text.\n\nText: {chunk['chunk']}")
    return {"summaries": [f"[Chunk {chunk['id']}] {response.content}"]}

import openai, json
from openai.types.chat import ChatCompletionMessage

client  = openai.OpenAI()
messages = []
def get_weather(city):
    return f"The weather in {city} is sunny"

FUNCTION_MAP = {
    "get_weather": get_weather
}

TOOLS = [
    {
        "type": "function",
        "function":{
            "name": "get_weather",
            "description": "A function to get the weather of a city",
            "parameters":{
                "type": "object",
                "properties":{
                    "city":{
                        "type": "string",
                        "description": "The name of the city to get the weather of"
                    }
                },
                "required": ["city"]
            }
        }
    }
]
def process_ai_response(message:ChatCompletionMessage):
    if message.tool_calls:
        messages.append(
            {
                "role": "assistant",
                "content": message.content or "",
                "tool_calls":[
                    {
                        "id": tool_call.id,
                        "type": "function",
                        "function":{
                            "name": tool_call.function.name,
                            "arguments": tool_call.function.arguments
                        }
                    } for tool_call in message.tool_calls
                ]
            }
        )
        for tool_call in message.tool_calls:
            function_name = tool_call.function.name
            arguments = tool_call.function.arguments
            print(f"Calling function:: {function_name} with {arguments}")
            try:
                arguments = json.loads(arguments)
            except json.JSONDecodeError:
                arguments = {}

            function_to_run = FUNCTION_MAP.get(function_name)

            result = function_to_run(**arguments)

            print(f"Ran {function_name} with args {arguments} for a result of {result}")

            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "name": function_name,
                "content": result
            })
        call_ai()
    else:
        content = message.content or ""
        messages.append({
            "role": "assistant", # 모델이 한말이라서 assistant
            "content": content
        })
        print(f"AI: {content}")


def call_ai():
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=messages,
        tools=TOOLS
    )
    process_ai_response(response.choices[0].message)


while True:
    message = input("Send a message to the LLM...")
    if message == "quit" or message =="q":
        break
    else:
        messages.append({
            "role": "user",
            "content": message
        })

        print(f"User: {message}")
        call_ai()

  1. 사용자가 메시지를 입력
  2. messages 전체를 LLM에게 전달
  3. LLM이
  • 그냥 답변하거나
  • tool을 호출해야 한다고 판단하면 tool_calls를 반환
  1. tool_calls가 있으면
  • 파이썬에서 해당 함수 실행
  • 실행 결과를 다시 messages에 추가
  • 그 상태로 다시 LLM 호출
  1. 최종 자연어 답변 출력

즉,

LLM이 “생각 → Tool 요청 → 실행 → 결과 전달 → 최종 응답 생성”

LLM은 이 정의를 보고

“아, 날씨 물어보면 get_weather를 쓰면 되겠네”

라고 판단합니다.

Agent와 Tool의 차이 및 Agent를 Tool로 변환할 수 있는 이유

1. Agent와 Tool의 근본적인 차이

Agent와 Tool은 역할이 완전히 다르다.

핵심 차이는 다음과 같다.

Agent = 판단하고 계획하는 주체
Tool  = 실행만 수행하는 기능

즉

Agent → 무엇을 해야 하는지 결정한다
Tool  → 주어진 작업을 수행한다

2. Tool의 구조

Tool은 기본적으로 함수(Function)이다.

구조

input parameters
    ↓
function execution
    ↓
output result

예시

def get_weather(city: str) -> str:
    ...

LLM은 Tool을 다음과 같은 형태로 인식한다.

{
  "tool": "get_weather",
  "city": "Seoul"
}

즉 Tool은 명확한 입력 파라미터와 실행 로직을 가진 함수이다.

Tool의 특징

1. 판단 능력이 없다
2. 입력을 받아 실행만 한다
3. 결과를 반환한다

3. Agent의 구조

Agent는 LLM 기반의 문제 해결 주체이다.

Agent는 다음 역할을 수행한다.

문제 이해
↓
판단
↓
계획
↓
Tool 선택
↓
응답 생성

Agent의 기본 구조

message
   ↓
LLM reasoning
   ↓
response

실행 예시

Runner.run(agent, message)

Agent의 특징

1. 상황을 이해한다
2. 어떤 Tool을 사용할지 판단한다
3. 다른 Agent에게 작업을 넘길 수도 있다
4. 최종 응답을 생성한다

즉 Agent는 AI Worker라고 볼 수 있다.

4. Agent와 Tool의 관계

Agent 시스템의 일반적인 구조는 다음과 같다.

User
 ↓
Agent
 ↓
Tool
 ↓
Agent
 ↓
User

예시

User: 서울 날씨 알려줘

Agent 판단
→ weather tool 호출

Tool 실행
→ 결과 반환

Agent
→ 결과 설명

즉 Tool은 Agent가 사용하는 실행 도구이다.

5. Agent를 Tool로 변환할 수 있는 이유

OpenAI Agents SDK에서는 다음 기능이 제공된다.

agent.as_tool()

이 기능은 Agent를 Tool 인터페이스로 변환하는 wrapper이다.

핵심 아이디어는 다음과 같다.

Agent 실행 = Runner.run(agent, input)

이를 함수 형태로 감싸면 Tool이 된다.

개념적 구현

def agent_tool(input: str):

    result = Runner.run(agent, input)

    return result.final_output

즉 Agent 실행을

input → Agent 실행 → output

형태의 함수로 변환한 것이다.

따라서 Tool 인터페이스로 사용할 수 있다.

6. Agent Tool의 구조

Agent를 Tool로 변환하면 구조는 다음과 같다.

input string
   ↓
Agent 실행
   ↓
LLM reasoning
   ↓
response

즉 Tool 인터페이스 기준으로 보면

input: string
output: string

이다.

따라서 LLM은 이 Agent Tool을 일반 Tool처럼 사용할 수 있다.

  • 이전 요청을 기억하지 않는다

2️⃣ 당신이 작성한 샘플 코드

import openai

client  = openai.OpenAI()
messages = []

def call_ai():
    response = client.chat.completions.create(
        model="gpt-5-nano",
        messages=messages
    )
    message = response.choices[0].message.content
    messages.append({
        "role": "assistant",  # 모델이 한 말이라서 assistant
        "content": message
    })
    print(f"AI: {message}")

while True:
    message = input("Send a message to the LLM...")
    if message == "quit" or message =="q":
        break
    else:
        messages.append({
            "role": "user",
            "content": message
        })

        print(f"User: {message}")
        call_ai()

개념 → 전체 코드 → 실행 흐름 → 내부 동작 → 확장 포인트 순서로 정리한다.

1. 전체 코드

아래는 강의에서 사용한 구조를 정리한 전체 예시 코드다.

from agents import Agent, Runner, function_tool, SQLiteSession

# 세션 생성 (user_2라는 사용자 ID 사용)
session = SQLiteSession("user_2", "ai-memory.db")


# Tool 정의
@function_tool
def get_weather(city: str):
    """Get weather by city"""
    return "30 degrees"


# Agent 생성
agent = Agent(
    name="Assistant Agent",
    instructions="You are a helpful assistant. Use tools when needed to answer questions",
    tools=[get_weather]
)


# Agent 실행
result = await Runner.run(
    agent,
    "what's the weather in the country i live in?",
    session=session,
)

print(result.final_output)


# 세션에 직접 메시지 추가
await session.add_items(
    [
        {"role": "user", "content": "My name is John Doe"}
    ]
)

# 마지막 메시지 제거
await session.pop_item()

# 세션 초기화 (필요 시)
# await session.clear_session()

2. 구성 요소 정리

이 코드는 4개의 핵심 구성 요소로 이루어진다.

1️⃣ Tool

@function_tool
def get_weather(city: str):

역할:

  • LLM이 호출할 수 있는 외부 함수
  • 내부적으로 JSON schema로 변환됨
  • 매 요청마다 LLM에 함께 전달됨

중요:

LLM은 tool을 기억하지 않는다.

매 호출마다 tool schema가 함께 전송된다.

2️⃣ Agent

agent = Agent(...)

역할:

  • system instructions 보관
  • tool 목록 보관
  • 역할 정의

Agent는 상태를 저장하지 않는다.

3️⃣ SQLiteSession

session = SQLiteSession("user_2", "ai-memory.db")

역할:

  • 대화 기록 저장
  • user_id 단위로 구분
  • DB 파일에 저장됨

이 객체가 메모리를 담당한다.

4️⃣ Runner

await Runner.run(...)

역할:

  • session에서 과거 대화 불러오기
  • messages 배열 구성
  • tools 포함
  • LLM 호출
  • 응답을 다시 session에 저장

외부 학습자료 기반 개인 재구성 원문

OpenAI SDK vs LangChain

RAG 및 Agent 구현 방식 비교 분석 (샘플 코드 포함)

1️⃣ 왜 이 비교가 중요한가?

LLM 기반 시스템을 만들 때 우리는 보통 두 가지 선택지를 가진다.

  1. OpenAI SDK만 사용해서 직접 구현
  2. LangChain 같은 프레임워크를 사용

강사들이 종종 이렇게 말한다:

“OpenAI SDK만으로도 충분하다.”

이 말의 의미를 정확히 이해하려면

두 방식의 차이를 구조적으로 비교해봐야 한다.

2️⃣ OpenAI SDK만으로 RAG 직접 구현하기

아래는 매우 단순화된 RAG 예제다.

(벡터 DB 대신 numpy 기반 유사도 계산으로 구조만 보여준다.)

✅ OpenAI SDK 기반 RAG 예제

from openai import OpenAI
import numpy as np
import json

client = OpenAI()

# 1️⃣ 문서 데이터
documents = [
    "Paris is the capital of France.",
    "Berlin is the capital of Germany.",
    "Madrid is the capital of Spain."
]

# 2️⃣ 임베딩 생성 함수
def embed(text):
    response = client.embeddings.create(
        model="text-embedding-3-small",
        input=text
    )
    return np.array(response.data[0].embedding)

# 3️⃣ 문서 임베딩 미리 생성
doc_embeddings = [embed(doc) for doc in documents]

# 4️⃣ 간단한 유사도 검색 함수
def search(query):
    query_embedding = embed(query)
    similarities = [
        np.dot(query_embedding, doc_embedding)
        for doc_embedding in doc_embeddings
    ]
    best_idx = np.argmax(similarities)
    return documents[best_idx]

# 5️⃣ 질문 처리
question = "What is the capital of Spain?"

context = search(question)

prompt = f"""
Use the following context to answer the question.

Context:
{context}

Question:
{question}
"""

response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "user", "content": prompt}
    ]
)

print(response.choices[0].message.content)

🔎 이 코드에서 네가 직접 구현한 것

  • 임베딩 호출
  • 벡터 저장
  • 유사도 계산
  • 문서 선택
  • Prompt 조합
  • LLM 호출
  • 응답 처리

즉, 오케스트레이션을 전부 직접 설계했다.

3️⃣ LangChain으로 같은 RAG 구현하기

이제 같은 구조를 LangChain으로 구현해보자.

✅ LangChain 기반 RAG 예제

from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain.vectorstores import FAISS
from langchain.chains import RetrievalQA
from langchain.docstore.document import Document

# 1️⃣ 문서 생성
docs = [
    Document(page_content="Paris is the capital of France."),
    Document(page_content="Berlin is the capital of Germany."),
    Document(page_content="Madrid is the capital of Spain.")
]

# 2️⃣ 임베딩 + 벡터스토어
embeddings = OpenAIEmbeddings()
vectorstore = FAISS.from_documents(docs, embeddings)

# 3️⃣ Retriever 생성
retriever = vectorstore.as_retriever()

# 4️⃣ LLM
llm = ChatOpenAI(model="gpt-4o-mini")

# 5️⃣ 체인 구성
qa_chain = RetrievalQA.from_chain_type(
    llm=llm,
    retriever=retriever
)

# 6️⃣ 질문 실행
result = qa_chain.run("What is the capital of Spain?")

print(result)

🔎 LangChain이 대신해준 것

  • 임베딩 생성
  • 벡터 저장
  • 유사도 계산
  • Retriever 구성
  • Prompt 자동 구성
  • LLM 호출
  • 결과 처리

즉, 많은 오케스트레이션을 추상화해줬다.

4️⃣ 차이점 비교

구분 OpenAI SDK LangChain
오케스트레이션 직접 설계 프레임워크가 처리
내부 구조 이해 매우 높음 추상화됨
개발 속도 느림 빠름
유연성 매우 높음 구조 제약 존재
디버깅 명확 추상화로 복잡

5️⃣ “SDK만으로 충분하다”의 진짜 의미

이 말은:

  • SDK가 더 쉽다는 뜻이 아니다.
  • LangChain이 쓸모없다는 뜻도 아니다.

의미는 이거다:

OpenAI SDK가 충분히 강력해졌기 때문에

기본적인 Agent / RAG 구조는 직접 구현 가능하다.

요즘 SDK는:

  • function calling
  • structured output
  • streaming
  • tool orchestration

을 기본 제공한다.

즉, 프레임워크 없이도 설계 가능하다는 뜻이다.

6️⃣ 구조적 관점에서의 이해

OpenAI SDK는:

“수동 변속기”

LangChain은:

“자동 변속기”

수동은 복잡하지만 구조를 이해하게 해준다.

자동은 편하지만 내부가 보이지 않는다.

7️⃣ 학습 전략 제안

지금 너 상황에서 가장 좋은 전략은:

1️⃣ SDK로 한 번 직접 구현해보기

2️⃣ 그 다음 LangChain 다시 보면 내부가 보임

3️⃣ 필요한 부분만 프레임워크 활용

이 순서가 가장 건강하다.

🎯 최종 정리

OpenAI SDK는 설계자의 도구다.

LangChain은 생산성을 높여주는 도구다.

강사가 말한 “SDK만으로 충분하다”는 의미는:

프레임워크 없이도

LLM 시스템을 설계할 수 있다.

라는 뜻이다.

외부 학습자료 기반 개인 재구성 원문

Tool 기반 Agent 내부 실행 구조 분석

1️⃣ 전체 코드

아래 코드는 Tool 기반 Agent가 내부적으로 어떻게 동작하는지를

스트리밍 이벤트 단위로 관찰하기 위한 예제다.

from agents import Agent, Runner, function_tool

@function_tool
def get_weather(city: str):
    """Get weather by city"""
    return "30 degress"

agent = Agent(
    name="Assistant Agent",
    instructions="You are a helpful assistant. Use tools when needed to answer questions",
    tools=[get_weather]
)

stream = Runner.run_streamed(
    agent,
    "Hello how are you? what is the weather in Spain?"
)

message = ""
args = ""

async for event in stream.stream_events():

    if event.type == "raw_response_event":
        event_type = event.data.type

        if event_type == "response.output_text.delta":
            message += event.data.delta
            print(message)

        elif event_type == "response.function_call_arguments.delta":
            args += event.data.delta
            print(args)

이 코드는 단순 날씨 예제가 아니다.

Tool 기반 Agent의 내부 실행 구조를 해부하기 위한 코드다.

2️⃣ Tool 호출은 어떻게 시작되는가?

사용자가 질문을 입력하면:

Hello how are you? what is the weather in Spain?

LLM은 먼저 판단한다.

  • 일반 텍스트 응답이 필요한가?
  • Tool 호출이 필요한가?

이 경우 LLM은 Tool 호출이 필요하다고 판단한다.

3️⃣ Tool 호출 시 실제 이벤트 구조

Tool 호출이 발생하면 다음과 같은 완전한 이벤트 구조가 등장한다.

{
  "type": "run_item_stream_event",
  "item": {
    "type": "tool_call_item",
    "raw_item": {
      "type": "function_call",
      "name": "get_weather",
      "arguments": ""
    }
  }
}

계층 구조 설명

  • type: 전체 이벤트 타입 (run_item_stream_event)
  • item.type: Tool 호출 아이템 (tool_call_item)
  • raw_item.type: 실제 호출 타입 (function_call)
  • raw_item.name: 호출할 함수 이름 (get_weather)
  • raw_item.arguments: 현재는 빈 문자열 (아직 인자 생성 전)

이 시점에서 이미 모델은:

“이 질문에는 get_weather를 호출해야 한다”

라고 결정했다.

4️⃣ arguments는 어떻게 생성되는가?

arguments는 한 번에 완성된 JSON으로 오지 않는다.

토큰 단위로 스트리밍된다.

다음과 같은 이벤트들이 순차적으로 들어온다.

{
  "type": "raw_response_event",
  "data": {
    "type": "response.function_call_arguments.delta",
    "delta": "{"
  }
}
{
  "type": "raw_response_event",
  "data": {
    "type": "response.function_call_arguments.delta",
    "delta": "\"city\""
  }
}
{
  "type": "raw_response_event",
  "data": {
    "type": "response.function_call_arguments.delta",
    "delta": ": \"Spain\"}"
  }
}

이렇게 이어져 최종적으로:

{"city": "Spain"}

이라는 JSON이 완성된다.

중요한 점:

  • 함수 이름은 이미 결정됨
  • 지금은 그 함수에 넣을 인자를 생성하는 단계
  • 이것도 일반 텍스트 생성과 동일한 메커니즘

5️⃣ Tool 실행 결과 이벤트

arguments가 완성되면 Runner가 실제 함수를 실행하고,

그 결과가 다음과 같이 이벤트로 들어온다.

{
  "type": "run_item_stream_event",
  "item": {
    "type": "tool_call_output_item",
    "output": "30 degress"
  }
}

이 "output"은 실제 Python 함수 실행 결과다.

6️⃣ 그럼 누가 실행하는가?

여기서 가장 중요한 구분이 나온다.

모델은 절대 Python 함수를 실행하지 않는다.

모델이 생성한 전체 구조는 다음과 같다:

{
  "type": "run_item_stream_event",
  "item": {
    "type": "tool_call_item",
    "raw_item": {
      "type": "function_call",
      "name": "get_weather",
      "arguments": "{\"city\": \"Spain\"}"
    }
  }
}

이건 어디까지나 텍스트(JSON)다.

7️⃣ Runner 내부에서 실제로 벌어지는 일

Runner.run_streamed() 내부에서는 다음 단계가 자동으로 수행된다.

  1. run_item_stream_event 감지
  2. item.type == "tool_call_item" 확인
  3. raw_item.type == "function_call" 확인
  4. raw_item.name으로 tool 목록 매칭
  5. raw_item.arguments를 JSON으로 파싱
  6. 실제 Python 함수 실행

개념적으로는 이런 코드가 실행된다:

tool = tools[raw_item["name"]]
parsed_args = json.loads(raw_item["arguments"])
result = tool(**parsed_args)

즉,

  • 모델은 실행하지 않는다
  • Runner가 실행한다
  • 실행은 로컬 Python 프로세스에서 일어난다

8️⃣ 자동 실행인가?

질문:

argument를 받으면 SDK가 자동으로 실행하도록 설계된 것인가?

정확한 답:

  • OpenAI 모델은 실행하지 않는다
  • OpenAI SDK도 실행하지 않는다
  • agents 라이브러리의 Runner가 function_call을 감지하면 자동으로 실행하도록 설계되어 있다

구조는 다음과 같다:

사용자 질문
    ↓
LLM이 function_call JSON 생성
    ↓
Runner가 이벤트 감지
    ↓
JSON 해석
    ↓
로컬 Python 함수 실행
    ↓
결과를 다시 LLM에 전달
    ↓
최종 텍스트 생성

자동 실행은 모델의 능력이 아니라

오케스트레이터(Runner)의 설계된 동작이다.

9️⃣ 전체 구조 요약

Tool 기반 Agent는 다음과 같은 파이프라인이다.

추론 (LLM)
    ↓
function_call JSON 생성
    ↓
오케스트레이션 (Runner)
    ↓
Python 함수 실행
    ↓
결과 전달
    ↓
최종 응답 생성 (LLM)

LLM은 두뇌

Runner는 집행자

이다.

🎯 최종 결론

Tool 기반 Agent의 내부 실행 구조는 다음과 같다:

LLM이 전체 function_call 이벤트 구조를 생성하고

Runner가 그것을 해석해

로컬 Python 함수를 실행한다.

모델은 실행하지 않는다.

Runner가 실행한다.

0️⃣ 먼저 반드시 알아야 할 기본 개념

중요: Crew가 시작되면 등록된 Task는 모두 실행됩니다.

  • assemble_crew()에서 tasks=self.tasks로 등록된 Task는
  • kickoff()가 호출되면 순서대로 전부 실행됩니다.
  • Tool은 “조건부 실행”이지만

Task는 무조건 실행됩니다.

이걸 헷갈리면 전체 구조가 무너집니다.

정리하면:

  • Task → 항상 실행
  • Tool → Agent가 호출해야 실행

1️⃣ Tool이 뭔가

Tool은:

Agent가 Task를 수행하는 도중 필요할 때 호출하는 함수

구조는 이렇게 이해하면 정확합니다:

Task (해야 할 일)
   ↓
Agent (수행자)
   ↓
Tool (필요하면 호출하는 함수)

Tool은 자동 실행이 아닙니다.

Agent가 판단해서 호출해야 실행됩니다.

2️⃣ Tool 샘플 (tools.py)

from crewai.tools import tool

@tool
def count_letters(sentence: str) -> int:
    return len(sentence)

여기서 @tool 데코레이터는

  • 이 함수를 “LLM이 호출 가능한 함수”로 등록
  • LLM이 function-calling 방식으로 호출 가능하게 만듦

3️⃣ Agent에 Tool 붙이는 샘플 (네 코드 구조)

Tool은 Task가 아니라 Agent에 붙습니다.

import dotenv
dotenv.load_dotenv()

from crewai import Crew, Agent, Task
from crewai.project import CrewBase, agent, task, crew
from tools import count_letters

@CrewBase
class TranslateCrew:
    @agent
    def translator_agent(self):
        return Agent(
           config=self.agents_config["translator_agent"]
        )

    @agent
    def counter_agent(self):
        return Agent(
           config=self.agents_config["counter_agent"],
           tools=[count_letters],   # 🔥 Tool은 여기 붙는다
        )

    @task
    def translate_task(self):
        return Task(
            config=self.tasks_config["translate_task"]
        )

    @task
    def retranslate_task(self):
        return Task(
            config=self.tasks_config["retranslate_task"]
        )

    @task
    def counter_task(self):
        return Task(
            config=self.tasks_config["counter_task"]
        )

    @crew
    def assemble_crew(self):
        return Crew(
            agents=self.agents,
            tasks=self.tasks,
            verbose=True
        )

TranslateCrew().assemble_crew().kickoff(
    inputs={"sentence": "Hello, how are you? \nI'm fine, thank you!"}
)

4️⃣ 실행 흐름을 정확히 이해하기

kickoff()가 호출되면:

  1. translate_task 실행
  2. retranslate_task 실행
  3. counter_task 실행

→ 등록된 Task는 모두 실행됨

여기서 중요한 점:

  • counter_task는 tasks.yaml에서

agent: counter_agent로 연결되어 있음

  • counter_agent는 tools=[count_letters]가 붙어 있음

그래서 실행 흐름은 이렇게 됩니다:

counter_task 실행
   ↓
counter_agent가 수행
   ↓
필요하다고 판단하면 count_letters() 호출

5️⃣ Task는 Tool을 모른다 (중요)

Task는 Tool을 직접 호출하지 않습니다.

Task는 단지:

  • “무슨 일을 해야 하는지”
  • “누가 수행하는지”

만 정의합니다.

Tool 실행 여부는 전적으로 Agent의 판단입니다.

6️⃣ Tool은 언제 실행되나?

counter_task가 실행된다고 해서

count_letters가 무조건 실행되지는 않습니다.

LLM은 이런 상황입니다:

  • Task 설명을 읽고
  • Tool이 목록에 있는 걸 보고
  • “이걸 써야겠다” 판단하면 호출

만약 반드시 Tool을 쓰게 만들고 싶다면

tasks.yaml의 description에 이렇게 적어야 합니다:

You MUST use the count_letters tool.
Do not guess the answer.

LLM에게 “추론하지 말고 함수 호출해라”라고 강제해야 합니다.

7️⃣ inputs는 어디에 쓰이나?

kickoff(inputs={"sentence": ...})

이 값은:

  • \{sentence\}로 Task description에 치환됨
  • Tool 호출 인자로도 전달될 수 있음

즉:

  • LLM prompt에도 들어가고
  • Tool argument에도 사용됨

🔥 전체 구조 핵심 요약

반드시 기억해야 할 것

  1. Task는 kickoff 시 모두 실행된다
  2. Tool은 Agent에 붙는다
  3. Tool은 Agent가 호출해야 실행된다
  4. Task는 Tool을 모른다
  5. Tool 강제 사용은 prompt로 제어한다

1️⃣ 왜 Permission denied가 뜨는가?

.venv/bin/activate는 보통 실행 권한(x) 이 없어.

확인해보면:

ls -l .venv/bin/activate

아마 이런 식일 거야:

-rw-r--r--

여기엔 x가 없지?

쉘은 파일을 직접 실행하려면 실행 권한이 필요해.

그래서:

.venv/bin/activate

→ 실행 시도

→ 실행 권한 없음

→ Permission denied

2️⃣ source는 왜 되는가?

source는 파일을 실행하는 게 아니라 읽어서 현재 쉘에 적용하는 거야.

즉,

source .venv/bin/activate

는

이 파일 안에 있는 내용을 내 현재 쉘에 붙여넣어서 실행해줘

라는 의미야.

그래서 실행 권한이 필요 없어.

읽기 권한(r)만 있으면 돼.

3️⃣ activate는 왜 원래 source로 써야 할까?

activate는 내부에서 이런 걸 해:

export VIRTUAL_ENV=...
export PATH=...

이걸 현재 쉘 환경에 적용해야 의미가 있어.

만약 실행 파일처럼 따로 실행되면:

  • 새로운 서브쉘에서 실행되고
  • 끝나면 사라짐
  • 내 현재 쉘에는 적용 안 됨

그래서 원래부터 이렇게 쓰는 게 정석이야:

source .venv/bin/activate

또는

. .venv/bin/activate

LangChain 핵심 정리: PromptTemplate vs ChatPromptTemplate

1. PromptTemplate — 단일 문자열 프롬프트

  • 텍스트 기반 LLM (OpenAI, GPT)에게 문자열을 전달할 때 사용
  • 변수 삽입 가능
from langchain.prompts import PromptTemplate

template = PromptTemplate.from_template("What is the capital of {country}?")
prompt = template.format(country="Japan")
print(prompt)
# 출력: What is the capital of Japan?

2. ChatPromptTemplate — 역할 기반 대화 메시지

  • Chat 모델 (ChatOpenAI) 전용
  • 메시지를 역할(role) 기반으로 구성 (system, ai, human 등)
from langchain.prompts import ChatPromptTemplate

template = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant who speaks only in {language}."),
    ("ai", "Nice to meet you! My name is {name}."),
    ("human", "Can you help me plan a trip to {destination}?")
])

messages = template.format_messages(
    language="French",
    name="Camille",
    destination="Paris"
)
print(messages)
#출력
[
    SystemMessage(content='You are a helpful assistant who speaks only in French.'),
    AIMessage(content='Nice to meet you! My name is Camille.'),
    HumanMessage(content='Can you help me plan a trip to Paris?')
]

ZeroShotAgent, StructuredToolAgent 차이

LangChain에서 ZeroShotAgent와 StructuredToolAgent(혹은 StructuredChatAgent)는 도구(tool)를 사용하는 방식과 입력/출력 구조의 차이에 따라 구분됩니다.

1. ZeroShotAgent

자연어 프롬프트 기반으로 도구 사용을 추론하는 방식

  • 설명:

LLM이 도구를 사용하는 방법을 프롬프트만 보고 유추해서 결정함.

즉, 사전에 훈련된 LLM의 언어 능력을 활용해 "이런 질문이면 이런 도구를 써야겠네"라고 추론함.

  • 특징:
  • 입력: 사용자 질문 (자연어)
  • 출력: 도구 사용 여부, 도구 선택, 인자 등을 LLM이 자연어 프롬프트로 추론
  • 별도의 명시적인 schema 없음
  • 예: "서울 내일 날씨 알려줘" → WeatherTool 자동 선택
  • 장점: 유연하고 간단하게 작동
  • 단점: 복잡하거나 구조적인 입력이 필요한 경우 실수 가능성 있음
  • 대표 클래스: initialize_agent(..., agent_type=AgentType.ZERO_SHOT_REACT_DESCRIPTION)

2. StructuredToolAgent 또는 StructuredChatAgent

도구 사용의 입력/출력을 명시적인 구조(Schema)로 정의하고 사용하는 방식

  • 설명:

도구(tool)에 대한 입력/출력 타입을 명시적으로 정의하고, LLM은 그 스키마에 맞춰 도구를 호출함.

  • 특징:
  • 입력: 자연어를 구조화된 입력으로 파싱
  • 출력: 구조화된 형식 (예: Pydantic 모델, JSON 등)
  • 함수형 API와 유사한 function call 기반 실행
  • 예: get_weather(city: str, date: str) 같은 구조화된 함수 스펙에 따라 작동
  • 장점: 정확한 파라미터 매핑이 필요할 때 강력함 (예: OpenAI function calling)
  • 단점: 초기 설정이 다소 복잡할 수 있음
  • 대표 클래스: create_openai_functions_agent(...), create_structured_chat_agent(...)

Chain vs Agent: LangChain 내부 메시지 흐름과 Tool Loop 분석

🧠 0️⃣ 전체 개념 지도

LangChain + OpenAI 기반 구조에는 크게 세 단계가 있습니다:

  1. LLM 단일 호출 (llm.invoke)
  2. Chain (Prompt → LLM)
  3. Agent (Tool + Loop + 반복 호출)

이 3개가 어떻게 다른지, 내부에서 실제로 무슨 일이 벌어지는지 단계별로 설명합니다.

1️⃣ LLM 단일 호출 구조

llm.invoke("내 이름은 뭐니?")

내부 동작

OpenAI API에 전달되는 실제 메시지:

[
  {
    "role": "user",
    "content": "내 이름은 뭐니?"
  }
]

✔ 반복 없음

✔ tool 없음

✔ 단순 ChatCompletion 1회 호출

구조:

질문 → LLM → 응답 → 끝

2️⃣ Chain 구조 (Prompt → LLM)

기본 코드

from langchain.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0.2)

prompt = ChatPromptTemplate.from_template(
    """
    다음 질문에 한국어로 답해줘.
    질문: {query}
    """
)

chain = prompt | llm

result = chain.invoke({
    "query": "내 이름은 뭐니?"
})

print(result.content)

① invoke 입력

chain.invoke({"query": "내 이름은 뭐니?"})

② 프롬프트 렌더링

렌더링 결과:

다음 질문에 한국어로 답해줘.
질문: 내 이름은 뭐니?

🔷 STEP 0 — 최초 LLM 호출 직전

[
  {
    "role": "system",
    "content": "You are a hedge fund manager..."
  },
  {
    "role": "user",
    "content": "삼성전자 분석해줘"

예:

[

📌 이 시점에서 LLM은:

“나는 이 함수들을 호출할 수 있다”

🔷 STEP 1 — 첫 번째 LLM 응답

LLM 판단:

  • 삼성전자 분석하려면 외부 데이터 필요
  • symbol 필요

}

❗ 자연어 답변 없음

❗ tool 실행 요청만 있음

StockMarketSymbolSearchTool._run(query="Stock market symbol for Samsung Electronics")

예시 결과:

"SAMSUNG ELECTRONICS CO., LTD. (KRX: 005930)"

🔷 STEP 3 — tool 결과를 메시지에 추가

메시지 배열이 이렇게 변합니다:

[
  {"role": "system", "..."},
  {"role": "user", "삼성전자 분석해줘"},
  {"role": "assistant", "tool_calls": [...]},
  {"role": "tool", "content": "SAMSUNG ELECTRONICS CO., LTD. (KRX: 005930)"}
]

이제 LLM은:

“나는 방금 tool 결과를 본 상태”

로 다시 호출됩니다.

🔷 STEP 4 — 두 번째 LLM 판단

LLM은 이제 판단합니다:

  • symbol 확보됨 → 005930
  • 재무 개요 필요

응답:

{
  "role": "assistant",
  "tool_calls": [
    {
      "name": "CompanyOverview",
      "arguments": "{\"symbol\":\"005930\"}"
    }
  ]
}

🔷 STEP 5 — 반복 실행

이 패턴이 반복됩니다:

  1. tool call 생성
  2. LangChain 실행
  3. tool 결과를 context에 추가
  4. LLM 재판단

5️⃣ Agent Loop의 핵심 구조

실제 내부 개념은:

while True:
    response = call_llm(messages, tools)

    if response.tool_calls:
        tool_result = run_tool(response.tool_calls)
        messages.append(tool_result)
    else:
        break

LangChain이 이 루프를 대신 관리합니다.

6️⃣ 종료 조건

명시적 \{done: true\} 없음.

종료 기준:

✔ tool_call 있음 → 계속

✔ tool_call 없음 → 종료

즉,

“tool을 더 부르냐 / 안 부르냐”

가 종료 판단입니다.

❗ DB에 저장되지 않음

LangChain의 SystemMessage, HumanMessage, AIMessage 역할

각각의 역할 정리

클래스 역할 (role) 설명
SystemMessage system 모델에게 행동 지침을 주는 역할 (ex. 너는 지리 전문가야)
HumanMessage user 사용자의 질문이나 입력
AIMessage assistant 이전에 모델(AI)이 했던 응답

그러면 AIMessage는 왜 필요할까?

모델이 "이전 대화 내용을 참고하여 답변을 만들도록" 하기 위해서입니다.

예를 들어, 이런 대화 기록이 있다고 해봅시다:

messages = [
    SystemMessage(content="You are a helpful assistant."),
    HumanMessage(content="What's the capital of France?"),
    AIMessage(content="The capital of France is Paris."),
    HumanMessage(content="And what about Germany?")
]

이 경우 모델은 이전에 했던 자신의 대답(AIMessage)도 참고해서 "Germany"가 France와 비슷한 맥락의 질문이라는 걸 인식할 수 있게 됩니다.
즉, 대화의 맥락(context)을 유지하는 데 필요해요.

쉽게 말해보면

  • SystemMessage는 성격 설정
  • HumanMessage는 내가 한 말
  • AIMessage는 모델이 예전에 한 말

결론

AIMessage는 모델이 지금까지 한 응답들을 기록하는 역할이고,
질문-응답의 흐름을 이어주는 “과거 응답”이라고 생각하면 됩니다.

그래서 새로 대화할 땐 AIMessage 없이 시작하고,
이전 대화를 이어서 할 땐 AIMessage를 넣어주는 겁니다.

llm.invoke(), chat.predict_messages 차이

핵심 요약

메서드명 주요 용도 입력 타입 출력 타입 사용 대상
predict() 문자열 기반 LLM str str LLM (OpenAI, HuggingFaceHub, 등)
predict_messages() 메시지 기반 Chat 모델 [BaseMessage] AIMessage ChatModel (ChatOpenAI, 등)
invoke() LangChain의 표준 인터페이스 (Runnable) 다양한 타입 다양 (str, Message, dict, 등) 모든 Runnable 객체

차이 상세 설명

1. predict()

  • 입력: 단일 문자열 (str)
  • 출력: 문자열 응답
  • 대상: 일반 텍스트 LLM (LLM 클래스)
llm.predict("What's the capital of France?")
# 출력: 'The capital of France is Paris.'

2. predict_messages()

  • 입력: SystemMessage, HumanMessage, AIMessage 리스트
  • 출력: AIMessage (역할이 assistant인 응답)
  • 대상: ChatModel (ChatOpenAI 등)
from langchain.schema import HumanMessage

chat.predict_messages([HumanMessage(content="What's the capital of France?")])
# 출력: AIMessage(content="The capital of France is Paris.")

3. invoke() — LangChain의 표준 호출 방식

  • LangChain 0.1 이후 도입된 Runnable 표준 API
  • ChatModel, LLM, Chains, PromptTemplate 전부 .invoke() 가능
  • 입력 타입과 출력 타입이 다양함

예시:

# 텍스트 기반 LLM
llm.invoke("What's the capital of France?")
# 출력: 'The capital of France is Paris.'

# Chat 기반 LLM
chat.invoke([HumanMessage(content="What's the capital of France?")])
# 출력: AIMessage(...)

실전 비교 예

# 일반 LLM
from langchain.llms import OpenAI
llm = OpenAI()
print(llm.predict("Hello"))
print(llm.invoke("Hello"))  # 동일

# Chat LLM
from langchain.chat_models import ChatOpenAI
chat = ChatOpenAI()
msgs = [HumanMessage(content="Hello")]
print(chat.predict_messages(msgs))  # AIMessage
print(chat.invoke(msgs))            # 동일한 결과지만 invoke는 더 일반화된 방식

결론

  • invoke()는 LangChain이 모든 구성 요소(Prompt, Chain, LLM, ChatModel)를 동일한 방식으로 실행할 수 있도록 만든 범용 실행 메서드
  • predict() / predict_messages()는 구 버전에서 주로 쓰이고, 목적이 명확한 메서드
  • 요즘은 invoke만 써도 충분하고, chain 구성할 때 특히 유리
원문 보존 단위

LLM이 어떻게 임베딩 모델처럼 동작해서 벡터 DB 구축에 활용될 수 있는가

1. 개요

우리가 흔히 알고 있는 LLM(Large Language Model)은

"문장을 넣으면 문장을 출력하는 생성 모델"로 알고 있지만,

실제로는 임베딩(embedding) 모델처럼 사용되어 벡터 DB를 구축하는 데에도 활용 가능하다.

이 문서에서는:

  • 왜 LLM이 임베딩에 활용 가능한가
  • LLM을 임베딩 모델로 사용하려면 무엇이 필요한가
  • LangChain + Ollama + Mistral을 이용한 실전 코드

를 통해 이 개념을 정리한다.

2. 왜 가능했는가?

LLM이 임베딩 모델로도 쓰일 수 있는 이유는 다음 두 가지에서 비롯된다.

① LLM은 내부적으로 입력 문장을 "벡터"로 처리함

  • 문장을 토크나이징한 후, 각 토큰은 임베딩 테이블을 통해 벡터화됨
  • Transformer 레이어를 통과하며 문맥 정보가 반영된 의미 벡터가 만들어짐
  • 이 벡터는 원래는 텍스트 생성을 위한 중간 산출물이지만, 그 자체로도 문장의 의미를 표현함

② 일부 프레임워크가 LLM에서 이 벡터를 추출할 수 있도록 지원함

  • Hugging Face → last_hidden_state를 직접 추출
  • Ollama → .embed 기능을 통해 벡터 반환
  • LangChain → OllamaEmbeddings 같은 래퍼 클래스 제공

3. 가능하기 위해 필요한 조건

LLM을 임베딩 모델로 활용하기 위해서는 다음 두 조건이 반드시 충족되어야 한다.

조건 설명
1. 모델 구조 Transformer 기반이어야 하고, hidden state를 통해 의미 벡터 생성이 가능해야 함
2. 벡터 추출 기능 해당 LLM을 실행하는 API/엔진/서버가 벡터 추출 기능을 제공해야 함 (예: Hugging Face, Ollama 등)

4. 실전 예제 코드 (LangChain + Ollama + Mistral)

from langchain.embeddings import CacheBackedEmbeddings, OllamaEmbeddings
from langchain.vectorstores.faiss import FAISS
from langchain.document_loaders import UnstructuredFileLoader
from langchain.storage import LocalFileStore
from langchain.text_splitter import CharacterTextSplitter

def embed_file(file):
    file_content = file.read()
    file_path = f"./.cache/private_files/{file.name}"
    with open(file_path, "wb") as f:
        f.write(file_content)

    cache_dir = LocalFileStore(f"./.cache/private_embeddings/{file.name}")
    splitter = CharacterTextSplitter.from_tiktoken_encoder(
        separator="\n",
        chunk_size=600,
        chunk_overlap=100,
    )

    loader = UnstructuredFileLoader(file_path)
    docs = loader.load_and_split(text_splitter=splitter)

    # LLM(Mistral)을 임베딩 모델처럼 사용
    embeddings = OllamaEmbeddings(model="mistral:latest")
    cached_embeddings = CacheBackedEmbeddings.from_bytes_store(embeddings, cache_dir)

    # 문서 → 임베딩 벡터로 변환 → FAISS에 저장
    vectorstore = FAISS.from_documents(docs, cached_embeddings)
    retriever = vectorstore.as_retriever()

    return retriever

설명:

  • OllamaEmbeddings(model="mistral:latest")

→ LLM인 Mistral을 임베딩 벡터 생성기로 사용

  • FAISS로 생성된 벡터들을 저장하면 벡터 DB 완성
  • 이후 질문을 던지면 같은 방식으로 임베딩하고 유사 문서 검색 가능

5. 결론

LLM은 단지 텍스트 생성만 하는 도구가 아니라,

그 내부 구조 덕분에 임베딩 벡터 생성기로도 활용할 수 있다.

다만 임의의 모든 LLM이 되는 건 아니고,

"구조적으로 가능하고, API적으로 벡터 추출을 지원해야" 임베딩 모델처럼 사용할 수 있다.

이 내용은 필요에 따라 별도 학습 문서나 실행 가능한 실습으로 분리할 수 있다.

원문 보존 단위

zeroshot, structured, openai agent 차이

LangChain에서 OpenAITools, ZeroShotAgent, StructuredTool은 각각 다른 개념 또는 계층에 속해 있어. 용어가 헷갈릴 수 있는데, 정확히 어떤 레벨에서 쓰이는 개념인지부터 잡고 갈게.

✅ 1. 개념 정리

1.1 StructuredTool — 도구 정의 방식

"어떤 방식으로 Tool을 정의하느냐" 에 해당하는 개념

  • BaseTool을 상속한 도구
  • args_schema로 입력 타입을 명확히 정의함 (Pydantic 기반)
  • LLM이 사용하는 파라미터를 structured하게 명세할 수 있음 (파라미터 이름, 설명 등)
class AddTool(StructuredTool):
    name = "add"
    description = "Adds two numbers"
    args_schema = AddArgsSchema  # Pydantic 클래스

1.2 ZeroShotAgent — 행동 전략 (Agent 방식)

"LLM이 도구를 어떻게 선택하냐" 에 해당하는 개념

  • 도구에 대한 사용 예시 없이, 설명(description)만 보고 LLM이 추론하여 사용
  • 예: "Calculate the result of 5 + 3" → LLM이 add라는 도구가 있을 거라 추론하고 사용함
agent = initialize_agent(
    agent=AgentType.ZERO_SHOT_REACT_DESCRIPTION,
    tools=[...],
    llm=ChatOpenAI()
)

1.3 OpenAITools (정확히는 AgentType.OPENAI_FUNCTIONS) — OpenAI Function Call 기반 에이전트

"도구를 OpenAI function-calling 방식으로 사용" 하는 에이전트

  • GPT-4/3.5-turbo의 function calling 기능을 사용함
  • 도구 스펙(name, parameters, description)이 JSON으로 변환되어 LLM에 전달됨
  • 도구의 args_schema가 함수 signature로 자동 변환됨
agent = initialize_agent(
    agent=AgentType.OPENAI_FUNCTIONS,
    tools=[StructuredTool(...), ...],
    llm=ChatOpenAI(model="gpt-4")
)

✅ 1. ZeroShotAgent 예시 (AgentType.ZERO_SHOT_REACT_DESCRIPTION)

from langchain.chat_models import ChatOpenAI
from langchain.agents import initialize_agent, AgentType
from langchain.tools import Tool

def add(a: int, b: int) -> int:
    return a + b

add_tool = Tool.from_function(
    func=add,
    name="add",
    description="두 숫자를 더합니다. a와 b를 입력으로 받습니다."
)

llm = ChatOpenAI(temperature=0)

agent = initialize_agent(
    llm=llm,
    tools=[add_tool],
    agent=AgentType.ZERO_SHOT_REACT_DESCRIPTION,
    verbose=True,
)

agent.invoke("a=4, b=5를 더해줘")

🧠 이 방식은 도구의 설명(description) 만 보고 LLM이 추론해서 도구를 사용할 수 있어야 함.

✅ 2. StructuredTool + OpenAITools 예시 (AgentType.OPENAI_FUNCTIONS)

from langchain.chat_models import ChatOpenAI
from langchain.agents import initialize_agent, AgentType
from langchain.tools import StructuredTool
from pydantic import BaseModel, Field

class AddArgs(BaseModel):
    a: int = Field(description="첫 번째 숫자")
    b: int = Field(description="두 번째 숫자")

def add(a: int, b: int) -> int:
    return a + b

add_tool = StructuredTool.from_function(
    func=add,
    name="add",
    description="두 숫자를 더하는 함수입니다.",
    args_schema=AddArgs,
)

llm = ChatOpenAI(temperature=0, model="gpt-4")  # function-calling 지원 모델

agent = initialize_agent(
    llm=llm,
    tools=[add_tool],
    agent=AgentType.OPENAI_FUNCTIONS,
    verbose=True,
)

agent.invoke("4와 5를 더해주세요")

🧠 이 방식은 GPT의 function calling 기능을 활용해서, 도구의 파라미터를 자동 JSON 변환해서 사용함. 도구가 StructuredTool 기반이어야만 제대로 동작해.

args_schema랑 _run()의 인자 개수나 이름이 다르면 에러 발생?

✅ 정답: 네, 에러 납니다.

정확히는 BaseTool이나 StructuredTool을 사용할 때, 내부적으로 LangChain이 _run()에 **kwargs로 값을 넘기는데, 이때 _run()의 시그니처가 맞지 않으면 TypeError 또는 ValueError가 발생합니다.

✅ 예제: 일부러 틀리게 작성했을 때

from langchain.tools import BaseTool
from pydantic import BaseModel

class AddArgs(BaseModel):
    a: int
    b: int

class AddTool(BaseTool):
    name = "add"
    description = "두 수를 더합니다."
    args_schema = AddArgs

    def _run(self, a):  # ❌ b 없음
        return a + 1

🔥 실행 시

tool = AddTool()
tool.invoke({"a": 3, "b": 5})

💥 결과

TypeError: _run() got an unexpected keyword argument 'b'

✅ 안전한 방법들

1. 모든 필드를 정확히 매칭해서 명시

def _run(self, a: int, b: int):
    return a + b

2. 안전하게 *kwargs 사용

def _run(self, **kwargs):
    a = kwargs["a"]
    b = kwargs["b"]
    return a + b

이 방식은 구조가 유연하지만, 타입 힌트와 자동 완성은 안 됨.

✅ 권장 패턴 (안정성 + IDE 지원)

class AddTool(BaseTool):
    name = "add"
    description = "두 수를 더합니다."
    args_schema = AddArgs

    def _run(self, a: int, b: int):  # ✅ 정확히 일치
        return a + b

또는 아예 StructuredTool.from_function(...)을 쓰면 자동으로 맞춰줌.

심화할 때는 StructuredTool.from_function()이 _run()을 구성하는 방식까지 추적할 수 있다.

편입 후 검증 메모

  • Agent 정의: LLM 호출 한 번과 Agent는 다르다. Agent는 모델 출력에 따라 도구 실행·상태 갱신·다음 호출을 반복하는 제어 루프와 종료 조건을 포함한다.
  • Tool 안전성: schema가 맞아도 도구 호출이 안전하다는 뜻은 아니다. 권한·입력 검증·timeout·재시도·idempotency와 외부 효과 승인을 별도로 설계한다.
  • Embedding: 생성 모델의 토큰 hidden state와 검색용 embedding API를 같은 것으로 간주하지 않는다. 목적에 맞는 embedding 모델·차원·거리 척도를 사용한다.
  • 버전 경계: SDK 클래스·메서드 이름은 바뀔 수 있다. 원문의 개념 흐름과 현재 설치 버전의 공식 API를 분리해 검증한다.
