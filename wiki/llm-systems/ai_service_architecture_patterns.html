AI 서비스 아키텍처 전체 정리

주제는 크게 두 축입니다:

  1. 오케스트레이션 서버 + async 구조에서 병목이 어디인가
  2. 인퍼런스 서버가 어떻게 병렬 처리를 하는가 (vLLM, batching, GPU)

(API → Orchestration → Inference → GPU, 병목과 병렬의 본질)

1️⃣ 기본 구조 정리

AI 기반 웹 서비스(ChatGPT, Perplexity 같은 구조)는 보통 이렇게 나뉩니다:

Client
   ↓
API Server (FastAPI 등)
   ↓
Orchestration Layer (LangGraph / LangChain)
   ↓
Inference Server (vLLM / TGI / OpenAI API)
   ↓
GPU

각 레이어의 역할은 명확히 다릅니다.

1. API Server

  • 인증
  • rate limit
  • 요청 검증
  • 세션 관리
  • 응답 포맷팅
  • 스트리밍 처리

여기는 HTTP 레이어입니다.

2. Orchestration Layer

  • Agent 실행
  • Tool 호출
  • Memory 관리
  • 상태 전이 (LangGraph의 state machine)
  • 여러 LLM 호출 조합

여기는 모델을 어떻게 사용할지 결정하는 계층입니다.

3. Inference Server

  • 실제 모델을 메모리에 올림
  • 토큰 생성
  • KV cache 관리
  • batching
  • GPU 메모리 스케줄링

여기가 진짜 연산이 일어나는 곳입니다.

2️⃣ 오케스트레이션 서버와 async의 역할

오케스트레이션 서버는 보통 이런 식으로 동작합니다:

result = await openai_client.chat(...)

이건 네트워크 I/O입니다.

async 구조에서는:

  • CPU를 거의 점유하지 않음
  • await 상태로 대기
  • 이벤트 루프는 다른 요청 처리 가능

따라서:

✔ LLM이 병목이 없다는 가정 하에서는

✔ 오케스트레이션 서버는 CPU 병목이 거의 없음

✔ 동시 대기가 가능

하지만 “병목이 없다”는 말은 정확히 표현해야 합니다

LLM이 완전히 무한 확장이고:

  • rate limit 없음
  • 네트워크 무한
  • 응답 지연 거의 없음

이라는 극단적 가정 하에서는

웹 서버 레벨에서 CPU 병목은 거의 없다.

하지만 여전히 다음 자원은 유한합니다:

① 동시 연결 수

  • OS 파일 디스크립터 한계

② 메모리

  • request 객체
  • coroutine state
  • JSON buffer

③ JSON 직렬화 CPU

따라서 정확한 표현은:

“CPU 병목은 거의 없다”가 맞고

“병목이 없다”는 틀립니다.

3️⃣ 이제 핵심: 인퍼런스 서버는 어떻게 병렬 처리하는가?

질문:

LLM은 한 토큰씩 순차 생성하는데, 병렬이 어떻게 되나?

맞습니다. LLM은 autoregressive라 본질적으로 순차입니다.

입력 → 토큰1 → 토큰2 → 토큰3 → ...

그런데 병렬처럼 보이는 이유는 GPU와 배치 처리 때문입니다.

4️⃣ GPU의 본질

GPU는:

같은 연산을 여러 데이터에 동시에 수행하는 데 최적화된 장치

대표적인 연산:

Y = W × X  (행렬 곱)

이 연산은 GPU에서 매우 빠릅니다.

중요한 점:

여러 요청을 하나의 큰 행렬로 묶어서 한 번에 계산할 수 있다.

5️⃣ 배치(batch)의 개념

가정:

Request A
Request B
Request C
Request D

각 요청을 따로 처리하면:

  • GPU 커널 실행 4번
  • 메모리 접근 4번

하지만 배치로 묶으면:

Batch = [A, B, C, D]

하나의 큰 텐서로 만들어서:

한 번의 GPU 연산으로 처리

이게 병렬처럼 보이는 이유입니다.

6️⃣ vLLM의 핵심: Dynamic Batching

전통적 배치는:

  • 같은 길이
  • 같은 타이밍

이어야 했습니다.

vLLM은:

들어오는 요청을 실시간으로 묶어서

GPU를 최대한 활용

이걸 dynamic batching이라고 합니다.

7️⃣ 토큰 생성은 순차인데 어떻게 병렬인가?

토큰 생성은 순차입니다.

하지만 각 토큰 단계마다:

Step 1: 모든 요청의 첫 토큰 생성
Step 2: 모든 요청의 두 번째 토큰 생성
Step 3: ...

이렇게 단계 단위로 병렬 처리가 가능합니다.

즉:

  • CPU 병렬 ❌
  • 요청 병렬 ⭕
  • GPU 벡터 병렬 ⭕
  • 토큰 단계 병렬 ⭕

8️⃣ vLLM이 중요한 이유

vLLM은:

  • KV cache 최적화
  • PagedAttention
  • 메모리 단편화 최소화
  • 동적 스케줄링

을 통해

GPU 메모리를 매우 효율적으로 사용

그래서 더 많은 동시 요청을 처리할 수 있습니다.

9️⃣ 병렬의 진짜 정체

요청 A, B, C를 동시에 실행하는 게 아니라:

같은 시간대의 연산을 하나의 GPU 벡터 연산으로 묶어 처리

하는 것입니다.

🔟 최종 통합 정리

async는 무엇을 해결하는가?

  • I/O 대기 중 CPU 낭비 제거
  • 동시 대기 가능

async가 해결하지 못하는 것

  • 외부 LLM 한계
  • GPU 처리 한계
  • 네트워크 대역폭
  • 메모리 한계

인퍼런스 서버 병렬의 본질

  • 멀티스레드 병렬 ❌
  • GPU 벡터 연산 병렬 ⭕
  • 배치 스케줄링 ⭕
  • 토큰 단계 병렬 ⭕

AI 서비스 병목 순서

  1. LLM / GPU
  2. 네트워크
  3. 메모리
  4. JSON 직렬화
  5. 마지막에 웹 서버

🔥 핵심 통찰

  • async는 동시성 문제 해결
  • ProcessPool은 CPU 병렬 문제 해결
  • Inference Server는 GPU 벡터 병렬 문제 해결

그리고:

AI 서비스의 진짜 병목은 웹 서버가 아니라 GPU다.

후속 검증 질문

이 연결 구조를 실제 부하와 지연 시간으로 검증하려면 다음 질문을 확인한다.

  • GPU 한 대로 실제 몇 명 동시 사용자 처리 가능?
  • 배치가 커질수록 latency는 어떻게 변하나?
  • 왜 배치 크기를 무한정 키울 수 없나?
  • streaming과 batching은 어떻게 공존하나?

편입 후 검증 메모

  • 계층은 선택: 모든 AI 서비스에 queue·vector DB·multi-agent가 필요한 것은 아니다. 단순 baseline에서 병목이 확인될 때 계층을 추가한다.
  • 비동기 경계: 오래 걸리는 작업을 queue로 넘길 때 job identity·중복 실행·취소·결과 보존과 사용자 상태 표시가 필요하다.
  • 평가: 모델 응답 성공 여부만으로 서비스 품질을 판단하지 않는다. retrieval·tool execution·groundedness·latency·cost를 단계별로 측정한다.
  • 운영: prompt·model·schema·dataset version을 추적하고 안전한 rollout·fallback·감사 로그를 갖춘다.
