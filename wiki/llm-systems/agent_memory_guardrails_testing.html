#17.2 Pytest test.py 기준 테스트 작성 정리

배경

이 문서는 test.py를 기준으로, 이메일 분류 그래프를 테스트하는 방법을 정리한 것이다. 핵심은 "입력값을 여러 개 나열하고, 기대값과 매칭해 자동 검증"이다.

파일 구조 요약 (test.py)

import pytest
from main import graph

@pytest.mark.parametrize(
    "email, expected_category, expected_score",
    [
        ("this is urgent", "urgent", 10),
        ("i wanna talk to you", "normal", 5),
        ("i have an offer for you", "spam", 1),
    ]
)
def test_full_graph(email, expected_category, expected_score):

    result = graph.invoke({"email": email})

    assert result["category"] == expected_category
    assert result["priority_score"] == expected_score

배운 포인트

1) @pytest.mark.parametrize로 테스트 케이스를 묶기

  • "email, expected_category, expected_score"처럼 테스트 함수 인자를 문자열로 지정한다.
  • 리스트에 (email, expected_category, expected_score) 형태로 테스트 케이스를 여러 개 넣는다.
  • 하나의 테스트 함수가 케이스 수만큼 반복 실행된다.

2) SUT(System Under Test) 실행

  • graph.invoke(\{"email": email\})로 입력을 전달해 실제 로직을 실행한다.
  • 여기서 graph는 main.py에서 만든 StateGraph의 실행 엔트리.

3) assert로 검증

  • assert result["category"] == expected_category

카테고리 예측이 기대값과 일치해야 합니다.

  • assert result["priority_score"] == expected_score

우선순위 점수가 기대값과 정확히 일치하는지 확인합니다.

실행 방법

pytest

단일 테스트만 실행할 경우:

pytest test.py

특정 함수만 실행:

pytest test.py -k test_full_graph

체크포인트 (테스트 작성 습관)

  1. 입력 3개, 기대값 2개처럼 구조화해도 가독성 유지.
  2. 기대값 변수명과 assert 비교 대상 타입이 정확히 대응되는지 확인.
  3. 실패 시 로그나 출력으로 비교 대상(result)을 먼저 확인해 보강.
  4. 테스트는 동작 규칙을 설명하는 문서처럼 다뤄야 한다.

참고

  • test.py에서 핵심은 파라미터화된 다중 케이스 테스트이다.
  • main.py의 분류 규칙이나 우선순위 점수가 바뀌면 이 테스트가 바로 회귀 여부를 알려준다.

#9.6 Hooks - 훅 기반 고객지원 라우팅

#9.6 Hooks (06:36) - 훅 기반 고객지원 라우팅

수정 목적

  • Triage에서 분기한 뒤 specialist의 실제 처리 이력을 놓치지 않도록 하기 위해 hook을 도입합니다.
  • handoff 이동 시 불필요한 tool 정보가 섞이지 않도록 remove_all_tools로 payload를 정리합니다.
  • 라우팅/도구 실행/로그가 일관되게 남아 운영자가 초보자도 쉽게 추적하도록 구조를 정리합니다.

핵심 개념

  • 이 변경의 핵심은 AgentToolUsageLoggingHooks와 handoff_filters.remove_all_tools입니다.
  • hook은 에이전트 동작 흐름에 부가 기록을 붙이는 장치입니다.
  • filter는 handoff로 전달되는 데이터에서 도구 정보와 같은 불필요 항목을 제거합니다.
  • 초보자 관점에서는 hook은 “작업 후 영수증”, filter는 “배송 전 불필요 물품 제거”로 이해하시면 됩니다.

동작 흐름

  • User 요청 수신
  • off_topic_guardrail 검증
  • triage 분류 후 handoff 대상 선택
  • make_handoff(...)에서 input_filter=remove_all_tools 적용
  • specialist Agent 실행 및 tools 호출
  • AgentToolUsageLoggingHooks가 각 Agent 실행/도구 사용 로그를 남김

사용 이유

  • 장애가 났을 때 “누가, 언제, 어디서” 잘못됐는지 빠르게 찾기 위해
  • handoff와 tool 호출 이력을 분리해 추적 가독성을 높이기 위해
  • specialist 추가 시 동일 패턴으로 코드 일관성을 유지하기 위해

한 줄 요약

  • triage와 4개 specialist에 공통 hooks를 붙이고 handoff 입력을 정제해 라우팅 정확도와 운영 추적성을 동시에 개선한 실습입니다.

무엇을 해결하는가

  • specialist 동작 로그가 분산되어 누락되던 문제
  • handoff 이동 시 payload 정합성 불명확 문제
  • 새 에이전트를 붙일 때도 동일 기준을 반복 적용하기 어려운 문제

async def off_topic_guardrail(
    wrapper: RunContextWrapper[UserAccountContext],
    agent: Agent[UserAccountContext],
    input: str,

        input_guardrail_agent, input, context=wrapper.context

        f"[GUARDRAIL] 완료 — {time.time():.4f}"
        f" | is_off_topic={final_output.is_off_topic}"
    )

    return GuardrailFunctionOutput(
        output_info=final_output,
        tripwire_triggered=final_output.is_off_topic,
    )

  • 기존 내용은 그대로 두고, 아래만 추가합니다.
  • LLM이 툴을 선택하는 기준은 “함수 정의 메타 + 에이전트 맥락 + 현재 대화 목적”입니다.

핵심 3요소

  • @function_tool 등록 여부
  • 툴로 노출되려면 함수가 이 데코레이터로 감싸져 있어야 합니다.
  • 툴 설명(docstring)
  • 함수 바로 아래 """ ... """ 블록의 내용이 어떤 요청에서 쓰면 되는지 판단 근거가 됩니다.
  • 에이전트의 tools=[...]
  • 현재 활성 에이전트의 도구 목록에 포함되어야 실제 호출 후보로 고려됩니다.

왜 함수 내 # 주석이 아닌 docstring이 중요하나?

  • # 주석은 코드 가독성용이며, LLM 판단용 메타데이터는 주로 docstring과 시그니처입니다.
  • 따라서 툴 선택 정확도를 높이려면 주석보다 docstring을 구체적으로 작성하는 편이 효과적입니다.

판단 흐름(예: export_account_data)

  • 에이전트가 계정 에이전트인지 확인
  • triage 또는 user 라우팅으로 account_agent에 도달했는지

  • 조건이 맞으면 tool call 파라미터를 구성
  • context는 시스템이 주입하고, data_types는 사용자 요청을 반영해 채워서 호출

#9.7 Output Guardrails (09:50) - 출력 가드레일

수정 목적

  • 기술 에이전트가 기술 질문 이외의 응답(결제/주문/계정 정보)을 섞어 말하는 문제를 방지했습니다.
  • 출력 단계에서도 안전장치를 추가해, 내부적으로 tripwire로 잘못된 응답을 차단할 수 있게 했습니다.
  • 에이전트 전환 흐름을 유지하면서 출력 가드레일이 실패했을 때 사용자 메시지를 일관되게 처리하도록 정리했습니다.
  • model이 직접 판단할 범위를 Technical 전용 규칙으로 더 좁혀 출력 품질을 높였습니다.

핵심 개념

  • 이번 변경의 핵심은 Output Guardrail입니다.
  • Input Guardrail은 질문 수용 전에 걸러내고, Output Guardrail은 답변 출력 전에 걸러냅니다.
  • 기술 지원 에이전트에서 Billing/Account/Order 관련 내용이 답변에 섞이면 차단하도록 정책을 넣었습니다.
  • 초보자 관점에서는 Output Guardrail을 “응답 출고 전 최종 검사대”로 이해하시면 됩니다.

동작 흐름

  • User 메시지 입력
  • triage_agent가 분류해 기술 에이전트로 라우팅
  • technical_agent가 답변 생성
  • 생성된 응답이 technical_output_guardrail 규칙을 통과하는지 검사
  • 통과 실패 시 OutputGuardrailTripwireTriggered 발생
  • 실패 메시지로 안전하게 응답 거부

사용 이유

  • 오답·주제 이탈을 출력 단계에서 조기에 차단할 수 있습니다.
  • 기술 지원 응답 범위를 명확히 관리해 규정 준수와 일관성을 높입니다.
  • 문제 추적이 쉬워집니다. (어떤 가드레일에서 실패했는지 구분 가능)

한 줄 요약

  • technical_agent에 출력 가드레일을 붙이고, main.py에서 실패 시 출력 차단 메시지를 처리해 응답 범위를 제어했습니다.

무엇을 해결하는가

  • 기술 지원 에이전트가 결제/주문/계정 정보를 과도하게 반환하던 범위를 제한
  • 기술/결제/계정/주문 주제 경계가 output 단계에서 다시 침범되는 문제 완화

                        )

                        response = ""

        except InputGuardrailTripwireTriggered:
            st.write("I can't help you with that.")

        except OutputGuardrailTripwireTriggered:
            st.write("Cant show you that answer.")
            st.session_state["text_placeholder"].empty()

)

    if message:

        asyncio.run(run_agent(message))

14.1 Tool Nodes (11:36) - Tool Nodes

수정 목적

  • LangGraph에서 ToolNode가 무엇이고, tool calling 그래프에서 어떤 위치를 맡는지 학습합니다.
  • ToolNode를 중심으로 bind_tools, tools_condition, custom_tools_node가 각각 어떤 보조 역할을 하는지 연결해서 이해합니다.
  • 이번 변경사항을 통해 LLM이 도구를 안다와 도구를 실제로 실행한다는 서로 다른 단계라는 점을 구분합니다.
  • 노트북의 추가 마크다운과 주석을 통해 표준 ToolNode 패턴과 커스텀 확장 패턴을 함께 정리합니다.

핵심 개념

  • ToolNode: LLM이 만든 tool_calls를 실제 함수 실행으로 연결하는 LangGraph의 prebuilt 노드입니다.
  • bind_tools: LLM에게 사용할 수 있는 도구의 스키마를 알려주는 단계입니다.
  • tools_condition: 마지막 AI 메시지에 tool_calls가 있는지 보고 다음 노드를 자동 선택하는 조건 라우터입니다.
  • custom_tools_node: ToolNode 대신 직접 구현하는 커스텀 tool 실행 노드입니다.

동작 흐름

flowchart LR
    A["START"] --> B["chatbot"]
    B --> C{"tools_condition"}
    C -- "tool_calls 있음" --> D["ToolNode"]
    C -- "tool_calls 없음" --> E["END"]
    D --> B
  • chatbot은 llm_with_tools를 호출해 필요하면 tool_calls를 포함한 AI 메시지를 만듭니다.
  • tools_condition이 tool execution이 필요한지 판단합니다.
  • 필요하면 ToolNode가 실제 함수를 실행하고, 실행 결과가 messages에 추가된 뒤 다시 chatbot으로 돌아갑니다.

이번 변경으로 무엇을 공부할 수 있었는가

  • LangGraph에서 ToolNode가 tool execution 담당 노드라는 점을 공부할 수 있습니다.
  • bind_tools는 실행기가 아니라 tool schema를 알려주는 단계라는 점을 공부할 수 있습니다.
  • tools_condition이 ToolNode로 갈지 END로 갈지를 판단하는 라우터라는 점을 공부할 수 있습니다.
  • tools_condition은 여러 tool 중 하나를 고르는 함수가 아니라, 기본적으로 tools로 갈지 END로 갈지를 정하는 2분기 라우터라는 점을 공부할 수 있습니다.

코드 설명

@tool
def get_weather(city:str):
    """ Gets weather in city """
    return f"The weather in {city} is sunny"

llm_with_tools = llm.bind_tools(tools=[get_weather])

def chatbot(state: State):
    response = llm_with_tools.invoke(state["messages"])
    return {
        "messages": [response]
    }

tool_node = ToolNode(
    tools=[
        get_weather
    ],
)

graph_builder.add_node("chatbot", chatbot)
graph_builder.add_node("tools", tool_node)
graph_builder.add_edge(START, "chatbot")
graph_builder.add_conditional_edges("chatbot", tools_condition)
graph_builder.add_edge("tools", "chatbot")

이 구조가 이번 노트북의 핵심입니다. ToolNode가 실제 tool execution을 맡고, bind_tools와 tools_condition은 ToolNode가 제대로 동작하기 위한 주변 구성요소입니다.

노트북 마크다운에서 정리한 추가 학습 포인트

bind_tools = 도구 인지/호출 생성
ToolNode = 도구 실제 실행
  • bind_tools에만 있으면 모델은 호출을 만들 수 있어도 실행 노드가 처리하지 못할 수 있습니다.
  • 반대로 ToolNode에만 있으면 실행기는 있어도 LLM이 도구 존재를 모르기 때문에 호출 생성이 약해질 수 있습니다.

tools_condition은 무엇을 결정하고, 무엇을 결정하지 않는가

graph_builder.add_node("tools", tool_node)
graph_builder.add_conditional_edges("chatbot", tools_condition)
  • tools_condition은 여러 tool 함수 중 무엇을 호출할지 고르는 함수가 아닙니다.
  • 어떤 tool을 쓸지는 LLM이 만든 tool_calls 안의 name 값이 결정합니다.
  • tools_condition의 역할은 tool_calls가 있으면 tool 실행 노드로 보내고, 없으면 END로 보내는 것입니다.
  • 그래서 기본형에서는 사실상 tools로 갈지 END로 갈지를 정하는 2분기 라우터라고 볼 수 있습니다.

자동 라우팅의 핵심은 ToolNode 타입이 아니라 노드 이름이다

graph_builder.add_node("tools", custom_tools_node)
graph_builder.add_conditional_edges("chatbot", tools_condition)
  • 이것도 동작할 수 있습니다.
  • tools_condition이 자동 라우팅하는 이유는 대상이 ToolNode 타입이라서가 아니라, 반환되는 라우트 키와 실제 노드 이름이 맞기 때문입니다.
  • 따라서 tools라는 이름으로 등록되어 있다면, 그 노드는 ToolNode일 수도 있고 custom_tools_node일 수도 있습니다.
graph_builder.add_node("custom_tools", custom_tools_node)
graph_builder.add_conditional_edges(
    "chatbot",
    tools_condition,
    {"tools": "custom_tools", "__end__": END}
)
  • 반대로 커스텀 노드 이름이 custom_tools처럼 다르면, 세 번째 파라미터로 직접 매핑해야 합니다.

주석으로 기억할 핵심 포인트

  • bind_tools는 도구 실행이 아니라, LLM이 tool call을 생성할 수 있게 만드는 단계입니다.
  • ToolNode는 AI 메시지의 tool_calls를 실제 함수 실행으로 연결하는 실행기입니다.
  • tools_condition은 기본형에서 사실상 tools로 갈지 END로 갈지를 정하는 2분기 함수입니다.
  • 어떤 tool 함수를 쓸지는 tools_condition이 아니라 LLM이 만든 tool_calls가 결정합니다.
  • 자동 라우팅의 핵심은 ToolNode 타입 여부가 아니라, tools_condition이 반환하는 라우트 키와 실제 노드 이름이 맞는지입니다.

14.2 Memory (11:16) - Checkpointer와 thread_id 메모리

수정 목적

  • LangGraph에서 checkpointer가 무엇이고 왜 메모리 기능의 핵심인지 먼저 이해합니다.
  • checkpointer를 연결해 대화 메모리를 부여하는 방법과 thread_id의 역할을 정리합니다.
  • invoke, get_state_history, stream, astream에서 메모리가 어떻게 보이는지 정리합니다.

핵심 개념

  • checkpointer: 그래프 실행 중 만들어지는 state를 저장하고 다음 호출에서 다시 복원하게 해주는 저장 계층입니다.
  • SqliteSaver: checkpointer의 SQLite 기반 동기 구현체입니다.
  • thread_id: 대화/세션을 구분하는 식별자이며, 같은 값이면 같은 메모리를 이어받습니다.
  • AsyncSqliteSaver: astream, ainvoke 같은 비동기 실행용 checkpointer 구현체입니다.

먼저 이해할 개념: checkpointer는 무엇인가

  • checkpointer는 LangGraph 상태를 저장하는 장치입니다.
  • 저장되는 것은 문자열 하나가 아니라 그 시점의 전체 state입니다. 예: messages, custom_stuff
  • 그래서 checkpointer가 있으면 그래프는 한 번 실행하고 끝나는 코드가 아니라, 다음 호출에서 이전 상태를 이어받는 기억하는 그래프가 됩니다.

시스템 구조

flowchart TD
    A["1. User 입력"] --> B["2. invoke / stream / astream 호출"]
    B --> C["3. checkpointer 접근"]
    C --> D["4. thread_id 확인"]
    D --> E["5. 저장된 state(messages) 복원"]
    E --> F["6. chatbot 실행"]
    F --> G{"7. tool_calls 있음?"}
    G -->|yes| H["8. ToolNode 실행 (여러 tool_call 처리, ToolMessage 생성)"]
    G -->|no| J["10. END"]
    H --> I["9. chatbot 재실행"]
    I --> K["11. 상태 저장(checkpoint)"]
    J --> K

번호별 의미

  • 5. 저장된 state(messages) 복원: 같은 thread_id의 이전 대화가 있으면 불러옵니다.
  • 8. ToolNode 실행: 여러 tool_calls가 있으면 ToolNode 한 번 실행 안에서 함께 처리하고, 결과를 하나 이상의 ToolMessage로 messages에 추가합니다.
  • 11. 상태 저장(checkpoint): tool_calls만이 아니라 messages를 포함한 전체 state를 저장합니다.

케이스별 실행 경로

  • tool_calls가 없는 질문: User 입력 → checkpointer 접근 → thread_id 확인 → 저장된 state 복원 → chatbot 실행 → tool_calls 없음 판단 → END → 상태 저장
  • tool_calls가 있는 질문: User 입력 → checkpointer 접근 → thread_id 확인 → 저장된 state 복원 → chatbot 실행 → tool_calls 있음 판단 → ToolNode 실행 → chatbot 재실행 → 상태 저장
  • 한 번에 여러 tool_calls가 있는 질문도 그래프 레벨에서는 같은 흐름입니다. 차이는 ToolNode 내부에서 여러 tool call을 처리한다는 점입니다.
  • 같은 thread_id로 다시 질문: 저장된 state 복원 이후 현재 질문을 이어서 처리합니다.
  • 다른 thread_id로 질문: 복원할 state가 없으므로 새 대화처럼 시작합니다.

여러 tool_calls 예시

  • 질문 예시: what is the weather in berlin, budapest and bratislava
  • chatbot은 하나의 AIMessage 안에 여러 tool_calls를 만듭니다.
  • ToolNode는 한 번 실행되면서 그 여러 tool_calls를 처리하고 여러 ToolMessage를 messages에 추가합니다.
  • 그 다음 chatbot이 ToolMessage들을 보고 최종 자연어 응답을 만듭니다.

get_state_history와 stream

  • get_state_history()는 최신 상태부터 반환되고, state.next는 방금 실행한 노드가 아니라 다음에 실행될 노드를 의미합니다.
  • stream_mode="tasks"에서는 각 노드마다 시작/종료 이벤트 2개가 나옵니다.
  • input에 전체 대화 히스토리가 들어있는 것은 Memory가 실제로 누적 저장되고 있다는 증거입니다.

동기 → 비동기 전환

  • 동기 SqliteSaver로는 astream, ainvoke를 쓸 수 없고 AsyncSqliteSaver로 바꿔야 합니다.
  • AsyncSqliteSaver.from_conn_string()은 async context manager를 반환하므로 async with 블록 안에서 compile과 실행을 모두 해야 합니다.

핵심 변경사항 요약

  1. SqliteSaver를 연결해 그래프에 메모리를 붙였습니다.
  2. thread_id로 대화 세션을 구분했습니다.
  3. get_state_history()와 stream_mode="tasks"로 저장된 상태와 실행 이벤트를 해석하는 예시를 추가했습니다.
  4. AsyncSqliteSaver로 비동기 전환하는 방법을 정리했습니다.

  • 한 줄 정의: 그래프 실행의 특정 시점을 통째로 캡처한 스냅샷 객체입니다.
    - 필요한 상황: 그래프의 과거 상태를 확인하거나, 그 시점부터 다시 실행하고 싶을 때 필요합니다.
    - 코드 역할: values(상태값), next(다음 실행 노드), config(checkpoint_id 포함), metadata(step 번호) 등을 담고 있습니다.
  • checkpoint_id
  • 한 줄 정의: 각 체크포인트를 고유하게 식별하는 ID입니다.
    - 필요한 상황: Time Travel로 특정 시점에서 그래프를 다시 실행하고 싶을 때 필요합니다.
    - 코드 역할: config에 checkpoint_id를 넣어 invoke()를 호출하면 해당 시점부터 재실행할 수 있습니다.
  • Time Travel
  • 한 줄 정의: 과거 체크포인트로 돌아가서 그래프를 다시 실행하는 기능입니다.
    - 필요한 상황: LLM 응답이 마음에 들지 않을 때 과거 시점으로 돌아가 다른 결과를 받고 싶을 때 필요합니다.
    - 코드 역할: checkpoint_id를 config에 지정하면 그 시점의 상태를 복원해서 이어서 실행합니다.
  • update_state()와 분기(Fork)
  • 한 줄 정의: 과거 체크포인트의 state를 수정해서 새로운 분기를 만드는 API입니다.
    - 필요한 상황: 대화 중간의 특정 메시지를 바꿔서 "만약 이렇게 말했다면?" 시나리오를 실행하고 싶을 때 필요합니다.
    - 코드 역할: 기존 체크포인트를 수정하지 않고 새 checkpoint_id를 가진 분기 체크포인트를 생성합니다.
    - 핵심 원리: 체크포인트는 불변(immutable)입니다. update_state()는 덮어쓰기가 아니라 Git의 브랜치처럼 새 타임라인을 만듭니다.

핵심 개념 설명

기술 설명

  • graph.get_state_history(config)
  • config에 담긴 thread_id 기준으로 저장된 모든 체크포인트를 반환합니다.
    - 반환 순서는 최신 → 과거입니다.
    - 각 항목은 StateSnapshot 객체입니다.
  • StateSnapshot의 주요 필드
  • values: 해당 시점의 state 전체 (예: \{"messages": [...]\})
    - next: 이 시점에서 다음에 실행될 노드 (빈 튜플이면 종료)
    - config.configurable.checkpoint_id: 이 체크포인트의 고유 ID
    - metadata.step: 몇 번째 스텝인지 (-1은 입력 전, 0부터 실제 실행)
    - parent_config: 바로 이전 체크포인트의 config (없으면 None)
    - tasks: 해당 스텝에서 실행되었거나 실행될 태스크 정보

쉬운 설명

  • get_state_history()는 게임의 세이브 파일 목록을 보는 것과 같습니다.
  • 각 StateSnapshot은 하나의 세이브 파일입니다.
  • checkpoint_id는 세이브 파일의 이름입니다.
  • Time Travel은 원하는 세이브 파일을 불러와서 거기서부터 다시 플레이하는 것입니다.
  • next는 "이 세이브를 불러오면 다음에 어떤 스테이지가 나오는지"를 알려줍니다.

코드 설명

1. 기본 그래프 구성 + checkpointer 연결

graph = graph_builder.compile(
    checkpointer=SqliteSaver(conn),
)
  • checkpointer를 붙여야 체크포인트가 자동으로 저장됩니다.
  • checkpointer가 없으면 get_state_history() 자체를 사용할 수 없습니다.

2. 그래프 실행 (invoke)

result = graph.invoke(
    {
        "messages": [
            {
                "role": "user",
                "content": "I live in Europe now. And the city I live in is Valencia."
            },
        ]
    },
    config=config,
)
  • 이 한 번의 invoke()로 3개의 체크포인트가 생성됩니다.
  • step -1: 입력 전
    - step 0: 입력 후 / chatbot 실행 전
    - step 1: chatbot 실행 후 / 그래프 종료
  • result["messages"]에는 해당 thread의 전체 메시지 히스토리가 들어있습니다.

3. 상태 히스토리 조회

state_history = graph.get_state_history(config)

for state_snapshot in list(state_history):
    print(state_snapshot.next)
    print(state_snapshot.values["messages"])
    print("======\n")
  • get_state_history()는 generator를 반환하므로 list()로 감싸거나 for로 순회합니다.
  • 각 state_snapshot에서 .next와 .values["messages"]를 출력하면 실행 흐름을 추적할 수 있습니다.

4. Time Travel — 과거 시점으로 되돌아가기

# Snapshot 2의 checkpoint_id를 가져온다
target_config = {
    "configurable": {
        "thread_id": "11",
        "checkpoint_id": "1f11e06c-bff3-627c-8000-99288ab5c8d5",
    }
}

# 이 시점(chatbot 실행 직전)부터 다시 실행
result = graph.invoke(None, config=target_config)
  • checkpoint_id를 config에 추가하면 해당 체크포인트의 상태를 복원합니다.
  • invoke(None)으로 호출하면 새 입력 없이 저장된 상태에서 이어서 실행합니다.
  • chatbot이 이번에는 다른 응답을 생성할 수 있습니다 (LLM의 비결정성).

update_state()와 분기 — 대화 중간을 수정하면 어떻게 되는가

핵심 원리: 수정이 아니라 분기(Fork)

update_state()로 과거 체크포인트의 메시지를 바꾸면, 기존 대화가 수정되는 것이 아니라 새 분기가 생성됩니다. Git에서 과거 커밋에서 새 브랜치를 만드는 것과 동일한 원리입니다.

원본:   1 → 2 → 3 → 4 → 5 → 6   (그대로 보존)
                     \
새 분기:              → 4' → A → B → ...  (새 타임라인)
  • 1~3: 두 분기가 공유하는 공통 히스토리
  • 4: 원본 브랜치의 원래 메시지 (사라지지 않음)
  • 4': update_state()로 수정된 메시지 (새 분기의 시작점)
  • 5, 6: 원본 브랜치에만 존재
  • A, B, ...: 새 분기에서 invoke()로 생성해야 할 후속 응답

수정 지점 이후의 메시지는?

\| \| 원본 브랜치 \| 새 분기 (fork) \|
\|---\|---\|---\|
\| 수정 지점 이전 \| 그대로 \| 동일하게 공유 \|
\| 수정 지점 \| 원래 메시지 그대로 존재 \| 수정된 메시지 \|
\| 수정 지점 이후 \| 원래 AI 응답 그대로 존재 \| 아직 없음 — invoke해야 생성 \|

새 분기에서는 수정 지점 이후의 메시지가 존재하지 않습니다. next=('chatbot',) 상태이므로 graph.invoke()를 호출해야 비로소 새 분기의 AI 응답이 생성됩니다.

노트북 예시로 보는 분기 흐름

원본 대화:
  Human("Valencia") → AI("Valencia 좋은 도시...") → Human("Valencia") → AI("Valencia 활기찬...")

update_state()로 분기:
  Human("Valencia") → AI("Valencia 좋은 도시...") → Human("Zagreb")  ← 여기서 분기!
                                                        ↓
                                                   next=('chatbot',)  ← AI 응답 아직 없음

코드 흐름

# 1. 과거 체크포인트 선택
to_fork = list(state_history)[-5]

# 2. 해당 시점의 메시지를 수정하여 새 분기 생성
graph.update_state(
    to_fork.config,
    {
        "messages": HumanMessage(
            content="I live in Europe now. And the city I live in is Zagreb.",
            id="1f11e0a5-cbf5-6258-8003-3b362392e228"  # 기존 메시지 ID → 덮어쓰기
        )
    }
)
# → 새 checkpoint_id가 반환됨 (원본은 그대로)

# 3. 새 분기에서 이어서 실행 (AI 응답 생성)
result = graph.invoke(None, config=forked_config)

왜 원본이 사라지지 않는가 — 체크포인트의 불변성

체크포인트는 불변(immutable)입니다. update_state()는 기존 체크포인트를 덮어쓰지 않고 항상 새 체크포인트를 생성합니다.

update_state() 호출 전:
  checkpoint A (원본) → checkpoint B → checkpoint C

update_state() 호출 후:
  checkpoint A (원본) → checkpoint B → checkpoint C     ← 원본 그대로
                             \
                              → checkpoint D (새 분기)  ← 새로 생긴 것

get_state_history()로 조회하면 원본 흐름과 분기된 흐름 모두 볼 수 있습니다. "Time Travel"이라는 이름인 이유가 여기 있습니다 — 과거로 돌아가서 다른 선택을 하면 그때부터 새로운 타임라인이 생깁니다.

주석으로 기억할 핵심 포인트

  • get_state_history()는 최신 → 과거 순으로 반환됩니다. 실제 실행 순서는 반대로 읽어야 합니다.
  • StateSnapshot.next는 "방금 실행한 노드"가 아니라 "다음에 실행될 노드"입니다.
  • step: -1은 그래프 시작 전 상태이고, step: 0부터 실제 노드 실행이 시작됩니다.
  • 하나의 invoke() 호출로 노드 수 + 2개의 체크포인트가 생깁니다 (입력 전 + 각 노드 후).
  • 같은 thread_id로 invoke()를 반복하면 메시지가 기존 것 위에 누적됩니다.
  • checkpoint_id를 config에 넣어 invoke(None)을 호출하면 해당 시점부터 다시 실행합니다.
  • parent_config는 바로 이전 체크포인트를 가리키므로, 체크포인트 간의 연결 관계를 추적할 수 있습니다.
  • update_state()는 기존 체크포인트를 수정하지 않고 새 분기 체크포인트를 생성합니다 (불변 원칙).
  • 분기 후 next에 노드가 남아있으면 invoke()를 호출해야 새 타임라인의 후속 응답이 생성됩니다.

같은 thread_id로 반복 실행하면 메시지가 누적되는 이유

같은 thread_id로 invoke()를 여러 번 실행하면 아래처럼 메시지가 계속 쌓입니다.

invoke 1회 후:
[Human, AI]

invoke 2회 후 (같은 thread_id, 같은 메시지):
[Human, AI, Human, AI]

invoke 3회 후:
[Human, AI, Human, AI, Human, AI]

이것은 checkpointer가 이전 실행의 최종 state를 복원한 뒤, 새 입력을 그 위에 추가하기 때문입니다. 이전 문서(14.2 Memory)에서 배운 것과 같은 원리입니다.

체크포인트도 함께 늘어납니다.

invoke 1회: 체크포인트 3개 (step -1, 0, 1)
invoke 2회: 체크포인트 6개 (1회차 3개 + 2회차 3개)
invoke 3회: 체크포인트 9개

초기화하려면 thread_id를 새 값으로 바꾸면 됩니다.

Before / After 비교

[Before]
- 그래프를 실행하면 결과만 받을 수 있었습니다.
- 중간에 어떤 상태를 거쳤는지 확인할 방법이 없었습니다.
- LLM 응답이 마음에 들지 않으면 처음부터 다시 실행해야 했습니다.

[After]
- get_state_history()로 모든 체크포인트를 조회할 수 있습니다.
- 각 스텝에서 messages가 어떻게 변했는지 추적할 수 있습니다.
- checkpoint_id를 사용해 과거 시점으로 돌아가 다시 실행할 수 있습니다 (Time Travel).
- 반복 실행 시 메시지가 누적되는 원리를 이해하고 thread_id로 제어할 수 있습니다.

핵심 변경사항 ② StateSnapshot 구조 이해

StateSnapshot 필드 정리

StateSnapshot(
    values      → 해당 시점의 state 전체 (messages 등)
    next        → 다음에 실행될 노드 (빈 튜플이면 종료)
    config      → checkpoint_id가 들어있는 config (Time Travel 키)
    metadata    → step 번호, source(input/loop) 등
    created_at  → 체크포인트 생성 시각
    parent_config → 바로 이전 체크포인트의 config
    tasks       → 해당 스텝의 태스크 정보 (실행 결과 포함)
    interrupts  → interrupt()로 중단된 경우의 정보
)

코드 의미

  • ① 무엇인가
  • 그래프 실행의 한 시점을 통째로 캡처한 객체의 구조입니다.
  • ② 어떻게 동작하는가
  • 그래프는 매 스텝마다 이 구조의 스냅샷을 checkpointer에 저장합니다.
    - next가 비어있으면 그래프가 종료된 시점이고, 값이 있으면 아직 실행할 노드가 남아있다는 뜻입니다.
  • ③ 실제 사용 방식
  • config.configurable.checkpoint_id를 추출해 Time Travel에 사용합니다.
    - metadata.step으로 몇 번째 스텝인지 빠르게 파악합니다.
  • ④ 왜 필요한가
  • 이 구조를 이해해야 get_state_history() 결과를 올바르게 해석할 수 있기 때문입니다.

코드 의미

  • ① 무엇인가
  • 과거 체크포인트의 상태를 복원해서 그래프를 다시 실행하는 Time Travel 코드입니다.
  • ② 어떻게 동작하는가
  • checkpoint_id를 config에 넣으면 checkpointer가 해당 시점의 state를 복원합니다.
    - invoke(None)은 새 입력 없이 복원된 state에서 next에 있는 노드부터 실행합니다.
    - 예를 들어 step 0 (chatbot 실행 직전)으로 돌아가면, chatbot이 다시 실행되어 다른 응답을 생성할 수 있습니다.
  • ③ 실제 사용 방식
  • LLM 응답 재생성, 디버깅, A/B 테스트 등에 사용합니다.
  • ④ 왜 필요한가
  • 프로덕션 환경에서 잘못된 응답이 나왔을 때, 전체 대화를 처음부터 다시 하지 않고 특정 분기점에서만 다시 시도할 수 있기 때문입니다.

  • "만약 사용자가 다른 메시지를 보냈다면?" 시나리오를 테스트할 때 사용합니다.
    - 잘못된 사용자 입력을 사후에 수정하고 다시 처리하고 싶을 때 사용합니다.
  • ④ 왜 필요한가
  • 대화 전체를 처음부터 다시 하지 않고, 특정 지점만 바꿔서 다른 결과를 얻을 수 있기 때문입니다.
    - 원본 대화가 보존되므로 A/B 비교, 디버깅, 롤백이 안전합니다.

import sqlite3
from langgraph.graph import StateGraph, START, END
from langchain.chat_models import init_chat_model
from langgraph.graph.message import MessagesState
from langgraph.checkpoint.sqlite import SqliteSaver

llm = init_chat_model("openai:gpt-4o-mini")

conn = sqlite3.connect(
    "memory.db",
    check_same_thread=False,
)

config = {
    "configurable": {
        "thread_id": "11",
    },
}

class State(MessagesState):
    pass


graph_builder = StateGraph(State)



def chatbot(state: State):
    response = llm.invoke(state["messages"])
    return {
        "messages": [response],
    }


graph_builder.add_node("chatbot", chatbot)

graph_builder.add_edge(START, "chatbot")
graph_builder.add_edge("chatbot", END)

graph = graph_builder.compile(
    checkpointer=SqliteSaver(conn),
)

result = graph.invoke(
    {
        "messages": [
            {
                "role": "user",

무엇을 해결하는가

  • 규칙문만으로 처리하기 어려운 이메일 분류를 LLM이 더 유연하게 처리하도록 만듭니다.
  • 점수 계산도 고정 맵이 아니라 이메일 내용과 카테고리를 함께 보고 판단하도록 바꿉니다.
  • 응답 문장도 템플릿 하드코딩 대신 실제 생성형 응답으로 대체합니다.
  • 테스트는 이런 변화 때문에 흔들리지 않도록, 결과 형식과 허용 범위를 중심으로 재설계합니다.

class PriorityScoreOutput(BaseModel):
    priority_score: int = Field(
            description = "Priority score from 1 to 10.",
            ge=1,
            le=10

def assign_priority(state: EmailState):

    result = s_llm.invoke(
        f"""Assign a priority score from 1-10 for this {state['category']} email.
        Consider:
        - Category: {state['category']}
        - Email content: {state.get('email',"")}

        Guidelines:

        - Normal emails: usually 4-7
        - Spam emails: usually 1-3"""

  • ① 무엇인가

  • 프롬프트에 카테고리와 본문을 주고, 1~10 범위 점수를 받습니다.
  • ③ 실제 사용 방식
  • 긴급 메일은 대체로 8~~10, 일반 메일은 4~~7, 스팸은 1~3 같은 정책을 프롬프트로 안내합니다.
  • ④ 왜 필요한가
  • 같은 normal 메일이어도 내용에 따라 실제 중요도가 달라질 수 있기 때문입니다.

main.py

from typing import Literal, List
from unicodedata import category
from pydantic import BaseModel, Field
from typing_extensions import TypedDict
from langgraph. graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver
from langchain.chat_models import init_chat_model

llm = init_chat_model("openai:gpt-4o")

checkpointer = MemorySaver()

class EmailState(TypedDict):
    email: str
    category: Literal["spam","normal","urgent"]
    priority_score: int
    response: str

class EmailClassificationOutput(BaseModel):
    category: Literal["spam", "normal", "urgent"] = Field(
            description="Category of the email"
        )

class PriorityScoreOutput(BaseModel):
    priority_score: int = Field(
            description = "Priority score from 1 to 10.",
            ge=1,
            le=10
        )




def categorize_email(state:EmailState):
    s_llm = llm.with_structured_output(EmailClassificationOutput)

    result = s_llm.invoke(
        f"""
            Classify this email into one of three categories:
            - urgent: time-sensitive, requires immediate attention
            - normal: regular business communication
            - spam: promotional, marketing, or unwanted content

            Email: {state['email']}
        """
    )

    return {
        "category": result.category
    }


def assign_priority(state: EmailState):
    s_llm = llm.with_structured_output(PriorityScoreOutput)

    result = s_llm.invoke(
        f"""Assign a priority score from 1-10 for this {state['category']} email.
        Consider:
        - Category: {state['category']}
        - Email content: {state.get('email',"")}

        Guidelines:
        - Urgent emails: usually 8-10
        - Normal emails: usually 4-7
        - Spam emails: usually 1-3"""
    )

    return {"priority_score": result.priority_score}

def draft_response(state: EmailState) -> EmailState:
    result = llm.invoke(
        f"""Draft a brief, professional response for this {state['category']} email.

        Original email: {state['email']}
        Category: {state['category']}
        Priority: {state['priority_score']}/10

        Guidelines:
        - Urgent: Acknowledge urgency, promise immediate attention
        - Normal: Professional acknowledgment, standard timeline
        - Spam: Brief notice that message was filtered

        Keep response under 2 sentences."""
    )
    return {
        "response": result.content,
    }

graph_builder = StateGraph(EmailState)

graph_builder.add_node("categorize_email", categorize_email)
graph_builder.add_node("assign_priority", assign_priority)
graph_builder.add_node("draft_response", draft_response)

graph_builder.add_edge(START, "categorize_email")
graph_builder.add_edge("categorize_email", "assign_priority")
graph_builder.add_edge("assign_priority", "draft_response")
graph_builder.add_edge("draft_response", END)

graph = graph_builder.compile(checkpointer=checkpointer)

## 현재 코드에서는 왜 `BaseModel`도 쓰나?

현재 `main.py`는 `TypedDict`와 `BaseModel`을 함께 사용하고 있습니다.

class EmailState(TypedDict):

email: str

category: Literal["spam", "normal", "urgent"]

priority_score: int

response: str

class EmailClassificationOutput(BaseModel):

category: Literal["spam", "normal", "urgent"] = Field(

description="Category of the email"

)


처음 보면 "`TypedDict` 대신 `BaseModel`로 바뀐 건가?"라고 느낄 수 있지만, 실제로는 역할이 다릅니다.

## 역할 차이

### `TypedDict`

`TypedDict`는 딕셔너리의 구조를 설명합니다.

이 프로젝트에서는 그래프가 공유하는 상태(state)를 표현하는 데 잘 어울립니다.

예를 들면 `EmailState`는:

- `email`
- `category`
- `priority_score`
- `response`

같은 키를 가진 상태 딕셔너리 구조를 설명합니다.

즉, `StateGraph(EmailState)`처럼 "그래프 상태가 어떤 모양인지" 알려주는 용도입니다.

### `BaseModel`

`BaseModel`은 단순 타입 설명을 넘어서 런타임 검증과 메타데이터를 함께 다룰 수 있습니다.

예를 들면:

- `Field(description="...")`로 필드 설명 추가
- `ge=1`, `le=10`처럼 값 범위 제한
- 잘못된 값이 들어오면 검증 에러 발생

즉, "`이런 형태의 데이터를 실제로 검증하고 싶다`"는 목적에 더 적합합니다.

## 언제 무엇을 쓰면 좋나?

### `TypedDict`가 더 자연스러운 경우

- LangGraph state처럼 딕셔너리 기반 상태를 표현할 때
- 타입 힌트와 자동완성이 주 목적일 때
- 런타임 검증까지는 필요하지 않을 때

### `BaseModel`이 더 자연스러운 경우

- LLM의 structured output 스키마를 정의할 때
- 입력/출력 데이터 검증이 필요할 때
- 각 필드에 설명이나 제약 조건을 주고 싶을 때

## 현재 `main.py`를 어떻게 이해하면 되나?

현재 코드 기준으로 보면:

- `EmailState`는 그래프 전체에서 공유되는 상태 구조
- `EmailClassificationOutput`, `PrioirityScoreOutput`은 개별 결과의 출력 스키마

라고 이해하면 됩니다.

즉, `TypedDict`가 없어지고 `BaseModel`로 완전히 바뀐 것이 아니라:

- 상태는 `TypedDict`
- 검증 가능한 출력 형식은 `BaseModel`

로 역할이 나뉜 것입니다.

## 한 줄 결론

현재 `main.py`에서 `TypedDict`와 `BaseModel`은 경쟁 관계가 아니라, 서로 다른 목적을 가진 타입 도구입니다.

17.6 Testing AI Responses

수정 목적

  • 기존 테스트에서 draft_response의 회신 품질을 정량적으로 검증하지 못한 점을 보완합니다.
  • 스팸/긴급/일반 응답이 기대되는 톤을 유지하는지 자동으로 확인할 수 있게 합니다.
  • 분류/우선순위 정보와 회신 문안 사이의 의존 관계를 주석으로 명확하게 기록합니다.

핵심 개념

  • 개념 한 줄 정의
  • with_structured_output은 LLM 출력 형식을 스키마로 고정해, 사람이 읽는 텍스트 대신 프로그램이 해석 가능한 값으로 받습니다.
  • 개념이 필요한 상황
  • 텍스트 유사도 판단이 필요하지만 표현 방식이 조금 바뀌어도 같은 의미로 허용해야 할 때 사용합니다.
  • 코드에서 이 개념이 맡는 역할
  • test.py의 judge_response가 스코어링 모델을 통해 회신 문안의 적합도를 판정합니다.

동작 흐름

  • 테스트가 draft_response 노드를 직접 실행합니다.
  • 생성된 응답을 judge_response에 전달합니다.
  • 분류별 예시 텍스트와 비교해 점수를 계산합니다.
  • 점수가 임계치 미만이면 테스트가 실패합니다.

사용 이유

  • 문자열 포함 검사보다 LLM 기반 스코어가 더 유연한 문장 품질 판별을 제공합니다.
  • 범주별 톤 가이드를 유지하면서도 문장 패턴 변화에 덜 민감하게 동작합니다.
  • 회귀 테스트 시 회신 내용 품질이 떨어지는 것을 조기에 감지할 수 있습니다.

한 줄 요약

  • draft_response 결과를 텍스트 유사도 점수로 검증해 회신 품질의 자동 품질 관문을 만든 변경입니다.

이번 변경으로 무엇을 공부할 수 있었는가

  • Pydantic 스키마 기반 구조화 출력의 안정성
  • 테스트에서 LLM을 심사자(judge)로 사용하는 패턴
  • 노드 단위 테스트와 노드 통합 실행 테스트의 보완 관계

무엇을 해결하는가

  • 회신 결과가 의미상 맞아도 문장 형태가 달라지는 경우에도 품질을 허용 범위 내에서 판단합니다.

main.py

from typing import Literal, List
from unicodedata import category
from pydantic import BaseModel, Field
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver
from langchain.chat_models import init_chat_model

llm = init_chat_model("openai:gpt-4o")

checkpointer = MemorySaver()

class EmailState(TypedDict):
    email: str
    category: Literal["spam","normal","urgent"]
    priority_score: int
    response: str

class EmailClassificationOutput(BaseModel):
    category: Literal["spam", "normal", "urgent"] = Field(
            description="Category of the email"
        )

class PriorityScoreOutput(BaseModel):
    priority_score: int = Field(
            description="Priority score from 1 to 10.",
            ge=1,
            le=10
        )


def categorize_email(state: EmailState):
    s_llm = llm.with_structured_output(EmailClassificationOutput)

    result = s_llm.invoke(
        f"""
            Classify this email into one of three categories:
            - urgent: time-sensitive, requires immediate attention
            - normal: regular business communication
            - spam: promotional, marketing, or unwanted content

            Email: {state['email']}
        """
    )

    return {
        "category": result.category
    }


def assign_priority(state: EmailState):
    s_llm = llm.with_structured_output(PriorityScoreOutput)

    result = s_llm.invoke(
        f"""Assign a priority score from 1-10 for this {state['category']} email.
        Consider:
        - Category: {state['category']}
        - Email content: {state.get('email',"")}

        Guidelines:
        - Urgent emails: usually 8-10
        - Normal emails: usually 4-7
        - Spam emails: usually 1-3"""
    )

    return {"priority_score": result.priority_score}


def draft_response(state: EmailState) -> EmailState:
    # 이전 노드에서 계산한 분류와 우선순위를 바탕으로 회신 초안을 생성한다.
    result = llm.invoke(
        f"""Draft a brief, professional response for this {state['category']} email.

        Original email: {state['email']}
        Category: {state['category']}
        Priority: {state['priority_score']}/10

        Guidelines:
        - Urgent: Acknowledge urgency, promise immediate attention
        - Normal: Professional acknowledgment, standard timeline
        - Spam: Brief notice that message was filtered

        Keep response under 2 sentences."""
    )
    return {
        "response": result.content,
    }

graph_builder = StateGraph(EmailState)

graph_builder.add_node("categorize_email", categorize_email)
graph_builder.add_node("assign_priority", assign_priority)
graph_builder.add_node("draft_response", draft_response)

graph_builder.add_edge(START, "categorize_email")
graph_builder.add_edge("categorize_email", "assign_priority")
graph_builder.add_edge("assign_priority", "draft_response")
graph_builder.add_edge("draft_response", END)

graph = graph_builder.compile(checkpointer=checkpointer)

18.3 Supervisor Architecture

수정 목적

  • 기존 handoff_tool 중심 분산 전달 구조를 supervisor 중심 중앙 라우팅 구조로 바꿉니다.
  • 언어 에이전트(korean/greek/spanish)는 처리 전용 노드로 단순화하고, 라우팅 결정은 supervisor가 전담합니다.
  • 라우팅 결정 근거(reasoning)를 상태에 남겨 디버깅 가능성을 높입니다.

핵심 개념

  • SupervisorOutput:
  • next_agent와 reasoning을 강제하는 구조화 출력 스키마입니다.
  • supervisor(state):
  • 대화 이력을 보고 다음 노드를 고르는 제어 플레인 노드입니다.
  • AgentsState.reasoning:
  • 왜 해당 노드로 보냈는지 추적 가능한 상태 필드입니다.

동작 흐름

  • START -> supervisor
  • supervisor -> (korean_agent | greek_agent | spanish_agent | END)
  • 각 언어 에이전트 처리 후 다시 supervisor로 복귀
  • supervisor가 다음 라우팅 또는 종료를 결정

사용 이유

  • 에이전트마다 handoff 규칙을 중복 구현하지 않아도 됩니다.
  • 라우팅 정책 변경 시 supervisor만 수정하면 됩니다.
  • 중앙 제어 구조라 관측성과 운영 안정성이 높아집니다.

한 줄 요약

  • 이번 diff의 핵심은 멀티 에이전트 구조를 Agent-to-Agent handoff에서 Supervisor-Orchestrated Routing으로 전환한 것입니다.

2️⃣ paint_history()의 의미

📌 왜 필요한가?

Streamlit은 사용자 인터랙션이 발생할 때마다 전체 스크립트를 다시 실행한다.

즉:

  • 메시지를 입력하면
  • 스크립트가 위에서부터 다시 실행되고
  • 화면은 새로 렌더링된다

만약 과거 메시지를 다시 그려주지 않으면

→ 화면에는 방금 입력한 것만 보이게 된다.

따라서:

DB에 저장된 과거 메시지를 다시 불러와서

화면에 재렌더링해주는 과정이 반드시 필요하다.

그 역할이 paint_history()이다.

3️⃣ 동작 흐름 정리

1️⃣ 세션에서 과거 메시지 조회

messages = await session.get_items()

SQLiteSession에 저장된 모든 대화 기록을 가져온다.

2️⃣ 메시지 하나씩 순회

for message in messages:

저장된 모든 메시지를 시간 순서대로 처리한다.

3️⃣ role에 따라 말풍선 생성

with st.chat_message(message["role"]):
  • “user” → 사용자 말풍선
  • “assistant” 또는 “ai” → AI 말풍선

4️⃣ user 메시지 처리

st.write(message["content"])

user 메시지는 단순 문자열이므로 그대로 출력.

5️⃣ AI 메시지 처리 (중요)

AI 응답은 단순 문자열이 아니다.

구조 예시:

{
  "role": "assistant",
  "type": "message",
  "content": [
      {
          "type": "output_text",
          "text": "안녕하세요"
      }
  ]
}

즉:

  • content가 배열
  • 여러 종류의 출력이 섞일 수 있음
  • tool call, refusal, 이미지 등도 포함 가능

그래서:

if message["type"] == "message":

일반 대화 메시지만 필터링하고

st.write(message["content"][0]["text"])

텍스트만 꺼내서 출력한다.

4️⃣ paint_history가 실행되는 위치

asyncio.run(paint_history())

이 위치가 매우 중요하다.

이 코드는:

  • 페이지가 실행될 때
  • 새로운 입력을 받기 전에
  • 먼저 과거 대화를 전부 그려준다

그래야:

  • 과거 대화가 유지된 것처럼 보이고
  • 그 아래에 새 대화가 이어진다

5️⃣ 전체 구조 정리 (한 줄 요약)

paint_history()는

SQLite에 저장된 과거 대화를

Streamlit이 재실행될 때마다 다시 화면에 복원해주는 역할을 한다.

이게 없으면

Streamlit은 매번 “새 화면”처럼 보이게 된다.

6️⃣ 구조적으로 보면

이제 앱은 이렇게 동작한다:

  1. Agent 생성
  2. Session 연결
  3. ⭐ 과거 대화 복원 (paint_history)
  4. 사용자 입력 받기
  5. AI 스트리밍 응답
  6. 응답은 자동으로 DB에 저장됨
  7. 다음 입력 시 1~6 반복

수정 목적

  • 고객 문의를 triage에서 모두 직접 처리하던 구조에서, 문의 유형별 specialist로 분리 라우팅하도록 변경했습니다.
  • 범위를 벗어난 질문은 가드레일에서 걸러내고, 범위 내 질문은 적절한 전문 에이전트로 넘기는 책임 구조를 고정했습니다.
  • handoff 전후 근거를 코드에서 추적할 수 있게 하여 운영 안정성을 높였습니다.

핵심 개념

  • 고객 지원 시스템은 분류용 triage와 처리용 specialist를 분리해야 명확한 책임이 생깁니다.
  • handoff는 triage가 요청 분류 후 제어권을 specialist에게 넘기는 라우팅 동작입니다.
  • HandoffData와 handoff_filters가 라우팅 품질을 일정하게 유지하도록 돕습니다.
  • 쉬운 말로 정리하면, 접수팀이 분류표를 작성해 알맞은 팀으로 전달하고, 전달 전 불필요한 잡음을 제거한 뒤 보내는 방식입니다.

  • User → main.py에서 입력 수신.
  • Input Guardrail에서 off-topic 여부를 먼저 검사.
  • 통과하면 triage가 카테고리 분류 후 specialist 후보를 판단.

사용 이유

  • 디버깅: 어떤 요청이 누구에게 어떻게 넘어갔는지 근거를 남겨 추적 가능합니다.
  • 유지보수: 기능 추가/수정 시 triage와 전문가 에이전트 책임이 분리되어 관리가 쉽습니다.
  • 확장성: specialist를 추가하면 handoffs 등록만으로 라우팅 대상을 늘릴 수 있습니다.

한 줄 요약

  • triage의 역할을 분류·이동 중심으로 바꾸고 specialist에게 처리권을 넘겨 더 안전한 고객지원 멀티에이전트 구조를 만들었습니다.

무엇을 해결하는가

  • triage가 모든 응답을 직접 만들던 책임 과다 문제를 완화합니다.
  • specialist 전환 근거가 모호하던 문제를 데이터 구조화로 정리합니다.
  • handoff 전달 시 tool 메타 데이터가 섞이는 위험을 필터로 제거합니다.

Delta vs Message Output Item 완전 정리

이 문서는 LLM 스트리밍 구조에서 delta와 message_output_item의 차이와 사용 목적을 명확하게 정리한다.

Agent, Streaming, UI, Backend 설계까지 연결되는 핵심 개념이다.

📌 1️⃣ 전체 개념 한 줄 요약

delta = "토큰 단위 실시간 출력"
message_output_item = "완성된 최종 응답"

📌 2️⃣ 전체 구조

LLM 응답은 두 레벨로 나뉜다:

[ Low-Level ]
raw_response_event
  └── delta (토큰 단위)

[ High-Level ]
run_item_stream_event
  └── message_output_item (완성된 메시지)

📌 3️⃣ delta (Low-Level Streaming)

🔹 정의

delta는 LLM이 생성하는 토큰 단위 출력 조각이다.

"I'm" → " doing" → " well" → "!"

🔹 특징

  • 실시간 생성됨
  • 순서대로 이어붙여야 의미가 완성됨
  • 매우 작은 단위 (token)
  • raw_response_event 내부에 존재

🔹 위치

if event.type == "raw_response_event":
    # 여기에 delta 있음

🔹 사용 목적

1. 실시간 UI

  • ChatGPT 스타일 타이핑 효과
  • 글자가 한 글자씩 나오는 경험

2. 사용자 경험 향상

  • 기다리는 느낌 감소
  • 즉각적인 반응 제공

3. 스트리밍 처리

  • 긴 응답도 바로 출력 가능
  • 응답 완료 전에 보여줄 수 있음

🔹 사용 예시 코드

async for event in stream.stream_events():
    if event.type == "raw_response_event":
        print(event.data, end="", flush=True)

📌 4️⃣ message_output_item (High-Level Output)

🔹 정의

message_output_item은 LLM이 생성한 완성된 최종 응답 객체다.

🔹 특징

  • 하나의 완성된 메시지
  • 구조화된 형태
  • Tool 결과까지 반영된 상태
  • 바로 사용자에게 반환 가능

🔹 위치

if event.type == "run_item_stream_event":
    if event.item.type == "message_output_item":

🔹 내부 구조

{
  "type": "message_output_item",
  "content": [
    {
      "type": "output_text",
      "text": "I'm doing well! The weather in Spain is 30 degrees."
    }
  ]
}

🔹 사용 목적

1. 백엔드 응답 처리

  • API response 반환
  • 서비스 로직 처리

2. 결과 저장

  • DB 저장
  • 로그 기록

3. 후처리

  • 텍스트 가공
  • 요약, 필터링 등

🔹 사용 예시 코드

async for event in stream.stream_events():
    if event.type == "run_item_stream_event":
        if event.item.type == "message_output_item":
            for content in event.item.content:
                if content.type == "output_text":
                    print(content.text)

📌 5️⃣ delta vs message_output_item 비교

구분 delta message_output_item
레벨 Low-Level High-Level
단위 토큰 완성된 메시지
생성 시점 생성 중 생성 완료 후
위치 raw_response_event run_item_stream_event
형태 문자열 조각 구조화된 객체
사용 목적 UI 스트리밍 최종 응답 처리

📌 6️⃣ 흐름으로 이해하기

LLM 생성 시작
↓
delta (토큰 계속 생성)
↓
delta 누적
↓
LLM 완료
↓
message_output_item 생성

📌 7️⃣ 중요한 차이 (핵심)

❗ delta는 “과정”

❗ message_output_item은 “결과”

🔹 delta

"응답을 만들어가는 중"

🔹 message_output_item

"응답이 완성됨"

📌 8️⃣ 언제 무엇을 써야 하는가

🔹 delta를 써야 하는 경우

  • 채팅 UI 구현
  • 스트리밍 출력
  • 실시간 반응
예: ChatGPT, Slack bot typing effect

🔹 message_output_item을 써야 하는 경우

  • API 서버 응답
  • DB 저장
  • Agent 결과 처리
예: FastAPI 응답, 로그 저장

📌 9️⃣ 실전 설계 기준 (중요)

✅ UI 레이어

delta 사용

✅ Backend / Agent 레이어

message_output_item 사용

✅ 둘 다 사용하는 구조

delta → 사용자에게 실시간 출력
message_output_item → 최종 결과 저장

📌 🔥 최종 결론

delta는 실시간 경험을 위한 스트리밍 데이터이고

message_output_item은 실제 서비스에서 사용하는 최종 결과다

이거 이해했으면 다음 단계 바로 가능하다:

  • streaming + tool_call 동시에 처리
  • multi-step agent에서 메시지 여러 개 나오는 구조
  • LangGraph node 설계

후속 단계에서는 이 흐름을 실제 코드까지 연결한다.

guardrail, triage_agent는 병렬이다.

Triage Agent와 Guardrail의 병렬 실행 정리

1. 최초 의문

stream.stream_events() 루프에서 is_off_topic=True인데도 guardrail의 에러가 즉시 발생하지 않고, triage_agent의 응답 토큰이 먼저 화면에 출력되는 현상이 있었다. 예상대로라면 guardrail이 먼저 판단을 끝내고, off-topic이면 바로 예외가 발생해야 할 것 같았다.

2. 원인

Runner.run_streamed()는 guardrail과 main agent를 순차가 아닌 병렬(concurrent)로 실행한다.

[t0] Runner.run_streamed() 호출
 ├─ Guardrail 실행 시작 (Runner.run → 비스트리밍)
 └─ Triage Agent 스트리밍 시작 (동시에)

[t0 ~ t2] Triage Agent가 토큰을 계속 스트리밍
           Guardrail은 아직 판단 중...

[t2] Guardrail 완료 → tripwire_triggered=True
     → InputGuardrailTripwireTriggered 예외 발생
     → 스트림 중단

3. 로그로 증명

타임스탬프 로그를 삽입하여 실제 실행 순서를 확인했다.

[GUARDRAIL] 시작          — 423.3347
[Triage Agent] 토큰 #1    — 423.8873  ← guardrail 완료 전에 이미 토큰 도착
[Triage Agent] 토큰 #2    — 423.8881
[Triage Agent] 토큰 #3    — 423.8899
[GUARDRAIL] 완료          — 425.4036  ← 토큰 #1보다 1.5초 늦게 완료
[TripwireTriggered]       — 425.4039  ← 완료 직후 0.0003초 만에 예외 발생
  • Triage Agent 토큰이 Guardrail 완료보다 1.5초 먼저 도착 → 병렬 실행 확정
  • Guardrail 완료 시점까지 이미 43개 토큰이 스트리밍됨
  • stream.current_agent.name으로 확인한 결과, 스트리밍된 토큰은 모두 Triage Agent 소속이었고, Guardrail Agent의 토큰은 이 스트림에 섞이지 않았음

4. 왜 이렇게 설계되었는가

성능 최적화 때문이다.

시나리오 병렬 실행 (현재) 순차 실행 (대안)
정상 요청 (대부분) guardrail 대기 없이 즉시 스트리밍 시작 guardrail 완료까지 ~2초 대기 후 스트리밍
off-topic 요청 일부 토큰이 출력된 후 중단 토큰 출력 없이 즉시 차단

대부분의 요청이 정상인 상황에서, 매번 guardrail 완료를 기다리면 모든 응답에 ~2초 지연이 추가된다. 병렬 실행은 정상 케이스의 응답 속도를 우선시하는 trade-off다.

순차실행

Runner.run() — 순차 실행

[t0] guardrail 실행 시작
[t1] guardrail 완료 → is_off_topic 판단
     ├─ True  → 즉시 예외 발생 (main agent 실행 안 함)
     └─ False → [t2] main agent 실행 시작
               [t3] main agent 완료 → 응답 반환

guardrail이 끝나야 main agent가 시작됩니다. 그래서 off-topic이면 토큰이 하나도 생성되지 않습니다.

Runner.run_streamed() — 병렬 실행

[t0] guardrail 실행 시작 ─────────────────── [t2] 완료 → 판단
[t0] main agent 스트리밍 시작 → 토큰 토큰 토큰 ... → [t2] 예외 발생 시 중단

guardrail과 main agent가 동시에 시작됩니다. 그래서 guardrail이 판단하는 동안 main agent의 토큰이 먼저 나올 수 있었던 것이고, 아까 로그에서 확인한 그 현상입니다.

왜 이렇게 다른가

스트리밍의 목적 자체가 빠른 응답 시작이기 때문입니다. guardrail 완료를 기다리면 스트리밍의 의미가 없어지므로, SDK 설계상 run_streamed()는 성능을 위해 병렬로 동작하도록 만들어진 것입니다.

OpenAI Agents SDK – 트레이싱과 멀티 에이전트 구조

1️⃣ OpenAI는 트레이싱 기능을 제공한다

원문 외부 그림 공개 제외: 강의·도구 화면 또는 출처가 불명확한 그림은 재배포하지 않았다. 코드와 설명은 보존했다.

OpenAI Agents SDK에서 Runner.run()을 호출하면

Agent 실행 과정이 자동으로 Trace로 기록된다.

Dashboard → Logs → Traces 화면에서 다음을 확인할 수 있다:

  • 어떤 Agent가 실행되었는지
  • handoff가 발생했는지
  • tool이 호출되었는지
  • 실행 시간
  • LLM API 호출 내역 (POST /v1/responses)
  • 최종 응답

즉, 단순히 결과만 보는 것이 아니라

“Agent 내부 실행 흐름”을 관찰할 수 있다.

이것이 OpenAI의 트레이싱 기능이다.

2️⃣ 기본 원리: run 기준으로 trace가 생성된다

가장 중요한 개념은 이것이다.

Runner.run() 1번 호출 = 기본적으로 1개의 trace 생성

예:

result = await Runner.run(main_agent, "hello")

이 한 번의 실행은

Dashboard에서 하나의 trace로 보인다.

3️⃣ 멀티 에이전트 구조에서는 어떻게 보이는가?

예를 들어 이런 구조가 있다고 하자.

main_agent (Router)
    ↓
geography_agent
    ↓
get_weather() tool

Router가 Specialist Agent로 넘기고

Specialist Agent가 Tool을 호출한다.

이 경우 여러 Agent가 실행되지만

이 모든 것이 하나의 run 안에서 일어난 일이라면

이미 하나의 trace로 묶인다.

그래서 Dashboard에서는 이렇게 보인다:

Assistant Agent
  └── Handoff → Geo Expert Agent
Geo Expert Agent
  └── POST /v1/responses

즉,

  • Agent 여러 개
  • handoff 발생
  • tool 호출

이 모든 것이 하나의 trace 안에서 계층 구조로 표시된다.

4️⃣ trace 없이 실행하면?

result = await Runner.run(
    main_agent,
    "what is weather in Spain?",
    session=session,
)

이 경우에도 trace는 생성된다.

(왜냐하면 run 자체가 trace를 만든다.)

따라서,

멀티 에이전트가 하나의 run 안에 있다면

이미 하나의 trace로 묶인다.

5️⃣ 그럼with trace()는 왜 쓰는가?

여기서 중요한 차이가 나온다.

with trace()는

여러 run 호출을 하나의 상위 workflow trace로 묶고 싶을 때 사용한다.

예:

with trace("workflow"):
    await Runner.run(agent1, "question 1")
    await Runner.run(agent2, "question 2")

이 경우:

  • run 1 → 내부 trace
  • run 2 → 내부 trace
원문 외부 그림 공개 제외: 강의·도구 화면 또는 출처가 불명확한 그림은 재배포하지 않았다. 코드와 설명은 보존했다.

이 두 개가 하나의 상위 workflow trace 안에 들어간다.

즉,

Workflow Trace
    ├── run 1
    └── run 2

구조가 된다.

6️⃣ 개념을 정확히 정리하면

✔ 기본 규칙

  • Runner.run() 1번 호출 → 1 trace 생성

✔ 멀티 에이전트 (handoff 구조)

  • 하나의 run 안에서 여러 Agent 실행
  • 그래도 1 trace

✔ 여러 run을 묶고 싶으면

  • with trace() 사용
  • 상위 workflow trace 생성

7️⃣ 네 질문에 대한 정확한 답

agent 단위는 무조건 하나의 트레이싱으로 묶이는거고

여러 agent를 하나의 트레이싱으로 묶으려면 with를 쓰는거 아니냐

정확히 말하면:

  • Agent 단위가 아니라 run 단위로 trace가 생성된다.
  • 하나의 run 안에서 실행된 여러 Agent는 이미 하나의 trace다.
  • 여러 Runner.run() 호출을 하나로 묶고 싶을 때 with trace()를 사용한다.

🔥 한 줄 요약

run 기준으로 trace가 생성되고,

with trace는 run 여러 개를 묶는 상위 컨테이너다.

이제 개념이 완전히 정리됐다.

OpenAI Agents SDK Handoff

1️⃣ 전체 코드

아래는 현재 handoff 구조 전체 코드다.

from agents import Agent, Runner, SQLiteSession

# 세션 생성 (user 단위 메모리)
session = SQLiteSession("user_2", "ai-memory.db")

# ----------------------------
# 1. Geography Expert Agent
# ----------------------------
geography_agent = Agent(
    name="Geo Expert Agent",
    instructions="You are an expert in geography. You answer questions related to geography.",
    handoff_description="Use this agent to answer geography related questions."
)

# ----------------------------
# 2. Economics Expert Agent
# ----------------------------
economics_agent = Agent(
    name="Economics Expert Agent",
    instructions="You are an expert in economics. You answer questions related to economics.",
    handoff_description="Use this agent to answer economics questions."
)

# ----------------------------
# 3. Main Router Agent
# ----------------------------
main_agent = Agent(
    name="Assistant Agent",
    instructions="""
You are a router agent.
You must NEVER answer directly.
If the question is about geography, transfer to Geo Expert Agent.
If the question is about economics, transfer to Economics Expert Agent.
""",
    handoffs=[geography_agent, economics_agent],
)

# ----------------------------
# 4. 실행
# ----------------------------
result = await Runner.run(
    main_agent,
    "why do countries sell bonds?",
    session=session,
)

print(result.last_agent.name)
print(result.final_output)

await session.clear_session()

2️⃣ 전체 구조 이해

현재 구조는 Router + Expert 구조다.

Assistant Agent (Router)
 ├── Geo Expert Agent
 └── Economics Expert Agent

각 Agent의 역할은 명확하다.

3️⃣ 각 Agent의 역할

🔹 1. Geography Agent

  • 지리 관련 질문에 답변
  • 직접 사용자와 대화하지 않음
  • Router가 넘겨줘야만 실행됨

🔹 2. Economics Agent

  • 경제 관련 질문에 답변
  • Router가 경제 질문이라고 판단할 때 호출됨

🔹 3. Main Agent (Router)

핵심 역할:

  • 직접 답하지 않음
  • 질문을 분석
  • 적절한 Expert에게 handoff

여기서 가장 중요한 문장:

You must NEVER answer directly.

이 문장이 있어야 Router가 직접 답하지 않는다.

4️⃣ handoff의 동작 원리

handoff는 자동 분기 로직이 아니다.

handoffs=[geography_agent, economics_agent]

이건 단순히:

“이 Agent들로 전환 가능하다”

라는 선언이다.

실제 전환 여부는 LLM이 판단한다.

5️⃣ 실행 시 내부 흐름

질문:

why do countries sell bonds?

실행 흐름은 다음과 같다.

STEP 1

Runner가 main_agent를 LLM에 전달

STEP 2

LLM이 main_agent instruction을 읽음

판단:

이 질문은 economics 관련이다

→ Economics Expert Agent로 handoff

STEP 3

Runner가 Economics Expert Agent로 컨텍스트 전환

STEP 4

Economics Expert Agent가 최종 답변 생성

STEP 5

결과 반환

print(result.last_agent.name)

출력:

Economics Expert Agent

6️⃣ result.last_agent의 의미

result.last_agent.name

이 값은:

최종 응답을 생성한 Agent의 이름

Router가 직접 답하면 "Assistant Agent"

Expert가 답하면 "Geo Expert Agent" 또는 "Economics Expert Agent"

7️⃣ handoff_description의 역할

각 Expert Agent에 있는:

handoff_description="Use this agent to answer economics questions."

이 값은:

  • Router가 판단할 때 참고하는 메타 정보
  • LLM이 어떤 Agent를 선택할지 판단하는 힌트

8️⃣ handoff vs tool call 차이

구분 handoff tool call
목적 Agent 전환 함수 실행
LLM Persona 바뀜 그대로
응답 생성 주체 새로운 Agent 기존 Agent

handoff는 persona 전환이다.

9️⃣ 이 구조의 특징

장점

  • 자연어 기반 라우팅
  • 확장 쉬움
  • 새로운 Expert 추가 간단

단점

  • 비결정적
  • 질문 표현에 따라 달라질 수 있음
  • 완전한 통제 어려움

🔟 핵심 정리

현재 코드의 handoff 구조는 다음과 같다.

1. Main Agent는 Router 역할
2. 질문 분석
3. 적절한 Expert 선택
4. Expert가 최종 응답 생성
5. last_agent는 최종 응답 Agent

즉,

Router는 절대 답하지 않고

전문가 Agent에게 위임하는 구조다.

Session + Function Calling으로 완성하는 OpenAI Agent 내부 동작 원리

📌 Stateless 기반 Agent 구조 정리

이 문서는 LLM Agent가 어떻게 동작하는지를

Stateless 관점에서 4가지 핵심 요소로 나누어 정리한다.

📌 1️⃣ Stateless

🔹 정의

LLM은 상태를 저장하지 않는다.

이전 대화를 기억하지 않는다
이전 tool 사용을 기억하지 않는다
이전 실행 결과도 기억하지 않는다

🔹 의미

LLM 입장에서는 모든 요청이:

"완전히 새로운 요청"

이다.

🔹 결과

그래서 매 요청마다 반드시 전달해야 한다:

messages (대화 내용)
tools (사용 가능한 기능)
system instructions (역할 정의)

🔹 핵심 포인트

LLM은 기억하는 존재가 아니라

매번 정보를 받아서 판단하는 엔진이다

📌 2️⃣ Session

🔹 정의

Session은 대화를 저장하는 외부 저장소다.

예: SQLiteSession

🔹 역할

1. 이전 대화 저장
2. 다음 요청 시 불러오기
3. messages 형태로 LLM에 전달

🔹 동작 구조

DB 저장
↓
다음 요청 시 조회
↓
messages 배열 생성
↓
LLM 요청에 포함

🔹 중요한 포인트

Session = LLM의 메모리 ❌
Session = 메시지 저장소 ✔

🔹 착시 현상

"LLM이 기억한다"

처럼 보이지만 실제로는:

외부에서 계속 다시 넣어주는 것

이다.

📌 3️⃣ Tools

🔹 정의

LLM이 사용할 수 있는 외부 기능 목록

🔹 구성 요소

  • 함수 이름
  • 설명
  • 파라미터 구조 (JSON Schema)

🔹 실제 전달 형태

매 요청마다 LLM에 전달된다:

{
  "name": "get_weather",
  "description": "Get weather by city",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string" }
    }
  }
}

🔹 핵심 특징

LLM은 tool을 기억하지 않는다
→ 매 요청마다 다시 전달해야 한다

🔹 역할

LLM이 "무엇을 할 수 있는지" 정의하는 영역

📌 4️⃣ Function Call

🔹 정의

LLM이 tool을 사용해야 한다고 판단한 결과

🔹 발생 흐름

사용자 질문
↓
messages + tools + system 전달
↓
LLM 판단
↓
"tool 필요하다"
↓
function_call 생성

🔹 예시

{
  "tool_name": "get_weather",
  "arguments": {
    "city": "Seoul"
  }
}

🔹 중요한 포인트

function_call은 실행이 아니라 "결정"

🔹 실행은 누가 하냐

Runner (SDK)가 수행한다

📌 🔥 전체 흐름 연결

Stateless (LLM은 기억 안함)
↓
Session → messages 제공
↓
Tools → 기능 정의 제공
↓
LLM 호출
↓
Function Call 생성 (tool 사용 결정)
↓
Runner가 tool 실행
↓
결과 다시 LLM 전달
↓
최종 응답 생성

📌 🔥 핵심 관계 한 번에 정리

Stateless LLM을 Stateful 시스템으로 만드는 법

— Streamlit + SQLiteSession + Streaming + asyncio 구조 완전 정리

📌 전체 코드

import asyncio
import streamlit as st
import dotenv

dotenv.load_dotenv()

from agents import Agent , Runner, SQLiteSession

if "agent" not in st.session_state:
    st.session_state["agent"] = Agent(
        name="ChatGPT Clone",
        instructions="""
        You are a helpful assistant.
        """
    )
agent = st.session_state["agent"]

if "session" not in st.session_state:
    st.session_state["session"] = SQLiteSession("chat-history", "chat-gpt-clone-memory.db")

session = st.session_state["session"]

async def run_agent(message):
    stream = Runner.run_streamed(
        agent,
        message,
        session=session,
    )

    with st.chat_message("ai"):
        placeholder = st.empty()
        full_text = ""

        async for event in stream.stream_events():
            if event.type == "raw_response_event":
                if event.data.type == "response.output_text.delta":
                    full_text += event.data.delta
                    placeholder.markdown(full_text)

prompt = st.chat_input("Write a message for your assistant")

if prompt:
    with st.chat_message("human"):
        st.write(prompt)
    asyncio.run(run_agent(prompt))

with st.sidebar:
    reset = st.button("Reset memory")
    if reset:
        asyncio.run(session.clear_session())
    st.write(asyncio.run(session.get_items()))

📌 이 문서에서 정리하는 핵심

이 실습을 통해 이해한 것:

  • LLM은 왜 Stateless인가
  • 어떻게 세션 메모리를 붙이는가
  • 스트리밍 응답은 내부적으로 어떻게 오는가
  • Streamlit은 왜 매번 재실행되는가
  • 왜 asyncio로 래핑해야 하는가

이 코드는 단순 챗봇이 아니라

LLM 애플리케이션 아키텍처의 축소판이다.

1️⃣ LLM은 기본적으로 Stateless

LLM은 이전 대화를 기억하지 않는다.

Runner.run_streamed(
    agent,
    message,
    session=session,
)

여기서 session을 전달하지 않으면

매번 완전히 새로운 요청이 된다.

즉,

LLM은 기억하지 않는다.

우리가 “기억 시스템”을 붙여주는 것이다.

2️⃣ SQLiteSession이 하는 일

SQLiteSession("chat-history", "chat-gpt-clone-memory.db")

이 객체는:

  • 대화 기록을 DB에 저장
  • 다음 요청 때 자동으로 이전 메시지를 불러와 LLM에 함께 전달

결과적으로:

LLM은 Stateless

시스템은 Stateful

이 구조가 만들어진다.

3️⃣ 스트리밍 응답의 본질

async for event in stream.stream_events():

여기서 중요한 점:

  • 응답은 한 번에 오지 않는다
  • 토큰 단위(delta)로 들어온다
  • 우리가 이어붙여서 보여줄 뿐이다
full_text += event.data.delta

즉,

LLM은 완성된 문장을 주는 것이 아니라

토큰 스트림을 밀어주는 것이다.

UI는 그걸 이어붙여서 “문장처럼” 보이게 한다.

4️⃣ Streamlit은 왜 매번 재실행되는가

Streamlit은 사용자 인터랙션이 발생할 때마다:

  • 스크립트 전체 재실행
  • 지역 변수 초기화
  • 객체 다시 생성

그래서 상태 유지를 위해 반드시 필요하다:

st.session_state

이 패턴:

if "agent" not in st.session_state:
    st.session_state["agent"] = Agent(...)

이를 통해:

Streamlit은 겉으로 Stateless처럼 보이지만

Stateful 시스템으로 만들 수 있다.

5️⃣ st.empty()의 UI 동작 원리

placeholder = st.empty()
placeholder.markdown(full_text)

empty()는:

  • 하나의 슬롯을 잡아둔다
  • 다시 호출하면 이전 내용을 덮어쓴다
  • 매번 전체를 다시 그리지만

사용자 눈에는 “점점 추가되는 것처럼” 보인다.

이건 UI 트릭이다.

6️⃣ 🔥 asyncio를 왜 래핑했는가?

이게 오늘 가장 중요한 구조 이해다.

6-1️⃣ 문제 상황

  • run_agent()는 async 함수
  • stream.stream_events()도 async iterator
  • session.get_items()도 async 함수

하지만

Streamlit은 기본적으로 동기 실행 환경이다.

여기서는 await를 직접 사용할 수 없다.

6-2️⃣ 그래서 등장하는 asyncio.run()

asyncio.run(run_agent(prompt))

이 함수는:

  1. 이벤트 루프 생성
  2. 코루틴 실행
  3. 완료될 때까지 블로킹
  4. 결과 반환
  5. 이벤트 루프 종료

즉,

비동기 코드를

동기 코드처럼 실행하게 만드는 브릿지다.

6-3️⃣ 왜 그냥 async 구조로 안 했는가?

Streamlit은:

  • 스크립트 기반 실행 모델
  • async def main() 구조가 아님
  • 자체 이벤트 루프를 직접 노출하지 않음

그래서:

  • await 사용 불가
  • 이벤트 루프 직접 관리 필요

결론:

asyncio.run()

으로 감싸서 동기 환경에서 실행해야 한다.

6-4️⃣ Python 실행 순서까지 이해해야 한다

st.write(asyncio.run(session.get_items()))

Python은:

  1. 함수 인자를 먼저 평가
  2. asyncio.run() 실행
  3. 완료 후 결과 반환
  4. st.write() 호출

즉,

asyncio.run은

비동기를 동기로 바꾸는 래퍼이자

실행 완료를 보장하는 블로킹 포인트다.

7️⃣ 메모리 리셋 구조

if reset:
    asyncio.run(session.clear_session())

이걸 통해 배운 것:

  • 세션은 DB 기반
  • clear_session()으로 완전 초기화 가능
  • “기억하는 것처럼 보이는 LLM”의 실체는 DB

🎯 핵심 한 줄 요약

LLM은 Stateless다.

우리는 세션과 이벤트 루프를 이용해 Stateful 시스템처럼 보이게 만든다.

그리고 asyncio.run은

동기 환경(Streamlit)에서 비동기 LLM 실행을 가능하게 하는 브릿지다.

이 문서는

단순 실습 정리가 아니라

LLM 애플리케이션 아키텍처 이해 기록이다.

편입 후 검증 메모

  • 메모리 층: 모델 context, 애플리케이션 session, 그래프 checkpoint, 장기 저장소는 수명과 조회 방식이 다르다. 한 단어 ‘memory’로 합치지 않는다.
  • Guardrail: 모델 기반 분류는 확률적이며 bypass·오탐이 가능하다. 민감 작업은 deterministic validation·권한·allowlist와 함께 막는다.
  • Time travel: 이전 checkpoint에서 재실행하면 외부 API·메일·DB 쓰기가 중복될 수 있다. side effect를 멱등하게 만들거나 재생 구간에서 차단한다.
  • 테스트: node의 순수 로직은 고정 입력으로 테스트하고, AI 응답은 구조·정책·범위와 평가 데이터로 검증한다. 문자열 완전 일치만으로 품질을 판단하지 않는다.
