1. Baseline·Train·Validation·Holdout

구분역할주의점
Baseline학습 전 base model의 현재 성능 측정tuned와 같은 추론 조건
Trainadapter parameter update최종 평가에 재사용하지 않음
Validation학습 중 loss와 일반화 확인하이퍼파라미터 판단용
Holdout/Test학습이 끝난 뒤 최종 전후 비교학습·튜닝에 보이지 않아야 함

학습에 들어간 문장을 다시 평가하면 암기 효과와 일반화를 구분할 수 없다. 그래서 tuned와 base를 같은 보지 않은 holdout에 보낸다.

2. 한 케이스를 채점하는 순서

1. 호출해야 하는데 호출했나? (call decision)
2. 함수명이 맞나? (tool selection)
3. arguments가 JSON인가? (JSON validity)
4. JSON Schema를 만족하나? (Schema validity)
5. 정답 인자 객체와 완전히 같은가? (exact match)
6. 모두 통과하면 full success

no-call 케이스는 호출이 없어야 통과한다. 모델이 지원하지 않는 삭제·재시작 요청에도 조회 도구를 호출하면 call decision과 no-call accuracy가 떨어진다.

3. Strict exact match의 의미

정답이 {"resource_id":"api"}인데 모델이 실행기 기본값과 같은 "limit":100을 추가하면 실제 실행 결과는 같을 수 있다. 그러나 키·값 전체가 다르므로 strict exact match는 실패한다.

두 평가를 분리해야 한다
strict contract 평가는 출력 형식을 안정화하는 데 좋고, semantic 평가는 실제 실행 결과가 같은지를 확인하는 데 좋다. 하나의 수치만으로 운영 가능성을 주장해서는 안 된다.

인자별 TP·FP·FN으로 F1을 함께 계산하면 “함수는 맞지만 한 인자를 빠뜨렸다” 같은 부분 개선도 볼 수 있다.

5. 적용 사례로 이동하기

실제 데이터 수량·전후 수치·실패 응답은 범용 평가 문서가 아니라 Kubernetes Function Calling 프로젝트의 평가 단계에 기록한다.
