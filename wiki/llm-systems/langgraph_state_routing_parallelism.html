#16.1 Prompt Chaining Architecture (14:08)

수정 목적

  • 하나의 큰 요청을 여러 단계의 작은 프롬프트로 나누어 더 안정적으로 결과를 생성하는 구조를 이해합니다.
  • 재료 추출, 레시피 생성, 플레이팅 설명을 분리해서 각 단계가 이전 단계의 출력을 다음 단계 입력으로 사용하는 방식을 정리합니다.
  • LangGraph에서 직선형 워크플로우를 어떻게 그래프로 연결하는지 학습합니다.

핵심 개념

  • Prompt Chaining: 큰 작업을 여러 개의 순차 프롬프트로 나누는 방식입니다. 코드에서는 list_ingredients -> create_recipe -> describe_plating 순서로 분리됩니다.
  • State: 각 단계가 공유하는 데이터 저장 공간입니다. dish, ingredients, recipe_steps, plating_instructions를 하나의 상태로 관리합니다.
  • Structured Output: LLM 응답을 정해진 스키마로 받는 방식입니다. Ingredient와 IngredientsOutput 모델이 재료 목록 형식을 고정합니다.

사용 이유

  • 복잡한 요청을 단계별로 쪼개면 각 노드의 책임이 분명해져 디버깅이 쉬워집니다.
  • 중간 결과를 상태에 남기기 때문에 어느 단계에서 품질이 흔들리는지 바로 확인할 수 있습니다.
  • 각 단계 사이에 검증 로직을 넣기 쉬워서 결과 품질을 통제하기 좋습니다.

한 줄 요약

Prompt Chaining은 하나의 큰 작업을 여러 노드로 나누고, 각 노드의 출력을 다음 노드 입력으로 넘겨 최종 결과를 만드는 직렬형 워크플로우입니다.

언제 사용하는가

  • 작업 순서가 비교적 명확하고 단계가 고정되어 있을 때 적합합니다.
  • 앞 단계의 결과를 다음 단계 입력으로 자연스럽게 넘길 수 있을 때 효과적입니다.
  • 한 번의 긴 프롬프트보다 여러 번 나누어 검증하는 편이 더 안전할 때 사용합니다.

코드 설명

from typing_extensions import TypedDict
from typing import List
from langgraph.graph import StateGraph, START, END
from langchain.chat_models import init_chat_model
from pydantic import BaseModel

llm = init_chat_model("openai:gpt-4o")

class State(TypedDict):
    dish: str
    ingredients: list[dict]
    recipe_steps: str
    plating_instructions: str

class Ingredient(BaseModel):
    name: str
    quantity: str
    unit: str

class IngredientsOutput(BaseModel):
    ingredients: List[Ingredient]

def list_ingredients(state: State):
    structured_llm = llm.with_structured_output(IngredientsOutput)
    response = structured_llm.invoke(f"List 5-8 ingredients need to make {state['dish']}")
    return {"ingredients": response.ingredients}

def create_recipe(state: State):
    response = llm.invoke(f"Write a step by step cooking instruction for {state['dish']}, using these ingredient {state['ingredients']}")
    return {"recipe_steps": response.content}

def describe_plating(state: State):
    response = llm.invoke(f"Describe how to beautifully plate this dish {state['dish']} based on this recipe {state['recipe_steps']}")
    return {"plating_instructions": response.content}

graph_builder = StateGraph(State)
graph_builder.add_node("list_ingredients", list_ingredients)
graph_builder.add_node("create_recipe", create_recipe)
graph_builder.add_node("describe_plating", describe_plating)
graph_builder.add_edge(START, "list_ingredients")
graph_builder.add_edge("list_ingredients", "create_recipe")
graph_builder.add_edge("create_recipe", "describe_plating")
graph_builder.add_edge("describe_plating", END)
graph = graph_builder.compile()
graph.invoke({"dish": "hummus"})

#16.2 Prompt Chaining Gate (03:33)

수정 목적

  • Prompt Chaining 흐름에 중간 검증 단계를 넣어, 잘못된 중간 결과가 다음 단계로 넘어가지 않도록 제어합니다.
  • 재료 개수가 기대 범위를 벗어나면 다음 노드로 진행하지 않고 다시 재료 생성 단계로 되돌리는 구조를 학습합니다.
  • LangGraph의 conditional edges가 단순 직렬 연결과 어떻게 다른지 이해합니다.

핵심 개념

  • Gate: 다음 단계로 넘어가도 되는지를 판단하는 조건 검사 함수입니다. ingredients 길이가 3~8 범위인지 검사해 True 또는 False를 반환합니다.
  • Conditional Edge: 함수 결과에 따라 다음 노드를 다르게 선택하는 엣지입니다. gate 결과가 True면 create_recipe, False면 list_ingredients로 이동시킵니다.
  • Retry Loop: 조건을 만족할 때까지 이전 단계를 다시 실행하는 반복 구조입니다. 재료 수가 기준에서 벗어나면 ingredient 생성 노드를 반복 실행합니다.

사용 이유

  • LLM 중간 출력 품질을 코드로 직접 통제할 수 있어서 결과 신뢰도가 높아집니다.
  • 잘못된 중간 결과를 뒤 단계에서 억지로 처리하지 않아도 되어 디버깅이 쉬워집니다.
  • 재료 개수뿐 아니라 형식 검증, 금지 재료 검사, 사용자 정책 검사 등으로 쉽게 확장할 수 있습니다.

한 줄 요약

Prompt Chaining Gate는 중간 결과를 검사한 뒤 통과하면 다음 단계로 보내고, 실패하면 이전 단계로 되돌려 재시도하게 만드는 조건부 워크플로우입니다.

이번 변경으로 무엇을 공부할 수 있었는가

  1. LangGraph에서 직렬 엣지를 조건부 엣지로 바꾸는 방법을 공부할 수 있었습니다.
  2. LLM 출력 검증을 프롬프트가 아니라 코드 레벨 gate 함수로 분리하는 이유를 이해할 수 있었습니다.
  3. 단순 체인에서 루프가 있는 워크플로우로 확장되는 과정을 diff 기준으로 확인할 수 있었습니다.

from typing_extensions import TypedDict
from typing import List
from langgraph.graph import StateGraph, START, END
from langchain.chat_models import init_chat_model
from pydantic import BaseModel

llm = init_chat_model("openai:gpt-4o")

class State(TypedDict):
    dish: str
    ingredients: list[dict]
    recipe_steps: str
    plating_instructions: str

class Ingredient(BaseModel):
    name: str
    quantity: str
    unit: str

class IngredientsOutput(BaseModel):
    ingredients: List[Ingredient]

def list_ingredients(state: State):
    structured_llm = llm.with_structured_output(IngredientsOutput)
    response = structured_llm.invoke(f"List 5-8 ingredients need to make {state['dish']}")
    return {"ingredients": response.ingredients}

def create_recipe(state: State):
    response = llm.invoke(
        f"Write a step by step cooking instruction for {state['dish']}, using these ingredient {state['ingredients']}",
    )
    return {"recipe_steps": response.content}

def describe_plating(state: State):
    response = llm.invoke(
        f"Describe how to beautifully plate this dish {state['dish']} based on this recipe {state['recipe_steps']}"
    )
    return {"plating_instructions": response.content}

def gate(state: State):
    ingredients = state['ingredients']
    if len(ingredients) > 8 or len(ingredients) < 3:
        return False
    return True

graph_builder = StateGraph(State)
graph_builder.add_node("list_ingredients", list_ingredients)
graph_builder.add_node("create_recipe", create_recipe)
graph_builder.add_node("describe_plating", describe_plating)
graph_builder.add_edge(START, "list_ingredients")
graph_builder.add_conditional_edges(
    "list_ingredients",
    gate,
    {
        True: "create_recipe",
        False: "list_ingredients"
    },
)
graph_builder.add_edge("create_recipe", "describe_plating")
graph_builder.add_edge("describe_plating", END)
graph = graph_builder.compile()
graph.invoke({"dish": "hummus"})

#16.3 Routing Architecture (16:38)

수정 목적

  • 하나의 고정된 체인 대신, 질문 난이도에 따라 다른 노드와 다른 모델로 보내는 라우팅 구조를 학습합니다.
  • 중간 판단 노드가 다음 실행 노드를 직접 선택하는 방식과 상태를 함께 갱신하는 방식을 이해합니다.
  • Prompt Chaining의 재시도 구조에서 더 나아가, 조건에 따라 여러 실행 경로로 분기하는 아키텍처를 정리합니다.

핵심 개념

  • Routing Architecture: 입력 상태를 보고 가장 적절한 다음 노드로 흐름을 보내는 그래프 구조입니다.
  • Command: 다음 이동 경로와 상태 갱신을 동시에 반환하는 LangGraph 제어 객체입니다.
  • Difficulty-based Model Routing: 질문 난이도에 따라 서로 다른 모델을 선택하는 전략입니다.

  • 질문 난이도에 따라 적절한 모델을 선택하므로 품질과 속도 균형을 맞추기 쉽습니다.
  • 라우팅 판단 결과를 상태에 남기기 때문에 왜 특정 모델이 선택됐는지 추적하기 쉽습니다.

Routing Architecture는 라우터 노드가 질문을 분류하고, 그 결과에 따라 적절한 모델 노드로 보내 답변을 생성하는 조건부 분기형 그래프 구조입니다.

from typing import List

from langchain.chat_models import init_chat_model

llm = init_chat_model("openai:gpt-4o")
dumb_llm = init_chat_model("openai:gpt-3.5-turbo")
average_llm = init_chat_model("openai:gpt-4o")

class State(TypedDict):
    question: str
    difficulty: str
    answer: str
    model_used: str

class DifficultyyResponse(BaseModel):
    difficulty_level: Literal["easy", "medium", "hard"]

from langgraph.types import Command

def dumb_node(state: State):
    response = dumb_llm.invoke(state["question"])
    return {
        "answer": response.content,
        "model_used": "gpt-3.5-turbo"

    response = average_llm.invoke(state["question"])
    return {
        "answer": response.content,

    }

def assess_difficulty(state: State):
    structured_llm = llm.with_structured_output(DifficultyyResponse)
    response = structured_llm.invoke(
        f"""
            Assess the difficulty of this question
            Question: {state['question']}

            - Easy: Simple facts, basic definitions, yes / no answers
            - MEDIUM: Requires explanation, comparison, analysis
            - HARD: Complex reasoning, multiple steps, deep expertise.
        """
    )
    difficulty_level = response.difficulty_level
    if difficulty_level == "easy":
        goto = "dumb_node"
    elif difficulty_level == "medium":
        goto = "average_node"
    elif difficulty_level == "hard":
        goto = "smart_node"
    return Command(goto=goto, update={"difficulty": difficulty_level})

graph_builder = StateGraph(State)
graph_builder.add_node("dumb_node", dumb_node)
graph_builder.add_node("average_node", average_node)
graph_builder.add_node("smart_node", smart_node)
graph_builder.add_node(
    "assess_difficulty",
    assess_difficulty,
    destinations=("dumb_node", "average_node", "smart_node"),
)
graph_builder.add_edge(START, "assess_difficulty")
graph_builder.add_edge("dumb_node", END)
graph_builder.add_edge("average_node", END)
graph_builder.add_edge("smart_node", END)
graph = graph_builder.compile()
graph.invoke({"question": "How do I make hummus?"})

#16.4 Parallelization Architecture

  • get_final_analysis
  • 여러 병렬 분석 결과를 입력으로 받아 하나의 최종 설명으로 합칩니다.
  • 실제 서비스에서는 이 노드가 "최종 사용자 응답"을 만드는 역할을 맡는 경우가 많습니다.

Prompt Chaining과 차이

  • Prompt Chaining은 앞 단계 출력이 다음 단계 입력이 되는 순차 구조입니다.
  • Parallelization은 여러 작업이 같은 입력을 기준으로 동시에 실행되는 구조입니다.
  • Prompt Chaining은 단계 간 의존성이 클 때 적합합니다.
  • Parallelization은 작업 간 독립성이 클 때 더 적합합니다.

장점

  • 독립 작업을 동시에 돌릴 수 있어 응답 시간을 줄이기 좋습니다.
  • 각 노드 책임이 분리되어 프롬프트 설계가 명확해집니다.
  • 특정 분석만 선택적으로 개선하기 쉽습니다.
  • aggregator를 통해 다면적인 결과를 하나로 통합할 수 있습니다.

주의할 점

  • 병렬로 나눈 작업이 실제로 독립적이지 않다면 결과 일관성이 깨질 수 있습니다.
  • aggregator 프롬프트가 약하면 부분 결과를 잘 모았더라도 최종 응답 품질이 떨어질 수 있습니다.
  • 상태 필드 이름이 정확히 맞지 않으면 마지막 통합 단계에서 누락이나 오류가 날 수 있습니다.
  • 입력 스키마와 실행 예시가 일치하지 않으면 이전 예제처럼 KeyError 같은 문제가 생길 수 있습니다.

stream_mode는 무엇인가

  • stream_mode는 LangGraph의 graph.stream(...)에서 무엇을 스트리밍해서 받을지 정하는 옵션입니다.
  • 이 예제에서는 각 노드가 실행될 때마다 새로 만들어진 상태 변화만 확인하기 위해 stream_mode="updates"를 사용합니다.
for chunk in graph.stream(
    {"document": document},
    stream_mode="updates"
):
    print(chunk, "\n")
  • 이 설정을 사용하면 전체 state를 매번 다 받는 것이 아니라, 각 노드가 이번 단계에서 새로 만든 값만 순서대로 받게 됩니다.
  • 따라서 병렬 노드가 있을 때 어떤 작업이 먼저 끝났는지 실시간으로 관찰하기 쉽습니다.

updates 예시

  • stream_mode="updates"는 각 단계에서 업데이트된 값만 반환합니다.
{"get_summary": {"summary": "..."}}
{"get_sentiment": {"sentiment": "..."}}
{"get_key_points": {"key_points": "..."}}
{"get_recomendation": {"recommendation": "..."}}
  • 이런 형태는 디버깅할 때 유용합니다.
  • 특히 병렬 구조에서는 어떤 노드가 먼저 완료되었는지 확인하기 좋습니다.
  • 실행 흐름을 설명하거나 중간 결과를 시각적으로 추적할 때도 많이 사용됩니다.

values와 차이

  • values
  • 매 단계마다 전체 state를 반환합니다.
  • updates
  • 매 단계마다 변경된 부분만 반환합니다.
  • 즉 values는 "현재까지 누적된 전체 상태"를 보는 데 적합하고, updates는 "이번 단계에서 무엇이 새로 바뀌었는지"를 보는 데 적합합니다.

한 줄 결론

  • Parallelization Architecture는 "같은 입력을 여러 관점에서 동시에 분석하고, 마지막에 하나로 합치는 구조"라고 이해하면 가장 쉽습니다.

#16.5 Orchestrator-workers Architecture

수정 목적

  • Orchestrator-workers Architecture의 동작 흐름을 코드와 실행 결과 기준으로 정리합니다.
  • Parallelization Architecture와의 공통점/차이점을 구체적으로 구분합니다.
  • Send를 통한 동적 fan-out가 무엇을 학습하게 하는지 이해할 수 있게 정리합니다.
  • 16.5 문서가 없던 상태에서, 코드 기반으로 재학습 가이드를 완성합니다.

핵심 개념

  • Orchestrator-workers: 입력을 먼저 분석해 하위 작업을 계획하고, 여러 worker를 동적으로 호출해 처리 후 합치는 구조입니다.
  • Send: START 단계에서 여러 작업 요청을 동적으로 생성해서 병렬 실행을 시작하는 객체입니다.
  • StateGraph: 상태를 공유하면서 노드 간 흐름을 구성하고 집계 노드까지 연결하는 그래프 엔진입니다.
  • Summaries: Annotated[list[dict], add]로 누적 합쳐지는 집계 상태입니다.
  • 최종 합성: 여러 worker 결과를 최종 응답 노드에서 한 번에 통합합니다.
  • index: 결과 순서가 뒤바뀌더라도 정렬을 복원하기 위한 키입니다.
  • diff 기반: 기존 문서와 코드를 함께 비교해 빠진 개념(동적 분해/집계)을 보완했습니다.

동작 흐름

  • 사용자 문서 입력(document) → START → dispatch_summarizers 실행
  • dispatch_summarizers가 문단별로 Send("summarize_p", \{...\}) 생성
  • summarize_p 노드가 각 문단 요약 실행 (병렬/동시적 분산 호출)
  • 각 호출 결과는 summaries에 \{summary, index\} 형태로 누적
  • final_summary가 누적된 summaries를 받아 최종 요약 생성
  • END

사용 이유

  • 같은 입력을 고정된 작업 목록이 아니라, 내용 기반으로 동적으로 분해해야 할 때 유용합니다.
  • 문서가 길수록 하나의 LLM 호출 대신 문단별 분해를 통해 병렬 처리 효율을 높일 수 있습니다.
  • 결과 병합에서 순서가 무너지는 문제를 index로 보완해 안정적으로 집계할 수 있습니다.

한 줄 요약

  • Orchestrator가 입력을 분할하고, worker 호출을 동적으로 생성한 뒤, 합성 노드에서 결과를 정리해 최종 응답으로 만드는 구조입니다.

이번 변경으로 무엇을 공부할 수 있었는지

  • 동적 라우팅의 실전 패턴: START에서 조건/전처리 함수로 여러 실행 경로를 생성하는 방식
  • 병렬 요약 파이프라인에서 상태 누적(add)의 동작 방식
  • 실행 순서가 섞일 수 있을 때, 식별자(index) 기반 정렬/추적 전략
  • Command/Send의 용도 차이에 대한 실전 감각 확장

무엇을 해결하는가

  • 고정 병렬 노드(항상 같은 수의 worker)로는 커버하기 어려운 가변 분해 문제를 해결합니다.
  • 긴 문서를 문단 단위로 쪼개어 병렬 처리하고, 최종 합성으로 품질을 유지합니다.
  • 각 결과의 순서 불확실성 문제를 키-값 기반으로 관리합니다.

핵심 개념 설명

  • 기술 설명
  • dispatch_summarizers는 chunks를 순회하며 Send("summarize_p", ...) 리스트를 반환해 여러 실행을 동적으로 생성합니다.
  • StateGraph.add_conditional_edges(START, dispatch_summarizers, ["summarize_p"])로 START에서 분해를 시작합니다.
  • StateGraph.add_edge("summarize_p", "final_summary")는 여러 worker 결과를 집계 후 합성 노드로 이동시킵니다.
  • summaries는 Annotated[list[dict], add]로 설계되어 다수 worker 결과가 누적됩니다.
  • 쉬운 설명

  • index는 “어떤 요약이 몇 번 문단인지” 붙이는 티켓 번호입니다.
  • 코드 위치
  • dispatch_summarizers: 오케스트레이션 지점
  • summarize_p: worker
  • final_summary: synthesizer
  • StateGraph 구성부: 전체 조립부

동작 흐름

  • document를 문단 단위로 분할
  • 각 문단마다 Send 반환
  • graph engine이 문단별 summarize_p를 실행
  • add reducer로 summaries 누적
  • 최종 노드에서 누적 값을 받아 최종 요약 생성

  • orchestrator 단계와 worker 단계가 분리되면 요구사항 변형이 쉬워집니다.

[Before]
- 병렬 작업은 미리 고정된 노드 목록에 따라 실행되거나
- 모든 단계를 수동으로 나열해야 했던 구조가 많았음
- 각 worker 결과의 순서 보장이 약했음

[After]
- 입력을 분해해 worker 수를 동적으로 생성
- Send 기반으로 실행량이 가변화
- index 기반으로 병렬 결과를 안정적으로 집계
- final_summary에서 한 번에 통합

  4. START -> conditional edges -> worker -> final_summary -> END 흐름으로 Orchestrator-workers 모델을 완성했습니다.

13.2 Graph State (13:47) - Graph State

수정 목적

  • LangGraph 노드가 상태를 실제로 갱신하도록 각 노드의 반환값을 명시적으로 상태 딕셔너리로 반환하도록 변경한 이유를 정리합니다.
  • 기존에는 상태 변화를 확인하기 어렵고, 최종 hello 값이 어디서 최종 결정되는지가 코드에서 명확하지 않았습니다.

핵심 개념

  • 노드의 반환값이 상태 키를 덮어쓰기 때문에, 같은 키(hello)를 여러 노드가 순차적으로 갱신할 수 있습니다.
  • 그래프 진입 시 전달한 입력 키 중, 스키마/로직에서 사용되지 않는 키는 최종 출력에 남지 않을 수 있습니다.

동작 흐름

  • 초기 입력: {'hello': 'world', 'no-key': 'no-value'} 를 graph.invoke()로 전달합니다.
  • node_one 실행:
  • 현재 state 출력
  • {'hello': 'from node one.'} 반환
  • node_two 실행:

  • node_three 실행:
  • 이전 상태 출력
  • {'hello': 'from node three'} 반환
  • 최종 결과:
  • {'hello': 'from node three'}

사용 이유

  • 노드별 책임을 분리해 상태 전파가 어떻게 되는지 단계별로 추적하기 위해서입니다.
  • 상태를 반환하지 않으면 값이 갱신되지 않기 때문에, 의도한 데이터 흐름이 반영되지 않습니다.
  • Graph State를 활용해 단계별로 상태가 어떻게 덮어쓰기되는지 확인하는 학습용 실습으로 적합합니다.

한 줄 요약

13.4 Multiple Schemas (12:50) - Graph State 다중 스키마

수정 목적

  • 하나의 그래프에서 input_schema, state_schema, output_schema를 분리해 사용하였습니다.

  • 노드가 반환한 값 중에서 다음 노드로 전달 가능한 값은 현재 그래프 스키마에 맞을 때만 반영됩니다.

13.6 Node Caching (03:56) - 노드 캐싱

수정 목적

  • 동일 입력에 대한 노드 실행 시간을 줄이기 위해 CachePolicy를 적용했습니다.
  • node_two 결과를 20초 동안 재사용해 중복 계산을 피하는 흐름을 실습으로 검증했습니다.
  • 동일 입력이 반복되는 상황에서 캐시 히트/미스 동작을 출력 비교로 확인할 수 있게 구성했습니다.

핵심 개념

  • CachePolicy는 노드 단위로 실행 결과를 캐시할 규칙을 정의합니다.
  • ttl=20은 20초가 지나면 캐시가 만료되어 다시 계산됨을 뜻합니다.
  • graph_builder.compile(cache=InMemoryCache())는 그래프 전체에서 노드 캐시 저장소를 사용하도록 합니다.
  • 빈 입력으로 graph.invoke({})를 5초 간격으로 여러 번 호출해 캐시 동작을 확인합니다.

동작 흐름

  • START → node_one → node_two → node_three → END 구조는 그대로 유지됩니다.
  • node_one은 현재 예제에서 상태를 추가로 반환하지 않습니다.
  • node_two는 datetime.now()를 time으로 반환합니다.
  • 첫 호출은 node_two를 실제로 실행해 시간을 계산해 저장합니다.
  • 20초 TTL 내 호출은 같은 입력이면 node_two 계산 결과를 재사용합니다.
  • 20초가 지나면 캐시가 만료되어 다시 계산됩니다.

사용 이유

  • 같은 입력으로 반복 호출되는 비용이 큰 노드를 줄이기 위함입니다.
  • 외부 API 호출이나 모델 추론처럼 반복 호출 비용이 큰 작업에서 반응 속도와 비용을 줄일 수 있습니다.
  • 캐시 정책이 없던 상태에서 캐시 설정의 효과를 정량적으로 확인할 수 있습니다.

한 줄 요약

  • Node Caching은 동일 상태 입력일 때 노드 실행 결과를 TTL 범위 내 재사용해, 같은 계산을 반복하지 않도록 하는 기능입니다.

무엇을 해결하는가

  • 동일 호출이 반복되어도 매번 node_two가 현재 시각을 새로 계산하던 비효율을 제거합니다.
  • 변경 없는 실행에서 불필요한 노드 재연산 시간을 줄입니다.
  • 캐시 만료(TTL) 전후 동작을 명확히 구분해 운영 정책을 설계할 수 있습니다.

13.7 Conditional Edges (10:36) - 조건부 엣지

수정 목적

  • LangGraph에서 한 노드 다음에 항상 같은 노드로 이동하는 것이 아니라, state 값에 따라 다른 노드로 분기하는 방법을 정리합니다.
  • add_conditional_edges()의 인자 구조와 실제 이동 규칙을 초보자 기준으로 명확히 이해하는 것이 목적입니다.
  • 코드 안에 적어둔 학습용 주석들, 특히 Literal, bool 분기, "hello": END, 암묵적 종료 개념을 빠짐없이 문서화합니다.

핵심 개념

  • Conditional Edges는 현재 상태를 보고 다음 노드를 동적으로 결정하는 분기 기능입니다.
  • 분기 함수는 state를 받아 “분기 키”를 반환하고, LangGraph는 그 값을 매핑표에서 찾아 다음 노드로 이동합니다.
  • 분기 키는 True/False 같은 불리언일 수도 있고, 문자열 같은 다른 값일 수도 있습니다.
  • 노드에 다음 엣지가 하나도 없으면 그 지점에서 그래프가 종료될 수 있습니다.

동작 흐름

  • START -> node_one -> node_two까지는 고정 흐름입니다.
  • node_two에서 decide_path(state)를 호출해 분기 키를 결정합니다.
  • 현재 코드에서는 state["seed"] % 2 == 0 결과가 True면 node_three, False면 node_four로 이동합니다.
  • node_four는 END로 명시적으로 연결됩니다.
  • node_three는 다음 엣지가 없으므로 지금 코드에서는 실행 후 거기서 종료됩니다.

사용 이유

  • 사용자 상태, 입력값, 계산 결과에 따라 서로 다른 처리 흐름을 만들 수 있습니다.
  • if/else를 노드 함수 내부에 과하게 넣는 대신, 그래프 구조 자체에 분기 규칙을 선언할 수 있습니다.
  • 분기 로직과 실제 작업 노드를 분리하면 유지보수와 디버깅이 쉬워집니다.

한 줄 요약

  • add_conditional_edges()는 분기 함수가 반환한 값을 기준으로 다음 노드를 고르는 기능이며, 이번 예제에서는 seed의 짝수/홀수 여부로 node_three와 node_four를 나눕니다.

무엇을 해결하는가

  • 단순 직선형 그래프만으로는 표현하기 어려운 조건 분기 흐름을 그래프 수준에서 설계할 수 있게 합니다.
  • 어느 값이 어떤 노드로 연결되는지를 선언적으로 적어, 실행 경로를 코드만 봐도 이해하기 쉽게 만듭니다.
  • 주석으로 적어둔 “현재는 bool만 반환하므로 hello 경로는 쓰이지 않는다” 같은 학습 포인트를 구조적으로 기억할 수 있게 합니다.

13.8 Send API (13:47) - Send API

수정 목적

  • LangGraph의 Send API를 사용해 하나의 입력 리스트를 여러 개의 개별 작업으로 fan-out 하는 구조를 정리합니다.
  • dispatcher가 실제 노드를 직접 호출하는 것이 아니라, “어떤 노드를 어떤 입력으로 몇 번 실행할지”를 선언한다는 점을 명확히 이해하는 것이 목적입니다.
  • 코드 주석에 적어둔 Send, dispatcher, reducer, 목적지 리스트(['node_two']) 의미를 빠짐없이 문서화합니다.

핵심 개념

  • Send("node_two", payload)는 특정 노드에 특정 입력을 보내는 “실행 지시”입니다.
  • dispatcher(state)는 데이터를 직접 처리하지 않고, LangGraph가 해석할 “다음 실행 목록”을 반환합니다.
  • node_two는 전체 State를 받는 것이 아니라, Send가 전달한 단일 word를 입력으로 받습니다.
  • 여러 번 실행된 node_two 결과는 State.output 채널에 모이고, Annotated[..., operator.add] reducer로 누적 병합됩니다.

동작 흐름

  • 시작 입력으로 words 리스트가 들어옵니다.
  • node_one이 먼저 실행되어 단어 개수를 출력합니다.
  • node_one 뒤에서 dispatcher(state)가 호출됩니다.
  • dispatcher는 words 개수만큼 Send("node_two", word)를 생성합니다.
  • 런타임은 node_two를 각 단어마다 한 번씩 실행합니다.
  • 각 실행 결과의 output 조각이 하나의 큰 리스트로 합쳐집니다.

사용 이유

  • 리스트에 들어 있는 각 항목을 동일한 로직으로 반복 처리할 때 자연스럽게 fan-out 구조를 만들 수 있습니다.
  • 노드 내부에서 직접 반복문을 돌리는 대신, 그래프 런타임에 병렬/반복 실행 구조를 선언적으로 맡길 수 있습니다.
  • 결과 병합 규칙을 State 스키마에 미리 선언하면, 여러 실행 결과를 수동으로 합칠 필요가 없어집니다.

한 줄 요약

  • Send API는 dispatcher가 작업 티켓(Send)을 여러 장 만들어 런타임에 fan-out 실행을 맡기고, 각 결과는 reducer로 하나의 output 리스트에 누적시키는 방식입니다.

무엇을 해결하는가

  • words 리스트의 각 원소를 개별 노드 실행으로 분리해 처리할 수 있게 합니다.
  • “어떤 노드를 몇 번 실행할지”와 “실제 노드가 무엇을 할지”를 분리해 그래프 구조를 더 명확하게 만듭니다.
  • 각 실행 결과를 output 채널에서 일관되게 합치도록 해, 후처리 코드를 줄입니다.

전체 코드(최종본)

from langgraph.graph import StateGraph, START, END
from typing_extensions import TypedDict, Annotated
from langgraph.types import Send
import operator
from typing import Union


class State(TypedDict):
    words: list[str]
    # output 채널에 여러 노드 결과가 동시에/반복적으로 들어올 때 어떻게 합칠지(reducer)를 지정한다.
    # Annotated[..., operator.add] 의미:
    # - 같은 실행 단계에서 output 값이 여러 번 반환되면 list + list로 누적 병합한다.
    # - 즉 node_two가 여러 번 반환한 {"output": [...]} 조각들이 하나의 큰 output 리스트로 합쳐진다.
    output: Annotated[list[dict[str, Union[str, int]]], operator.add]


graph_builder = StateGraph(State)


def node_one(state: State):
    print(f'I want to count {len(state["words"])} words in my state.')


def node_two(word: str):
    # 중요: node_two의 입력은 전체 State가 아니라 dispatcher가 Send로 전달한 단일 word(str)다.
    # 예) Send("node_two", "hello") 라면 node_two("hello") 형태로 실행된다.
    # node_two는 실행 1회마다 output 조각 1개를 반환한다.
    return {
        "output": [
            {
                "word": word,
                "letters": len(word),
            }
        ]
    }


graph_builder.add_node("node_one", node_one)
graph_builder.add_node("node_two", node_two)


def dispatcher(state: State):
    # Send("node_two", word)는 "node_two" 노드로 보낼 실행 지시(작업 티켓)이다.
    # 여기서 반환하는 것은 단순 데이터 리스트가 아니라, LangGraph가 해석할 "다음 실행 목록"이다.
    # 즉 이 함수는 node_two를 직접 호출하지 않고, "node_two를 어떤 입력으로 몇 번 실행할지"를 선언한다.
    # 아래 리스트 컴프리헨션은 words 길이만큼 Send를 만든다.
    # 예) words = ["hello", "world"]
    # -> [Send("node_two", "hello"), Send("node_two", "world")]
    # -> 런타임이 node_two를 2회 스케줄링/실행한다.
    return [Send("node_two", word) for word in state["words"]]


graph_builder.add_edge(START, "node_one")

# add_conditional_edges는 "분기/라우팅 등록" API다.
# node_one 실행 후 dispatcher를 호출하고, dispatcher 반환값을 보고 다음 실행 경로를 동적으로 결정한다.

# dispatcher가 Send를 반환하면:
# - Send의 첫 인자: 목적지 노드 이름
# - Send의 둘째 인자: 그 노드에 전달할 입력 데이터(payload)
# dispatcher가 Send 리스트를 반환하면 리스트 길이만큼 fan-out 실행된다.

# 세 번째 인자 ["node_two"]가 리스트인 이유:
# - 이 자리는 "가능한 목적지 노드들"을 넘기는 자리라 원래 복수 분기를 전제로 list 타입이다.
# - 지금은 목적지가 하나뿐이라 ["node_two"] 한 개만 넣은 상태다.
# - 분기가 여러 개면 ["node_two", "node_three", ...]처럼 늘어난다.
# - 이 예제처럼 Send 안에 목적지("node_two")를 직접 담는 경우에도,
#   해당 리스트는 허용 목적지/그래프 구조를 명시하는 선언으로 이해하면 된다.

# 추가 정리(중요): dispatcher에 Send를 쓰지 않는 경우
# - 실제 분기 대상은 dispatcher "반환값"으로 결정된다.
# - 반환값이 "node_two" 같은 노드명이면 그 노드로 라우팅된다.
# - 반환값이 "A" 같은 라벨이면, path_map(세 번째 인자)으로 "A -> 실제 노드" 매핑이 필요하다.
# - 반대로 dispatcher가 목적지 정보를 반환하지 않으면,
#   세 번째 인자에 ["node_two"]를 적어두었다고 해서 자동으로 node_two로 가지는 않는다.

# 그리고 각 실행에서 반환된 output 조각은 State.output 채널로 모인 뒤,
# 위에서 정의한 Annotated(..., operator.add) 규칙으로 순차 누적(list + list) 병합된다.
# 결과적으로 최종 output에는 모든 word 처리 결과가 한 리스트로 합쳐져 저장된다.
graph_builder.add_conditional_edges("node_one", dispatcher, ["node_two"])
graph_builder.add_edge("node_two", END)

graph = graph_builder.compile()

graph.invoke(
    {
        "words": ["hello", "world", "how", "are", "you", "doing"],
    }
)

13.9 Command (08:06) - Command 기반 라우팅

수정 목적

  • LangGraph에서 Command를 사용해 한 노드 안에서 상태 업데이트와 다음 노드 이동을 동시에 결정하는 패턴을 정리합니다.
  • conditional_edges와 Command 중 언제 무엇을 선택하면 좋은지, 코드 주석에 적어둔 실무 기준을 중심으로 문서화합니다.
  • goto, update, Literal 반환 타입이 각각 어떤 역할을 하는지 초보자 기준으로 이해할 수 있게 정리합니다.

핵심 개념

  • Command는 상태 업데이트와 다음 노드 이동을 한 번에 반환하는 객체입니다.
  • goto는 다음에 실행할 노드를 런타임에 결정하고, update는 이동 전에 state에 반영할 값을 정의합니다.
  • Literal["account_support", "tech_support"]는 가능한 이동 대상 노드를 타입 차원에서 명시하는 장치입니다.

시스템 구조

flowchart LR
    A["START"] --> B["triage_node"]
    B --> C{"Command"}
    C --> D["update<br>transfer_reason"]
    C --> E["goto<br>account_support or tech_support"]
    D --> E
    E --> F["account_support"]
    E --> G["tech_support"]
    F --> H["END"]
    G --> H

주석으로 기억할 핵심 포인트

  • conditional_edges는 분기 규칙을 그래프 선언부에 모아둘 수 있어 전체 흐름을 한눈에 보기 좋고, 협업·리뷰·테스트에도 유리해서 기본 선택으로 자주 씁니다.
  • Command는 한 노드 안에서 state 업데이트와 다음 노드 이동을 함께 결정해야 할 때 유용하며, 트리아지·핸드오프처럼 판단 후 즉시 이동하는 패턴에서 코드가 간결해집니다.
  • 반환 타입에 Literal로 가능한 goto 노드를 명시하면 그래프를 출력할 때 triage_node의 분기 관계를 더 명확하게 확인할 수 있습니다.

핵심 코드

def triage_node(state: State) -> Command[Literal["account_support", "tech_support"]]:
    return Command(
        goto="account_support",
        update={
            "transfer_reason": "The user wants to change password.",
        },
    )

Before / After

Before: 분기와 state 업데이트를 conditional_edges와 별도 노드 로직으로 나눠 처리했습니다. 그래프 선언부는 명확하지만 판단 + 즉시 이동 패턴에서는 코드가 길어질 수 있습니다.

After: triage_node가 Command 하나로 update와 goto를 동시에 반환합니다. 핸드오프/트리아지처럼 즉시 이동해야 하는 경우 코드가 더 짧고 직관적입니다.

실행 흐름 정리

User 입력 → triage_node 실행 → Command(update + goto) 반환 → state에 transfer_reason 반영 → account_support 이동 → END

14.0 LangGraph Chatbot (13:11) - MessagesState와 add_messages

수정 목적

  • LangGraph에서 가장 기본적인 챗봇 그래프를 만들고, messages 상태 채널이 어떻게 흐르는지 학습합니다.
  • Annotated[..., reducer]가 상태 병합 규칙을 어떻게 결정하는지 확인합니다.
  • operator.add와 add_messages가 실제 메시지 히스토리 관리 방식에서 어떻게 다른지 비교합니다.

핵심 개념

  • MessagesState: LangGraph에서 messages 채널을 기본으로 제공하는 상태 타입입니다.
  • Annotated[..., reducer]: 상태 필드에 어떻게 병합할지를 메타데이터로 붙이는 문법입니다.
  • add_messages: 메시지 ID를 기준으로 append와 update를 처리하는 LangGraph용 병합 함수입니다.

동작 흐름

flowchart LR
    A["START"] --> B["chatbot"]
    B --> C["END"]
  • graph.invoke()로 사용자 메시지가 들어갑니다.
  • chatbot 노드가 state["messages"]를 LLM에 전달합니다.
  • 노드는 \{"messages": [response]\} 형태로 새 응답만 반환하고, reducer가 기존 상태와 병합합니다.

이번 변경으로 무엇을 공부할 수 있었는가

  • START -> node -> END 형태의 가장 기본적인 LangGraph 챗봇 그래프 구성을 공부할 수 있습니다.
  • MessagesState를 쓰면 messages 채널을 따로 선언하지 않아도 된다는 점을 공부할 수 있습니다.
  • operator.add는 단순 누적이고, add_messages는 메시지 ID 기반 update라는 점을 공부할 수 있습니다.
  • 재시도, 정정, 스트리밍 같은 상황에서는 왜 add_messages가 더 안전한 기본값인지 공부할 수 있습니다.

코드 설명

import operator
from typing import Annotated
from langgraph.graph import StateGraph, START, END
from langchain.chat_models import init_chat_model
from langgraph.graph.message import MessagesState

llm = init_chat_model("openai:gpt-4o-mini")

class State(MessagesState):
    pass

graph_builder = StateGraph(State)

def chatbot(state: State):
    response = llm.invoke(state["messages"])
    return {
        "messages": [response]
    }

graph_builder.add_node("chatbot", chatbot)
graph_builder.add_edge(START, "chatbot")
graph_builder.add_edge("chatbot", END)

graph = graph_builder.compile()

이 코드는 LangGraph 챗봇의 최소 구조입니다. 중요한 학습 포인트는 노드 로직보다 messages가 어떤 규칙으로 병합되느냐입니다.

from langchain_core.messages import HumanMessage, AIMessage

base = [
    HumanMessage(content="안녕", id="u1"),
    AIMessage(content="초기 답변", id="a1"),
]

retry_or_fix = [
    AIMessage(content="수정된 답변", id="a1"),
]

merged_with_operator = operator.add(base, retry_or_fix)
merged_with_add_messages = add_messages(base, retry_or_fix)

같은 ID를 가진 메시지가 다시 들어왔을 때 operator.add는 기존 답변과 수정된 답변을 둘 다 남기고, add_messages는 기존 답변을 수정본으로 교체합니다.

주석으로 기억할 핵심 포인트

  • messages는 그래프를 흐르면서 누적되는 대화 히스토리 채널입니다.
  • Annotated[..., reducer]의 reducer는 이전 상태(left)와 새 출력(right)을 어떻게 합칠지 정합니다.
  • operator.add는 단순 리스트 이어붙이기라서 같은 메시지가 다시 와도 중복이 계속 쌓입니다.
  • add_messages는 메시지 ID 기반 병합이라서 같은 id가 오면 append가 아니라 update가 됩니다.
  • 재시도, 툴 결과 수정, 스트리밍 최종본 반영처럼 기존 메시지를 최신 상태로 바꿔야 하는 상황에서는 add_messages가 더 안전합니다.

[Before]
- 기본 챗봇 그래프 예제가 없었습니다.
- messages 상태 채널의 병합 전략 차이를 비교하는 코드가 없었습니다.

[After]
- MessagesState 기반 챗봇 그래프 예제가 추가되었습니다.
- 같은 id를 가진 메시지로 operator.add와 add_messages를 비교하는 실험 코드가 추가되었습니다.
- 실무에서 add_messages가 더 안전한 이유가 주석으로 상세히 정리되었습니다.
- 환경 변수 파일이 Git 제외 목록에 추가되어 로컬 비밀값 관리가 정리되었습니다.

16.4 Parallelization Architecture

수정 목적

  • 하나의 입력을 여러 LLM 작업으로 동시에 분해해 처리하는 Parallelization Architecture를 이해합니다.
  • 요약, 감성 분석, 핵심 포인트 추출, 추천 생성처럼 서로 독립적인 작업을 병렬로 실행하는 이유를 정리합니다.
  • 여러 병렬 결과를 마지막 Aggregator 노드가 하나의 최종 분석으로 합치는 구조를 학습합니다.

핵심 개념

  • Parallelization
  • 한 줄 정의: 하나의 입력에 대해 여러 작업을 동시에 실행하는 워크플로우 구조입니다.
  • 필요한 상황: 각 작업이 서로 의존하지 않고 같은 원본 입력을 독립적으로 처리할 수 있을 때 적합합니다.
  • 코드 역할: get_summary, get_sentiment, get_key_points, get_recomendation가 같은 입력 문서를 병렬로 처리합니다.
  • Fan-out
  • 한 줄 정의: 하나의 시작점에서 여러 노드로 흐름이 갈라지는 구조입니다.
  • 필요한 상황: 같은 입력을 서로 다른 관점으로 동시에 분석하고 싶을 때 사용합니다.
  • 코드 역할: START에서 여러 분석 노드로 동시에 엣지를 연결합니다.
  • Aggregator
  • 한 줄 정의: 병렬 실행된 여러 결과를 하나로 모아 최종 출력을 만드는 노드입니다.
  • 필요한 상황: 분리된 부분 결과를 사용자에게 보여줄 하나의 응답으로 합쳐야 할 때 필요합니다.
  • 코드 역할: get_final_analysis가 summary, sentiment, key points, recommendation을 모아 최종 분석을 생성합니다.

동작 흐름

  • User document 입력

-> get_summary

-> get_sentiment

-> get_key_points

-> get_recomendation

-> get_final_analysis

-> 최종 상태 반환

  • 중간 상태 변화
  • get_summary가 문서 요약을 생성합니다.
  • get_sentiment가 전체 감정 톤을 분석합니다.
  • get_key_points가 핵심 포인트를 추출합니다.
  • get_recomendation이 후속 추천이나 제안을 생성합니다.
  • get_final_analysis가 이 결과들을 모아 최종 분석을 만듭니다.

사용 이유

  • 서로 독립적인 작업을 순차로 실행하지 않고 동시에 처리할 수 있어 전체 처리 시간을 줄일 수 있습니다.
  • 각 노드가 하나의 역할만 맡으므로 프롬프트 목적이 분명해지고 결과 품질을 관리하기 쉬워집니다.
  • 특정 분석만 교체하거나 추가하기 쉬워 확장성이 좋습니다.
  • 마지막 aggregator에서 전체 결과를 다시 통합하므로 분산된 분석 결과를 사용자 친화적인 하나의 출력으로 정리할 수 있습니다.

한 줄 요약

  • Parallelization Architecture는 하나의 입력을 여러 독립 분석 노드로 동시에 보내고, 그 결과를 aggregator가 합쳐 최종 응답을 만드는 병렬형 워크플로우입니다.

이번 변경으로 무엇을 공부할 수 있었는가

  • LangGraph에서 START에서 여러 노드로 동시에 분기하는 구조를 공부할 수 있습니다.
  • 병렬 실행이 직렬 실행보다 적합한 상황이 무엇인지 이해할 수 있습니다.
  • 부분 분석 결과를 상태에 저장한 뒤 마지막 노드에서 통합하는 패턴을 배울 수 있습니다.
  • fan-out -> aggregate 구조가 문서 분석, 평가, 추천 생성 같은 작업에 왜 잘 맞는지 확인할 수 있습니다.

무엇을 해결하는가

  • 하나의 긴 프롬프트에 요약, 감정 분석, 핵심 포인트, 추천까지 모두 맡길 때 생기는 역할 혼합 문제를 줄입니다.
  • 독립 작업을 직렬로 길게 수행하면서 생기는 불필요한 대기 시간을 줄일 수 있습니다.
  • 중간 결과를 분리해 저장하므로 어떤 분석 단계에서 품질이 흔들리는지 추적하기 쉬워집니다.
  • 최종 응답이 하나의 관점에 치우치지 않고 여러 분석 결과를 반영하도록 만들 수 있습니다.

언제 사용하는가

  • 같은 입력을 서로 다른 관점에서 동시에 분석할 수 있을 때 적합합니다.
  • 각 하위 작업이 서로 결과를 기다리지 않아도 될 때 효과적입니다.
  • 최종 단계에서 여러 결과를 종합해 하나의 결론을 만들어야 할 때 잘 맞습니다.
  • 속도와 모듈성이 모두 중요한 워크플로우에서 유리합니다.

적합한 상황

  • 문서를 요약, 감성 분석, 핵심 포인트 추출, 추천 생성으로 나눠 동시에 처리하는 경우
  • 상품 리뷰를 별점 경향, 주요 불만, 장점, 개선 제안으로 병렬 분석하는 경우
  • 회의록에서 요약, 액션 아이템, 리스크, 후속 질문을 동시에 뽑는 경우
  • 지원서나 보고서를 여러 평가 기준으로 병렬 채점한 뒤 종합 의견을 만드는 경우

핵심 개념 설명

1. Parallel Nodes

  • 기술 설명
  • 여러 노드가 동일한 state["document"]를 입력으로 받아 각자 다른 분석을 수행합니다.
  • 이 노드들은 서로의 결과를 기다리지 않고 독립적으로 실행될 수 있습니다.
  • 쉬운 설명
  • 한 명이 모든 일을 다 하는 대신, 여러 사람이 같은 문서를 나눠서 동시에 각자 맡은 분석을 하는 구조입니다.
  • 코드 역할
  • get_summary, get_sentiment, get_key_points, get_recomendation

2. Shared State

  • 기술 설명
  • 각 병렬 노드는 자신이 만든 결과를 상태의 다른 필드에 기록합니다.
  • 이렇게 저장된 값은 마지막 aggregator 노드에서 함께 읽을 수 있습니다.
  • 쉬운 설명
  • 각 사람이 자기 분석 결과를 공용 메모판에 적어두고, 마지막 사람이 그 메모들을 보고 종합 보고서를 만드는 방식입니다.
  • 코드 역할
  • summary, sentiment, key_points, recommendation, final_analysis

3. Aggregator Node

  • 기술 설명
  • aggregator는 병렬 노드들이 만든 여러 필드를 입력으로 받아 최종 분석을 생성합니다.
  • 이 노드는 전체 워크플로우의 통합 지점이며, 부분 결과들을 사용자에게 보여줄 단일 출력으로 정리합니다.
  • 쉬운 설명
  • 여러 분석 보고서를 한 장의 최종 보고서로 정리하는 편집자 역할입니다.
  • 코드 역할
  • get_final_analysis

동작 흐름

  1. 사용자가 document를 입력합니다.
  2. START에서 네 개의 분석 노드로 동시에 흐름이 갈라집니다.
  3. 각 노드는 같은 문서를 기준으로 서로 다른 결과를 만듭니다.
  4. 각 결과는 상태에 저장됩니다.
  5. get_final_analysis가 이 상태값들을 읽어 종합 분석을 생성합니다.
  6. 최종 분석이 상태에 저장되고 그래프가 종료됩니다.

Prompt Chaining과 차이

  • Prompt Chaining은 앞 단계 출력이 다음 단계 입력이 되는 순차 구조입니다.
  • Parallelization은 여러 작업이 같은 입력을 기준으로 동시에 실행되는 구조입니다.
  • Prompt Chaining은 단계 간 의존성이 클 때 적합합니다.
  • Parallelization은 작업 간 독립성이 클 때 더 적합합니다.

장점

  • 독립 작업을 동시에 돌릴 수 있어 응답 시간을 줄이기 좋습니다.
  • 각 노드 책임이 분리되어 프롬프트 설계가 명확해집니다.
  • 특정 분석만 선택적으로 개선하기 쉽습니다.
  • aggregator를 통해 다면적인 결과를 하나로 통합할 수 있습니다.

주의할 점

  • 병렬로 나눈 작업이 실제로 독립적이지 않다면 결과 일관성이 깨질 수 있습니다.
  • aggregator 프롬프트가 약하면 부분 결과를 잘 모았더라도 최종 응답 품질이 떨어질 수 있습니다.
  • 상태 필드 이름이 정확히 맞지 않으면 마지막 통합 단계에서 누락이나 오류가 날 수 있습니다.
  • 입력 스키마와 실행 예시가 일치하지 않으면 이전 예제처럼 KeyError 같은 문제가 생길 수 있습니다.

stream_mode는 무엇인가

  • stream_mode는 LangGraph의 graph.stream(...)에서 무엇을 스트리밍해서 받을지 정하는 옵션입니다.
  • 이 예제에서는 각 노드가 실행될 때마다 새로 만들어진 상태 변화만 확인하기 위해 stream_mode="updates"를 사용합니다.
for chunk in graph.stream(
    {"document": document},
    stream_mode="updates"
):
    print(chunk, "\n")
  • 이 설정을 사용하면 전체 state를 매번 다 받는 것이 아니라, 각 노드가 이번 단계에서 새로 만든 값만 순서대로 받게 됩니다.
  • 따라서 병렬 노드가 있을 때 어떤 작업이 먼저 끝났는지 실시간으로 관찰하기 쉽습니다.

updates 예시

  • stream_mode="updates"는 각 단계에서 업데이트된 값만 반환합니다.
{"get_summary": {"summary": "..."}}
{"get_sentiment": {"sentiment": "..."}}
{"get_key_points": {"key_points": "..."}}
{"get_recomendation": {"recommendation": "..."}}
  • 이런 형태는 디버깅할 때 유용합니다.
  • 특히 병렬 구조에서는 어떤 노드가 먼저 완료되었는지 확인하기 좋습니다.
  • 실행 흐름을 설명하거나 중간 결과를 시각적으로 추적할 때도 많이 사용됩니다.

values와 차이

  • values
  • 매 단계마다 전체 state를 반환합니다.
  • updates
  • 매 단계마다 변경된 부분만 반환합니다.
  • 즉 values는 "현재까지 누적된 전체 상태"를 보는 데 적합하고, updates는 "이번 단계에서 무엇이 새로 바뀌는지"를 보는 데 적합합니다.

16.4 Parallelization Architecture - 왜 병렬인데 순차처럼 보이는가

수정 목적

  • 현재 Parallelization Architecture 실습가 왜 병렬 처리로 볼 수 있는지 정리합니다.
    - 화면에는 결과가 순차적으로 보이는데도 실제 실행은 병렬일 수 있는 이유를 설명합니다.
    - 병렬 실행 여부를 로그로 확인하는 방법과 get_final_analysis가 마지막에 실행되는 이유를 함께 복습합니다.

먼저 결론

  • 이 그래프는 앞단의 분석 노드들이 병렬로 실행되고, 마지막 get_final_analysis는 그 결과를 모두 받은 뒤 실행되는 구조입니다.
    - 따라서 "전체 그래프가 전부 동시에 실행되는 것"은 아니고, "앞단은 병렬, 마지막 aggregator는 순차"라고 이해하는 것이 가장 정확합니다.

왜 이 코드가 병렬 처리인가

그래프 연결을 보면 START에서 네 개의 노드로 동시에 갈라집니다.

graph_builder.add_edge(START, "get_summary")
graph_builder.add_edge(START, "get_sentiment")
graph_builder.add_edge(START, "get_key_points")
graph_builder.add_edge(START, "get_recomendation")

이 구조는 하나의 입력 문서를 네 개의 독립 작업으로 나누는 fan-out 구조입니다.

  • get_summary
    - get_sentiment
    - get_key_points
    - get_recomendation

이 네 노드는 모두 같은 document를 읽지만 서로의 결과를 기다리지 않습니다.
즉 의존성이 없기 때문에 같은 step 안에서 병렬 실행될 수 있습니다.

그런데 왜 화면에는 순차처럼 보이는가

헷갈리는 이유는 graph.stream(..., stream_mode="updates")의 출력 방식 때문입니다.

for chunk in graph.stream(
    {"document": document},
    stream_mode="updates"
):
    print(chunk, "\n")

이 코드는 병렬 노드 결과를 한꺼번에 섞어서 보여주는 것이 아니라, 끝난 결과부터 하나씩 이벤트처럼 출력합니다.

즉:

  1. 여러 노드가 병렬로 시작될 수 있습니다.
    2. 하지만 출력은 "완료된 순서대로" 하나씩 나옵니다.
    3. 그래서 화면만 보면 순차 실행처럼 느껴질 수 있습니다.

중요한 점은:

  • 출력이 순차적이라는 것
    - 실행이 순차적이라는 것

이 둘은 다를 수 있다는 점입니다.

실제로 병렬인지 로그로 확인하는 방법

노트북에는 시작 시각과 종료 시각을 찍는 로그 함수를 넣었습니다.

def log_node(event: str, node_name: str):
    now = datetime.now().strftime("%H:%M:%S.%f")[:-3]
    thread_name = threading.current_thread().name
    print(f"[{now}] [{thread_name}] {node_name} {event}")

각 노드에서는 시작과 종료 시점을 기록합니다.

def get_summary(state: State):
    started_at = time.perf_counter()
    log_node("start", "get_summary")
    response = llm.invoke(f"Write a 3-sentence summary of this document {state['document']}")
    elapsed = time.perf_counter() - started_at
    log_node(f"end ({elapsed:.2f}s)", "get_summary")
    return {
        "summary": response.content,
    }

이렇게 하면 실제 실행 시 아래처럼 로그가 나옵니다.

[12:43:22.721] [ThreadPoolExecutor-3_0] get_key_points start
[12:43:22.724] [ThreadPoolExecutor-3_1] get_recomendation start
[12:43:22.725] [ThreadPoolExecutor-3_2] get_sentiment start
[12:43:22.726] [ThreadPoolExecutor-3_3] get_summary start

이 로그에서 볼 수 있는 핵심은 다음과 같습니다.

  • 네 개 노드의 start 시각이 거의 동시에 찍힙니다.
    - 스레드 이름도 서로 다릅니다.
    - 즉 네 개 작업이 같은 시점에 병렬로 시작되었다는 근거가 됩니다.

반면 종료 시점은 이렇게 다르게 찍힐 수 있습니다.

[12:43:24.775] [ThreadPoolExecutor-3_3] get_summary end (2.05s)
[12:43:27.186] [ThreadPoolExecutor-3_2] get_sentiment end (4.46s)

이건 이상한 것이 아닙니다.
각 LLM 호출 시간이 다르기 때문에 시작은 비슷해도 끝나는 시점은 다를 수 있습니다.

chunk 출력이 순차적인 이유

스트리밍 셀에서는 이런 식으로 결과가 나옵니다.

for chunk in graph.stream(
    {"document": document},
    stream_mode="updates"
):
    print("chunk ->", list(chunk.keys())[0])
    print(chunk, "\n")

예를 들어:

chunk -> get_summary
chunk -> get_sentiment
chunk -> get_key_points
chunk -> get_recomendation

이 순서는 "실행 순서"가 아니라 완료된 결과가 밖으로 전달된 순서입니다.

즉:

  • get_summary가 먼저 끝나면 먼저 출력
    - get_sentiment가 나중에 끝나면 나중에 출력

그래서 stream 출력은 "병렬 실행 결과의 도착 순서"를 보여준다고 이해하면 쉽습니다.

get_final_analysis는 왜 마지막에 실행되는가

이 노드는 앞의 네 개 결과를 모아 최종 분석을 만드는 aggregator입니다.

그래프 연결은 이렇게 되어 있습니다.

graph_builder.add_edge("get_summary", "get_final_analysis")
graph_builder.add_edge("get_sentiment", "get_final_analysis")
graph_builder.add_edge("get_key_points", "get_final_analysis")
graph_builder.add_edge("get_recomendation", "get_final_analysis")

즉 get_final_analysis는 다음 값들이 필요합니다.

  • summary
    - sentiment
    - key_points
    - recommendation

따라서 이 노드는 앞의 네 노드가 모두 끝나기 전에는 실행될 수 없습니다.

흐름으로 보면:

  1. START
    2. 네 개 분석 노드 병렬 실행
    3. 각 결과가 state에 저장
    4. get_final_analysis 실행
    5. END

그래서 이 그래프는:

  • 앞단: 병렬
    - 마지막 통합 단계: 순차

로 이해하면 됩니다.

초보자 기준으로 가장 쉽게 이해하는 방법

이 구조를 "여러 사람이 동시에 일하고, 마지막에 한 사람이 보고서를 합치는 구조"라고 생각하면 쉽습니다.

  • get_summary: 요약 담당
    - get_sentiment: 감성 분석 담당
    - get_key_points: 핵심 포인트 담당
    - get_recomendation: 추천 담당
    - get_final_analysis: 최종 편집자

앞의 네 사람은 동시에 일할 수 있습니다.
하지만 최종 편집자는 앞의 네 사람이 결과를 다 제출해야 종합 보고서를 만들 수 있습니다.

병렬 여부를 판단하는 기준

병렬인지 확인할 때는 출력 순서만 보면 안 됩니다. 아래를 봐야 합니다.

1. 시작 시각이 거의 같은가

  • 병렬이라면 여러 노드의 start 시각이 거의 동시에 찍힙니다.

2. 서로 다른 실행 컨텍스트에서 동작하는가

  • 로그에 서로 다른 스레드 이름이 보이면 병렬 실행 근거가 됩니다.

3. 출력 순서는 완료 순서라는 점을 이해했는가

  • chunk가 순서대로 출력된다고 해서 실행 자체가 순차라는 뜻은 아닙니다.

자주 하는 오해

오해 1. 결과가 하나씩 나오니까 순차 실행이다

  • 아닙니다.
    - 스트리밍 출력은 병렬 작업의 완료 이벤트를 하나씩 보여주는 것입니다.

오해 2. get_final_analysis도 병렬이어야 한다

  • 아닙니다.
    - 이 노드는 앞의 결과를 모두 합쳐야 하므로 의존성 때문에 마지막에 실행되어야 합니다.

오해 3. 병렬이면 모든 로그가 완전히 같은 시간에 찍혀야 한다

  • 아닙니다.
    - 실제로는 몇 ms 차이로 시작할 수 있고, 종료 시점은 작업 난이도에 따라 크게 달라질 수 있습니다.

한 줄 결론

  • 이 코드는 앞단 분석 노드들이 병렬로 실행되고, stream은 그 완료 결과를 순서대로 보여주기 때문에 화면상 순차처럼 보일 뿐입니다. 마지막 get_final_analysis는 여러 결과를 합쳐야 하므로 모든 병렬 노드가 끝난 뒤에 실행됩니다.
외부 학습자료 기반 개인 재구성 원문

16.4 Parallelization Architecture - 총정리

수정 목적

  • Parallelization Architecture를 단일 예제가 아니라 전체 학습 흐름으로 다시 정리합니다.
    - 기존 16.4 문서들에서 나뉘어 설명된 병렬 실행 구조, stream 관찰 방식, 병렬처럼 보이지 않는 이유를 하나로 합칩니다.
    - 기존 문서를 삭제하지 않고, 여러 문서를 한 번에 복습할 수 있는 기준 문서를 만듭니다.

핵심 개념

  • Parallelization Architecture
    - 한 줄 정의: 하나의 입력을 여러 독립 작업으로 동시에 분기하고, 마지막에 결과를 합치는 구조입니다.
    - 필요한 상황: 같은 입력을 여러 관점으로 분석해야 하고, 각 작업이 서로를 기다리지 않아도 될 때 적합합니다.
    - 코드 역할: 요약, 감성 분석, 핵심 포인트, 추천 생성 같은 노드가 동시에 실행됩니다.
    - graph.invoke(...)
    - 한 줄 정의: 그래프를 끝까지 실행한 뒤 최종 state만 반환하는 실행 방식입니다.
    - 필요한 상황: 중간 과정 없이 최종 결과만 빠르게 확인하고 싶을 때 사용합니다.
    - 코드 역할: 병렬 노드 내부 상태 갱신은 일어나지만, 바깥에서는 마지막 결과만 보게 됩니다.
    - graph.stream(..., stream_mode="updates")
    - 한 줄 정의: 그래프 실행 중간에 발생하는 상태 변경을 단계별로 받는 방식입니다.
    - 필요한 상황: 병렬 실행 순서, 중간 결과, 디버깅 포인트를 관찰하고 싶을 때 필요합니다.
    - 코드 역할: 병렬 노드의 완료 순서대로 chunk를 받아 실행 흐름을 눈으로 확인할 수 있게 합니다.
    - Aggregator
    - 한 줄 정의: 병렬 노드가 만든 결과를 하나로 통합하는 마지막 노드입니다.
    - 필요한 상황: 분산된 결과를 사용자 응답 하나로 묶어야 할 때 필요합니다.
    - 코드 역할: summary, sentiment, key_points, recommendation을 읽어 final_analysis를 만듭니다.

동작 흐름

  • 병렬화 기본 흐름
    - User document 입력
    - START
    - get_summary, get_sentiment, get_key_points, get_recomendation 병렬 실행
    - get_final_analysis
    - 최종 상태 반환
    - 스트리밍 관찰 흐름
    - graph.stream(..., stream_mode="updates")
    - 각 노드 완료 시점마다 변경분 출력
    - 출력 순서는 실행 순서가 아니라 완료 순서입니다.

사용 이유

  • 병렬화 구조와 스트리밍 관찰 방식은 함께 봐야 실제 동작을 정확히 이해할 수 있습니다.
    - 화면에 순차적으로 보이는 출력만 보고 구조를 오해하는 문제를 줄일 수 있습니다.
    - 학습 문서가 여러 개로 나뉘어 있으면 개념이 분산되기 쉬우므로, 총정리 문서가 복습 기준점 역할을 합니다.

한 줄 요약

  • Parallelization Architecture는 같은 입력을 여러 독립 노드에 동시에 보내고, stream으로 그 완료 과정을 관찰하며, 마지막 aggregator가 결과를 하나로 합치는 구조입니다.

이번 변경으로 무엇을 공부할 수 있었는가

  • 병렬 노드와 aggregator로 구성된 fan-out -> aggregate 패턴을 공부할 수 있습니다.
    - invoke와 stream의 차이가 "업데이트 여부"가 아니라 "보여주는 방식" 차이라는 점을 이해할 수 있습니다.
    - 병렬 실행인데도 화면상 순차처럼 보이는 이유를 로그와 스트리밍 관점에서 설명할 수 있습니다.

무엇을 해결하는가

  • 하나의 프롬프트에 여러 역할을 몰아넣을 때 생기는 책임 혼합 문제를 줄입니다.
    - 중간 결과가 보이지 않아 병렬 동작을 오해하는 문제를 줄입니다.
    - 기존 16.4 문서들을 각각 다시 열어보지 않아도 핵심 개념을 한 번에 복습할 수 있게 합니다.

핵심 개념 설명

1. Parallel Nodes

  • 기술 설명
    - 여러 노드가 같은 document를 입력으로 받지만 서로의 결과를 기다리지 않고 독립적으로 실행됩니다.
    - LangGraph에서는 START에서 여러 노드로 edge를 연결하면 이런 병렬 fan-out 구조를 만들 수 있습니다.
    - 쉬운 설명
    - 한 문서를 여러 담당자에게 동시에 보내 각자 맡은 분석만 하게 만드는 구조입니다.
    - 코드 위치
    - get_summary, get_sentiment, get_key_points, get_recomendation

2. Shared State

  • 기술 설명
    - 각 병렬 노드는 자신이 만든 결과를 서로 다른 state 필드에 기록합니다.
    - 마지막 aggregator는 이 공용 state를 읽어 최종 결과를 만듭니다.
    - 쉬운 설명
    - 여러 사람이 같은 메모판에 자기 결과를 적고, 마지막 담당자가 그 메모를 보고 종합 보고서를 씁니다.
    - 코드 위치
    - summary, sentiment, key_points, recommendation, final_analysis

3. invoke와 stream

  • 기술 설명
    - invoke도 내부적으로 state를 계속 갱신하지만 최종 결과만 반환합니다.
    - stream은 실행 도중의 이벤트를 밖으로 내보내므로, 각 단계 결과를 순회하면서 볼 수 있습니다.
    - 쉬운 설명
    - invoke는 최종본만 받는 방식이고, stream은 작업 진행 상황을 중간중간 보는 방식입니다.
    - 코드 위치
    - graph.invoke(\{...\})
    - graph.stream(\{...\}, stream_mode="updates")

4. stream_mode="updates"

  • 기술 설명
    - updates는 전체 state가 아니라 이번 단계에서 새로 바뀐 값만 내보냅니다.
    - 병렬 구조에서는 어떤 노드가 먼저 끝났는지 확인하기 쉬워 디버깅에 유리합니다.
    - 쉬운 설명
    - 전체 메모판을 매번 다시 보는 대신, 방금 추가된 메모만 보는 방식입니다.
    - 코드 위치
    - for chunk in graph.stream(..., stream_mode="updates")

5. 왜 병렬인데 순차처럼 보이는가

  • 기술 설명
    - 병렬 실행된 노드들의 결과가 스트리밍 시점에는 완료 순서대로 하나씩 전달되기 때문입니다.
    - 따라서 출력이 순차적이라는 사실만으로 실행도 순차적이라고 판단하면 안 됩니다.
    - 쉬운 설명
    - 여러 사람이 동시에 일해도, 보고는 끝난 사람부터 차례대로 올라올 수 있습니다.
    - 코드 위치
    - chunk 출력 순서
    - 시작/종료 로그 타임스탬프

동작 흐름

  1. 사용자가 document를 입력합니다.
    2. 그래프는 START에서 네 개의 분석 노드로 동시에 분기합니다.
    3. 각 노드는 같은 문서를 서로 다른 관점으로 분석합니다.
    4. 각 노드 결과는 state의 서로 다른 필드에 저장됩니다.
    5. stream_mode="updates"를 쓰면, 각 결과는 완료된 순서대로 chunk로 보입니다.
    6. 모든 병렬 노드가 끝나면 aggregator가 이 결과를 읽어 final_analysis를 만듭니다.
    7. 최종 state가 반환됩니다.

코드 설명

병렬 분석 노드

  • get_summary
    - 문서를 짧게 요약합니다.
    - get_sentiment
    - 문서의 감정 톤을 분석합니다.
    - get_key_points
    - 핵심 포인트를 추출합니다.
    - get_recomendation
    - 후속 행동이나 추천을 생성합니다.

통합 노드

  • get_final_analysis
    - 앞선 네 개 결과를 읽어 최종 설명으로 통합합니다.
    - 의존성이 있으므로 병렬 노드가 모두 끝난 뒤 실행됩니다.

스트리밍 코드

for chunk in graph.stream(
    {"document": document},
    stream_mode="updates"  # NEW
):
    print(chunk, "\n")
  • 코드 의미
    - graph.stream(...)은 그래프를 실행하면서 중간 결과를 내보냅니다.
    - stream_mode="updates"는 변경분만 보여준다는 뜻입니다.
    - 따라서 병렬 구조에서는 어떤 노드가 먼저 끝났는지 확인하기 쉽습니다.

주석으로 기억할 핵심 포인트

  • stream_mode는 state를 바꾸는 옵션이 아니라, state 변경을 어떻게 보여줄지 정하는 옵션입니다.
    - chunk 출력 순서는 실행 순서가 아니라 완료 순서입니다.
    - aggregator는 병렬 노드가 만든 결과를 모두 받아야 하므로 마지막에 실행됩니다.

Before / After 비교

[Before]
- Parallelization 구조, stream 관찰, 병렬처럼 보이지 않는 이유가 각각 별도 문서에 나뉘어 있었습니다.

[After]
- 병렬 fan-out 구조, stream/invoke 차이, 완료 순서 출력, aggregator를 한 문서에서 이어서 볼 수 있습니다.
- 기존 16.4 문서들은 유지한 채, 전체 학습 흐름을 복습하는 기준 문서가 추가되었습니다.

핵심 변경사항 요약

  • 기존 16.4 병렬화 문서 3개를 하나의 학습 흐름으로 통합해 정리했습니다.
    - invoke, stream, stream_mode="updates", 완료 순서 출력, aggregator 실행 시점을 한 문서 안에서 연결했습니다.

전체 코드(최종본)

from typing import TypedDict
from langgraph.graph import StateGraph, START, END


class State(TypedDict):
    document: str
    summary: str
    sentiment: str
    key_points: str
    recommendation: str
    final_analysis: str


def get_summary(state: State):
    return {"summary": "..."}


def get_sentiment(state: State):
    return {"sentiment": "..."}


def get_key_points(state: State):
    return {"key_points": "..."}


def get_recomendation(state: State):
    return {"recommendation": "..."}


def get_final_analysis(state: State):
    return {
        "final_analysis": f"""
        Summary: {state['summary']}
        Sentiment: {state['sentiment']}
        Key Points: {state['key_points']}
        Recommendation: {state['recommendation']}
        """
    }


graph_builder = StateGraph(State)
graph_builder.add_node("get_summary", get_summary)
graph_builder.add_node("get_sentiment", get_sentiment)
graph_builder.add_node("get_key_points", get_key_points)
graph_builder.add_node("get_recomendation", get_recomendation)
graph_builder.add_node("get_final_analysis", get_final_analysis)

graph_builder.add_edge(START, "get_summary")
graph_builder.add_edge(START, "get_sentiment")
graph_builder.add_edge(START, "get_key_points")
graph_builder.add_edge(START, "get_recomendation")

graph_builder.add_edge("get_summary", "get_final_analysis")
graph_builder.add_edge("get_sentiment", "get_final_analysis")
graph_builder.add_edge("get_key_points", "get_final_analysis")
graph_builder.add_edge("get_recomendation", "get_final_analysis")

graph_builder.add_edge("get_final_analysis", END)

graph = graph_builder.compile()

result = graph.invoke({"document": document})

for chunk in graph.stream(
    {"document": document},
    stream_mode="updates"
):
    print(chunk)

16.4 Parallelization Architecture - graph.stream, invoke, stream_mode 이해

수정 목적

  • graph.stream(...)이 무엇을 하는지 초보자 기준으로 이해합니다.
    - invoke와 stream의 차이를 분명하게 구분합니다.
    - stream_mode가 state 업데이트 자체를 바꾸는 옵션이 아니라, 업데이트 결과를 어떻게 보여줄지 정하는 옵션이라는 점을 정리합니다.

먼저 한 줄로 정리

  • invoke는 그래프를 끝까지 실행한 뒤 최종 결과만 한 번에 받는 방식입니다.
    - stream은 그래프를 실행하면서 중간 결과를 단계별로 계속 받는 방식입니다.
    - stream_mode는 그 중간 결과를 어떤 형태로 보여줄지 정하는 옵션입니다.

왜 헷갈리기 쉬운가

  • invoke도 내부적으로는 state를 계속 업데이트합니다.
    - 그래서 처음 보면 "invoke도 업데이트되는데 왜 stream_mode="updates"를 따로 써야 하지?"라는 의문이 생기기 쉽습니다.
    - 핵심은 "업데이트가 일어나는가"와 "업데이트를 어떻게 보여주는가"는 다른 문제라는 점입니다.

graph.invoke(...)는 무엇인가

  • graph.invoke(...)는 그래프를 처음부터 끝까지 실행합니다.
    - 각 노드의 반환값은 내부적으로 state에 반영됩니다.
    - 하지만 사용자는 보통 중간 과정이 아니라 마지막 결과만 받습니다.
result = graph.invoke({"document": document})
print(result)
  • 이 방식은 "최종 state"를 한 번에 받는다고 이해하면 쉽습니다.
    - 즉 요약, 감성 분석, 핵심 포인트, 추천, 최종 분석이 내부적으로 차례로 state에 반영되더라도 바깥에서는 마지막 결과만 확인하게 됩니다.

graph.stream(...)는 무엇인가

  • graph.stream(...)도 그래프를 실행합니다.
    - 다만 실행 중간에 생기는 결과를 하나씩 바깥으로 내보냅니다.
    - 그래서 for문으로 순회하면서 각 단계의 결과를 받을 수 있습니다.
for chunk in graph.stream({"document": document}, stream_mode="updates"):
    print(chunk)
  • 여기서 chunk는 미리 만들어둔 변수가 아닙니다.
    - graph.stream(...)이 실행 중에 내보내는 값을 for문이 하나씩 받아서 chunk에 넣어주는 것입니다.
    - 즉 chunk는 "각 스트리밍 이벤트 1개"라고 이해하면 됩니다.

invoke와 stream의 차이

\| 항목 \| invoke \| stream \|
\| --- \| --- \| --- \|
\| 실행 방식 \| 그래프를 끝까지 실행 \| 그래프를 실행하면서 중간 결과도 전달 \|
\| 반환 형태 \| 최종 결과 1번 \| 중간 결과 여러 번 \|
\| 사용 방식 \| 결과를 한 번에 받고 싶을 때 \| 실행 흐름이나 중간 상태를 보고 싶을 때 \|
\| 병렬 노드 관찰 \| 어려움 \| 쉬움 \|

중요한 포인트: state 업데이트는 둘 다 한다

  • invoke도 state를 업데이트합니다.
    - stream도 state를 업데이트합니다.
    - 차이는 state 업데이트 여부가 아니라, 그 과정을 밖으로 보여주느냐의 차이입니다.

쉽게 말하면

  • invoke
    - 내부에서는 업데이트되지만 바깥에는 최종본만 보여줍니다.
    - stream
    - 내부 업데이트 과정을 바깥으로도 보여줄 수 있습니다.

stream_mode는 무엇인가

  • stream_mode는 graph.stream(...)에서 무엇을 스트리밍해서 받을지 정하는 옵션입니다.
    - 다시 말해 state를 어떻게 업데이트할지 정하는 옵션이 아니라, 업데이트된 결과를 어떤 모양으로 보여줄지 정하는 옵션입니다.
for chunk in graph.stream(
    {"document": document},
    stream_mode="updates"
):
    print(chunk, "\n")
  • 위 코드에서는 그래프가 실행될 때 각 노드가 state에 반영한 변경분만 순서대로 받습니다.
    - 따라서 병렬 구조에서는 어떤 노드가 먼저 끝났는지 실시간으로 보기 좋습니다.

updates는 무슨 뜻인가

  • stream_mode="updates"는 각 단계에서 방금 업데이트된 값만 보여줍니다.
    - 전체 state를 매번 다 주는 것이 아니라, 이번 단계에서 새로 생긴 부분만 보여주는 방식입니다.

예시

{"get_summary": {"summary": "이 문서는 ..."}}
{"get_sentiment": {"sentiment": "전반적으로 신중한 톤이다."}}
{"get_key_points": {"key_points": "1. 금리 유지\n2. 인플레이션 우려\n..."}}
{"get_recomendation": {"recommendation": "1. 시장 반응을 계속 확인\n2. ..."}}
{"get_final_analysis": {"final_analysis": "전체적으로 이 문서는 ..."}}
  • 이런 형태는 "이번 단계에서 뭐가 바뀌었는지"를 보기에 좋습니다.
    - 특히 병렬 구조에서는 어떤 노드가 먼저 끝났는지 파악하기 쉽습니다.

values는 어떻게 다른가

  • stream_mode="values"는 그 시점까지 누적된 전체 state를 보여줍니다.
    - 따라서 뒤로 갈수록 데이터가 점점 커집니다.

예시

{
    "document": "...원문...",
    "summary": "이 문서는 ..."
}
{
    "document": "...원문...",
    "summary": "이 문서는 ...",
    "sentiment": "전반적으로 신중한 톤이다."
}
{
    "document": "...원문...",
    "summary": "이 문서는 ...",
    "sentiment": "전반적으로 신중한 톤이다.",
    "key_points": "1. 금리 유지\n2. 인플레이션 우려\n..."
}
  • 이런 형태는 "현재까지 state가 어떻게 쌓였는지"를 보기에 좋습니다.
    - 반면 출력이 커질 수 있어서 간단히 흐름만 보려면 updates가 더 편한 경우가 많습니다.

초보자용 핵심 구분

1. 업데이트는 원래 항상 된다

  • 각 노드가 딕셔너리를 반환하면 LangGraph는 그 값을 state에 반영합니다.
    - 이건 invoke에서도 일어나고 stream에서도 일어납니다.

2. stream_mode는 업데이트 방식이 아니라 표시 방식이다

  • updates는 "바뀐 것만 보여주기"
    - values는 "현재 전체 state 보여주기"

3. stream은 중간 과정을 보고 싶을 때 쓴다

  • 병렬 노드 실행 순서를 보고 싶을 때
    - 디버깅하고 싶을 때
    - 단계별 결과를 설명하고 싶을 때

이 노트북에서의 흐름

  • 입력: document
    - 병렬 실행: get_summary, get_sentiment, get_key_points, get_recomendation
    - 통합: get_final_analysis

즉 이 그래프는 다음처럼 동작합니다.

  1. 입력 문서가 들어옵니다.
    2. 네 개의 분석 노드가 같은 문서를 기준으로 병렬 실행됩니다.
    3. 각 노드 결과가 state에 저장됩니다.
    4. 마지막 노드가 그 결과들을 읽어 최종 분석을 만듭니다.
    5. stream_mode="updates"라면 각 노드가 끝날 때마다 그 변경분만 chunk로 보게 됩니다.

가장 많이 헷갈리는 질문 정리

Q1. chunk는 어디서 오나요

  • graph.stream(...)이 실행되면서 내보내는 값을 for문이 하나씩 받습니다.
    - 즉 chunk는 스트리밍 중간 결과입니다.

Q2. invoke와 stream은 같은 건가요

  • 완전히 같지는 않습니다.
    - 둘 다 그래프를 실행하지만, invoke는 최종 결과만 주고 stream은 중간 결과도 줍니다.

Q3. stream_mode="updates"는 state를 업데이트하라는 뜻인가요

  • 아닙니다.
    - state 업데이트는 원래 일어납니다.
    - updates는 업데이트된 부분만 보여주겠다는 뜻입니다.

Q4. 왜 invoke는 stream_mode가 필요 없나요

  • invoke는 중간 결과를 보여주지 않고 최종 결과만 반환하기 때문입니다.
    - 즉 보여주는 형식을 고를 필요가 없습니다.

한 줄 결론

  • invoke는 "최종 결과만 받는 실행 방식"이고, stream은 "중간 결과까지 받는 실행 방식"이며, stream_mode는 그 중간 결과를 어떤 형태로 보여줄지 정하는 옵션입니다.

LangGraph 선형 그래프 구성 기초 정리

수정 목적

  • Python 3.13 환경에서 실행 가능한 최소 LangGraph 프로젝트 골격을 만드는 것이 목표입니다.
  • 가장 단순한 상태 기반 그래프 패턴(START -> node_one -> node_two -> node_three -> END)을 통해 실행 흐름을 먼저 고정합니다.
  • 패키지 선언과 의존성 잠금 파일을 함께 두어 재현 가능한 실습 환경을 만들었습니다.
  • 기존 코드가 없는 상태에서, 커밋 기준으로 프로젝트의 기본 뼈대를 학습 포인트로 정리했습니다.

핵심 개념

  • StateGraph: 상태(TypedDict)를 기준으로 노드를 연결해 실행 흐름을 선언하는 LangGraph의 그래프 빌더입니다.
  • State(TypedDict): 그래프 전반에서 공유되는 상태 스키마입니다.
  • START / END: 그래프의 시작/종료 지점입니다.
  • graph_builder.add_node: 실행 단위를 노드로 등록합니다.
  • graph_builder.add_edge: 노드 간 선형 흐름을 연결합니다.
  • graph.invoke({}): 노드 호출을 시작해 출력 메시지를 실제로 실행합니다.
  • 이 커밋은 실무 로직보다 “LangGraph 실행 구조의 최소 골격”을 학습하기 위한 스텝입니다.

동작 흐름

User 코드 실행 요청
      ↓
[입력: 상태 객체 {}]
      ↓
START → node_one → node_two → node_three
      ↓
END
      ↓
실행 결과 출력(콘솔 print)

사용 이유

  • 초보자도 먼저 노드 등록→연결→컴파일→호출의 패턴을 익히면, 이후 조건 분기/조건부 라우팅으로 확장하기가 쉽습니다.
  • 실습 노트북에서 바로 실행 가능해 실습/시연 학습에 적합합니다.
  • pyproject.toml과 uv.lock을 함께 두면 동일 환경 재현이 쉬워 팀 공유와 디버깅 비용이 줄어듭니다.

1. 한 줄 요약

  • 커밋에서 LangGraph의 기본 순차 그래프(세 노드 체인)를 실행 가능한 형태로 구성했습니다.

2. 무엇을 해결하는가

  • LangGraph 실행 엔진의 최소 동작 단위를 만들고, 상태 기반 그래프가 어떻게 작동하는지 한 번에 확인하도록 정리했습니다.
  • 의존성 정의와 Python 버전까지 고정해 다음 실습에서 즉시 이어서 실행할 수 있게 만들었습니다.

3. 시스템 구조 (Architecture Diagram)

[pyproject/uv.lock] ── 패키지 환경 고정
        ↓
      [실습 노트북]
        ↓
  StateGraph + 노드 등록 + 엣지 연결
        ↓
  graph.compile() ── 실행 엔진 생성
        ↓
     graph.invoke({})
        ↓
  콘솔 출력(node_one/node_two/node_three)

4. 핵심 개념 설명

기술 설명

  • TypedDict로 상태 타입을 명시합니다.
  • StateGraph(State)로 상태 공유 규칙을 가진 그래프를 정의합니다.
  • add_node로 노드 함수를 등록하고, add_edge로 실행 순서를 지정합니다.
  • compile 후 invoke로 실제 실행합니다.

쉬운 설명

  • 노드를 3개의 칸으로 된 컨베이어 벨트처럼 보고, 상태는 그 위를 흐르는 메모지처럼 생각하면 이해가 쉽습니다.
  • START에서 시작해 END로 가는 “항상 같은 순서”가 곧 동작의 핵심입니다.

코드 위치

  • 상태·그래프·노드 정의: 실습 노트북
  • 실행 환경과 의존성: .python-version, pyproject.toml, uv.lock

5. 동작 흐름

  • graph_builder = StateGraph(State)로 그래프 인스턴스 생성
  • node_one, node_two, node_three를 각각 등록
  • START → node_one → node_two → node_three → END로 고정된 라우팅 설정
  • graph = graph_builder.compile()로 실행 가능한 객체 생성
  • graph.invoke({})로 노드 실행 시작
  • 노드 함수는 각각 print("node_x") 출력

6. 코드 설명

  • 첫 실행 파일은 실습 노트북의 코드 셀이며, 실습 대상은 state 처리보다 그래프 연결입니다.
  • 현재 상태는 기본값으로 빈 딕셔너리({})를 전달하고 있으며, 이것으로도 노드 함수는 호출됩니다.
  • 각 노드 함수는 입출력 값이 없어도 동작을 확인 가능한 print 기반 예시입니다.

핵심 변경사항 ① 상태 기반 상태 스키마 도입

코드

from typing_extensions import TypedDict

class State(TypedDict):
    hello: str

코드 의미

  • ① 무엇인가: 노드 간 공유 상태의 타입 규칙입니다.
  • ② 어떻게 동작하는가: StateGraph(State)에 전달되어 상태 타입을 명확히 합니다.
  • ③ 실제 사용 방식: 필요 시 각 노드에서 state["hello"] 같은 값을 읽고 씁니다.
  • ④ 왜 필요한지: 타입 예측성이 높아져 노드 추가/확장 시 버그 원인 추적이 쉬워집니다.

핵심 변경사항 ② 선형 노드 체인 구성

코드

graph_builder = StateGraph(State)
...
graph_builder.add_node("node_one", node_one)
graph_builder.add_node("node_two", node_two)
graph_builder.add_node("node_three", node_three)

graph_builder.add_edge(START, "node_one")
graph_builder.add_edge("node_one", "node_two")
graph_builder.add_edge("node_two", "node_three")
graph_builder.add_edge("node_three", END)

graph = graph_builder.compile()
graph.invoke({})

코드 의미

  • ① 무엇인가: START→node_one→node_two→node_three→END 순서 그래프입니다.
  • ② 어떻게 동작하는가: 컴파일된 그래프를 invoke하면 선언된 순서대로 노드가 실행됩니다.
  • ③ 실제 사용 방식: 노드 함수 내부에서 계산/외부 API 호출/조건 분기 등을 추가하면 동작이 확장됩니다.
  • ④ 왜 필요한지: 분기보다 단순한 선형 파이프라인이 가장 빠르게 동작 원리를 검증하기 좋습니다.

📌 1️⃣ LangGraph의 본질

LangGraph는 이렇게 동작한다:

Node 실행
↓
State 일부 변경
↓
다음 Node로 전달

👉 핵심:

Node는 “값을 반환”하는 게 아니라

“State를 어떻게 바꿀지”를 반환한다

📌 2️⃣ 왜 Node 리턴이 dict이어야 하는가

🔹 이유: “부분 업데이트 (partial update)”를 위해

LangGraph는 State를 이렇게 관리한다:

state = {
    "dish": "hummus",
    "ingredients": [],
    "recipe_steps": ""
}

Node는 전체를 바꾸는 게 아니라:

return {"ingredients": [...]}

👉 의미:

"ingredients만 바꿔라"

👉 그래서 dict가 필요하다:

key 기반으로 어떤 값이 바뀌는지 명확하게 표현 가능

📌 3️⃣ 내부 update 동작

LangGraph 내부는 개념적으로 이렇게 동작한다:

new_state = old_state.copy()
new_state.update(node_output)

🔹 dict.update 의미

state.update({
    "ingredients": [...]
})

👉 내부적으로:

state["ingredients"] = [...]

🔹 결과

{
    "dish": "hummus",
    "ingredients": [...],  # ← 여기만 바뀜
    "recipe_steps": ""
}

👉 핵심:

기존 값 유지 + 일부만 변경

📌 4️⃣ 객체로 return하면 왜 문제인가

❌ 문제 1. “어디를 바꿀지” 알 수 없음

return Ingredient(...)

👉 이게 의미하는 바:

"이걸 state 어디에 넣어?"

👉 key 없음 → merge 불가

❌ 문제 2. partial update 불가능

객체는 보통:

State(dish=..., ingredients=..., recipe_steps=...)

👉 전체 상태 표현

하지만 LangGraph는:

{"ingredients": ...}

👉 일부만 변경

👉 철학 자체가 다름

❌ 문제 3. update 구조 깨짐

state.update(node_output)

👉 node_output은 반드시 dict여야 한다

객체면:

state.update(Ingredient(...))  # ❌ 불가능

❌ 문제 4. 데이터 흐름 깨짐

LangGraph는:

State = JSON-like 데이터 흐름

객체는:

Python 내부 구조

👉 외부(LMM, API, 로그)와 단절됨

📌 5️⃣ 핵심 개념 정리

🔹 LangGraph는 “객체 시스템”이 아니다

객체 흐름 ❌
데이터 흐름 ✔

🔹 Node는 “값 반환 함수”가 아니다

return 값 ❌
return 상태 변경(diff) ✔

🔹 State는 이렇게 변한다

초기 상태
↓
node1 → 일부 추가
↓
node2 → 일부 추가
↓
node3 → 일부 수정

👉 점진적 누적 구조

📌 🔥 최종 한 줄 정리

LangGraph는 dict.update 기반으로 State를 부분 업데이트하는 시스템이기 때문에

Node는 반드시 “변경할 key-value dict”를 반환해야 하며

객체를 반환하면 merge 구조가 깨진다

📌 🔥 진짜 핵심 감각

Java → 객체를 전달한다
LangGraph → 상태 변경(diff)을 전달한다

여기까지 이해하면 다음 단계 가능하다:

👉 여러 노드가 같은 key 수정할 때 충돌 처리

👉 reducer / aggregator

👉 병렬 노드 merge 전략

이거 들어가면 LangGraph 설계 끝난다

Python Graphviz는 왜 시스템 설치가 필요한가?

(가상환경 vs 시스템 바이너리 vs Docker 배포 구조 정리)

1. 문제 상황

pyproject.toml에 다음과 같이 작성되어 있다.

graphviz>=0.21

그리고 다음과 같이 설치한다.

uv add graphviz

그런데 실행 시 이런 에러가 발생한다:

ExecutableNotFound: failed to execute 'dot'

왜 이런 문제가 생길까?

2. 핵심 원인: 같은 이름이지만 다른 두 가지

graphviz는 실제로 두 개다.

1) Python 패키지 (wrapper)

설치 방법:

uv add graphviz

역할:

  • import graphviz 가능하게 함
  • DOT 언어 문자열 생성
  • 내부적으로 dot 실행파일 호출

렌더링은 하지 않는다.

2) 시스템 Graphviz 프로그램 (렌더링 엔진)

설치 방법 (macOS):

brew install graphviz

설치 위치 예시:

/opt/homebrew/bin/dot

역할:

  • DOT 파일을 PNG, SVG, PDF 등으로 변환
  • 실제 이미지 생성

C로 작성된 OS 레벨 실행파일이다.

3. 동작 구조

Graphviz가 실제로 동작하는 흐름은 다음과 같다.

Python 코드
    ↓
graphviz Python wrapper
    ↓
OS에 설치된 dot 실행파일
    ↓
이미지 생성

Python은 단지 "중간 호출자"다.

이미지를 그리는 것은 시스템에 설치된 dot이다.

4. 왜 가상환경으로는 해결되지 않는가?

가상환경이 관리하는 것

  • Python 패키지
  • site-packages 내부 모듈
  • Python 인터프리터 레벨 의존성

가상환경이 관리하지 못하는 것

  • OS 실행파일
  • C 기반 바이너리
  • /usr/bin, /opt/homebrew/bin 등 시스템 경로

dot은 Python 코드가 아니라 OS 프로그램이기 때문에

venv 범위를 벗어난다.

따라서:

  • Python 패키지만 설치 → dot을 못 찾아서 에러
  • 시스템 프로그램만 설치 → import graphviz 실패

결론: 둘 다 필요하다.

5. 왜 Python 패키지에 엔진을 포함하지 않는가?

Graphviz 엔진은:

  • C 기반
  • OS별로 빌드 필요
  • 폰트 및 시스템 라이브러리 의존
  • 크기가 큼

pip 패키지에 포함시키면:

  • macOS / Linux / Windows 각각 다른 바이너리 필요
  • wheel 용량 증가
  • 빌드 환경 복잡도 상승

그래서 Python 패키지는 단순 wrapper 역할만 한다.

6. Docker 환경에서는 어떻게 하나?

Docker에서는 OS와 Python을 함께 격리할 수 있다.

예시:

FROM python:3.13-slim

RUN apt-get update && apt-get install -y graphviz
RUN pip install graphviz

WORKDIR /app
COPY . /app

CMD ["python", "main.py"]

이렇게 하면:

  • 컨테이너 내부에 OS-level graphviz 존재
  • Python-level graphviz 존재

완전히 격리된 실행 환경이 된다.

7. 이것을 어떻게 이해하면 좋은가?

이 구조는 다음과 비슷하다.

  • psycopg2 → PostgreSQL 서버 필요
  • torch → CUDA 드라이버는 OS에 존재
  • ffmpeg-python → ffmpeg 바이너리 필요

Python은 모든 걸 처리하는 게 아니라

외부 엔진을 호출하는 "래퍼"인 경우가 많다.

8. 최종 정리

  • uv add graphviz는 Python wrapper 설치
  • brew install graphviz는 실제 렌더링 엔진 설치
  • 가상환경은 OS 바이너리를 관리하지 못함
  • Docker에서는 둘 다 함께 설치하면 문제 없음

가상환경은 Python 세계만 관리하고, Graphviz는 OS 세계 엔진을 사용하기 때문에 시스템 설치가 필요하다.

컨테이너에서는 둘 다 함께 넣으면 완전한 격리가 가능하다.

📌 🔥 개념 + 코드 통합 정리

📌 1️⃣ State = 공유 데이터 저장소

from typing_extensions import TypedDict

📌 2️⃣ Node = State를 읽고 diff 반환

🔹 Node 1

def list_ingredients(state: State):

👉 핵심:

전체 state 반환 ❌
변경사항만 반환 ✔

🔹 Node 2

def create_recipe(state: State):

    recipe = f"Mix {', '.join(ingredients)} and blend."

    return {"recipe_steps": recipe}

graph_builder = StateGraph(State)

graph_builder.add_node("list_ingredients", list_ingredients)
graph_builder.add_node("create_recipe", create_recipe)

graph_builder.add_edge(START, "list_ingredients")
graph_builder.add_edge("list_ingredients", "create_recipe")
graph_builder.add_edge("create_recipe", END)

graph = graph_builder.compile()

를 정적으로 표현한 구조도다.

즉:

  • 어떤 Agent가 존재하는지
  • 어떤 handoff가 연결되어 있는지
  • 어떤 Tool이 연결되어 있는지
  • 시작과 종료 노드가 어떻게 연결되는지

를 보여주는 설계도(Architecture Diagram)다.

실제 실행 흐름은 다음과 같다:

  ↓
Assistant Agent (Router 판단)
  ↓
Geo Expert Agent

하지만 draw_graph는 이렇게

“실제로 어떤 경로를 탔는지”를 표시하지 않는다.

대신 이렇게 보여준다:

__start__
   ↓
Assistant Agent

Geo Agent   Economics Agent

get_weather      __end__

즉:

  • Geo로 갈 수도 있고
  • Economics로 갈 수도 있고
  • Tool도 연결되어 있다

는 가능한 전체 구조를 보여주는 것이다.

외부 학습자료 기반 개인 재구성 원문

TypedDict 정리

from typing_extensions import TypedDict

class EmailState(TypedDict):
    email: str
    priority: str

TypedDict는 객체 클래스가 아니라 딕셔너리 키-타입 설명입니다.

왜 TypedDict를 상속하나?

클래스 상속 형식은 문법적으로 보이지만, 타입 검사기에게 정해진 딕셔너리 스키마를 알리는 선언입니다.

타입 검사에서 잡히는 사례

  • 필수 키가 빠지면 누락으로 판단됩니다.
  • 값 타입이 다르면 타입 오류로 검출 대상이 됩니다.

주의사항

코드에서 필드 타입이 빠진 선언은 TypedDict 필드로 유효하지 않습니다. 각 키마다 타입을 명시하세요.

원문 보존 단위

LangGraph 상태(State) 복잡도 관리 전략

1. 문제 정의

LangGraph에서 State가 복잡해지는 상황

  • State에 데이터가 과도하게 누적됨
  • 노드 간 의존성이 증가
  • 디버깅 및 유지보수 어려움
  • 특정 노드 수정 시 전체 영향 발생

→ 단순 코드 문제가 아니라 워크플로우 설계 문제

2. 핵심 원칙

State는 저장소가 아니다

  • State = 흐름 제어용 데이터
  • 대용량 데이터 저장 용도 아님

3. 해결 전략

3.1 State 최소화

핵심 아이디어

  • 필요한 정보만 유지
  • 중간 결과를 모두 저장하지 않음

예시

❌ 전체 로그 저장
state = { "logs": [...] }

✅ 요약 정보만 저장
state = { "error_summary": "OOM 발생" }

3.2 State 구조화 (Schema 설계)

문제

  • State가 커지는 이유 = 구조 없음

해결

  • TypedDict / Pydantic 사용
  • 단계별 필드 분리

예시

state = {
  "input": {},
  "processed": {},
  "analysis": {},
  "result": {}
}

효과

  • 책임 분리
  • 디버깅 용이
  • 확장성 증가

3.3 Graph 분리 (Subgraph 구조)

핵심

  • 하나의 Graph에 모든 로직을 넣지 않음
  • 기능 단위로 분리

구조

  • 상위 Graph → orchestration
  • 하위 Graph → 기능 수행

예시

  • Log 수집 Graph
  • 분석 Graph
  • 요약 Graph

효과

  • 복잡도 감소
  • 재사용성 증가

3.4 상태 전달 최적화

문제

  • 모든 노드가 전체 State를 공유

해결

  • 필요한 데이터만 전달

전략

  • partial state 전달
  • immutable state (copy-on-write)
  • event 기반 전달

효과

  • 의존성 감소
  • 사이드 이펙트 감소

3.5 Externalization (핵심 고급 전략)

문제

  • 모든 데이터를 State에 저장하려고 함

해결

  • 외부 저장소 활용

예시

state = {
  "log_ref": "s3://logs/123"
}

외부 저장소

  • S3 / MinIO
  • DB
  • Cache (Redis)

효과

  • State 경량화
  • 성능 개선
  • 확장성 확보

4. 아키텍처 관점 정리

[User Input]
      ↓
[Orchestration Graph]
      ↓
 ┌───────────────┐
 │ Sub Graph     │
 │ (Log Collect) │
 └───────────────┘
      ↓
 ┌───────────────┐
 │ Sub Graph     │
 │ (Analysis)    │
 └───────────────┘
      ↓
 ┌───────────────┐
 │ Sub Graph     │
 │ (Summary)     │
 └───────────────┘
      ↓
[Result]

State는 각 단계에서 최소한으로 전달됨

5. 면접 답변 템플릿

LangGraph에서 state가 복잡해지는 문제는 단순히 agent를 나누는 것으로 해결하기보다는
state 자체를 최소화하고 구조화하는 방향으로 접근해야 한다고 생각합니다.

먼저 state는 흐름 제어에 필요한 최소한의 정보만 유지하고,
로그나 대용량 데이터는 외부 저장소로 분리합니다.

또한 state를 Typed 구조로 정의하여 단계별로 책임을 나누고,
전체 graph를 subgraph 단위로 분리하여 관리합니다.

마지막으로 각 노드는 전체 state를 공유하기보다 필요한 데이터만 전달받도록 설계하여
상태의 복잡도를 줄이는 방향으로 설계합니다.

6. 핵심 요약

  • State는 저장소가 아니라 흐름 제어 도구
  • 최소화 → 구조화 → 분리 → 외부화 순으로 해결
  • 단순 분리가 아니라 아키텍처 설계 문제

7. 추가로 준비해야 할 것 (면접 대비)

꼬리 질문 대비

  • 실제 State가 커져서 문제된 경험
  • Externalization 적용 사례
  • Subgraph 설계 경험
  • 디버깅 전략

편입 후 검증 메모

  • State: 노드가 반환하는 dict는 전체 State 교체가 아니라 channel별 update다. 같은 key를 여러 노드가 쓰면 reducer와 병렬 merge 규칙을 명시해야 한다.
  • 병렬성: 그래프 구조상 병렬 가능한 것과 실행 로그가 순차로 출력되는 것은 별개다. 시작·종료 시각, thread/task 식별자와 stream mode로 실제 중첩을 확인한다.
  • Send: 동적 worker 입력을 만들 때 사용하며, 결과를 모으는 State key에는 결합 가능한 reducer가 필요하다.
  • 시각화: Graphviz Python 패키지와 시스템 실행 파일은 역할이 다르다. 렌더러가 필요한 기능은 OS 패키지 설치 여부를 별도로 확인한다.
