1. 입력과 출력의 계약

요청 시 모델은 사용자 메시지와 선택 가능한 tools 목록을 함께 본다. 응답은 일반 텍스트이거나 함수 호출 후보일 수 있다.

사용자: "문서 R-1042의 상세 내용을 보여줘"
tools: [read_resource, list_resources, ...]
↓
assistant.message.tool_calls[0]
  function.name = "read_resource"
  function.arguments = {"resource_id": "R-1042", "format": "detail"}

이 출력은 “read_resource를 실행하라”는 신뢰할 수 있는 명령이 아니라, 서버가 검증할 구조화된 제안이다.

2. Schema가 제한하는 것

Schema는 함수의 이름·설명·인자 타입·필수값·허용 enum을 고정한다. 예시 시스템에서는 조회 함수만 허용하고 additionalProperties: false로 알 수 없는 키를 막을 수 있다.

{
  "name": "read_resource",
  "parameters": {
    "type": "object",
    "properties": {
      "resource_id": {"type": "string"},
      "format": {"type": "string", "enum": ["summary", "detail"]}
    },
    "required": ["resource_id"],
    "additionalProperties": false
  }
}

JSON으로 파싱되는 것과 Schema를 만족하는 것은 다르다. 문자열이 JSON이어도 필수값이 없거나 잘못된 enum이면 실행 전에 거절해야 한다.

3. 모델·서버·실행기의 경계

권한 경계
도구 설명을 프롬프트에 넣었다고 모델에게 실행 권한이 생기는 것은 아니다. 실행기는 반드시 모델 출력과 독립적으로 권한을 확인해야 한다.

4. 한 번의 호출과 Agent Loop

한 번의 호출:
user → model(tool_call) → server 실행 → 결과 반환

Agent Loop:
user → model(tool_call) → server 실행
     → tool result를 다시 model에 전달
     → 다음 호출 또는 최종 답변

한 번의 호출만 사용하는 시스템과 여러 도구를 순서대로 사용하며 상태·재시도·종료 조건을 관리하는 시스템은 다르다. 후자는 Loop Engineering / Agentic Loop에서 다룬다.

5. 재사용 가능한 결론

Function Calling 품질은 함수명을 맞히는 것만이 아니라, 도구 계약·생략 가능한 인자·검증 정책·실행 권한을 함께 설계하는 문제다.
