가변 인자 (*args, **kwargs) 완벽 정리

  1. 가변 인자란?

함수를 정의할 때 인자의 개수를 미리 정하지 않고, 호출 시점에 원하는 만큼의 인자를 넘길 수 있게 하는 문법입니다.

2. 핵심 메커니즘: "자동 래핑(Wrapping)"

가장 중요한 차이점은 사용자가 직접 괄호를 써서 묶어주느냐, 파이썬이 알아서 묶어주느냐의 차이입니다.

구분 기호 자동 래핑 형식 호출 예시 함수 내부 모습
args * Tuple (튜플) func(1, 2, 3) args = (1, 2, 3)
kwargs ** Dictionary (딕셔너리) func(a=1, b=2) kwargs = {'a': 1, 'b': 2}

3. 왜 그냥 튜플/딕셔너리 타입을 안 쓰고 가변 인자를 쓰나요?

① 사용자의 편의성 (문법적 설탕)

  • 일반 튜플 인자: func((1, 2, 3)) 처럼 호출자가 직접 소괄호를 쳐서 묶어줘야 합니다.
  • 가변 인자 (args): func(1, 2, 3) 처럼 나열만 하면 파이썬이 알아서 튜플로 포장합니다. (가독성이 훨씬 좋습니다.)

② 유연한 함수 설계

고정된 인자와 가변적인 인자를 섞어서 쓸 때 매우 직관적입니다.

def make_pizza(size, *toppings):
    # size는 첫 번째 인자로, 나머지는 toppings 튜플로 쏙!
    print(f"{size} 피자에 {toppings} 추가")

make_pizza("Large", "치즈", "페퍼로니")`

③ 설정 값(Option) 전달의 용이성

  • *kwargs를 사용하면 마치 변수를 지정하듯 key=value 형태로 옵션을 넘길 수 있어, 딕셔너리 데이터를 직접 만드는 번거로움을 덜어줍니다.
원문 보존 단위

데코레이터(Decorator)와 AOP

1. 데코레이터는 파이썬식 AOP이다

  • 핵심 로직: 함수가 원래 하려던 일 (예: 데이터 계산, DB 저장)
  • 횡단 관심사(Cross-cutting Concerns): 로직 전후에 공통으로 필요한 일 (예: 실행 시간 측정, 로그인 확인, 권한 체크)
  • 데코레이터의 역할: 핵심 로직을 건드리지 않고 횡단 관심사를 모듈화하여 @ 하나로 적용함.

2. 왜 args, *kwargs가 필수인가?

데코레이터는 '어떤 함수'가 자기 안으로 들어올지 미리 알 수 없습니다.

  • 인자가 없는 함수, 1개인 함수, 키워드 인자가 5개인 함수 등 다양하겠죠?
  • 포장지(Wrapper)가 어떤 선물이든 다 감쌀 수 있도록, 모든 인자를 다 받아낼 수 있는 가변 인자를 사용하는 것입니다.

3. 데코레이터 최종 구조 및 샘플

def login_required(func):
    def wrapper(*args, **kwargs):
        # [공통 로직/AOP] 로그인 여부 확인
        is_login = True # 예시를 위한 변수
        if not is_login:
            return "로그인이 필요합니다."

        # [핵심 로직] 원래 함수 실행
        return func(*args, **kwargs)
    return wrapper

@login_required
def write_post(title, content):
    return f"포스팅 완료: {title}"

@login_required
def delete_comment(comment_id):
    return f"{comment_id}번 댓글 삭제"`

데코레이터 핵심 요약

  1. AOP 구현: 여러 함수에 공통적으로 적용될 기능을 분리하여 코드 중복을 제거함.
  2. 함수의 일급 객체 특성 활용: 함수를 인자로 받고, 새로운 함수(wrapper)를 만들어 반환함.
  3. 유연성: args, *kwargs를 사용해 인자의 개수나 종류에 상관없이 모든 함수를 장식(Decorate)할 수 있음.
  4. 가독성: @데코레이터_이름만 보고도 이 함수가 어떤 부가 기능을 수행하는지 한눈에 파악 가능.
원문 보존 단위

제너레이터(Generator) 핵심 정리

1. 제너레이터 생성 방법 (두 가지 형태)

① yield 함수형 (정석)

복잡한 로직이나 구간별 처리가 필요할 때 사용합니다. yield를 만나면 값을 반환하고 그 자리에 함수 실행을 '일시 정지'합니다.

② 제너레이터 표현식 (축약형)

리스트 컴프리헨션과 유사하지만 소괄호 ()를 사용합니다.

# 리스트: 100만 개를 즉시 메모리에 생성 [ ]
list_data = [i for i in range(1000000)]

# 제너레이터: 100만 개를 만들 '규칙'만 저장 ( )
gen_data = (i for i in range(1000000))

2. 실무 활용 샘플 및 메모리 동작 원리 (중요)

아래 코드는 100GB 이상의 대용량 로그를 처리할 때 사용하는 가장 표준적인 방식입니다. 각 줄이 실행될 때의 메모리 변화를 주목하세요.

def get_errors_gen(file_path):
    # [Step 1] 통로(빨대)만 확보
    # open()은 파일을 읽지 않습니다. 파일의 시작 지점을 가리키는
    # '파일 포인터(Pointer)' 정보만 생성하여 메모리 점유가 거의 없습니다.
    with open(file_path, 'r') as f:

        # [Step 2] 데이터 로드 시점 (한 모금씩 마시기)
        # for문이 돌 때 비로소 '한 줄'씩 메모리에 올라옵니다.
        for line in f:
            if "ERROR" in line:
                # [Step 3] 일시 정지 및 전달
                # 찾은 '한 줄'만 메모리에 둔 채로 호출자에게 전달하고 멈춥니다.
                yield line.strip()

        # [Step 4] 메모리 교체
        # 다음 루프가 돌면 이전 line이 차지했던 메모리는 비우고(GC),
        # 새로운 '한 줄'만 다시 가져와서 채우기를 반복합니다.

💡 이 방식이 왜 획기적인가? (면접 필살기)

  • 메모리 고정: 파일 크기가 100GB든 1TB든, 내 프로그램의 최대 메모리 점유량은 항상 '가장 긴 한 줄의 크기'로 일정하게 유지됩니다.
  • 지연 연산(Lazy Evaluation): 모든 데이터를 다 읽을 때까지 기다릴 필요 없이, 첫 번째 에러가 발견되는 즉시 바로 처리를 시작할 수 있습니다.

3. 리스트 vs 제너레이터 한눈에 비교

구분 리스트 (List) 제너레이터 (Generator)
생성 시점 선언 즉시 모든 데이터 생성 next() 호출 시점에 하나씩 생성
메모리 사용 데이터 개수에 비례 (메모리 폭발 위험) 데이터 개수와 상관없이 매우 적음
비유 도서관 책을 몽땅 빌려와서 쌓아두기 번호표만 가지고 있다가 한 권씩 빌려보기

4. 면접용 최종 요약 (Q&A)

Q. 제너레이터가 리스트보다 메모리 효율이 좋은 구체적인 이유가 뭔가요?

A. 리스트는 모든 데이터를 메모리에 미리 적재하지만, 제너레이터는 파일 포인터를 활용해 필요한 시점에만 데이터를 읽어오는 지연 연산(Lazy Evaluation)을 수행하기 때문입니다. 이를 통해 전체 데이터가 아닌 '현재 처리 중인 단위'만큼의 메모리만 유지하며 대용량 데이터를 안전하게 처리할 수 있습니다.

원문 보존 단위

클래스 기초 (self와 __init__)

1. __init__ 메서드: "객체 초기화의 마법사"

많은 분이 생성자라고 부르지만, 정확히는 초기화(Initializer) 메서드입니다.

  • 호출 시점: 클래스 이름으로 객체를 만드는 순간(p = Person()) 자동으로 실행됩니다.
  • 역할: 객체가 태어나자마자 가져야 할 초기값(이름, 나이 등)을 설정합니다.

2. self: "이 데이터는 내 거야!"

self는 인스턴스(생성된 객체) 자신을 가리키는 대명사입니다.

  • 왜 명시적으로 쓰나요?
  • 파이썬은 메서드를 호출할 때 호출한 객체를 첫 번째 인자로 자동으로 전달합니다.
  • p.greet()라고 쓰면 내부적으로는 Person.greet(p)로 동작하는 셈이죠. 그래서 받을 때도 self라는 자리가 필요합니다.
  • 필드 접근: self.name = name이라고 쓰는 순간, 그 데이터는 클래스 공용이 아니라 그 객체만의 고유한 저장 공간(필드)에 저장됩니다.

3. 실무 예제: self가 없으면 발생하는 일

class Dog:
    def __init__(self, name):
        self.name = name  # self를 붙여야 객체에 저장됨

    def bark(self):
        # self.name이 아니라 그냥 name이라고 쓰면 에러 발생!
        print(f"{self.name}: 멍멍!")

dog1 = Dog("초코")
dog2 = Dog("백구")

dog1.bark() # "초코: 멍멍!"
dog2.bark() # "백구: 멍멍!"

만약 self가 없다면, 파이썬은 bark 안에서 어떤 강아지의 이름을 불러야 할지 알 수 없게 됩니다.

노션 정리용 요약

  • __init__: 객체 생성 시 자동으로 호출되어 초기 상태를 설정하는 메서드.
  • self: 인스턴스 메서드가 호출될 때 "어떤 객체가 나를 불렀는지" 알려주기 위해 전달되는 첫 번째 인자.
  • 핵심 포인트: self를 통해 동일한 클래스로부터 만들어진 여러 객체가 각자 서로 다른 고유한 상태(값)를 유지할 수 있음.
원문 보존 단위

클래스 변수 vs 인스턴스 변수

🐍 파이썬 클래스 변수 vs 인스턴스 변수 완벽 정리

1. 기본 개념 (Java와 비교)

파이썬 클래스 내부에 선언된 변수는 기본적으로 Java의 static 변수처럼 동작합니다.

  • 클래스 변수: 모든 객체가 공유하는 변수 (Java의 static)
  • 인스턴스 변수: 각 객체가 개별적으로 가지는 변수 (Java의 일반 필드)
class Developer:
    language = "Python"  # 클래스 변수 (공유)

    def __init__(self, name):
        self.name = name # 인스턴스 변수 (독립)

2. 수정의 법칙: "누가 접근하느냐"가 핵심

여기서 자바와 파이썬의 가장 큰 차이가 발생합니다. 파이썬은 객체(인스턴스)를 통해 클래스 변수 값을 바꾸려 할 때 아주 독특하게 반응합니다.

🅰️ 클래스 이름으로 수정할 때 (정석)

  • 동작: 클래스 변수 자체가 바뀝니다.
  • 결과: 해당 클래스로 만든 모든 객체의 값이 한꺼번에 바뀝니다. (Java의 static 수정과 동일)

🅱️ 인스턴스(객체) 이름으로 수정할 때 (함정 ⚠️)

  • 동작: 클래스 변수를 건드리지 않습니다. 대신, 그 객체 안에 클래스 변수와 이름이 똑같은 '인스턴스 변수'를 새로 만들어 버립니다.
  • 결과: 해당 객체만 별도의 값을 갖게 되고, 다른 객체들은 여전히 원래의 클래스 변수 값을 바라봅니다.

3. 한눈에 보는 수정 결과 비교

dev1 = Developer("Alice")
dev2 = Developer("Bob")

# 상황 1: 클래스 이름으로 수정 (모두 바뀜)
Developer.language = "Kotlin"
print(dev1.language) # Kotlin
print(dev2.language) # Kotlin

# 상황 2: 인스턴스(dev1)로 수정 (dev1만 독립!)
dev1.language = "Java"
print(Developer.language) # Kotlin (클래스 변수는 그대로)
print(dev1.language)      # Java   (자기만의 변수가 새로 생김)
print(dev2.language)      # Kotlin (여전히 클래스 변수를 참조)

4. 상수(final)의 부재

파이썬에는 final 키워드가 없습니다. 오로지 약속으로만 존재합니다.

  • 관례: 변수명을 모두 대문자(MAX_COUNT = 10)로 쓰면 개발자들끼리 "이건 절대 바꾸지 말자"라고 약속한 것입니다.
  • 진실: 실제로는 바꿀 수 있습니다. 하지만 바꾸면 협업하는 동료들에게 큰 혼란을 주게 됩니다.

📝 최종 요약 (자바 개발자용 암기법)

  1. 클래스 변수 수정: 무조건 클래스명.변수명으로 접근하라. (안 그러면 나만의 변수가 새로 생겨버림)
  2. 공유 vs 독점: 클래스 변수는 공유되지만, 객체가 값을 새로 쓰는 순간 그 객체는 클래스 변수를 가리고(Shadowing) 자기만의 값을 갖는다.
  3. 상수: final은 없으니 대문자를 믿어라.

후속 학습 후보

변수 타입을 이해하셨다면, 이제 파이썬의 메서드(Method) 종류에 대해 알아볼 차례입니다.

파이썬에는 self를 받는 일반 메서드 외에도 @classmethod와 @staticmethod라는 독특한 데코레이터가 있습니다.

자바의 static method와 비슷해 보이지만, 파이썬에서는 왜 이 둘을 굳이 구분해서 쓸까요? 이 차이점에 대해 궁금하지 않으신가요?

파이썬 컨텍스트 매니저 (Context Manager) 총정리

🛠 파이썬 컨텍스트 매니저 (Context Manager) 총정리

1. 컨텍스트 매니저란?

리소스(파일, DB 연결, 락 등)를 사용할 때 "시작 시 준비 → 사용 → 종료 시 해제"의 과정을 자동으로 관리해 주는 도구입니다. with 문과 함께 사용하며, 코드 중간에 에러가 발생하더라도 반드시 뒷정리를 보장합니다.

2. 구현 방식 비교: 클래스 vs 함수

A. 클래스 방식 (__enter__, __exit__)

객체 지향적으로 상태를 저장하거나 정교한 에러 처리가 필요할 때 사용합니다.

  • __enter__: 리소스를 준비하고 as 뒤의 변수에 값을 전달합니다.
  • __exit__: with 블록을 나갈 때 실행됩니다. 에러 정보(type, value, traceback)를 인자로 받아 에러 처리 여부를 결정할 수 있습니다.
class MyResource:
    def __enter__(self):
        print("1. 리소스 확보")
        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        print("3. 리소스 해제 (무조건 실행)")
        if exc_type:
            print(f"로그: 에러 발생 - {exc_val}")
        return True # 에러를 외부로 전파하지 않음 (False면 전파됨)

B. 함수 방식 (@contextmanager)

간단한 로직을 구현할 때 매우 유용하며 가독성이 좋습니다. yield를 기준으로 실행 시점이 나뉩니다.

  • yield 이전: __enter__ 역할 (준비)
  • yield 이후: __exit__ 역할 (정리)

3. [중요] 실무형 에러 방지 (Safe Cleanup)

함수형 방식(@contextmanager)에서 yield 이후의 코드는 with 블록 내에서 에러가 발생하면 실행되지 않을 수 있습니다. 이를 방지하기 위해 try...finally로 감싸는 것이 실무 표준입니다.

from contextlib import contextmanager

@contextmanager
def safe_database():
    try:
        print("1. DB 연결 (준비)")
        yield "DB Connection"
    finally:
        # yield 부분에서 에러가 나더라도 finally는 무조건 실행됨
        print("3. DB 연결 해제 (정리 보장)")

# 사용 예시
with safe_database() as db:
    print(f"2. {db} 작업 중...")
    # raise ValueError("갑작스런 에러!")

4. 핵심 요약 (노션 복습용)

특징 클래스 방식 함수형 방식 (@contextmanager)
장점 상태 저장 용이, 복잡한 에러 제어 가능 코드가 간결하고 구현이 빠름
에러 대응 __exit__에서 자동으로 에러 감지 내부에서 try...finally를 써야 안전함
추천 상황 라이브러리 개발, 복잡한 상태 관리 간단한 로깅, 임시 설정 변경, DB 연결

"컨텍스트 매니저는 리소스 누수를 방지하는 안전장치입니다. 클래스에서는 __exit__가, 함수형에서는 finally 블록이 어떤 상황에서도 리소스를 해제하도록 보장하기 때문입니다."

원문 보존 단위

파이썬에서 순환 참조(circular reference)가 발생했을 때 어떤 일이 일어나며, 파이썬은 이를 어떻게 해결하나요?

사전지식

파이썬은 메모리를 자동으로 관리하기 위해 참조 카운팅(Reference Counting) 과 가비지 컬렉션(Garbage Collection, GC) 을 함께 사용합니다.

  1. 참조 카운팅
  • 모든 객체는 자신을 참조하는 횟수를 기록합니다.
  • 참조 카운트가 0이 되면, 즉 더 이상 그 객체를 참조하는 변수가 없을 때 메모리에서 즉시 해제됩니다.
  • 하지만 순환 참조(circular reference) 가 생기면, 서로 참조하기 때문에 참조 카운트가 0이 되지 않아 자동 해제가 안 됩니다.
  1. 가비지 컬렉션 (GC)
  • 참조 카운팅만으로 해결할 수 없는 순환 참조 문제를 해결하기 위해 주기적으로 동작합니다.
  • 세대별(Generational) 방식으로 관리되며, 일정 횟수 이상 객체가 생성·삭제되면 자동으로 실행됩니다.
  • gc 모듈을 통해 수동으로 실행하거나 상태를 확인할 수도 있습니다 (gc.collect(), gc.get_count() 등).
  1. del의 역할
  • del a는 객체를 삭제하는 것이 아니라, 변수명 a와 객체의 연결(참조)을 끊는 것뿐입니다.
  • 객체가 메모리에서 실제로 제거되려면, 참조 카운트가 0이 되어야 합니다.

질문

파이썬에서 순환 참조(circular reference)가 발생했을 때 어떤 일이 일어나며, 파이썬은 이를 어떻게 해결하나요?

모범 답변

파이썬은 기본적으로 참조 카운팅(reference counting) 으로 객체의 메모리를 관리합니다.

하지만 두 객체가 서로를 참조하면, 참조 카운트가 0이 되지 않아 자동 해제가 되지 않는 순환 참조(circular reference) 가 발생합니다.

이를 해결하기 위해 파이썬은 가비지 컬렉터(garbage collector) 를 사용합니다.

GC는 주기적으로 객체 그래프를 검사하여 외부에서 접근할 수 없는 순환 참조 객체들을 찾아 메모리에서 해제합니다.

즉, 일반적으로 순환 참조가 발생해도 자동으로 정리됩니다.

또한 개발자가 원할 경우 gc.collect()를 호출하여 수동으로 가비지 컬렉션을 강제로 실행할 수도 있습니다.

del a는 객체를 삭제하는 것이 아니라 이름표(a)를 제거할 뿐이며,

참조가 모두 끊어져야 객체가 실제로 메모리에서 해제됩니다.

예시 코드

import gc

class Node:
    def __init__(self):
        self.ref = None

a = Node()
b = Node()
a.ref = b
b.ref = a  # 순환 참조 발생

del a
del b  # 이름표 제거, 하지만 두 객체는 여전히 서로를 참조 중

print(gc.collect())  # 가비지 컬렉션 강제 실행 → 순환 참조된 객체 해제

핵심 요약

구분 설명
del a 변수 이름만 제거 (객체는 남음)
참조 카운팅 참조가 0이면 즉시 메모리 해제
순환 참조 참조 카운팅으로는 해제 불가
GC 순환 참조를 자동으로 탐지·해제 (세대별 관리)
gc.collect() 수동으로 즉시 GC 실행 가능 (일반적으론 불필요)

contextmanager 개념

1. 기본 개념

@contextmanager는 파이썬 표준 라이브러리 contextlib 모듈이 제공하는 데코레이터야.

이걸 쓰면 with 구문에서 쓸 수 있는 Context Manager를 훨씬 간단하게 작성할 수 있어.

보통 with 구문을 쓰려면 클래스에서 __enter__ / __exit__를 직접 구현해야 하는데,

@contextmanager를 쓰면 제너레이터 함수(yield)로 간단히 만들 수 있다.

2. 예시 – 파일 열고 닫기

클래스로 만들면:

class MyFile:
    def __init__(self, path):
        self.path = path
    def __enter__(self):
        self.f = open(self.path, "w")
        return self.f
    def __exit__(self, exc_type, exc_val, exc_tb):
        self.f.close()

with MyFile("test.txt") as f:
    f.write("hello")

→ 귀찮음 😅

같은 걸 @contextmanager로 만들면:

from contextlib import contextmanager

@contextmanager
def my_file(path):
    f = open(path, "w")
    try:
        yield f   # with 블록 안에서 사용할 값
    finally:
        f.close()  # with 블록 끝나면 실행됨

with my_file("test.txt") as f:
    f.write("hello")

→ 훨씬 간단하지?

3. 동작 원리

  • yield 앞 부분 → __enter__ 역할
  • yield 반환값 → as 변수에 바인딩
  • yield 뒤 부분 → __exit__ 역할 (cleanup)

즉, @contextmanager는 함수 하나를 Context Manager 프로토콜로 변환해 주는 데코레이터라고 보면 돼.

4. 예외 처리까지

from contextlib import contextmanager

@contextmanager
def db_conn():
    conn = connect_db()
    try:
        yield conn
    except Exception:
        conn.rollback()
        raise
    finally:
        conn.close()

→ with db_conn() as conn: 구문 안에서 예외가 나도 cleanup(rollback / close)이 보장됨.

✅ 정리

  • @contextmanager는 __enter__, __exit__ 구현 대신 yield 기반 함수로 Context Manager를 쉽게 만드는 방법
  • yield 전 → 자원 획득 (__enter__)
  • yield 값 → with ... as 변수로 전달
  • yield 후 → 자원 해제 (__exit__)
  • 주로 파일, DB, 락(lock) 같은 획득/해제가 필요한 자원에 유용

👉 혹시 내가 @contextmanager vs Depends + yield (FastAPI에서 자원 해제 자동 처리) 비교 코드도 만들어줄까?

원문 보존 단위

기본값 있는 파라미터 항상 맨뒤에

그건 아마 기본값 있는 파라미터 규칙이랑 섞여서 기억한 거야.

Python에서 중요한 규칙은 이거다:

  • 기본값 없는 파라미터 뒤에 기본값 있는 파라미터가 올 수는 있어도
  • 기본값 있는 파라미터 뒤에 기본값 없는 파라미터는 못 온다

예:

가능:

def f(a, b=1):
    ...

불가능:

def f(a=1, b):
    ...

그래서 예전 FastAPI 스타일인 이걸 많이 봤을 거야:

def create_cluster(
    payload: ClusterCreate,
    db: Session = Depends(get_db),
):
    ...

여기서 db: Session = Depends(get_db)는 문법상 기본값이 있는 파라미터처럼 취급돼.

그래서 만약 db를 앞에 두고 payload를 뒤에 두면:

def create_cluster(
    db: Session = Depends(get_db),
    payload: ClusterCreate,
):

이건 Python 문법 에러가 난다.

즉 네가 기억하는 “맨뒤에 있어야 한다”는 건 보통 이 경우야:

  • db: Session = Depends(get_db)처럼
  • =를 써서 기본값 형태로 선언했을 때

반면 지금 코드처럼 Annotated를 쓰면:

db: Annotated[Session, Depends(get_db)]

이건 기본값 파라미터가 아니다.

그래서 순서 제약이 훨씬 덜하다.

정리:

  • 옛날 스타일 db: Session = Depends(get_db)에서는 뒤에 두는 게 사실상 필요할 때가 많음
  • 지금 스타일 Annotated[Session, Depends(get_db)]에서는 그 제약이 없음

한 줄로 말하면:
네가 기억하는 “맨뒤여야 한다”는 건 예전 = Depends(...) 문법 때문일 가능성이 크고, Annotated[...] 방식에선 그 제약이 없다.

원문 보존 단위

키워드 인자

이 *는 이 뒤 파라미터들은 키워드 인자로만 받겠다는 뜻이야.

즉 이 함수는:

def create_cluster_record(
    db: Session,
    *,
    name: str,
    api_server: str,
    token: str,
    prometheus_endpoint: str | None = None,
) -> Cluster:

이렇게 생겼으니까

  • db만 위치 인자로 받을 수 있고
  • name, api_server, token, prometheus_endpoint는 반드시 이름을 붙여서 넘겨야 해

가능한 호출:

create_cluster_record(
    db,
    name="minikube",
    api_server="<https://cluster.example.invalid>",
    token="[REDACTED_EXAMPLE]",
)

불가능한 호출:

create_cluster_record(
    db,
    "minikube",
    "<https://cluster.example.invalid>",
    "abc",
)

왜 쓰냐:

  1. 인자 의미를 명확하게 하려고
  • 문자열 인자가 여러 개면 순서 헷갈리기 쉬움
  1. 실수 방지
  • name, api_server, token 자리 바뀌는 걸 막음
  1. 가독성
  • 함수 호출할 때 각 값 의미가 바로 보임

즉 여기서는:

  • db는 보통 이미 명확한 객체니까 위치 인자로 받아도 괜찮고
  • 나머지는 문자열이라 헷갈리기 쉬워서 키워드 전용으로 만든 거야

한 줄로 말하면:
*는 그 뒤의 인자들을 위치 인자가 아니라 키워드 인자로만 받게 만드는 문법이다.

편입 후 검증 메모

  • __init__: 객체 생성을 담당하는 __new__ 뒤에 호출되는 초기화 메서드다. 일반적으로 생성자라고 부르지만 두 역할을 구분한다.
  • 클래스 변수: 인스턴스에서 같은 이름에 할당하면 공유 값을 바꾸는 대신 인스턴스 속성이 새로 생겨 클래스 변수를 가릴 수 있다.
  • 정리 보장: @contextmanager에서는 획득 뒤의 코드를 try, 해제를 finally에 두어 본문 예외에도 반환이 실행되게 한다.
  • GC: CPython의 참조 카운팅과 순환 GC 설명은 구현 세부사항이다. 다른 Python 구현의 메모리 회수 시점까지 동일하다고 일반화하지 않는다.
