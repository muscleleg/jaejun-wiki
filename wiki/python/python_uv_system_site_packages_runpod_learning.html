일회성 RunPod에서 기존 CUDA Package를 재사용해 환경 구성 시간을 줄이기

반납할 때 초기화되는 GPU 환경에서 이미 설치된 CUDA·PyTorch를 다시 설치하지 않으면서, 프로젝트에 필요한 패키지는 별도의 가상환경으로 관리한 이유와 실제 동작 구조를 정리합니다.

← 기술 위키Device·CUDA·병렬 연산
겪은 문제 이미 있던 환경 재설치를 피한 이유 선택한 구성 복사가 아닌 참조 Import 우선순위 실제 출처 확인 파일별 역할 얻은 것과 한계 결론

1. 겪은 문제

GPU를 잠시 대여해 실습하고 Persistent Storage(영구 저장소)를 연결하지 않으면, Pod를 반납할 때 설치한 환경도 함께 사라집니다. 다음 실습에서 새 Pod를 만들면 Python 환경을 다시 준비해야 합니다.

환경을 다시 만드는 것 자체는 감수할 수 있었습니다. 문제는 이미지 안에 CUDA와 PyTorch가 이미 설치되어 있는데도, 프로젝트 가상환경을 만든다는 이유로 큰 패키지를 매번 다시 내려받고 설치하는 일이었습니다.

새 GPU Pod 생성
→ 이미 설치된 CUDA·PyTorch 확인
→ 프로젝트 가상환경 생성
→ PyTorch를 또 설치
→ 다운로드와 설치가 끝날 때까지 유료 GPU 대기
해결하고 싶었던 핵심은 격리를 포기하는 것이 아니라, 이미지에 이미 있는 무거운 패키지는 재사용하고 프로젝트에 부족한 패키지만 추가하는 것이었습니다.

2. GPU 이미지에는 이미 실행 환경이 있었습니다

GPU용 PyTorch 이미지에는 보통 Python, CUDA를 지원하는 PyTorch와 관련 라이브러리가 준비되어 있습니다. 실제로 새 환경에서도 다음 항목을 먼저 확인할 수 있었습니다.

Python 실행 가능
PyTorch Import 가능
CUDA 사용 가능
GPU 이름 확인 가능

따라서 필요한 것은 PyTorch 전체를 새로 설치하는 작업이 아니라, 기존 실행 환경을 활용하면서 프로젝트 전용 패키지를 분리해 관리할 방법이었습니다.

3. 이미 있는 패키지를 다시 설치하지 않으려는 이유

PyTorch 같은 GPU 패키지는 크기가 크고 CUDA 조합에도 영향을 받습니다. 새 Pod를 만들 때마다 같은 패키지를 다시 설치하면 다음 비용이 반복됩니다.

  • 큰 Wheel과 의존성을 다시 내려받는 시간
  • 패키지를 설치하는 동안 발생하는 GPU 대여 비용
  • 이미 동작하는 CUDA·PyTorch 조합을 다시 맞추는 위험

영구 저장소를 계속 유지하면 설치 결과를 보존할 수 있지만, 저장소 자체에도 비용이 듭니다. 짧은 실습을 위해 Pod를 자주 만들고 반납한다면 이미지의 기존 패키지를 재사용하는 편이 더 단순합니다.

4. --system-site-packages를 사용한 가상환경

uv는 가상환경 그 자체가 아니라, 가상환경 생성과 패키지 설치를 빠르게 수행하는 도구입니다. 실제 격리된 환경은 uv venv가 만드는 .venv입니다.

uv venv \
  --python python3 \
  --system-site-packages \
  .venv

이 명령은 프로젝트에 .venv를 만들면서, 가상환경의 Python이 기준 Python의 System Site-packages(시스템 패키지 설치 위치)도 탐색할 수 있게 합니다.

그다음 이미지에 없고 프로젝트에 필요한 패키지만 .venv에 설치합니다.

uv pip install \
  --python .venv/bin/python \
  transformers \
  jaxtyping

여기서 중요한 점은 두 번째 명령의 --python이 반드시 새 가상환경의 Python을 가리켜야 한다는 것입니다. 기준 Python을 다시 지정하면 시스템 환경에 설치하려고 하며, 외부 관리 환경에서는 설치가 거부될 수 있습니다.

5. 시스템 패키지를 복사하는 것이 아니라 보이게 합니다

--system-site-packages는 시스템에 설치된 PyTorch 파일을 .venv 안으로 복사하지 않습니다. 가상환경의 패키지 탐색 범위에 시스템 site-packages를 추가합니다.

프로젝트 .venv
├─ .venv에 직접 설치한 패키지
└─ 기준 Python의 system site-packages도 탐색 가능
   └─ 이미지에 이미 있던 PyTorch 등을 참조

따라서 디스크에 같은 PyTorch가 한 벌 더 생기는 구조가 아닙니다. 가상환경을 활성화한 Python이 필요할 때 기존 시스템 파일을 불러오는 구조입니다.

또한 PyTorch만 선택적으로 보이게 하는 옵션도 아닙니다. 기준 Python의 시스템 site-packages에 있는 모든 패키지가 가상환경의 탐색 대상이 됩니다.

6. 가상환경 패키지가 먼저, 시스템 패키지가 그다음입니다

가상환경에서 import할 때는 일반적으로 .venv에 직접 설치된 패키지를 먼저 찾고, 거기에 없으면 열어 둔 시스템 site-packages에서 찾습니다.

1. .venv의 site-packages 탐색
2. 없으면 system site-packages 탐색

예를 들어 PyTorch는 시스템 환경에서 가져오고, transformers와 jaxtyping은 .venv에 따로 설치할 수 있습니다.

torch        → 시스템 패키지 사용
transformers → .venv 패키지 사용
jaxtyping    → .venv 패키지 사용

같은 이름의 패키지를 .venv에도 설치하면 가상환경 쪽이 먼저 선택될 수 있습니다. 이 방식은 편리하지만, 시스템 패키지와 가상환경 패키지의 버전 호환성은 직접 확인해야 합니다.

7. 어떤 패키지를 어디서 가져왔는지는 어떻게 확인하는가

.venv 안에 “이 패키지는 시스템에서 가져왔고 저 패키지는 가상환경에 있다”는 중앙 목록이 자동으로 만들어지지는 않습니다.

.venv/pyvenv.cfg에는 시스템 패키지를 볼 수 있게 했다는 설정만 기록됩니다.

include-system-site-packages = true

개별 패키지의 실제 출처는 실행 중인 Python이 어느 파일을 불러왔는지 확인해야 합니다. 가장 직접적인 방법은 모듈의 __file__을 출력하는 것입니다.

import torch
import transformers

print(torch.__file__)
print(transformers.__file__)

여러 배포 패키지의 버전과 설치 위치를 함께 보고 싶다면 importlib.metadata를 사용할 수 있습니다.

from importlib.metadata import distribution

for name in ["torch", "transformers", "jaxtyping"]:
    package = distribution(name)
    print(
        name,
        package.version,
        package.locate_file(""),
    )
경로가 .venv 아래에 있음
→ 프로젝트 가상환경에 직접 설치된 패키지

경로가 기준 Python의 site-packages 아래에 있음
→ 시스템 환경에서 참조한 패키지

즉 설정 파일은 시스템 패키지 접근 허용 여부를 알려 주고, 실제로 선택된 패키지는 런타임 경로가 알려 줍니다.

8. pyproject.toml·uv.lock·pyvenv.cfg·런타임 경로의 역할

환경과 관련된 파일들은 서로 다른 질문에 답합니다.

항목답하는 질문역할
pyproject.toml프로젝트가 무엇을 필요로 하는가?직접 의존성과 프로젝트 설정을 선언합니다.
uv.lock의존성을 어떤 버전 조합으로 해결했는가?해결된 버전과 재현 가능한 설치 정보를 기록합니다.
.venv/pyvenv.cfg이 가상환경은 어떤 기준 Python과 정책을 사용하는가?기준 환경과 include-system-site-packages 설정을 기록합니다.
module.__file__·importlib.metadata이번 실행에서 실제로 어느 패키지를 불러왔는가?현재 Import 결과의 실제 파일 위치를 보여 줍니다.

pyproject.toml과 uv.lock은 프로젝트 의존성의 선언과 해결 결과입니다. 그러나 --system-site-packages로 외부에서 보이게 된 모든 시스템 패키지의 실제 Import 출처를 대신 기록하는 목록은 아닙니다.

9. 무엇을 해결했고 어떤 한계가 남는가

이 구성으로 이미 설치된 CUDA 지원 PyTorch를 다시 내려받지 않고, 프로젝트에 필요한 작은 패키지만 가상환경에 추가할 수 있습니다. 새 GPU 환경의 준비 시간이 짧아지고 설치 중 발생하는 대기 비용도 줄어듭니다.

다만 완전히 독립된 가상환경은 아닙니다. 시스템 패키지를 함께 보기 때문에 이미지가 바뀌면 보이는 패키지와 버전도 달라질 수 있습니다. 따라서 환경을 준비한 뒤에는 다음을 검증해야 합니다.

사용 중인 Python 실행 파일
PyTorch·CUDA 사용 가능 여부
GPU 이름
핵심 패키지 버전
핵심 패키지의 실제 Import 경로

재현성을 가장 강하게 고정해야 하는 환경이라면 모든 의존성을 프로젝트 가상환경이나 컨테이너에 직접 고정하는 편이 낫습니다. 이번 선택은 짧게 빌려 쓰는 GPU 실습 환경의 준비 비용을 줄이는 데 목적이 있습니다.

10. 결론

uv venv --system-site-packages는 시스템 패키지를 가상환경으로 복사하지 않습니다. 프로젝트 가상환경을 만들되 기준 Python의 모든 시스템 site-packages도 참조할 수 있게 하고, 가상환경에 직접 설치한 패키지를 우선 사용합니다.

이 방식은 반납할 때 초기화되는 GPU 환경에서 이미 준비된 CUDA·PyTorch를 재사용하고, 부족한 프로젝트 패키지만 별도로 설치하려고 선택했습니다. 어떤 패키지가 실제로 시스템과 가상환경 중 어디에서 로드되었는지는 중앙 목록이 아니라 __file__ 또는 importlib.metadata가 보여 주는 런타임 경로로 확인합니다.
