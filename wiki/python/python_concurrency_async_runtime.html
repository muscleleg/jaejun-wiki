멀티 프로세싱

🏎️ 파이썬 멀티 프로세싱 (Multiprocessing) 총정리

1. 왜 멀티 프로세싱인가? (GIL의 벽)

  • Java: 1개 프로세스 내 멀티 스레드가 여러 코어를 동시에 점유하여 계산 가능.
  • Python: GIL(Global Interpreter Lock) 때문에 한 프로세스 내에서는 스레드가 아무리 많아도 한 번에 딱 하나의 코어에서만 파이썬 바이트코드를 실행할 수 있음.
  • 해결책: 4코어를 다 쓰려면 파이썬 인터프리터 자체를 4개 띄워야 함. 이것이 멀티 프로세싱임.

2. 핵심 컴포넌트: ProcessPoolExecutor

비동기 루프(asyncio)와 멀티 코어(Process)를 연결하는 다리 역할을 합니다.

  • 역할: 자바의 FixedThreadPool과 유사하지만, 스레드가 아닌 독립된 OS 프로세스를 미리 생성해두고 관리함.
  • 작동 방식: 무거운 연산을 프로세스 풀로 던지면(하청), 각 프로세스가 각자의 코어에서 독립적으로 연산 후 결과를 돌려줌.

3. 실전 코드 패턴 (자바 스타일 비유)

import asyncio
from concurrent.futures import ProcessPoolExecutor

# [계산 작업] - static 메서드처럼 독립적이어야 함
def cpu_bound_task(data):
    # 실제 멀티코어에서 돌아갈 무거운 연산 로직
    return sum(i * i for i in range(data))

async def main():
    # 1. 프로세스 풀 생성 (try-with-resources와 동일)
    # max_workers를 지정하지 않으면 논리 코어 개수만큼 프로세스 생성
    with ProcessPoolExecutor() as executor:
        loop = asyncio.get_running_loop()

        # 2. 작업 지시서 리스트 작성 (List Comprehension)
        # loop.run_in_executor가 Future 객체를 즉시 반환함
        tasks = [
            loop.run_in_executor(executor, cpu_bound_task, 10**7)
            for _ in range(4) # 4개 코어에 4개 작업 할당
        ]

        # 3. 모든 프로세스의 결과 취합 (CompletableFuture.allOf().join()과 유사)
        # *tasks는 배열을 가변 인자로 펼쳐주는 '언패킹' 문법
        results = await asyncio.gather(*tasks)
        print(f"작업 완료: {results}")

if __name__ == "__main__":
    # [중요] 윈도우/맥에서 자식 프로세스가 무한 생성되는 것을 방지하는 안전장치
    asyncio.run(main())

5. 노션용 체크리스트 (언제 쓸까?)

  1. 계산 중심(CPU Bound): 이미지 처리, 대량 연산, 머신러닝 모델 추론 등 → 멀티 프로세싱
  2. I/O 중심(I/O Bound): API 호출, DB 쿼리, 파일 읽기/쓰기 → asyncio (싱글 스레드)
  3. 레거시 I/O: 비동기를 지원하지 않는 requests 사용 시 → ThreadPoolExecutor

⚠️ 주의사항 (Interview Point)

  • Pickle(직렬화): 프로세스 간에 데이터를 주고받을 때 파이썬 객체를 바이트로 변환해야 하므로, 너무 거대한 리스트나 객체를 인자로 넘기면 통신 비용 때문에 성능이 떨어질 수 있습니다.
  • Shared Nothing: 한 프로세스에서 전역 변수를 수정해도 다른 프로세스에는 반영되지 않습니다.

비동기의 전염성과 "레거시 동기 코드의 수용

🐍 Python 비동기 실전 가이드 (for Java Developers)

1. 비동기의 전염성 (The Async Contagion)

파이썬의 비동기는 이벤트 루프(Event Loop)라는 단일 엔진 위에서 돌아가는 연극과 같습니다.

  • 원칙: 최하단(I/O 호출)이 async라면, 최상단(Controller)까지 모두 async여야 합니다.
  • 이유: def 컨트롤러는 이벤트 루프가 없는 별도의 워커 스레드에서 실행됩니다. 여기서 async 함수를 쓰려면 일회용 루프(asyncio.run)를 계속 만들어야 하며, 이는 요청이 1,000개면 루프도 1,000개 생기는 재앙을 초래합니다.
  • 자바와의 차이: 자바는 어느 스레드에서든 Future.get()이 가능하지만, 파이썬은 메인 이벤트 루프라는 하나의 흐름을 타야만 자원(DB 커넥션 등) 공유와 고성능 발휘가 가능합니다.

2. 레거시 동기 코드(requests) 처리법

비동기 전용 라이브러리(aiohttp)가 없다면, 동기 라이브러리를 비동기 흐름을 방해하지 않게 감싸야 합니다.

✅ 패턴: run_in_executor를 활용한 외주 주기

이벤트 루프(메인 스레드)가 직접 일을 하지 않고, 별도의 스레드 풀에 일을 던지는 방식입니다.

import asyncio
import requests
from concurrent.futures import ThreadPoolExecutor

# 1. 자바의 커스텀 ExecutorService처럼 별도의 스레드 풀 생성
executor = ThreadPoolExecutor(max_workers=100)

def legacy_blocking_call(url):
    # 이 안에서는 requests 같은 동기 라이브러리를 마음껏 써도 됨
    return requests.get(url).status_code

async def service_layer():
    loop = asyncio.get_running_loop()
    urls = ["https://google.com"] * 100

    # 2. 동기 함수를 스레드 풀에 '외주' 주고 Future 객체 리스트 생성
    # CompletableFuture.supplyAsync(..., executor)와 동일
    tasks = [
        loop.run_in_executor(executor, legacy_blocking_call, url)
        for url in urls
    ]

    # 3. 100개의 결과를 비동기적으로 취합 (루프는 얼지 않음)
    results = await asyncio.gather(*tasks)
    return results

3. 요약 및 주의사항 (Checklist)

🚨 대참사 케이스 (Anti-Patterns)

  1. async def 안에서 requests.get() 호출:
  • 이벤트 루프 자체가 멈춰버립니다. 서버가 한 번에 한 명만 처리하는 구식 서버로 변합니다.
  1. def 컨트롤러 안에서 asyncio.run() 호출:
  • 요청마다 일회용 루프가 생성되어 메모리와 CPU가 폭발합니다. 커넥션 풀링도 불가능해집니다.

✨ 정석 케이스 (Best Practice)

  1. 전 구간 비동기: async def 컨트롤러 -> async def 서비스 -> await aiohttp.get().
  2. 동기 외주: async def 컨트롤러 -> async def 서비스 -> loop.run_in_executor -> requests.get().

📂 [최종] 파이썬 동시성/병렬성 일꾼 관리 (Pool & Loop)

파이썬은 GIL(Global Interpreter Lock)이라는 독특한 제약 때문에, 작업의 종류(I/O인가 계산인가)에 따라 사용하는 '일꾼 수용소(Pool)'를 명확히 구분해야 합니다.

1. 파이썬의 3대 핵심 일꾼 (Comparison Table)

분류 이름 자바 대응 개념 핵심 용도 작동 원리
기본 엔진 이벤트 루프 Single Thread Executor 비동기 I/O (API, DB) 혼자서 수만 개의 예약된 일을 관리함
I/O 하청 스레드 풀 Fixed Thread Pool 레거시 동기 I/O (requests) 스레드를 생성해 대기 시간을 나눠 가짐
계산 하청 프로세스 풀 Fork/Join Pool (Parallel) 무거운 계산 (CPU 연산) 프로세스를 생성해 멀티코어 진짜 병렬 연산

2. "동기 작업을 비동기 루프에서 돌리는 원리" (하청과 알림)

비동기를 지원하지 않는 레거시 라이브러리(requests 등)를 쓸 때 사용하는 loop.run_in_executor의 내부 동작 방식입니다.

  • 외주 전달 (Offloading): 이벤트 루프(메인 사장님)는 자신이 직접 일을 하면 전 직원이 멈춰버리므로, 작업을 스레드 풀(외부 업체)에게 던집니다.
  • 영수증 발급 (Future/Promise): 던지자마자 루프는 Future 객체(Java의 CompletableFuture와 유사)를 즉시 반환하고 다음 코드로 넘어갑니다. (Non-blocking)
  • 작업 수행: 스레드 풀의 개별 스레드가 실제 I/O 작업(네트워크 응답 대기 등)을 수행합니다.
  • 완료 통지 (Notification): 작업이 끝나면 스레드 풀은 이벤트 루프에게 "작업 완료! 결과 여기 있어!"라고 신호를 보냅니다.
  • 코루틴 재개 (Resume): 신호를 받은 이벤트 루프는 해당 영수증을 들고 await 하던 지점으로 돌아가 코드를 이어갑니다.

💡 요약: 이벤트 루프는 관리만 하고, 기다리는 일은 스레드 풀이 대신 한 뒤 나중에 루프에게 알려주는 구조입니다.

3. 결정 트리: 어떤 풀을 쓸 것인가?

  1. async/await를 지원하는 비동기 작업인가?
  • YES: 이벤트 루프만 사용 (asyncio)
  1. 기다려야 하는 일(I/O)인데 동기 방식(레거시)인가?
  • YES: 스레드 풀에 하청 (ThreadPoolExecutor)
  1. 기다리는 게 아니라 계산(CPU)이 많은 일인가?
  • YES: 프로세스 풀에 하청 (ProcessPoolExecutor) → GIL을 우회하여 멀티코어 100% 활용

4. 실전 코드 패턴 (복습용)

🅰️ [패턴 1] 레거시 I/O 래핑 (ThreadPool)

requests처럼 await가 안 되는 함수가 루프를 멈추지 않게 하기 위해 사용합니다.

import asyncio
from concurrent.futures import ThreadPoolExecutor
import requests

# 1. 스레드 풀 생성 (보조 일꾼)
io_executor = ThreadPoolExecutor(max_workers=10)

async def service_layer_io():
    loop = asyncio.get_running_loop()

    # loop.run_in_executor를 통해 외주를 주고 결과를 비동기로 기다림
    # 루프는 이 동안 다른 웹 요청을 처리할 수 있음
    result = await loop.run_in_executor(io_executor, requests.get, "https://api.com")

    return result.status_code

🅱️ [패턴 2] 무거운 연산 병렬화 (ProcessPool)

파이썬의 GIL을 뚫고 여러 코어에서 동시에 연산을 돌리기 위해 사용합니다.

import asyncio
from concurrent.futures import ProcessPoolExecutor

# 1. 프로세스 풀 생성 (별도 주방 - 멀티코어 활용)
cpu_executor = ProcessPoolExecutor(max_workers=4)

def heavy_calculation(n):
    """실제 CPU 코어를 100% 점유하는 무거운 연산 (동기 함수)"""
    return sum(i * i for i in range(n))

async def service_layer_cpu():
    loop = asyncio.get_running_loop()

    # 프로세스 풀로 던지면 각 코어가 독립적으로 연산을 수행함
    # 결과값은 직렬화(Pickle)되어 루프로 전달됨
    result = await loop.run_in_executor(cpu_executor, heavy_calculation, 10**8)

    return result

5. 자바 개발자를 위한 최종 팁 (Final Insight)

  • Java: ExecutorService가 모든 병렬/동시성 처리를 다 하지만, Python은 분업 시스템입니다.
  • 핵심: 메인 사장님(이벤트 루프)이 직접 무거운 일을 하거나 대기하게 만들면 안 됩니다. (Blocking 방지)
  • 주의: 프로세스 풀은 메모리를 공유하지 않으므로, 인자로 너무 큰 데이터를 넘기면 직렬화(Pickle) 비용 때문에 성능이 떨어질 수 있습니다.

코루틴

🌀 파이썬 코루틴 (Coroutine) 핵심 정리

1. 코루틴이란?

일반적인 함수(Subroutine)는 호출되면 끝날 때까지 실행되지만, 코루틴은 실행 도중 멈췄다가(Suspend) 나중에 중단된 지점부터 다시 시작(Resume)할 수 있는 특별한 형태의 함수입니다.

  • 키워드: async def (정의), await (중단 및 제어권 양보)
  • 철학: "내가 I/O 작업을 하느라 기다려야 할 때, 가만히 서서 스레드를 점유하지 않고 인터프리터에게 제어권을 돌려줄게. 딴 일 하다가 결과 나오면 날 다시 불러줘."

2. 코루틴의 동작 원리

코루틴은 이벤트 루프(Event Loop)라는 관리자 위에서 돌아갑니다.

  1. 호출: async def 함수를 호출하면 즉시 실행되지 않고 코루틴 객체가 생성됩니다.
  2. 등록: 이 객체를 이벤트 루프에 등록(Task 생성)합니다.
  3. 실행 및 중단: 실행 중 await를 만나면 코루틴은 현재 상태(로컬 변수 등)를 보존하고 루프에 제어권을 넘깁니다.
  4. 재개: 기다리던 작업(네트워크 응답 등)이 완료되면, 루프는 저장된 상태를 복구하여 중단된 지점 바로 다음부터 실행을 이어갑니다.

3. 왜 사용하는가? (장점)

  • 극강의 가성비: 스레드는 생성 시 약 1MB의 메모리를 사용하지만, 코루틴은 단순 객체라 수 KB면 충분합니다. (수만 개를 동시에 띄워도 메모리가 버팁니다.)
  • 비동기의 동기화: 콜백 방식(callback hell) 대신, 일반적인 순차 코드처럼 작성할 수 있어 가독성이 압도적입니다.
  • 컨텍스트 스위칭 비용 감소: OS가 개입하는 스레드 전환보다 애플리케이션 계층에서의 제어권 전환이 훨씬 빠릅니다.

4. 주의사항: "Blocking을 피하라"

코루틴은 단일 스레드에서 돌아가는 협력적(Cooperative) 모델입니다.

  • 잘못된 예: time.sleep(1) — 스레드 자체를 멈춰버려 이벤트 루프 전체가 마비됩니다.
  • 옳은 예: await asyncio.sleep(1) — 루프에게 제어권을 넘기고 1초 뒤에 다시 불러달라고 예약합니다.

📝 코루틴 요약 코드

import asyncio

async def fetch_data():
    print("데이터 요청 시작...")
    # await를 만나는 순간 제어권을 루프에 반납 (Non-blocking)
    await asyncio.sleep(2)
    print("데이터 수신 완료!")
    return {"data": 123}

async def main():
    # 코루틴 호출 -> 루프가 관리하도록 Task로 등록
    result = await fetch_data()
    print(f"결과 처리: {result}")

asyncio.run(main())

🐍 Python ContextVars: 비동기 데이터 격리 가이드

1. 왜 사용하는가?

비동기 환경은 싱글 스레드 내에서 수만 개의 코루틴(Task)이 번갈아가며 실행됩니다.

  • 일반적인 전역 변수나 스레드 변수를 쓰면 A 고객의 데이터가 B 고객에게 유출되는 재앙이 발생합니다.
  • ContextVar는 각 코루틴(태스크)마다 독립된 사물함을 제공하여 데이터를 안전하게 격리합니다.

2. 핵심 동작: "영수증(Token)과 복구(Reset)"

set()은 단순히 값을 바꾸는 것이 아니라, 기존 값을 영수증에 적어두고 새 값을 덮어쓰는 행위입니다. reset()은 그 영수증을 제출하고 이전 상태로 되돌리는(Undo) 핵심 안전장치입니다.

3. 실전 코드 (주석 및 예상 결과 포함)

import asyncio
import contextvars

# [사물함 생성] 기본값은 "GUEST"로 설정
user_role_ctx = contextvars.ContextVar("user_role", default="GUEST")

async def child_service():
    """하위 서비스: 특정 작업을 위해 임시로 권한을 상승함"""

    # [자식 진입 시점] 부모가 설정한 값을 그대로 복사해서 가져옴
    # 결과: "USER"
    print(f"   [Child] 진입 시점 값: {user_role_ctx.get()}")

    # [set 호출] "ADMIN_TEMPORARY"로 덮어쓰면서, "이전엔 USER였음"이 적힌 영수증(token)을 받음
    token = user_role_ctx.set("ADMIN_TEMPORARY")

    # 결과: "ADMIN_TEMPORARY" (현재 이 코루틴의 상태)
    print(f"   [Child] 임시 권한 상승: {user_role_ctx.get()}")

    await asyncio.sleep(0.1)

    # [reset 호출] 영수증을 제출해서 다시 "USER" 상태로 타임머신 탑승
    # ★ 만약 여기서 reset을 안 하면? 부모 서비스로 돌아갔을 때 부모도 ADMIN 권한이 되어버림 (망함)
    user_role_ctx.reset(token)

    # 결과: "USER" (원상복구 완료)
    print(f"   [Child] 권한 복구 완료: {user_role_ctx.get()}")

async def parent_service():
    """상위 서비스: 사용자 권한으로 메인 로직 수행"""

    # [부모 값 설정] 사물함에 "USER"를 집어넣음
    user_role_ctx.set("USER")

    # [질문하신 지점] set 직후이므로 당연히 USER가 나옴
    # 결과: "USER"
    print(f"👨 [Parent] 자식 호출 전 권한: {user_role_ctx.get()}")

    # [자식 호출] 제어권이 자식에게 넘어감
    await child_service()

    # [복구 확인] 자식이 내부에서 무슨 짓을 했든 reset 덕분에 부모는 안전함
    # 결과: "USER" (무결성 유지)
    print(f"👨 [Parent] 자식 호출 후 권한: {user_role_ctx.get()}")

async def main():
    # [시작 전] 아무것도 설정 안 했으므로 기본값이 나옴
    # 결과: "GUEST"
    print(f"🏁 시작 전 기본값: {user_role_ctx.get()}")

    await parent_service()

# 이벤트 루프 시작
asyncio.run(main())`

🏁 시작 전 기본값: GUEST
👨 [Parent] 자식 호출 전 권한: USER
   [Child] 진입 시점 값: USER
   [Child] 임시 권한 상승: ADMIN_TEMPORARY
   [Child] 권한 복구 완료: USER
👨 [Parent] 자식 호출 후 권한: USER

5. reset(token)을 안 하면 벌어지는 대참사 (망하는 이유)

  1. 권한 상승 공격: 하위 서비스에서 올린 ADMIN 권한이 부모 서비스까지 전염되어, 일반 유저가 관리자 기능을 실행할 수 있게 됨 (보안 뚫림).
  2. 데이터 오염: 로그 파일에 A 사용자의 작업인데 B 사용자의 ID가 찍혀서 장애 추적이 불가능해짐 (디버깅 지옥).
  3. DB 트랜잭션 오류: 자식이 쓰던 DB 세션이 부모에게 남아서, 닫힌 세션에 쿼리를 날리다 서버가 뻗음 (서비스 장애).

📝 결론

"파이썬 비동기 환경에서 set()은 빚을 지는 것이고, reset()은 그 빚을 갚는 것이다." 자식이 부모의 사물함 상태를 잠시 빌려 썼다면, 반드시 나갈 때 원래대로 정리해두어야 전체 시스템이 안전합니다.

파이썬 GIL (Global Interpreter Lock)

1. 한 줄 정의

파이썬(CPython) 인터프리터가 한 번에 단 하나의 스레드만 파이썬 바이트코드를 실행할 수 있도록 제어하는 전역 실행 권한 자물쇠입니다.

2. 왜 존재하나요? (Why?)

  • 참조 횟수(Reference Counting)의 안전성: 파이썬의 메모리 관리 방식은 객체 참조 횟수를 계산하는데, 여러 스레드가 동시에 이 카운트를 건드리면 데이터가 깨질 수 있습니다. 이를 방지하기 위해 인터프리터 수준에서 실행 권한을 한 명에게만 줍니다.
  • 설계의 단순함: 멀티스레드 환경에서 복잡한 자물쇠 설계 없이도 안정적으로 엔진을 구동하기 위해 채택되었습니다.

3. 왜 "강제 교체"와 "수동 락(Lock)"이 필요한가?

GIL이 있다고 해서 데이터가 무조건 안전한 것은 아닙니다. 바로 이 지점에서 개발자의 수동 락이 필요합니다.

  • 시분할 및 I/O 교체: 파이썬은 일정 시간(약 15ms)이 지나거나, DB 조회/네트워크 요청 같은 I/O 작업이 시작되면 현재 스레드의 GIL을 강제로 회수하여 다른 스레드에게 줍니다.
  • 데이터 오염의 위험: * 스레드 A가 DB 값을 기다리며 쉬는 동안 GIL을 반납하면, 권한을 새로 얻은 스레드 B가 깨어납니다.
  • 이때 스레드 B가 스레드 A가 사용 중이던 메모리(변수 등)를 수정해버릴 수 있습니다. (데이터 오염)
  • 수동 락(threading.Lock)의 역할: * 따라서 개발자는 "내가 DB에 다녀와서 이 데이터를 최종 처리할 때까지는 아무도 이 구간을 건드리지 마!"라고 직접 자물쇠를 걸어 데이터의 일관성(Idempotency)을 지켜야 합니다.

4. 핵심 요약 (면접용)

  • GIL: "파이썬 엔진(인터프리터) 사용권"을 관리 (자동)
  • User Lock: "비즈니스 데이터의 상태"를 관리 (수동)
  • 결론: GIL이 있어도 I/O 대기나 시분할로 인해 스레드는 언제든 교체될 수 있으므로, 공유 자원을 안전하게 보호하려면 반드시 수동 락을 병행해야 합니다.

asyncio.create_task()

1. asyncio 핵심 개념

Task란?

  • 이벤트 루프에 등록된 독립적으로 실행되는 코루틴
  • Python asyncio는 싱글 스레드 + 이벤트 루프 구조

create_task() vs await

실행 시작? 다음 줄로 넘어감?
asyncio.create_task() ✅ 바로 시작 ✅ 즉시 넘어감
await task (이미 돌고 있음) ❌ 끝날 때까지 기다림
  • create_task() = 실행 시작 + 즉시 다음 줄로
  • await task = 끝날 때까지 기다려서 결과값 받기

샘플 코드

import asyncio

async def slow_job(name, seconds):
    print(f"[{name}] 시작")
    await asyncio.sleep(seconds)
    print(f"[{name}] 완료")
    return f"{name} 결과"

async def main():
    # 순차 실행: 총 3초
    await slow_job("A", 2)   # 2초 기다림
    await slow_job("B", 1)   # 그 다음 1초 기다림

    # 동시 실행: 총 2초
    task_a = asyncio.create_task(slow_job("A", 2))  # 등록+실행, 즉시 반환
    task_b = asyncio.create_task(slow_job("B", 1))  # 등록+실행, 즉시 반환
    result_a = await task_a  # A 끝날 때까지 기다림 (그 사이 B도 돌아감)
    result_b = await task_b  # B는 이미 끝나있어서 즉시 반환
    print(result_a, result_b)

asyncio.run(main())

GIL

🐍 파이썬의 심장: GIL과 메모리 관리

1. 파이썬은 어떻게 메모리를 관리하나? (Reference Counting)

파이썬은 모든 객체에 "나를 몇 명이 사용 중인가?"를 나타내는 숫자를 붙여놓습니다. 이를 참조 횟수(Reference Counting)라고 합니다.

  • 원리: 누군가 나를 사용하면 +1, 사용을 끝내면 1.
  • 삭제: 이 숫자가 0이 되는 순간, "아, 이제 아무도 나를 안 쓰는구나"라고 판단하고 즉시 메모리에서 지워버립니다.

2. 왜 GIL(Global Interpreter Lock)이 필요한가?

파이썬 인터프리터(실행기) 내부에서 이 '숫자 세기'가 꼬이면 대재앙이 일어납니다.

  • 문제 상황 (Race Condition): 스레드 2개가 동시에 어떤 객체의 숫자를 올리려고 하면, 실제로는 2가 올라가야 하는데 1만 올라가는 상황이 발생할 수 있습니다.
  • 결과: 숫자가 실제보다 낮아지면 사용 중인 객체가 갑자기 삭제되어 프로그램이 터지고, 숫자가 실제보다 높게 남으면 영원히 삭제되지 않는 메모리 누수가 발생합니다.
  • 해결책 (GIL): 객체마다 일일이 자물쇠를 채우면 너무 느려지니까, 아예 파이썬 실행기 전체에 큰 자물쇠(GIL)를 하나만 걸었습니다. "한 번에 딱 한 놈(스레드)만 들어와서 숫자도 고치고 코드도 실행해!"라고 규칙을 정한 것이죠.

3. 멀티스레드와 '마이크' 권한

파이썬에서 스레드를 여러 개 만든다는 것은, 무대 위에 여러 명의 가수를 세우는 것과 같습니다. 하지만 마이크(GIL 점유권)는 단 하나뿐입니다.

  • 실행: 마이크를 잡은 스레드만 노래(코드 실행)를 할 수 있습니다.
  • 교체: 파이썬은 한 스레드가 마이크를 독점하지 못하게 강제로 뺏어서 다음 스레드에게 넘겨줍니다.
  • 주의사항: 마이크를 뺏기는 시점은 무작위입니다. 데이터를 읽기만 하고 아직 수정해서 저장하기 전인데 마이크를 뺏기면, 다음 스레드가 들어와서 이전 데이터를 건드려 로직이 꼬일 수 있습니다(Race Condition).

4. 그래서 개발자는 무엇을 해야 하나? (Lock)

GIL은 파이썬 엔진이 고장 나지 않게 숫자를 잘 세도록 도와줄 뿐, 여러분이 만든 데이터가 꼬이는 것까지 막아주지는 않습니다.

  • 수동 Lock: 여러 스레드가 동시에 접근하면 안 되는 중요한 데이터(예: 잔액, 재고)가 있다면, 반드시 threading.Lock()을 사용하여 직접 보호해야 합니다. 파이썬은 이걸 자동으로 해주지 않습니다.

5. 요약: CPU 작업 vs I/O 작업

  • CPU 작업 (계산만 주구장창): 스레드를 늘려봤자 서로 마이크 뺏기 싸움만 하느라 더 느려집니다. 이때는 Multiprocessing을 써서 실행기(인터프리터) 자체를 여러 개 띄워야 합니다.
  • I/O 작업 (파일 읽기, 네트워크 대기): 대기 시간에는 마이크를 알아서 반납하므로, 스레드를 여러 개 쓰는 게 아주 효율적입니다.

java의 CompletableFuture를 대체할 수 있는 방법

Java CompletableFuture vs Python asyncio

1. 성능 모델의 차이: Parallelism vs Concurrency

CompletableFuture를 쓴다는 것은 대개 "다른 코어(스레드)에 일을 시키겠다"는 의도입니다. 하지만 파이썬은 "기다리는 시간을 쪼개 쓰겠다"는 전략을 취합니다.

  • Java (CompletableFuture):
  • 방식: 멀티 코어 기반의 병렬(Parallel) 처리.
  • 강점: I/O를 기다리는 동안에도 다른 스레드가 CPU 연산을 동시에 수행할 수 있음.
  • Python (asyncio):
  • 방식: 싱글 코어 기반의 동시(Concurrent) 처리.
  • 강점: 코어는 하나만 쓰지만, I/O 대기(DB, API)가 발생할 때 제어권을 아주 빠르게 전환하여 수만 개의 연결을 혼자서 관리함.

2. 왜 asyncio가 자바의 멀티스레딩을 대체하는가? (자원 효율성)

자바 개발자들이 가장 놀라는 점은 "스레드 1만 개 생성 vs 코루틴 1만 개 생성"의 결과입니다.

  • 메모리 효율:
  • Java 스레드: 스레드당 최소 0.5~1MB의 스택 메모리를 점유합니다. 스레드가 1만 개면 메모리만 수십 GB가 필요합니다.
  • Python 코루틴 (asyncio): 단순한 객체에 불과하여 수 KB 수준입니다. 싱글 스레드 위에서 수만 개의 비동기 작업을 띄워도 메모리 부담이 거의 없습니다.
  • 컨텍스트 스위칭 비용:
  • Java: OS 수준의 스레드 스위칭은 CPU 비용이 큽니다.
  • Python: 애플리케이션 수준(이벤트 루프)의 점프이므로 훨씬 가볍습니다.

결론: "계산"이 목적이 아니라 "엄청나게 많은 네트워크 연결(C10K 문제)"이 목적이라면 파이썬의 asyncio가 자바의 일반적인 멀티스레딩 방식보다 훨씬 경제적입니다.

3. 코드 구현의 직관성 (Explicit vs Implicit)

CompletableFuture의 콜백 지옥(.thenApply().thenCompose()...)에 지친 개발자에게 파이썬의 async/await는 축복과 같습니다.

  • Java: 비동기 흐름을 메서드 체이닝으로 제어해야 하므로 로직이 복잡해지면 가독성이 떨어집니다.
  • Python: await 키워드를 사용하면 비동기 코드를 동기 코드와 거의 똑같은 구조로 짤 수 있습니다. 어디서 멈추고 어디서 재개되는지 눈에 명확히 보입니다.

✔ 프로그램 vs 프로세스

예:

python app.py

→ Python 인터프리터 프로세스 하나 생성

프로세스
 ├─ 스레드 A
 ├─ 스레드 B
 └─ 스레드 C
  • 프로세스 = 자원 단위 (메모리, 파일, 소켓 등)
  • 스레드 = 실행 단위 (코드를 실제로 실행하는 흐름)

2️⃣ 스레드는 CPU 코어와 같은 개념인가?

아니요.

여기서 혼동이 많이 생깁니다.

🔹 하이퍼스레딩의 “스레드”

  • 하드웨어 실행 슬롯
  • CPU 코어 내부 구조

🔹 OS 스레드 (프로그래밍에서 말하는 스레드)

  • 운영체제가 관리하는 실행 흐름
  • CPU 코어에 번갈아 배치됨

즉,

CPU 코어 8개
OS 스레드 100개

가능합니다.

동시에 실행되는 스레드는 최대 코어 수만큼입니다.

CPython에는 GIL (Global Interpreter Lock) 이 있습니다.

의미:

하나의 프로세스 안에서는

4️⃣ ThreadPool이란?

ThreadPool은:

하나의 프로세스 안에서 여러 스레드를 만들어

작업을 분산 실행하는 구조

특징

  • 같은 메모리 공간 공유
  • 같은 GIL 공유
  • CPU 병렬 X (CPython 기준)
  • 오버헤드 적음

그럼 ThreadPool은 왜 쓰는가?

CPU 병렬용이 아니라,

async 환경에서 블로킹 I/O를 격리하기 위한 완충 장치

예:

await asyncio.to_thread(blocking_function)

이 경우:

  • 이벤트 루프는 멈추지 않음
  • 블로킹 함수는 별도 스레드에서 실행
  • 완료되면 Future를 통해 이벤트 루프로 복귀

5️⃣ ProcessPool이란?

ProcessPool은:

여러 개의 프로세스를 만들어

CPU 작업을 병렬 실행하는 구조

특징

  • 메모리 완전 분리
  • 프로세스마다 GIL 독립
  • 진짜 멀티코어 병렬 가능
  • 오버헤드 큼
  • 데이터 직렬화 필요

6️⃣ 이벤트 루프로 복귀 구조는 동일한가?

이벤트 루프로 복귀하는 기본 구조는 동일하다.

async 코드에서:

result = await loop.run_in_executor(pool, func, arg)

흐름은 ThreadPool과 ProcessPool 모두 같습니다.

내부 흐름

  1. 이벤트 루프가 executor에 작업 위임
  2. 현재 코루틴 일시 정지
  3. 이벤트 루프는 다른 작업 처리
  4. executor에서 작업 완료
  5. Future 완료 상태 변경
  6. 이벤트 루프가 감지
  7. 멈췄던 코루틴 재개

✔ 완료 후 이벤트 루프로 돌아오는 구조는 동일

❌ 하지만 실행 특성은 완전히 다름

구분 ThreadPool ProcessPool

ThreadPool

  • async = I/O 동시성 모델
  • ThreadPool = 블로킹 완충

이 셋은 역할이 다릅니다.

Async 전파

1️⃣ 우리가 확실히 정리한 핵심 문장

await가 존재하는 호출 체인에서는

그 체인 위쪽 함수들이 async로 전파된다.

이게 비동기 설계의 가장 정확한 규칙이다.

2️⃣ 왜 async가 전파되는가?

이건 “문법” 문제가 아니라 호출 규약(call contract) 문제다.

예를 보자.

async def child():
    await something()

child()는 코루틴 함수다.

즉, 호출하면 바로 실행되는 게 아니라 코루틴 객체를 반환한다.

이걸 동기 함수에서 호출하면:

def parent():
    child()   # ❌ 실행되지 않음

child()는 코루틴 객체만 반환하고 실제로 실행되지 않는다.

코루틴을 실행하려면 반드시 await가 필요하다.

따라서 부모는 이렇게 되어야 한다.

async def parent():
    await child()

여기서 핵심은 이것이다:

코루틴을 기다리려면, 기다릴 수 있는 문맥(async)이 필요하다.

그래서 async가 “전파되는 것처럼” 보이는 것이다.

3️⃣ 정확한 표현

❌ async가 하나 있으면 전부 async

✔ await를 직접 호출하는 경로만 async

비동기는 무조건 확장되는 것이 아니라,

await가 호출 규약을 강제하기 때문에 연결되는 것이다.

4️⃣ 전파는 어디서 멈추는가?

전파는 await 경계에서 멈춘다.

async def service():
    await repo()

def calculate():
    return 10
  • service()는 async
  • calculate()는 sync 유지 가능

계산 함수까지 async로 만들 필요는 없다.

5️⃣ 실무 기준 정리

async가 필요한 경우 (I/O 바운드)

  • DB 접근
  • HTTP 요청
  • 파일 I/O
  • 외부 API 호출
  • 네트워크 통신

async가 필요 없는 경우 (CPU/순수 로직)

  • 계산
  • 조건 분기
  • 데이터 변환
  • 문자열 처리
  • DTO 변환
  • 유효성 체크 (I/O 없는 경우)

6️⃣ 설계 판단 기준 (실무용 체크리스트)

비동기를 설계할 때는 이렇게 판단한다:

  1. 이 함수는 I/O가 있는가?
  2. 그 I/O를 await 하는가?
  3. 그렇다면 async로 선언한다.
  4. 아니라면 sync로 둔다.

이 순서로 판단하면 과도한 async 확장을 막을 수 있다.

7️⃣ 가장 중요한 통찰

async는 전파되는 게 아니라

await가 호출 규약을 강제하기 때문에 연결되는 것이다.

이걸 이해하면:

  • 무작정 async 확장하지 않게 된다.
  • 비동기 경계를 명확히 나눌 수 있다.
  • 레이어 설계가 단순해진다.
  • 테스트 구조도 깔끔해진다.

1️⃣ ProcessPool은 실제로 무엇을 만드는가?

ProcessPool은 개념적인 “논리적 풀”이 아닙니다.

실제 OS 레벨 프로세스를 생성합니다.

예:

from concurrent.futures import ProcessPoolExecutor

pool = ProcessPoolExecutor(max_workers=4)

이 코드가 실행되면 내부적으로:

  • 메인 프로세스 1개
  • 워커 프로세스 4개

총 5개의 진짜 OS 프로세스가 생성됩니다.

2️⃣ OS 레벨에서 실제로 보이는가?

워커는 OS 프로세스 목록에서 각각 별도의 프로세스로 보인다.

Linux 기준:

ps -ef | grep python

또는

top

보면 대략 이런 구조가 나타납니다:

PID   CMD
1001  python app.py    ← 메인 프로세스
1002  python app.py    ← 워커 프로세스
1003  python app.py
1004  python app.py
1005  python app.py

PID가 다르면 완전히 다른 프로세스입니다.

3️⃣ 체감용 샘플 코드 – PID 확인

from concurrent.futures import ProcessPoolExecutor
import asyncio
import os

def cpu_heavy(n):
    print(f"[Worker PID] {os.getpid()}")
    total = 0
    for i in range(n):
        total += i
    return total

async def main():
    print(f"[Main PID] {os.getpid()}")
    loop = asyncio.get_running_loop()

    with ProcessPoolExecutor(max_workers=2) as pool:
        result1 = await loop.run_in_executor(pool, cpu_heavy, 10_000_000)
        result2 = await loop.run_in_executor(pool, cpu_heavy, 10_000_000)

    print(result1, result2)

asyncio.run(main())

실행 결과 예시:

[Main PID] 1001
[Worker PID] 1002
[Worker PID] 1003

👉 메인과 다른 PID가 찍히면

진짜 별도 프로세스에서 실행된 것입니다.

4️⃣ 병렬 실행 확인 코드

from concurrent.futures import ProcessPoolExecutor
import asyncio
import time
import os

def cpu_task(seconds):
    print(f"Start PID {os.getpid()}")
    time.sleep(seconds)
    print(f"End PID {os.getpid()}")
    return seconds

async def main():
    loop = asyncio.get_running_loop()

    with ProcessPoolExecutor(max_workers=2) as pool:
        tasks = [
            loop.run_in_executor(pool, cpu_task, 3),
            loop.run_in_executor(pool, cpu_task, 3),
        ]

        results = await asyncio.gather(*tasks)

    print(results)

asyncio.run(main())
  • 3초짜리 작업 2개
  • max_workers=2
  • 총 실행 시간 약 3초 → 진짜 병렬 실행

5️⃣ ProcessPool은 언제 생성되는가?

🔹 방식 ① with 블록 안에서 생성

with ProcessPoolExecutor(max_workers=2) as pool:
    ...

이 블록이 실행될 때마다 새로운 ProcessPool이 생성됩니다.

→ 요청마다 실행되면 매우 비효율

→ 프로세스 폭증 가능

🔹 방식 ② 전역 생성 (실무 권장)

pool = ProcessPoolExecutor(max_workers=4)
  • 모듈 로딩 시 1회 생성
  • 이후 재사용
  • 워커 유지

이게 안정적인 패턴입니다.

6️⃣ lazy 생성이란 무엇인가?

lazy 생성은:

풀 객체는 만들어졌지만

실제 워커 프로세스는 첫 작업이 들어올 때 생성되는 방식

환경에 따라:

  • 생성 시점에 워커 생성 (eager)
  • 첫 작업 제출 시 생성 (lazy)

하지만 실무에서는 이 차이는 거의 중요하지 않습니다.

진짜 중요한 건:

풀을 요청마다 만들지 않는 것.

7️⃣ 코드 보고 생성 방식 판단 기준

❌ 나쁜 패턴 (요청마다 생성)

@app.get("/compute")
async def compute():
    pool = ProcessPoolExecutor(max_workers=4)

요청 100개 → 풀 100개 → 프로세스 폭증

✅ 정상 패턴 (전역 재사용)

pool = ProcessPoolExecutor(max_workers=4)

@app.get("/compute")
async def compute():

→ 안정적

8️⃣ 결과는 어떻게 메인 프로세스로 돌아오는가?

프로세스는 메모리를 공유하지 않습니다.

그래서 내부적으로:

  1. 함수 + 인자를 pickle로 직렬화
  2. 워커 프로세스로 전달
  3. 워커 실행
  4. 결과를 pickle로 직렬화
  5. 메인 프로세스로 반환
  6. Future 완료
  7. 이벤트 루프가 감지 → await 재개

9️⃣ ProcessPool의 현실 제약 (중요)

1) 왜 DB 세션/소켓은 전달이 안 되나?

  • 프로세스는 메모리 완전 분리
  • DB 세션, 소켓은 OS 자원을 붙잡는 “핸들” 객체
  • 다른 프로세스가 그대로 이어받아 쓸 수 없음

비유:

  • DB 세션 = 현재 열려 있는 전화 통화
  • 소켓 = 현재 연결된 네트워크 선
  • 그걸 “복사해서 다른 프로세스에서 이어서 써라”는 불가능

✔ 워커에서 DB 작업이 필요하면

→ 워커 프로세스가 새로 세션을 만들어야 함

2) pickle 가능한 데이터만 가능

프로세스 간 전달은 직렬화 필요.

가능:

  • int, float, str
  • list, dict
  • 단순 클래스

불가능:

  • DB session
  • 소켓
  • 파일 핸들
  • threading.Lock
  • 일부 C 확장 객체

3) 직렬화 비용

  • 작은 dict → 거의 무시
  • 10MB JSON → 꽤 무거움
  • 500MB numpy → 매우 느림

“병렬이라 빨라질 것”이라 생각했는데

데이터 옮기느라 느려질 수 있음.

4) IPC 비용

  • 파이프/큐 쓰기
  • 커널 버퍼 복사
  • 메모리 복사
  • 역직렬화

비유:

  • 직렬화 = 포장
  • IPC = 택배 배송
  • 역직렬화 = 개봉

큰 데이터일수록 택배 비용이 커짐.

10️⃣ GIL과의 관계

  • ThreadPool → 같은 프로세스 → GIL 공유 → CPU 병렬 X
  • ProcessPool → 다른 프로세스 → GIL 독립 → CPU 병렬 O

즉:

CPU 병렬은 프로세스 레벨 문제

11️⃣ 그런데 왜 실무에서 ProcessPool을 잘 안 쓰는가?

이유:

  • 직렬화 비용
  • IPC 비용
  • 코드 복잡성
  • API 서버가 CPU 책임까지 떠안음

그래서 보통은:

FastAPI (I/O 중심)
   ↓
작업 큐 (Redis/Kafka)
   ↓
Worker 서버 (CPU 전용)

12️⃣ 더 나은 방식: uvicorn workers

uvicorn app:app --workers 4

구조:

OS
 ├─ FastAPI 프로세스 1
 ├─ FastAPI 프로세스 2
 ├─ FastAPI 프로세스 3
 └─ FastAPI 프로세스 4

각 프로세스:

  • 독립 이벤트 루프
  • 독립 GIL
  • 독립 메모리

즉:

서버 자체를 멀티프로세스로 확장

13️⃣ 왜 uvicorn workers가 더 나은가?

✔ 구조 단순

✔ 직렬화 비용 없음

✔ 요청 자체를 프로세스 단위 분산

✔ 확장성 뛰어남

✔ 실무 표준

14️⃣ 최종 비교

방식 목적 권장도
ThreadPool 블로킹 I/O 완충 높음
ProcessPool API 내부 CPU 병렬 제한적
uvicorn workers 서버 레벨 병렬 매우 높음
외부 Worker 서버 CPU 전용 처리 대규모 최상

🔥 최종 통찰

  • async → 동시성 문제
  • ProcessPool → 함수 단위 병렬
  • uvicorn workers → 서버 단위 병렬
  • 외부 워커 서버 → 시스템 단위 병렬

그리고 가장 중요한 것:

lazy냐 eager냐가 아니라

프로세스를 몇 번 생성하느냐가 핵심이다.

여기까지 갈까요?

편입 후 검증 메모

  • GIL의 범위: 원문의 설명은 주로 CPython을 가리킨다. GIL이 있어도 I/O 대기 중이거나 GIL을 해제하는 네이티브 연산에서는 스레드가 유용하며, 모든 Python 구현에 같은 결론을 적용하지 않는다.
  • 코루틴의 비용: 스레드와 코루틴의 메모리를 고정된 1MB·수KB로 단정할 수 없다. 핵심은 OS 스레드보다 사용자 공간 Task가 일반적으로 가볍고, 협력적으로 제어권을 넘긴다는 점이다.
  • create_task: Task 생성은 동시 실행을 예약하지만 완료·예외·취소를 관리해야 한다. 결과가 필요하면 Task 참조를 보관하고 적절히 await한다.
  • 프로세스 풀: 함수와 인자가 직렬화 가능해야 하며, 웹 서버 워커마다 별도 풀이 생기면 총 프로세스와 메모리가 곱해진다. CPU-bound 작업이라는 이유만으로 무제한 워커를 만들지 않는다.
