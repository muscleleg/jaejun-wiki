Django Model·Migration·QuerySet 실행 흐름

Django의 ORM(객체 관계 매핑)을 클래스 문법으로만 보지 않고, Python 선언이 Migration을 거쳐 데이터베이스 스키마가 되고 QuerySet이 SQL로 평가되는 전체 경로로 이해합니다.

Project·AppModelMigration관계ManagerQuerySet조회Admin결론

1. Project와 App은 설정 범위와 기능 경계를 나눈다

Django Project는 전체 사이트의 설정·URL·배포 진입점을 묶고, App은 회원·게시물·예약처럼 재사용 가능한 기능 단위를 묶습니다. App을 만들었다고 자동으로 활성화되는 것은 아니며 INSTALLED_APPS에 등록해야 Model 검색, Migration, Admin 연동 대상이 됩니다.

python manage.py startapp rooms
python manage.py makemigrations
python manage.py migrate
흐름
models.py 선언 → Migration 파일 생성 → Migration 적용 → 데이터베이스 테이블 변경 → Manager·QuerySet으로 조회

2. Model은 Python 클래스이면서 데이터 계약이다

from django.conf import settings
from django.db import models

class TimeStampedModel(models.Model):
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)

    class Meta:
        abstract = True

class Room(TimeStampedModel):
    name = models.CharField(max_length=120)
    owner = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
        related_name="rooms",
    )
    guests = models.ManyToManyField(
        settings.AUTH_USER_MODEL,
        related_name="bookmarked_rooms",
        blank=True,
    )

필드는 단순한 변수 선언이 아닙니다. 자료형, 최대 길이, 빈 값 허용, 기본값, 관계, 삭제 정책을 스키마와 검증 계층에 전달합니다. abstract=True인 추상 Model은 자기 테이블을 만들지 않고 공통 필드를 자식 Model에 제공합니다.

옵션의미구분할 점
null=True데이터베이스에 NULL 허용문자열 필드는 빈 문자열과 NULL이 두 상태가 될 수 있음
blank=TrueForm·Validation에서 빈 입력 허용DB NULL과 같은 의미가 아님
default=...새 객체의 기본값변경 가능한 객체는 callable 사용 검토
on_delete참조 대상 삭제 시 정책관계 데이터 수명 결정

3. Migration은 현재 DB를 보고 추측하는 스크립트가 아니라 변경 이력이다

makemigrations는 현재 Model과 저장된 Migration 상태의 차이를 선언적 작업으로 기록합니다. migrate는 아직 적용되지 않은 작업을 순서대로 실행합니다.

python manage.py makemigrations rooms
python manage.py showmigrations rooms
python manage.py sqlmigrate rooms 0002
python manage.py migrate

운영 데이터가 있는 테이블에 필수 ForeignKey를 추가한다면 기존 행의 값을 어떻게 채울지 먼저 결정해야 합니다. 일반적인 경로는 nullable 필드 추가 → data migration으로 값 채우기 → non-null 제약 추가입니다.

피해야 할 일반화
관계를 추가할 때마다 Migration 파일과 데이터베이스를 삭제하는 것은 해법이 아닙니다. 버릴 수 있는 초기 실습 DB가 아니라면 데이터 손실과 이력 불일치를 만듭니다.

4. 관계는 정방향·역방향·소유 필드를 함께 읽는다

Room.owner처럼 ForeignKey를 선언한 쪽에서 대상 User로 가는 접근이 정방향입니다. User에서 자신을 참조하는 Room들을 찾는 것이 역방향입니다.

room.owner                 # User 한 개
user.rooms.all()           # related_name으로 만든 Room QuerySet
room.guests.all()          # 여러 User
user.bookmarked_rooms.all()# 역방향 Room QuerySet

related_name을 생략한 ForeignKey의 기본 역방향 accessor는 보통 room_set입니다. 관계 lookup은 owner__username처럼 double underscore로 이어지며 마지막 필드의 자료형에 맞는 값을 비교해야 합니다.

Room.objects.filter(owner__username="sample")
# username 문자열 필드에는 문자열을 비교한다.
# owner__username=room.owner 처럼 User 객체를 넣지 않는다.

ManyToMany 관계는 중간 연결 테이블을 사용합니다. 연결 자체에 예약 시각·역할 같은 추가 속성이 필요하면 자동 중간 테이블 대신 명시적인 through Model을 정의합니다.

5. Manager는 QuerySet을 시작하는 Model 수준의 진입점이다

Room.objects가 기본 Manager입니다. Manager는 쿼리 생성의 시작점이고, all()·filter() 등은 QuerySet을 반환합니다. 공통 필터가 반복되면 사용자 정의 QuerySet 메서드를 만들고 as_manager()로 노출할 수 있습니다.

class RoomQuerySet(models.QuerySet):
    def published(self):
        return self.filter(is_published=True)

class Room(models.Model):
    is_published = models.BooleanField(default=False)
    objects = RoomQuerySet.as_manager()

Room.objects.published().order_by("name")

6. QuerySet은 결과 배열이 아니라 아직 실행 가능한 쿼리다

rooms = Room.objects.filter(owner=user)  # 보통 아직 SQL 미실행
rooms = rooms.exclude(name="hidden")     # 쿼리 조건 조합
rooms = rooms.order_by("name")           # 정렬 조건 조합

for room in rooms:                        # 여기서 평가
    print(room.name)

QuerySet은 지연 평가됩니다. 반복, list(), len(), repr(), boolean 검사, 일부 slicing처럼 결과가 실제로 필요할 때 SQL이 실행됩니다. count()와 exists()는 목적에 맞는 별도 쿼리를 실행할 수 있습니다.

표현주요 결과주의
filter()0개 이상 QuerySet없어도 예외가 아님
get()객체 정확히 한 개0개·2개 이상이면 예외
first()첫 객체 또는 None유일성을 보장하지 않음
exists()존재 여부객체 데이터가 필요하면 중복 조회 고려
values()dict 형태 QuerySetModel 메서드·관계 객체가 아님

7. Lookup과 Q 객체로 조건을 표현한다

from django.db.models import Q

Room.objects.filter(
    Q(name__icontains="sea") | Q(owner__username__startswith="sam"),
    is_published=True,
)

field__lookup=value가 기본 형태입니다. 같은 filter() 호출의 keyword 조건은 AND로 묶입니다. OR·NOT·괄호가 필요한 조건은 Q 객체를 사용합니다. QuerySet을 출력하기 전에 str(queryset.query)와 데이터베이스 쿼리 로그를 보면 ORM 표현이 어떤 SQL로 번역됐는지 확인할 수 있습니다.

관계 객체를 반복 접근할 때 쿼리가 늘어나면 select_related는 ForeignKey·OneToOne의 SQL JOIN, prefetch_related는 별도 조회 후 Python 결합을 사용한다는 차이를 검토합니다.

8. Admin은 Model을 보여주는 운영 UI이지 Model 설계의 대체물이 아니다

Django Admin에서 list_display, search_fields, list_filter를 정의하면 운영자가 데이터를 탐색하기 쉬워집니다. 관계 값을 열에 표시하는 메서드는 화면마다 추가 쿼리를 만들 수 있으므로 get_queryset()에서 관련 객체 로딩을 조정합니다.

@admin.register(Room)
class RoomAdmin(admin.ModelAdmin):
    list_display = ("name", "owner", "created_at")
    search_fields = ("name", "owner__username")

    def get_queryset(self, request):
        return super().get_queryset(request).select_related("owner")

사용자 Model을 확장한다면 프로젝트 초기에 AUTH_USER_MODEL을 정하고 관계에서는 직접 User 클래스를 하드코딩하지 않는 편이 안전합니다.

9. 결론

Django 데이터 흐름은 Model 선언 → Migration 이력 → DB 스키마 → Manager → 지연 QuerySet → SQL 평가입니다. 관계를 이해할 때는 ForeignKey가 어느 쪽에 있는지, 역방향 이름이 무엇인지, 조회가 몇 번 실행되는지를 함께 확인해야 합니다.
