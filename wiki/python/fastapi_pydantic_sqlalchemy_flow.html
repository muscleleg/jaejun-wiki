📖 파이썬 엔티티 매핑: 물리적 연결 vs 논리적 연결

1. 핵심 개념 정의

구분 물리적 연결 (ForeignKey) 논리적 연결 (relationship)
관리 주체 데이터베이스 (DB) 파이썬 메모리 (ORM)
주요 목적 데이터 무결성 (데이터 오염 방지) 개발 편의성 (객체 그래프 탐색)
결과물 DB 테이블에 생성되는 INT 컬럼 파이썬 클래스 내의 객체 참조 변수
비유 실제 땅에 묻은 광케이블 차에 장착된 내비게이션

2. 왜 파이썬은 두 줄을 다 써야 하나요?

자바(JPA)는 @JoinColumn을 통해 이를 암시적으로 합치지만, 파이썬은 명시성을 위해 이를 분리합니다.

  • 물리적 연결(ForeignKey)만 하면: post.user_id 숫자값(1, 2, 3...)은 알 수 있지만, 유저의 이름(post.user.name)을 알려면 DB를 직접 또 조회해야 합니다. (불편함)
  • 논리적 연결(relationship)까지 하면: post.author.name처럼 점(.)만 찍어서 연관된 객체의 데이터를 즉시 가져올 수 있습니다. (편리함)

3. 실무 코드 패턴 (Java vs Python)

[Java JPA 스타일]

Java

@ManyToOne // 논리적 연결
@JoinColumn(name = "user_id") // 물리적 연결
private User user; // 자바는 변수 하나로 해결

[Python SQLAlchemy 스타일]

Python

class Post(Base):
    __tablename__ = "posts"
    id: Mapped[int] = mapped_column(primary_key=True)

    # 1. 물리적 연결 (컬럼 적고 시마이!)
    # 실제 DB에 'user_id'라는 정수형 FK 컬럼이 생성됩니다.
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))

    # 2. 논리적 연결 (엔티티로 연결!)
    # DB에는 없지만, 파이썬 코드에서 post.author로 User 객체에 접근하게 해줍니다.
    author: Mapped["User"] = relationship(back_populates="posts")

4. 결정적 차이: "객체 없이 ID만으로 일하기"

자바와 달리 파이썬은 ID 컬럼을 명시적으로 두기 때문에, 성능 최적화가 매우 쉽습니다.

  • Java: 유저 ID만 알아도 보통 userRepository.findById()로 객체를 가져와야 함.
  • Python: 객체 조회 없이 ID 숫자값만 넣어서 바로 저장 가능.Python
# 유저 객체를 조회(SELECT)할 필요 없이 숫자만으로 게시글 생성!
new_post = Post(title="공부 중", user_id=10)
db.add(new_post)
db.commit()

📝 최종 실습 문제 (정답 포함)

아래는 부서(Department)와 직원(Employee)의 1:N 관계 매핑 완성본입니다.

Python

class Department(Base):
    __tablename__ = "departments"
    id: Mapped[int] = mapped_column(primary_key=True)

    # [논리적] 부서 객체에서 직원 리스트를 바로 보고 싶을 때
    employees: Mapped[List["Employee"]] = relationship(back_populates="dept")

class Employee(Base):
    __tablename__ = "employees"
    id: Mapped[int] = mapped_column(primary_key=True)

    # [물리적] 실제 DB에 부서 ID를 저장할 정수형 컬럼 생성
    # 정답: ForeignKey
    dept_id: Mapped[int] = mapped_column(ForeignKey("departments.id"))

    # [논리적] 직원 객체에서 부서 객체로 바로 이동하고 싶을 때
    # 정답: back_populates
    dept: Mapped["Department"] = relationship(back_populates="employees")

후속 학습 후보

데이터 설계(Entity) 다음에는 데이터를 실제 API로 주고받는 FastAPI 컨트롤러 구현과 Pydantic DTO·엔티티 변환을 각각 작은 예제로 검증할 수 있다.

원문 보존 단위

pydentic, response, 엔티티 플로우

FastAPI의 전체 흐름(DTO -> Entity -> DB Save -> Response)을 데이터 변환과 의존성 경계 중심으로 정리한다.

🏗️ FastAPI 표준 아키텍처: 데이터 흐름과 의존성 주입

이 가이드는 클라이언트의 요청이 입구(Request DTO)를 지나, 실제 DB에 저장(Entity & Persistence)되고, 안전하게 응답(Response DTO)으로 나가는 전체 과정을 다룹니다.

1. 전체 통합 코드 샘플

from fastapi import FastAPI, Depends
from pydantic import BaseModel, ConfigDict, Field
from sqlalchemy import Column, Integer, String, create_engine
from sqlalchemy.orm import declarative_base, sessionmaker, Session

app = FastAPI()
Base = declarative_base()

# --- [Layer 1: Database Entity (JPA @Entity)] ---
class UserEntity(Base):
    __tablename__ = "users"
    id = Column(Integer, primary_key=True, index=True)
    username = Column(String, unique=True)
    password_hash = Column(String)

# --- [Layer 2: Pydantic DTO (Request/Response DTO)] ---
class UserCreateRequest(BaseModel):
    """입력 검증: Java의 @RequestBody 역할"""
    # Field(...)의 '...'은 @NotNull(필수값)을 의미함
    username: str = Field(..., min_length=3, max_length=20)
    password: str = Field(..., min_length=8)

class UserResponse(BaseModel):
    """출력 제어: 클라이언트에게 나갈 필드만 정의"""
    model_config = ConfigDict(from_attributes=True) # Entity -> DTO 변환 스위치
    id: int
    username: str

# --- [Layer 3: Dependency Injection (Java @Autowired)] ---
# DB 세션을 생성하고 반납하는 제어의 역전(IoC) 로직
def get_db():
    db = SessionLocal() # DB 세션 오픈
    try:
        yield db        # 비즈니스 로직에 세션 주입
    finally:
        db.close()      # 응답 후 세션 자동 닫기 (try-with-resources 유사)

# --- [Layer 4: Controller (Java @RestController)] ---
@app.post("/users", response_model=UserResponse)
async def create_user(request: UserCreateRequest, db: Session = Depends(get_db)):
    # 1. 입구 컷: UserCreateRequest가 유효성 검사를 자동으로 수행

    # 2. 비즈니스 로직: DTO를 기반으로 Entity 객체 생성
    new_user = UserEntity(
        username=request.username,
        password_hash=f"hashed_{request.password}" # 실제로는 암호화 필수
    )

    # 3. Persistence: 실제 DB 저장 (Save 로직)
    db.add(new_user)          # Java: em.persist(entity)
    db.commit()               # Java: transaction.commit()
    db.refresh(new_user)      # 저장 후 생성된 ID 등을 다시 읽어옴

    # 4. 반환: response_model 설정 덕분에 Entity가 DTO로 자동 변환되어 나감
    return new_user

🧐 핵심 계층 및 문법 파헤치기

1. Field(..., ) : 입구 컷 (Validation)

  • ... (Ellipsis): 파이썬에서 "필수값(Required)"을 뜻합니다. 자바의 @NotNull과 같습니다.
  • 클라이언트가 값을 빼먹으면 함수가 실행되기도 전에 422 Unprocessable Entity 에러를 응답합니다.

2. Depends(get_db) : 의존성 주입 (DI)

  • 자바의 @Autowired 또는 생성자 주입과 같은 역할을 합니다.
  • yield의 마법: 비즈니스 로직이 실행될 때 세션을 빌려주고, 로직이 끝나면(finally) 자동으로 세션을 닫아주는 AOP(Aspect Oriented Programming) 역할을 수행합니다.

3. from_attributes=True & response_model : 보안 필터링

  • 문제: UserEntity에는 비밀번호(password_hash)가 들어있습니다.
  • 해결: response_model=UserResponse를 선언하면, FastAPI가 리턴되는 객체에서 UserResponse에 정의된 id, username만 골라냅니다. from_attributes=True 설정이 있어야만 엔티티의 속성을 읽어올 수 있습니다.

📝 자바 시니어의 노션 요약 (Quick Recall)

  • 데이터의 3단 변환:
  1. UserCreateRequest: 클라이언트가 준 생(Raw) 데이터를 검증하며 받는다.
  2. UserEntity: 검증된 데이터를 DB용 객체로 옮겨 담아 저장(db.commit)한다.
  3. UserResponse: 저장된 객체에서 나갈 정보만 추려서 응답한다.
  • ... 기호: "없으면 안 됨(Required)"을 뜻하는 파이썬 전용 마커.
  • Depends: DB 커넥션처럼 라이프사이클 관리가 필요한 객체를 주입받는 표준 도구.
원문 보존 단위

SQLAlchemy scalars()와 ORM 매핑의 동작 원리

1. scalars()는 첫 번째 컬럼만 가져온다

정의

scalars()는 Row 결과에서 “첫 번째 컬럼 값만 꺼내는 함수”다

예시 1 (ORM 객체)

select(Cluster)

→ Row 안에 Cluster 객체 하나 있음

→ scalars() → Cluster 반환

예시 2 (단일 컬럼)

select(Cluster.id)

→ Row 안에 id 값 있음

→ scalars() → int 반환

예시 3 (여러 컬럼)

select(Cluster.id, Cluster.name)

→ Row 안에 (id, name) 있음

→ scalars() → id만 반환 (name 버려짐)

핵심 한 줄

scalars()는 항상 “첫 번째 값만 꺼낸다”

2. Base를 상속한 경우만 ORM 매핑된다

정의

SQLAlchemy는 Declarative Base를 상속한 클래스만 DB row를 객체로 자동 매핑한다

예시 (가능한 경우)

class Cluster(Base):
    ...
select(Cluster)

→ DB row → Cluster 객체 자동 변환

→ Session이 관리 (더티체킹 가능)

예시 (불가능한 경우)

class ClusterDTO:
    ...
select(ClusterDTO)  # ❌ 안 됨

→ SQLAlchemy가 모르는 클래스

→ 자동 매핑 불가

핵심 한 줄

ORM 매핑은 Base를 상속한 클래스에서만 발생한다

3. 둘의 관계 (헷갈리는 포인트 정리)

이 둘은 완전히 다른 개념이다

개념 역할
select(Cluster) ORM 매핑 수행
scalars() 결과에서 값 꺼냄

흐름으로 보면

db.execute(select(Cluster)).scalars().all()
  1. select → ORM 매핑 발생
  2. execute → Row 생성
  3. scalars → 객체 꺼냄

4. 최종 정리 (이대로 기억해라)

scalars()는 첫 번째 컬럼만 꺼내는 도구이고,

ORM 매핑은 Base를 상속한 클래스에서만 일어난다

이 두 개만 정확히 구분하면

SQLAlchemy 2.x에서 헷갈릴 일 거의 없다.

편입 후 검증 메모

  • Pydantic과 ORM: Pydantic 모델은 API 경계의 검증·직렬화 모델이고 SQLAlchemy 모델은 영속성 매핑이다. 이름이 비슷해도 한 객체가 두 책임을 대신하지 않는다.
  • ORM 객체 변환: Pydantic v2에서 ORM 속성을 읽으려면 모델 설정의 from_attributes=True와 model_validate 흐름을 확인한다.
  • scalars(): 결과 Row마다 첫 번째 컬럼 값을 꺼내는 API다. select(Entity)에서는 그 첫 컬럼이 ORM 객체이지만, 여러 컬럼을 선택하면 나머지는 버려질 수 있다.
  • 응답 안전성: Entity를 그대로 직렬화하지 말고 허용된 Response 모델을 사용한다. 비밀번호 해시·토큰·내부 식별 정보가 스키마에서 제외되는지 테스트한다.
