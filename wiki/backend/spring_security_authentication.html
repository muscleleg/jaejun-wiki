Spring Security · Authentication · Authorization

Spring Security 인증·인가·Filter chain

보안을 설정 코드 조각으로 외우지 않고, 요청이 Filter chain을 통과하며 신원을 확인하고 권한을 판단하고 실패 응답을 만드는 순서로 이해합니다.

보안 목표인증·인가Filter chainSecurityContext예외원래 요청비밀번호JWT결론

1. 보안 기능은 CIA 세 목표를 지키기 위한 수단이다

약어한국어 뜻질문
C · Confidentiality기밀성허가되지 않은 사람이 정보를 읽지 못하는가?
I · Integrity무결성정보가 허가 없이 바뀌지 않았는가?
A · Availability가용성허가된 사용자가 필요할 때 서비스를 쓸 수 있는가?

로그인 기능만 있다고 세 목표가 자동으로 충족되지는 않습니다. 전송 암호화, 입력 검증, 권한, 감사 로그, 백업·복구와 과부하 대응이 함께 필요합니다.

2. 인증과 인가는 다른 질문이다

  • Authentication(인증): 요청을 보낸 주체가 누구인지 확인합니다.
  • Authorization(인가): 확인된 주체가 이 자원과 동작을 사용할 수 있는지 판단합니다.

인증이 먼저이고 인가가 뒤따릅니다. 인증되지 않은 요청과 인증됐지만 권한이 부족한 요청은 실패 이유와 응답 처리도 다릅니다.

3. Spring Security는 Servlet Filter chain 안에서 동작한다

대표 흐름
요청 → 보안 exploit 방어 → 인증 정보 추출·검증 → SecurityContext 설정 → 권한 판단 → Controller

DelegatingFilterProxy가 Servlet container와 Spring bean을 연결하고, FilterChainProxy가 요청에 맞는 SecurityFilterChain을 선택합니다. Filter 순서는 중요합니다. 현재 사용자를 필요로 하는 Filter는 인증 Filter보다 뒤에 있어야 합니다.

@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/public/**").permitAll()
            .anyRequest().authenticated()
        )
        .formLogin(Customizer.withDefaults())
        .build();
}
버전 경계
과거의 WebSecurityConfigurerAdapter 기반 설정을 현재 코드에 그대로 복사하지 않습니다. 설치된 Spring Security major version의 공식 설정 API를 확인합니다.

4. 인증 결과는 SecurityContext에 보관된다

인증 Filter는 credential 또는 token을 읽어 Authentication을 만들고 AuthenticationManager에 검증을 요청합니다. 성공한 Authentication에는 principal, 권한, 인증 여부가 들어가며 SecurityContextHolder를 통해 이후 계층이 접근합니다.

객체역할
Authentication현재 주체와 credential·authority를 표현
AuthenticationManager인증 요청을 적절한 provider에 위임
UserDetailsService사용자 이름으로 사용자 정보를 읽는 계약
PasswordEncoder비밀번호 단방향 검증
SecurityContext현재 요청의 인증 결과 보관

5. 인증 실패와 권한 부족은 서로 다른 응답 경로를 가진다

ExceptionTranslationFilter는 아래쪽 chain에서 발생한 인증·인가 예외를 HTTP 응답으로 변환합니다.

  • AuthenticationException 또는 미인증 상태: AuthenticationEntryPoint가 로그인을 시작하거나 401 응답을 만듭니다.
  • 인증됐지만 AccessDeniedException: AccessDeniedHandler가 403 응답을 만듭니다.

Controller 예외 처리만 살펴보면 Controller에 도달하기 전에 발생한 보안 실패를 놓칠 수 있습니다. Filter 로그와 Security debug 로그에서 실제로 어느 Filter가 응답을 끝냈는지 추적합니다.

6. 로그인 뒤 원래 페이지로 돌아가려면 요청을 저장해야 한다

보호된 페이지에 접근한 미인증 사용자를 로그인 화면으로 보낸 뒤 원래 URL로 복귀하려면 RequestCache가 원래 요청을 저장하고 인증 성공 handler가 그 요청을 사용해야 합니다. 성공 URL을 항상 한 곳으로 고정하면 저장된 요청보다 고정 URL이 우선될 수 있습니다.

세션 기반 form login과 stateless bearer token API는 요청 저장 전략이 다릅니다. REST API는 보통 redirect 대신 401을 반환하고 client가 인증 상태를 처리합니다.

7. 비밀번호는 복호화하는 값이 아니라 검증하는 값으로 저장한다

@Bean
PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}

String encoded = passwordEncoder.encode(rawPassword);
boolean matches = passwordEncoder.matches(candidate, encoded);

BCrypt는 salt와 반복 비용을 포함한 password hashing 방식입니다. 같은 원문 비밀번호를 두 번 encode해 결과 문자열이 달라도 matches로 검증할 수 있습니다. 비밀번호를 일반 SHA-256 한 번으로 hash하거나 암호화해 복호화하는 방식으로 저장하지 않습니다.

8. JWT 서명 용어를 분리한다

JWT(JSON Web Token: JSON 웹 토큰)는 header, payload, signature를 점으로 연결한 token 형식입니다. 기본 서명 JWT는 payload를 암호화하지 않으므로 민감정보를 넣지 않습니다.

용어뜻핵심
SHA-256256-bit secure hash algorithm(보안 해시 알고리즘)임의 길이 입력을 고정 길이 digest로 변환
HMACHash-based Message Authentication Code(해시 기반 메시지 인증 코드)공유 secret으로 무결성과 인증 확인
RSA공개키 암호 기술 계열private key 서명, public key 검증 가능
HS256HMAC + SHA-256서명·검증자가 같은 secret 공유
RS256RSA signature + SHA-256private/public key 역할 분리

exp, nbf, iat 같은 시간 claim은 UTC epoch 기반 NumericDate로 검증합니다. 중요한 것은 시스템의 절대시각이며, timezone은 주로 표시와 로그 해석에 영향을 줍니다.

Algorithm allowlist, issuer, audience, signature, 만료를 모두 검증합니다. Token 문자열을 단순 decode해서 payload가 읽힌다는 사실은 서명이 유효하다는 뜻이 아닙니다.

9. 결론

Spring Security 문제는 어느 Filter가 요청을 처리했는가 → Authentication이 만들어졌는가 → SecurityContext에 저장됐는가 → 어느 권한 규칙이 거부했는가 → 누가 응답을 만들었는가 순서로 추적합니다. 설정 method 이름만 암기하는 것보다 이 흐름이 버전 변화에도 오래 남습니다.
