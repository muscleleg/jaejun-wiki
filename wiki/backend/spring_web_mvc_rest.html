Spring MVC·Thymeleaf·REST API 요청 흐름

브라우저 요청이 Servlet Filter와 DispatcherServlet을 지나 Controller에 도착하고, HTML 또는 JSON 응답으로 돌아가는 경로를 서버 렌더링과 REST(표현 상태 전송) API 두 갈래로 연결합니다.

HTTP 요청Spring MVCJSP·ThymeleafForm BindingREST APIDTOPUT·PATCH오류 경계결론

1. HTTP 요청은 문자열 묶음에서 Java 객체로 변환된다

HTTP(하이퍼텍스트 전송 규약) 요청은 method, path, header, body로 구성됩니다. Servlet Container는 이를 HttpServletRequest와 HttpServletResponse 객체로 표현하고 Filter chain을 거쳐 Spring의 DispatcherServlet에 전달합니다.

실행 경로
Browser → Web server/Servlet container → Filter chain → DispatcherServlet → HandlerMapping → Controller → View 또는 HttpMessageConverter → HTTP response

URL(통합 자원 위치)은 전체 주소이고 URI(통합 자원 식별자)는 자원을 식별하는 문자열 범주입니다. Controller에서는 request path, query string, path variable, header, body가 서로 다른 입력 위치라는 점이 중요합니다.

2. Controller는 요청을 사용 사례에 연결하는 경계다

@Controller
@RequestMapping("/rooms")
class RoomController {
    @GetMapping("/{id}")
    String detail(@PathVariable long id, Model model) {
        RoomView room = roomService.findView(id);
        model.addAttribute("room", room);
        return "rooms/detail";
    }
}

@Controller가 반환한 문자열은 기본적으로 View 이름입니다. Controller가 직접 데이터베이스 세부사항을 처리하기보다 Service에 사용 사례를 위임하고, 화면에 필요한 값을 Model에 담습니다.

@ResponseBody를 메서드에 붙이면 반환값을 View 이름으로 해석하지 않고 response body로 직렬화합니다. @RestController는 @Controller + @ResponseBody 역할을 클래스 수준에서 제공합니다.

3. JSP와 Thymeleaf는 서버에서 HTML을 완성한다

JSP(Java Server Pages: 자바 서버 페이지)는 Servlet으로 변환되어 실행되고, Thymeleaf는 HTML template의 attribute를 해석합니다. 두 방식 모두 서버가 데이터를 결합해 완성된 HTML을 브라우저에 보냅니다.

관심사JSPThymeleaf
값 출력EL(표현 언어) ${...}th:text="${...}"
조건JSTL(표준 태그 라이브러리) c:ifth:if
Form fieldname·value 직접 연결th:object·th:field
권장 경계scriptlet Java 코드 최소화복잡한 로직을 template 밖으로 이동

JSP scriptlet에 Java 제어 흐름을 많이 넣거나 Thymeleaf attribute에 긴 JavaScript를 조립하면 View가 사용 사례 로직을 떠안습니다. Controller·Service에서 화면 모델을 준비하고 template은 표시와 간단한 분기에 집중합니다.

4. 새 Form에 빈 객체를 보내는 이유는 입력 이름과 객체 필드를 연결하기 위해서다

@GetMapping("/new")
String createForm(Model model) {
    model.addAttribute("roomForm", new RoomForm());
    return "rooms/new";
}

@PostMapping
String create(@Valid @ModelAttribute RoomForm roomForm,
              BindingResult bindingResult) {
    if (bindingResult.hasErrors()) {
        return "rooms/new";
    }
    long id = roomService.create(roomForm);
    return "redirect:/rooms/" + id;
}
<form th:object="${roomForm}" th:action="@{/rooms}" method="post">
  <input th:field="*{name}">
  <button type="submit">저장</button>
</form>

th:field는 field 이름·현재 값·오류 표시를 form object의 property와 연결합니다. 제출된 문자열은 WebDataBinder를 통해 객체 필드로 binding되고 validation이 실행됩니다.

문자 인코딩은 request를 읽기 전에 결정되어야 합니다. 현재 Servlet 기반 애플리케이션은 UTF-8 설정과 Spring Boot 기본값을 확인하고, 오래된 JSP의 request.setCharacterEncoding 한 줄만 모든 구간의 인코딩 해법으로 일반화하지 않습니다.

5. REST API는 Java 객체를 응답 표현으로 직렬화한다

@RestController
@RequestMapping("/api/rooms")
class RoomApiController {
    @GetMapping("/{id}")
    ResponseEntity<RoomResponse> detail(@PathVariable long id) {
        RoomResponse body = roomService.findResponse(id);
        return ResponseEntity.ok(body);
    }
}

ResponseEntity는 status code, header, body를 함께 표현합니다. Java 객체는 HttpMessageConverter를 통해 Content-Type에 맞는 JSON 등의 표현으로 변환됩니다.

Content-Typebody 해석예
application/jsonJSON 문서API request/response
application/x-www-form-urlencodedkey-value form기본 HTML form
multipart/form-data여러 part와 파일파일 업로드
text/htmlHTML 문서서버 렌더링 화면

6. Entity를 그대로 응답하지 않고 DTO로 경계를 만든다

DTO(Data Transfer Object: 데이터 전송 객체)는 특정 요청·응답에 필요한 필드만 표현합니다. JPA Entity를 직접 JSON으로 내보내면 lazy proxy, 양방향 관계 순환, 내부 필드 노출, API schema와 DB schema의 강한 결합이 생길 수 있습니다.

record RoomResponse(long id, String name, String ownerName) {
    static RoomResponse from(Room room) {
        return new RoomResponse(
            room.getId(),
            room.getName(),
            room.getOwner().getUsername()
        );
    }
}

@JsonIgnore로 문제를 하나씩 숨기는 것보다 응답 타입을 명시하는 편이 허용 목록을 만들기 쉽습니다. 입력 DTO와 출력 DTO는 validation·노출 책임이 다르므로 같아야 할 이유가 없습니다.

7. PUT과 PATCH는 변경 범위 계약이 다르다

Method일반 의미설계 질문
PUT자원의 전체 표현 교체누락 field를 초기화할 것인가?
PATCH일부 field 변경누락과 명시적 null을 어떻게 구분할 것인가?

HTTP method 이름만으로 동작이 자동 보장되지는 않습니다. 같은 요청을 반복했을 때 결과가 같은지, validation과 권한 검사를 어디서 하는지, 동시 수정 충돌을 어떻게 처리하는지 API 명세에 적어야 합니다.

8. 실패도 Controller 경계의 응답 계약이다

Validation 실패, 리소스 없음, 인증 실패, 서버 오류를 모두 200 응답과 문자열 메시지로 반환하면 client가 결과를 구분하기 어렵습니다. @ControllerAdvice와 @ExceptionHandler를 사용해 예외를 일관된 status와 body로 변환합니다.

@RestControllerAdvice
class ApiExceptionHandler {
    @ExceptionHandler(RoomNotFoundException.class)
    ResponseEntity<ApiError> handle(RoomNotFoundException ex) {
        return ResponseEntity.status(404)
            .body(new ApiError("ROOM_NOT_FOUND", ex.getMessage()));
    }
}

로그에는 원인과 추적 식별자를 남기되 응답 body에는 stack trace, 내부 클래스명, 데이터베이스 정보 같은 구현 세부사항을 노출하지 않습니다.

9. 결론

Spring Web에서 가장 중요한 경계는 HTTP 입력 → Controller 입력 모델 → Service 사용 사례 → View/응답 DTO → HTTP 응답입니다. JSP·Thymeleaf와 REST API는 응답 표현이 다르지만 Controller가 외부 계약과 내부 모델을 분리해야 한다는 원칙은 같습니다.
