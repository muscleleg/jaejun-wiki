JPA 영속성·연관관계·조회 성능

JPA(Java Persistence API: 자바 영속성 API)를 annotation 모음으로 보지 않고, transaction 안에서 객체 상태가 SQL로 동기화되는 과정으로 이해합니다.

전체 흐름Entity 상태영속성 컨텍스트flush연관관계cascadefetchN+1callback결론

1. 객체와 행 사이에는 영속성 컨텍스트가 있다

쓰기 흐름
Entity 변경 → 영속성 컨텍스트가 변경 감지 → flush 시 SQL 생성 → transaction commit

ORM(Object-Relational Mapping: 객체 관계 매핑)은 객체와 관계형 table을 연결합니다. JPA는 그 동작 계약이고, Hibernate 같은 provider가 계약을 구현합니다. EntityManager는 현재 transaction의 Entity를 추적하는 영속성 컨텍스트에 접근하는 핵심 API입니다.

따라서 Java field를 바꾼 순간 database가 즉시 바뀐다고 생각하면 안 됩니다. 언제 관리 상태가 됐고, 언제 flush됐으며, transaction이 commit됐는지를 함께 봐야 합니다.

2. Entity 생명주기는 네 상태로 나뉜다

상태의미대표 전환
transient(비영속)새 Java 객체이며 영속성 컨텍스트가 추적하지 않음new Member()
managed(영속)현재 context가 identity와 변경을 추적persist, find
detached(준영속)식별자는 있지만 현재 context가 추적하지 않음detach, clear, context 종료
removed(삭제 예정)flush 때 삭제될 대상으로 표시됨remove

persist와 merge는 같은 저장 명령이 아니다

  • persist(entity)는 전달한 새 Entity 자체를 managed 상태로 만듭니다.
  • merge(detached)는 전달 객체의 값을 managed instance에 복사하고 그 managed instance를 반환합니다. 전달했던 객체 자체는 계속 detached일 수 있습니다.
Member managed = entityManager.merge(detached);
// 이후 변경은 detached가 아니라 managed에 적용한다.

새 Entity 생성에는 보통 persist를 사용하고, web 요청 DTO(데이터 전송 객체)를 곧바로 merge해 전체 field를 덮어쓰는 방식은 피합니다. 기존 Entity를 조회한 뒤 허용된 값만 변경하는 편이 의도와 권한을 명확히 합니다.

3. 영속성 컨텍스트는 identity map과 변경 감지를 제공한다

같은 context에서 같은 Entity type과 primary key를 조회하면 같은 managed instance를 돌려주는 것이 identity 보장의 핵심입니다. 이를 흔히 1차 cache라고 부르지만, application 전체가 공유하는 cache가 아니라 보통 현재 transaction 범위의 작업 공간입니다.

Member first = entityManager.find(Member.class, 1L);
Member second = entityManager.find(Member.class, 1L);
assert first == second;

managed Entity의 field를 바꾸면 provider는 snapshot과 비교해 UPDATE를 생성합니다. 이것이 dirty checking(변경 감지)입니다. setter 호출 자체가 SQL 실행을 의미하지는 않습니다.

4. flush, commit, clear를 구분한다

동작무엇이 바뀌는가transaction 종료?
flush()현재 변경을 SQL로 database와 동기화아니오
commit()transaction 결과를 확정하며 보통 먼저 flush예
clear()관리 중인 Entity를 모두 detached로 전환아니오

flush 뒤에도 rollback하면 transaction 결과는 취소될 수 있습니다. 반대로 flush하지 않고 native query나 외부 connection에서 값을 확인하면 아직 SQL이 전달되지 않아 예상과 다른 결과를 볼 수 있습니다.

긴 batch에서는 일정 단위로 flush와 clear를 실행해 context가 계속 커지는 것을 막을 수 있습니다. 다만 clear 이후 객체가 detached가 된다는 사실을 코드가 고려해야 합니다.

5. 양방향 연관관계에는 외래 키를 갱신하는 한쪽만 있다

database의 foreign key는 한 column에 있습니다. 객체가 양쪽 reference를 갖더라도 JPA mapping에서는 그 column을 쓰는 owning side(연관관계 주인)를 정해야 합니다. mappedBy가 있는 쪽은 inverse side이며 외래 키를 직접 갱신하지 않습니다.

@Entity
class Order {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "member_id")
    private Member member; // owning side
}

@Entity
class Member {
    @OneToMany(mappedBy = "member")
    private List<Order> orders = new ArrayList<>();

    void addOrder(Order order) {
        orders.add(order);
        order.setMember(this);
    }
}

양쪽 객체 graph의 일관성을 위해 helper method가 두 reference를 모두 맞추되, 실제 외래 키 SQL은 owning side 값으로 결정됩니다. JSON(JavaScript Object Notation: 자바스크립트 객체 표기법) 직렬화 때 양방향 reference가 무한 순환하지 않도록 Entity를 response에 직접 노출하지 않는 것도 중요합니다.

6. cascade와 orphan removal은 관계 mapping과 다른 축이다

  • cascade: 부모에 수행한 persist·remove 같은 생명주기 작업을 자식에게 전파할지 정합니다.
  • orphanRemoval = true: 부모 collection에서 제거되어 더는 소유되지 않는 자식을 삭제할지 정합니다.

둘 다 database의 ON DELETE CASCADE와 같은 설정은 아닙니다. 여러 aggregate가 공유하는 Entity에 CascadeType.REMOVE를 무심코 적용하면 예상보다 넓게 삭제될 수 있으므로, 생명주기를 실제로 함께 소유하는 관계에만 사용합니다.

7. fetch type은 조회 계획의 기본값에 가깝다

JPA 기본은 to-many 연관관계가 LAZY(지연), to-one 연관관계가 EAGER(즉시)입니다. 특히 LAZY는 provider가 지연을 허용한다는 hint 성격도 있으므로, 성능이 중요한 query는 기본값에 기대지 말고 명시적인 조회 계획으로 검증합니다.

영속성 context가 닫힌 뒤 LAZY 연관관계에 접근하면 필요한 SQL을 실행할 수 없어 예외가 날 수 있습니다. 이를 피하려고 모든 관계를 EAGER로 바꾸기보다 transaction 안에서 필요한 DTO projection이나 fetch join을 사용합니다.

8. N+1은 객체 수가 아니라 SQL 횟수 문제다

부모 목록 1회 조회 뒤 각 부모의 자식에 접근할 때 부모 수만큼 추가 query가 실행되면 1 + N 문제가 됩니다. log나 profiler에서 실제 SQL 횟수를 세어 확인합니다.

상황대표 전략주의
to-one을 함께 읽음fetch join, EntityGraph중복 join과 불필요한 column 확인
to-many 전체를 함께 읽음fetch join, batch fetchingrow 중복과 memory 증가
to-many + pagination부모 ID page 조회 후 자식 별도 조회collection fetch join에 database pagination을 그대로 기대하지 않음
화면 전용 조회DTO projectionEntity 수정 목적에는 부적합

정답은 “항상 fetch join”이 아닙니다. 필요한 graph 크기, page 여부, query 수, 반환 row 수를 함께 측정해 선택합니다.

9. callback과 auditing은 저장 생명주기에 붙는다

@PrePersist, @PreUpdate 같은 callback은 해당 생명주기 event 전에 실행됩니다. 생성·수정 시각처럼 반복되는 값은 callback이나 Spring Data auditing으로 관리할 수 있습니다. 외부 API(응용 프로그램 인터페이스) 호출처럼 실패와 재시도가 필요한 작업을 Entity callback에 숨기면 transaction 경계가 불명확해지므로 domain event나 service 흐름으로 분리합니다.

10. 결론

JPA 문제를 볼 때는 현재 Entity 상태 → 영속성 컨텍스트 범위 → owning side → flush 시점 → 실제 SQL 횟수와 row 수 순서로 확인합니다. annotation 이름보다 이 실행 흐름을 잡으면 저장 누락, detached 객체, N+1, pagination 오류를 같은 지도 위에서 설명할 수 있습니다.
