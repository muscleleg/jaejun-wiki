Spring Data JPA · Repository · Query

Spring Data JPA 조회·페이지·성능

Repository method 이름이 어떤 query로 해석되고, 반환형과 page 방식이 실행 SQL과 memory 사용량을 어떻게 바꾸는지 연결합니다.

Repositorymethod query@Query반환형수정 queryPage·Slice조회 성능확장검증결론

1. Repository는 EntityManager 위의 반복 작업을 추상화한다

Spring Data JPA는 JPA(Java Persistence API: 자바 영속성 API) 위에서 CRUD(Create·Read·Update·Delete: 생성·조회·수정·삭제), query 생성, pagination을 제공합니다. Interface만 선언해도 proxy 구현체가 만들어지지만, 결국 JPA query와 transaction으로 실행된다는 사실은 그대로입니다.

interface MemberRepository extends JpaRepository<Member, Long> {
    Optional<Member> findByEmail(String email);
}

일반적으로 읽기 method에는 read-only transaction 기본 설정이 적용되고, 저장·삭제 method에는 일반 transaction이 적용됩니다. 여러 repository 호출을 하나의 업무 단위로 묶는 transaction 경계는 service에서 명시하는 편이 안전합니다.

2. query method 이름은 정해진 문법으로 해석된다

List<Member> findTop10ByAgeGreaterThanOrderByCreatedAtDesc(int age);
List<Member> findByTeamIdIn(Collection<Long> teamIds);
  • Top10: 최대 결과 수
  • AgeGreaterThan: age > ?
  • OrderByCreatedAtDesc: 생성 시각 내림차순
  • TeamIdIn: team ID 집합 안에 있는 값

method 이름이 길어져 의미를 읽기 어렵거나 join·집계·조건 분기가 복잡해지면 억지로 이름을 늘리지 말고 명시적인 query나 custom repository로 이동합니다.

3. @Query는 실행할 JPQL을 명시한다

JPQL(Java Persistence Query Language: 자바 영속성 질의 언어)은 table 이름이 아니라 Entity와 field 이름을 대상으로 합니다. Native query는 database SQL을 직접 쓰므로 제품별 문법과 mapping 책임이 커집니다.

@Query("""
    select new com.example.MemberSummary(m.id, m.name, t.name)
    from Member m join m.team t
    where m.active = true
    """)
List<MemberSummary> findActiveSummaries();

DTO(데이터 전송 객체) projection은 화면이나 API(응용 프로그램 인터페이스)에 필요한 column만 읽을 때 유용합니다. Entity 전체를 읽고 serialization 단계에서 자르는 방식보다 조회 의도를 SQL에 가깝게 표현합니다.

4. 반환형은 결과 개수 계약이다

반환형0건2건 이상용도
List<T>빈 list모두 반환여러 건
Optional<T>empty단일 결과 계약 위반 예외 가능0 또는 1건
Tnull 가능단일 결과 위반 예외단일 제약이 명확할 때

Optional은 여러 건 중 첫 번째를 고르는 기능이 아닙니다. database unique constraint와 query 조건이 정말 0 또는 1건을 보장하는지 함께 확인합니다.

5. bulk 수정 query는 영속성 컨텍스트를 우회한다

@Modifying은 @Query로 선언한 UPDATE·DELETE처럼 결과 집합을 반환하지 않는 query에 붙입니다. 일반 save method에 붙이는 annotation이 아닙니다.

@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("update Member m set m.active = false where m.lastLoginAt < :cutoff")
int deactivateDormant(Instant cutoff);

bulk query는 managed Entity 각각의 상태를 바꾸지 않고 database row를 직접 수정합니다. 이미 읽어 둔 Entity가 오래된 값을 갖지 않도록 먼저 flush하고, 실행 뒤 context를 clear하거나 다시 조회하는 전략이 필요합니다.

6. Page, Slice, Window는 필요한 부가 정보가 다르다

형태추가 query·정보적합한 상황
Page<T>대개 전체 건수 count query총 페이지 수가 반드시 필요
Slice<T>다음 page 존재 여부더 보기, 무한 scroll
Window<T>scroll position 기반 다음 구간큰 data의 순차 탐색

offset pagination은 뒤 page로 갈수록 database가 건너뛸 row가 커질 수 있습니다. 안정적인 정렬 key가 있다면 keyset 방식으로 마지막 key 이후를 읽는 scroll을 검토합니다. 동률을 깨는 고유한 보조 정렬 key가 없으면 page 사이에서 항목이 중복되거나 빠질 수 있습니다.

7. 성능은 query 수와 반환 row 수를 함께 측정한다

  • to-one 관계: fetch join이나 @EntityGraph로 한 번에 읽을 수 있습니다.
  • to-many 관계: fetch join은 SQL row를 늘리고 Entity 중복을 만들 수 있습니다.
  • to-many와 page: collection fetch join으로 database page가 그대로 적용된다고 가정하지 않습니다. 부모 ID page와 연관 data 조회를 분리합니다.
  • 화면 전용 목록: DTO projection으로 필요한 column만 선택합니다.

N+1 해결 뒤 query가 1회가 됐더라도 수십만 row를 반환하면 개선이 아닐 수 있습니다. SQL log, 실행 계획, query 횟수, row 수, memory를 같이 봅니다.

8. 복잡한 동적 조회는 custom repository로 옮긴다

선택 조건이 많고 projection·join 전략을 조정해야 하면 repository fragment와 custom 구현을 사용합니다. Querydsl이나 Criteria API를 선택할 수 있지만, 도구보다 먼저 입력 조건, 반환 DTO, 정렬 안정성, page 방식과 허용 가능한 query 수를 계약으로 적습니다.

Lock과 query hint는 contention과 provider 동작에 영향을 주므로 “성능 향상 annotation”처럼 일반 적용하지 않습니다. transaction 격리 수준, lock 대기와 실패 처리까지 함께 설계합니다.

9. Repository test는 반환값뿐 아니라 계약을 검증한다

  • 0건·1건·중복 data에서 반환형 계약
  • page 경계와 동일 정렬값에서 항목 누락 여부
  • bulk 수정 뒤 같은 transaction에서 재조회한 값
  • N+1이 의심되는 화면의 SQL 횟수
  • unique constraint와 예외 변환

AssertJ assertion은 assertThat(actual).isEqualTo(expected)처럼 실제값에서 시작합니다. 실패 message가 domain 규칙을 드러내게 작은 검증을 분리합니다.

10. 결론

Spring Data JPA method를 설계할 때는 결과 개수 계약 → query 표현 방식 → transaction → page 정보 → SQL 횟수와 row 수를 차례로 결정합니다. Repository가 SQL을 숨겨 주더라도 실행 비용과 영속성 컨텍스트의 일관성까지 숨겨 주지는 않습니다.
