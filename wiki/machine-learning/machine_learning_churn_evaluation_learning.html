회원 이탈 예측으로 이해하는 머신러닝 실무 기초

회사 동료와의 대화에서 나온 Loss, Precision, Recall, AUC를 출발점으로 머신러닝 실무가 문제 정의·데이터·학습·평가·반복 실험으로 연결되는 과정을 정리한다.

← 학습 로드맵 출발점 문제 정의 학습 평가 Dummy Baseline Logistic 평가 읽기 실무 반복 정확히 구분하기 데이터 품질 실습 다음 학습

이 문서의 출발점

머신러닝 실무는 논문과 수식을 완전히 이해한 뒤 새로운 알고리즘을 직접 구현하는 일만을 뜻하지 않는다. 이미 알려진 방법을 조사하고 현재 문제에 적용한 뒤, 동일한 조건에서 지표와 오류를 비교해 개선하는 작업도 큰 비중을 차지한다.

대화의 위치
동료 한 명의 경험은 머신러닝 직무 전체를 대표하는 객관적 근거가 아닙니다. 여기서는 그 대화를 학습 질문을 발견한 계기로 사용하며, 개별 업무 설명을 일반 법칙으로 단정하지 않습니다.
현재 바뀐 관점
실무의 핵심은 모든 이론을 먼저 완주하는 것이 아니라, 문제를 정확히 정의하고 검증 가능한 Baseline을 만든 뒤 지표와 오류 사례에 근거해 다음 실험을 선택하는 것입니다.

1. 회원 이탈을 머신러닝 문제로 바꾼다

Feature와 Label

구분회원 이탈 예시역할
Feature X최근 접속 이후 일수, 로그인 횟수, 가입 기간, 결제 금액, 문의 횟수예측에 사용하는 입력 정보
Label y이탈 1, 비이탈 0모델이 맞혀야 하는 실제 정답
Feature(X) → Model → Prediction → Label(y)과 비교

Feature와 Label만 정하면 끝나는 것이 아니다

예측 대상어떤 회원을 대상으로 하는가?
기준 시점언제까지의 정보만 Feature로 쓰는가?
예측 기간앞으로 며칠 이내의 이탈을 예측하는가?
업무 조치예측 후 쿠폰·상담 등 무엇을 실행하는가?
오류 비용FP와 FN 중 어느 실수가 더 비싼가?

예를 들어 이탈을 “향후 30일 동안 접속하지 않음”으로 정의한다면 예측 시점 이후의 30일은 Label을 만드는 데 사용해야 합니다. 이 미래 정보를 Feature에 섞으면 모델이 실제 예측 시점에 알 수 없는 정보를 본 것이므로 데이터 누수가 됩니다.

2. Weight와 Loss로 모델을 학습한다

사람이 Feature별 Weight를 일일이 정하는 것이 아니라, 모델이 학습 과정에서 Loss를 줄이는 방향으로 Weight를 조정합니다.

예측값 = Feature₁ × Weight₁ + Feature₂ × Weight₂ + ···
1. 입력Feature를 모델에 넣는다.
2. 예측현재 Weight로 결과를 계산한다.
3. LossPrediction과 Label의 차이를 수치화한다.
4. 학습Loss가 감소하는 방향으로 Weight를 수정한다.
5. 반복새 Weight로 다시 예측하고 평가한다.
실무자가 직접 조절하는 것
학습된 Weight 자체를 한 칸씩 손으로 바꾸기보다 Feature, 데이터 구성, 모델 종류, Hyperparameter, Loss, Class weight와 Threshold 등을 선택하고 실험합니다.

학습을 오래 한다고 무조건 좋아지지 않는다

분할역할
TrainWeight를 실제로 학습시키는 데이터
Validation학습 중 일반화 성능, Hyperparameter와 Threshold를 선택하는 데이터
Test선택을 모두 끝낸 뒤 마지막 성능을 평가하는 데이터

Train 성능만 계속 좋아지고 Validation 성능이 나빠지면 학습 데이터를 외우는 Overfitting을 의심합니다. Test 결과를 보면서 Threshold나 모델을 반복 선택하면 Test도 선택 과정에 오염됩니다.

3. 확률을 Threshold로 판정하고 결과를 평가한다

이진 분류기는 이탈 여부를 바로 출력하기보다 이탈 점수 또는 확률을 만들 수 있습니다. Threshold가 0.5라면 그 이상을 이탈로 판정합니다.

실제 이탈실제 비이탈
이탈로 예측TP · 정확히 발견FP · 잘못 경보
비이탈로 예측FN · 이탈을 놓침TN · 정확히 제외
TP·FP·TN·FN을 읽는 고정 규칙
P / N = 모델이 Positive / Negative 중 무엇으로 예측했는가
T / F = 그 예측이 실제 정답과 같았는가

Positive는 좋다는 뜻이 아니라 이 문제에서 찾아내기로 정한 대상입니다. 스팸 탐지에서는 스팸, 질병 검사에서는 질병 있음, 불량품 검사에서는 불량품을 Positive로 정할 수 있습니다.

이름모델의 예측예측이 맞았는가?
TPPositive맞음 · 실제도 Positive
FPPositive틀림 · 실제는 Negative
TNNegative맞음 · 실제도 Negative
FNNegative틀림 · 실제는 Positive

문제가 바뀌어도 같은 규칙을 적용하는 샘플

회원 이탈

TP 이탈로 예측 → 실제 이탈
FP 이탈로 예측 → 실제 비이탈
TN 비이탈로 예측 → 실제 비이탈
FN 비이탈로 예측 → 실제 이탈

스팸 탐지

TP 스팸으로 예측 → 실제 스팸
FP 스팸으로 예측 → 실제 정상
TN 정상으로 예측 → 실제 정상
FN 정상으로 예측 → 실제 스팸

질병 검사

TP 질병 있음으로 예측 → 실제 질병 있음
FP 질병 있음으로 예측 → 실제 질병 없음
TN 질병 없음으로 예측 → 실제 질병 없음
FN 질병 없음으로 예측 → 실제 질병 있음

불량품 검사

TP 불량품으로 예측 → 실제 불량품
FP 불량품으로 예측 → 실제 정상 제품
TN 정상 제품으로 예측 → 실제 정상 제품
FN 정상 제품으로 예측 → 실제 불량품

Precision · Recall · Accuracy · F1

Precision = TPTP + FP = 이탈이라고 예측한 사람 중 실제 이탈자 비율
Recall = TPTP + FN = 실제 이탈자 중 찾아낸 비율
Accuracy = TP + TN전체 데이터
F1 = 2 × Precision × RecallPrecision + Recall

실제 이탈자가 10명, 비이탈자가 90명일 때 전부 비이탈이라고 예측해도 Accuracy는 90%입니다. 그러므로 Positive가 적은 문제에서는 Accuracy만으로 모델을 평가하면 안 됩니다.

같은 모델도 Yes 기준으로 무엇을 묻느냐가 다르다

이탈을 Yes로 정하면, Recall은 실제로 이탈한 Yes 고객들 중 모델이 Yes로 찾아낸 비율이다. 따라서 실제 Yes인데 예측 No로 나온 FN이 많으면 Recall이 낮아진다. 이 지표는 “이탈자를 얼마나 놓치지 않았는가?”를 묻는다.

Precision은 모델이 Yes라고 예측한 고객들 중 실제로 Yes였던 비율이다. 따라서 실제 No인데 예측 Yes로 나온 FP이 많으면 Precision이 낮아진다. 이 지표는 “이탈이라고 경고한 대상이 얼마나 믿을 만한가?”를 묻는다.

무엇을 우선할지는 오류의 비용으로 정한다.
실제 이탈자를 놓치는 손해가 크면 Recall을 우선한다. 실제로 이탈하지 않을 고객에게 할인·상담 같은 유지 조치를 잘못 주는 비용이 크면 Precision을 우선한다. 두 오류의 비용이 비슷하면 Precision과 Recall이 모두 높고 서로 한쪽만 낮지 않게 보는 F1을 중심 지표로 둘 수 있다.

Threshold를 바꾸면 무엇이 달라지는가?

변경일반적인 영향비즈니스 의미
Threshold를 높임Precision 상승 가능, Recall 하락 가능확실한 대상만 조치하지만 실제 이탈자를 더 놓칠 수 있음
Threshold를 낮춤Recall 상승 가능, Precision 하락 가능더 많은 이탈자를 찾지만 불필요한 조치가 늘 수 있음
지표는 업무 비용과 연결해야 합니다.
쿠폰 비용이 매우 크면 FP를 줄이는 Precision이 중요할 수 있고, 고가 고객의 이탈을 놓치는 손해가 크면 FN을 줄이는 Recall이 중요할 수 있습니다.

4. 아무 패턴도 배우지 않는 Dummy Baseline

일반적인 모델은 X를 예측으로 바꾸는 계산 구조를 가진다. 학습할 때는 X_train으로 만든 예측과 정답지 y_train의 오차가 줄어들도록 그 구조 안의 가중치를 조절한다. 모델마다 표현할 수 있는 패턴의 형태가 다르며, y는 입력이 아니라 예측과 비교할 정답이다.

DummyClassifier는 예외적인 기준 모델입니다.
Feature X의 패턴을 학습하거나 일반 모델처럼 Feature 가중치를 맞추지 않습니다. y_train의 정답 분포만 사용해, 실제 모델이 최소한 넘어야 할 기준을 만듭니다.

most_frequent와 stratified

전략동작
most_frequenty_train에서 가장 많은 클래스 하나로 모든 예측을 고정한다.
stratifiedy_train의 클래스 비율을 확률로 사용해 무작위로 예측한다. 매번 클래스 개수를 정확히 같은 비율로 보장한다는 뜻은 아니다.

학습 데이터에서 선택하고 Validation에서 평가한다

from sklearn.dummy import DummyClassifier

dummy_model = DummyClassifier(
    strategy="most_frequent"
)

dummy_model.fit(
    X_train,
    y_train,
)
확인 항목실제 결과해석
classes_['No', 'Yes']정답에 존재하는 두 클래스
class_prior_[0.73464679, 0.26535321]Train의 No·Yes 비율

y_train에서 No가 가장 많았으므로 most_frequent는 X_valid 1,409개를 모두 No로 예측했다.

dummy_predictions = dummy_model.predict(
    X_valid
)

pd.Series(dummy_predictions).value_counts()
# No    1409
Train과 Validation의 역할 구분
가장 많은 정답이 No라는 선택은 y_train에서 한다. 그렇게 정한 규칙을 X_valid에 적용한 뒤, 실제 정답 y_valid와 비교해 성능을 평가한다.

predict() 결과가 1차원인 이유

scikit-learn의 단일 Target 분류에서 predict()는 보통 NumPy ndarray를 반환하며 Shape은 (n_samples,)다. Feature가 19개여도 고객 한 명마다 최종 정답 하나를 예측하므로 입력 Feature 수와 예측 출력 차원은 별개다.

출력일반적인 Shape
단일 Target predict()(n_samples,)
여러 Target을 동시에 예측하는 Multi-output(n_samples, n_outputs)
이진 분류 predict_proba()보통 (n_samples, 2)

Pandas Series는 1차원 값에 Label Index와 이름을 함께 가진다. pd.Series(dummy_predictions).value_counts()는 NumPy 배열을 Series로 감싼 뒤 값별 개수를 세기 위한 코드다. NumPy만 사용한다면 np.unique(dummy_predictions, return_counts=True)로도 확인할 수 있다.

Accuracy를 직접 계산해 기준을 재현한다

correct_predictions = (
    dummy_predictions == y_valid.to_numpy()
)

dummy_accuracy = correct_predictions.mean()

비교 결과는 예측이 맞으면 True, 틀리면 False인 Boolean 배열이다. 평균을 구할 때 True=1, False=0으로 계산되므로 전체 중 맞힌 비율이 Accuracy가 된다.

Dummy Accuracy = 0.7345635202271115 = 73.45635202271114%
사용자의 말로 해석
y_train에서 No가 가장 많아 most_frequent가 모든 예측을 No로 고정했다. 그래서 Validation에서는 실제 No인 비율만큼 맞았고 Accuracy가 약 73.456%가 나왔다.
Dummy 챕터 완료
무조건 다수 클래스만 예측해도 얻는 Accuracy를 실제로 재현했다. 이 값은 새 모델이 넘어야 할 최소 비교 기준이지, 회원 이탈 패턴을 학습한 결과가 아니다.
다음 단계
문자형 Feature와 숫자형 Feature를 서로 다르게 처리하는 전처리 Pipeline을 이해한 뒤 Logistic Regression을 같은 Train/Validation Split에서 학습한다. Accuracy뿐 아니라 Precision과 Recall도 Dummy와 비교한다.

4-1. Logistic Regression 결과를 표로 읽기

같은 Train/Validation 분할에서 전처리된 Feature를 Logistic Regression에 학습시킨 뒤, Validation 예측을 실제 정답과 비교했다. Accuracy는 80.55%로 Dummy Baseline 73.46%보다 약 7.10%p 높다. 다만 Accuracy 하나로는 실제 이탈자를 얼마나 놓쳤는지 알 수 없으므로, 혼동 행렬을 함께 읽는다.

학습된 점수 · 확률 · 최종 Label은 서로 다른 출력이다

LogisticRegression.fit(X_train_processed, y_train)은 Train Feature에서 y_train의 No·Yes를 구분하도록 가중치를 학습한다. 같은 Validation 입력이라도 어떤 메서드를 호출하느냐에 따라 출력의 뜻이 다르다.

메서드무엇을 돌려주는가
decision_function(X_valid_processed)제한 없는 원시 점수. 음수·양수 모두 될 수 있으며 아직 확률이나 Label이 아니다.
predict_proba(X_valid_processed)클래스별 확률. 이 실습의 클래스 순서는 ['No', 'Yes']이므로 두 번째 열이 Yes 확률이다.
predict(X_valid_processed)확률을 판정 기준과 비교한 최종 No 또는 Yes Label이다.

이진 분류에서 Yes 확률은 원시 점수 s에 sigmoid를 적용해 만든다.

Yes 확률 = sigmoid(s) = 11 + exp(−s)

첫 다섯 검증 입력에서 실제로 확인한 원시 점수 [-3.0338, 0.7709, -2.7705, -0.3978, -3.8216]에 sigmoid를 적용하면 Yes 확률 [0.04592, 0.68371, 0.05894, 0.40184, 0.02142]가 나온다. 이 값은 predict_proba(...)의 Yes 열과 np.allclose로 같음을 확인했다.

같은 입력을 세 단계로 읽는다.
decision_function은 “Yes 쪽으로 얼마나 기울었는가”라는 원시 점수, predict_proba는 이를 0과 1 사이의 Yes 확률로 바꾼 값, predict는 그 확률을 기준으로 고른 최종 클래스다. 그래서 Threshold를 바꾸는 실습에서는 먼저 확률 열을 보고, 최종 Label이 어떻게 달라지는지 확인한다.

confusion_matrix를 DataFrame 표로 만든 이유

from sklearn.metrics import confusion_matrix

confusion = pd.DataFrame(
    confusion_matrix(
        y_valid,
        logistic_predictions,
        labels=["No", "Yes"],
    ),
    index=["실제 No", "실제 Yes"],
    columns=["예측 No", "예측 Yes"],
)

confusion_matrix(y_valid, logistic_predictions)에서 첫 번째 입력 y_valid는 실제 정답이므로 행이 되고, 두 번째 입력 logistic_predictions는 모델 예측이므로 열이 된다. labels=["No", "Yes"]는 두 클래스의 행·열 순서를 No, Yes로 고정한다. index와 columns는 계산을 바꾸지 않고 사람이 읽을 표의 행·열 제목을 붙인다.

예측 No예측 Yes
실제 No926109
실제 Yes165209
  • 926: 실제 No를 No로 맞춘 수
  • 109: 실제 No를 Yes로 잘못 경고한 수 (FP)
  • 165: 실제 Yes를 No로 놓친 수 (FN)
  • 209: 실제 Yes를 Yes로 찾아낸 수 (TP)

Accuracy는 전체 네 칸 중 정답인 대각선 두 칸을 더한 비율이다.

Accuracy = 926 + 209926 + 109 + 165 + 209 = 1,1351,409 ≈ 80.55%

Yes를 기준으로 행과 열을 다르게 읽는다

실제 Yes 행은 실제 이탈자 전체 165 + 209 = 374명이다. 이 행에서 예측 Yes 209명을 고르면 “실제 이탈자 중 찾아낸 비율”이 된다.

Yes Recall = 209165 + 209 ≈ 55.88%

반대로 예측 Yes 열은 모델이 이탈이라고 경고한 전체 109 + 209 = 318명이다. 이 열에서 실제 Yes 209명을 고르면 “이탈이라고 한 예측을 얼마나 믿을 수 있는가”가 된다.

Yes Precision = 209109 + 209 ≈ 65.72%
행 하나나 열 하나는 전체 모집단이 아니다.
실제 Yes 행은 실제 Yes라는 조건으로 자른 374명이고, 예측 Yes 열은 모델이 Yes라고 한 조건으로 자른 318명이다. 네 칸을 모두 더한 1,409명이 전체 Validation 모집단이다.

F1은 한쪽만 높은 상태를 그대로 좋다고 보지 않는다

이번 Yes Precision과 Recall의 단순 평균은 약 60.80%이고, F1은 약 60.40%다.

Yes F1 = 2 × 65.72 × 55.8865.72 + 55.88 ≈ 60.40%

F1은 Precision과 Recall의 조화평균이다. 한쪽만 높고 다른 쪽이 낮으면 단순 평균보다 낮은 쪽의 문제를 더 반영한다. 따라서 단순 평균과 F1이 비슷하면서 둘 다 높다면, Precision과 Recall이 모두 높고 균형도 비교적 맞는 상태다. 반대로 둘이 비슷해도 값 자체가 낮으면 좋은 모델이라는 뜻은 아니다.

4-2. Decision Tree: 학습 대상을 질문으로 계속 나누는 Baseline

Decision Tree는 Logistic Regression처럼 모든 Feature를 한 번에 가중합하는 대신, 현재 학습 대상에게 하나의 질문을 던져 두 묶음으로 나누는 모델이다. 예를 들어 Contract_Month-to-month <= 0.5라는 질문의 답에 따라 한쪽과 다른 쪽으로 보낸 뒤, 각 묶음에서 다시 다음 질문을 고른다.

이번 Pipeline에서 데이터가 지나가는 순서

tree_pipeline = Pipeline(
    steps=[
        ("preprocessor", preprocessor_scaled),
        ("model", DecisionTreeClassifier(random_state=42)),
    ]
)

tree_pipeline.fit(X_train, y_train)
tree_predictions = tree_pipeline.predict(X_valid)
원본 입력X_train은 문자열 범주와 숫자 열을 함께 가진 고객 DataFrame이다.
전처리기preprocessor_scaled가 범주형은 One-Hot 숫자 열로, 숫자형은 StandardScaler 결과로 바꾼다.
트리 모델전처리된 숫자 Feature와 y_train의 No·Yes 정답을 이용해 질문 순서를 학습한다.
검증 예측X_valid도 같은 전처리 규칙을 거친 뒤, 각 고객이 질문 분기를 따라가 최종 No 또는 Yes Label 하나를 받는다.

Pipeline이 전처리와 학습을 한 모델로 합쳐 버린 것은 아니다. 원본 X를 넣었을 때 전처리기 → 트리를 정해진 순서로 호출하도록 묶은 관리자다. 따라서 Tree 자체가 문자열을 이해하는 것이 아니라, 앞 단계에서 숫자로 바뀐 Feature를 받는다.

노드는 “현재까지 같은 답을 따라온 고객 묶음”이다

루트 노드는 처음에는 Train 고객 전체다. 루트가 하나의 질문을 골라 답에 따라 두 묶음으로 나누면, 그 두 묶음이 자식 노드가 된다. 다음 질문은 전체 고객을 다시 보는 것이 아니라 각 자식 노드에 남은 고객만 대상으로 따로 고른다.

루트 노드Train 고객 전체에서 후보 질문들을 비교한다.
첫 분기선택된 질문의 예/아니오로 고객이 두 자식 노드에 나뉜다.
각 자식 노드그 노드에 남은 고객만 보고 다시 후보 질문을 비교한다.
마지막 잎 노드더 나누지 않으면 그 묶음에서 많은 Label을 최종 예측으로 사용한다.
45개 Feature가 45개의 트리를 만드는 것은 아니다.
한 노드에서 45개 전처리 Feature가 모두 질문 후보가 될 뿐이다. 그중 가장 잘 나누는 질문 하나만 고른다. 다음 노드에서는 같은 Feature를 다시 쓰거나 다른 Feature를 고를 수 있다.

질문 후보는 숫자 Feature에서 기계적으로 만들어진다

전처리가 끝난 뒤에는 Feature가 모두 숫자이므로 트리는 기본적으로 어떤 값 이하인가? 형태의 이진 질문을 시험한다. 사람이 질문 문장을 만들거나 “분포가 가장 큰 Feature”를 고르는 방식이 아니다.

전처리 뒤 Feature트리가 시험할 수 있는 질문사람이 읽는 뜻
Contract_Month-to-month (0 또는 1)Contract_Month-to-month <= 0.5?월 단위 계약이 아닌가? / 맞는가?
numeric__tenurenumeric__tenure <= t?StandardScaler 뒤 가입 기간 값이 학습된 경계 t 이하인가?
numeric__MonthlyChargesnumeric__MonthlyCharges <= u?StandardScaler 뒤 월 요금 값이 학습된 경계 u 이하인가?

One-Hot으로 만든 범주형 열도 결국 0과 1인 숫자 열이므로, 트리 입장에서는 <= 0.5 질문으로 처리된다. 이번 Pipeline의 숫자형 열은 StandardScaler를 이미 통과했으므로 Tree가 실제로 보는 경계도 원래의 개월·요금이 아니라 평균 0·표준편차 1 기준으로 바뀐 값이다. 원래 단위로 읽고 싶다면 학습된 경계를 Scaler의 평균과 표준편차로 되돌려야 한다.

“잘 나누는 질문”은 No·Yes가 얼마나 덜 섞였는지로 고른다

트리가 의미를 이해하거나 확률 모델이 되어 질문을 발명하는 것은 아니다. 현재 노드의 y_train 정답을 세고, 후보 질문마다 나눠 본 뒤 양쪽에서 No·Yes가 얼마나 한쪽으로 쏠리는지 비교한다. 기본 DecisionTreeClassifier는 이 섞임을 보통 Gini 불순도로 계산한다.

후보 질문 결과왼쪽 묶음오른쪽 묶음판단
변환된 tenure <= t?Yes 4명, No 1명Yes 1명, No 4명양쪽 모두 한 Label 쪽으로 치우쳐 잘 갈린다.
다른 후보 질문Yes 3명, No 2명Yes 2명, No 3명나눈 뒤에도 두 묶음이 섞여 있어 덜 유용하다.
현재 이해에 맞춘 한 줄
후보 질문을 전부 기계적으로 실험하고, 질문 뒤의 두 묶음에서 No·Yes가 가장 덜 섞이는 질문을 하나 고른다. 이것을 각 노드에서 반복한다.

질문을 무한히 붙이지 않도록 멈추는 이유

학습 데이터 한 명씩까지 계속 나누면 Train 정답을 외워 버릴 수 있다. 이런 상태는 Train에서는 좋아 보여도 처음 보는 Validation 고객에서는 성능이 떨어지는 과적합이다. 그래서 트리는 더 나눌 의미가 없거나, 사람이 정한 제한에 닿으면 잎 노드에서 멈춘다.

  • 현재 묶음의 Label이 전부 No 또는 전부 Yes여서 이미 순수할 때
  • 어떤 후보 질문을 써도 No·Yes 섞임이 더 줄지 않을 때
  • 현재 묶음의 샘플 수가 분기에 필요한 최소 수보다 작을 때
  • 사람이 max_depth 같은 제한을 설정해 최대 질문 단계에 닿았을 때
DecisionTreeClassifier(
    max_depth=3,
    min_samples_leaf=10,
    random_state=42,
)
  • max_depth=3: 한 고객이 통과할 질문 단계를 최대 3단계로 제한한다.
  • min_samples_leaf=10: 마지막 고객 묶음 하나에 최소 10명은 남아야 한다. 한두 명만 남도록 지나치게 쪼개는 것을 막는다.

실제 복잡도 제한 비교: Train을 더 맞춘다고 좋은 모델은 아니다

제한 없는 Tree의 실제 최대 깊이는 22, 최종 잎 노드 수는 1,106이었다. 즉 가장 깊은 고객 경로는 질문을 22번 통과하고, 질문이 끝나 최종 Label을 내리는 고객 묶음은 깊이가 서로 달라도 모두 합쳐 1,106개다.

trained_tree = tree_pipeline.named_steps["model"]

print(trained_tree.get_depth())
print(trained_tree.get_n_leaves())

tree_pipeline.named_steps["model"]은 Pipeline에서 이름을 model로 붙였던 두 번째 단계를 꺼낸다. fit()이 끝난 뒤이므로 이 객체는 이미 질문 구조를 학습한 DecisionTreeClassifier다. get_depth()는 루트에서 가장 깊은 잎까지의 최대 질문 수를, get_n_leaves()는 깊이가 서로 달라도 더 이상 자식 질문이 없는 모든 최종 잎의 개수를 센다. 가장 아래 한 층의 잎만 세는 것이 아니다.

제한 없는 Tree도 Train 100%가 아니었던 이유
customerID를 제외한 Train Feature가 완전히 같은데 정답은 No·Yes로 충돌하는 묶음이 실제로 11개 있었다. 같은 숫자 Feature를 받은 Tree는 이 고객들을 서로 다른 질문으로 가를 수 없으므로, 각 묶음의 소수 정답 11개를 틀려 Train Accuracy가 99.8048%에서 멈췄다.

같은 Train/Validation split과 random_state=42에서 Tree의 제한만 바꿔 비교했다. Train Accuracy는 학습 고객을 얼마나 맞췄는지, Validation Accuracy는 처음 보는 고객에게 얼마나 일반화하는지 보는 값이다. 따라서 모델 선택에서는 Validation 쪽을 우선한다.

Logistic과 Tree 중 무엇이 맞는지는 구조 가설과 검증으로 정한다

모델표현하는 방식먼저 시험하기 좋은 경우주의할 점
Logistic Regression각 Feature에 가중치를 주고 모두 더한 하나의 점수로 클래스를 가른다.Feature의 영향이 전체적으로 더해지는 비교적 단순한 경계인지 확인할 때, 해석 가능한 가중치와 안정적인 첫 Baseline이 필요할 때복잡한 조건 조합과 구간별 반응은 직접 Feature를 만들지 않으면 놓칠 수 있다.
Decision TreeFeature ≤ 경계? 질문을 이어 붙여 조건 조합과 구간을 만든다.특정 조건 조합, 비선형 구간, 사람이 읽을 수 있는 분기 규칙이 중요할 때깊어지면 Train 사례를 외우기 쉬워 Validation과 클래스별 Metric을 반드시 확인해야 한다.

이 설명은 어떤 모델이 항상 우수하다는 규칙이 아니다. 같은 Train/Validation split과 같은 Metric에서 실제로 비교하고, Accuracy뿐 아니라 중요한 클래스의 Precision·Recall과 오류 비용까지 본다. 이번 데이터에서는 Logistic의 Validation Accuracy가 더 높았고, 깊이 5 Tree는 Yes Recall이 낮아 Logistic을 현재 Baseline으로 유지했다.

이탈자 Yes를 기준으로 다시 읽기

깊이 5 Tree의 분류 보고서에서 No Recall은 약 0.88, Yes Recall은 약 0.57, Yes Precision은 약 0.63이었다. 즉 실제 Yes 100명 중 약 57명만 Yes로 찾아내고 약 43명은 놓친다. 이탈자를 놓치는 비용이 큰 문제라면 Accuracy가 약 0.80이어도 충분하다고 결론 낼 수 없다.

이번 Tree 실험의 최종 결론은 “Tree가 항상 나쁘다”가 아니다. Tree는 질문 깊이와 잎 크기라는 복잡도 제한에 따라 일반화 성능이 달라지고, 이번 데이터·설정에서는 깊이 5 Tree가 시험한 Tree 중 가장 좋았지만 Logistic Regression의 Validation Accuracy 80.5536%와 Yes 지표를 넘지는 못했다는 것이다.

DecisionTree 비교 실험 완료
기본 Tree의 과적합을 Train/Validation으로 확인하고, max_depth·min_samples_leaf를 바꿔 같은 Validation에서 비교했다. 이제 이 scikit-learn Baseline 단위를 닫고, 같은 Train/Validation·Metric 관점을 PyTorch nn.Module과 Optimizer 학습으로 연결한다.

5. 실제 업무는 지표를 근거로 한 반복 실험에 가깝다

1. 현재 평가Baseline과 오류를 확인한다.
2. 문제 발견어떤 집단에서 무엇을 틀리는지 찾는다.
3. 가설성능 저하의 원인을 하나 정한다.
4. 조사·변경Feature·알고리즘·설정을 하나 바꾼다.
5. 비교같은 Split과 Metric에서 다시 평가한다.

비교 가능한 실험을 위해 데이터 Split, Seed, Metric을 고정하고 한 번에 한 요인을 바꿉니다. “새 알고리즘을 사용했더니 좋아졌다”가 아니라 어떤 조건에서 어떤 지표가 얼마나 변했고 어떤 오류가 남았는지 기록해야 합니다.

문제 정의 → 데이터 준비 → Baseline → 학습 → 평가 → 오류 분석 → 가설 → 실험 → 비교

6. 오늘 내용에서 정확히 구분할 부분

Loss와 Metric

Loss는 Weight 학습에 사용하는 목적함수이고, Metric은 모델을 업무 관점에서 평가하는 수치입니다. 둘이 같을 필요는 없습니다.

Weight와 Hyperparameter

Weight는 모델이 학습하고, Learning rate·Tree depth·Threshold 같은 Hyperparameter나 운영 기준은 사람이 실험으로 선택합니다.

F1과 조화평균

같은 거리의 평균속도 예시는 조화평균이 등장하는 사례이지 F1 공식의 직접적인 증명은 아닙니다. F1은 Precision과 Recall 중 하나만 낮아도 점수가 크게 낮아지도록 조화평균을 사용합니다.

AUC와 Threshold

AUC가 높다고 특정 Threshold의 실제 업무 성과가 자동으로 좋다는 뜻은 아닙니다. 순위 능력과 최종 판정 성능을 구분해야 합니다.
