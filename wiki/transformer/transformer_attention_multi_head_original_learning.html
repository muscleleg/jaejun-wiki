Multi-Head Attention 계산 상세

Q·K·V를 Head로 나누고 Attention을 계산한 뒤 Token 기준으로 다시 합치는 Shape 흐름을 자세히 따라간다.

← Multi-Head Attention 학습 경로

이 예제는 Head 분리와 Shape 확인에 집중하기 위해 Projection 계산 대신 Q·K·V 결과를 직접 선언한 단순화된 실험이다. 실제 Transformer에서는 같은 입력을 서로 다른 nn.Linear에 통과시켜 Q·K·V를 만든 뒤 이 흐름으로 들어온다.

오늘 완성한 전체 흐름

1Q·K·V 준비
2각 Token의 특징 차원을 Head별 조각으로 분리
3Head별 Q @ Kᵀ → √head_dim Scaling → Softmax
4Attention Weight @ Value
5같은 Token의 Head 결과를 다시 모아 d_model로 병합

Head로 나눴다가 합쳐도 순서가 유지되는가?

Multi-Head Attention은 Token 자체를 여러 Token으로 쪼개는 연산이 아니다. 각 Token이 가진 특징 차원을 여러 Head 조각으로 나누어 같은 Token에 대해 여러 관점의 Attention을 계산하는 연산이다.

원래[batch, token, d_model] = [3, 4, 4]
의미문장 3개 · 문장마다 Token 4개 · Token마다 특징 4개
Head 설정num_heads=2, head_dim=2

한 Token의 특징 벡터가 [0, 1, 2, 3]이라면 Head 분리는 다음처럼 해석된다.

Token 1 = [0, 1, 2, 3]

Head 1 조각 = [0, 1]
Head 2 조각 = [2, 3]

view()는 숫자를 정렬하거나 섞지 않고 새로운 Shape으로 해석한다. transpose(1, 2)도 Token 축과 Head 축의 위치만 바꾼다. Attention 계산을 마친 뒤 축을 다시 되돌리고 reshape()하면 Head 조각은 원래 순서로 이어진다.

Head 1 결과 = [a, b]
Head 2 결과 = [c, d]

다시 병합 → [a, b, c, d]
[batch, token, d_model] → [batch, token, num_heads, head_dim]
→ [batch, head, token, head_dim]
→ 다시 [batch, token, d_model]

포지셔널 인코딩은 Head 계산에서 사라진 것처럼 보이는 이유

포지셔널 인코딩은 Head 분리 직전에 다시 더하는 값이 아니다. 보통 Token Embedding에 먼저 더해져 x가 되고, 그 x가 Q·K·V Projection의 입력이 된다.

x = token_embedding + positional_encoding

query = query_projection(x)
key = key_projection(x)
value = value_projection(x)

따라서 이후의 Q·K·V와 Head 조각에는 이미 다음 정보가 함께 들어 있다.

Token 의미

어떤 단어·토큰인가

+
위치 정보

문장 안에서 몇 번째 위치인가

핵심 정리 — Head 분리는 Token 순서를 없애지 않는다. Token 축은 계속 유지되고, 각 Token의 특징 차원만 Head별로 나뉜다. 포지셔널 인코딩도 버려지는 것이 아니라 x에 더해진 뒤 Q·K·V Projection을 거쳐 각 Head의 계산에 간접적으로 포함된다.

1. Query를 현재 셀에서 다시 선언하기

실습용 QueryToken 2개 · 차원 2개
import torch

query = torch.tensor([[
    [0.1, 0.2],  # Token 1
    [0.3, 0.4],  # Token 2
]])

print("query:")
print(query)
print("query shape:", query.shape)
query[batch, token, d_model] = [1, 2, 2]
Token 1[0.1, 0.2]
Token 2[0.3, 0.4]

실제 모델에서는 Q = x @ W_Q로 만들어지지만, 이번 셀에서는 Head Shape에 집중하기 위해 Query 결과값을 직접 만들었다.

2. Head 수와 Head 차원 계산

Head 크기 계산d_model = num_heads × head_dim
batch_size, token_count, d_model = query.shape

num_heads = 2
head_dim = d_model // num_heads

print("batch_size:", batch_size)
print("token_count:", token_count)
print("d_model:", d_model)
print("num_heads:", num_heads)
print("head_dim:", head_dim)

현재는 d_model=2, num_heads=2이므로 head_dim=1이다.

3. view()로 Head별 조각 만들기

Head split숫자는 그대로, Shape만 변경
query_split = query.view(
    batch_size,
    token_count,
    num_heads,
    head_dim,
)

print("query_split:")
print(query_split)
print("query_split shape:", query_split.shape)
변경 전[batch, token, d_model] = [1, 2, 2]
변경 후[batch, token, num_heads, head_dim] = [1, 2, 2, 1]

view()는 숫자의 값이나 순서를 계산으로 바꾸지 않고, 같은 숫자를 새로운 Shape으로 다시 해석한다. 이번 코드에서는 d_model 2 = num_heads 2 × head_dim 1이 되도록 Shape을 직접 지정했다.

view()와 reshape() — 이번 실습에서는 둘 다 같은 용도로 이해해도 된다. view()는 메모리가 연속적으로 배치되어 있어야 하고, reshape()는 필요하면 복사해서라도 Shape을 바꿀 수 있다.

4. “Token 조각이 늘었다”는 감각

Head로 나누었다고 문장의 Token 수가 늘어난 것은 아니다.

그대로인 것

Token 수 = 2개

대신
늘어난 것

Token × Head 조합 = 2 × 2 = 4개의 조각

Token 1
  Head 1 조각 → [0.1]
  Head 2 조각 → [0.2]

Token 2
  Head 1 조각 → [0.3]
  Head 2 조각 → [0.4]

따라서 “Token 하나를 Head 수만큼 조각내서 처리할 조각의 개수를 늘렸다”는 표현은 맞다. 다만 실제 Token 수와 전체 숫자 개수는 그대로다.

5. transpose(1, 2)로 같은 Head끼리 모으기

축 순서 변경Token 축과 Head 축 교환
query_heads = query_split.transpose(1, 2)

print("query_heads:")
print(query_heads)
print("query_heads shape:", query_heads.shape)
전[batch, token, head, head_dim]
후[batch, head, token, head_dim]
Head 1
  Token 1 → [0.1]
  Token 2 → [0.3]

Head 2
  Token 1 → [0.2]
  Token 2 → [0.4]

각 Head가 모든 Token의 자기 담당 특징 조각을 한꺼번에 볼 수 있도록 축을 바꾼다. 현재는 Token 수도 Head 수도 2라 Shape 숫자는 우연히 전후 모두 [1, 2, 2, 1]로 보이지만, 축의 의미와 숫자 배치는 달라졌다.

6. 4차원 Tensor에서 인덱스 일부만 지정하기

query_heads의 Shape은 다음과 같다.

[batch, head, token, head_dim] = [1, 2, 2, 1]

따라서 다음 코드는 4차원 전체를 선택한 것이 아니다.

query_heads[0, 0]

이는 Batch 0과 Head 0만 선택하고, 뒤의 Token과 head_dim 축은 남겨두는 코드다.

query_heads[0, 0]
== query_heads[0, 0, :, :]

결과 Shape: [token, head_dim] = [2, 1]
결과값:
[
    [0.1],  # Token 1
    [0.3],  # Token 2
]

숫자 하나를 선택하려면 인덱스 4개가 필요하다.

query_heads[0, 0, 0, 0]
→ Batch 0, Head 0, Token 0, 차원 0
→ 0.1

7. Key와 Value도 같은 방식으로 분리하기

Key·Value splitQ와 동일한 축 흐름
key = torch.tensor([[
    [0.5, 0.6],  # Token 1
    [0.7, 0.8],  # Token 2
]])

value = torch.tensor([[
    [10.0, 20.0],  # Token 1
    [30.0, 40.0],  # Token 2
]])

key_heads = key.view(
    batch_size, token_count, num_heads, head_dim
).transpose(1, 2)

value_heads = value.view(
    batch_size, token_count, num_heads, head_dim
).transpose(1, 2)

Q·K·V는 모두 다음 Shape으로 정렬된다.

[batch, head, token, head_dim] = [1, 2, 2, 1]

예를 들면 Head 1의 Value는 Token 1의 [10.0], Token 2의 [30.0]을 가지고, Head 2의 Value는 [20.0], [40.0]을 가진다.

실습 중 오타 — [30.0, 40,0]은 [30.0, 40, 0]처럼 숫자 3개로 해석된다. 다른 행의 숫자 2개와 길이가 달라 Tensor를 만들 수 없으므로 [30.0, 40.0]으로 고친다.

8. Head별 Q @ Kᵀ Score

Head별 내적각 Head마다 Query-Key 표 생성
scores_heads = torch.matmul(
    query_heads,
    key_heads.transpose(-2, -1),
)

print("scores_heads:")
print(scores_heads)
print("scores_heads shape:", scores_heads.shape)
query_heads[batch, head, query_token, head_dim]
key_heads.transpose(-2, -1)[batch, head, head_dim, key_token]
scores_heads[batch, head, query_token, key_token] = [1, 2, 2, 2]

Single-head에서는 [batch, query_token, key_token]였던 Score에 Head 축이 하나 추가됐다. 지금은 2 × 2 Score 표가 Head마다 하나씩, 총 2개 생겼다.

9. 왜 √head_dim으로 나누는가

Scaled Score현재 head_dim=1
import math

scaled_scores_heads = scores_heads / math.sqrt(head_dim)

print("head_dim:", head_dim)
print("scaled_scores_heads:")
print(scaled_scores_heads)

Head 하나의 Score는 head_dim개의 곱을 더해 만든다.

Score = q₁k₁ + q₂k₂ + ··· + qhead_dimkhead_dim

Q·K 원소의 분산이 대략 1이라고 가정하면 Score의 분산은 head_dim, 표준편차는 √head_dim 규모로 커진다. 따라서 Score / √head_dim으로 표준편차를 다시 약 1 규모로 맞춘다. 이번 예제는 head_dim=1이라 √1=1이고 값이 바뀌지 않는다.

초기화와 Scaling은 서로 다른 연산이다.
1 / √d_model 규모의 가중치 초기화는 많은 입력을 곱하고 더해 만든 Q·K 원소 하나의 크기를 안정화하는 쪽이다. Score / √head_dim은 Head 안에서 여러 Q·K 곱을 더해 커진 최종 Score의 표준편차를 안정화하는 쪽이다. Embedding에서 √d_model을 곱한 것을 취소하는 연산이 아니다.

10. Head별 Softmax와 dim=-1

Attention Weight마지막 Key 축의 합 = 1
attention_weights_heads = torch.softmax(
    scaled_scores_heads,
    dim=-1,
)

print("attention_weights_heads:")
print(attention_weights_heads)
print("shape:", attention_weights_heads.shape)
print(
    "Key 방향 합:",
    attention_weights_heads.sum(dim=-1),
)

Shape은 여전히 [batch, head, query_token, key_token]이다. dim=-1은 마지막 축인 Key 방향으로 Softmax를 적용한다는 뜻이다.

예시 한 Head:
[
    [0.3, 0.7],  # Query 1이 Key 1·2를 참고하는 비율
    [0.4, 0.6],  # Query 2가 Key 1·2를 참고하는 비율
]

sum(dim=-1)
→ [0.3 + 0.7, 0.4 + 0.6]
→ [1, 1]

합산 전 Shape이 [batch, head, query_token, key_token]이면 마지막 Key 축을 합산한 결과는 [batch, head, query_token]이다. 즉 각 Query가 Key에 배정한 비율의 합이 1인지 확인하는 검산이다.

11. Attention Weight와 Value의 가중합

Value 가중합각 Head의 출력 벡터 생성
head_outputs = torch.matmul(
    attention_weights_heads,
    value_heads,
)

print("head_outputs:")
print(head_outputs)
print("head_outputs shape:", head_outputs.shape)
attention_weights_heads[batch, head, query_token, key_token]
value_heads[batch, head, key_token, head_dim]
head_outputs[batch, head, query_token, head_dim] = [1, 2, 2, 1]

Query Token 0의 Weight가 a₀₀, a₀₁이라면:

Output₀ = a₀₀ × Value₀ + a₀₁ × Value₁

Value가 여러 차원이라면 각 차원에 같은 Attention Weight를 곱한 뒤 더한다. 관련도가 Value 안으로 들어가는 것이 아니라, 관련도를 가중치로 사용해 Value 벡터들을 섞어 새로운 출력 벡터를 만드는 것이다.

12. Head 결과를 Token 기준으로 다시 모으기

Head 축 되돌리기Token별 Head 조각을 이웃하게 배치
outputs_by_token = head_outputs.transpose(1, 2)

print("outputs_by_token:")
print(outputs_by_token)
print("outputs_by_token shape:", outputs_by_token.shape)
변경 전[batch, head, token, head_dim]
변경 후[batch, token, head, head_dim]

Head별로 흩어져 있던 결과를 같은 Token 아래에 모은다.

Token 1
  Head 1 결과 조각
  Head 2 결과 조각

Token 2
  Head 1 결과 조각
  Head 2 결과 조각

13. Head 조각을 다시 하나의 Token 벡터로 합치기

Head mergehead × head_dim → d_model
multi_head_output = outputs_by_token.reshape(
    batch_size,
    token_count,
    d_model,
)

print("multi_head_output:")
print(multi_head_output)
print("multi_head_output shape:", multi_head_output.shape)
병합 전[batch, token, head, head_dim] = [1, 2, 2, 1]
병합 후[batch, token, d_model] = [1, 2, 2]

num_heads × head_dim = d_model이므로 각 Token의 Head 조각들을 다시 붙이면 원래 Token 벡터와 같은 폭으로 돌아온다.

오늘의 최종 Shape 흐름

query
[batch, token, d_model]

↓ view

[batch, token, num_heads, head_dim]

↓ transpose(1, 2)

query_heads
[batch, head, token, head_dim]

↓ Q @ Kᵀ

scores_heads
[batch, head, query_token, key_token]

↓ √head_dim으로 Scaling → Softmax

attention_weights_heads
[batch, head, query_token, key_token]

[batch, head, query_token, head_dim]

오늘의 결론 — 각 Token의 특징 차원을 여러 Head 조각으로 나누고, Head마다 독립적으로 Token 간 관련도와 Value 가중합을 계산한 뒤, 같은 Token의 Head 결과들을 다시 하나의 d_model 벡터로 합치는 것이 Multi-Head Attention이다.

내 표현으로 다시 정리하기

지금까지의 흐름을 내가 이해한 말로 다시 연결하면 다음과 같다. 먼저 입력 x를 서로 다른 가중치 표에 통과시켜 Q·K·V를 만든다.

x → W_Q → Q
x → W_K → K
x → W_V → V
Q무엇을 찾을지 표현하는 중간 벡터
K각 Token이 어떤 정보인지 표현하는 중간 벡터
V관련도가 높을 때 실제로 가져올 정보

그 다음 Token을 쪼개는 것이 아니라, 각 Token의 특징 차원을 여러 Head로 나눈다. 예를 들어 하나의 Token이 [0, 1, 2, 3]이고 Head가 2개라면 다음처럼 나뉜다.

Head 1 조각 = [0, 1]
Head 2 조각 = [2, 3]

각 Head는 담당한 특징 조각을 사용해 독립적으로 다음 계산을 한다.

Q @ Kᵀ
→ Scaling
→ Softmax
→ Attention Weight @ V

그래서 Head마다 서로 다른 관련도와 Value 가중합이 만들어질 수 있다. 다만 가중치가 아직 랜덤인 초기 상태에서는 그 출력에 학습된 의미가 생긴 것은 아니다. 학습이 진행되면 각 Head가 서로 다른 패턴이나 관점을 잘 포착하도록 조정될 수 있다.

Head 결과와 multi_head_output

Head별 결과가 다음처럼 나왔다고 하자.

Head 1 결과 = [a, b]
Head 2 결과 = [c, d]

축을 Token 기준으로 되돌린 뒤 reshape()하면:

multi_head_output = [a, b, c, d]

이 결과는 여러 Head의 결과를 원래 d_model 폭에 맞춰 단순히 이어 붙인 중간 표현이다. reshape()는 값을 새로 계산하거나 의미를 부여하지 않고, 숫자의 배치와 Shape을 다시 해석한다.

순서는 유지된다. Token 축은 계속 Token 축으로 남고, view()와 transpose()는 정해진 축의 위치만 바꾼다. 다시 축을 되돌린 뒤 reshape()하면 Head 1 조각과 Head 2 조각이 원래 특징 차원 순서대로 이어진다. 따라서 Multi-Head Attention은 Token을 여러 Token으로 늘리는 작업이 아니다.

왜 multi_head_output에 다시 Output Linear를 적용하는가?

multi_head_output은 다음처럼 Head 결과가 나란히 있는 상태다.

Head 1 정보 | Head 2 정보 | ...

여기에 Output Projection W_O를 적용하면 단순히 이어 붙은 정보가 학습된 가중치로 다시 조합된다.

multi_head_output → W_O → projected_output

예를 들어 출력 한 차원은 Head 1의 정보와 Head 2의 정보를 함께 사용해 만들어질 수 있다.

새로운 출력 1
= Head 1 정보 일부
+ Head 2 정보 일부

따라서 reshape()와 Output Linear는 서로 다른 역할을 한다.

reshape값을 바꾸지 않고 Head 결과를 원래 폭으로 이어 붙임
W_O Linear이어 붙인 특징들을 학습된 가중치로 다시 섞고 변환함

Output Projection은 보통 Shape을 바꾸지 않는다.

[batch, token, d_model] → W_O → [batch, token, d_model]

Linear가 의미를 부여한다는 말의 정확한 뜻

Linear가 각 행에 사람이 정한 의미를 직접 넣는 것은 아니다. 입력 특징들을 서로 다른 비율로 섞어 새로운 특징을 만든다.

x = [x₁, x₂]

y₁ = x₁ × w₁₁ + x₂ × w₁₂
y₂ = x₁ × w₂₁ + x₂ × w₂₂

각 출력 차원은 입력 차원들의 새로운 조합이다. 학습이 끝난 뒤 이 조합이 유용한 패턴을 담게 되면 사람이 그 의미를 해석할 수 있지만, 처음부터 특정 행이 문법·위치·주제 같은 의미로 고정되어 있는 것은 아니다.

Q·K·V와 W_O는 어떻게 학습되는가?

Q·K·V와 W_O가 각각 정답을 직접 맞추는 것은 아니다. 최종 예측에서 계산한 Loss가 전체 연산을 거꾸로 통과하면서 모든 가중치에 Gradient를 전달한다.

최종 logits
→ Loss
→ loss.backward()
→ W_Q, W_K, W_V, W_O 모두 Gradient 계산
→ Optimizer가 모든 가중치 업데이트

따라서 Q·K·V Projection과 Output Projection은 서로 따로 정답을 맞추는 것이 아니라, 최종 예측 Loss를 함께 줄이는 방향으로 학습된다.

포지셔널 인코딩은 어디에 있는가?

포지셔널 인코딩은 Multi-Head 단계에서 사라진 것이 아니다. Attention보다 앞에서 Token Embedding에 이미 더해져 x가 되고, 그 x가 Q·K·V Projection의 입력이 된다.

x = token_embedding + positional_encoding

query = query_projection(x)
key = key_projection(x)
value = value_projection(x)
