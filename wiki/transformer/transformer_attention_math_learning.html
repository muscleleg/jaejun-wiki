Q·K 내적과 Scaling

Score 한 칸은 하나의 Query와 하나의 Key 벡터를 내적한 값이다.

한 칸의 ScoreSᵢⱼ = qᵢ₁kⱼ₁ + qᵢ₂kⱼ₂ + ··· + qᵢdₖkⱼdₖ

초기 상태에서 각 곱의 평균이 0에 가깝고 분산이 약 1이며 서로 독립이라고 단순화하면, d_k개를 더한 Score의 분산은 약 d_k, 표준편차는 약 √d_k 규모가 된다.

Scalingscaled_scores = scores / math.sqrt(d_k)임베딩에서 했던 스케일을 취소하는 것이 아니라, Q·K 곱을 여러 개 합쳐 커진 Score 분포를 안정화하는 연산이다.

Multi-Head에서는 전체 d_model이 아니라 Head 하나의 마지막 차원인 head_dim을 사용한다.

왜 Score의 표준편차가 √head_dim만큼 커지는가?

토큰 수와 head_dim은 서로 다른 역할을 합니다. 토큰이 2개이고 head_dim=2라면 Q와 K는 다음처럼 생각할 수 있습니다.

Query 토큰 1 = [q₁₁, q₁₂]
Query 토큰 2 = [q₂₁, q₂₂]

Key 토큰 1 = [k₁₁, k₁₂]
Key 토큰 2 = [k₂₁, k₂₂]

따라서 Score는 2×2 행렬이 됩니다. token_count는 Score 칸의 개수를 정하고, head_dim은 각 칸에서 몇 개의 곱을 더할지 정합니다.

Score[1, 1] = (q₁₁ × k₁₁) + (q₁₂ × k₁₂)
Score[1, 2] = (q₁₁ × k₂₁) + (q₁₂ × k₂₂)
Score[2, 1] = (q₂₁ × k₁₁) + (q₂₂ × k₁₂)
Score[2, 2] = (q₂₁ × k₂₁) + (q₂₂ × k₂₂)

이제 Score 한 칸만 놓고 보자.

A = q₁₁ × k₁₁
B = q₁₂ × k₁₂

Score[1, 1] = A + B

이 설명에서는 A와 B가 각각 평균 0, 분산 1이고 서로 독립적이라고 둡니다. 이것은 모든 실제 Q와 K에서 반드시 성립하는 자연법칙이 아니라, 일반적인 초기 분포의 크기를 분석하기 위한 통계적 전제입니다.

여러 입력과 여러 토큰 쌍에서 같은 위치의 Score를 반복해서 계산하면 Score 집단이 생깁니다. 이 Score의 평균이 0이면, 분산 공식은 각 Score를 제곱한 값들의 평균과 같은 모양이 됩니다.

Score² = (A + B)²
       = A² + 2AB + B²

A²의 평균 = 1
B²의 평균 = 1
AB의 평균 = 0  # 독립적이고 양수·음수가 상쇄됨

Score²의 평균
= 1 + 2 × 0 + 1
= 2

Score 평균이 0이므로 이 Score²의 평균이 Score의 분산입니다.

여기서 아래 첨자를 구분해야 합니다. 여러 입력·토큰 쌍에서 Score를 반복 계산하면 아래처럼 기록할 수 있습니다. 이때 아래 첨자는 차원 번호가 아니라 반복 계산 횟수입니다.

첫 번째 계산: Score₁ = A₁ + B₁
두 번째 계산: Score₂ = A₂ + B₂
세 번째 계산: Score₃ = A₃ + B₃
...

분산의 정의에 이 Score들을 그대로 대입하면:

Score 분산
= ((Score₁ - 0)² + (Score₂ - 0)² + (Score₃ - 0)² + ...) ÷ Score 개수
= (Score₁² + Score₂² + Score₃² + ...) ÷ Score 개수
= Score²의 평균

예를 들어 Score가 [2, 0, 0, -2]라면:

Score² = [4, 0, 0, 4]
Score²의 평균 = (4 + 0 + 0 + 4) ÷ 4 = 2
Score 분산 = 2
Score 표준편차 = √2

이것은 (A² + B²) ÷ 2와 다른 계산입니다. 전자는 (A+B)²를 여러 Score에 대해 평균낸 것이고, 후자는 Score를 만들기 전 두 곱의 제곱을 평균낸 것입니다.

Score 분산 = 2
Score 표준편차 = √2

즉, 더하기 전 곱 하나의 표준편차가 1이어도, 곱 두 개를 Score 안에서 더하면 Score 집단의 표준편차는 √2가 됩니다. 여기서 중요한 것은 곱 결과를 배열에 담기만 한 것이 아니라, Score를 만들기 위해 실제로 더했다는 점입니다.

head_dim=3이면 Score는 다음과 같이 세 곱을 더합니다.

A = Query 차원 1 × Key 차원 1
B = Query 차원 2 × Key 차원 2
C = Query 차원 3 × Key 차원 3

Score = A + B + C

각 곱의 제곱 평균은 1이고, 서로 다른 곱을 곱한 교차항의 평균은 0이므로:

Score 분산 = 1 + 1 + 1 = 3
Score 표준편차 = √3

일반적으로 head_dim=d_k라면:

Score = 분산 1인 독립적인 곱을 d_k개 더한 값
Score 분산 = 1을 d_k개 더한 값 = d_k
Score 표준편차 = √d_k

양수와 음수가 서로 상쇄되기 때문에 d_k배까지 커지지는 않고, 독립적인 변동이 더해지면서 전형적으로 √d_k배만큼 퍼집니다. 다만 모든 곱이 독립적이지 않거나 한 방향으로 고정되어 있다면 실제 표준편차가 정확히 √d_k가 되지는 않습니다.

Score 표준편차가 커진 상태에서 Softmax를 적용하면 Score 차이가 지나치게 크게 해석됩니다.

softmax([4, 1])
→ [0.9526, 0.0474]

softmax([16, 4])
→ [0.999994, 0.000006]

실제 관련도가 더 정확해진 것이 아니라, 차원 수 때문에 Score의 규모가 커졌다는 이유만으로 한쪽에 확률이 몰릴 수 있습니다. 그래서:

scaled_scores = scores / math.sqrt(head_dim)

으로 나누어 head_dim을 더한 데서 생긴 Score 분포의 증가분을 줄입니다. 이것은 임베딩에 √d_model을 곱한 것을 취소하는 연산이 아니라, Softmax 직전의 Score 규모를 안정화하는 별도의 보정입니다.

Mask와 Softmax

Mask는 Q나 K를 지우는 것이 아니라, 이미 계산된 Score 행렬에서 볼 수 없는 칸을 숨긴다.

scores = scores.masked_fill(
    mask == 0,
    float("-inf"),
)
attention_weights = torch.softmax(scores, dim=-1)
Padding Mask길이를 맞추려고 넣은 PAD Token을 참고하지 않게 한다.
Causal Mask현재 Query가 미래의 Key Token을 보지 못하게 한다.

dim=-1은 마지막 축인 Key 방향이다. 각 Query가 모든 Key에 배정한 비율을 따로 계산하므로 행별 합이 1이 된다.

[0.3, 0.7] → 1
[0.4, 0.6] → 1

e-∞는 0에 가까우므로 Mask된 칸의 Softmax 비율은 0이 된다.

Attention Weight와 Value

Attention Weight는 Query가 각 Key를 얼마나 참고할지 나타내는 비율이다. 이 비율을 Value 벡터에 곱해 더한다.

첫 번째 Query의 출력Output₁ = a₁₁ × Value₁ + a₁₂ × Value₂ + ···

따라서 Output은 “관련도 숫자” 자체가 아니라, 관련도를 가중치로 사용해 Value 벡터를 섞은 새로운 벡터다.

여기까지의 핵심 — Score는 Query-Key 관련도, Softmax 결과는 Key별 참고 비율, Value 가중합 결과는 그 비율을 반영한 새로운 Token 표현이다.
