Query는 문장 전체에 하나가 아니라 토큰마다 하나다

Self-Attention에서 입력 문장에 토큰이 n개 있으면 Query도 n개 있습니다. 문장 전체가 Query 벡터 하나를 갖는 것이 아니라, 문장 안의 각 토큰이 자기 Query 벡터 하나를 갖습니다.

토큰 3개인 문장토큰마다 Q·K·V 하나씩
[나는] [학교에] [갔다]

[나는]   → Query₁, Key₁, Value₁
[학교에] → Query₂, Key₂, Value₂
[갔다]   → Query₃, Key₃, Value₃
토큰 개수3
Query 개수3
Key 개수3
Value 개수3

각 Query가 하는 질문은 “현재 이 토큰은 문장 안의 어떤 토큰들을 얼마나 참고해야 하는가?”라고 이해할 수 있습니다. 따라서 Query 하나는 모든 Key와 비교하고, 토큰마다 이 비교를 반복합니다.

Q, K, V shape = [batch, token 개수, dimension] 토큰 n개 → Q n개 × K n개 → scores [n,n]
현재 예제의 “두 Query” — 입력 토큰을 2개로 가정했기 때문에 query=[1,2,2] 안에 Query 벡터가 2개 있습니다. 그래서 Attention weight도 첫 번째 Query 행과 두 번째 Query 행, 총 2행으로 나온 것입니다.
scaled_dot_product_attention.py현재 손코딩 범위
scores = torch.matmul(
    query,
    key.transpose(-2, -1),
)

d_k = query.size(-1)
scores = scores / math.sqrt(d_k)

Q @ Kᵀ가 만드는 것

[n, d_k] @ [d_k, n] → [n, n] scores[i, j] = i번 Query · j번 Key

내적 점수 하나는 같은 차원의 원소끼리 곱한 뒤 모두 더한 값입니다. 즉, [n,n] 전체를 한꺼번에 더하는 것이 아니라 점수 행렬의 각 칸마다 d_k개의 곱을 더합니다.

scores[i,j] = qᵢ₁kⱼ₁ + qᵢ₂kⱼ₂ + ... + qᵢdk kⱼdk

Self-Attention에서는 토큰 n개의 모든 조합을 비교하므로 결과는 토큰 개수만큼의 정사각 점수 행렬 [n,n]이 됩니다.

왜 √d_k로 나누는가?

앞의 Token Embedding에서는 작은 임베딩 원소에 √d_model을 곱해, 각 원소가 평균 0을 중심으로 표준편차 약 1인 규모가 되도록 키웠습니다. 이는 위치 인코딩과 더할 때 임베딩 정보가 묻히지 않게 하기 위한 원소 단위의 조절이었습니다. 이후 선형 투영으로 만든 Q와 K도 초기에는 각 원소의 분산이 대략 1인 규모를 유지한다고 가정합니다.

임베딩의 처음 예산Var(wᵣ)=1/d_model → E[||W||²]≈1
임베딩 확대× √d_model → Var(xᵣ)≈1, E[||x||²]≈d_model
Q·K 한 칸d_k개 곱을 더함 → 합의 Var ≈ d_k
점수 보정÷ √d_k → 점수 한 칸의 Var ≈ 1
두 종류의 ‘1’을 구분해야 합니다. 임베딩 초기화에서 목표로 삼은 1은 원소 하나의 분산이 아니라 E[||W||²], 즉 임베딩 벡터 전체의 제곱합 기댓값입니다. Attention에서 다시 목표로 삼는 1은 완성된 점수 한 칸의 분산입니다.

이번에 빠뜨렸던 연결고리: 분산에는 평균이 들어간다

분산은 값을 바로 제곱하는 공식이 아니라, 값에서 평균을 뺀 뒤 제곱한 값의 기댓값입니다.

Var(X) = E[(X - E[X])²] 현재 설명에서는 초기화 분포의 기댓값을 0으로 두었기 때문에 E[X]=0입니다.

따라서 평균이 0이라는 전제를 대입하면 다음처럼 단순해집니다.

Var(X) = E[(X - 0)²] = E[X²] 그래서 이 설명 안에서만 원소 제곱의 기댓값을 곧바로 분산으로 연결할 수 있습니다.
가장 중요했던 정정 — “분산합이니까 원소를 그냥 제곱한다”가 아닙니다. 원래는 자기 자신 - 평균을 제곱합니다. 다만 초기화에서 평균을 0으로 정했기 때문에 결과적으로 X²가 된 것입니다.

Q와 K의 곱도 왜 평균 0으로 보는가?

초기 상태에서 Q와 K의 각 원소가 평균 0에 가깝고 서로 독립적이라고 단순화하면 다음 관계를 사용할 수 있습니다.

E[qᵣ] ≈ 0, E[kᵣ] ≈ 0 E[qᵣkᵣ] = E[qᵣ]E[kᵣ] ≈ 0

따라서 각 곱 Xᵣ=qᵣkᵣ도 평균 0이라고 근사합니다. 이때 평균 0은 분산을 E[Xᵣ²]로 단순화하게 하고, 서로 독립적이라는 가정은 여러 곱을 더할 때 분산도 더할 수 있게 합니다. 두 조건의 역할은 서로 다릅니다.

임베딩 초기화부터 Attention 스케일링까지 한 번에 연결하기

  1. 임베딩 벡터 전체의 처음 예산을 1로 잡습니다.

    d_model=512라면 E[||W||²]≈1이 되도록 각 원소의 분산을 1/512, 표준편차를 1/√512로 정합니다. 여기서 1은 원소 하나의 분산이 아니라 벡터 전체 제곱합의 기댓값입니다.

  2. Positional Encoding에 묻히지 않도록 임베딩을 확대합니다.

    작은 임베딩 원소에 √512를 곱하면 각 원소의 표준편차는 1/√512 → 1, 분산은 1/512 → 1이 됩니다. 각 원소의 숫자를 정확히 1로 만드는 것이 아니라, 0을 중심으로 퍼지는 규모를 키우는 것입니다.

  3. Q와 K의 내적에서는 여러 차원의 곱을 한 칸에 합칩니다.

    Q와 K의 각 원소가 분산 약 1인 규모를 유지한다고 보면, d_k=512인 점수 한 칸은 분산 약 1인 곱 512개를 더합니다. 실제 점수가 512가 되는 것이 아니라, 그 점수 한 칸의 분산이 약 512가 됩니다.

  4. 커진 점수의 분산을 다시 1로 맞춥니다.

    scores / √512는 각 점수 칸에 1/√512를 곱하는 것과 같습니다. 분산에는 배율의 제곱이 적용되므로 512/(√512)²=1이 되어 Softmax에 들어갈 점수의 규모가 안정됩니다.

이번 복습에서 확정한 전체 이야기
임베딩 원소를 평균 0, 표준편차 1/√512로 초기화해 벡터 제곱합의 기댓값을 1로 만듭니다. 입력에서는 √512를 곱해 원소 표준편차를 1로 만듭니다. Q와 K의 각 곱도 평균 0, 분산 1이고 서로 독립적이라고 가정하면, 512개를 합친 Score의 실제 값이 512가 되는 것이 아니라 분산이 512, 표준편차가 √512가 됩니다. 그래서 Score를 √512로 나누어 표준편차를 다시 약 1로 맞춥니다.
이 문장의 적용 범위
평균 0·분산 1·독립은 ScaledDotProductAttention.forward()가 실행 중 직접 검사하거나 강제하는 조건이 아니라, √d_k의 이론적 근거를 설명할 때 사용하는 초기 상태의 근사 가정입니다. Multi-Head Attention에서는 512 대신 실제 query.size(-1)인 d_k를 사용합니다.
E[||W||²]≈1 → ×√d_model → Var(Q·K의 한 칸)≈d_k → ÷√d_k → Var(score)≈1 앞의 1은 임베딩 벡터 전체의 제곱합 기댓값이고, 마지막 1은 Attention 점수 한 칸의 분산입니다.
Single Head와 Multi-Head의 차이 — 한 개의 Head에서 d_model=d_k=512라면 앞에서 곱한 값과 뒤에서 나누는 값이 모두 √512로 보입니다. 하지만 Multi-Head Attention에서 512차원을 8개 Head로 나누면 각 Head의 d_k=64이므로 Attention 점수는 √64로 나눕니다. 따라서 두 연산은 같은 숫자를 무조건 곱했다가 취소하는 구조가 아닙니다.

이제 점수 한 칸을 S = X₁ + X₂ + ... + X_dk, 각 곱을 Xᵣ = qᵢᵣkⱼᵣ라고 놓겠습니다. 각 Xᵣ가 평균 0, 분산 약 1이고 서로 독립적이라고 보면, 합의 분산은 다음처럼 더해집니다.

Var(S) ≈ 1 + 1 + ... + 1 = d_k 이 식은 점수 S의 숫자가 d_k라는 뜻이 아니라, 점수 S의 분산이 d_k라는 뜻입니다.

표준편차는 분산의 제곱근이므로 나누기 전 점수 한 칸의 표준편차는 약 √d_k입니다. 따라서 √d_k로 나누면, 다시 말해 1/√d_k를 곱하면 점수의 분산이 약 1로 돌아옵니다.

Var(S/√d_k) = Var(S)/(√d_k)² ≈ d_k/d_k = 1
곱의 합S = qᵢ₁kⱼ₁ + ... + qᵢdk kⱼdk
나누기 전Var(S)≈d_k · Std(S)≈√d_k
스케일링score[i,j] = S/√d_k = S×(1/√d_k)
나눈 후Var(score)≈1 · Std(score)≈1
두 연산은 취소 관계가 아닙니다. 임베딩의 ×√d_model은 위치 인코딩과 합치기 전에 벡터의 각 원소를 키웁니다. Attention의 ÷√d_k는 Q와 K의 원소 d_k개를 곱해 모두 더한 뒤, 그렇게 완성된 점수 한 칸을 줄입니다. 앞에서는 원소의 규모를 맞추고, 뒤에서는 합산 때문에 커진 점수의 분산을 맞춥니다. 또한 Multi-Head Attention에서는 보통 d_k=d_model/헤드 수이므로 두 제곱근의 숫자도 같지 않을 수 있습니다.
잘못 이해하기

scores / √d_k가 모든 내적 점수를 숫자 1로 만드는 것은 아닙니다.

→
정확한 이해

Q와 K의 곱의 합이 대체로 크기 1 정도로 분포하도록, 내적 점수들의 표준편차를 약 1로 맞춥니다.

한 문장 결론 — scores = scores / math.sqrt(d_k)는 Q와 K의 곱의 합을 각각 정확히 1로 만드는 코드가 아니라, 차원 수 때문에 커진 내적 점수의 일반적인 크기를 약 1 규모로 되돌리는 코드입니다.

Mask가 있다면 사용할 수 없는 점수를 없앤다

mask 적용1은 허용 · 0은 차단
if mask is not None:
    scores = scores.masked_fill(
        mask == 0,
        float("-inf"),
    )

if mask is not None은 mask가 실제로 전달됐을 때만 아래 코드를 실행한다는 뜻입니다. mask=None이면 아무것도 채우지 않고 기존 scores를 그대로 사용합니다.

mask 없음mask=None → if 블록을 건너뜀 → scores 유지
mask 있음mask==0인 위치를 찾음 → 같은 위치의 scores를 -∞로 변경
예시일부 점수만 무효화
scores = [
    [3, 2, 5],
    [1, 4, 6],
]

mask = [
    [1, 0, 0],
    [1, 1, 0],
]

적용 후 scores = [
    [3, -∞, -∞],
    [1,  4, -∞],
]

masked_fill은 mask 자체를 채우는 함수가 아닙니다. mask가 0인 칸을 기준으로 scores의 같은 칸을 -∞로 채웁니다. 다음 단계에서 softmax를 적용하면 e-∞=0이므로 해당 위치의 Attention 비율이 0이 됩니다.

Causal Mask

Decoder가 아직 생성하지 않은 미래 토큰을 보지 못하도록 위쪽 삼각 영역을 0으로 만듭니다.

또는
Padding Mask

문장 길이를 맞추기 위해 추가한 PAD 토큰을 Attention 대상에서 제외합니다.

구분 — 이 코드는 Causal Mask를 직접 만드는 코드가 아닙니다. 다른 곳에서 만든 Causal Mask나 Padding Mask를 전달받아, 0으로 표시된 점수만 무효화하는 공통 적용 코드입니다.

Padding Mask는 길이를 맞추기 위해 넣은 PAD를 숨긴다

하나의 배치에는 길이가 다른 문장들이 들어올 수 있습니다. 하지만 하나의 Tensor로 묶으려면 문장들의 Token 길이가 같아야 하므로, 짧은 문장의 뒤에 특별한 [PAD] Token을 채웁니다.

Padding 전과 후배치의 길이 통일
Padding 전
문장 1: [나는] [학교에] [갔다]
문장 2: [안녕]

Padding 후
문장 1: [나는] [학교에] [갔다]
문장 2: [안녕] [PAD] [PAD]

Padding mask
문장 1: [1, 1, 1]
문장 2: [1, 0, 0]
1실제 Token → Attention에서 참고 가능
0길이를 맞추려고 넣은 PAD → Attention에서 참고 금지

[PAD]는 실제 문장 정보가 아니므로 다른 Query들이 해당 위치의 Key와 Value를 참고하면 안 됩니다. Padding Mask가 0인 Key의 Score를 -∞로 바꾸고, Softmax가 그 Attention weight를 0으로 만들어 PAD의 Value가 최종 가중합에 들어오지 않게 합니다.

현재 실험: 두 Query 모두 두 번째 Token을 보지 않는다

현재 작은 실험에서는 Token이 2개이고, 두 번째 Token을 [PAD]라고 가정합니다.

테스트용 Mask두 번째 Key 열 전체 차단
Token: [실제 Token, PAD]

mask = torch.tensor([[
    [1, 0],  # Query 1: Key 1 허용, Key 2(PAD) 차단
    [1, 0],  # Query 2: Key 1 허용, Key 2(PAD) 차단
]])

Mask의 행은 Query이고 열은 Key입니다. 따라서 두 행이 모두 [1,0]이라는 것은 두 Query 모두 첫 번째 Key만 보고 두 번째 Key인 PAD는 보지 말라는 뜻입니다.

mask shape = [batch=1, query=2, key=2] 두 번째 Key 열의 Score → -∞ → Attention weight 0

현재 Value가 V₁=[10,0], V₂=[0,20]라면 Mask 적용 후에는 두 Query 모두 V₂를 전혀 참고하지 못합니다. 따라서 Attention weight는 두 행 모두 [1,0]이 되고, 두 출력도 모두 [10,0]이 될 것으로 예상할 수 있습니다.

왜 처음에 낯설었는가? — 이 Mask를 처음 제시할 때 두 번째 Token을 PAD로 가정한다는 설명이 생략되었습니다. 아무 이유 없이 두 번째 Token을 막는 Mask가 아니라, [실제 Token, PAD]라는 상황을 검증하기 위한 Padding Mask 실험입니다.

Causal Mask도 실제 Tensor로 검증했다

Padding Mask 실험 다음에는 첫 번째 Query만 미래의 두 번째 Token을 보지 못하게 하는 Causal Mask를 적용했습니다. 두 번째 Query는 이미 두 Token 위치까지 도달했으므로 첫 번째와 두 번째 Key를 모두 볼 수 있습니다.

Causal Mask미래 위치만 차단
causal_mask = torch.tensor([[
    [1, 0],
    [1, 1],
]])

causal_output, causal_attention_weights = attention(
    query,
    key,
    value,
    mask=causal_mask,
)
실행 결과가린 위치만 0
causal_attention_weights = [
    [1.0000, 0.0000],
    [0.3302, 0.6698],
]

causal_output = [
    [10.0000,  0.0000],
    [ 3.3024, 13.3952],
]
실험 결론 — 첫 번째 Query에서는 미래 Key의 비율만 0이 되었습니다. 두 번째 Query의 행은 가려지지 않았으므로 Mask 적용 전과 같은 [0.3302, 0.6698]을 유지합니다. 즉 전체 행을 없애는 것이 아니라 Mask가 0인 칸만 사라집니다.

Mask는 Q와 K를 0으로 만드는 연산이 아니다

Padding Mask를 적용해도 원래 query와 key Tensor는 바뀌지 않습니다. 먼저 원래 Q와 K로 모든 내적 Score를 계산하고 √d_k로 나눈 다음, 완성된 Score 행렬에서 Mask가 0인 칸만 -∞로 바꿉니다.

현재 숫자 예시Q·K는 유지 · Score만 변경
query = key = [

Softmax는 단순한 값 ÷ 합이 아니다

Softmax는 원래 숫자를 바로 전체 합으로 나누지 않습니다. 먼저 각 Score를 eˣ로 바꾼 뒤, 변환된 값들의 합으로 나눕니다.

softmax(xᵢ) = eˣⁱ ÷ (eˣ¹ + eˣ² + ...)
행별 Softmax유효한 Key 하나만 남음
첫 번째 행
softmax([0.707, -∞])
→ [e⁰·⁷⁰⁷, e⁻∞]
→ [2.028, 0]
→ [1, 0]

두 번째 행
softmax([0, -∞])
→ [e⁰, e⁻∞]
→ [1, 0]
→ [1, 0]
Score가 0

e⁰=1이므로 정상적인 참고 후보입니다. 예를 들어 softmax([0,0])=[0.5,0.5]입니다.

Attention weight가 0

참고하지 않는다는 뜻입니다. Mask로 Score를 -∞로 만들어야 e⁻∞=0이 됩니다.

한 문장 결론 — Mask는 Q와 K를 0으로 만드는 것이 아니라 QKᵀ로 만든 Score의 금지된 칸을 -∞로 바꾸며, Softmax는 남아 있는 Key들 사이에서 참고 비율의 합을 다시 1로 만듭니다.

왜 Mask에 큰 음수가 아니라 -∞를 넣는가?

지수함수 eˣ는 입력이 작아질수록 0에 가까워집니다. 유한한 음수의 결과는 매우 작아도 정확히 0은 아닙니다.

지수함수의 감소유한한 음수와 -∞의 차이
e⁻¹⁰  ≈ 0.000045     # 매우 작지만 0은 아님
e⁻¹⁰⁰ ≈ 3.72 × 10⁻⁴⁴ # 더 작지만 여전히 0은 아님

lim eˣ = 0
x→-∞

따라서 Softmax에서는 e⁻∞ = 0으로 다룬다.

-∞는 “0에 가까운 임의의 숫자”가 아니라, 입력이 끝없이 작아질 때 eˣ가 향하는 극한을 나타냅니다. 따라서 Mask된 위치는 Softmax의 분자에서 정확히 0이 되어 참고 비율을 받지 않습니다.

softmax([0.707, -∞]) → [e⁰·⁷⁰⁷, e⁻∞] → [2.028, 0] → [1, 0]
실제 컴퓨터 계산 — 부동소수점에서는 충분히 큰 음수를 사용해도 지수함수 계산이 underflow되어 0이 될 수 있습니다. 하지만 코드에 float("-inf")를 넣으면 “이 위치는 확실히 금지한다”는 의도를 직접 표현할 수 있습니다.

Softmax로 Key별 참고 비율을 만든다

softmax마지막 차원 기준
attention_weights = F.softmax(
    scores,
    dim=-1,
)

먼저 각 Query는 모든 Key와 점수를 계산합니다. Softmax는 Query 한 행씩, 각 점수에 지수함수 eˣ를 적용한 뒤 그 행의 전체 합으로 나누어 비율을 만듭니다.

softmax(xᵢ) = eˣⁱ / Σeˣʲ 각 Query 행의 attention_weights 합 = 1
행별 계산Q마다 Attention 예산 1

softmax는 함수의 이름이고, attention_weights는 그 함수를 scores에 적용해서 얻은 결과 행렬입니다.

dim=-1은 마지막 차원을 뜻한다

PyTorch에서 음수 차원 번호는 뒤에서부터 셉니다. dim=-1은 마지막 차원, dim=-2는 뒤에서 두 번째 차원입니다.

scores shape[batch, head, query_token, key_token]
마지막 차원key_token
dim=-1각 Query가 가진 모든 Key 점수를 가로 방향으로 softmax
한 문장 결론 — F.softmax(scores, dim=-1)은 각 Query가 모든 Key에 줄 참고 비율을 마지막 차원에서 계산하며, 각 Query 행의 비율 합은 1이 됩니다. mask로 -∞가 된 위치의 비율은 0이 됩니다.

왜 Tensor가 3차원인가?

문장 하나만 보면 Attention weight는 [n,n] 행렬입니다. PyTorch에서는 여러 문장을 한 번에 처리하기 위해 맨 앞에 Batch 차원을 둡니다.

attention_weights[0]첫 번째 Batch의 [Query, Key] 행렬

attention_weights[0,0,0]첫 번째 Query가 Token1에 준 비율 0.5084
value[0,0]첫 번째 Batch의 Token1 Value 벡터 전체 [0.1052, -0.3093]
value[0,0,0]Token1 Value 벡터의 첫 번째 좌표 0.1052
헷갈렸던 구분 — value[0,0]은 숫자 하나가 아니라 Token1의 Value 벡터 전체입니다. Attention weight 하나는 특정 Value 좌표 하나가 아니라 해당 Token의 Value 벡터 모든 차원에 곱해집니다.
수동 검산가중합이므로 두 항을 더함
manual_output_1 = (
    attention_weights[0, 0, 0] * value[0, 0]
    + attention_weights[0, 0, 1] * value[0, 1]
)

Output₁ = 0.5084 × Value₁ + 0.4916 × Value₂ = 0.5084 × [0.1052, -0.3093] + 0.4916 × [-0.3062, 0.4331] ≈ [-0.0971, 0.0557]

첫 번째 좌표만 보면 0.5084×0.1052 + 0.4916×(-0.3062) ≈ -0.0971입니다. 두 번째 좌표도 같은 두 Attention weight를 사용해 계산하므로 약 0.0557이 됩니다.

+를 사용해야 하는 이유 — Attention은 각 Value를 참고 비율대로 모으는 가중합입니다. 두 번째 항 앞에 -를 쓰면 Value2의 기여를 빼는 전혀 다른 연산이 되어 attention_weights @ value와 일치하지 않습니다.
이번 실습의 결론 — attention_weights @ value는 각 Query가 Token별 Attention weight를 해당 Token의 Value 벡터 전체에 곱한 뒤 모두 더하여, 문맥이 반영된 새로운 출력 벡터를 만드는 연산입니다.

두 번째 Query가 첫 번째 Value도 사용하는 이유

Attention weight를 Batch 차원을 빼고 [Query, Key] 행렬로 보면 각 칸의 위치는 다음과 같습니다.

Attention weight 위치행은 Query, 열은 Key
             Key1   Key2
Query1        a1     a2
Query2        a3     a4
a3Q2와 K1에서 시작해 만들어진 비율
a4Q2와 K2에서 시작해 만들어진 비율
attention_weights[0,1,0]첫 Batch의 Q2 → K1 비율 = a3 = 0.4306
attention_weights[0,1,1]첫 Batch의 Q2 → K2 비율 = a4 = 0.5694

정확히는 a1부터 a4까지가 원래의 qᵢ·kⱼ 내적값 그 자체는 아닙니다. 내적 Score를 √d_k로 나누고 각 행에 Softmax까지 적용한 뒤 얻은 참고 비율입니다.

QKᵀ → √d_k로 Scaling → 행별 Softmax → attention_weights

Q2는 두 번째 Token이 만든 Query입니다. 그렇다고 두 번째 Token만 참고하는 것은 아닙니다. Q2는 K1과 비교해 Token1을 얼마나 참고할지 정하고, K2와 비교해 Token2를 얼마나 참고할지 정합니다.

두 번째 출력 수동 검산Q2의 행 a3, a4 사용
manual_output_2 = (
    attention_weights[0, 1, 0] * value[0, 0]
    + attention_weights[0, 1, 1] * value[0, 1]
)

print("직접 계산한 두 번째 출력:", manual_output_2)
print("matmul로 계산한 두 번째 출력:", output[0, 1])
print("같은가:", torch.allclose(manual_output_2, output[0, 1]))
# 예상: True
Output₂ = a₃ × Value₁ + a₄ × Value₂ = 0.4306 × [0.1052, -0.3093] + 0.5694 × [-0.3062, 0.4331] ≈ [-0.1291, 0.1135]

여기서 a3는 Token1의 Value 벡터 전체에, a4는 Token2의 Value 벡터 전체에 곱해집니다. Q2의 계산에 Value1이 들어가더라도 첫 번째 출력이 되는 것이 아닙니다. Token1의 정보를 두 번째 Token의 새 표현인 Output2로 가져오는 것입니다.

이번에 풀린 혼동 — attention_weights[0,1]은 두 번째 Query의 행입니다. 따라서 [a3,a4]를 사용해 a3×V1 + a4×V2를 계산하며, 그 결과는 두 번째 Token의 문맥 반영 출력인 Output2가 됩니다.

현재 작성한 Scaled Dot-Product Attention 전체 코드

Single-head Attention현재 구현 완료 지점
class ScaledDotProductAttention(nn.Module):
    def forward(self, query, key, value, mask=None):
        scores = torch.matmul(
            query,
            key.transpose(-2, -1),
        )

        d_k = query.size(-1)
        scores = scores / math.sqrt(d_k)

        if mask is not None:
            scores = scores.masked_fill(
                mask == 0,
                float("-inf"),
            )

        attention_weights = F.softmax(scores, dim=-1)
        output = torch.matmul(attention_weights, value)

        return output, attention_weights
코드 검사 결과 — 현재 노트북의 계산 순서와 반환값은 올바르며, 테스트에서 output=[1, 2, 2], attention_weights=[1, 2, 2], 각 Attention 행의 합이 1임을 확인했습니다. Mask가 0인 Key의 비율도 0이 되고 출력에서 제외됐습니다.
클래스 이름 확인 — 노트북의 클래스 이름도 정확한 용어인 ScaledDotProductAttention으로 수정되어 있습니다.
Mask Shape 조건 — masked_fill에 전달하는 mask는 scores와 브로드캐스트 가능한 Shape이어야 합니다. 예를 들어 Single-head의 scores=[batch, query_token, key_token]에 Padding Mask를 적용한다면 보통 [batch, 1, key_token] 형태로 맞춥니다.
