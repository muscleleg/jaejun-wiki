KV Cache를 실제로 전달하고
과거 input_ids를 다시 넣지 않는 이유

Prompt 전체를 처음 한 번 계산한 뒤에는 왜 새 Token ID 하나와 past_key_values만 모델에 전달하는지, A·B → C → D 예제와 실제 Cache Shape 변화로 연결합니다.

현재 이해도

과거 input_ids를 다시 넣지 않아도 Cache의 K·V로 과거 문맥을 사용할 수 있다는 점을 자신의 말로 정확히 설명했고, 새 Token 하나와 past_key_values를 전달해 Cache Token 축이 실제로 S → S+1이 되는 것을 확인했습니다.

검증 완료 4 / 4100%
  • ● 첫 Forward에서 Prompt 전체의 K·V가 Layer별 Cache에 저장된다고 설명합니다.
  • ● 다음 Forward의 input_ids와 past_key_values가 맡는 역할을 구분합니다.
  • ● 과거 ID 없이 새 ID 하나만 넣어도 전체 문맥을 사용하는 이유를 설명합니다.
  • ● Key Cache Shape [1,2,2,1] → [1,2,3,1]을 실제 출력으로 확인했습니다.
첫 Forward 다음 Token 선택 두 번째 Forward 새 Q·K·V 과거 ID가 필요 없는 이유 Cache Shape 두 ID 보관 흐름 결론

1. 첫 Forward에는 Prompt 전체를 넣습니다

Prompt의 Token을 [A,B]라고 하겠습니다. 처음에는 과거 Cache가 없으므로 모델이 A와 B의 문맥을 처음부터 만들어야 합니다. 따라서 첫 Forward에는 Prompt 전체의 input_ids=[A,B]를 전달합니다.

prompt = "I study"

fresh_input_ids = tokenizer(
    prompt,
    return_tensors="pt",
).input_ids.to(device)

prompt_outputs = model(
    input_ids=fresh_input_ids,
    use_cache=True,
)

prompt_cache = prompt_outputs.past_key_values

실제 Prompt "I study"의 입력 Shape은 [1,2]였습니다. 첫 Forward에서 모델은 A와 B의 Q·K·V를 계산하고, 다음 생성 Step에 다시 필요한 A와 B의 K·V를 Layer별 past_key_values로 반환합니다.

Prompt 입력 Shape = [1,2]

Layer 0 Key Cache Shape = [1,2,2,1]
                         [B,H,S,d]

2. 마지막 Logit에서 다음 Token C를 선택합니다

첫 Forward의 Logit에는 A 위치와 B 위치의 다음 Token 후보가 모두 들어 있습니다. 현재 Prompt 전체 다음에 올 Token을 고르려면 마지막 B 위치의 Logit만 사용합니다. 그중 가장 큰 값을 가진 Token ID를 선택하면 새 Token C가 됩니다.

last_prompt_logits = prompt_outputs.logits[:, -1, :]

next_token_ids = last_prompt_logits.argmax(
    dim=-1,
    keepdim=True,
)

# 실제 선택 결과
next_token_ids = [[16046]]  # Token C

여기까지의 전체 Token 순서는 [A,B,C]이지만, A와 B는 이미 첫 Forward에서 계산되어 Cache에 들어 있습니다.

3. 새 Token ID와 past_key_values를 함께 전달합니다

두 번째 Forward에는 input_ids=next_token_ids와 past_key_values=prompt_cache를 전달합니다. 두 인자는 서로 다른 역할을 맡습니다.

input_ids=[C]이번 Step에서 새로 Embedding하고 Q·K·V를 계산할 Token을 지정합니다.
past_key_values이전에 처리한 A와 B의 Layer별 K·V를 전달해 과거 문맥을 다시 계산하지 않고 사용하게 합니다.
next_outputs = model(
    input_ids=next_token_ids,      # [C], Shape [1,1]
    past_key_values=prompt_cache,  # A·B의 K·V
    use_cache=True,
)
따라서 모델에 실제로 전달하는 input_ids는 [C] 하나뿐이지만, Attention에서는 A·B·C 전체 문맥을 사용할 수 있다.

4. 두 번째 Forward에서는 새 Token C의 Q·K·V만 계산합니다

A와 B의 Hidden State에서 K·V를 만드는 계산은 첫 Forward에서 이미 끝났습니다. 두 번째 Forward에서는 새 Token C의 Embedding과 각 Layer의 새 Q_C·K_C·V_C만 계산합니다.

새 Query
Q_C

Attention에 사용하는 전체 Key
[K_A, K_B] Cache + K_C

Attention에 사용하는 전체 Value
[V_A, V_B] Cache + V_C

Q_C가 A·B의 과거 Key와 C의 새 Key를 함께 조회하고, 그 Attention 비율로 A·B·C의 Value를 섞어 C 위치의 출력을 만듭니다. 이 출력의 마지막 Logit에서 다음 Token D를 선택할 수 있습니다.

Q_C × [K_A,K_B,K_C]ᵀ
  → C가 A·B·C를 참고하는 Attention Score

Attention Weight × [V_A,V_B,V_C]
  → C 위치의 문맥 표현
  → 다음 Token D의 후보 Logit

5. 과거 input_ids를 다시 넣을 필요가 없습니다

No-cache 방식은 새 Token C가 붙을 때 [A,B,C] 전체를 다시 input_ids로 전달합니다. 그러면 A와 B의 Q·K·V까지 다시 계산합니다. KV Cache 방식은 A와 B의 K·V 결과를 이미 가지고 있으므로 [C]만 새 입력으로 전달합니다.

No-cache
첫 Step: [A,B]
다음 Step: [A,B,C]
→ A·B·C의 Q·K·V를 모두 다시 계산

KV Cache
첫 Step: input_ids=[A,B], cache 없음
다음 Step: input_ids=[C], cache=[A·B의 K·V]
→ C의 Q·K·V만 새로 계산

과거 input_ids가 필요 없다는 말은 과거 문맥을 버린다는 뜻이 아닙니다. A와 B라는 정수 ID 자체를 다시 Embedding부터 처리하지 않을 뿐, 그 ID들이 각 Layer를 통과해 만든 K·V 결과는 Cache로 계속 Attention에 참여합니다.

6. Cache의 Token 축이 실제로 S → S+1이 되었습니다

두 번째 Forward에 전달한 새 Token 입력 Shape은 [1,1]이었습니다. 모델이 반환한 Layer 0의 갱신된 Key Cache는 과거 A·B 두 Token 뒤에 C 한 Token의 Key가 추가되어 [1,2,3,1]이 되었습니다.

Prompt 입력 Shape          = [1,2]
새 Token C 입력 Shape     = [1,1]

처음 Layer 0 Key Cache    = [1,2,2,1]
갱신된 Layer 0 Key Cache  = [1,2,3,1]

[Batch, Head, Token, Head dim]
Token 축: 2 → 3, 즉 S → S+1

이 Shape 변화는 과거 [A,B]를 두 번째 input_ids로 다시 보내지 않았는데도, 반환된 Cache에는 A·B·C 세 Token의 Key가 모두 들어 있다는 직접적인 실행 증거입니다. 실제로 선택한 C의 Token ID는 16046이었습니다.

7. 계산용 input_ids와 Decode용 전체 ID 보관은 구분합니다

Cache 생성에서 모델 계산에 넣는 ID와, 나중에 전체 문장을 Decode하기 위해 보관하는 ID는 목적이 다릅니다. 모델에는 매 Step 새 Token 하나만 넣지만, 사용자에게 전체 생성 문장을 보여 주려면 전체 ID Sequence는 별도 Tensor에 계속 이어 붙여야 합니다.

# 모델 계산용: 이번 Step의 새 Token만 전달
step_input_ids = [C]
model(
    input_ids=step_input_ids,
    past_key_values=prompt_cache,
)

# Decode·출력용: 전체 Token 순서를 별도로 보관
generated_ids = [A,B]
generated_ids = [A,B,C]

# 다음 Logit에서 D를 선택한 뒤
step_input_ids = [D]
generated_ids = [A,B,C,D]

generated_ids 전체는 최종 Decode, 출력 표시, 종료 Token 확인 등에 사용할 수 있습니다. 그러나 그 전체 ID를 매번 모델의 input_ids로 다시 전달하면 Cache로 피하려던 과거 계산을 중복하게 됩니다.

실제 5-Token 반복 생성에서도 이 구분을 유지했습니다. 모델 입력은 첫 Step의 Prompt [1,2] 뒤부터 계속 새 Token 하나인 [1,1]이었고, Decode용 generated_ids는 Prompt 2개와 생성 Token 5개를 합쳐 [1,7]이 되었습니다. 동시에 Layer 0 Key Cache의 Token 축은 2 → 3 → 4 → 5 → 6으로 증가했습니다.

8. 결론

첫 Forward에서 Prompt 전체 A·B의 K·V를 Cache에 저장했기 때문에 다음 Forward에는 새 Token C 하나만 input_ids로 전달합니다. C의 새 Q가 Cache의 A·B Key와 새 C Key를 함께 조회하므로, 과거 ID를 다시 입력하지 않고도 A·B·C 전체 문맥으로 다음 Token D를 계산할 수 있습니다.

실제 실행에서도 새 입력은 [1,1]이었지만 Layer 0 Key Cache는 [1,2,2,1] → [1,2,3,1]로 늘었습니다. 이어 5개 Token 반복 루프에서 Cache Token 축이 2 → 6으로 증가하는 것을 확인했고, 같은 Prompt·Greedy·생성 길이의 No-cache와 KV Cache가 동일한 Token ID [40,2050,16046,16046,16046,16046,16046]과 동일한 문장을 생성했습니다. Latency와 Batch 처리량 비교는 현재 추론 관문의 다음 검증 항목으로 남아 있습니다.

  • KV Cache가 저장하는 Tensor와 GPT-2 QKV Projection
  • KV Cache가 Layer별·Head별 형태로 저장되는 이유
  • tiny GPT-2 Cache 전달 실행 기록
