Transformer detail · Mutable Cache

추론 전후 KV Cache는 같은 객체이고
내부 상태만 갱신된다

Cache의 Token 길이는 분명히 6 → 7로 변했는데 Forward 후 prompt_cache와 updated_cache에서 모두 7이 출력된 이유를 Python의 객체 참조와 제자리 갱신으로 증명합니다.

← Q·K·V Projection 학습 경로Cache와 input_ids 전달Cache 반환과 여러 새 Token
주제 첫 Cache 두 번째 Forward 객체 동일성 코드로 증명 둘 다 7로 보인 이유 변경 전 값 보존 결론

1. 주제

첫 Forward에서 Prompt 전체를 처리하면 Token 6개의 K·V가 들어 있는 Cache를 얻습니다. 이 Cache와 새 Token 하나를 두 번째 Forward에 전달하면 새 Token의 K·V가 추가되므로 실제 Cache Token 길이는 6 → 7로 변합니다.

추론 전 Cache Shape  = [2,2,6,1]
추론 후 Cache Shape  = [2,2,7,1]

[Batch, Head, Token, Head dimension]

그런데 두 번째 Forward가 끝난 뒤 아래 두 변수를 출력하면 모두 [2,2,7,1]이 나옵니다.

print(prompt_cache[0][0].shape)
print(updated_cache[0][0].shape)

# 둘 다 torch.Size([2,2,7,1])

이 결과는 추론 전후의 Shape이 같다는 뜻이 아닙니다. prompt_cache라는 변수가 추론 전 상태의 복사본을 보관하는 것이 아니라, Forward 과정에서 갱신된 동일한 Cache 객체를 계속 가리키기 때문에 발생합니다.

2. 첫 Forward에서 Cache 객체를 얻습니다

with torch.inference_mode():
    prompt_outputs = model(
        input_ids=input_ids,
        attention_mask=attention_mask,
        position_ids=position_ids,
        use_cache=True,
    )

prompt_cache = prompt_outputs.past_key_values

현재 Layer 0의 Key Cache Shape은 [2,2,6,1]입니다. Python 변수는 객체 자체를 복제해 담는 상자라기보다 객체에 연결된 이름으로 이해할 수 있습니다. 자바의 참조 변수와 비슷한 관점입니다.

prompt_cache
      │
      ▼
Cache 객체 X
Token 길이: 6

3. 같은 Cache 객체를 두 번째 Forward에 전달합니다

with torch.inference_mode():
    next_outputs = model(
        input_ids=next_token_ids,
        attention_mask=extended_attention_mask,
        position_ids=next_position_ids,
        past_key_values=prompt_cache,
        use_cache=True,
    )

이번 입력은 새 Token 하나입니다. 모델은 그 Token의 K·V를 계산하고 전달받은 Cache 객체의 내부 상태에 추가합니다.

추론 전 Cache
[A,B,C,D,E,F]

새 Token
[G]

추론 후 Cache
[A,B,C,D,E,F,G]

Token 길이: 6 → 7

4. updated_cache도 같은 객체를 가리킵니다

모델이 반환한 Cache를 새 변수에 저장해도 Cache 복사본이 자동으로 만들어지는 것은 아닙니다.

updated_cache = next_outputs.past_key_values
prompt_cache  ─┐
               ├→ 동일한 Cache 객체 X
updated_cache ─┘

Cache 객체 X의 현재 Token 길이: 7

자바식으로 비유하면 Cache updatedCache = promptCache;처럼 두 참조 변수가 같은 Heap 객체를 바라보는 상태입니다. 변수 이름이 다르다는 사실만으로 추론 전후의 복사본이 생기지는 않습니다.

5. 객체 동일성과 길이 변화를 코드로 증명합니다

먼저 두 번째 Forward 전에 Cache 길이를 정수로 저장합니다.

cache_length_before: int = (
    prompt_cache.get_seq_length()
)

그다음 두 번째 Forward를 실행하고 반환 Cache를 받습니다.

with torch.inference_mode():
    next_outputs = model(
        input_ids=next_token_ids,
        attention_mask=extended_attention_mask,
        position_ids=next_position_ids,
        past_key_values=prompt_cache,
        use_cache=True,
    )

updated_cache = next_outputs.past_key_values

cache_length_after: int = (
    updated_cache.get_seq_length()
)

is는 두 변수가 동일한 객체를 가리키는지 확인합니다. id()로 객체 식별값도 비교할 수 있습니다.

print(
    "동일한 Cache 객체:",
    prompt_cache is updated_cache,
)

print(id(prompt_cache))
print(id(updated_cache))

print("추론 전 Cache 길이:", cache_length_before)
print("추론 후 Cache 길이:", cache_length_after)

실제 실행에서는 다음 결과를 확인했습니다.

동일한 Cache 객체: True
추론 전 Cache 길이: 7
추론 후 Cache 길이: 8

이 실행에서 시작 길이가 6이 아니라 7이었던 이유는 바로 앞의 두 번째 Forward가 이미 같은 prompt_cache 객체에 새 Token 하나를 추가했기 때문입니다. 후속 확인 셀은 그 상태에서 새 Token을 다시 하나 처리했으므로 길이가 7 → 8로 증가했습니다. 첫 Prompt Forward를 다시 실행해 Cache를 6으로 초기화한 뒤 같은 검증을 실행하면 6 → 7을 확인할 수 있지만, 객체 동일성과 제자리 갱신을 증명하는 데에는 실제 7 → 8 결과로도 충분합니다.

객체의 동일성과 내부 상태의 동일성은 다른 질문입니다. 객체는 동일하지만 그 객체가 담는 K·V와 Token 길이는 Forward 과정에서 6 → 7로 변경됩니다.

6. Forward 후 두 Shape이 모두 7로 보인 이유

Forward 전에는 Cache 객체 X의 Token 길이가 6입니다. Forward 과정에서 같은 객체에 새 Token의 K·V가 추가된 뒤에는 Token 길이가 7이 됩니다.

Forward 전

prompt_cache
      │
      ▼
Cache 객체 X
Token 길이: 6


Forward 후

prompt_cache  ─┐
               ├→ Cache 객체 X
updated_cache ─┘
                  Token 길이: 7

Forward가 끝난 다음 prompt_cache와 updated_cache를 출력하면 두 이름 모두 현재의 객체 X를 읽습니다. 따라서 양쪽에서 갱신된 Shape [2,2,7,1]이 나옵니다.

prompt_cache라는 이름이 추론 전 상태를 보존하지는 않습니다. 이름은 그대로지만 그 이름이 가리키는 객체의 내부 상태는 이미 갱신됐습니다.

7. 추론 전 값을 비교하려면 호출 전에 보존해야 합니다

Forward가 끝난 뒤에는 같은 Cache 객체를 통해 변경 전 길이 6을 다시 읽을 수 없습니다. 따라서 길이나 Shape을 모델 호출 전에 별도의 불변 값으로 꺼내 둡니다.

cache_length_before: int = (
    prompt_cache.get_seq_length()
)

key_shape_before: tuple[int, ...] = tuple(
    prompt_cache[0][0].shape
)

Forward 후에는 현재 Cache에서 새 값을 읽습니다.

cache_length_after: int = (
    updated_cache.get_seq_length()
)

key_shape_after: tuple[int, ...] = tuple(
    updated_cache[0][0].shape
)

# cache_length_before = 6
# cache_length_after  = 7
# key_shape_before    = (2,2,6,1)
# key_shape_after     = (2,2,7,1)

정수와 Shape Tuple을 미리 저장하면 이후 Cache 객체가 갱신되어도 추론 전 값을 비교 근거로 유지할 수 있습니다.

8. 결론

추론 전 Cache Shape: [2,2,6,1]
추론 후 Cache Shape: [2,2,7,1]

prompt_cache  ─┐
               ├→ 동일한 Cache 객체
updated_cache ─┘

동일한 객체의 내부 Token 길이
6 → 7
추론 전 prompt_cache와 추론 후 updated_cache는 동일한 Cache 객체를 가리키며, 두 번째 Forward가 그 객체의 내부 K·V 상태를 Token 6개에서 7개로 갱신합니다. 따라서 변경 전 값을 비교하려면 Forward 전에 길이나 Shape을 별도로 저장해야 합니다.
