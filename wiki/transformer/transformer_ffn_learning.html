Attention과 FFN은 무엇이 다른가?

Attention
→ Token과 Token 사이의 정보를 섞음

FFN
→ Attention으로 모은 정보를 각 Token 내부에서 따로 가공함

입력이 다음처럼 두 Token으로 이루어졌다고 하자.

Token 1 = [a, b]
Token 2 = [c, d]

FFN은 Token 1과 Token 2를 서로 섞지 않고 각각 처리한다.

Token 1 [a, b] → 같은 FFN → 새로운 Token 1 벡터
Token 2 [c, d] → 같은 FFN → 새로운 Token 2 벡터
같은 네트워크를 공유한다 — Token마다 서로 다른 FFN을 새로 만드는 것이 아니다. 모든 Token에 동일한 Linear 가중치와 bias를 적용하되, 각 Token 벡터의 계산은 독립적으로 진행한다.

d_model → d_ff → d_model

Transformer의 FFN은 보통 Token의 마지막 특징 차원을 잠시 확장하고, Activation을 거친 뒤 원래 크기로 줄인다.

d_model
→ Linear로 d_ff까지 확장
→ ReLU 또는 GELU
→ Linear로 d_model까지 축소

현재 작은 실습에서는 다음 흐름이다.

2차원 → Linear(2, 4) → 4차원
      → Activation
      → Linear(4, 2) → 다시 2차원

중간 차원을 넓히면 Token의 정보를 더 많은 특징 조합으로 가공할 공간이 생긴다. 마지막에 다시 d_model로 줄이면 다음 Residual 연결에서 원래 입력과 Shape을 맞출 수 있다.

학습되는 것과 고정되는 것

두 Linear의 차원 구조는 모델을 만들 때 정하고, 학습에서는 그 안의 숫자가 조정된다.

고정되는 것
Linear(2, 4)의 입력·출력 차원
Linear(4, 2)의 입력·출력 차원

학습되는 것
두 Linear의 weight
두 Linear의 bias

PyTorch에서 실제 Weight Shape은 입력과 출력 순서를 뒤집어 저장한다.

Linear(2, 4).weight → [4, 2]
Linear(2, 4).bias   → [4]

Linear(4, 2).weight → [2, 4]
Linear(4, 2).bias   → [2]

최종 Loss에서 시작한 Gradient가 역전파되면 이 Weight와 bias가 함께 조정된다. 2 → 4 → 2라는 구조 자체가 학습 도중 2 → 8 → 2처럼 바뀌는 것은 아니다.

ReLU와 GELU는 같은 방식으로 자르지 않는다

ReLU는 음수를 완전히 0으로 자르고 양수는 그대로 통과시킨다.

ReLU(x) = max(0, x)

ReLU(-2) = 0
ReLU(-1) = 0
ReLU( 1) = 1
ReLU( 2) = 2

GELU는 음수를 전부 0으로 만들지 않는다. 특히 음수 입력을 크기에 따라 부드럽게 줄이므로 일부 음수는 작은 음수로 남고, 큰 음수는 0에 가까워질 수 있다. 양수도 원래 값을 그대로 복사하지 않고 크기에 따라 부드럽게 조절한다.

GELU(-1) ≈ -0.16
GELU( 1) ≈  0.84

중간 Activation이 없다면 Linear(2,4) → Linear(4,2)라는 두 선형변환은 결국 하나의 Linear로 합칠 수 있다. Activation이 두 Linear 사이에 비선형성을 넣어, 단순한 선형변환 하나보다 복잡한 특징 변환을 배우게 한다.

직접 비교해 확인한 표현 — “ReLU는 음수를 0으로 만들고, GELU는 0에 가깝게 만든다.” 이 방향은 맞다. 정확히는 ReLU가 모든 음수를 정확히 0으로 만들고, GELU는 음수를 부드럽게 줄여 작은 음수값을 남길 수 있으며 양수도 크기에 따라 조절한다.

Linear를 만드는 것과 값을 넣는 것은 별개다

ffn_expand = nn.Linear(
    in_features=2,
    out_features=4,
)

이 코드는 입력값을 이미 4차원으로 바꾼 것이 아니다. 2차원을 받아 4차원을 만드는 Linear 모듈을 준비하고, 그 안에 학습 가능한 Weight와 bias를 생성한다.

expanded_output = ffn_expand(
    normalized_output
)

이때 실제 normalized_output을 앞에서 만든 모듈에 넣어 계산한다.

normalized_output
→ ffn_expand의 weight와 bias로 계산
→ expanded_output

내부 계산을 단순하게 적으면 다음과 같다.

expanded_output
= normalized_output @ ffn_expand.weight.T
  + ffn_expand.bias
현재 이해한 표현 — “nn.Linear(2,4)로 Linear를 만들고, ffn_expand(normalized_output)에서 그 기계에 실제 값을 단순히 넣어 실행한 것이다.” Q Projection에서 모듈을 만든 뒤 query_projection(x)를 호출했던 것과 같은 구조다.

FFN 첫 Linear 실행 결과

현재 노트북에서 normalized_output을 ffn_expand에 실제로 넣어 다음 Shape 변화를 확인했다.

LayerNorm 출력 shape:
torch.Size([1, 2, 2])

FFN 확장 출력:
tensor([[[-0.3127, -0.2737,  1.1960,  0.1387],
         [-0.1453, -0.1580,  0.0040, -0.6528]]])

shape:
torch.Size([1, 2, 4])
확인한 Shape 흐름
[batch, token, d_model]
[1,     2,     2]

→ Linear(2, 4)

[batch, token, d_ff]
[1,     2,     4]

Batch 1개와 Token 2개는 그대로 유지되고, 각 Token에 같은 Linear(2,4)가 적용되어 마지막 특징 차원만 2에서 4로 확장됐다.

당시 검증 범위 — nn.Linear(2,4)는 모듈과 파라미터를 만드는 단계이고, ffn_expand(normalized_output)은 실제 Tensor를 넣어 계산하는 단계임을 설명했다. 실행 결과로 마지막 차원의 2 → 4 변화도 확인했다. ReLU와 GELU의 출력도 직접 비교했다. 이 시점에는 두 번째 Linear(4,2)와 Residual까지 연결한 전체 의미가 열린 질문이었다.

LayerNorm의 출력이 FFN으로 들어간다

현재 실습 흐름normalized_output = LayerNorm(x + Attention(x))contracted_output = FFN(normalized_output)

LayerNorm은 Residual 덧셈으로 커진 값을 단순히 작게 줄이는 작업이 아니다. 각 Token의 마지막 차원에서 평균과 퍼짐을 정돈하는 작업이다.

값이 크면 무조건 줄임  → 아님
값이 작으면 그대로 둠  → 아님

Token별 평균과 퍼짐을 정돈
→ 작은 값이 오히려 커질 수도 있음

따라서 FFN은 “작아진 값”을 받는 것이 아니라, Token마다 규모가 정돈된 현재 표현 normalized_output을 받는다고 이해하는 편이 정확하다.

2 → 4는 의미를 네 개로 확정하는 일이 아니다

d_model=2에서 d_ff=4로 확장한다고 해서 사람이 이름 붙일 수 있는 의미의 개수가 두 개에서 네 개로 늘어났다고 단정할 수는 없다.

첫 Linear는 Token의 두 입력값을 서로 다른 Weight 조합으로 섞어 네 개의 중간값을 만든다. 이 네 값은 FFN이 Token을 가공할 때 잠시 사용하는 더 넓은 작업공간이다.

Token [a, b]

→ 서로 다른 Weight 조합 네 개

→ [중간 특징1, 중간 특징2, 중간 특징3, 중간 특징4]
현재 잡을 표현 — “의미 네 개를 새로 만든다”보다 “각 Token을 더 넓은 중간 공간에서 여러 가중치 조합으로 가공할 여유를 만든다”가 가깝다.

음수는 노이즈라서 지우는 것이 아니다

Linear 출력의 음수라는 이유만으로 그 값이 노이즈이거나 쓸모없다는 뜻은 아니다. ReLU와 GELU의 핵심 목적은 두 Linear 사이에 비선형성을 넣는 것이다.

Activation이 없음
Linear(2,4) → Linear(4,2)
→ 하나의 Linear와 같은 종류의 변환으로 합칠 수 있음

Activation이 있음
Linear → ReLU/GELU → Linear
→ 하나의 Linear로 합칠 수 없는 변환

앞쪽 Linear의 Weight도 학습되므로, 학습 과정에서는 다음 Activation을 거친 뒤 유용하게 쓰일 중간 특징이 나오도록 그 Weight가 조정된다. 즉 모델은 “어떤 특징을 통과시키고 어떤 특징을 약하게 만들지”에 맞춰 앞 Linear까지 함께 바꾼다.

4 → 2로 줄인 뒤 왜 다시 더하는가?

두 번째 Linear는 네 개의 중간 특징을 다시 섞어 d_model=2 크기로 돌려보낸다.

[중간 특징1, 중간 특징2, 중간 특징3, 중간 특징4]
→ Linear(4, 2)
→ [FFN 수정값1, FFN 수정값2]

이 축소는 중간 특징을 버리고 원상 복구하는 일이 아니다. 네 중간 특징을 학습된 Weight로 조합해, 다음 Transformer 단계가 사용할 수 있는 d_model 크기의 결과로 만드는 과정이다.

contracted_output = FFN(normalized_output)

contracted_output은 기존 Token 표현을 완전히 교체할 최종 완성본보다, FFN이 현재 표현에 제안한 수정값으로 이해할 수 있다.

두 번째 Residual
= normalized_output + contracted_output

이 덧셈은 현재 표현 normalized_output을 보존하면서 FFN의 수정값을 반영한다. 또한 역전파 때 Gradient가 FFN을 통과하는 경로뿐 아니라 Residual 지름길을 통해서도 이전 표현으로 흐를 수 있게 한다.

두 값을 더하려면 Shape이 같아야 하므로 FFN의 마지막 Linear가 4 → 2로 줄여 contracted_output을 다시 [batch, token, d_model] Shape으로 맞춘다.

수식으로 연결한 전체 흐름y = LayerNorm(x + Attention(x))delta = W2(GELU(W1(y)))output = y + delta
현재 자기 말로 연결한 흐름 — “x + Attention을 정돈한 normalized 값과, 그 값을 FFN에 넣어 양수 중간 반응은 많이 통과시키고 음수 중간 반응은 억제한 뒤 나온 값을 합친다.” 이 설명은 전체 방향을 정확히 잡았다.

다만 Residual에 더하는 delta, 즉 contracted_output은 GELU 직후의 4차원 값 자체가 아니다. GELU로 부드럽게 선별된 중간 특징을 두 번째 Linear W2가 다시 섞어 d_model 크기로 만든 수정값이다.

GELU 직후
[선별된 중간 특징 4개]

→ W2 = Linear(4, 2)

contracted_output
[현재 표현에 더할 수정값 2개]

W2는 중간 특징을 학습된 양수·음수 Weight로 다시 조합하므로, GELU가 음수 반응을 억제했더라도 최종 contracted_output에는 다시 음수가 나올 수 있다.

검증 전 질문과 후속 결과

첫 Linear의 생성·호출, Shape 확장과 ReLU·GELU의 차이를 확인한 뒤, y → W1 → GELU → W2 → delta → y+delta의 개념 흐름을 자기 말로 연결했다. 당시에는 두 번째 Linear와 Residual이 현재 노트북의 실제 숫자에도 맞는지가 열린 질문이었다.

검증했던 질문 — Linear(4,2)의 contracted_output을 실제로 출력하고, normalized_output + contracted_output을 계산한 뒤 “현재 표현을 보존하면서 FFN 수정값을 더한다”는 설명이 숫자와 Shape에도 맞는지 확인한다.

실행 검증에서 확인한 결론

두 번째 Residual에서도 [1,2,2] Shape이 유지됐고, 이어지는 LayerNorm은 Token별 평균을 사실상 0, 분산을 1로 정돈했다. Dropout은 train()에서 원소를 독립적으로 끄고 살아남은 값을 보정하지만, eval()에서는 입력을 그대로 통과시킨다.

Attention
→ Residual + LayerNorm
→ Linear(d_model, d_ff) + GELU + Linear(d_ff, d_model)
→ Dropout
→ Residual + LayerNorm
→ [batch, token, d_model] 유지

이 연산들을 하나의 TransformerBlock.forward()로 묶어 입력·출력 Shape과 두 Residual의 역할까지 검증했다.

Tiny Decoder LM의 Causal Transformer Block 실행

후속 Tiny Decoder LM 실습에서는 미래 Key를 보지 못하게 하는 Causal Multi-Head Attention을 같은 Post-LN Block 흐름에 연결했습니다. 사용자는 실행 전에 “Causal Mask는 값을 마스킹 처리하는 것이지 차원이 바뀌지 않는다”고 설명했고, Block의 순서도 다음과 같이 자기 말로 연결했습니다.

입력 x [1, 3, 2]
→ Causal Multi-Head Attention
→ x + attention_output                 # 첫 Residual
→ LayerNorm                            # normalized_attention
→ Linear(2, 8)
→ GELU
→ Linear(8, 2)                         # FFN 수정값
→ normalized_attention + FFN 수정값   # 두 번째 Residual
→ LayerNorm
→ Block 출력 [1, 3, 2]

두 Linear는 마지막 특징 축만 2 → 8 → 2로 바꿉니다. 마지막에 다시 d_model=2로 돌아오기 때문에 두 번째 Residual을 더할 수 있고, batch 1개와 sequence 위치 3개는 전체 Block을 지나도 유지됩니다.

저장된 실행 Shape입력 hidden_states: [1, 3, 2]Block 출력: [1, 3, 2]Attention weights: [1, 2, 3, 3]

Attention weight Shape [1,2,3,3]은 배치 1개, Head 2개, Query 위치 3개, Key 위치 3개를 뜻합니다. Causal Mask는 이 Score 행렬에서 미래 Key 칸의 참고 비율을 0으로 만들지만 Query·Key 위치 축 자체를 없애지 않습니다. 따라서 Attention 결과와 Block 출력의 sequence 길이도 3으로 남습니다.

Block 출력:
[[[ 1.0000, -1.0000],
  [-1.0000,  1.0000],
  [ 1.0000, -1.0000]]]

이 숫자는 두 번째 LayerNorm까지 지난 각 Token의 최종 Block 표현입니다. Attention weight나 Token 확률이 아니며, Shape은 예측대로 [1,3,2]입니다.

당시 최소 구현의 경계와 후속 완료 — 기존 전체 Transformer Block 학습에서는 Attention·FFN 분기의 Dropout도 별도로 구현·검증했습니다. 이 Causal Block 셀은 연결 순서와 Shape을 작게 확인하기 위해 Dropout을 생략했습니다. 당시에는 Causal Block 한 번만 실행했지만, 이후 Tiny Decoder LM 최종 검증에서 LM Head·Loss 감소·다음 Token 반복 생성을 연결해 완료했습니다.
