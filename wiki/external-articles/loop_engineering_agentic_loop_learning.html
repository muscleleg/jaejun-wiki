1. Loop Engineering의 개념

Loop Engineering은 에이전트가 한 번 작업하고 끝나는 대신, 목표 상태에 도달할 때까지 실행과 검증을 반복하도록 만드는 설계 방식이다.

while True:
    agent.run()

이런 반복문 자체가 핵심은 아니다. 시스템은 다음 질문에 답할 수 있어야 한다.

상태현재 상태는 무엇인가?
다음 단계어떤 Agent를 실행할 것인가?
실패실패 원인은 구현·계획·분석 중 어디인가?
종료어떤 증거가 있으면 루프를 끝낼 것인가?

따라서 Loop Engineering은 다음 요소를 설계하는 일로 이해할 수 있다.

State + Role + Evaluation + Feedback + Retry + Stop Condition

2. 왜 Loop가 필요한가

단순한 사용 방식에서는 사람이 매번 결과를 검토하고 다음 프롬프트를 작성한다.

사람 → "구현해줘" → Agent → 구현
사람 확인 → "여기 틀렸어" → Agent → 수정

Agent의 구현 속도보다 사람의 검토 속도가 느리면 자동화의 이점이 줄어든다. Loop를 설계하면 프로그램이 다음 작업과 검증을 이어간다.

Run Loop
   ↓
Implement
   ↓
Verify
   ↓
FAIL → Fix → Verify
   ↓
PASS

3. Acceptance Gate: 언제 끝낼 것인가

“더 고칠 것이 있는가?”를 종료 조건으로 삼으면 여백, 변수명, 리팩터링처럼 계속 개선할 항목이 생겨 루프가 끝나지 않을 수 있다.

대신 사람이 완료 조건을 Gate로 정의한다.

G1 API 계약 동일
G2 비즈니스 로직 동일
G3 UI 동일
G4 URL 구조 동일
G5 Tracking Event 동일
G6 SEO 동일
G7 Design System 사용
종료 규칙 — G1부터 G7까지 모두 PASS이면 DONE, 하나라도 FAIL이면 해당 실패를 수정하고 다시 검증한다.

즉 질문은 “다 됐어?”가 아니라 “정의된 완료 조건을 모두 만족했는가?”가 되어야 한다.

4. Agent 역할과 Orchestrator

하나의 Agent가 분석·계획·구현·검증을 모두 맡기보다 역할을 나누면 각 단계의 책임과 입력·출력이 선명해진다.

Analyzer(input)   → Analysis
Planner(Analysis) → Plan
Implementer(Plan) → Code
Verifier(Code, Expected) → Evaluation
Analyzer원본의 UI·Logic·API·Tracking·SEO 요구사항 분석
Planner분석 결과를 구현 가능한 계획으로 변환
Implementer계획에 따라 코드를 수정하거나 실행
Verifier실제 Evidence를 수집하고 Acceptance Gate와 비교

Orchestrator는 전문 Agent보다 제어 흐름을 담당한다.

Orchestrator
 ├─ 다음 Agent 선택
 ├─ 전달할 Context 결정
 ├─ 실패 시 재시작 지점 선택
 ├─ 재시도 횟수 관리
 └─ 종료 조건 판정

5. Pipeline과 Agent Loop의 차이

단순 Pipeline은 항상 같은 방향으로 흐른다.

A → B → C → D

Agent 시스템은 실행 결과에 따라 다음 단계가 달라지는 State Machine 또는 Graph에 가깝다.

              Plan
               ↓
           Implement
               ↓
            Verify
        ↙       ↓       ↘
 Implement    Plan    Analysis

LangGraph 같은 프레임워크가 Graph 개념을 사용하는 이유도 작업이 성공·실패와 원인에 따라 다른 노드로 이동하기 때문이다.

6. 실패 원인별 Retry와 Rollback

Verifier가 FAIL을 반환했다고 항상 처음부터 다시 시작하면 안 된다. 실패 원인에 따라 가장 가까운 단계로 되돌아가야 비용을 줄일 수 있다.

실패 유형의미다시 시작할 지점
Implementation Error계획은 맞지만 구현이 틀림Implementer
Plan Error원본 요구사항이 계획에서 빠짐Planner → Implementer
Analysis Error원본 분석 자체가 잘못됨Analyzer → Planner → Implementer
 
Implementation Error
→ Implement 단계까지 rollback

Planning Error
→ Planning 단계까지 rollback

Analysis Error
→ Analysis 단계까지 rollback

이미 PASS한 API·Logic·SEO를 다시 검사하지 않고 FAIL한 UI만 수정하는 식으로 범위를 좁힐 수 있다.

7. Verifier는 Evidence를 수집해야 한다

Verifier가 코드를 읽고 “대충 맞는 것 같다”고 말하는 것은 충분한 검증이 아니다. 실제 실행 결과와 비교 가능한 Evidence를 수집해야 한다.

Verifier
 ├─ Browser
 ├─ Test
 ├─ Network
 ├─ DOM
 ├─ Screenshot
 ├─ Event Log
 ├─ Source Code
 └─ Runtime Output
       ↓
    Evidence
       ↓
   PASS / FAIL

기계적으로 판단 가능한 것은 프로그램에 맡기고, LLM은 검사할 상태·실패 원인·rollback 지점을 판단하는 데 집중시키는 것이 좋다.

프로그램이 판단Unit Test, HTTP Status, URL, DOM, Pixel Diff, Event, Type Check, Build
LLM이 판단숨겨진 상태, 실패 원인, 누락 요구사항, 적절한 Retry 경로

8. 페이지가 아니라 상태를 검증한다

UI 페이지 하나에는 초기 화면, 입력 중, 버튼 활성화, 다음 단계처럼 여러 State가 있다. 초기 화면만 비교하면 이후 Interaction의 오류를 놓친다.

State 1: 초기 화면
   ↓ 입력
State 2: 일부 입력
   ↓ 조건 충족
State 3: Next 활성화
   ↓ 클릭
State 4: 다음 Step

따라서 원본과 새 시스템을 같은 시나리오로 실행하고 State별로 비교한다.

원본 State 1 ↔ 새 시스템 State 1
원본 State 2 ↔ 새 시스템 State 2
원본 State 3 ↔ 새 시스템 State 3
원본 State 4 ↔ 새 시스템 State 4

9. 분야별 검증 예시

UI

같은 Interaction을 수행한 뒤 Screenshot과 DOM 상태를 비교한다. “비슷해 보인다”보다 허용된 Rendering Noise를 제외한 Pixel Diff처럼 결정 가능한 기준을 둔다.

Logic

이름 없음 + 이메일 없음 → Next disabled
이름 있음 + 이메일 없음 → Next disabled
이름 있음 + 이메일 있음 → Next enabled

API

HTTP Method, URL, Query, Request Body, Header, Response Status와 Schema를 원본과 비교한다.

SEO

title, meta description, canonical, OG, structured data와 robots를 실제 DOM에서 추출해 비교한다.

Tracking

Event Name, Payload, 발생 시점과 횟수를 비교한다. 기능이 동작해도 Event가 빠지면 Acceptance Gate를 통과하지 못할 수 있다.

10. 구조화된 Verification Result

Verifier 결과는 다음 Agent가 바로 사용할 수 있도록 구조화하는 편이 좋다.

{
  "gate": "G2",
  "status": "FAIL",
  "scope": "logic",
  "cause": "IMPLEMENTATION_ERROR",
  "expected": "모든 입력 완료 후 Next 활성화",
  "actual": "Next가 계속 disabled",
  "evidence": {"state": "valid-form", "selector": "#next"},
  "retry_from": "implementation"
}

Plan 누락이라면 cause: PLAN_INCOMPLETE, 원본 분석 오류라면 retry_from: analysis처럼 어느 단계부터 다시 할지 명시할 수 있다.

11. 공유된 잘못된 가정과 독립 검증

멀티 Agent라고 자동으로 안전해지는 것은 아니다. Analyzer의 누락된 요구사항을 Planner·Implementer·Verifier가 모두 같은 Context에서 공유하면 기능이 빠진 상태로 PASS할 수 있다.

Plan에 Tooltip 없음
       ↓
Implementer도 구현하지 않음
       ↓
Verifier도 검사하지 않음
       ↓
기능은 빠졌지만 PASS
해결 방향 — Verifier가 Plan만 믿지 않고 원본 화면, 원본 Request, 원본 Event 같은 독립 Evidence를 직접 확인하게 한다.

12. Human-in-the-loop

모든 단계를 자동화하는 것보다 되돌리기 비용이 높은 단계에 사람의 확인을 두는 것이 현실적이다.

Analysis
   ↓
Plan
   ↓
[Human Review]
   ↓
Foundation
   ↓
[Human Review]
   ↓
Implementation
   ↓
Verify Loop

분석이나 폴더·라우팅 구조가 틀리면 이후 모든 구현이 영향을 받는다. 반대로 명확한 Unit Test나 DOM 존재 여부는 자동 검증에 맡길 수 있다.

한 문장 결론 — 좋은 Agent 시스템은 LLM을 반복 호출하는 시스템이 아니라, 상태와 역할을 관리하고 실제 Evidence로 Acceptance Gate를 통과할 때까지 실패 원인에 맞게 되돌아가는 제어 시스템이다.

14. Function Calling 프로젝트와의 경계

개인 프로젝트의 현재 결과는 Agent Loop 전체가 아니라 한 번의 요청을 도구 이름과 인자로 변환하는 라우터다. 모델의 tool_calls를 서버가 검증하고 실행하는 지점까지 구현했지만, 결과를 다시 모델에 넣어 다음 도구를 자율적으로 선택하는 루프는 아직 범위 밖이다.

현재 프로젝트
user → model → one tool_call → server validation → handler

다음 확장
user → model → tool_call → handler → observation
     ↖ model receives observation and chooses next action
연결 문서
Function Calling과 도구 계약에서 한 번 호출·Context 재전송·MCP와의 차이를, 프로젝트 허브에서 이번 범위와 다음 단계를 확인한다.
