이 글의 핵심을 한 문장으로 다시 쓰기

토큰당 비용 ≈ 포워드 1회의 메모리·실행 비용한 포워드에서 확정한 평균 토큰 수

커널 최적화는 분자를 줄이고, MTP는 분모를 키우려는 접근이라고 읽을 수 있다. 이것은 원문을 이해하기 위한 개념 모델이며 실제 시스템의 모든 비용을 포함한 정확한 공식은 아니다.

기초 연결 · 포워드, Hidden State, Logits

이 글에서 말하는 포워드 한 번이 실제로 무엇을 출력하는지 먼저 연결합니다.

포워드란 무엇인가?

포워드(forward)는 입력 토큰을 모델의 첫 연산부터 마지막 출력층까지 한 방향으로 통과시켜 결과를 계산하는 과정입니다. 생성 모델의 추론에서는 현재까지의 토큰들을 입력하고 다음 토큰을 고르는 데 필요한 점수를 계산합니다.

입력 Token현재까지 생성된 문장
Embedding토큰 번호를 벡터로 변환
Transformer여러 Layer에서 문맥 계산
LM Head단어장 차원으로 변환
Logits다음 토큰별 점수
학습과 추론의 차이
학습에서는 forward → loss → backward가 이어집니다. 이 글은 생성 추론 성능을 다루므로 포워드로 점수를 계산한 뒤 토큰을 선택하며, 가중치를 학습시키는 backward()는 수행하지 않습니다.

Hidden State는 모델 내부의 문맥 표현이다

Transformer Layer들을 통과한 각 토큰에는 d_model개의 숫자로 이루어진 내부 벡터가 남습니다. 이것이 Hidden State입니다.

hidden_states shape = [batch, sequence, d_model]

예를 들어 d_model=4096이라면 마지막 위치의 Hidden State는 숫자 4096개입니다. 이것은 단어별 확률이 아니라, 현재 문맥을 모델 내부 차원으로 표현한 값입니다.

Logits는 Hidden State를 단어장 차원으로 바꾼 결과다

마지막 출력층인 LM Head가 Hidden State를 vocab_size개의 점수로 변환합니다.

logits = LM Head(hidden_state)
[d_model] × [d_model, vocab_size] → [vocab_size]

d_model=4096, vocab_size=100,000이라면 다음과 같이 바뀝니다.

값Shape의미
마지막 Hidden State[4096]현재 문맥의 내부 표현
Logits[100,000]단어장 토큰 10만 개 각각의 다음 토큰 점수
Hidden State와 Logits는 동일하지 않습니다.
Hidden State는 모델 내부 표현이고, Logits는 그 표현을 단어장 차원으로 투영한 점수입니다. Logits도 아직 확률이 아니며, Softmax를 적용한 뒤 토큰별 확률로 해석할 수 있습니다.
Hidden State → LM Head → Logits → Softmax/선택 → 다음 Token

일반적인 생성에서는 왜 포워드를 반복하는가?

"나는 오늘 학교에" → 포워드 → "갔다" 선택

"나는 오늘 학교에 갔다" → 다시 포워드 → "." 선택

일반적인 Autoregressive decoding은 토큰 하나를 확정할 때마다 다음 입력이 달라지므로 포워드를 반복합니다. 이 글의 MTP 설명은 작은 모델이 미래 토큰 후보를 만들고 메인 모델이 여러 후보를 함께 검증해, 메인 모델 포워드 한 번당 확정하는 평균 토큰 수를 늘리는 접근입니다.

MTP · 미래 토큰 후보를 한 번에 검증하는 흐름

확정된 토큰이 [나는]뿐이고, 최종적으로 [나는] [학교에] [갔다]가 만들어지는 상황을 따라갑니다.

먼저 용어를 구분합니다.
MTP는 넓게는 Multi-Token Prediction, 즉 미래의 여러 토큰을 예측하는 방식을 뜻합니다. 작은 Draft가 후보를 먼저 만들고 큰 모델이 한꺼번에 검증하는 실행 방식은 Speculative decoding입니다. 이 글에서는 MTP가 만든 여러 후보를 speculative하게 검증하는 흐름으로 연결해 설명하지만, 모든 MTP가 반드시 별도의 작은 Draft 모델을 사용한다는 뜻은 아닙니다.

1. 지금 확정된 문장은 [나는]뿐이다

확정된 Prefix = [나는]

[학교에]와 [갔다]는 아직 정답이 아닙니다. 작은 Draft가 빠르게 추측해서 만든 임시 후보입니다.

Draft의 임시 후보 = [학교에] [갔다]

Draft도 순서를 무시하는 것은 아닙니다. 먼저 [나는]을 보고 [학교에]를 추측하고, 이어서 임시 문장 [나는] [학교에]를 보고 [갔다]를 추측합니다.

2. 큰 모델은 후보 Token ID를 자기 방식으로 다시 계산한다

작은 모델의 Hidden State를 가져다 쓰는 것이 아닙니다. 작은 모델이 내놓은 Token ID 후보를 큰 모델이 자신의 Embedding, Transformer Layer, LM Head로 처리하여 자신의 Logits를 계산합니다.

확정 Prefix[나는]
Draft 추측[학교에] [갔다]
Main 1회 Forward후보 위치들을 병렬 계산
Token 비교Main 예측과 Draft 후보 비교
Prefix 확정앞에서부터 연속으로 맞은 후보만 채택

3. 큰 모델의 한 번의 Forward 자체가 검증이다

핵심은 후보를 병렬 계산한 뒤 큰 모델을 다시 순차 실행하는 것이 아니라는 점입니다. 아래 두 계산이 큰 모델의 한 번의 Forward 안에서 위치별로 함께 수행됩니다.

검증할 Draft 후보큰 모델이 사용하는 문맥큰 모델에게 묻는 것
[학교에][나는][나는] 다음 토큰으로 [학교에]가 맞는가?
[갔다][나는] [학교에][나는] [학교에] 다음 토큰으로 [갔다]가 맞는가?

Causal Mask 때문에 첫 번째 위치는 뒤의 후보를 볼 수 없습니다. 두 번째 위치는 앞의 임시 후보 [학교에]까지는 볼 수 있지만 미래 후보는 볼 수 없습니다. 따라서 각 위치는 Autoregressive 규칙을 지키면서도 GPU에서는 여러 위치의 행렬 연산을 한꺼번에 수행할 수 있습니다.

가장 중요한 문장
앞 후보가 맞을 것이라고 임시로 가정하고 뒤 위치까지 모두 병렬 계산한 다음, 계산이 끝나면 앞에서부터 확인하여 연속으로 맞은 구간만 확정합니다.

4. 앞에서부터 맞은 구간만 확정한다

큰 모델의 예측도 [학교에] [갔다]라면 두 후보를 모두 확정합니다.

Draft [학교에, 갔다] = Main [학교에, 갔다] → 두 토큰 확정

큰 모델의 예측이 [학교에] [간다]라면 첫 후보만 맞습니다. [학교에]는 확정하고, 처음 불일치한 [갔다]부터 뒤의 후보는 버립니다.

Draft [학교에, 갔다] ≠ Main [학교에, 간다] → [학교에]만 확정

첫 후보부터 틀렸다면 뒤쪽 계산은 틀린 임시 문맥을 전제로 했으므로 전부 버립니다. 반대로 첫 후보가 맞았다면 두 번째 위치가 사용한 임시 문맥은 실제 문맥과 같아지므로 그 결과도 검증에 사용할 수 있습니다.

5. Draft는 모든 미래가 아니라 짧은 후보 묶음만 제안한다

작은 모델이 완성될 문장 전체를 미리 제공할 필요는 없습니다. 한 번에 제안할 후보 개수 k를 정하고, 그만큼만 임시로 생성합니다.

현재 확정 [나는] + Draft 후보 2개 [학교에, 갔다]

큰 모델이 두 후보를 모두 승인하면 우선 [나는] [학교에] [갔다]까지 확정합니다. 그다음에는 Draft가 새로운 후보 묶음을 만들거나, 필요에 따라 큰 모델이 직접 다음 토큰을 생성할 수 있습니다. 이 과정을 반복하므로 Draft가 문장의 끝까지 한꺼번에 알아야 하는 구조가 아닙니다.

검증 Forward에서 다음 토큰까지 얻을 수 있다

큰 모델은 Draft 후보들을 검증하는 동안 마지막 후보 다음에 올 토큰의 Logits도 계산할 수 있습니다. 모든 후보가 승인되면 큰 모델이 직접 예측한 이 토큰을 하나 더 채택할 수 있는데, 이를 흔히 Bonus token이라고 부릅니다.

Draft 후보 [학교에, 갔다] + Main의 추가 예측 [.] → [학교에, 갔다, .] 확정 가능
후보 개수도 조절 대상입니다.
후보가 너무 적으면 큰 모델 Forward 횟수를 충분히 줄이지 못합니다. 너무 많으면 앞부분에서 틀렸을 때 버리는 뒤쪽 계산이 많아집니다. 따라서 Draft 비용, 후보 적중률, 평균 Acceptance length를 보고 적당한 후보 묶음 크기를 선택합니다.

6. 왜 빨라질 수 있는가?

일반 생성Draft + 병렬 검증
Main Forward → [학교에] 확정
Main Forward → [갔다] 확정		작은 Draft가 후보 생성
Main Forward 1회 → 두 후보를 함께 검증

큰 모델의 가중치를 읽는 작업이 비싸다면, 한 번 읽고 한 위치만 계산하는 것보다 여러 후보 위치를 함께 계산해 여러 토큰을 확정하는 편이 유리할 수 있습니다. 검증이 끝난 뒤 하는 일은 이미 계산된 Main 예측과 Draft Token ID를 앞에서부터 비교하는 것이므로, 큰 모델을 다시 순차 Forward하는 비용과는 다릅니다.

항상 빨라지는 것은 아닙니다.
Draft가 충분히 싸고, 후보가 자주 맞아 Acceptance length가 길며, 큰 모델의 1회 Forward 비용이 큰 상황에서 이득이 커집니다. 후보가 자주 틀리면 미리 계산한 뒤쪽 위치를 버리므로 이득이 줄어듭니다.

이 예시를 한 문장으로 복원하기

[나는]만 확정된 상태에서 Draft가 [학교에] [갔다]를 임시로 제안하고, 큰 모델은 한 번의 병렬 Forward로 “나는→학교에”와 “나는 학교에→갔다”를 동시에 계산한 뒤, 앞에서부터 맞은 후보만 실제 문장으로 확정합니다.
