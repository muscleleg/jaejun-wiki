📌 컨테이너(Container)란?

컨테이너(Container)는 애플리케이션과 그 실행 환경을 하나의 패키지로 묶어 어디서든 동일하게 실행할 수 있도록 만든 기술이야.

컨테이너를 사용하면 애플리케이션과 실행 의존성을 묶어 다른 환경에서도 일관되게 실행할 수 있다.

✅ 1. 컨테이너의 핵심 개념

  • 컨테이너는 "가상 머신(VM)"과 비슷하지만, 더 가볍고 빠른 실행 환경을 제공함.
  • 리눅스의 프로세스 격리 기능을 활용하여 독립적인 실행 환경을 만듦.
  • 컨테이너 내부에서 실행되는 애플리케이션은 운영체제(OS)와 독립적으로 실행됨.
  • 컨테이너를 이용하면 개발 환경과 배포 환경의 차이를 최소화할 수 있음.
  • 대표적인 컨테이너 기술: Docker, Podman, LXC, CRI-O

💡 쉽게 말하면, 컨테이너는 가상 머신보다 가볍고 빠르게 애플리케이션을 실행할 수 있는 기술이야!

📌 가상 머신(VM)과 컨테이너의 차이

가상 머신(VM) 컨테이너(Container)
실행 방식 전체 운영체제(OS)를 가상화 프로세스를 격리하여 실행
무게 무거움 (OS 포함) 가벼움 (OS 공유)
부팅 속도 느림 (몇 분) 빠름 (몇 초)
자원 활용 독립된 OS를 사용 OS를 공유하여 효율적
대표 기술 VMware, VirtualBox, KVM Docker, Podman, LXC

💡 VM은 하드웨어를 가상화하는 개념이고, 컨테이너는 운영체제(OS) 수준에서 가상화를 하는 개념이야!

📌 컨테이너가 리눅스에서 시작된 이유

컨테이너는 리눅스의 핵심 기능(커널 기능)을 활용하여 만들어졌어.

즉, 리눅스에서 제공하는 프로세스 격리 기술이 컨테이너 기술의 기반이야!

🔹 컨테이너의 핵심 리눅스 기술

리눅스 기술 역할
Namespaces 프로세스를 격리하여 독립적인 실행 환경 제공
Cgroups (Control Groups) CPU, 메모리 등 자원 사용을 제한하고 관리
OverlayFS 컨테이너 이미지 레이어를 효율적으로 관리
Chroot (Change Root) 특정 디렉터리를 루트(root) 디렉터리처럼 사용
Seccomp & AppArmor 보안 정책을 적용하여 컨테이너 보호

💡 즉, 컨테이너는 리눅스의 격리(Namespaces)와 자원 제한(Cgroups) 기능을 활용해서 만들어진 기술이야!

📌 브릿지 네트워크(Bridge Network)란?

컨테이너가 실행되면 서로 통신할 수 있어야 해.

이때 컨테이너들이 같은 네트워크 안에서 통신할 수 있도록 도와주는 가상의 네트워크가 "브릿지 네트워크"야!

💡 브릿지 네트워크(Bridge Network)는 여러 개의 컨테이너를 같은 네트워크로 묶어, 마치 물리적인 네트워크처럼 통신할 수 있도록 해주는 기술이야!

📌 브릿지 네트워크(Bridge Network)의 개념

  • 리눅스에서는 네트워크 인터페이스를 가상화하여 컨테이너 간 통신을 가능하게 함.
  • 브릿지 네트워크를 사용하면 컨테이너끼리 같은 네트워크 안에서 서로 통신할 수 있음.
  • 컨테이너가 생성될 때 브릿지 네트워크에 연결되면 IP 주소를 할당받고, 같은 브릿지 네트워크 내에서는 자유롭게 통신할 수 있음.
  • 외부 네트워크와 연결되지 않아도 내부에서 자체적으로 통신 가능.
  • 쿠버네티스에서 Pod들은 브릿지 네트워크를 통해 서로 연결됨.

💡 쉽게 말해, 브릿지 네트워크는 여러 개의 컨테이너를 하나의 가상의 네트워크로 묶어주는 역할을 해!

📌 브릿지 네트워크의 특징

  1. 같은 브릿지 네트워크에 있는 컨테이너(Pod, VM 등)는 직접 통신 가능.
  2. 하나의 네트워크 인터페이스(eth0)만 있어도 여러 개의 가상 네트워크 인터페이스를 만들 수 있음.
  3. 외부 네트워크와 연결되지 않아도 내부 통신이 가능함.
  4. 쿠버네티스에서는 브릿지 네트워크를 이용해 Pod들이 같은 노드 안에서 서로 통신하도록 설정됨.

📌 컨테이너 + 브릿지 네트워크 = 어떻게 동작할까?

컨테이너는 기본적으로 서로 독립적인 환경에서 실행됨.

하지만, 브릿지 네트워크를 사용하면 같은 네트워크 안에서 컨테이너들이 서로 통신할 수 있어.

🔹 예제: 두 개의 컨테이너가 브릿지 네트워크에서 통신하는 과정

[컨테이너1] --(Bridge)--> [브릿지 네트워크] --(Bridge)--> [컨테이너2]
  • 컨테이너1과 컨테이너2는 같은 브릿지 네트워크에 연결됨.
  • 컨테이너1에서 컨테이너2로 데이터를 보낼 수 있음.
  • 쿠버네티스에서는 Pod 간 통신도 동일한 방식으로 동작.

브리지 네트워크를 사용하면 같은 브리지에 연결된 컨테이너끼리 내부 통신할 수 있다.

📌 브릿지 네트워크와 쿠버네티스

쿠버네티스에서는 각 Pod가 고유한 IP 주소를 가지지만, 같은 노드 안에서는 브릿지 네트워크를 통해 통신해.

그러나 기본적으로 리눅스는 브릿지 네트워크에서 패킷을 필터링하지 않기 때문에, br_netfilter 설정을 활성화해야 해!

sudo modprobe br_netfilter

✅ 브릿지 네트워크에서 iptables가 패킷을 필터링할 수 있도록 설정함.

echo 'net.bridge.bridge-nf-call-iptables=1' | sudo tee -a /etc/sysctl.d/k8s.conf
sudo sysctl --system

✅ 쿠버네티스 네트워크 정책이 올바르게 동작하도록 설정함.

📌 정리

✅ 컨테이너(Container)는 애플리케이션과 실행 환경을 패키징해서 가볍고 빠르게 실행할 수 있는 기술.

✅ 컨테이너는 리눅스의 네임스페이스(Namespaces), Cgroups 등 커널 기능을 활용해서 격리된 환경을 제공함.

✅ 브릿지 네트워크(Bridge Network)는 여러 개의 컨테이너를 같은 네트워크로 묶어 서로 통신할 수 있도록 해줌.

✅ 쿠버네티스에서는 브릿지 네트워크를 사용하여 Pod들이 서로 연결됨.

✅ 기본적으로 리눅스에서는 브릿지 네트워크의 패킷을 iptables에서 필터링하지 않기 때문에, br_netfilter 설정을 활성화해야 함.

1. 사전 준비

쿠버네티스를 설치하려면 여러 개의 서버(노드)가 필요합니다.

쿠버네티스 클러스터는 마스터 노드와 워커 노드로 구성됩니다..

1-1. 서버 구성

노드 종류 역할
마스터 노드 (master-node) 클러스터 전체를 관리
워커 노드 (worker-node) 애플리케이션이 실행되는 곳

우리는 Ubuntu 20.04 또는 22.04 운영체제를 사용합니다.

명령어를 실행하려면 root 계정 또는 sudo를 사용해야 합니다.

1-2. 호스트 이름 변경 (선택 사항)

각 서버의 이름(호스트 이름)을 설정하면 나중에 관리하기 편합니다.

기본적으로 Ubuntu에서는 ubuntu라는 이름을 사용하지만, 역할에 맞게 이름을 바꿔주면 서버를 구분하기 쉽습니다.

마스터 노드에서 실행

sudo hostnamectl set-hostname master-node

이 명령어의 역할:

  • hostnamectl set-hostname [새 이름] → 현재 서버의 호스트 이름을 master-node로 변경함.
  • 이 변경 사항은 서버를 재부팅해도 유지됨.

워커 노드에서 실행

sudo hostnamectl set-hostname worker-node

이 명령어의 역할:

  • 위와 동일한 방식으로 워커 노드의 이름을 worker-node로 변경.

/etc/hosts 파일 수정 (모든 노드에서 실행)

각 노드가 서로 통신할 수 있도록, 모든 노드에서 /etc/hosts 파일을 수정해야 합니다.

sudo nano /etc/hosts

파일 내용 수정 (예제):

127.0.1.1 master-node  # 마스터 노드
127.0.1.1 worker-node  # 워커 노드

이게 왜 필요할까?

  • 기본적으로, 서버들은 IP 주소를 사용해서 서로 통신합니다.
  • 하지만 사람이 IP 주소를 직접 관리하기 어려우니까, 이름(호스트명)으로 접근할 수 있도록 등록하는 겁니다.
  • 위 설정을 하면, master-node라고 입력하면 자동으로 127.0.1.1(자신의 IP)로 연결됩니다.

설정을 적용하려면 쉘을 다시 실행해야 합니다.

exec bash
  • 이 명령어는 현재 쉘을 다시 시작해서 변경된 호스트 이름이 즉시 적용되도록 해.

2. 방화벽 및 스왑(Swap) 설정 (모든 노드에서 실행)

쿠버네티스는 안정적으로 동작하기 위해 몇 가지 필수적인 환경 설정이 필요합니다.

스왑(Swap) 비활성화

sudo swapoff -a
sudo sed -i '/swap/d' /etc/fstab

Swap이란?

  • RAM(메모리)이 부족할 때, 디스크의 일부를 임시 메모리처럼 사용하는 기능이야.
  • 일반적으로 성능이 낮은 서버에서는 RAM이 부족하면 디스크에 데이터를 저장했다가 다시 불러오는데, 디스크 속도는 RAM보다 훨씬 느려.
  • 이 때문에 애플리케이션 실행 속도가 느려지고, 쿠버네티스의 자원 관리가 꼬일 수 있어.

왜 Swap을 꺼야 할까?

  1. 성능 저하 방지
  • 쿠버네티스는 메모리 사용량을 정확하게 예측해서 컨테이너를 배치하는데, 스왑이 활성화되어 있으면 잘못된 예측이 발생할 수 있어.
  1. 노드의 신뢰성 향상
  • 쿠버네티스는 스왑을 고려하지 않고 설계됐기 때문에, 스왑이 켜져 있으면 컨테이너가 비정상적으로 종료될 수도 있어.
  1. 클러스터 불안정 방지
  • 클러스터 전체에서 균형 있게 노드를 배치하려면, 각 노드의 리소스 상태를 정확하게 파악해야 하는데, 스왑이 활성화되어 있으면 이를 정확하게 측정할 수 없음.

명령어 설명

  • swapoff -a → 현재 활성화된 스왑을 모두 비활성화함.
  • sed -i '/swap/d' /etc/fstab → 재부팅해도 스왑이 자동으로 켜지지 않도록 설정 파일에서 스왑 항목을 삭제.
  • sed: 파일의 내용을 직접 열지 않고도 특정한 텍스트를 찾아서 변경, 삭제, 추가할 수 있는 명령어

방화벽 비활성화

sudo ufw disable

왜 방화벽을 비활성화할까?

  • 기본적으로 Ubuntu의 방화벽(UFW)은 네트워크 트래픽을 차단할 수 있습니다.
  • 쿠버네티스는 여러 노드 간에 자유롭게 네트워크 통신을 해야 하므로, 방화벽을 끄는 게 안전합니다.
  • 필요하면 나중에 설정을 조정할 수도 있습니다.

네트워크 필터링 설정

sudo modprobe br_netfilter
echo 'net.bridge.bridge-nf-call-iptables=1' | sudo tee -a /etc/sysctl.d/k8s.conf
echo 'net.ipv4.ip_forward=1' | sudo tee -a /etc/sysctl.d/k8s.conf
sudo sysctl --system

br_netfilter란?

  • 쿠버네티스에서는 여러 개의 컨테이너가 서로 같은 네트워크 안에서 통신해야 합니다.
  • 그런데 기본적으로 Linux 커널은 브릿지 네트워크에서 패킷을 필터링하지 않습니다.
  • 이를 활성화하면, 컨테이너 간 통신이 원활하게 되고, 네트워크 정책이 제대로 적용됩니다..

각 명령어 설명

  • modprobe br_netfilter → 브릿지 네트워크에서 패킷을 필터링하는 기능을 활성화합니다.
  • echo 'net.bridge.bridge-nf-call-iptables=1' \| sudo tee -a /etc/sysctl.d/k8s.conf → iptables가 브릿지 네트워크의 트래픽을 필터링할 수 있도록 설정합니다.
  • tee는 표준 입력(stdin)으로 받은 데이터를 화면에 출력하면서 동시에 파일에 저장하는 명령어
  • echo 'net.ipv4.ip_forward=1' \| sudo tee -a /etc/sysctl.d/k8s.conf → 패킷이 다른 네트워크로 전달될 수 있도록 허용합니다.
  • sysctl --system → 설정을 즉시 적용함.

3. 컨테이너 런타임 (crio) 설치

쿠버네티스는 애플리케이션을 실행할 때 "컨테이너(Container)"라는 기술을 사용합니다.

컨테이너를 실행하려면 이를 관리하는 컨테이너 런타임(Container Runtime)이 필요합니다.

쿠버네티스에서 지원하는 컨테이너 런타임에는 여러 가지가 있지만, 현재 가장 권장되는 것은 containerd입니다.

하지만 crio를 이용해 설치할겁니다.

1. 환경 변수 설정

  • 사용할 OS 및 CRI-O 버전 지정
export OS=xUbuntu_22.04
export CRIO_VERSION=1.24

2. 저장소 추가

  • CRI-O 및 libcontainers 저장소를 APT에 등록
echo "deb https://download.opensuse.org/repositories/devel:/kubic:/libcontainers:/stable/$OS/ /" | sudo tee /etc/apt/sources.list.d/devel:kubic:libcontainers:stable.list
echo "deb http://download.opensuse.org/repositories/devel:/kubic:/libcontainers:/stable:/cri-o:/$CRIO_VERSION/$OS/ /" | sudo tee /etc/apt/sources.list.d/devel:kubic:libcontainers:stable:cri-o:$CRIO_VERSION.list

3. GPG 키 등록

  • 저장소에 대한 신뢰를 위해 GPG 키 추가
curl -L https://download.opensuse.org/repositories/devel:kubic:libcontainers:stable:cri-o:$CRIO_VERSION/$OS/Release.key | sudo apt-key add -
curl -L https://download.opensuse.org/repositories/devel:/kubic:/libcontainers:/stable/$OS/Release.key | sudo apt-key add -

4. 패키지 목록 업데이트 및 CRI-O 설치

sudo apt update
sudo apt install cri-o cri-o-runc

5. CRI-O 서비스 시작 및 부팅 시 자동 실행 설정

sudo systemctl start crio
sudo systemctl enable crio

6. CRI-O 상태 확인

sudo systemctl status crio
  • active (running) 상태이면 정상적으로 실행 중입니다.

4. 쿠버네티스 핵심 구성 요소 설치

쿠버네티스를 설치하려면 세 가지 핵심 프로그램이 필요해.

프로그램 역할
kubeadm 쿠버네티스 클러스터를 초기화하는 도구
kubelet 각 노드에서 컨테이너를 실행하는 프로그램
kubectl 쿠버네티스를 제어하는 CLI(Command Line Interface) 도구

4-1. 쿠버네티스 패키지 다운로드를 위한 보안 키 추가

curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.30/deb/Release.key | \
sudo gpg --dearmor -o /usr/share/keyrings/kubernetes-archive-keyring.gpg

📌 이 명령어는 무슨 역할을 할까?

  • 리눅스에서 패키지를 설치하려면 해당 저장소가 "신뢰할 수 있는 곳"인지 확인해야 해.
  • 쿠버네티스 패키지는 공식 저장소에서 다운로드해야 하므로 보안 키(GPG Key)를 등록해야 해.
  • gpg --dearmor → 키 파일을 변환해서 리눅스에서 사용할 수 있도록 만듦.
  • /usr/share/keyrings/kubernetes-archive-keyring.gpg에 저장함.

4-2. 쿠버네티스 패키지 저장소 추가

echo "deb [signed-by=/usr/share/keyrings/kubernetes-archive-keyring.gpg] \
https://pkgs.k8s.io/core:/stable:/v1.30/deb/ /" | \
sudo tee /etc/apt/sources.list.d/kubernetes.list

왜 해야 할까?

  • apt(패키지 관리자)는 기본적으로 우분투의 공식 저장소에서만 패키지를 다운로드해.
  • 하지만 쿠버네티스는 별도의 저장소에서 제공되므로, 추가로 등록해야 함.
  • /etc/apt/sources.list.d/kubernetes.list → 쿠버네티스 저장소를 등록하는 파일.

4-3. kubeadm, kubelet, kubectl 설치

sudo apt update
sudo apt install -y kubelet=1.30.0-1.1 kubeadm=1.30.0-1.1 kubectl=1.30.0-1.1
sudo apt-mark hold kubelet kubeadm kubectl

📌 각 프로그램의 역할

  • kubeadm → 클러스터 초기화 및 설정 도구
  • kubelet → 각 노드에서 컨테이너 실행 및 관리
  • kubectl → 쿠버네티스를 제어하는 CLI(Command Line Interface) 도구

4-4. 쿠버네티스 버전 고정

sudo apt-mark hold kubelet kubeadm kubectl

이 명령어가 하는 일

  • 쿠버네티스는 계속해서 새로운 버전이 나오지만, 자동 업데이트되면 기존 설정과 충돌할 가능성이 있습니다.
  • apt-mark hold를 사용하면 이 세 가지 프로그램이 자동으로 업데이트되지 않도록 막을 수 있습니다.
  • 버전 관리를 직접 하고 싶을 때 유용한 설정이야.

5. 마스터 노드 설정 (kubeadm init)

이제 모든 노드에서 기본 프로그램을 설치했으니까, 마스터 노드를 초기화해서 클러스터를 구성할 겁니다.

sudo kubeadm init --pod-network-cidr=192.168.0.0/16 --cri-socket=unix:///var/run/crio/crio.sock

이 명령어가 하는 일

  • kubeadm init → 쿠버네티스 클러스터를 생성하는 명령어.
  • pod-network-cidr=192.168.0.0/16 → 클러스터 내부에서 사용할 네트워크 범위를 지정.

초기화가 끝나면 아래와 같은 메시지가 출력될 겁니다.

Your Kubernetes control-plane has initialized successfully!
To start using your cluster, you need to run the following as a regular user:
...
Then you can join any number of worker nodes by running the following on each as root:
kubeadm join <MASTER_IP>:6443 --token <TOKEN> --discovery-token-ca-cert-hash sha256:<HASH>
  • 이 kubeadm join 명령어를 복사해두세요
  • 나중에 워커 노드를 마스터 노드에 연결할 때 사용할 겁니다.

6. 마스터 노드에서 kubectl 사용 설정

쿠버네티스를 제대로 사용하려면 kubectl을 설정해야 합니다.

kubectl은 쿠버네티스를 조작하는 CLI(Command Line Interface) 도구입니다.

🔹 kubectl을 사용할 수 있도록 환경 설정

mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

📌 각 명령어의 역할

  1. mkdir -p \$HOME/.kube → 쿠버네티스 설정 파일을 저장할 폴더를 생성. (p는 폴더가 이미 있으면 그냥 넘어가라는 의미)
  2. sudo cp -i /etc/kubernetes/admin.conf \$HOME/.kube/config → 클러스터 인증 파일(admin.conf)을 사용자의 설정 폴더로 복사.
  3. sudo chown \$(id -u):\$(id -g) \$HOME/.kube/config → 현재 사용자에게 config 파일의 소유권을 부여.

이제부터 kubectl을 사용해서 쿠버네티스를 조작할 수 있어요

7. CNI(네트워크 플러그인) 설치

쿠버네티스에서 컨테이너끼리 통신하려면 "네트워크 플러그인(CNI)"을 설치해야합니다.

CNI는 쿠버네티스 내부의 Pod들이 서로 네트워크를 통해 연결되도록 도와주는 역할을 합니다.

쿠버네티스에서 많이 사용하는 CNI 플러그인

CNI 플러그인 특징
Calico 보안 정책(NetworkPolicy) 지원, 복잡하지만 강력함
Flannel 가장 간단한 네트워크 플러그인, 빠르고 설정이 쉬움

우리는 Calico를 설치할겁니다.

Calico 설치

kubectl apply -f <https://docs.projectcalico.org/manifests/calico.yaml>

이 명령어의 역할

  • kubectl apply -f [파일] → 쿠버네티스 리소스를 적용하는 명령어.
  • https://docs.projectcalico.org/manifests/calico.yaml → Calico 네트워크 플러그인을 쿠버네티스에 설치하는 YAML 파일.

8. 워커 노드 연결

쿠버네티스 클러스터는 마스터 노드 + 워커 노드로 구성됩니다.

이제 워커 노드를 클러스터에 연결할 차례입니다.

마스터 노드에서 kubeadm init 실행했을 때 출력된 명령어 실행

sudo kubeadm join <MASTER_IP>:6443 --token <TOKEN> --discovery-token-ca-cert-hash sha256:<HASH>

각 항목의 의미

  • <MASTER_IP>:6443 → 마스터 노드의 API 서버 주소.
  • <TOKEN> → 워커 노드가 마스터 노드에 연결할 때 사용하는 인증 토큰.
  • discovery-token-ca-cert-hash sha256:<HASH> → 클러스터의 보안 인증을 확인하는 해시 값.

이 명령어는 마스터 노드를 초기화할 때(kubeadm init) 출력됐던 명령어를 그대로 사용해야 합니다.

워커 노드가 join 명령어를 실행하면 어떻게 될까요?

  1. 워커 노드가 마스터 노드와 연결됨.
  2. 마스터 노드가 워커 노드를 쿠버네티스 클러스터의 일부로 추가함.
  3. 워커 노드에서 실행되는 kubelet이 컨테이너를 실행할 준비를 함.

9. 클러스터 상태 확인

이제 모든 설정이 끝났으니까, 클러스터가 정상적으로 동작하는지 확인해봅시다.

마스터 노드에서 실행

kubectl get nodes

출력 예시

NAME          STATUS   ROLES           AGE    VERSION
master-node   Ready    control-plane   10m    v1.29.5
worker-node   Ready    <none>          5m     v1.29.5

여기서 중요한 부분

  • STATUS가 Ready면 클러스터가 정상적으로 동작 중.
  • master-node는 control-plane 역할을 하고 있습니다.
  • worker-node가 정상적으로 추가됐는지 확인할 수 있습니다.

📌 컨테이너(Container)란?

컨테이너(Container)는 애플리케이션과 그 실행 환경을 하나의 패키지로 묶어 어디서든 동일하게 실행할 수 있도록 만든 기술이야.

컨테이너를 사용하면 애플리케이션과 실행 의존성을 묶어 다른 환경에서도 일관되게 실행할 수 있다.

✅ 1. 컨테이너의 핵심 개념

  • 컨테이너는 "가상 머신(VM)"과 비슷하지만, 더 가볍고 빠른 실행 환경을 제공함.
  • 리눅스의 프로세스 격리 기능을 활용하여 독립적인 실행 환경을 만듦.
  • 컨테이너 내부에서 실행되는 애플리케이션은 운영체제(OS)와 독립적으로 실행됨.
  • 컨테이너를 이용하면 개발 환경과 배포 환경의 차이를 최소화할 수 있음.
  • 대표적인 컨테이너 기술: Docker, Podman, LXC, CRI-O

💡 쉽게 말하면, 컨테이너는 가상 머신보다 가볍고 빠르게 애플리케이션을 실행할 수 있는 기술이야!

📌 가상 머신(VM)과 컨테이너의 차이

가상 머신(VM) 컨테이너(Container)
실행 방식 전체 운영체제(OS)를 가상화 프로세스를 격리하여 실행
무게 무거움 (OS 포함) 가벼움 (OS 공유)
부팅 속도 느림 (몇 분) 빠름 (몇 초)
자원 활용 독립된 OS를 사용 OS를 공유하여 효율적
대표 기술 VMware, VirtualBox, KVM Docker, Podman, LXC

💡 VM은 하드웨어를 가상화하는 개념이고, 컨테이너는 운영체제(OS) 수준에서 가상화를 하는 개념이야!

📌 컨테이너가 리눅스에서 시작된 이유

컨테이너는 리눅스의 핵심 기능(커널 기능)을 활용하여 만들어졌어.

즉, 리눅스에서 제공하는 프로세스 격리 기술이 컨테이너 기술의 기반이야!

🔹 컨테이너의 핵심 리눅스 기술

리눅스 기술 역할
Namespaces 프로세스를 격리하여 독립적인 실행 환경 제공
Cgroups (Control Groups) CPU, 메모리 등 자원 사용을 제한하고 관리
OverlayFS 컨테이너 이미지 레이어를 효율적으로 관리
Chroot (Change Root) 특정 디렉터리를 루트(root) 디렉터리처럼 사용
Seccomp & AppArmor 보안 정책을 적용하여 컨테이너 보호

💡 즉, 컨테이너는 리눅스의 격리(Namespaces)와 자원 제한(Cgroups) 기능을 활용해서 만들어진 기술이야!

📌 브릿지 네트워크(Bridge Network)란?

컨테이너가 실행되면 서로 통신할 수 있어야 해.

이때 컨테이너들이 같은 네트워크 안에서 통신할 수 있도록 도와주는 가상의 네트워크가 "브릿지 네트워크"야!

💡 브릿지 네트워크(Bridge Network)는 여러 개의 컨테이너를 같은 네트워크로 묶어, 마치 물리적인 네트워크처럼 통신할 수 있도록 해주는 기술이야!

📌 브릿지 네트워크(Bridge Network)의 개념

  • 리눅스에서는 네트워크 인터페이스를 가상화하여 컨테이너 간 통신을 가능하게 함.
  • 브릿지 네트워크를 사용하면 컨테이너끼리 같은 네트워크 안에서 서로 통신할 수 있음.
  • 컨테이너가 생성될 때 브릿지 네트워크에 연결되면 IP 주소를 할당받고, 같은 브릿지 네트워크 내에서는 자유롭게 통신할 수 있음.
  • 외부 네트워크와 연결되지 않아도 내부에서 자체적으로 통신 가능.
  • 쿠버네티스에서 Pod들은 브릿지 네트워크를 통해 서로 연결됨.

💡 쉽게 말해, 브릿지 네트워크는 여러 개의 컨테이너를 하나의 가상의 네트워크로 묶어주는 역할을 해!

📌 브릿지 네트워크의 특징

  1. 같은 브릿지 네트워크에 있는 컨테이너(Pod, VM 등)는 직접 통신 가능.
  2. 하나의 네트워크 인터페이스(eth0)만 있어도 여러 개의 가상 네트워크 인터페이스를 만들 수 있음.
  3. 외부 네트워크와 연결되지 않아도 내부 통신이 가능함.
  4. 쿠버네티스에서는 브릿지 네트워크를 이용해 Pod들이 같은 노드 안에서 서로 통신하도록 설정됨.

📌 컨테이너 + 브릿지 네트워크 = 어떻게 동작할까?

컨테이너는 기본적으로 서로 독립적인 환경에서 실행됨.

하지만, 브릿지 네트워크를 사용하면 같은 네트워크 안에서 컨테이너들이 서로 통신할 수 있어.

🔹 예제: 두 개의 컨테이너가 브릿지 네트워크에서 통신하는 과정

[컨테이너1] --(Bridge)--> [브릿지 네트워크] --(Bridge)--> [컨테이너2]
  • 컨테이너1과 컨테이너2는 같은 브릿지 네트워크에 연결됨.
  • 컨테이너1에서 컨테이너2로 데이터를 보낼 수 있음.
  • 쿠버네티스에서는 Pod 간 통신도 동일한 방식으로 동작.

브리지 네트워크를 사용하면 같은 브리지에 연결된 컨테이너끼리 내부 통신할 수 있다.

📌 브릿지 네트워크와 쿠버네티스

쿠버네티스에서는 각 Pod가 고유한 IP 주소를 가지지만, 같은 노드 안에서는 브릿지 네트워크를 통해 통신해.

그러나 기본적으로 리눅스는 브릿지 네트워크에서 패킷을 필터링하지 않기 때문에, br_netfilter 설정을 활성화해야 해!

sudo modprobe br_netfilter

✅ 브릿지 네트워크에서 iptables가 패킷을 필터링할 수 있도록 설정함.

echo 'net.bridge.bridge-nf-call-iptables=1' | sudo tee -a /etc/sysctl.d/k8s.conf
sudo sysctl --system

✅ 쿠버네티스 네트워크 정책이 올바르게 동작하도록 설정함.

📌 정리

✅ 컨테이너(Container)는 애플리케이션과 실행 환경을 패키징해서 가볍고 빠르게 실행할 수 있는 기술.

✅ 컨테이너는 리눅스의 네임스페이스(Namespaces), Cgroups 등 커널 기능을 활용해서 격리된 환경을 제공함.

✅ 브릿지 네트워크(Bridge Network)는 여러 개의 컨테이너를 같은 네트워크로 묶어 서로 통신할 수 있도록 해줌.

✅ 쿠버네티스에서는 브릿지 네트워크를 사용하여 Pod들이 서로 연결됨.

✅ 기본적으로 리눅스에서는 브릿지 네트워크의 패킷을 iptables에서 필터링하지 않기 때문에, br_netfilter 설정을 활성화해야 함.

frontend kubernetes-frontend
    bind *:6443
    mode tcp
    default_backend kubernetes-backend

backend kubernetes-backend
    mode tcp
    balance roundrobin
    option ssl-hello-chk
    server master1 192.168.0.11:6443 check
    server master2 192.168.0.12:6443 check
    server master3 192.168.0.13:6443 check

Kubespray에서는 아래처럼 인벤토리 설정에 명시:

apiserver_loadbalancer_domain_name: "192.168.0.10"

loadbalancer_apiserver:
  address: 192.168.0.10
  port: 6443

이 값은 다음과 같이 사용됨:

  • kubeadm의 controlPlaneEndpoint에 들어감
  • kubeconfig (admin.conf 등) 내 cluster.server 주소로 들어감 → https://192.168.0.10:6443
  • 마스터 간 통신, 워커의 join, 외부 kubectl 접속 모두 이 주소 기준

✅ 4. 주의할 점

  • HAProxy 설정만 해두고 apiserver_loadbalancer_domain_name을 누락하면 비정상 연결 발생
  • 모든 마스터가 로드밸런서를 통해 join하지 않으면 HA가 아닌 단일 마스터 기반 동작으로 fallback됨
  • 로드밸런서는 외부 접근용 + 클러스터 내부 통신용 모두 담당

후속 참고 항목은 HAProxy 설정 템플릿과 admin.conf 구조다.

쿠버네티스 프록시

쿠버네티스 프록시는 쿠버네티스 클러스터 내에서 서비스 간 통신을 관리하고 로드 밸런싱을 수행하는 역할을 하는 중요한 구성 요소 중 하나입니다. 이를 통해 서비스 간의 통신을 안전하고 효율적으로 라우팅하며, 서비스의 확장과 로드 밸런싱을 담당합니다.

여러 종류의 쿠버네티스 프록시가 있지만, 가장 널리 사용되는 두 가지 종류는 kube-proxy와 ingress controller입니다.

  1. kube-proxy:
  • kube-proxy는 쿠버네티스 노드에서 동작하는 네트워크 프록시 서비스입니다.
  • 각 노드에서 실행되며, 클러스터 내부의 서비스에 대한 로드 밸런싱을 담당합니다.
  • NodePort와 같은 서비스 유형을 통해 외부에서 클러스터 내의 서비스에 접근할 수 있도록 지원합니다.
  • IPVS, iptables 등과 같은 다양한 프록시 모드를 지원하며, 클러스터 구성에 따라 선택할 수 있습니다.
  1. Ingress Controller:
  • Ingress는 쿠버네티스에서 외부 트래픽을 클러스터 내부의 서비스로 라우팅하는 규칙을 정의하는 API 객체입니다.
  • Ingress Controller는 이러한 Ingress 규칙을 해석하고, 실제로 HTTP(S) 트래픽을 적절한 서비스로 전달하는 역할을 합니다.
  • 주로 Nginx, Traefik, HAProxy와 같은 인그레스 컨트롤러를 사용하여 구현됩니다.

쿠버네티스 프록시의 역할은 다음과 같습니다:

  • 로드 밸런싱: 클러스터 내 여러 인스턴스에 대한 트래픽을 균등하게 분산하여 서비스의 가용성을 높이고 성능을 향상시킵니다.
  • 서비스 디스커버리: 클러스터 내의 서비스들을 자동으로 발견하고, 동적으로 그에 맞는 라우팅을 제공합니다.
  • 네트워크 정책: 서비스 간의 통신을 제어하고, 보안 및 네트워크 정책을 적용하여 안전한 통신을 유지합니다.

쿠버네티스 프록시는 클러스터의 네트워킹 구성에 핵심적이며, 서비스 간 통신의 원활한 운영을 지원합니다.

VM1, VM2

  • OpenStack에서 생성한 가상 머신(Virtual Machine) 들
  • 각각의 VM에는 하나 이상의 가상 NIC(네트워크 인터페이스 카드) 가 붙어 있어.
  • 여기서는 각각 eth0 같은 NIC가 하나씩 있는 구조로 그려져 있음

Tap

  • VM에 연결된 NIC는 실제로는 hypervisor 수준에서 생성된 TAP 인터페이스와 연결돼.
  • 이 TAP 인터페이스들은 호스트(OS)의 네트워크 인터페이스이며, VM에서 나가는 트래픽이 가장 먼저 도달하는 지점이야.
  • 즉, tap0은 VM1의 eth0과 연결되고, tap1은 VM2의 eth0과 연결돼 있어.
  • 이 인터페이스는 libvirt나 qemu-kvm이 생성하며, 일반적으로 qbr, vnet, tap 등의 이름으로 나타나.

VM과 Tap의 관계

[ VM1 ] eth0 ─────> tap0 ─────> OVS(br-int)
[ VM2 ] eth0 ─────> tap1 ─────> OVS(br-int)

[인스턴스] eth0 ─────> tap0 ─────> OVS(br-int)

  • 이 부분은 tap 인터페이스들이 OVS의 브리지로 연결되는 흐름을 나타냄
  • 예를 들어, tap0은 OVS의 br-int 브리지에 하나의 포트로 연결됨
  • 이 연결을 통해 VM의 트래픽이 OVS 내부를 통해 흐르게 되는 것

1. br-int란?

br-int는 Open vSwitch(OVS)에서 사용하는 가상의 브리지(Virtual Switch) 중 하나이며,

OpenStack Neutron에서 VM 내부 네트워크를 처리하는 중심 허브 역할을 해.

  • br-int = "Integration Bridge"
  • 말 그대로, 여러 네트워크 요소를 통합하는 역할을 해.
  • VM의 가상 NIC(tap 장치), 다른 브리지들(예: br-tun), 보안그룹, DHCP, Floating IP 등과 연결돼.

2. br-int의 역할

기능 설명
VM의 트래픽 수신/전송 VM의 tap 장치가 여기에 연결됨. VM ↔ 외부 네트워크의 시작점.
보안그룹 적용 Neutron이 br-int에 flow rule을 생성해서 VM 간 통신을 제한함.
L2 브리지 기능 내부 네트워크 구성, VLAN 처리 없이 포트 연결로 동작
터널 브리지(br-tun) 연결 VXLAN을 통한 네트워크 노드 간 통신 경로 제공 (patch 포트 사용)

3. tap 장치와 br-int의 관계

VM이 생성되면, 하이퍼바이저(libvirt)가 가상의 네트워크 인터페이스(tapX) 를 생성해.

이 tap 장치는 마치 VM의 이더넷 카드처럼 동작하며, 이를 br-int에 연결한다.

[VM eth0]
   │
[tapX]  ──▶  [br-int]  ──▶  내부 통신 (br-tun, DHCP, etc)
  • tapX는 리눅스 커널이 제공하는 가상 네트워크 인터페이스
  • 이 인터페이스는 OVS 브리지에 포트로 등록됨
  • br-int는 이러한 tap 장치들을 통해 VM 트래픽을 수신하고 처리함

4. 전체 흐름 간단 정리

[VM1 eth0] → [tap0] ─┐
                     ├→ [br-int] → patch-int → [br-tun] → VXLAN 터널 등
[VM2 eth0] → [tap1] ─┘
  • br-int는 여러 VM의 tap 장치를 한데 모으는 가상의 브리지이자, 스위치 역할
  • 내부 통신, 외부 통신으로 가는 트래픽의 중심 경로
  • 보안그룹은 이 br-int의 포트(flow)에 적용됨

1. 브리지(Bridge)의 기본 개념

  • 브리지(Bridge)는 OSI 2계층(L2, 데이터링크 계층) 장비
  • 여러 개의 네트워크 인터페이스(포트)를 묶어서, 같은 네트워크(LAN)처럼 동작하도록 해줘.
  • 목적은 패킷 전달과 네트워크 분할이야.

브리지는 두 개 이상의 네트워크 세그먼트를 연결하고, MAC 주소를 기준으로 프레임을 전달하는 장비야.

2. 동작 방식

  1. 각 포트로 들어온 이더넷 프레임을 MAC 주소 테이블에 기록.
  2. 이후 들어오는 프레임의 목적지 MAC 주소를 보고,
  • 해당 포트만 프레임을 전달함 (flooding 아님).
  • 만약 주소를 모르면 모든 포트로 브로드캐스트.
[PC1] ────┐
          │
       ┌───────┐
       │ Bridge│ ← MAC 주소 테이블로 학습
       └───────┘
          │
[PC2] ────┘

3. 스위치와의 관계

  • 스위치는 멀티포트 브리지(multport bridge)
  • 내부 구조나 동작은 거의 같고, 성능과 기능이 강화된 브리지라고 보면 됨
구분 브리지 스위치
포트 수 보통 2~4개 수십 개 이상 가능
속도 느림 하드웨어 기반이라 빠름
기능 단순 MAC 전달 VLAN, QoS 등 고급 기능

4. 리눅스와 가상화에서의 브리지

  • 리눅스에서 br0, br-int 같은 가상 브리지는:
  • 여러 NIC나 tap 인터페이스를 묶는 논리적 스위치 역할
  • 실제로는 커널 수준에서 브리지 모듈(bridge module) 이 처리.

   │        │

      │
   [eth0]

요약

  • 브리지는 MAC 주소 기반으로 프레임을 전달하는 2계층 장비.
  • 네트워크를 분할하고 충돌 도메인을 줄여줌.
  • 리눅스/OVS에서 브리지는 가상 스위치처럼 동작함.

기본 개념

OpenStack Neutron에서 OVS(Open vSwitch)는 가상 브리지를 여러 개 만들어 VM 네트워크 트래픽을 처리합니다. 그 중 핵심 역할을 하는 브리지가 다음 두 개입니다:

브리지 이름 전체 이름 주요 역할
br-int Integration Bridge VM에서 나오는 트래픽의 중심 허브. 보안 그룹 등 정책 적용
br-tun Tunnel Bridge VXLAN/GRE 터널 처리. 다른 노드와의 통신 중간지점

patch-int와 patch-tun의 역할

브리지 구성

  • br-int: 통합 브리지. VM(tap 장치) 가 여기에 붙어 있음.
  • br-tun: 터널 브리지. VXLAN 터널 처리를 담당하고 물리 NIC(eth0)와 연결됨.

각각의 포트 설명

포트 이름 역할
patch-int VM에서 발생한 트래픽을 br-tun 쪽으로 넘겨줌 (출구)
patch-tun 외부에서 온 VXLAN 트래픽을 디캡슐화한 후 br-int 쪽으로 넘겨줌 (입구)

VM → 외부 (Outbound)

VM → tapX → br-int → patch-int → br-tun → VXLAN Encapsulation → eth0
  • VM에서 나온 트래픽은 br-int에서 patch-int로 들어가고,
  • patch-tun을 통해 br-tun으로 연결되어,
  • VXLAN으로 캡슐화된 후 eth0을 통해 외부 전송됨.

외부 → VM (Inbound)

eth0 → br-tun →VXLAN Decapsulation →  patch-tun → patch-int → br-int → tap0 → VM
  • 외부에서 VXLAN으로 온 트래픽은 eth0을 통해 들어오고,
  • br-tun에서 디캡슐화됨.
  • patch-tun을 통해 patch-int로 이동해서,
  • br-int를 통해 해당 VM으로 전달됨.

Multus - NetworkAttachmentDefinition

1. NAD란?

NAD = NetworkAttachmentDefinition

Kubernetes에서 Pod에 추가 네트워크 인터페이스를 붙이기 위한 정의를 의미하는 리소스

Multus CNI가 설치된 클러스터에서만 동작하며,

Pod에 eth0 외에 net1, net2 같은 보조 네트워크를 붙이고 싶을 때 사용함.

개념 설명
기본 Pod 기본 CNI(예: Cilium, Calico)가 eth0만 붙여줌
Multus CNI NAD를 참고해서 net1, net2 같은 보조 NIC 추가
NAD “이 보조 NIC는 어떻게 만들지?”를 JSON으로 정의해둔 리소스

2. NAD 구성요소 요약

apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata:
  name: sample-nad-net         # <- metadata.name: 이 NAD의 이름
  namespace: default
spec:
  config: '{
    "cniVersion": "0.3.1",
    "type": "macvlan",         // <- type: 사용할 CNI 종류
    "master": "ens7",          // <- master: 실제 NIC 이름
    "mode": "bridge",          // <- mode: L2 연결 방식
    "vlan": 100,               // <- vlan: VLAN ID 지정
    "ipam": {                  // <- ipam: IP 할당 방식
      "type": "whereabouts",
      "range": "192.168.100.0/24",
      "range_start": "192.168.100.100",
      "range_end": "192.168.100.200",
      "gateway": "192.168.100.1"
    }
  }'
항목 설명
metadata.name NAD 이름. Pod에 붙일 때 annotations.k8s.v1.cni.cncf.io/networks에서 참조함
spec.config CNI 설정을 담는 JSON 문자열. 어떤 네트워크를 어떻게 붙일지 정의
type 사용할 CNI 종류 (macvlan, ipvlan, bridge, host-device, sriov 등)
ipam IP 주소 할당 방식 (static, whereabouts, dhcp 등)
master CNI가 연결할 물리 NIC 이름 (예: ens7)
mode 동작 방식 (bridge, private, l2, l3 등, type에 따라 다름)
vlan VLAN 태깅이 필요할 경우 ID 지정
device / deviceID / pfName host-device나 SR-IOV에서 물리 인터페이스 식별용

3. CNI type별 NAD 구성 요약

목적 type 주요 설정 필드 설명
리눅스 브릿지를 통한 통신 bridge "bridge": "br0" Host의 Linux bridge에 Pod를 연결. 테스트 환경에 적합
가상 MAC 인터페이스로 외부 통신 macvlan "master": "ens7", "mode": "bridge" 외부망 직접 연결. L2 기반 통신 가능. VLAN 설정 가능
MAC 없이 L3 기반 외부 통신 ipvlan "master": "ens7", "mode": "l3" Host의 MAC을 공유. 외부와만 통신 시 적합
물리 NIC 또는 VF를 직접 할당 host-device "device": "ens7" SR-IOV 없이도 특정 NIC를 Pod에 직접 바인딩
SR-IOV VF를 Pod에 직접 연결 sriov "vf": 0, "vlan": 100, "trust": "on" 등 고성능 네트워크. 추가 CRD 및 Node 설정 필요
DHCP로 IP 자동 할당 macvlan 또는 bridge "ipam": \{ "type": "dhcp" \} DHCP 서버 필요. 운영환경에선 권장되지 않음
VLAN 태깅 macvlan 또는 sriov "vlan": 200 Pod별 VLAN 분리 필요할 때 사용

Multus + whereabouts

Multus를 통해 Pod에 네트워크를 할당하는 주요 방법

1. bridge 방식

  • 개념: 사전에 Linux Bridge를 생성하고 NIC을 연결한 후, Pod에 해당 bridge를 연결
  • 특징:
  • 간단한 테스트 환경에 적합
  • Static IP 설정 가능
  • 예시:
{
  "cniVersion": "0.4.0",
  "name": "my-bridge-net",
  "type": "bridge",
  "bridge": "br0",
  "isGateway": true,
  "ipMasq": true,
  "hairpinMode": true,
  "ipam": {
    "type": "host-local",
    "subnet": "10.22.0.0/16",
    "rangeStart": "10.22.0.100",
    "rangeEnd": "10.22.0.200",
    "routes": [
      { "dst": "0.0.0.0/0" }
    ],
    "gateway": "10.22.0.1"
  }
}

모든 노드에 해당 bridge가 생성되어있어야함

2. host-device 방식

  • 개념: 노드의 NIC (예: ens7)를 그대로 Pod에 할당.
  • 특징:
  • 가장 직접적인 방식 (성능 최상)
  • NIC 1개를 1 Pod에서만 사용 가능 (공유 불가)
  • Neutron과 연동 시 허용된 주소 쌍 설정 필수
  • 예시:
{
  "type": "host-device",
  "device": "ens7"
}

해당 nic의 소유권을 넘겨주는 방식임. 해당 pod의 nic에는 뉴트론 네트워크의 IP가 지정되며 다른 pod는 해당 nda를 사용할 수 없음

3. ipvlan 방식

  • 개념: 하나의 물리 NIC를 여러 Pod가 공유하되, IP는 각자 독립적으로 가짐
  • 특징:
  • NIC 공유 가능
  • mode: l2 또는 l3 가능
  • IP 충돌 방지를 위해 static 또는 whereabouts IPAM과 함께 사용
  • 예시 (+ whereabouts 조합):
{
  "cniVersion": "0.4.0",
  "name": "ipvlan-net",
  "type": "ipvlan",
  "master": "ens7",
  "mode": "l3",
  "ipam": {
    "type": "whereabouts",
    "range": "192.168.200.0/24",
    "range_start": "192.168.200.100",
    "range_end": "192.168.200.200",
    "gateway": "192.168.200.1"
  }
}

ip를 통해 nic을 나누어 사용하는 방식임

whereabouts가 해당 클러스터에 중복되지 않는 PodIP를 지정해줌

4. macvlan 방식

  • 개념:

하나의 물리 NIC에서 여러 개의 가상 MAC 주소를 가진 네트워크 인터페이스(macvlan)를 생성하여 Pod 또는 컨테이너에 부여하는 방식.

→ 각 Pod이 고유한 MAC + IP를 가짐

  • 특징:
  • ✅ 일반 NIC에서도 동작 가능 (SR-IOV 필요 없음)
  • ✅ L2 계층에서 동작 → Host ↔ Pod ↔ 외부망 통신이 가능
  • ✅ iptables, NAT 없이도 고성능 L2 통신 가능
  • ❌ 같은 NIC에서 생성된 Pod 간에는 mode에 따라 통신 제한 (ex. private)
  • ❌ L2 브로드캐스트 환경이 안 되는 클라우드에서는 사용 어려움
  • 활용 예시:
  • 외부 네트워크에 직접 연결되어야 하는 Pod (예: 특정 VLAN, 실시간 API Client)
  • 고성능 네트워크 처리 필요한 서비스 (ex. 패킷 분석기, 방화벽)
apiVersion: "k8s.cni.cncf.io/v1"
kind: NetworkAttachmentDefinition
metadata:
  name: macvlan-bridge
spec:
  config: '{
    "cniVersion": "0.3.1",
    "type": "macvlan",
    "master": "ens7",
    "mode": "bridge",
    "ipam": {
      "type": "static",
      "addresses": [
        {
          "address": "192.168.10.2/24",
          "gateway": "192.168.10.1"
        }
      ]
    }
  }'

4. IPAM 설정 방식 (Multus가 CNI에 붙일 때 IP를 어떻게 할당하느냐)

방식 설명 예시
static 고정 IP를 명시적으로 지정 ✅ 단순
whereabouts IP 충돌 방지, 자동 IP 할당 (동적 IPAM) ✅ 추천
dhcp DHCP 서버로부터 IP를 받아옴 ⚠️ 외부 DHCP 필요
host-local 노드별 로컬 IPAM (노드 간 IP 충돌 가능성 있음) ❌ 비추천

Whereabouts란?

1. 개요

Whereabouts는 Kubernetes CNI에서 사용하는 분산형 IP 주소 자동 할당기(IPAM)이다

특히 macvlan, ipvlan, sriov 같이 Pod가 별도 IP를 필요로 하는 CNI 플러그인들과 함께 사용됨.

2. Whereabouts가 필요한 이유

기존 IPAM(host-local)의 한계

기존 방식 문제점
host-local IPAM 노드마다 로컬에서 IP를 관리하므로 노드 간 IP 충돌 가능
static IP 운영자가 직접 IP를 지정 → 비효율적, 실수 발생 가능
DHCP 별도 서버 필요, 보안 문제로 클러스터에서 잘 안 씀

멀티노드 + 다중 NIC + Multus 환경에서는 실질적으로 사용할 수 없음

예시

A. macvlan + whereabouts:

  1. macvlan은 각 Pod에 고유한 MAC과 IP를 부여하여 L2 네트워크에 직접 붙이는 방식
  2. 외부망과 직접 통신이 가능하고, Host ↔ Pod 통신도 가능 (bridge 모드)
  3. Pod 간에도 통신 가능 (mode: bridge)
  4. 고정 IP or DHCP 없이, 자동으로 IP를 부여하려면 whereabouts 필요

활용 예시:

  • 보안 장비, 방화벽, 실시간 분석기 같은 네트워크 센시티브한 서비스
  • VLAN 외부망 통신이 필요한 컨테이너

B. ipvlan + whereabouts

  1. ipvlan은 MAC 없이 Host NIC의 MAC을 공유하여 IP로만 통신 (L3 기반)
  2. Pod ↔ Pod 통신은 제한되지만, 외부 통신 전용 API Client처럼 가볍고 고립된 워크로드에 적합
  3. 성능도 우수하며, macvlan보다 네트워크 제약이 덜함

활용 예시:

  • 외부 API polling 전용 Pod
  • 내부 통신은 불필요하고 외부 전용 트래픽만 처리하는 서비스

구성 예시 (macvlan + whereabouts)

apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata:
  name: macvlan-net
spec:
  config: '{
    "cniVersion": "0.3.1",
    "type": "macvlan",
    "master": "ens7",
    "mode": "bridge",
    "ipam": {
      "type": "whereabouts",
      "range": "192.168.100.0/24",
      "range_start": "192.168.100.100",
      "range_end": "192.168.100.200",
      "gateway": "192.168.100.1"
    }
  }'

ipvlan도 "type": "ipvlan"만 바꾸면 구성 방식은 동일함.

요약 비교표

항목 macvlan + whereabouts ipvlan + whereabouts
계층 L2 (MAC 있음) L3 (MAC 없음)
통신 방식 MAC 기반 브로드캐스트 IP 라우팅 기반
Pod ↔ Pod 통신 가능 (bridge 모드) 제한됨 (L3 모드)
Host ↔ Pod 통신 가능 제한됨
외부망 통신 가능 가능
보안 분리 낮음 (L2 노출) 높음 (L3 격리)
추천 사용 고성능, 직접 외부망 연결 서비스 외부 통신 전용 API 클라이언트 등

Whereabouts는 macvlan, ipvlan처럼 “Pod에게 직접 외부 IP를 부여해야 하는” 환경에서 필수적인 IPAM 도구다.

DHCP나 static 설정 없이, 멀티노드에서도 충돌 없는 자동 IP 할당을 가능하게 해준다.

특히 Multus, macvlan, ipvlan, SR-IOV 등으로 멀티네트워크를 구성하는 현실적인 Kubernetes 환경에서 안정성과 편의성을 모두 잡기 위해 사용하는 핵심 요소

Multus란?

개요

Multus는 Kubernetes에서 Pod에 여러 개의 네트워크 인터페이스를 붙일 수 있게 해주는 CNI 플러그인. 기본적으로 Kubernetes는 한 Pod당 하나의 네트워크 인터페이스(eth0)만 붙이는데, Multus를 사용하면 Pod에 eth0 외에도 추가 인터페이스(예: net1, net2 등)를 연결할 수 있음.

Multus의 개념 정리

  • 기본 CNI 플러그인 위에 동작하는 meta-CNI 플러그인
  • Pod에 다중 네트워크를 할당할 수 있게 해줌
  • 기본 인터페이스(eth0)는 기존 CNI가 담당하고, 추가 인터페이스는 Multus가 지정한 다른 CNI 플러그인(e.g., macvlan, sriov, ipvlan 등)이 담당함

왜 필요할까?

  1. 내부망/외부망 분리
  • eth0은 Kubernetes 클러스터 내부 통신용, net1은 외부망 통신용 등.
  1. 특정 네트워크 하드웨어 장치 사용 (e.g., SR-IOV, DPDK)
  2. 보안 및 트래픽 분리
  • 각 네트워크마다 역할이 다르면 보안/정책 적용이 쉬움.
  1. 네트워크 기능 가상화(NFV) 환경에서는 필수적

편입 후 검증 메모

  • Service: port, targetPort, 컨테이너가 실제 listen하는 port는 서로 다른 값일 수 있다. 같아야 한다는 원문 단정은 일반 규칙이 아니다.
  • kube-proxy: Service 가상 IP를 구현하는 방식은 iptables·IPVS 등 환경에 따라 다르며, CNI가 맡는 Pod 네트워크와 역할을 구분한다.
  • Multus: 기본 CNI 위에서 추가 interface를 요청하는 meta-plugin이다. NetworkAttachmentDefinition만 만들었다고 실제 네트워크·IPAM·라우팅이 자동 완성되지는 않는다.
  • 환경 주소: 공개본의 실습 주소와 host 값은 예시로만 읽고, 실제 cluster CIDR·MTU·security group을 기준으로 다시 검증한다.
