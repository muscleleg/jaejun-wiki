마지막 커밋에서 .DS_Store 제거 후 히스토리 정리하기 (force push 방식)

📌 마지막 커밋에서.DS_Store 제거 후 히스토리 정리하기 (force push 방식)

.DS_Store가 실수로 마지막 커밋에 포함되어 remote까지 올라간 상황에서, 해당 파일을 커밋 기록에서 완전히 제거하고 “깔끔한 커밋 하나”로 다시 만들기 위한 정리 문서이다.

이 방식은 커밋 히스토리를 다시 쓰는 작업이므로, 협업 중인 공용 브랜치(main, develop 등)에서는 신중해야 한다. 개인 브랜치나 PR 브랜치에서 사용하는 것이 적절하다.

왜 이런 작업이 필요한가

macOS는 디렉토리를 열 때 자동으로 .DS_Store 파일을 생성한다.

이 파일은 프로젝트와 무관한 OS 메타데이터 파일이기 때문에 git에 포함되면 안 된다.

이미 커밋되고 push까지 되었다면 두 가지 선택이 있다.

  • 기록은 그대로 두고 “제거 커밋”을 하나 더 추가하는 방법
  • 마지막 커밋을 수정해서 처음부터 .DS_Store가 없었던 것처럼 만드는 방법

여기서는 두 번째 방식(히스토리 정리 방식)을 설명한다.

전체 흐름의 개념

이 작업은 다음 순서로 이루어진다.

  1. 마지막 커밋을 취소한다.
  2. .DS_Store를 git 추적에서 제거한다.
  3. .gitignore에 .DS_Store를 등록한다.
  4. 나머지 정상 변경사항만 다시 커밋한다.
  5. remote 히스토리를 강제로 덮어쓴다.

1단계: 마지막 커밋 취소

git reset HEAD~1

이 명령은 “마지막 커밋만” 없앤다.

중요한 점은 파일 변경 내용은 사라지지 않는다는 것이다.

커밋만 취소되고, 변경 내용은 다시 작업 중 상태로 돌아온다.

즉, 실수로 포함된 .DS_Store와 정상 변경사항들이 모두 로컬에 그대로 남아 있다.

2단계:

.DS_Store

를 git 추적에서 제거

git rm --cached .DS_Store

이 명령은 .DS_Store 파일을 디스크에서 삭제하지 않는다.

git이 추적하지 않도록 인덱스에서만 제거한다.

이 단계에서 .DS_Store는 더 이상 커밋 대상이 아니다.

3단계: .gitignore에 등록

echo ".DS_Store" >> .gitignore

이렇게 해야 앞으로 .DS_Store가 자동으로 add되지 않는다.

이미 추적 중인 파일은 .gitignore에 추가해도 자동으로 추적 대상에서 빠지지 않으므로, 먼저 git rm --cached를 실행해야 한다.

4단계: 변경사항 다시 커밋

git add .
git commit -m "clean commit"

이제 커밋에는 다음만 포함된다.

  • 원래 의도했던 정상 변경사항
  • .gitignore 수정
  • .DS_Store는 제외

이 시점에서 git show --name-only로 확인하면 .DS_Store가 없어야 정상이다.

5단계: remote 히스토리 덮어쓰기

git push --force

왜 force가 필요한가?

이미 remote에는 “이전 커밋”이 올라가 있다.

우리는 그 커밋을 reset으로 없애고 새 커밋을 만들었기 때문에,

로컬과 remote의 히스토리가 달라진다.

일반 push는 이를 거부한다.

그래서 강제로 덮어써야 한다.

더 안전한 방법

가능하다면 다음 명령을 사용하는 것이 더 안전하다.

git push --force-with-lease

이 옵션은 “내가 마지막으로 확인한 remote 상태와 같을 때만 force” 한다.

그 사이에 다른 사람이 push했다면 실패해서 사고를 막아준다.

이 방식이 안전한 경우

  • 개인 브랜치
  • PR 브랜치
  • 혼자 작업 중인 기능 브랜치

이 방식이 위험한 경우

  • main 브랜치
  • 여러 명이 동시에 작업 중인 브랜치
  • 이미 다른 사람이 pull 받은 커밋이 있는 경우

이 경우에는 force 대신 “제거 커밋 추가 방식”이 더 적절하다.

핵심 요약

이 작업은 단순히 파일을 지우는 것이 아니라,

“마지막 커밋을 다시 쓰는 작업”이다.

reset은 커밋만 취소한다.

rm –cached는 git 추적만 끊는다.

.gitignore는 재발 방지 장치다.

force push는 히스토리 덮어쓰기다.

amend

git commit –amend –no-edit

1. 한 줄 설명

git commit --amend --no-edit는 가장 최근 커밋에 새로운 변경사항을 추가해서 커밋을 다시 만드는 명령어이다.

단, 기존 커밋 메시지는 그대로 유지한다.

즉,

“방금 만든 커밋을 수정하지만 메시지는 바꾸지 않는다”

2. 왜 필요한가

개발하다 보면 이런 상황이 자주 생긴다.

예시

git add .
git commit -m "Add login API"

그런데 커밋하고 나서 보니까

  • 파일 하나를 add 안 했거나
  • 코드 한 줄을 수정해야 하는 상황이 생긴다.

이때 보통 두 가지 방법이 있다.

방법 1 (커밋을 하나 더 만든다)

git add .
git commit -m "fix"

하지만 이렇게 하면 히스토리가 이렇게 된다.

Add login API
fix

커밋 히스토리가 지저분해진다.

방법 2 (이전 커밋에 합친다)

이때 사용하는 것이

git commit --amend

또는

git commit --amend --no-edit

3. 동작 원리

예시 상황

현재 상태

commit A

파일 수정 후

git add .
git commit --amend --no-edit

결과

commit A'

즉

A → A'

기존 커밋이 수정된 새로운 커밋으로 교체된다.

주의할 점

Git에서는 커밋을 수정하는 것이 아니라 새로운 커밋을 다시 만든다.

4. –no-edit 옵션 의미

기본 git commit --amend

git commit --amend

실행하면 커밋 메시지 편집 창이 열린다.

예시

Add login API

여기서 메시지를 수정할 수 있다.

하지만

git commit --amend --no-edit

옵션을 사용하면

  • 커밋 메시지 편집 창이 열리지 않는다
  • 기존 메시지를 그대로 사용한다

즉

기존 메시지 유지 + 커밋만 수정

5. 가장 흔한 사용 패턴

개발 중 가장 많이 쓰는 흐름

git add .
git commit -m "Add login API"

# 이후 코드 수정
git add .

git commit --amend --no-edit

결과

Add login API

커밋 하나만 남는다.

6. 언제 사용하면 좋은가

사용 추천 상황

  • 방금 커밋했는데 파일 하나 빠졌을 때
  • 오타 수정
  • 코드 한 줄 수정
  • 커밋을 깔끔하게 유지하고 싶을 때

특히 로컬 작업 중일 때 매우 유용하다.

7. 주의사항 (중요)

이미 원격 저장소에 push한 커밋에는 사용을 조심해야 한다.

이유

  • -amend는 커밋 히스토리를 변경하기 때문이다.

예시

이미 push된 커밋

origin/main

A

amend 하면

A → A'

이 상태에서 push 하면

git push --force

가 필요하다.

팀 프로젝트에서는 히스토리가 꼬일 수 있다.

따라서

push 전에만 사용하는 것이 가장 안전하다.

8. 한 줄 정리

git commit --amend --no-edit

의미

마지막 커밋에 변경사항을 추가하지만 커밋 메시지는 수정하지 않는다.

후속 정리 후보

  • git commit --amend
  • git rebase -i
  • fixup / squash
  • git push --force-with-lease

이 네 개 알면 Git 히스토리 관리 90%는 끝난다.

commit 취소

1️⃣ 아직 push 안 한 경우

✅ 가장 최근 commit만 취소 (내용은 유지)

git reset --soft HEAD~1

결과:

  • commit만 취소
  • 변경 내용은 staging 상태로 남아있음
  • 다시 commit 가능

✅ commit 취소 + staging도 해제 (파일 수정은 유지)

git reset --mixed HEAD~1

결과:

  • commit 취소
  • staging 해제
  • 파일은 수정된 상태로 남아있음

❗ commit 취소 + 수정 내용도 삭제

git reset --hard HEAD~1

결과:

  • commit 삭제
  • 변경 내용도 전부 삭제
  • 되돌릴 수 없음 (주의)

2️⃣ 이미 push 한 경우

⚠ 혼자 작업 중이고 강제로 되돌려도 되는 경우

git reset --hard HEAD~1
git push --force

주의:

  • 협업 중이면 절대 함부로 쓰면 안 됨
  • 다른 사람 히스토리 깨짐

✅ 안전하게 취소하고 싶다면 (히스토리 유지)

git revert HEAD

결과:

  • 이전 commit을 되돌리는 새 commit 생성
  • 협업 중이면 이 방법이 안전함

3️⃣ 최근 commit 메시지만 수정하고 싶을 때

git commit --amend

🔥 요약

상황 명령어
commit만 취소 git reset --soft HEAD~1
commit + staging 해제 git reset --mixed HEAD~1
commit + 변경내용 삭제 git reset --hard HEAD~1
이미 push했고 안전하게 되돌림 git revert HEAD
메시지만 수정 git commit --amend

Git 내부 구조 · 협업 · 충돌 · 그래프 완전 정리 노트

0️⃣ Git의 본질

Git은:

  • 파일 버전 관리 도구
  • 변경 이력 관리 시스템
  • 커밋 기반 그래프 구조 저장 시스템

Git은:

  • 코드 문법을 이해하지 않는다
  • 충돌 마커의 의미를 모른다
  • 텍스트를 “바이트 덩어리”로만 본다

Git이 이해하는 것:

  • 파일 스냅샷
  • 커밋 객체
  • parent 포인터
  • 브랜치가 가리키는 커밋

1️⃣ 협업 기본 원칙

🎯 원칙

Push 전에 반드시 원격 변경을 먼저 통합한다.

📌 기본 협업 흐름 (Merge 전략 기준)

git fetch
git merge origin/main
→ 충돌 해결
git add .
git commit
git push

의미

  1. 원격 변경을 먼저 가져오고
  2. 내 변경과 병합하고
  3. 충돌이 나면 수동으로 해결하고
  4. 최종 상태를 확정한 뒤
  5. push

❌ 왜 바로 push 하면 안 되는가?

에러 예시:

non-fast-forward

의미:

원격 브랜치가 내가 모르는 커밋을 가지고 있다.

Git은 원격 이력을 덮어쓰는 것을 막는다.

2️⃣ Fast-forward와 분기 판단 원리

🎯 Git이 push 시 검사하는 것

원격 브랜치가 가리키는 커밋이

내 브랜치의 조상(ancestor)인가?

📌 Fast-forward 가능한 경우

A --- B --- C --- D   (main)
                ^
           (origin/main)

D에서 parent를 따라가면 C가 나온다.

→ C 위에 D만 추가하면 된다

→ 브랜치 포인터 이동

→ fast-forward 가능

❌ Fast-forward 불가능한 경우

A --- B --- C   (origin/main)
         \
          D --- E   (main)

E에서 parent를 따라가도 C가 나오지 않는다.

→ 히스토리가 분기됨

→ non-fast-forward

→ push 거부

3️⃣ Git은 그래프를 어떻게 판단하는가?

🎯 Git은 그래프를 저장하는가?

아니다.

Git은 각 커밋에 parent 해시만 저장한다.

📌 커밋 객체 구조

각 커밋은 다음 정보를 가진다:

commit hash
tree hash
parent commit hash
author
message

핵심:

parent: 이전 커밋 해시

📌 예시

A --- B --- C   (origin/main)
         \
          D --- E   (main)

Git 내부 저장:

C → parent B
D → parent B
E → parent D

parent 포인터를 따라가면 DAG 구조가 된다.

Git은 “그래프를 그리는” 게 아니라

parent 체인을 따라가며 포함 여부를 검사한다.

4️⃣ Merge의 정체

📌 Merge를 하면

새 커밋 M이 생성된다:

A --- B --- C -------- M
       \              /
        D --- E -----

M의 내부:

parent1: E
parent2: C

→ parent가 2개

→ 두 히스토리를 합치는 지점

5️⃣ Rebase의 정체

Rebase는:

  • 기존 커밋을 복사해서
  • 다른 parent 위에 다시 만든다
A --- B --- C   (origin/main)
         \
          D --- E   (main)

rebase 후:

A --- B --- C --- D' --- E'

D', E'는 새 커밋이다.

→ parent가 달라진다

→ 해시가 바뀐다

6️⃣ Merge 충돌이 발생하는 이유

Git은 3-way merge를 시도한다.

비교 대상:

  1. 공통 조상 (base)
  2. 현재 브랜치 (HEAD)
  3. 병합 대상 브랜치 (origin/main)

자동 병합 불가능하면 충돌 발생.

7️⃣ 충돌 발생 시 상태 확인

git status

출력 예시:

both modified: example.py

8️⃣ 충돌 마커의 의미

파일 안에 이런 표시가 삽입된다:

<<<<<<< HEAD
내 브랜치 내용
=======
origin/main 내용
>>>>>>> origin/main

의미:

  • 위쪽: 현재 브랜치
  • 아래쪽: 병합 대상
  • 가운데: 구분선

9️⃣ 충돌 해결의 진짜 의미

중요:

마커를 지우는 것이 목적이 아니다.

최종 코드 상태를 직접 만드는 것이 목적이다.

가능한 선택:

  • 내 것만 남긴다
  • 원격 것만 남긴다
  • 둘을 조합해 새로 작성한다

⚠ 반드시 삭제해야 할 것:

<<<<<<<
=======
>>>>>>>

🔟 git add의 진짜 의미

git add 파일

은:

이 파일은 내가 최종 상태로 확정했다.

라는 선언이다.

Git은:

  • 마커가 남아있는지 검사하지 않는다
  • 문법 오류인지 검사하지 않는다
  • 논리적으로 맞는지 검사하지 않는다

단지:

  • 파일이 stage 되었는지

만 본다.

1️⃣1️⃣ 마커 안 지우고 add 하면?

예:

<<<<<<< HEAD
print("hello")
=======
print("hi")
>>>>>>> origin/main

이 상태에서:

git add test.py
git commit

하면,

이 텍스트 그대로 커밋에 저장된다.

Git은 그냥 문자열로 본다.

⚠ 발생 가능한 문제

  • Python → 문법 에러

Git은 책임지지 않는다.

1️⃣2️⃣ 여러 파일 충돌 시 처리 방식

예:

CONFLICT in a.py

CONFLICT in c.py

모든 파일 add 완료 시:

이제:

1️⃣3️⃣ 내부적으로 index는 어떻게 저장하나?

충돌 시 index는 3개 버전을 가진다:

  • stage 1: base
  • stage 2: HEAD
  • stage 3: merge 대상

git add 하면:

  • stage 1/2/3 제거
  • stage 0(정상 상태)로 변경

1️⃣4️⃣ 핵심 철학 요약

Git은:

  • 코드 의미를 모른다
  • 문법을 모른다
  • 충돌 마커를 이해하지 못한다
  • parent 포인터만 저장한다
  • 조상 포함 여부만 검사한다

충돌 해결은:

개발자의 책임이다.

git add는:

내가 책임진다는 선언이다.

Git 여러 커밋을 하나로 합치는 방법 (reset –soft + force push)

1️⃣ 언제 이 방법을 쓰는가?

다음과 같은 상황에서 사용합니다:

  • 최근 여러 커밋을 하나로 정리하고 싶을 때
  • WIP, 테스트 커밋 등을 깔끔하게 합치고 싶을 때
  • 이미 원격에 올라간 커밋을 정리하고 싶을 때
  • merge commit 포함해서 깔끔하게 히스토리를 재작성하고 싶을 때

2️⃣ 현재 상황 예시

8f5b43c (HEAD -> main, origin/main) Merge remote-tracking branch 'origin/main'
a6e0652 충돌 테스트3
f548450 WIP
83c8f07 #2.2 Your First AI Agent (07:30)
9ee68e3 충돌 테스트
763f49b #2.2 Your First AI Agent

여기서:

9ee68e3 ~ 8f5b43c

위 커밋들을 하나로 합치고 싶다고 가정합니다.

3️⃣ 핵심 원리

git reset --soft <기준커밋>은

HEAD를 기준 커밋으로 이동시키되

변경사항은 그대로 유지한다.

즉,

  • 커밋 기록은 제거
  • 변경 내용은 유지
  • 변경 내용은 stage 상태로 남음

4️⃣ 실행 단계

① 기준 커밋으로 HEAD 이동

git reset --soft 763f49b

의미:

  • 763f49b 이후 커밋들은 제거됨
  • 하지만 그 커밋들의 변경사항은 전부 stage 상태로 모임

② 새로운 하나의 커밋 생성

git commit -m "정리된 커밋"

이제 구조는:

763f49b
   \
    NEW_COMMIT

③ 원격 반영

히스토리가 바뀌었기 때문에 일반 push는 안 됩니다.

git push --force-with-lease

5️⃣ 왜 force-with-lease가 필요한가?

우리는 기존 커밋을 삭제하고

새 커밋을 만든 것입니다.

즉:

  • 커밋 해시가 바뀌었고
  • 원격과 히스토리가 달라졌습니다.

Git은 기본적으로 히스토리 덮어쓰기를 막기 때문에

force push가 필요합니다.

6️⃣ 왜 -force 대신 -force-with-lease인가?

  • -force-with-lease는:

내가 마지막으로 본 원격 상태가 그대로일 때만 덮어쓴다.

즉:

  • 다른 사람이 그 사이에 push했다면
  • 덮어쓰지 않고 실패합니다.

👉 훨씬 안전한 force입니다.

7️⃣ 내부적으로 무슨 일이 일어났는가?

기존 구조:

763f49b
   \
    9ee68e3
      \
       83c8f07
         \
          f548450
            \
             a6e0652
               \
                8f5b43c

reset 후:

763f49b

하지만 working tree에는

위 5개 커밋의 변경 내용이 모두 존재.

새 commit 후:

763f49b
   \
    NEW_COMMIT

8️⃣ reset –soft / –mixed / –hard 차이

옵션 커밋 이동 stage 유지 파일 유지
–soft O O O
–mixed O X O
–hard O X X

우리는 --soft를 쓴 이유:

변경 내용은 유지하면서 커밋만 제거하기 위해

9️⃣ 이 방법의 장점

  • merge commit 포함 커밋 정리가 쉬움
  • interactive rebase보다 단순
  • 실수 가능성 낮음
  • 한 번에 여러 커밋 합치기 쉬움

🔟 반드시 주의할 점

이 방법은:

히스토리를 재작성한다.

따라서:

  • 개인 브랜치 → 안전
  • 팀 main 브랜치 → 매우 위험

원문 보존 단위

Git 인덱스에서 파일 제거하기 (git rm --cached)

1️⃣ 왜 필요한가?

.gitignore는 이미 추적 중인(tracked) 파일에는 적용되지 않는다.

즉,

git add some.db
git commit -m "add db"

이후에 .gitignore에 some.db를 추가해도

Git은 계속 변경사항을 추적한다.

이럴 때 필요한 명령이:

🔥 git rm --cached

2️⃣ 핵심 개념

git rm --cached

의 의미:

  • Git 인덱스(= staging area)에서 제거
  • 로컬 파일은 삭제되지 않음
  • 추적(tracking)만 해제

즉,

“파일은 남기고 Git만 잊게 만들기”

3️⃣ 단일 파일 제거

git rm --cached <파일명>

예시:

git rm --cached chat-gpt-clone-memory.db

결과

  • Git은 해당 파일을 더 이상 추적하지 않음
  • 로컬 파일은 그대로 존재
  • .gitignore 규칙이 이후부터 정상 적용됨

4️⃣ 디렉토리 전체 제거

git rm --cached -r <디렉토리명>

예시:

git rm --cached -r logs/

옵션 설명

  • r → recursive (하위 파일까지 모두 처리)

결과

  • 해당 디렉토리 내부 모든 파일 추적 해제
  • 로컬 파일은 그대로 유지

5️⃣ 실제 적용 순서 (중요)

① .gitignore 먼저 작성

echo "chat-gpt-clone-memory.db" >> .gitignore

② Git 인덱스에서 제거

git rm --cached chat-gpt-clone-memory.db

③ 상태 확인

git status

④ 커밋

git commit -m "Stop tracking memory DB file"

6️⃣ 전체 프로젝트에서 잘못 추적된 파일 정리

여러 파일이 이미 추적되고 있다면:

git rm -r --cached .
git add .
git commit -m "Reapply gitignore"

의미

  1. 인덱스 전체 제거
  2. .gitignore 기준으로 다시 add
  3. 커밋

⚠️ 변경 파일이 많아질 수 있으니 주의

7️⃣ git rm vs git rm --cached 차이

명령어 Git 추적 해제 로컬 파일 삭제
git rm O O
git rm --cached O ❌

🔥 실수로 git rm 쓰면 로컬 파일도 삭제된다.

8️⃣ 한 줄 요약

git rm --cached는

“파일은 남기고 Git의 기억만 지우는 명령어”다.

확장 학습 후보

  • 팀 프로젝트에서 DB 파일 관리 전략
  • 환경 변수 파일, .db, .log 관리 베스트 프랙티스
  • CI/CD에서 무시 패턴 설계

Git 커밋별 문서 병합 정리

요청: 15.0/15.1/15.2 강의 커밋 각각에 해당 문서를 뒤늦게 붙여서 커밋별로 정리하고, 그 과정을 노션에 학습 기록으로 남기기

요구사항

  • 각 강의 커밋(15.0, 15.1, 15.2)에 맞는 문서를 해당 커밋에만 합칠 것
  • 새 커밋이 아니라 기존 커밋 메시지를 유지한 채 내용을 합치는 방식으로 처리할 것
  • 작업 후 어떤 커밋 해시가 되었는지 명확히 기록할 것

해결 방법

amend를 각 대상 커밋 단위로 반복 적용했습니다. 즉 HEAD를 해당 커밋으로 이동해 doc 파일을 git add한 뒤 git commit --amend --no-edit으로 커밋을 치환했습니다.

루트 커밋부터 순서대로 처리해 충돌 없이 체인을 유지했고, 15.1/15.2 구간은 체인 정렬을 위해 cherry-pick을 사용해 문서를 정확한 커밋에 넣었습니다.

적용한 핵심 커맨드

git checkout 86ca243
git add -- "doc/15.0 프로젝트 준비와 실행 환경 구성.md"
git commit --amend --no-edit

git cherry-pick 5204eb9
git add -- "doc/15.1 오디오 추출과 Whisper 전사 파이프라인.md"
git commit --amend --no-edit

git cherry-pick c05f291
git add -- "doc/15.2 조건부 엣지 기반 청크 요약 그래프.md"
git commit --amend --no-edit

git log --oneline --decorate -n 3

최종 결과

  1. #15.0 Introduction (03:56) → 7eeb3c6
  2. #15.1 Audio Extraction and Transcription (16:17) → 6d62a49
  3. #15.2 Summarizer Nodes (12:52) → 78fb270

각 커밋에 문서가 정확히 병합되어 git add + amend로 기존 커밋을 치환한 히스토리 구조입니다. 백업 브랜치 backup-before-15x-rewrite를 남겨 복구 경로도 확보했습니다.

현재 상태

원격 강제 푸시(--force-with-lease)가 필요하고, 푸시는 별도로 수동 반영된 상태입니다.

요약: 별도 브랜치 병합이 아니라, 같은 라인에서 커밋을 재작성해 강의별 요구사항을 반영한 방식입니다.

3️⃣ 파일 이름만 간단히 보고 싶을 때

git diff --cached --name-only

그러면 파일 이름만 출력됩니다.

정리

파일 목록만 확인 →

git status

stage에 올라간 diff 확인 →

git diff --cached

파일 이름만 간단히 확인 →

git diff --cached --name-only

working directory / stage / commit 구조는 별도 개념 정리로 확장할 수 있다.

git diff

1️⃣ git diff는 무엇을 비교하는가?

git은 “파일을 수정했다”고 생각하지 않는다.

git은 이렇게 생각한다:

이전 스냅샷 상태 vs 현재 스냅샷 상태

이 두 상태를 비교하는 시스템이다.

즉,

  • 파일을 줄 단위로 추적하는 게 아니라
  • 스냅샷 전체를 저장하고 비교한다.

예시:

@@ -1,13 +1,115 @@

형식:

이전 스냅샷과 비교 기준이다.

Git Stash

1️⃣ Git Stash란 무엇인가?

🎯 정의

git stash는:

현재 작업 중인 변경사항을

임시로 저장해두고

working directory를 깨끗하게 만드는 기능

📌 언제 쓰는가?

  • 작업 중인데 급하게 브랜치 변경해야 할 때
  • pull 전에 작업 내용을 잠시 치워야 할 때
  • 실험 코드 잠깐 보관하고 싶을 때

2️⃣ 기본 개념 구조

Git에는 3가지 상태가 있다:

  1. Working Directory (내가 수정 중인 파일)
  2. Staging Area (git add 한 상태)
  3. Repository (commit된 상태)

git stash는:

  • Working Directory 변경사항
  • Staging Area 변경사항

을 함께 저장한다.

3️⃣ Stash 저장하기

📌 기본 저장

git stash

→ 현재 변경사항을 저장

→ working directory를 마지막 commit 상태로 되돌림

📌 메시지와 함께 저장

git stash push -m "로그인 기능 작업 중"

4️⃣ Stash 목록 확인

git stash list

예시:

stash@{0}: WIP on main: 8f5b43c Merge remote-tracking branch 'origin/main'
stash@{1}: On main: 로그인 기능 작업 중

의미

  • stash@{0} → 가장 최근 stash
  • 숫자가 작을수록 최신
  • 위에서 아래로 오래된 stash

5️⃣ Stash 내용 미리 보기

📌 간단 요약

git stash show

📌 상세 diff 보기

git stash show -p stash@{0}

6️⃣ Stash 꺼내기 (적용하기)

🔹 ① apply — 적용만

git stash apply

또는

git stash apply stash@{0}

✔ working directory에 적용

✔ stash 목록에는 그대로 남음

🔹 ② pop — 적용 + 삭제

git stash pop

또는

git stash pop stash@{0}

✔ working directory에 적용

✔ stash 목록에서 삭제됨

7️⃣ apply vs pop 차이

명령어 적용 stash 삭제
apply O X
pop O O

실무에서는 보통 pop을 많이 사용한다.

안전하게 하려면:

git stash apply
# 문제 없으면
git stash drop stash@{0}

8️⃣ 충돌이 발생할 수 있다

stash는 단순 복사가 아니다.

stash 저장 당시의 base 커밋 기준으로 만들어지기 때문에

현재 브랜치 상태가 달라졌다면 충돌이 날 수 있다.

충돌 해결 방법은 merge와 동일:

  1. 파일 열기
  2. 충돌 마커 정리
  3. git add
  4. 필요 시 commit

9️⃣ 특정 stash 삭제

git stash drop stash@{0}

🔟 stash 전체 삭제

git stash clear

⚠ 복구 불가

1️⃣1️⃣ Stash 내부 구조 (중요 개념)

stash는 단순 메모가 아니다.

실제로는:

  • commit 객체 2개 (또는 3개)
  • WIP 커밋 형태로 저장

구조:

stash commit
 ├─ working tree 상태
 └─ index 상태

그래서 브랜치가 바뀌면 충돌이 날 수 있다.

1️⃣2️⃣ 다른 브랜치에 stash 적용

가능하다:

git checkout feature
git stash pop

→ 다른 브랜치에 작업 내용 옮길 수 있음

1️⃣3️⃣ Stash를 브랜치로 만들기

git stash branch new-branch stash@{0}

→ 새 브랜치 생성

→ stash 적용

→ stash 삭제

1️⃣4️⃣ 자주 헷갈리는 질문

Q. stash는 commit인가?

네. 내부적으로 commit 객체다.

Q. stash는 원격에 push 되나?

아니요.

stash는 로컬 전용이다.

Q. add 안 한 파일도 stash 되나?

기본적으로는 tracked 파일만.

untracked까지 포함하려면:

git stash -u

Q. ignored 파일도 포함하려면?

git stash -a

  • stash는 작업 임시 보관함
  • list로 확인
  • show -p로 내용 확인
  • apply는 적용만
  • pop은 적용 + 삭제
  • drop은 삭제
  • clear는 전체 삭제
  • stash는 commit 객체다
  • stash 적용 시 충돌 날 수 있다

Git의 3단계 구조 완전 이해

1. Git은 파일 저장 시스템이 아니다

Git은 “파일을 저장”하는 시스템이 아니라

📸

프로젝트의 스냅샷을 저장하는 시스템

이다.

커밋은 “변경사항 저장”이 아니라

“현재 상태 전체를 스냅샷으로 기록”하는 행위다.

2. Git의 3단계 구조

Git은 항상 3단계를 거친다.

1️⃣ Working Directory
2️⃣ Staging Area (Index)
3️⃣ Commit

1️⃣ Working Directory (작업 공간)

  • 내가 실제로 파일을 수정하는 공간
  • 아직 Git이 커밋에 포함할지 결정하지 않은 상태

예:

A.txt 수정
B.txt 수정

이 시점에서는 단순히 파일이 바뀐 것뿐이다.

2️⃣ Staging Area (Index)

“다음 커밋에 포함할 파일을 선택하는 단계”

명령어:

git add 파일명

이 의미는:

“이 파일의 현재 상태를 다음 커밋에 포함시키겠다”

아직 커밋은 아니다.

단지 “커밋 후보”로 올려놓은 상태다.

예시 흐름

현재 상태:

Working Directory: A 수정, B 수정
Staging Area: 없음

이제:

git add A.txt

상태:

Working Directory: A 수정, B 수정
Staging Area: A만 있음

3️⃣ Commit

명령어:

git commit -m "A 수정"

이때 발생하는 일:

  • Staging Area에 있는 파일들만
  • 하나의 스냅샷으로 저장됨

결과:

  • A는 커밋됨
  • B는 여전히 수정 상태로 남아있음

3. 왜 Staging 단계가 필요한가?

Git은 이렇게 생각한다:

“이번 커밋에 어떤 변경을 포함할지 명확히 선택하라”

이 덕분에 가능한 것:

  • 여러 파일 중 일부만 커밋
  • 한 파일 안에서도 일부 코드만 커밋
  • 의미 있는 단위로 커밋 분리

4. GUI에서 헷갈리는 이유

GUI에서는 보통:

  • 체크박스 선택 = git add
  • Commit 버튼 = git commit

즉,

add + commit을 버튼으로 감싸서 보여주기 때문에

staging 개념이 흐려진다.

5. 핵심 개념 정리

단계 의미
Working Directory 내가 수정한 상태
Staging Area 다음 커밋에 포함할 파일 선택
Commit 선택된 파일들을 스냅샷으로 저장

6. 가장 중요한 한 문장

Git은 파일을 저장하는 것이 아니라

“선택된 파일들의 스냅샷을 기록하는 시스템”이다.

편입 후 검증 메모

  • git diff: 인자 없는 diff는 worktree와 index, --cached는 index와 HEAD를 비교한다. 무엇을 비교하는지 먼저 적고 실행한다.
  • 히스토리 재작성: amend·rebase·reset 뒤 새 commit ID가 생기면 이미 공유된 원격 이력과 갈라진다. 개인 브랜치인지 확인하고 협업자와 조율한다.
  • 강제 푸시: 원문 명령을 보존했지만 일반 --force보다 원격이 예상 상태일 때만 덮어쓰는 --force-with-lease가 안전하다. 그래도 공유 브랜치에서는 별도 합의가 필요하다.
  • 복구: 실수 직후에는 추가 조작을 멈추고 git reflog로 이전 HEAD를 찾는다. 작업 트리 변경이 남아 있다면 먼저 별도 패치·stash·백업으로 보존한다.
