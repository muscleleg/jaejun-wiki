쿠버네티스 설치

📌 쿠버네티스 v1.29.5 클러스터 설치 (kubeadm 사용) - 완벽한 개념 정리

  • 쿠버네티스(Kubernetes)는 여러 개의 컴퓨터(서버)를 하나의 클러스터로 묶어 애플리케이션을 자동으로 배포하고 관리할 수 있도록 도와주는 플랫폼이야.

각 명령의 역할·필요성·내부 동작을 순서대로 설명한다.

1. 사전 준비

쿠버네티스를 설치하려면 여러 개의 서버(노드)가 필요해.

쿠버네티스 클러스터는 마스터 노드와 워커 노드로 구성돼.

1-1. 서버 구성

노드 종류 역할
마스터 노드 (master-node) 클러스터 전체를 관리
워커 노드 (worker-node) 애플리케이션이 실행되는 곳

우리는 Ubuntu 20.04 또는 22.04 운영체제를 사용할 거야.

명령어를 실행하려면 root 계정 또는 sudo를 사용해야 해.

1-2. 호스트 이름 변경 (선택 사항)

각 서버의 이름(호스트 이름)을 설정하면 나중에 관리하기 편해.

기본적으로 Ubuntu에서는 ubuntu라는 이름을 사용하지만, 역할에 맞게 이름을 바꿔주면 서버를 구분하기 쉬워.

🔹 마스터 노드에서 실행

sudo hostnamectl set-hostname master-node

📌 이 명령어의 역할:

  • hostnamectl set-hostname [새 이름] → 현재 서버의 호스트 이름을 master-node로 변경함.
  • 이 변경 사항은 서버를 재부팅해도 유지됨.

🔹 워커 노드에서 실행

sudo hostnamectl set-hostname worker-node

📌 이 명령어의 역할:

  • 위와 동일한 방식으로 워커 노드의 이름을 worker-node로 변경.

🔹 /etc/hosts 파일 수정 (모든 노드에서 실행)

각 노드가 서로 통신할 수 있도록, 모든 노드에서 /etc/hosts 파일을 수정해야 해.

sudo nano /etc/hosts

📌 파일 내용 수정 (예제):

127.0.1.1 master-node  # 마스터 노드
127.0.1.1 worker-node  # 워커 노드

이게 왜 필요할까?

  • 기본적으로, 서버들은 IP 주소를 사용해서 서로 통신해.
  • 하지만 사람이 IP 주소를 직접 관리하기 어려우니까, 이름(호스트명)으로 접근할 수 있도록 등록하는 거야.
  • 위 설정을 하면, master-node라고 입력하면 자동으로 127.0.1.1(자신의 IP)로 연결됨.

📌 설정을 적용하려면 쉘을 다시 실행해야 해.

exec bash
  • 이 명령어는 현재 쉘을 다시 시작해서 변경된 호스트 이름이 즉시 적용되도록 해.

2. 방화벽 및 스왑(Swap) 설정 (모든 노드에서 실행)

쿠버네티스는 안정적으로 동작하기 위해 몇 가지 필수적인 환경 설정이 필요해.

🔹 스왑(Swap) 비활성화

sudo swapoff -a
sudo sed -i '/swap/d' /etc/fstab

📌 Swap이란?

  • RAM(메모리)이 부족할 때, 디스크의 일부를 임시 메모리처럼 사용하는 기능이야.
  • 일반적으로 성능이 낮은 서버에서는 RAM이 부족하면 디스크에 데이터를 저장했다가 다시 불러오는데, 디스크 속도는 RAM보다 훨씬 느려.
  • 이 때문에 애플리케이션 실행 속도가 느려지고, 쿠버네티스의 자원 관리가 꼬일 수 있어.

📌 왜 Swap을 꺼야 할까?

  1. 성능 저하 방지
  • 쿠버네티스는 메모리 사용량을 정확하게 예측해서 컨테이너를 배치하는데, 스왑이 활성화되어 있으면 잘못된 예측이 발생할 수 있어.
  1. 노드의 신뢰성 향상
  • 쿠버네티스는 스왑을 고려하지 않고 설계됐기 때문에, 스왑이 켜져 있으면 컨테이너가 비정상적으로 종료될 수도 있어.
  1. 클러스터 불안정 방지
  • 클러스터 전체에서 균형 있게 노드를 배치하려면, 각 노드의 리소스 상태를 정확하게 파악해야 하는데, 스왑이 활성화되어 있으면 이를 정확하게 측정할 수 없음.

📌 명령어 설명

  • swapoff -a → 현재 활성화된 스왑을 모두 비활성화함.
  • sed -i '/swap/d' /etc/fstab → 재부팅해도 스왑이 자동으로 켜지지 않도록 설정 파일에서 스왑 항목을 삭제.

하위 원문: sed란?

🔹 방화벽 비활성화

sudo ufw disable

📌 왜 방화벽을 비활성화할까?

  • 기본적으로 Ubuntu의 방화벽(UFW)은 네트워크 트래픽을 차단할 수 있어.
  • 쿠버네티스는 여러 노드 간에 자유롭게 네트워크 통신을 해야 하므로, 방화벽을 끄는 게 안전함.
  • 필요하면 나중에 설정을 조정할 수도 있음.

🔹 네트워크 필터링 설정

sudo modprobe br_netfilter
echo 'net.bridge.bridge-nf-call-iptables=1' | sudo tee -a /etc/sysctl.d/k8s.conf
echo 'net.ipv4.ip_forward=1' | sudo tee -a /etc/sysctl.d/k8s.conf
sudo sysctl --system

📌 br_netfilter란?

  • 쿠버네티스에서는 여러 개의 컨테이너가 서로 같은 네트워크 안에서 통신해야 해.
  • 그런데 기본적으로 Linux 커널은 브릿지 네트워크에서 패킷을 필터링하지 않아.
  • 이를 활성화하면, 컨테이너 간 통신이 원활하게 되고, 네트워크 정책이 제대로 적용됨.

📌 각 명령어 설명

  • modprobe br_netfilter → 브릿지 네트워크에서 패킷을 필터링하는 기능을 활성화함.
  • echo 'net.bridge.bridge-nf-call-iptables=1' | sudo tee -a /etc/sysctl.d/k8s.conf
    → iptables가 브릿지 네트워크의 트래픽을 필터링할 수 있도록 설정함.

하위 원문: tee란?

  • echo 'net.ipv4.ip_forward=1' | sudo tee -a /etc/sysctl.d/k8s.conf
    → 패킷이 다른 네트워크로 전달될 수 있도록 허용함.
  • sysctl --system → 설정을 즉시 적용함.

3. 컨테이너 런타임 (containerd) 설치

쿠버네티스는 애플리케이션을 실행할 때 "컨테이너(Container)"라는 기술을 사용해.

컨테이너를 실행하려면 이를 관리하는 컨테이너 런타임(Container Runtime)이 필요해.

쿠버네티스에서 지원하는 컨테이너 런타임에는 여러 가지가 있지만, 현재 가장 권장되는 것은 containerd야.

3-1. containerd 설치

sudo apt update && sudo apt install -y containerd

📌 이 명령어는 무슨 역할을 할까?

  • apt update → 패키지 목록을 최신 상태로 업데이트함.
  • apt install -y containerd → containerd를 설치함. (y는 "설치할까요?"라는 질문 없이 자동 진행)

3-2. containerd 설정

쿠버네티스에서 containerd를 제대로 사용하려면 몇 가지 설정이 필요해.

sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml

📌 각 명령어의 역할

  • sudo mkdir -p /etc/containerd
    → /etc/containerd 폴더를 생성함. (p는 "이미 폴더가 있으면 그냥 넘어가라"는 의미)
  • containerd config default | sudo tee /etc/containerd/config.toml
    → 기본 설정 파일을 /etc/containerd/config.toml에 저장함.

3-3. containerd의 CGroup 설정 변경

sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml

📌 이게 왜 필요할까?

  • CGroup(Control Groups): 리눅스에서 CPU, 메모리, 네트워크 같은 자원을 여러 프로세스가 효율적으로 나눠 쓰도록 도와주는 기능.
  • 쿠버네티스는 기본적으로 CGroup을 systemd 방식으로 사용해야 하는데, 기본 설정은 false로 되어 있음.
  • 그래서 sed 명령어를 사용해서 SystemdCgroup = true로 변경해 줌.

3-4. containerd 서비스 재시작 및 자동 실행 설정

sudo systemctl restart containerd
sudo systemctl enable containerd

📌 각 명령어의 역할

  • systemctl restart containerd → 변경된 설정을 적용하기 위해 containerd를 다시 시작.
  • systemctl enable containerd → 서버를 재부팅해도 containerd가 자동으로 실행되도록 설정.

4. 쿠버네티스 핵심 구성 요소 설치

쿠버네티스를 설치하려면 세 가지 핵심 프로그램이 필요해.

프로그램 역할
kubeadm 쿠버네티스 클러스터를 초기화하는 도구
kubelet 각 노드에서 컨테이너를 실행하는 프로그램
kubectl 쿠버네티스를 제어하는 CLI(Command Line Interface) 도구

4-1. 쿠버네티스 패키지 다운로드를 위한 보안 키 추가

curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.29/deb/Release.key | sudo gpg --dearmor -o /usr/share/keyrings/kubernetes-archive-keyring.gpg

📌 이 명령어는 무슨 역할을 할까?

  • 리눅스에서 패키지를 설치하려면 해당 저장소가 "신뢰할 수 있는 곳"인지 확인해야 해.
  • 쿠버네티스 패키지는 공식 저장소에서 다운로드해야 하므로 보안 키(GPG Key)를 등록해야 해.
  • gpg --dearmor → 키 파일을 변환해서 리눅스에서 사용할 수 있도록 만듦.
  • /usr/share/keyrings/kubernetes-archive-keyring.gpg에 저장함.

4-2. 쿠버네티스 패키지 저장소 추가

echo "deb [signed-by=/usr/share/keyrings/kubernetes-archive-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.29/deb/ /" | sudo tee /etc/apt/sources.list.d/kubernetes.list

📌 왜 해야 할까?

  • apt(패키지 관리자)는 기본적으로 우분투의 공식 저장소에서만 패키지를 다운로드해.
  • 하지만 쿠버네티스는 별도의 저장소에서 제공되므로, 추가로 등록해야 함.
  • /etc/apt/sources.list.d/kubernetes.list → 쿠버네티스 저장소를 등록하는 파일.

4-3. kubeadm, kubelet, kubectl 설치

sudo apt update
sudo apt install -y kubeadm=1.29.5-1.1 kubelet=1.29.5-1.1 kubectl=1.29.5-1.1

📌 각 프로그램의 역할

  • kubeadm → 클러스터 초기화 및 설정 도구
  • kubelet → 각 노드에서 컨테이너 실행 및 관리
  • kubectl → 쿠버네티스를 제어하는 CLI(Command Line Interface) 도구

4-4. 쿠버네티스 버전 고정

sudo apt-mark hold kubelet kubeadm kubectl

📌 이 명령어가 하는 일

  • 쿠버네티스는 계속해서 새로운 버전이 나오지만, 자동 업데이트되면 기존 설정과 충돌할 가능성이 있어.
  • apt-mark hold를 사용하면 이 세 가지 프로그램이 자동으로 업데이트되지 않도록 막을 수 있어.
  • 버전 관리를 직접 하고 싶을 때 유용한 설정이야.

5. 마스터 노드 설정 (kubeadm init)

이제 모든 노드에서 기본 프로그램을 설치했으니까, 마스터 노드를 초기화해서 클러스터를 구성할 거야.

sudo kubeadm init --pod-network-cidr=192.168.0.0/16

📌 이 명령어가 하는 일

  • kubeadm init → 쿠버네티스 클러스터를 생성하는 명령어.
  • -pod-network-cidr=192.168.0.0/16 → 클러스터 내부에서 사용할 네트워크 범위를 지정.

📌 초기화가 끝나면 아래와 같은 메시지가 출력될 거야.

Your Kubernetes control-plane has initialized successfully!
To start using your cluster, you need to run the following as a regular user:
...
Then you can join any number of worker nodes by running the following on each as root:
kubeadm join <MASTER_IP>:6443 --token <TOKEN> --discovery-token-ca-cert-hash sha256:<HASH>
  • 이 kubeadm join 명령어를 복사해 두자!
  • 나중에 워커 노드를 마스터 노드에 연결할 때 사용할 거야

6. 마스터 노드에서 kubectl 사용 설정

쿠버네티스를 제대로 사용하려면 kubectl을 설정해야 해.

kubectl은 쿠버네티스를 조작하는 CLI(Command Line Interface) 도구야.

🔹 kubectl을 사용할 수 있도록 환경 설정

mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

📌 각 명령어의 역할

  1. mkdir -p $HOME/.kube
    → 쿠버네티스 설정 파일을 저장할 폴더를 생성. (p는 폴더가 이미 있으면 그냥 넘어가라는 의미)
  2. sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
    → 클러스터 인증 파일(admin.conf)을 사용자의 설정 폴더로 복사.
  3. sudo chown $(id -u):$(id -g) $HOME/.kube/config
    → 현재 사용자에게 config 파일의 소유권을 부여.

이제 kubectl로 Kubernetes API의 리소스를 조회하고 변경할 수 있다.

7. CNI(네트워크 플러그인) 설치

쿠버네티스에서 컨테이너끼리 통신하려면 "네트워크 플러그인(CNI)"을 설치해야 해.

CNI는 쿠버네티스 내부의 Pod들이 서로 네트워크를 통해 연결되도록 도와주는 역할을 해.

📌 쿠버네티스에서 많이 사용하는 CNI 플러그인

CNI 플러그인 특징
Calico 보안 정책(NetworkPolicy) 지원, 복잡하지만 강력함
Flannel 가장 간단한 네트워크 플러그인, 빠르고 설정이 쉬움

우리는 Calico 또는 Flannel 중에서 하나를 설치하면 돼.

🔹 Calico 설치

kubectl apply -f https://docs.projectcalico.org/manifests/calico.yaml

📌 이 명령어의 역할

  • kubectl apply -f [파일] → 쿠버네티스 리소스를 적용하는 명령어.
  • https://docs.projectcalico.org/manifests/calico.yaml
    → Calico 네트워크 플러그인을 쿠버네티스에 설치하는 YAML 파일.

🔹 Flannel 설치

kubectl apply -f https://raw.githubusercontent.com/coreos/flannel/master/Documentation/kube-flannel.yml

📌 이 명령어의 역할

  • Flannel 네트워크 플러그인을 설치하는 YAML 파일을 적용함.

💡 둘 중 하나만 선택해서 설치하면 돼!

8. 워커 노드 연결

쿠버네티스 클러스터는 마스터 노드 + 워커 노드로 구성돼.

이제 워커 노드를 클러스터에 연결할 차례야.

🔹 마스터 노드에서 kubeadm init 실행했을 때 출력된 명령어 실행

sudo kubeadm join <MASTER_IP>:6443 --token <TOKEN> --discovery-token-ca-cert-hash sha256:<HASH>

📌 각 항목의 의미

  • <MASTER_IP>:6443 → 마스터 노드의 API 서버 주소.
  • <TOKEN> → 워커 노드가 마스터 노드에 연결할 때 사용하는 인증 토큰.
  • -discovery-token-ca-cert-hash sha256:<HASH>
    → 클러스터의 보안 인증을 확인하는 해시 값.

💡 이 명령어는 마스터 노드를 초기화할 때(kubeadm init) 출력됐던 명령어를 그대로 사용해야 해.

🔹 워커 노드가 join 명령어를 실행하면 어떻게 될까?

  1. 워커 노드가 마스터 노드와 연결됨.
  2. 마스터 노드가 워커 노드를 쿠버네티스 클러스터의 일부로 추가함.
  3. 워커 노드에서 실행되는 kubelet이 컨테이너를 실행할 준비를 함.

9. 클러스터 상태 확인

이제 모든 설정이 끝났으니까, 클러스터가 정상적으로 동작하는지 확인해보자.

🔹 마스터 노드에서 실행

kubectl get nodes

📌 출력 예시

NAME          STATUS   ROLES           AGE    VERSION
master-node   Ready    control-plane   10m    v1.29.5
worker-node   Ready    <none>          5m     v1.29.5

📌 여기서 중요한 부분

  • STATUS가 Ready면 클러스터가 정상적으로 동작 중.
  • master-node는 control-plane 역할을 하고 있음.
  • worker-node가 정상적으로 추가됐는지 확인할 수 있음.

🎉 쿠버네티스 클러스터 설치 완료!

✅ 쿠버네티스를 실행할 기본적인 환경을 모두 설정했어.

✅ 이제 kubectl을 사용해서 쿠버네티스를 제어할 수 있어.

✅ 네트워크 플러그인을 설치해서 Pod끼리 통신이 가능해.

✅ 워커 노드를 마스터 노드에 연결해서 클러스터 구성이 완료됐어.

이 구성 이후 Kubernetes에서 애플리케이션을 배포하고 관리할 수 있다.

💡 추가적으로 알면 좋은 내용

✅ 클러스터 상태 확인

kubectl get pods -A
  • 모든 네임스페이스(A)의 Pod 상태를 확인할 수 있음.
  • 네트워크 플러그인이 정상적으로 실행되는지 체크할 수 있음.

✅ 만약 워커 노드가 NotReady 상태라면?

kubectl describe node worker-node
  • 자세한 오류 메시지를 확인하고 문제를 해결할 수 있음.

✅ kubeadm join 명령어를 잃어버렸다면?

kubeadm token create --print-join-command
  • 새로운 kubeadm join 명령어를 생성할 수 있음.

✅ 클러스터 삭제 (연습 후 초기화할 때 사용)

kubeadm reset
  • 쿠버네티스 클러스터를 완전히 초기화함.
  • 연습 후 다시 클러스터를 만들 때 사용 가능.

📌 정리

  • 마스터 노드에서 kubectl 설정 → 쿠버네티스를 제어할 수 있도록 환경 설정.
  • CNI(네트워크 플러그인) 설치 → Pod들이 서로 통신할 수 있도록 설정.
  • 워커 노드 연결 → kubeadm join 명령어를 실행해서 마스터 노드에 연결.
  • 클러스터 확인 → kubectl get nodes를 실행해서 모든 노드가 Ready 상태인지 확인.

✅ 마무리

이제 쿠버네티스 클러스터를 완전히 설치하고 사용할 준비가 끝났어! 🎉

이제 kubectl을 사용해서 Pod, Service, Deployment 같은 리소스를 생성하고, 애플리케이션을 배포할 수 있어.

재검토 대상 원문

sed란?

📌 sed란?

sed는 Stream Editor(스트림 편집기)의 줄임말이야.

즉, 파일의 내용을 직접 열지 않고도 특정한 텍스트를 찾아서 변경, 삭제, 추가할 수 있는 명령어야.

📌 sed의 기본 문법

sed 's/찾을_문자열/바꿀_문자열/' 파일이름

📌 문법 설명

  • 's/찾을_문자열/바꿀_문자열/' → 특정 문자열을 다른 문자열로 변경하는 명령어
  • s → "substitute" (치환)
  • /찾을_문자열/바꿀_문자열/ → 찾을 문자열을 바꿀 문자열로 대체
  • 파일이름 → 변경할 파일

📌 sed를 사용한 예제

🔹 예제 1: hello를 hi로 변경

echo "hello world" | sed 's/hello/hi/'

📌 출력 결과

hi world

💡 원래 문자열에서 "hello"를 "hi"로 변경함.

🔹 예제 2: 파일에서 특정 단어 바꾸기

sed 's/cat/dog/' example.txt

📌 example.txt 내용 (변경 전)

I have a cat.

📌 출력 결과 (변경 후)

I have a dog.

💡 파일을 직접 수정하지 않고, cat을 dog로 바꿔서 출력함.

🔹 i 옵션: 파일을 직접 수정

sed -i 's/cat/dog/' example.txt

📌 설명

  • i 옵션을 사용하면 파일을 직접 수정함.
  • 이제 example.txt 파일을 열어보면 cat이 dog로 변경되어 있을 거야.

💡 ⚠️ 주의: -i 옵션을 사용하면 원본 파일이 즉시 변경되므로 조심해서 사용해야 해!

📌 sed가 swap을 삭제하는 원리

🔹 우리가 실행한 명령어

sudo sed -i '/swap/d' /etc/fstab

📌 각 부분의 의미

  • i → 파일을 직접 수정
  • '/swap/d' → swap이 포함된 줄을 삭제 (d는 delete의 약자)
  • /etc/fstab → 수정할 파일 (fstab은 부팅 시 마운트할 파일 시스템을 정의하는 설정 파일)

💡 즉, fstab 파일에서 "swap"이 포함된 줄을 찾아서 삭제하는 명령어야.

💡 이렇게 하면 재부팅해도 swap이 다시 켜지지 않게 돼. 🚀

📌 추가적으로 sed에서 자주 사용하는 기능

✅ 대소문자 구분 없이 변경하기 (I 옵션 사용)

echo "Hello hello" | sed 's/hello/hi/I'

📌 출력 결과

hi hello

💡 기본적으로 sed는 대소문자를 구분하지만, I 옵션을 사용하면 무시할 수 있어.

✅ 특정 단어가 포함된 줄 삭제 (/문자열/d 사용)

sed '/error/d' logfile.txt

💡 logfile.txt에서 "error"가 포함된 모든 줄을 삭제함.

✅ 파일에서 특정 부분만 출력 (-n 옵션 + p 명령어 사용)

sed -n '2p' example.txt

💡 example.txt의 2번째 줄만 출력함.

📌 정리

  • sed는 파일을 직접 열지 않고도 특정한 텍스트를 찾아서 변경, 삭제, 추가할 수 있는 명령어.
  • s/문자열1/문자열2/ → 문자열을 변경함.
  • i → 파일을 직접 수정함.
  • d → 특정한 줄을 삭제함.
  • 우리가 실행한 sudo sed -i '/swap/d' /etc/fstab은 fstab 파일에서 swap이 포함된 줄을 삭제해서 재부팅해도 swap이 다시 활성화되지 않도록 설정하는 명령어.
재검토 대상 원문

tee란?

📌 tee 명령어란?

tee는 표준 입력(stdin)으로 받은 데이터를 화면에 출력하면서 동시에 파일에 저장하는 명령어야.

✅ tee의 기본 역할

  • 출력 결과를 화면과 파일에 동시에 기록
  • 파일을 덮어쓰거나(>) 추가(>>)할 수 있음
  • 권한이 필요한 파일에도 sudo와 함께 사용 가능

📌 tee 기본 사용법

echo "Hello World" | tee output.txt

📌 출력 결과

Hello World

📌 파일 내용 (output.txt)

Hello World
  • echo "Hello World" → "Hello World"를 출력.
  • | tee output.txt → 출력 결과를 output.txt 파일에도 저장하면서 동시에 화면에도 출력.
  • 💡 >(리다이렉션)와 비슷하지만, tee는 화면에도 출력함!

📌 tee를 사용해야 하는 이유

보통 > 연산자를 사용하면 파일에만 기록되고 화면에는 출력되지 않아.

하지만 tee를 사용하면 파일에도 저장하면서, 실행된 결과를 바로 확인할 수 있음.

✅ 1️⃣ 파일을 덮어쓰는 경우 (>와 동일)

echo "New Content" | tee output.txt

📌 출력 결과

New Content

📌 파일 내용 (output.txt)

New Content

💡 파일 내용이 기존 내용 없이 새 내용으로 덮어씌워짐.

✅ 2️⃣ 파일에 내용을 추가하는 경우 (>>와 동일)

echo "Another Line" | tee -a output.txt

📌 출력 결과

Another Line

📌 파일 내용 (output.txt)

New Content
Another Line

💡 -a 옵션을 사용하면 기존 파일 내용에 추가(Append)됨.

📌 tee가 쿠버네티스 설정에서 사용되는 이유

🔹 우리가 실행한 명령어

echo 'net.bridge.bridge-nf-call-iptables=1' | sudo tee -a /etc/sysctl.d/k8s.conf

📌 이 명령어가 하는 일

  1. echo 'net.bridge.bridge-nf-call-iptables=1'
    → "net.bridge.bridge-nf-call-iptables=1"이라는 설정을 출력함.
  2. | sudo tee -a /etc/sysctl.d/k8s.conf
    → 이 출력을 /etc/sysctl.d/k8s.conf 파일에 추가함.
  3. a (append) 옵션을 사용했으므로 기존 설정을 유지하면서 새 줄을 추가.

💡 즉, tee를 사용하면 설정을 추가하면서, 동시에 화면에도 출력돼서 확인할 수 있음!

🔹 tee를 안 쓰고 >만 사용하면?

echo 'net.bridge.bridge-nf-call-iptables=1' > /etc/sysctl.d/k8s.conf

⚠ 이렇게 하면 기존 파일의 내용이 전부 사라지고 덮어쓰기됨.

📌 원래 있던 설정을 유지하면서 추가하려면 tee -a를 사용해야 해.

📌 결론

  • tee는 출력된 내용을 파일에 저장하면서 동시에 화면에도 보여주는 명령어야.
  • a 옵션을 사용하면 기존 파일 내용에 추가(Append) 가능.
  • 쿠버네티스 설정 파일을 수정할 때 기존 내용을 유지하면서 새로운 설정을 추가할 때 유용함.
  • sudo와 함께 사용하면 권한이 필요한 시스템 파일도 수정 가능.

📌 정리

명령어 역할
echo "Hello" > file.txt file.txt에 "Hello"를 저장 (기존 내용 삭제됨)
echo "Hello" >> file.txt file.txt에 "Hello"를 추가 (기존 내용 유지)
\`echo "Hello" tee file.txt\`
\`echo "Hello" tee -a file.txt\`

📌 k8s.conf 파일은 원래 존재하는 파일일까?

기본적으로 리눅스에는 /etc/sysctl.d/k8s.conf 파일이 존재하지 않는다.

없는 파일에도 tee 명령어를 사용해서 새로 생성할 수 있다.

📌 tee는 없는 파일에도 적용 가능할까?

tee는 파일이 존재하지 않으면 새로운 파일을 자동으로 생성한다.

🔹 예제 1: 없는 파일에 tee 사용

echo "Hello Kubernetes" | tee newfile.txt

📌 실행 후 확인

cat newfile.txt

📌 출력 결과

Hello Kubernetes

💡 파일이 없었지만 tee가 자동으로 생성해서 내용을 기록함.

🔹 우리가 실행한 명령어를 다시 분석해보자

echo 'net.bridge.bridge-nf-call-iptables=1' | sudo tee -a /etc/sysctl.d/k8s.conf

📌 이 명령어가 하는 일

  1. echo 'net.bridge.bridge-nf-call-iptables=1'
    → "net.bridge.bridge-nf-call-iptables=1" 문자열을 출력.
  2. | sudo tee -a /etc/sysctl.d/k8s.conf
    → /etc/sysctl.d/k8s.conf 파일이 없으면 자동으로 생성하고, 있으면 내용을 추가함.

k8s.conf 파일이 존재하지 않더라도 tee가 새 파일을 만들고 내용을 기록할 수 있다.

📌 k8s.conf는 왜 따로 만들어야 할까?

✅ 리눅스에서 시스템 커널 설정을 관리하는 파일은 /etc/sysctl.conf 또는 /etc/sysctl.d/*.conf 경로에 위치해야 해.

✅ sysctl.d/ 디렉터리는 여러 설정 파일을 개별적으로 관리할 수 있도록 지원함.

✅ k8s.conf는 쿠버네티스 관련 네트워크 설정을 따로 관리하기 위해 수동으로 생성하는 파일이야.

✅ /etc/sysctl.d/에 .conf 파일을 추가하면 sysctl --system을 실행할 때 자동으로 읽혀서 설정이 적용됨.

📌 tee가 없으면 어떻게 해야 할까?

만약 tee를 쓰지 않는다면 > 또는 >> 연산자를 사용해야 해.

✅ >를 사용한 방법 (덮어쓰기)

echo 'net.bridge.bridge-nf-call-iptables=1' | sudo sh -c 'cat > /etc/sysctl.d/k8s.conf'

📌 문제점: 기존 설정이 있으면 사라짐! (덮어쓰기)

✅ >>를 사용한 방법 (추가하기)

echo 'net.bridge.bridge-nf-call-iptables=1' | sudo sh -c 'cat >> /etc/sysctl.d/k8s.conf'

📌 tee -a와 같은 효과지만, tee보다 명확한 에러 메시지를 보기 어려움.

📌 tee는 실행하면 화면에도 결과를 보여주므로 더 편리함.

📌 정리

✅ /etc/sysctl.d/k8s.conf 파일은 기본적으로 존재하지 않지만, tee가 자동으로 생성해줌.

✅ tee는 없는 파일도 만들면서, 기존 파일이 있으면 내용을 추가(-a)할 수 있음.

✅ /etc/sysctl.d/k8s.conf 파일을 따로 만드는 이유는 쿠버네티스 관련 네트워크 설정을 분리해서 관리하기 위함.

✅ tee 없이 > 또는 >>를 사용할 수도 있지만, sudo tee를 쓰는 게 더 명확하고 편리함.

📌 쿠버네티스 v1.29.5 클러스터 설치 (kubeadm 사용) - 완벽한 개념 정리

  • 쿠버네티스(Kubernetes)는 여러 개의 컴퓨터(서버)를 하나의 클러스터로 묶어 애플리케이션을 자동으로 배포하고 관리할 수 있도록 도와주는 플랫폼이야.

각 명령의 역할·필요성·내부 동작을 순서대로 설명한다.

1. 사전 준비

쿠버네티스를 설치하려면 여러 개의 서버(노드)가 필요해.

쿠버네티스 클러스터는 마스터 노드와 워커 노드로 구성돼.

1-1. 서버 구성

노드 종류 역할
마스터 노드 (master-node) 클러스터 전체를 관리
워커 노드 (worker-node) 애플리케이션이 실행되는 곳

우리는 Ubuntu 20.04 또는 22.04 운영체제를 사용할 거야.

명령어를 실행하려면 root 계정 또는 sudo를 사용해야 해.

1-2. 호스트 이름 변경 (선택 사항)

각 서버의 이름(호스트 이름)을 설정하면 나중에 관리하기 편해.

기본적으로 Ubuntu에서는 ubuntu라는 이름을 사용하지만, 역할에 맞게 이름을 바꿔주면 서버를 구분하기 쉬워.

🔹 마스터 노드에서 실행

sudo hostnamectl set-hostname master-node

📌 이 명령어의 역할:

  • hostnamectl set-hostname [새 이름] → 현재 서버의 호스트 이름을 master-node로 변경함.
  • 이 변경 사항은 서버를 재부팅해도 유지됨.

🔹 워커 노드에서 실행

sudo hostnamectl set-hostname worker-node

📌 이 명령어의 역할:

  • 위와 동일한 방식으로 워커 노드의 이름을 worker-node로 변경.

🔹 /etc/hosts 파일 수정 (모든 노드에서 실행)

각 노드가 서로 통신할 수 있도록, 모든 노드에서 /etc/hosts 파일을 수정해야 해.

sudo nano /etc/hosts

📌 파일 내용 수정 (예제):

127.0.1.1 master-node  # 마스터 노드
127.0.1.1 worker-node  # 워커 노드

이게 왜 필요할까?

  • 기본적으로, 서버들은 IP 주소를 사용해서 서로 통신해.
  • 하지만 사람이 IP 주소를 직접 관리하기 어려우니까, 이름(호스트명)으로 접근할 수 있도록 등록하는 거야.
  • 위 설정을 하면, master-node라고 입력하면 자동으로 127.0.1.1(자신의 IP)로 연결됨.

📌 설정을 적용하려면 쉘을 다시 실행해야 해.

exec bash
  • 이 명령어는 현재 쉘을 다시 시작해서 변경된 호스트 이름이 즉시 적용되도록 해.

2. 방화벽 및 스왑(Swap) 설정 (모든 노드에서 실행)

쿠버네티스는 안정적으로 동작하기 위해 몇 가지 필수적인 환경 설정이 필요해.

🔹 스왑(Swap) 비활성화

sudo swapoff -a
sudo sed -i '/swap/d' /etc/fstab

📌 Swap이란?

  • RAM(메모리)이 부족할 때, 디스크의 일부를 임시 메모리처럼 사용하는 기능이야.
  • 일반적으로 성능이 낮은 서버에서는 RAM이 부족하면 디스크에 데이터를 저장했다가 다시 불러오는데, 디스크 속도는 RAM보다 훨씬 느려.
  • 이 때문에 애플리케이션 실행 속도가 느려지고, 쿠버네티스의 자원 관리가 꼬일 수 있어.

📌 왜 Swap을 꺼야 할까?

  1. 성능 저하 방지
  • 쿠버네티스는 메모리 사용량을 정확하게 예측해서 컨테이너를 배치하는데, 스왑이 활성화되어 있으면 잘못된 예측이 발생할 수 있어.
  1. 노드의 신뢰성 향상
  • 쿠버네티스는 스왑을 고려하지 않고 설계됐기 때문에, 스왑이 켜져 있으면 컨테이너가 비정상적으로 종료될 수도 있어.
  1. 클러스터 불안정 방지
  • 클러스터 전체에서 균형 있게 노드를 배치하려면, 각 노드의 리소스 상태를 정확하게 파악해야 하는데, 스왑이 활성화되어 있으면 이를 정확하게 측정할 수 없음.

📌 명령어 설명

  • swapoff -a → 현재 활성화된 스왑을 모두 비활성화함.
  • sed -i '/swap/d' /etc/fstab → 재부팅해도 스왑이 자동으로 켜지지 않도록 설정 파일에서 스왑 항목을 삭제.

하위 원문: sed란?

🔹 방화벽 비활성화

sudo ufw disable

📌 왜 방화벽을 비활성화할까?

  • 기본적으로 Ubuntu의 방화벽(UFW)은 네트워크 트래픽을 차단할 수 있어.
  • 쿠버네티스는 여러 노드 간에 자유롭게 네트워크 통신을 해야 하므로, 방화벽을 끄는 게 안전함.
  • 필요하면 나중에 설정을 조정할 수도 있음.

🔹 네트워크 필터링 설정

echo 'net.ipv4.ip_forward=1' | sudo tee -a /etc/sysctl.d/k8s.conf
sudo sysctl --system

📌 br_netfilter란?

  • 쿠버네티스에서는 여러 개의 컨테이너가 서로 같은 네트워크 안에서 통신해야 해.
  • 그런데 기본적으로 Linux 커널은 브릿지 네트워크에서 패킷을 필터링하지 않아.
  • 이를 활성화하면, 컨테이너 간 통신이 원활하게 되고, 네트워크 정책이 제대로 적용됨.

📌 각 명령어 설명

  • modprobe br_netfilter → 브릿지 네트워크에서 패킷을 필터링하는 기능을 활성화함.
  • echo 'net.bridge.bridge-nf-call-iptables=1' | sudo tee -a /etc/sysctl.d/k8s.conf
    → iptables가 브릿지 네트워크의 트래픽을 필터링할 수 있도록 설정함.

하위 원문: tee란?

  • echo 'net.ipv4.ip_forward=1' | sudo tee -a /etc/sysctl.d/k8s.conf
    → 패킷이 다른 네트워크로 전달될 수 있도록 허용함.
  • sysctl --system → 설정을 즉시 적용함.

하위 원문: 이걸 왜 사용자가 수동으로 해야하는지?

하위 원문: 브릿지 네트워크

3. 컨테이너 런타임 (containerd) 설치

쿠버네티스는 애플리케이션을 실행할 때 "컨테이너(Container)"라는 기술을 사용해.

컨테이너를 실행하려면 이를 관리하는 컨테이너 런타임(Container Runtime)이 필요해.

쿠버네티스에서 지원하는 컨테이너 런타임에는 여러 가지가 있지만, 현재 가장 권장되는 것은 containerd야.

3-1. containerd 설치

sudo apt update && sudo apt install -y containerd

📌 이 명령어는 무슨 역할을 할까?

  • apt update → 패키지 목록을 최신 상태로 업데이트함.
  • apt install -y containerd → containerd를 설치함. (y는 "설치할까요?"라는 질문 없이 자동 진행)

3-2. containerd 설정

쿠버네티스에서 containerd를 제대로 사용하려면 몇 가지 설정이 필요해.

sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml

📌 각 명령어의 역할

  • sudo mkdir -p /etc/containerd
    → /etc/containerd 폴더를 생성함. (p는 "이미 폴더가 있으면 그냥 넘어가라"는 의미)
  • containerd config default | sudo tee /etc/containerd/config.toml
    → 기본 설정 파일을 /etc/containerd/config.toml에 저장함.

3-3. containerd의 CGroup 설정 변경

sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml

📌 이게 왜 필요할까?

  • CGroup(Control Groups): 리눅스에서 CPU, 메모리, 네트워크 같은 자원을 여러 프로세스가 효율적으로 나눠 쓰도록 도와주는 기능.
  • 쿠버네티스는 기본적으로 CGroup을 systemd 방식으로 사용해야 하는데, 기본 설정은 false로 되어 있음.
  • 그래서 sed 명령어를 사용해서 SystemdCgroup = true로 변경해 줌.

3-4. containerd 서비스 재시작 및 자동 실행 설정

sudo systemctl restart containerd
sudo systemctl enable containerd

📌 각 명령어의 역할

  • systemctl restart containerd → 변경된 설정을 적용하기 위해 containerd를 다시 시작.
  • systemctl enable containerd → 서버를 재부팅해도 containerd가 자동으로 실행되도록 설정.

4. 쿠버네티스 핵심 구성 요소 설치

쿠버네티스를 설치하려면 세 가지 핵심 프로그램이 필요해.

프로그램 역할
kubeadm 쿠버네티스 클러스터를 초기화하는 도구
kubelet 각 노드에서 컨테이너를 실행하는 프로그램
kubectl 쿠버네티스를 제어하는 CLI(Command Line Interface) 도구

4-1. 쿠버네티스 패키지 다운로드를 위한 보안 키 추가

curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.29/deb/Release.key | sudo gpg --dearmor -o /usr/share/keyrings/kubernetes-archive-keyring.gpg

📌 이 명령어는 무슨 역할을 할까?

  • 리눅스에서 패키지를 설치하려면 해당 저장소가 "신뢰할 수 있는 곳"인지 확인해야 해.
  • 쿠버네티스 패키지는 공식 저장소에서 다운로드해야 하므로 보안 키(GPG Key)를 등록해야 해.
  • gpg --dearmor → 키 파일을 변환해서 리눅스에서 사용할 수 있도록 만듦.
  • /usr/share/keyrings/kubernetes-archive-keyring.gpg에 저장함.

4-2. 쿠버네티스 패키지 저장소 추가

echo "deb [signed-by=/usr/share/keyrings/kubernetes-archive-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.29/deb/ /" | sudo tee /etc/apt/sources.list.d/kubernetes.list

📌 왜 해야 할까?

  • apt(패키지 관리자)는 기본적으로 우분투의 공식 저장소에서만 패키지를 다운로드해.
  • 하지만 쿠버네티스는 별도의 저장소에서 제공되므로, 추가로 등록해야 함.
  • /etc/apt/sources.list.d/kubernetes.list → 쿠버네티스 저장소를 등록하는 파일.

4-3. kubeadm, kubelet, kubectl 설치

sudo apt update
sudo apt install -y kubeadm=1.29.5-1.1 kubelet=1.29.5-1.1 kubectl=1.29.5-1.1

📌 각 프로그램의 역할

  • kubeadm → 클러스터 초기화 및 설정 도구
  • kubelet → 각 노드에서 컨테이너 실행 및 관리
  • kubectl → 쿠버네티스를 제어하는 CLI(Command Line Interface) 도구

4-4. 쿠버네티스 버전 고정

sudo apt-mark hold kubelet kubeadm kubectl

📌 이 명령어가 하는 일

  • 쿠버네티스는 계속해서 새로운 버전이 나오지만, 자동 업데이트되면 기존 설정과 충돌할 가능성이 있어.
  • apt-mark hold를 사용하면 이 세 가지 프로그램이 자동으로 업데이트되지 않도록 막을 수 있어.
  • 버전 관리를 직접 하고 싶을 때 유용한 설정이야.

5. 마스터 노드 설정 (kubeadm init)

이제 모든 노드에서 기본 프로그램을 설치했으니까, 마스터 노드를 초기화해서 클러스터를 구성할 거야.

sudo kubeadm init --pod-network-cidr=192.168.0.0/16

📌 이 명령어가 하는 일

  • kubeadm init → 쿠버네티스 클러스터를 생성하는 명령어.
  • -pod-network-cidr=192.168.0.0/16 → 클러스터 내부에서 사용할 네트워크 범위를 지정.

📌 초기화가 끝나면 아래와 같은 메시지가 출력될 거야.

Your Kubernetes control-plane has initialized successfully!
To start using your cluster, you need to run the following as a regular user:
...
Then you can join any number of worker nodes by running the following on each as root:
kubeadm join <MASTER_IP>:6443 --token <TOKEN> --discovery-token-ca-cert-hash sha256:<HASH>
  • 이 kubeadm join 명령어를 복사해 두자!
  • 나중에 워커 노드를 마스터 노드에 연결할 때 사용할 거야

6. 마스터 노드에서 kubectl 사용 설정

쿠버네티스를 제대로 사용하려면 kubectl을 설정해야 해.

kubectl은 쿠버네티스를 조작하는 CLI(Command Line Interface) 도구야.

🔹 kubectl을 사용할 수 있도록 환경 설정

mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

📌 각 명령어의 역할

  1. mkdir -p $HOME/.kube
    → 쿠버네티스 설정 파일을 저장할 폴더를 생성. (p는 폴더가 이미 있으면 그냥 넘어가라는 의미)
  2. sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
    → 클러스터 인증 파일(admin.conf)을 사용자의 설정 폴더로 복사.
  3. sudo chown $(id -u):$(id -g) $HOME/.kube/config
    → 현재 사용자에게 config 파일의 소유권을 부여.

이제 kubectl로 Kubernetes API의 리소스를 조회하고 변경할 수 있다.

7. CNI(네트워크 플러그인) 설치

쿠버네티스에서 컨테이너끼리 통신하려면 "네트워크 플러그인(CNI)"을 설치해야 해.

CNI는 쿠버네티스 내부의 Pod들이 서로 네트워크를 통해 연결되도록 도와주는 역할을 해.

📌 쿠버네티스에서 많이 사용하는 CNI 플러그인

CNI 플러그인 특징
Calico 보안 정책(NetworkPolicy) 지원, 복잡하지만 강력함
Flannel 가장 간단한 네트워크 플러그인, 빠르고 설정이 쉬움

우리는 Calico 또는 Flannel 중에서 하나를 설치하면 돼.

🔹 Calico 설치

kubectl apply -f https://docs.projectcalico.org/manifests/calico.yaml

📌 이 명령어의 역할

  • kubectl apply -f [파일] → 쿠버네티스 리소스를 적용하는 명령어.
  • https://docs.projectcalico.org/manifests/calico.yaml
    → Calico 네트워크 플러그인을 쿠버네티스에 설치하는 YAML 파일.

🔹 Flannel 설치

kubectl apply -f https://raw.githubusercontent.com/coreos/flannel/master/Documentation/kube-flannel.yml

📌 이 명령어의 역할

  • Flannel 네트워크 플러그인을 설치하는 YAML 파일을 적용함.

💡 둘 중 하나만 선택해서 설치하면 돼!

8. 워커 노드 연결

쿠버네티스 클러스터는 마스터 노드 + 워커 노드로 구성돼.

이제 워커 노드를 클러스터에 연결할 차례야.

🔹 마스터 노드에서 kubeadm init 실행했을 때 출력된 명령어 실행

sudo kubeadm join <MASTER_IP>:6443 --token <TOKEN> --discovery-token-ca-cert-hash sha256:<HASH>

📌 각 항목의 의미

  • <MASTER_IP>:6443 → 마스터 노드의 API 서버 주소.
  • <TOKEN> → 워커 노드가 마스터 노드에 연결할 때 사용하는 인증 토큰.
  • -discovery-token-ca-cert-hash sha256:<HASH>
    → 클러스터의 보안 인증을 확인하는 해시 값.

💡 이 명령어는 마스터 노드를 초기화할 때(kubeadm init) 출력됐던 명령어를 그대로 사용해야 해.

🔹 워커 노드가 join 명령어를 실행하면 어떻게 될까?

  1. 워커 노드가 마스터 노드와 연결됨.
  2. 마스터 노드가 워커 노드를 쿠버네티스 클러스터의 일부로 추가함.
  3. 워커 노드에서 실행되는 kubelet이 컨테이너를 실행할 준비를 함.

9. 클러스터 상태 확인

이제 모든 설정이 끝났으니까, 클러스터가 정상적으로 동작하는지 확인해보자.

🔹 마스터 노드에서 실행

kubectl get nodes

📌 출력 예시

NAME          STATUS   ROLES           AGE    VERSION
master-node   Ready    control-plane   10m    v1.29.5
worker-node   Ready    <none>          5m     v1.29.5

📌 여기서 중요한 부분

  • STATUS가 Ready면 클러스터가 정상적으로 동작 중.
  • master-node는 control-plane 역할을 하고 있음.
  • worker-node가 정상적으로 추가됐는지 확인할 수 있음.

🎉 쿠버네티스 클러스터 설치 완료!

✅ 이제 kubectl을 사용해서 쿠버네티스를 제어할 수 있어.

✅ 네트워크 플러그인을 설치해서 Pod끼리 통신이 가능해.

✅ 워커 노드를 마스터 노드에 연결해서 클러스터 구성이 완료됐어.

이 구성 이후 Kubernetes에서 애플리케이션을 배포하고 관리할 수 있다.

💡 추가적으로 알면 좋은 내용

✅ 클러스터 상태 확인

kubectl get pods -A
  • 모든 네임스페이스(A)의 Pod 상태를 확인할 수 있음.
  • 네트워크 플러그인이 정상적으로 실행되는지 체크할 수 있음.

✅ 만약 워커 노드가 NotReady 상태라면?

kubectl describe node worker-node
  • 자세한 오류 메시지를 확인하고 문제를 해결할 수 있음.

✅ kubeadm join 명령어를 잃어버렸다면?

kubeadm token create --print-join-command
  • 새로운 kubeadm join 명령어를 생성할 수 있음.

✅ 클러스터 삭제 (연습 후 초기화할 때 사용)

kubeadm reset
  • 쿠버네티스 클러스터를 완전히 초기화함.
  • 연습 후 다시 클러스터를 만들 때 사용 가능.

📌 정리

  • 마스터 노드에서 kubectl 설정 → 쿠버네티스를 제어할 수 있도록 환경 설정.
  • CNI(네트워크 플러그인) 설치 → Pod들이 서로 통신할 수 있도록 설정.
  • 워커 노드 연결 → kubeadm join 명령어를 실행해서 마스터 노드에 연결.
  • 클러스터 확인 → kubectl get nodes를 실행해서 모든 노드가 Ready 상태인지 확인.

버전 고정 운영 기록

이걸 왜 사용자가 수동으로 해야하는지?

📌 왜 kubeadm이 자동으로 k8s.conf 설정을 안 해줄까?

좋은 질문이야! 쿠버네티스를 설치할 때 필수적인 네트워크 설정이라면, 왜 kubeadm이 자동으로 해주지 않을까? 🤔

✅ 1. kubeadm은 최소한의 설정만 자동화함

  • kubeadm은 쿠버네티스 클러스터를 설정하는 도구일 뿐, OS 네트워크 설정까지 자동으로 구성하지 않아.
  • 쿠버네티스를 실행하는 환경(리눅스 배포판, 네트워크 구조, 방화벽 설정 등)은 사용자마다 다를 수 있어서, OS-level 설정을 강제하지 않음.
  • 쿠버네티스는 다양한 환경에서 실행될 수 있기 때문에, 운영체제(OS) 관련 설정은 사용자가 직접 설정하도록 설계됨.

💡 즉, kubeadm은 "쿠버네티스를 설치하는 도구"이지 "리눅스 환경을 자동 설정하는 도구"가 아님.

✅ 2. kubeadm이 sysctl 설정을 자동으로 바꾸지 않는 이유

쿠버네티스가 정상적으로 작동하려면 리눅스 커널에서 몇 가지 네트워크 설정이 필요해.

대표적으로 두 가지:

  1. net.bridge.bridge-nf-call-iptables=1
  • iptables가 브릿지 네트워크 트래픽을 필터링할 수 있도록 설정.
  • 만약 이 설정이 없으면, 쿠버네티스에서 네트워크 정책(NetworkPolicy)이 제대로 동작하지 않음.
  1. net.ipv4.ip_forward=1
  • 패킷이 다른 네트워크로 전달될 수 있도록 설정.
  • 이 설정이 없으면, Pod 간 통신이 불가능해질 수도 있음.

💡 하지만 이 값들은 쿠버네티스만 사용하는 설정이 아니고, 리눅스 시스템 전체에 영향을 줄 수 있기 때문에 kubeadm이 자동으로 변경하지 않음!

→ 만약 kubeadm이 임의로 이 설정을 바꿔버리면 다른 네트워크 애플리케이션이 오작동할 수도 있음.

→ 그래서 사용자가 직접 설정하도록 문서에서 안내하고 있음.

✅ 3. kubeadm은 특정 환경에서 실행될 수도 있기 때문

  • kubeadm은 Bare-metal 서버, 가상 머신, 클라우드(AWS, GCP, Azure) 등 다양한 환경에서 실행될 수 있어.
  • 하지만 각 환경마다 네트워크 설정이 다름.
  • 클라우드에서는 기본적으로 net.ipv4.ip_forward=1이 설정되어 있을 수도 있음.
  • 일부 보안이 중요한 환경에서는 브릿지 네트워크 트래픽 필터링(bridge-nf-call-iptables=1)을 허용하지 않을 수도 있음.

💡 즉, kubeadm이 임의로 설정을 변경하면 특정 환경에서 문제가 발생할 수 있기 때문에, 사용자가 직접 설정하도록 유도하는 거야.

✅ 4. 네트워크 플러그인(CNI)마다 필요한 설정이 다를 수 있음

  • 쿠버네티스에서 Pod 간 네트워크 통신을 담당하는 플러그인(CNI, Container Network Interface)이 여러 가지 있어.
  • 대표적인 CNI 플러그인:
  • Calico
  • Flannel
  • Cilium
  • Weave Net
  • 하지만 각 네트워크 플러그인마다 필요한 커널 설정이 다를 수도 있음.
  • kubeadm이 특정 설정을 강제해버리면 어떤 CNI에서는 불필요한 설정이 적용될 수도 있고, 다른 CNI에서는 설정이 부족할 수도 있어.

💡 그래서 네트워크 플러그인을 설치하기 전에 사용자가 직접 OS-level 설정을 해야 하는 거야!

✅ 5. kubeadm 문서에서도 사용자가 직접 설정하라고 안내함

쿠버네티스 공식 문서에서도 kubeadm을 실행하기 전에 사용자가 직접 sysctl 설정을 해야 한다고 설명하고 있어.

📌 쿠버네티스 공식 문서에서 요구하는 sysctl 설정 예시 (출처: Kubernetes 공식 문서)

cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF

sudo modprobe overlay
sudo modprobe br_netfilter

cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF

sudo sysctl --system

📌 이 파일을 직접 설정해야 하는 이유

  1. OS 설정은 사용자의 책임이므로, kubeadm이 자동으로 하지 않음.
  2. 시스템마다 기본값이 다를 수 있어서, 사용자가 직접 확인하고 적용해야 함.
  3. 쿠버네티스가 네트워크를 제대로 관리할 수 있도록 보장하기 위함.

📌 결론

✅ kubeadm은 쿠버네티스를 설치하는 도구일 뿐, OS-level 설정을 자동으로 변경하지 않음.

✅ net.bridge.bridge-nf-call-iptables=1과 net.ipv4.ip_forward=1 설정은 쿠버네티스 네트워크 정책과 Pod 간 통신에 필요하지만, OS 전체에 영향을 줄 수 있어서 사용자가 직접 설정해야 함.

✅ 다양한 환경(Bare-metal, 클라우드, VM 등)에서 실행되기 때문에, 자동으로 설정하면 오히려 문제가 발생할 수 있음.

✅ 네트워크 플러그인(CNI)마다 필요한 설정이 다를 수 있어서, kubeadm이 강제하지 않고 사용자가 직접 설정하도록 유도함.

✅ 쿠버네티스 공식 문서에서도 sysctl 설정을 수동으로 하라고 안내하고 있음.

sed란?

📌 sed란?

sed는 Stream Editor(스트림 편집기)의 줄임말이야.

즉, 파일의 내용을 직접 열지 않고도 특정한 텍스트를 찾아서 변경, 삭제, 추가할 수 있는 명령어야.

📌 sed의 기본 문법

sed 's/찾을_문자열/바꿀_문자열/' 파일이름

📌 문법 설명

  • 's/찾을_문자열/바꿀_문자열/' → 특정 문자열을 다른 문자열로 변경하는 명령어
  • s → "substitute" (치환)
  • /찾을_문자열/바꿀_문자열/ → 찾을 문자열을 바꿀 문자열로 대체
  • 파일이름 → 변경할 파일

📌 sed를 사용한 예제

🔹 예제 1: hello를 hi로 변경

echo "hello world" | sed 's/hello/hi/'

📌 출력 결과

hi world

💡 원래 문자열에서 "hello"를 "hi"로 변경함.

🔹 예제 2: 파일에서 특정 단어 바꾸기

sed 's/cat/dog/' example.txt

📌 example.txt 내용 (변경 전)

I have a cat.

📌 출력 결과 (변경 후)

I have a dog.

💡 파일을 직접 수정하지 않고, cat을 dog로 바꿔서 출력함.

🔹 i 옵션: 파일을 직접 수정

sed -i 's/cat/dog/' example.txt

📌 설명

  • i 옵션을 사용하면 파일을 직접 수정함.
  • 이제 example.txt 파일을 열어보면 cat이 dog로 변경되어 있을 거야.

💡 ⚠️ 주의: -i 옵션을 사용하면 원본 파일이 즉시 변경되므로 조심해서 사용해야 해!

📌 sed가 swap을 삭제하는 원리

🔹 우리가 실행한 명령어

sudo sed -i '/swap/d' /etc/fstab

📌 각 부분의 의미

  • i → 파일을 직접 수정
  • '/swap/d' → swap이 포함된 줄을 삭제 (d는 delete의 약자)
  • /etc/fstab → 수정할 파일 (fstab은 부팅 시 마운트할 파일 시스템을 정의하는 설정 파일)

💡 즉, fstab 파일에서 "swap"이 포함된 줄을 찾아서 삭제하는 명령어야.

💡 이렇게 하면 재부팅해도 swap이 다시 켜지지 않게 돼. 🚀

📌 추가적으로 sed에서 자주 사용하는 기능

✅ 대소문자 구분 없이 변경하기 (I 옵션 사용)

echo "Hello hello" | sed 's/hello/hi/I'

📌 출력 결과

hi hello

💡 기본적으로 sed는 대소문자를 구분하지만, I 옵션을 사용하면 무시할 수 있어.

✅ 특정 단어가 포함된 줄 삭제 (/문자열/d 사용)

sed '/error/d' logfile.txt

💡 logfile.txt에서 "error"가 포함된 모든 줄을 삭제함.

✅ 파일에서 특정 부분만 출력 (-n 옵션 + p 명령어 사용)

sed -n '2p' example.txt

💡 example.txt의 2번째 줄만 출력함.

📌 정리

  • sed는 파일을 직접 열지 않고도 특정한 텍스트를 찾아서 변경, 삭제, 추가할 수 있는 명령어.
  • s/문자열1/문자열2/ → 문자열을 변경함.
  • i → 파일을 직접 수정함.
  • d → 특정한 줄을 삭제함.
  • 우리가 실행한 sudo sed -i '/swap/d' /etc/fstab은 fstab 파일에서 swap이 포함된 줄을 삭제해서 재부팅해도 swap이 다시 활성화되지 않도록 설정하는 명령어.

tee란?

📌 tee 명령어란?

tee는 표준 입력(stdin)으로 받은 데이터를 화면에 출력하면서 동시에 파일에 저장하는 명령어야.

✅ tee의 기본 역할

  • 출력 결과를 화면과 파일에 동시에 기록
  • 파일을 덮어쓰거나(>) 추가(>>)할 수 있음
  • 권한이 필요한 파일에도 sudo와 함께 사용 가능

📌 tee 기본 사용법

echo "Hello World" | tee output.txt

📌 출력 결과

Hello World

📌 파일 내용 (output.txt)

Hello World
  • echo "Hello World" → "Hello World"를 출력.
  • | tee output.txt → 출력 결과를 output.txt 파일에도 저장하면서 동시에 화면에도 출력.
  • 💡 >(리다이렉션)와 비슷하지만, tee는 화면에도 출력함!

📌 tee를 사용해야 하는 이유

보통 > 연산자를 사용하면 파일에만 기록되고 화면에는 출력되지 않아.

하지만 tee를 사용하면 파일에도 저장하면서, 실행된 결과를 바로 확인할 수 있음.

✅ 1️⃣ 파일을 덮어쓰는 경우 (>와 동일)

echo "New Content" | tee output.txt

📌 출력 결과

New Content

📌 파일 내용 (output.txt)

New Content

💡 파일 내용이 기존 내용 없이 새 내용으로 덮어씌워짐.

✅ 2️⃣ 파일에 내용을 추가하는 경우 (>>와 동일)

echo "Another Line" | tee -a output.txt

📌 출력 결과

Another Line

📌 파일 내용 (output.txt)

New Content
Another Line

💡 -a 옵션을 사용하면 기존 파일 내용에 추가(Append)됨.

📌 tee가 쿠버네티스 설정에서 사용되는 이유

🔹 우리가 실행한 명령어

echo 'net.bridge.bridge-nf-call-iptables=1' | sudo tee -a /etc/sysctl.d/k8s.conf

📌 이 명령어가 하는 일

  1. echo 'net.bridge.bridge-nf-call-iptables=1'
    → "net.bridge.bridge-nf-call-iptables=1"이라는 설정을 출력함.
  2. | sudo tee -a /etc/sysctl.d/k8s.conf
    → 이 출력을 /etc/sysctl.d/k8s.conf 파일에 추가함.
  3. a (append) 옵션을 사용했으므로 기존 설정을 유지하면서 새 줄을 추가.

💡 즉, tee를 사용하면 설정을 추가하면서, 동시에 화면에도 출력돼서 확인할 수 있음!

🔹 tee를 안 쓰고 >만 사용하면?

echo 'net.bridge.bridge-nf-call-iptables=1' > /etc/sysctl.d/k8s.conf

⚠ 이렇게 하면 기존 파일의 내용이 전부 사라지고 덮어쓰기됨.

📌 원래 있던 설정을 유지하면서 추가하려면 tee -a를 사용해야 해.

📌 결론

  • tee는 출력된 내용을 파일에 저장하면서 동시에 화면에도 보여주는 명령어야.
  • a 옵션을 사용하면 기존 파일 내용에 추가(Append) 가능.
  • 쿠버네티스 설정 파일을 수정할 때 기존 내용을 유지하면서 새로운 설정을 추가할 때 유용함.
  • sudo와 함께 사용하면 권한이 필요한 시스템 파일도 수정 가능.

📌 정리

명령어 역할
echo "Hello" > file.txt file.txt에 "Hello"를 저장 (기존 내용 삭제됨)
echo "Hello" >> file.txt file.txt에 "Hello"를 추가 (기존 내용 유지)
\`echo "Hello" tee file.txt\`
\`echo "Hello" tee -a file.txt\`

📌 k8s.conf 파일은 원래 존재하는 파일일까?

기본적으로 리눅스에는 /etc/sysctl.d/k8s.conf 파일이 존재하지 않는다.

없는 파일에도 tee 명령어를 사용해서 새로 생성할 수 있다.

📌 tee는 없는 파일에도 적용 가능할까?

tee는 파일이 존재하지 않으면 새로운 파일을 자동으로 생성한다.

🔹 예제 1: 없는 파일에 tee 사용

echo "Hello Kubernetes" | tee newfile.txt

📌 실행 후 확인

cat newfile.txt

📌 출력 결과

Hello Kubernetes

💡 파일이 없었지만 tee가 자동으로 생성해서 내용을 기록함.

🔹 우리가 실행한 명령어를 다시 분석해보자

echo 'net.bridge.bridge-nf-call-iptables=1' | sudo tee -a /etc/sysctl.d/k8s.conf

📌 이 명령어가 하는 일

  1. echo 'net.bridge.bridge-nf-call-iptables=1'
    → "net.bridge.bridge-nf-call-iptables=1" 문자열을 출력.
  2. | sudo tee -a /etc/sysctl.d/k8s.conf
    → /etc/sysctl.d/k8s.conf 파일이 없으면 자동으로 생성하고, 있으면 내용을 추가함.

k8s.conf 파일이 존재하지 않더라도 tee가 새 파일을 만들고 내용을 기록할 수 있다.

📌 k8s.conf는 왜 따로 만들어야 할까?

✅ 리눅스에서 시스템 커널 설정을 관리하는 파일은 /etc/sysctl.conf 또는 /etc/sysctl.d/*.conf 경로에 위치해야 해.

✅ sysctl.d/ 디렉터리는 여러 설정 파일을 개별적으로 관리할 수 있도록 지원함.

✅ k8s.conf는 쿠버네티스 관련 네트워크 설정을 따로 관리하기 위해 수동으로 생성하는 파일이야.

✅ /etc/sysctl.d/에 .conf 파일을 추가하면 sysctl --system을 실행할 때 자동으로 읽혀서 설정이 적용됨.

📌 tee가 없으면 어떻게 해야 할까?

만약 tee를 쓰지 않는다면 > 또는 >> 연산자를 사용해야 해.

✅ >를 사용한 방법 (덮어쓰기)

echo 'net.bridge.bridge-nf-call-iptables=1' | sudo sh -c 'cat > /etc/sysctl.d/k8s.conf'

📌 문제점: 기존 설정이 있으면 사라짐! (덮어쓰기)

✅ >>를 사용한 방법 (추가하기)

echo 'net.bridge.bridge-nf-call-iptables=1' | sudo sh -c 'cat >> /etc/sysctl.d/k8s.conf'

📌 tee -a와 같은 효과지만, tee보다 명확한 에러 메시지를 보기 어려움.

📌 tee는 실행하면 화면에도 결과를 보여주므로 더 편리함.

📌 정리

✅ /etc/sysctl.d/k8s.conf 파일은 기본적으로 존재하지 않지만, tee가 자동으로 생성해줌.

✅ tee는 없는 파일도 만들면서, 기존 파일이 있으면 내용을 추가(-a)할 수 있음.

✅ /etc/sysctl.d/k8s.conf 파일을 따로 만드는 이유는 쿠버네티스 관련 네트워크 설정을 분리해서 관리하기 위함.

✅ tee 없이 > 또는 >>를 사용할 수도 있지만, sudo tee를 쓰는 게 더 명확하고 편리함.

kubespray

Kubespray 기반 Kubernetes 클러스터 구성 가이드 (HAProxy 포함)

구성 예시

  • HAProxy: 192.168.0.10
  • Master 1: 192.168.0.11
  • Master 2: 192.168.0.12
  • Master 3: 192.168.0.13
  • Worker 1: 192.168.0.21

1. HAProxy 설치 및 설정

1-1. 설치 (Ubuntu 기준)

sudo apt update
sudo apt install -y haproxy

1-2. 설정 파일 수정

sudo nano /etc/haproxy/haproxy.cfg

추가 내용:

frontend kubernetes-frontend
    bind *:6443
    mode tcp
    default_backend kubernetes-backend

backend kubernetes-backend
    mode tcp
    balance roundrobin
    option ssl-hello-chk
    server master1 192.168.0.11:6443 check
    server master2 192.168.0.12:6443 check
    server master3 192.168.0.13:6443 check

1-3. HAProxy 재시작

sudo systemctl restart haproxy
sudo systemctl enable haproxy

✅ pong의 의미

명령 실행 결과가 아래와 같다면:

master1 | SUCCESS => {
    "changed": false,
    "ping": "pong"
}

이때의 "ping": "pong"은:

  • Ansible이 해당 노드에 SSH 접속 성공했고
  • 모듈 실행도 문제없이 완료되었다는 뜻입니다.
  • 즉, 해당 노드는 Ansible 플레이북 실행이 가능한 상태라는 걸 의미합니다.

❌ 반면, 실패한다면

예시:

master1 | UNREACHABLE! => {
    "msg": "Failed to connect to the host via ssh: ..."
}

이 경우는:

  • IP 설정, SSH 접근 권한, 방화벽, 사용자 비밀번호 등 확인해야 합니다.

즉, pong이 뜨면 준비 완료 상태입니다.

이제 ansible-playbook으로 설치 진행해도 됩니다.

Cilium 설치가 필요한 이유

핵심 요약

Multus는 CNI가 아니다. "CNI 플러그인을 여러 개 연결해주는 메타 플러그인"이다.

즉, Multus는 직접 네트워크를 제공하지 않기 때문에, 최소 하나의 기본 CNI 플러그인이 꼭 필요

그래서 Cilium이 필요한 이유

항목 설명
Multus Pod에 여러 네트워크를 붙일 수 있게 해주는 메타 CNI 플러그인
Cilium Pod 간 통신을 실제로 처리하는 기본 CNI 플러그인 중 하나
이유 Multus 자체는 네트워크 연결을 제공하지 않으므로, Pod의 eth0에 붙일 기본 네트워크(CNI)가 필요함. 그 역할을 Cilium이 수행할 수 있음

구조적으로 보면 이렇게 생김:

Pod

├── eth0 (기본 CNI, 예: Cilium, Calico, Flannel 등)

└── eth1 (Multus가 붙여준 SR-IOV/macvlan 등 서브 CNI)

  • eth0: Cilium이 제공
  • eth1, eth2 등: Multus가 붙여주는 추가 네트워크

CNI plugin 디렉토리 확인 방법

CNI plugin 디렉토리란?

Kubernetes에서 네트워크를 구성할 때 사용하는 CNI 플러그인 바이너리 (bridge, macvlan, host-local 등) 들이 설치되는 디렉토리야.

Multus나 Cilium, Calico 같은 CNI는 내부적으로 여기 있는 바이너리들을 실행해서 네트워크를 설정함.

기본 디렉토리 위치

표준 CNI 디렉토리는 다음 두 가지:

  1. CNI 바이너리 디렉토리 (plugin binaries)

→ /opt/cni/bin

  1. CNI 설정 파일 디렉토리 (plugin config)

→ /etc/cni/net.d/

실제 확인 방법

▶︎ CNI 바이너리 디렉토리 확인

ls /opt/cni/bin

예시:

bridge host-local loopback macvlan ptp static vlan flannel cilium multus

여기 있는 파일들이 CNI plugin 실행 파일임 (bridge, macvlan, multus, cilium, flannel 등)

CNI 설치

“CNI”란?

  • CNI(Container Network Interface)는 Kubernetes에서 Pod에 네트워크를 붙이는 플러그인 체계
  • .conf 파일과 /opt/cni/bin 안의 실행 가능한 플러그인 파일들로 구성됨

✅ 2. Multus는 CNI 플러그인이 아니라

“메타 CNI”

Multus는 직접 네트워크를 생성하지 않고,

여러 CNI 플러그인(macvlan, host-device, bridge 등)을 조합해서 호출하는 역할이야.

즉, Multus 혼자선 아무것도 못 하고,

실제 네트워크를 구성해줄 CNI 플러그인들을 따로 설치해야 함

3. Multus를 쓸 때 필요한 CNI는?

CNI 플러그인 이름 역할 필요 여부
macvlan 물리 NIC 위에서 가상 NIC 생성 선택적
bridge 리눅스 bridge 생성 (br0 등) 선택적
host-device 물리 디바이스 직접 파드에 붙임 선택적
ipvlan macvlan과 유사하나 IP 기반 선택적
sriov SR-IOV VF 직접 파드에 붙임 선택적
ptp point-to-point 연결용 실험적
dhcp DHCP로 IP 부여 사용 시 필요

파드를 이해하기 앞서

어플리케이션은 이미 개발이 되어있어야하고 도커이미지로 빌드되어있어야함

또한 쿠버네티스 클러스터가 이미 세팅되어있어야함

→ 싱글노드이건 멀티노드이건 상관없음

우리의 목적은 워커노드와 같은 여러개의 머신에 어플리케이션이 배포되는 것임

쿠버네티스는 다이렉트로 workernode에 컨테이너를 배포하지 않음

→ 컨테이너는 파드라는 형태로 캡슐화됨

파드는 어플리케이션의 하나의 인스턴스임

→ 파드는 k8s에서 만들수 있는 가장 작은 오브젝트임

파드는 일반적으로 컨테이너와 1:1 관계임

→ 스케일을 늘리기위해 기존 파드에 컨테이너를 추가하면 안됨

1:1 관계가 일반적이기 때문에 하나의 파드에 하나의 콘테이너로 제한됨?

→ 아님, 하나의 파드는 동일한 종류의 여러 컨테이너를 갖지 않는다는 사실을 제외하고는 여러 컨테이너를 가질 수 있음

"하지만 때로는 사용자가 입력한 데이터를 처리하거나 사용자가 업로드한 파일을 처리하는 등 웹 애플리케이션을 지원하는 작업을 수행하는 도우미 컨테이너가 있는 시나리오가 있을 수 있습니다. 이러한 도우미 컨테이너들을 웹 애플리케이션 컨테이너와 함께 운영하고 싶을 수 있습니다."

도우미 컨테이너가 너의 어플리케이션과 함께 공존하게 하고 싶을때 같은 파드에 두 컨테이너를 생성할 수 있다.

→ 대신 파드가 죽으면 두컨테이너 같이 죽음

헬퍼컨테이너와 어플리케이션 컨테이너가 1:1 관계를 유지하기 위해서는 서로 1:1로 통실할 필요가 있고 서로의 컨테이너로 부터 데이터를 접근할 수 있어야함

→ 이를 위해서 헬퍼 컨테이너가 어떤 어플리키이션에 연결되어있는지 확인 할 수 있는 맵을 관리해야함

→ 우리는 링크(link)와 사용자 정의 네트워크(custom networks)를 사용하여 이러한 컨테이너들 사이에 네트워크 연결성을 직접 설정해야 합니다."

→ 우리는 공유 가능한 볼륨을 생성하고 이를 컨테이너들 사이에서 공유해야 할 것입니다.

파드가 죽었는지 더이상 필요한지 잘 모니터링해야함

→ 이걸 쿠버네티스는 자동으로 해줌

"팟 내의 컨테이너들은 기본적으로 동일한 저장소에 액세스하며, 동일한 네트워크 네임스페이스에 액세스하며, 함께 생성되고 함께 파기될 운명을 갖습니다."

어플리케이션이 복잡하지 않더라도, 하나의 컨테이너가 있더라도 k8s는 pods를 생성할 필요가 있음

→ 스케일링이나 아키텍처 변화와 같은 미래를 위해서 이게 좋음

하나의 파드안에 멀티컨테이너 사용은 희귀한 케이스임, 보통 하나임

kubectl run nginx

위 명령은 nginx라는 이름의 파드를 만들고, 해당 파드 내에서 nginx 이미지를 사용하여 컨테이너를 실행합니다. 이제 Kubernetes 클러스터에서 해당 파드가 실행되고 NGINX 서버가 실행됩니다.

→ nginx의 이미지는 어디에서 올까?

→ 이미지를 가져오기위해서는 이미지 파라미터를 사용하여 이미지이름을 정해야한다.

→ 이 경우 도커 허브 리포지토리를 통해 nginx를 다운로드함
