물리 계층 장비(허브)와 통신 방식

1. 계층별 장비 구분 기준

네트워크 장비를 물리 계층(1계층)과 데이터 링크 계층(2계층)으로 구분하는 가장 중요한 기준은 주소(Address) 개념의 이해 여부입니다.

구분 물리 계층 장비 (예: 허브, 리피터) 데이터 링크 계층 장비 (예: 스위치)
주소 개념 없음 (주소를 이해하지 못함) 있음 (MAC 주소를 이해함)
정보 처리 송수신 정보에 대한 판단이나 조작이 불가능함. 송수신지를 특정할 수 있으며, 정보에 대한 판단 및 조작이 가능함.
동작 방식 그저 통신 매체의 신호를 중계하거나 증폭할 뿐임. 주소 기반으로 선택적 전달을 수행함.

2. 허브(Hub)의 주요 전송 특징 및 문제점

허브는 주소 개념이 없는 물리 계층의 대표적인 장비이며, 오늘날에는 거의 사용되지 않지만 스위치와의 비교를 위해 학습합니다.

원문 외부 그림 공개 제외: 권리·출처가 확인되지 않거나 링크가 만료된 그림은 재배포하지 않았다. 그림 전후의 설명·표·코드와 판독 가능한 고유 내용은 본문 또는 검증 메모에 보존했다.

① 모든 포트로 메시지 내보내기

  • 특징: 어떤 호스트로부터 메시지를 전달받으면, 수신지 주소를 알 수 없기 때문에 모든 포트에 메시지를 내보냅니다.
  • 문제점: 불필요한 트래픽이 네트워크에 넘쳐나 효율이 매우 낮아집니다.

② 반이중 통신 (Half-Duplex)

  • 특징: 한 번에 한쪽 방향으로만 송수신이 가능한 통신 방식입니다. (예: 무전기)
  • 결과: 한 호스트가 허브에 메시지를 보내고 있을 때, 다른 호스트는 전송을 기다려야 합니다.

③ 충돌 도메인 (Collision Domain) 문제

  • 충돌 발생: 반이중 통신 중 두 호스트가 동시에 메시지를 전송하면 충돌(Collision)이 발생하여 메시지가 손상됩니다.
  • 콜리전 도메인: 충돌이 발생할 수 있는 위험 영역을 콜리전 도메인이라고 합니다. 허브에 연결된 모든 호스트는 하나의 동일한 콜리전 도메인에 속하게 됩니다. 이 영역이 넓어질수록 충돌 가능성이 높아지므로, 네트워크 성능 저하의 주범이 됩니다.

3. 충돌 완화 프로토콜: CSMA/CD

허브 환경에서 충돌을 줄이고 통신을 가능하게 하기 위해 CSMA/CD (Carrier Sense Multiple Access / Collision Detection) 프로토콜을 사용합니다.

  • CS (Carrier Sense): 메시지를 보내기 전, 통신 매체 상에 다른 전송 중인 메시지가 없는지 감지합니다.
  • MA (Multiple Access): 여러 호스트가 동시에 네트워크에 접근할 수 있습니다.
  • CD (Collision Detection):
  • 충돌 발생 시, 잼 시그널(Jam Signal)을 보내 충돌 사실을 모든 호스트에게 알립니다.
  • 충돌 호스트들은 랜덤한 시간(Backoff Time) 동안 대기한 뒤 재전송을 시도하여, 동시에 재전송하는 것을 방지합니다.

이 프로토콜 덕분에 허브 환경에서도 어느 정도 통신이 가능하지만, 스위치는 이와 달리 전이중 통신을 지원하고 콜리전 도메인을 포트별로 분리하여 충돌 문제를 근본적으로 해결합니다.

2. 스위치의 주요 기능

스위치는 MAC 주소를 인식함으로써 허브와 달리 지능적인 데이터 전달이 가능합니다.

① MAC 주소 학습 기능

  • 원리: 스위치는 호스트가 보내는 프레임의 송신지 MAC 주소를 보고, 해당 MAC 주소가 어떤 포트에 연결되어 있는지를 스스로 학습하여 MAC 주소 테이블에 저장합니다. * 플러딩 (Flooding): 목적지 MAC 주소를 아직 모를 경우(테이블에 없을 경우) 한 번만 모든 포트로 프레임을 내보내어 목적지를 찾습니다 (허브와 유사한 초기 동작).
  • 포워딩 & 필터링: 목적지 MAC 주소를 학습한 후에는 해당 포트로만 데이터를 포워딩(Forwarding)하고, 불필요한 포트로는 내보내지 않아 필터링(Filtering)합니다.
  • 에이징 (Aging): MAC 주소 테이블에 등록된 항목을 일정 시간이 지나면 자동으로 삭제하여 테이블을 최신 상태로 유지합니다.

② 브이랜 (VLAN, Virtual LAN) 기능

  • 개념: 하나의 물리적인 스위치를 사용하더라도, 호스트의 물리적 위치와 관계없이 네트워크를 논리적으로 구획하고 나누어 여러 개의 가상의 LAN을 만드는 기능입니다.
  • 목적: 불필요한 트래픽(예: 브로드캐스트 메시지)을 논리적인 구획으로 분리하여 네트워크 성능 저하를 방지합니다.
  • 특징:
  • VLAN으로 나누어진 영역은 서로 다른 네트워크로 간주됩니다.
  • VLAN이 다르면 통신을 위해 스위치(2계층 장비)가 아닌 라우터(3계층 장비)가 필요합니다.
  • VLAN 종류:
  • 포트 기반 VLAN (정적 VLAN): 스위치의 특정 포트에 특정 VLAN을 할당하는 방식입니다 (가장 일반적).
  • MAC 기반 VLAN (동적 VLAN): 호스트의 MAC 주소에 따라 자동으로 VLAN이 결정되는 방식입니다.

17. 네트워크 계층의 기능과 역할

  1. 네트워크 계층(3계층)의 존재 목적

물리 계층(1계층)과 데이터 링크 계층(2계층) 기술은 주로 LAN(같은 네트워크) 내 통신에 한정됩니다. 네트워크 계층은 이 한계를 극복하고 다른 네트워크와의 통신을 가능하게 하기 위해 존재합니다.

구분 1, 2계층 범위 3계층 범위
통신 범위 LAN(같은 네트워크) 내 인접 호스트 간 통신 LAN을 넘어서는 다른 네트워크 간 통신 (WAN)
주요 장비 스위치, 허브, NIC 라우터 (Router)

2. 네트워크 계층의 핵심 제공 기능

다른 네트워크와의 통신을 위해 네트워크 계층은 크게 두 가지 기능을 제공합니다.

  1. IP 주소 지정 (Addressing): IP 주소라는 논리 주소 체계를 통해 송수신 대상을 지정합니다.
  2. 라우팅 (Routing): 패킷이 이동할 최적의 경로를 결정하여 전달합니다. 라우팅을 수행하는 장비가 바로 라우터입니다.

3. 1, 2계층 기술의 한계 (IP가 필요한 이유)

물리 계층과 데이터 링크 계층의 기술만으로는 랜을 넘어서는 통신이 어려운 두 가지 한계가 있습니다.

① 한계 1: 도달 경로 파악의 어려움

지구 반대편 친구와 통신하는 상황처럼 패킷이 여러 네트워크를 거쳐 이동할 때, 어떤 경로로 이동하는 것이 최적인지를 1, 2계층 기술만으로는 판단하기 어렵습니다.

  • 해결: 라우팅(Routing) 기술을 통해 패킷이 이동할 최적의 경로를 결정합니다.

② 한계 2: MAC 주소만으로 위치 특정의 어려움

MAC 주소는 네트워크 인터페이스(NIC)마다 부여되는 고정된 주소입니다. 호스트(컴퓨터)는 시시때때로 속해 있는 네트워크가 달라질 수 있습니다.

  • 문제: MAC 주소만으로는 이 세상 모든 네트워크에 속한 모든 호스트의 현재 위치를 특정하기 어렵습니다.
  • 해결: IP 주소라는 논리 주소를 도입하여 MAC 주소의 한계를 극복하고, 호스트의 현재 논리적 위치를 지정합니다.

4. MAC 주소와 IP 주소의 역할 구분 (비유)

패킷 전송 시 IP 주소와 MAC 주소는 모두 명시되어야 하지만, 그 역할이 명확히 다릅니다.

네트워크 핵심 정리: IP 프로토콜, 주소 체계 및 계층별 역할

1. IP 프로토콜의 기본 정의와 기능 (18강, RFC 791)

IP(Internet Protocol)는 네트워크 계층(3계층)의 핵심 프로토콜이며, 물리/데이터 링크 계층의 한계를 극복하여 네트워크 간 통신을 가능하게 합니다.

1.1. IP의 공식적인 두 가지 기능 (RFC 791)

인터넷 표준 문서인 RFC 791에 정의된 IP의 공식 기능입니다.

  1. 주소 지정 (Addressing): IP 주소를 활용하여 송수신 호스트와 네트워크를 식별합니다.
  2. 단편화 (Fragmentation): 전송 패킷의 크기가 MTU를 초과할 경우, 패킷을 작은 조각으로 나누어 전송합니다.

1.2. IP 주소 체계

구분 IPv4 (32비트) IPv6 (128비트)
길이 32비트 (4옥텟) 128비트 (16바이트)
형식 점(.)으로 구분된 10진수 (192.168.1.1) 콜론(:)으로 구분된 16진수 그룹

3. IP와 도메인 주소의 관계 (사용자 질문 응답)

IP 패킷의 헤더에는 도메인 주소(Domain Name)가 직접 실리지 않습니다.

3.1. 도메인 주소의 처리 과정

  1. 변환 (DNS): 사용자가 입력한 도메인 주소(www.example.com)는 전송 전에 DNS(Domain Name System)를 통해 IP 주소(203.0.113.5)로 변환됩니다.
  2. 헤더 기록: 이 변환된 IP 주소가 IPv4 헤더의 수신지 IP 주소 필드에 기록됩니다. (라우터가 경로를 찾는 데 필요한 정보)

3.2. Host 정보의 위치 (HTTP, DB 통신)

HTTP나 DB 통신에서 사용되는 도메인 이름(Host 정보)은 IP 헤더가 아닌, 데이터(페이로드) 영역에 실려 전송됩니다.

  • Host 위치: 응용 계층 프로토콜(예: HTTP)의 헤더 필드(Host: www.example.com)에 문자열로 기록됩니다.
  • 목적: 이는 라우터의 경로 결정과는 무관하며, 서버에 도착했을 때 서버 프로그램이 이 이름을 보고 특정 서비스(가상 호스팅 등)를 식별하기 위해 사용됩니다.

19. ARP(Address Resolution Protocol)

  1. ARP의 정의와 존재 목적
  • 필요성: 네트워크 통신 시 호스트는 상대방의 IP 주소(\$3\$계층)와 MAC 주소(\$2\$계층)를 모두 알아야 데이터 전달이 가능합니다. 그러나 IP 주소는 알지만 MAC 주소는 모르는 상황이 발생할 수 있습니다.
  • ARP의 역할: IP 주소(논리 주소)를 통해 MAC 주소(물리 주소)를 알아내는 프로토콜입니다.
  • 동작 범위: ARP는 동일 네트워크(같은 LAN) 내에서만 수행됩니다.

2. ARP의 3단계 동작 과정

ARP를 통해 MAC 주소를 알아내는 과정은 다음과 같은 3단계로 이루어집니다.

단계 동작 통신 방식 설명
1. ARP 요청 송신 호스트가 네트워크 전체에 질의 메시지를 보냅니다. (예: "이 IP 가진 호스트, 네 MAC 주소를 알려줘!") 브로드캐스트 (Broadcast) 같은 네트워크의 모든 호스트가 이 메시지를 받습니다.
2. ARP 응답 해당 IP 주소를 가진 호스트만 자신의 MAC 주소를 담아 응답합니다. 유니캐스트 (Unicast) 요청한 호스트에게만 1:1로 직접 응답합니다.
3. ARP 테이블 갱신 요청 호스트는 알아낸 IP-MAC 주소 쌍을 ARP 테이블에 기록합니다. 로컬 저장 다음 통신 시 ARP 요청을 다시 보낼 필요가 없도록 저장합니다.

3. ARP 패킷 구조 및 테이블 관리

1. ARP 패킷 (요청/응답의 내용)

ARP 요청/응답은 ARP 패킷을 주고받는 과정입니다.

  • Operation Code (오퍼레이션 코드): 이 메시지가 ARP 요청인지 응답인지를 나타냅니다.
  • 요청 (Request): 코드 값 1
  • 응답 (Reply): 코드 값 2
  • 주소 필드: 송신지/수신지의 하드웨어 주소(MAC 주소)와 프로토콜 주소(IP 주소)를 명시합니다.

2. ARP 테이블

  • 기능: IP 주소와 그에 매핑되는 MAC 주소를 기록해 두는 로컬 메모리 정보입니다.
  • 관리: 항목은 일정 시간이 지나면 자동으로 삭제되거나(에이징), 사용자가 수동으로 삭제할 수도 있습니다. (예: arp -a 명령어로 확인 가능).

4. ARP의 범위 및 라우팅과의 관계

  • 다른 네트워크 통신 시: 송신 호스트가 다른 네트워크에 속한 호스트와 통신하려 할 때, 최종 목적지 호스트의 MAC 주소는 직접 알 수 없습니다.
  • 라우터 개입: 대신, 송신 호스트는 경로상의 다음 라우터의 MAC 주소를 알아내기 위해 ARP를 사용합니다. 이후 라우터가 패킷을 받아 다시 다음 네트워크의 라우터 MAC 주소를 찾는 ARP를 수행하는 등, ARP는 네트워크별로 수행됩니다.

20. IP 단편화를 피하는 방법

1. 단편화(Fragmentation)의 정의

  • 정의: IP 프로토콜의 공식 기능 중 하나로, 전송하려는 패킷의 크기가 MTU (Maximum Transmission Unit)라고 정해진 최대 크기(일반적으로 1,500바이트)보다 클 경우, 패킷을 MTU 이하의 작은 조각으로 나누어 전송하는 것을 의미합니다 [00:53].
  • 처리: 쪼개진 패킷들은 수신지에 도착하면 다시 하나의 데이터로 재조립됩니다 [01:06].

2. 단편화가 성능에 미치는 악영향 (왜 피해야 하는가)

IP 단편화는 네트워크 성능을 저하시키는 부작용이 크기 때문에, 발생하지 않도록 회피하는 것이 좋습니다.

  1. 대역폭 낭비 및 트래픽 증가:
  • 패킷이 쪼개지면, 조각마다 불필요한 IP 헤더가 다시 덧붙습니다 [01:40].
  • 이 헤더 크기만큼 불필요한 트래픽이 증가하고, 그만큼 네트워크 대역폭이 낭비됩니다.
  1. 수신 측의 부하 증가:
  • 단편화된 패킷들을 하나로 합치는 재조립 과정은 수신 호스트에게 CPU 부하를 발생시킵니다 [02:04].
  • 이는 호스트의 성능 저하 요인이 됩니다.

3. 단편화 회피 방법: 경로 MTU (Path MTU)

단편화를 피하는 가장 좋은 방법은 패킷을 주고받는 경로상의 모든 노드가 단편화 없이 처리할 수 있는 최대 크기만큼만 데이터를 전송하는 것입니다.

1. 경로 MTU (Path MTU)의 정의

  • 정의: IP 단편화 없이 데이터를 주고받을 수 있는 최대 크기입니다 [04:04].
  • 결정 기준: 패킷이 출발지에서 목적지까지 도달하는 경로상에 있는 모든 장치(호스트 및 중간 라우터)의 MTU 크기 중 가장 작은 값으로 결정됩니다 [03:40].

2. 경로 MTU 발견 (Path MTU Discovery)

  • 기법: 통신을 시작하기 전에 이 경로 MTU가 어느 정도인지 계산하여 발견하는 기술입니다 [04:27].
  • 동작 원리: 호스트는 이 경로 MTU 발견을 통해 가장 작은 MTU를 가진 장치(주로 라우터)를 식별하고, 그 크기만큼만 패킷을 송수신하여 단편화를 회피합니다.

3. DF 플래그 설정 (Don't Fragment)

  • 오늘날 대부분의 IP 패킷(IPv4)은 헤더의 플래그 필드 중 DF (Don't Fragment) 비트가 설정되어 있습니다 (DF=1) [05:46].
  • 이는 라우터에게 "이 패킷을 절대로 단편화하지 말라"고 명령하는 것으로, 단편화가 잘 발생하지 않도록 의도된 조치입니다.

21. IP 주소의 구조와 클래스풀 주소 체계

1. IP 주소의 기본 구조

IP 주소는 총 32비트로 구성되며, 크게 두 가지 부분으로 나누어집니다.

  1. 네트워크 주소 (Network ID):
  • 호스트가 속한 특정 네트워크 전체를 식별하는 부분입니다.
  • 라우터가 패킷을 다른 네트워크로 보낼지 여부를 판단하는 기준이 됩니다.
  1. 호스트 주소 (Host ID):
  • 특정 네트워크 내에 속해 있는 개별 호스트(컴퓨터, 장치)를 식별하는 부분입니다.
  • 비트 할당의 유연성: IP 주소의 총 32비트 중 네트워크 주소와 호스트 주소에 몇 비트를 할당할지는 고정되어 있지 않으며, 네트워크의 규모에 따라 달라질 수 있습니다 [02:40].
  • 호스트 주소 공간이 클수록: 네트워크당 더 많은 호스트(장치)에 IP를 할당할 수 있습니다.
  • 단점: IP 주소 공간이 낭비될 가능성이 높습니다.
  • 호스트 주소 공간이 작을수록: 할당할 수 있는 호스트 수가 부족해질 위험이 있습니다.

2. 클래스풀 주소 체계 (Classful Addressing)

IP 주소에서 네트워크 주소와 호스트 주소의 크기를 얼마나 가져갈지 하는 고민을 해결하기 위해, IP 주소의 유형을 미리 정해진 크기대로 분류한 기준이 바로 클래스(Class)입니다 [05:23].

이 주소 체계는 IP 주소의 첫 번째 옥텟 값을 기준으로 유형을 분류합니다.

1. 주요 클래스 (주소 지정에 사용)

클래스 네트워크 주소 할당 호스트 주소 할당 첫 옥텟 범위 네트워크당 호스트 수 (사용 가능)
A 클래스 1 옥텟 (8비트) 3 옥텟 (24비트) 0 ~ 127 2\^24 - 2 (약 1,600만 개)
B 클래스 2 옥텟 (16비트) 2 옥텟 (16비트) 128 ~ 191 2\^16 - 2 (약 6만 5천 개)
C 클래스 3 옥텟 (24비트) 1 옥텟 (8비트) 192 ~ 223 2\^8 - 2 (254개)
  • 선택 기준: 필요한 호스트의 개수가 많다면 A 클래스, 적다면 C 클래스를 선택하여 IP 주소를 할당하면 됩니다 [06:30].

2. 주소 범위 및 시작 비트

클래스 시작 비트 네트워크 수 (이론적)
A 클래스 0으로 시작 2\^7 개 (첫 비트가 0으로 고정되므로, 나머지 7비트만 사용 가능)
B 클래스 10으로 시작 2\^14 개 (첫 2비트가 10으로 고정되므로, 나머지 14비트만 사용 가능)
C 클래스 110으로 시작 2\^21 개 (첫 3비트가 110으로 고정되므로, 나머지 21비트만 사용 가능)

3. 예약된 주소 (할당 불가 주소)

호스트 주소 공간 중에서 개별 호스트에게 할당하여 사용할 수 없는 주소가 두 가지 있습니다 [12:59]. 이는 모든 클래스에 공통으로 적용됩니다.

  1. 네트워크 주소: 호스트 주소 부분이 전부 0인 IP 주소입니다.
  • 해당 네트워크 자체를 지칭하는 주소로 사용됩니다 (예: 172.16.0.0).
  1. 브로드캐스트 주소: 호스트 주소 부분이 전부 1인 IP 주소입니다.
  • 해당 네트워크에 속한 모든 호스트에게 동시에 메시지를 보내는 용도(브로드캐스트)로 사용됩니다 (예: 172.16.255.255).

4. 기타 클래스

  • D 클래스 (224 ~ 239): 주소 지정에 직접 사용되지 않고, 멀티캐스트(Multicast) 통신용 주소로 예약되어 있습니다.
  • E 클래스 (240 ~ 255): 연구 및 실험용으로 예약되어 있습니다.

22. 클래스리스 주소 체계와 서브네팅

1. 클래스풀 주소 체계의 한계 (클래스리스 등장 배경)

기존의 A, B, C 클래스 방식(클래스풀)은 다음과 같은 두 가지 주요 한계 때문에 비효율적이었습니다 [00:11].

  1. IP 주소 낭비 심화:
  • 클래스별 네트워크 크기가 8, 16, 24비트로 고정되어 있어, 필요한 호스트 수에 정확히 맞추기 어렵습니다.
  • 예: 300개의 호스트가 필요한 경우, C 클래스(254개)로는 부족하여 B 클래스(6만 5천 개)를 써야 하므로, 수많은 IP 주소가 낭비됩니다 [01:26].
  1. 정교한 네트워크 구성의 어려움:
  • 사전에 정해진 3가지 크기 이외에 더 유동적이고 정교한 크기로 네트워크를 구획하는 것이 불가능했습니다 [01:47].

2. 클래스리스 주소 체계 (Classless Addressing)

클래스리스 주소 체계는 클래스 개념에 얽매이지 않고 네트워크 영역을 유동적으로 나누어 IP 주소의 낭비를 최소화하는 방식입니다 [02:08].

2.1. 서브넷 마스크 (Subnet Mask)의 도입

클래스 개념을 사용하지 않기 때문에, IP 주소에서 네트워크 주소와 호스트 주소를 구분할 수 있는 별도의 기준이 필요합니다. 그 기준이 바로 서브넷 마스크입니다 [03:16].

  • 서브넷 마스크: 1과 0으로 이루어진 32비트 비트열입니다.
  • 네트워크 주소 부분은 1로, 호스트 주소 부분은 0으로 채워서 IP 주소의 구획을 표시합니다.
  • 서브넷(Subnet)이란 네트워크 내의 부분적인 네트워크를 의미합니다 [03:56].

2.2. CIDR (Classless Inter-Domain Routing) 표기법

서브넷 마스크를 IP 주소 뒤에 슬래시(/)와 함께 1의 개수로 표기하는 방식입니다 [09:17].

  • 예시: 192.168.1.0 / 24
  • 이는 서브넷 마스크의 1이 24개(\$255.255.255.0\$)임을 의미합니다.

3. 서브네팅 (Subnetting)의 원리와 계산

서브네팅이란 서브넷 마스크를 기반으로 기존 네트워크를 원하는 크기대로 더 잘게 나누어 사용하는 행위를 말합니다 [04:54].

3.1. 네트워크 주소 계산 (비트 AND 연산)

IP 주소와 서브넷 마스크 중 어느 부분이 네트워크 주소인지를 계산하는 방법입니다.

  • 원리: IP 주소와 서브넷 마스크를 비트 AND 연산(Bitwise AND)하면, 그 결과가 네트워크 주소 부분이 됩니다 [05:27].
  • AND 연산은 두 피연산자(비트)가 모두 1일 때만 1을, 그 외에는 0을 결과로 냅니다.
  • 서브넷 마스크의 1 부분만 IP 주소를 그대로 통과시켜 네트워크 주소를 추출하는 역할을 합니다 [06:52].

3.2. 유효 주소 범위 계산

서브넷 마스크를 통해 네트워크 주소가 확정되면, 해당 네트워크에서 호스트에게 할당할 수 있는 유효 주소 범위를 알 수 있습니다.

  • 네트워크 주소: 호스트 주소 부분이 전부 0인 IP 주소 (네트워크 자체를 지칭) [13:09].
  • 브로드캐스트 주소: 호스트 주소 부분이 전부 1인 IP 주소 (해당 네트워크의 모든 호스트를 지칭) [13:25].
  • 유효 호스트 주소: 네트워크 주소와 브로드캐스트 주소를 제외한 나머지 주소(\$2\^n - 2\$개)가 유효 호스트에게 할당 가능한 IP 주소 범위가 됩니다.

참고: 이 모든 계산(비트 연산)은 실제로 손으로 할 필요 없이, 서브넷 계산기(Subnet Calculator)를 통해 쉽게 확인할 수 있습니다 [12:20].

3. 사설 IP의 인터넷 통신: NAT 기술의 필요성

  • NAT의 역할: IP 주소를 변환(Translate)해주는 기술로, 주로 사설 IP 주소를 공인 IP 주소와 상호 변환하는 데 사용됩니다 [04:20].
  • 변환 과정 (송신): 사설 IP 주소를 가진 호스트가 외부로 패킷을 보낼 때, NAT 기능이 내장된 라우터(공유기)를 거치면서 송신지 IP 주소가 공인 IP 주소로 변경되어 인터넷으로 나갑니다.
  • 변환 과정 (수신): 외부에서 공인 IP 주소로 도착한 패킷은 라우터를 거치면서 사설 IP 주소로 변경되어 내부의 특정 호스트에게 전달됩니다.
  • N:1 변환: NAT 기술은 포트(Port) 개념과 함께 사용되어, 여러 개의 사설 IP 주소를 가진 호스트들이 하나의 공인 IP 주소를 공유하며 인터넷에 접속하는 N:1 변환도 가능하게 합니다. (이것이 가정에서 여러 장치가 하나의 공유기 IP로 인터넷을 사용하는 원리입니다.)

  • 내부 IP 확인 (사설 IP): ipconfig (Windows)나 ifconfig (Mac/Linux)와 같은 특정 명령어를 통해 확인하면, 라우터가 할당해 준 사설 IP 주소를 볼 수 있습니다.
  • 외부 IP 확인 (공인 IP): 인터넷 검색창에 '내 IP 주소'를 검색하면, 라우터에 할당된 공인 IP 주소가 표시됩니다. 이는 웹 서버(예: 구글 서버)와 통신할 때 사용된 공인 주소를 보여주는 것입니다.

  • 사람이 입력하므로 오입력·중복 가능성

필수 입력값 (4가지):

  4. DNS 주소 — 도메인 이름을 IP로 변환하는 서버 주소

개념:

DHCP 프로토콜을 통해 IP 주소를 자동으로 할당받는 방식.

(DHCP 서버는 보통 라우터나 공유기가 담당)

특징:

  • IP 주소가 자동으로 관리 및 분배됨
  • 사용 기간이 제한된 임대(Lease) 개념 적용
  • 임대 기간 종료 시 IP 반납 → 재할당 시 다른 주소를 받을 수도 있음
  • 임대 만료 전 자동 갱신(renewal) 가능

3. DHCP의 동작 과정 — DORA 절차

단계 메시지 방향 설명
D Discover Client → Broadcast “DHCP 서버 있나요? IP 주세요!”
O Offer Server → (Unicast/Broadcast) “할당 가능한 IP 제안합니다.”
R Request Client → Broadcast “그 IP 사용하겠습니다.”
A ACK Server → (Unicast/Broadcast) “승인 완료! 해당 IP 사용하세요.”

요약:

클라이언트가 DHCP 서버를 찾고(Discover), 서버가 제안(Offer),

클라이언트가 요청(Request), 서버가 승인(ACK)하면

→ IP 주소가 임시로(임대 기간 동안) 자동 설정된다.

핵심 정리

  • 정적 IP: 수동, 고정, 실수·관리 부담 큼
  • 동적 IP: 자동, 효율적, DHCP 서버 필요
  • DHCP = DORA 절차 + 임대(Lease) 개념

25. 예약 주소 ( 0.0.0.0 과 127.0.0.1 )

IP 주소 중에는 특정한 목적을 위해 미리 예약된 주소(Reserved IP) 들이 있습니다. 사설 IP 주소 대역(예: 192.168.x.x, 10.x.x.x, 172.16.x.x 등)도 예약 주소의 일부이지만, 이 강의에서는 개발자가 가장 자주 접하는 두 가지 주소인 127.0.0.1과 0.0.0.0을 중심으로 다룹니다.

1. 127.0.0.1 (루프백 주소, Loopback Address)

127.0.0.1은 IP 주소 대역 127.0.0.0 ~ 127.255.255.255 중 대표적인 주소입니다.

용도:

자기 자신(로컬 호스트, *Localhost*)을 가리키는 특별한 주소입니다.

별칭:

localhost라는 이름으로도 불립니다.


특징:


이 주소로 전송된 패킷은 실제 네트워크 인터페이스를 거치지 않고 자신의 내부 네트워크 스택을 통해 즉시 되돌아옵니다.


즉, 외부 네트워크와는 전혀 관련이 없는 자기 자신으로의 통신(루프백) 전용 주소입니다.


활용 예시:


개발자가 자신의 컴퓨터에서 웹 서버나 데이터베이스 서버 등을 테스트할 때 자주 사용합니다.


예: 127.0.0.1의 8080 포트 또는 localhost의 8080 포트

2. 0.0.0.0 (특정 주소 없음, Unspecified Address)

0.0.0.0은 상황에 따라 두 가지 의미로 사용됩니다.

① 클라이언트의 송신 주소 (IP 미할당 상태)

용도:

호스트가 아직 IP 주소를 부여받기 전, 혹은 자신을 나타낼 유효한 주소가 없을 때 임시로 사용하는 주소입니다.

예시:

DHCP 클라이언트가 네트워크에서 IP 주소를 요청할 때 보내는 DHCP Discover 메시지의 송신지 주소가 0.0.0.0입니다.

즉, “나는 아직 IP 주소가 없지만, 누군가 주소를 줄 수 있나요?”라는 의미입니다.

② 서버의 수신 주소 (모든 주소 허용 상태)

용도:

서버 프로그램이 네트워크 바인딩 시,

“모든 네트워크 인터페이스로부터의 연결을 수락하겠다”는 의미로 사용됩니다.

예시:

웹 서버를 0.0.0.0 주소로 바인딩하면, 해당 서버는

시스템에 연결된 모든 NIC(Network Interface Card) 와

그에 할당된 모든 IP 주소로부터 들어오는 요청을 수락할 수 있습니다.

즉, 특정 IP가 아닌 전체 네트워크 인터페이스를 대상으로 대기합니다.

3. 0.0.0.0/0 (디폴트 라우트, Default Route)

0.0.0.0에 서브넷 마스크가 /0으로 지정된 형태(0.0.0.0/0)는


라우팅 테이블에서 “모든 IP 주소를 의미하는 기본 경로(Default Route)”로 사용됩니다.

26. 라우팅 테이블 정리

1. 라우팅과 라우터의 역할

라우팅(Routing)

  • 서로 다른 네트워크 간에 데이터를 전달하기 위해 최적의 경로를 선택하는 과정
  • 물리 계층/데이터링크 계층의 한계를 넘어 외부 네트워크로 나가기 위해 필수

라우터(Router)

  • 라우팅을 수행하는 네트워크 계층 장비
  • 패킷은 여러 라우터를 거쳐 이동하는데, 이를 Hop-by-Hop 방식이라고 함

관련 개념

  • Hop: 패킷이 한 네트워크 장비를 지나갈 때마다 증가하는 단계
  • 경로 확인 명령어
  • Windows: tracert
  • Linux/Mac: traceroute

2. 라우팅 테이블(Routing Table)

라우터 또는 호스트가 패킷을 어디로 보낼지 결정하기 위해 사용하는 경로 정보 표

생성 방식

  • 수동 라우팅: 관리자가 직접 설정
  • 자동 라우팅: 라우팅 프로토콜(OSPF, RIP 등)이 자동으로 생성

라우팅 테이블 주요 항목

항목 설명
Destination IP / Netmask 향해야 할 최종 목적지 IP 또는 네트워크 대역
Next Hop (Gateway) 다음에 거쳐야 할 라우터의 IP
Interface 패킷을 내보낼 라우터의 포트(인터페이스)
Metric 경로의 비용. 낮을수록 우선순위 높음

3. 디폴트 라우트(Default Route)

표기: 0.0.0.0/0

의미:

  • 라우팅 테이블에 더 구체적인 경로가 없을 때 사용되는 기본 경로
  • "이 IP로 가는 길을 모르겠으면 이쪽으로 보내라"는 의미

용도:

  • 보통 인터넷으로 나가는 기본 게이트웨이를 지정하는 경로

4. 라우팅 테이블 확인 방법

  • Windows: route print
  • Linux / Mac: netstat -rn

27. 라우팅의 분류와 라우팅 프로토콜

라우팅 분류와 프로토콜의 동작 차이에 집중해 정리한다.

네트워크 기초 강의 27강 요약: 라우팅의 분류와 프로토콜

1. 라우팅 테이블 생성 방식에 따른 분류

라우팅 테이블에 경로 항목을 채워 넣는 방식에 따라 크게 정적 라우팅과 동적 라우팅으로 분류됩니다.

분류 특징 장점/단점
정적 라우팅 (Static Routing) 사용자가 수동으로 경로 항목을 직접 입력합니다. 장점: 안정적, 단순. 단점: 규모가 커지면 관리 어려움, 휴먼 에러 발생 가능성, 경로 우회 어려움.
동적 라우팅 (Dynamic Routing) 라우팅 프로토콜을 기반으로 경로 항목이 자동으로 생성 및 갱신됩니다. 장점: 네트워크 변화에 유연하게 대응 가능, 경로 우회 자동 갱신, 대규모 환경에 적합.

2. 라우팅 프로토콜의 분류 기준: AS (자율 시스템)

동적 라우팅의 기반이 되는 라우팅 프로토콜은 AS(Autonomous System)를 기준으로 분류됩니다.

  • AS (자율 시스템): 단일 기술 관리 주체(ISP, 대기업 등)가 관리하는 라우터들의 집단 또는 네트워크 영역을 의미합니다.
  • AS 번호 (ASN): 각 AS에 할당되는 고유 번호이며, 전 세계적으로 유일합니다.
  • AS 경계 라우터 (ASBR): AS의 경계에 위치하여 AS 간의 라우팅을 수행하는 특별한 라우터입니다.

AS 기반 라우팅 프로토콜 분류

분류 약자 의미 프로토콜 예시
AS 내부 라우팅 IGP (Interior Gateway Protocol) 하나의 AS 내부에서 최적 경로를 찾습니다. RIP, OSPF
AS 간 라우팅 EGP (Exterior Gateway Protocol) 서로 다른 AS 간에 최적 경로를 찾습니다. BGP

3. 대표적인 라우팅 프로토콜 상세

A. IGP: RIP (거리 벡터 기반)

  • 기반: 거리 벡터(Distance Vector) 기반입니다.
  • 경로 결정 기준 (Metric): 홉 수(Hop Count), 즉 패킷이 경유하는 라우터의 수가 적을수록 최적 경로로 판단합니다.
  • 작동 방식: 이웃 라우터와 주기적으로 자신의 전체 라우팅 테이블을 교환하며 홉 수를 계산합니다.

B. IGP: OSPF (링크 상태 기반)

  • 기반: 링크 상태(Link State) 기반입니다.
  • 경로 결정 기준 (Metric): 주로 대역폭(Bandwidth)을 기반으로 Metric을 계산하며, 대역폭이 높은 링크일수록 Metric 값이 낮아져 우선 선택됩니다.
  • 작동 방식:
  1. 현재 네트워크의 구성(링크 상태)을 그래프 형태로 구성합니다.
  2. 링크 상태 데이터베이스(Link State Database)에 이 정보를 저장합니다.
  3. 최단 경로 알고리즘 (Dijkstra)을 수행하여 최적의 경로를 찾아냅니다.

C. EGP: BGP (경로 벡터 기반)

  • 기반: 경로 벡터(Path Vector) 기반입니다. 패킷이 거쳐온 AS의 목록(경로)을 고려합니다.
  • 유형: AS 간 통신을 위한 eBGP와 AS 내부 통신을 위한 iBGP로 나뉩니다.
  • 작동 방식: 피어링(Peering) 과정을 통해 다른 AS의 BGP 라우터와 연결을 맺고 경로 정보를 교환합니다.
  • 최적 경로 결정의 복잡성: RIP나 OSPF에 비해 최적 경로 결정 과정이 복잡하며, 다양한 속성(Attribute)과 정책(Policy)이 고려됩니다.

BGP 경로 결정 속성 (Attributes) 예시

  1. AS Path (AS 경로): 메시지가 수신지에 이르는 과정에서 거치게 된 AS들의 목록을 나타냅니다.
  2. Next Hop (다음 홉): 다음으로 거칠 라우터의 IP 주소입니다.
  3. Local Preference (지역 선호도): 외부 경로를 선택하는 과정에서 내부적으로 어떤 경로를 가장 선호할지 AS 관리 주체가 부여한 정책적인 Metric입니다.

30. ICMP

  1. ICMP의 정의와 목적
  • 정의: IP(Internet Protocol)를 보조하는 프로토콜로, 인터넷 제어 메시지 프로토콜이라고 불립니다.
  • 주요 목적: 신뢰성이 없는 IP 통신 과정에서 발생하는 문제에 대한 피드백(Feedback)을 제공하여, 네트워크 상태를 진단하고 오류를 보고하는 데 사용됩니다.
  • 데이터 전송 역할은 아님: ICMP는 TCP나 UDP처럼 사용자의 응용 프로그램 데이터를 목적지로 전송하는 용도로 사용되지 않습니다.
  1. ICMP의 계층적 위치
  • OSI 7계층 기준: 네트워크 계층 (Network Layer, L3)에 속합니다.
  • TCP/IP 모델 기준: 인터넷 계층 (Internet Layer)에 속하며, IP 프로토콜과 함께 작동합니다.
    ICMP는 전송 계층(L4)의 TCP나 UDP와는 계층과 역할이 다릅니다.
  1. ICMP 메시지의 캡슐화 (패킷 구조)
  • 위치: ICMP 메시지는 IP 패킷의 페이로드(Payload, 데이터 영역) 안에 캡슐화되어 전송됩니다.
  • 구분: IP 패킷을 수신한 장치는 IP 헤더에 있는 프로토콜 번호 필드를 보고 페이로드 내용이 ICMP인지(번호: 1) TCP인지(번호: 6) 구분합니다.
  • 동시 사용 불가: 하나의 IP 패킷 페이로드에는 ICMP와 TCP/UDP가 동시에 담길 수 없습니다. 오직 하나만 담깁니다.
  1. ICMP 메시지의 주요 유형
    ICMP 메시지는 크게 오류 보고 메시지와 진단 메시지 두 가지 유형으로 나뉩니다.
    \| 유형 \| 메시지 예시 (타입 번호) \| 사용 예시 \|
    \|---\|---\|---\|
    \| 오류 보고 \| 수신지 도달 불가 (Type 3) \| 목적지 네트워크, 호스트, 포트 등으로 도달할 수 없을 때 \|
    \| \| 시간 초과 (Type 11) \| IP 패킷의 TTL(Time-to-Live)이 0이 되어 패킷이 폐기될 때 \|
    \| 진단 \| 에코 요청 (Type 8) \| ping 명령어 실행 시, 상대방에게 연결 상태 확인 요청 \|
    \| \| 에코 응답 (Type 0) \| ping 요청에 대한 응답 메시지 \|
  2. ICMP의 한계
  • ICMP는 IP 통신의 신뢰성을 완전히 보장하지 않습니다. 단지 오류를 보고할 뿐, 오류를 수정하거나 패킷의 유실을 방지하는 기능은 전송 계층의 TCP가 담당합니다.
  • ICMP 메시지 자체도 네트워크 환경에 따라 유실될 수 있습니다.
  1. 에코(Echo)의 기본 개념

에코(Echo) = 메아리
→ 내가 보낸 것을 그대로 되돌려받는 것을 의미함.

ex) 산에서 “야!” 하면 “야!”가 다시 돌아오는 것.

네트워크에서도 똑같이
보낸 메시지가 그대로 돌아오면, 상대방이 살아있음을 확인할 수 있음.

  1. 네트워크에서의 에코(Echo)

네트워크 장치에게 어떤 메시지를 보내고,
그 메시지가 똑같이 되돌아오면(메아리처럼)
“상대 장치가 정상적으로 동작 중”임을 증명할 수 있음.

그래서 IP 네트워크에서는 이 원리를 그대로 적용해서
“에코 요청(Echo Request)”과 “에코 응답(Echo Reply)” 구조를 만든 것.

  1. 에코 요청(Echo Request, Type 8)

내가 상대에게 보내는 ICMP 메시지

의미: “내 메시지 들리냐? 네트워크 연결돼 있냐?”

  1. 에코 응답(Echo Reply, Type 0)

상대가 에코 요청을 받으면 그대로 되돌려주는 메시지

의미: “응! 네가 보낸 메시지 잘 받았어. 나 정상적으로 작동 중이야!”

  1. ping이 이걸 어떻게 활용하는가?

ping 명령은 네트워크 연결 상태를 확인할 때 아래와 같이 동작함:

  1. 내 PC → 서버
    에코 요청(Type 8) 전송
  2. 서버 → 내 PC
    에코 응답(Type 0) 수신
  3. ping이 계산

요청~응답까지 걸린 시간 → 왕복 시간(RTT)

응답이 아예 안 돌아오면 → 연결 끊김 혹은 문제

즉, ping은 “메아리가 돌아오는지”로 네트워크를 점검하는 도구이다.

  1. 한 문장 요약

에코(Echo)는 “보낸 것을 그대로 돌려받는 메아리”이고,
ICMP의 에코 요청(Type 8)/에코 응답(Type 0)은
ping이 연결 상태와 왕복 시간을 확인하기 위해 사용하는 메커니즘이다.

🌐 핵심 네트워크 및 라우팅 개념 정리

1. AS (자율 시스템)와 IP 대역의 관계

핵심 개념

  • AS(Autonomous System): 단일 기술 관리 주체(ISP, 대기업 등)가 관리하는 네트워크의 집합입니다. 이 하나의 덩어리가 인터넷에 연결되기 위해 부여받는 고유 식별 번호입니다.
  • IP 대역 (Prefix): AS가 소유하고 관리하는 IP 주소의 묶음입니다.

IPv4와 IPv6에서의 AS

  • AS는 IP 버전에 독립적입니다. AS는 IPv4만을 위한 것이 아닙니다.
  • 하나의 AS(예: KT의 AS4766)는 IPv4 주소 대역과 IPv6 주소 대역을 모두 소유하고 관리할 수 있습니다.
  • AS 간의 경로 교환에 사용되는 BGP는 MP-BGP (Multi-Protocol BGP) 기능을 통해 두 버전의 IP 경로를 동시에 처리합니다.

2. RIP (Routing Information Protocol)의 작동 원리와 한계

RIP의 특징

  • 유형: 거리 벡터(Distance-Vector) 라우팅 프로토콜입니다.
  • 경로 결정 기준: 홉 수(Hop Count)가 가장 적은 경로를 최적 경로로 선택합니다.
  • 정보 학습 방식: 이웃 라우터와 주기적으로 자신의 전체 라우팅 테이블을 교환하며 정보를 학습합니다.
  • 홉 계산 원리: 이웃으로부터 받은 경로 정보의 홉 수에 1을 더하여 자신의 테이블에 기록합니다.

RIP의 한계 (Scale Limit)

  • 최대 홉 수 제한: 15 홉까지만 유효한 경로로 간주하며, 16 홉 이상은 '도달 불가능(Infinity)'으로 처리합니다.
  • 용도: 이러한 한계 때문에 RIP는 전 세계 인터넷이 아닌, 소규모 네트워크(AS 내부)에서만 사용됩니다.

3. 기본 경로 (Default Route)와 계층적 라우팅

0.0.0.0/0의 역할

  • 정의: 기본 경로(Default Route) 또는 Gateway of Last Resort라고 불리며, '모든 주소'를 의미합니다.
  • 사용 목적: 라우터가 자신의 테이블에 없는 미지의 목적지(외부 인터넷)로 가는 트래픽을 처리할 때 사용합니다.
  • 작동 원리: 홈 라우터는 0.0.0.0/0 경로를 통해 패킷을 ISP 라우터라는 다음 홉(Next Hop)으로 전달(토스)합니다.

ISP 라우터의 역할 (경로 위임)

  • 홈 라우터는 ISP 라우터까지의 1 홉 거리만 알면 됩니다.
  • 전달받은 ISP 라우터는 BGP를 사용하여 전 세계 AS 정보를 기반으로 패킷의 최종 목적지까지의 경로를 결정하고 라우팅을 진행합니다.
  • 즉, 홈 라우터는 복잡한 인터넷 라우팅을 ISP 장비에 위임하여 효율성을 높입니다.

4. TTL (Time to Live)과 홉 수 측정

TTL의 본래 목적과 실제 의미

  • 이름: Time to Live (생존 시간) - 유효 기간이라는 뜻을 가집니다.
  • 실제 단위: 하지만 네트워크 환경에서는 '시간(초)'이 아닌 '통과 횟수(홉 수)'를 단위로 사용합니다. 따라서 '살아있는 홉 수'로 이해할 수 있습니다.
  • 기능: 패킷이 라우터를 하나 통과할 때마다 TTL 값은 1씩 감소합니다. 이는 패킷이 라우팅 루프에 빠지는 것을 막기 위한 가장 중요한 안전장치입니다.

홉 수 측정에의 활용

  • ping: 출발 시 설정된 TTL 값과 응답 패킷의 TTL 값을 비교하여 간접적으로 홉 수를 계산합니다.
  • traceroute: TTL 값을 1부터 순차적으로 증가시키며 보내 경로상의 모든 라우터가 TTL 만료 오류를 반환하도록 유도하여 직접적으로 경로상의 모든 홉을 확인합니다.

인터넷 기초 - IP, DNS, router, 패킷

이번 목표는:

“브라우저에서 google.com을 입력하면 실제로 무슨 일이 벌어질까?”

를 이해하는 거야.

그리고 네트워크는 결국 이 질문으로 거의 다 연결돼.

먼저 가장 큰 그림

네가 브라우저에서:

google.com

입력했다고 해보자.

그러면 실제로는:

내 컴퓨터
→ 공유기
→ 통신사(ISP)
→ 여러 라우터
→ 구글 서버

까지 데이터가 이동해야 해.

그런데 문제

세상에는 컴퓨터가 엄청 많음.

예:

수십억 대

그러면 질문.

“누구한테 보내야 하는지 어떻게 알까?”

현실에서도:

서울시 마포구 ...

같은 주소 있어야 택배 보내지?

인터넷도 똑같아.

컴퓨터마다:

IP 주소(IP Address)

가 존재해.

IP 주소란?

네트워크 상 컴퓨터 주소.

예:

142.250.206.14

같은 형태.

즉:

"누구한테 보낼지"

를 식별하는 주소.

그런데 사람은 IP 기억하기 힘듦

예:

142.250.206.14

이런 거 기억하기 어렵지.

그래서 등장한 게:

도메인(Domain)

예:

google.com

즉:

사람용 이름

인 거야.

그러면 컴퓨터는 어떻게 찾을까?

여기서 등장:

DNS

DNS는:

google.com
→ IP 주소

로 바꿔주는 시스템.

즉 흐름은

google.com 입력
      ↓
DNS 조회
      ↓
IP 주소 획득

이제 주소를 알았음

그러면 데이터 보내야 함.

근데 데이터는 그냥 통째로 안 감

예:

100MB 파일

한 번에 보내면 문제 많음.

그래서 네트워크는 데이터를:

Packet(패킷)

이라는 작은 조각으로 나눔.

Packet이란?

네트워크 데이터 조각.

느낌적으로:

[출발지]
[목적지]
[데이터]

형태.

왜 조각으로 나눌까?

이유:

  • 중간 오류 시 일부만 재전송 가능
  • 여러 사용자 데이터 섞어 전달 가능
  • 네트워크 효율 증가

그러면 패킷은 어떻게 이동할까?

여기서 등장:

Router(라우터)

Router 역할

"이 패킷 어디로 보내야 하지?"

판단.

즉 인터넷은 사실:

라우터들의 거대한 연결망

에 가까워.

예시 흐름

내 컴퓨터
→ 집 공유기
→ 통신사
→ 중간 라우터
→ 구글 서버

그런데 여기서 중요한 사실

패킷은:

중간에 유실 가능

함.

예:

  • 네트워크 혼잡
  • 장비 오류
  • 라우터 문제

등.

그리고 순서도 꼬일 수 있음

예:

패킷1
패킷2
패킷3

보냈는데,

실제로는:

패킷2
패킷1
패킷3

순으로 도착 가능.

여기서 문제 발생

그러면:

파일 전송
웹페이지
영상

같은 걸 어떻게 믿고 쓰지?

여기서 등장하는 게

TCP

야.

즉:

IP = 주소 기반 전달
TCP = 신뢰성 보장

이제 다음 단계에서:

  • 연결(Connection)
  • 3-way handshake
  • ACK
  • 재전송
  • 순서 보장

같은 TCP 핵심으로 들어가게 된다.

편입 후 검증 메모

  • 외부 그림: 허브와 IP/MAC 비유의 원문 이미지는 외부 라이선스 링크가 만료되어 재배포하지 않았다. 모든 기술 설명과 역할 비교 표는 본문에 보존했다.
  • 클래스풀 주소: A/B/C 클래스는 역사적 배경이다. 현재 라우팅과 주소 계획은 CIDR prefix를 기준으로 이해한다.
  • ARP 범위: ARP는 IPv4에서 같은 링크의 다음 홉 MAC 주소를 알아내는 데 사용한다. 원격 목적지의 MAC을 인터넷 전체에서 직접 찾는 프로토콜이 아니다.
  • 단편화: IPv4와 IPv6의 단편화 책임이 다르며, 현대 경로에서는 Path MTU Discovery와 적절한 패킷 크기가 중요하다.
