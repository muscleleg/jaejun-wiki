  • 안전한 세션 토큰 생성, 전송 (HTTPS, Secure/HttpOnly Flag), 저장 및 만료 처리.

  • 데이터베이스/파일 시스템의 민감 정보 암호화.
  • 환경 설정 및 API 보안
  • Security Misconfiguration: 기본 설정 오류 방지 및 서버 설정 강화.
  • 민감 정보 (DB 접속 정보, API Key)의 안전한 관리 (환경 변수 또는 비밀 관리 서비스 사용).
  • API 보안: Rate Limiting, 입력 검증, Key 관리.
  • 보안 로깅과 예외 처리

원문 보존 단위

소프트웨어 보안의 이해: 핵심 원칙 및 프로세스

1. 보안 개발 생명 주기 (SSDLC)의 중요성

  • SSDLC (Secure Software Development Life Cycle)는 소프트웨어 개발의 전 과정(계획, 요구사항 정의, 설계, 구현, 테스트, 배포, 유지보수)에 보안 활동을 통합한 방법론입니다.

🎯 중요성

  • 비용 절감: 보안 취약점은 코드가 배포된 후 발견될 경우, 초기 단계에서 발견했을 때보다 수십 배에서 수백 배의 수정 비용이 발생합니다. SSDLC는 취약점을 초기 단계에서 예방하거나 발견하여 전체 비용을 절감합니다.
  • 사전 예방: 개발이 완료된 후 막판에 보안을 '덧붙이는' 것이 아니라, 요구사항 정의 및 설계 단계부터 보안을 고려하여 근본적으로 안전한 아키텍처를 만듭니다.
  • 규정 준수: 국내외 여러 산업 표준(예: ISO 27001, 국내 개인정보보호법)에서 개발 프로세스 내에 보안 활동을 의무화하고 있어, 법적/규제적 요구사항을 충족하는 데 필수적입니다.
  • 기업 신뢰도: 보안 사고는 고객의 데이터 유출 및 서비스 중단을 야기하여 기업의 신뢰도와 평판에 치명적인 손상을 입힙니다.

2. 정보보안의 3요소 (CIA Triad)

정보보안이 추구하는 궁극적인 목표를 정의하는 세 가지 핵심 요소입니다. 이 세 가지 요소 중 하나라도 손상되면 보안 사고로 간주됩니다.

요소 정의 (Definition) 목표 (Goal) 손상 사례 (Compromise Example)
기밀성 (Confidentiality) 인가된 사용자만 정보에 접근할 수 있도록 보장하는 것. 정보 노출 방지 허가받지 않은 사용자가 고객의 개인정보를 열람함.
무결성 (Integrity) 정보가 정확하고, 인가된 방법에 의해서만 변경될 수 있도록 보장하는 것. 정보 위변조 방지 해커가 웹사이트에 접속하여 게시글 내용이나 가격 정보를 임의로 수정함.
가용성 (Availability) 인가된 사용자가 필요할 때 지연 없이 정보와 시스템에 접근하여 사용할 수 있도록 보장하는 것. 서비스 중단 방지 DoS/DDoS 공격으로 인해 서버가 마비되어 사용자가 서비스에 접속하지 못함.

3. 개발자가 지켜야 할 3대 보안 원칙

이 원칙들은 모든 코딩 및 설계 결정에서 보안을 최우선으로 고려하게 만드는 기본 지침입니다.

① 최소 권한의 원칙 (Principle of Least Privilege)

  • 정의: 사용자, 프로세스, 시스템 등 모든 주체에게 자신의 작업을 수행하는 데 필요한 최소한의 권한만을 부여해야 한다는 원칙입니다.
  • 개발 적용:
  • 서비스 계정: 웹 서버가 데이터베이스에 접근할 때, SELECT/UPDATE 권한만 필요한 경우 DROP/DELETE와 같은 치명적인 권한을 부여하지 않습니다.
  • 접근 통제: 일반 사용자에게 관리자 페이지에 접근하거나 다른 사용자의 데이터를 수정할 수 있는 권한을 부여하지 않습니다.

② 깊이 있는 방어 (Defense in Depth)

  • 정의: 단 하나의 보안 메커니즘이 뚫리더라도 전체 시스템이 무너지지 않도록, 여러 계층에 걸쳐 다양한 보안 통제를 적용해야 한다는 원칙입니다.
  • 개발 적용:
  • 데이터 보호: 사용자 비밀번호를 DB에 저장할 때 암호화(1차 방어)를 하고, 전송 시 HTTPS(2차 방어)를 사용하며, 접근 시 다중 인증(3차 방어)을 요구합니다.
  • 입력 검증: 클라이언트(프론트엔드)에서 입력값을 한 번 검증하고, 서버(백엔드)에서 반드시 다시 한 번 검증합니다.

③ 입력 불신 (Never Trust User Input)

  • 정의: 애플리케이션에 들어오는 모든 사용자 입력 데이터(폼 데이터, URL 파라미터, 쿠키, HTTP 헤더 등)는 잠재적인 위협으로 간주하고, 사용하기 전에 반드시 유효성을 검증하고 정리(Sanitize)해야 한다는 원칙입니다.
  • 개발 적용:
  • SQL Injection 방지: 사용자 입력값을 SQL 쿼리에 직접 사용하지 않고, Prepared Statements를 통해 안전하게 처리합니다.
  • XSS 방지: 사용자 입력값이 웹 페이지에 출력될 때, 스크립트 실행을 막기 위해 < > 등의 특수문자를 안전한 문자열로 인코딩하여 출력합니다.

편입 후 검증 메모

  • 보안은 속성: 보안을 마지막 테스트 단계의 기능으로만 두지 않고 요구사항·설계·배포·운영 전반의 제약으로 다룬다.
  • 비밀값: token·password·key는 코드·로그·문서에서 제거하고 짧은 수명·회전·최소 권한과 사용 감사가 가능한 저장소에서 주입한다.
  • 입력 신뢰: 형식 검증뿐 아니라 권한·소유권·business invariant·출력 encoding과 resource limit를 함께 확인한다.
  • 검증 근거: “안전하다”는 선언 대신 threat model, test 결과, dependency scan, incident 대응과 복구 훈련 증거를 남긴다.
