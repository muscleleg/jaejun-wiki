리눅스 아키텍처의 본질

1. 리눅스 아키텍처의 본질

1.1 리눅스는 무엇인가

일반적으로 “리눅스”라고 부르는 것은 운영체제 전체를 의미하는 것처럼 보이지만,

엄밀히 말하면 리눅스는 커널(Kernel) 이다.

GNU 유틸리티(ls, cp, bash 등), 패키지 관리자, systemd, 각종 서버 프로그램은

모두 커널 위에서 동작하는 사용자 공간 프로그램이다.

따라서:

리눅스 = 커널

이라는 이해가 출발점이다.

2. 커널과 사용자 공간

2.1 커널(Kernel)

커널은 운영체제의 핵심이며, 다음을 담당한다.

  • CPU 스케줄링
  • 메모리 관리
  • 파일 시스템 관리
  • 네트워크 스택
  • 디바이스 드라이버 관리

중요한 점은:

하드웨어를 직접 제어할 수 있는 유일한 존재는 커널이다.

2.2 사용자 공간(User Space)

사용자 공간에는 우리가 실행하는 모든 프로그램이 포함된다.

예:

  • bash
  • python
  • nginx
  • docker
  • kubernetes
  • ls, cat 등 명령어

이 프로그램들은 하드웨어를 직접 접근할 수 없다.

왜냐하면:

  • 시스템 안정성
  • 보안
  • 프로세스 격리

를 보장해야 하기 때문이다.

따라서 사용자 프로그램은 반드시 커널을 통해서만 하드웨어를 사용할 수 있다.

3. System Call의 의미

3.1 System Call이란 무엇인가

System Call은

사용자 프로그램이 커널에게 작업을 요청하는 공식 인터페이스

이다.

예:

  • 파일 열기 → open()
  • 파일 읽기 → read()
  • 프로세스 생성 → fork()
  • 네트워크 연결 → connect()

이 함수들은 실제로 커널 내부 기능이다.

사용자 프로그램은 system call을 통해서만:

  • 파일을 읽고
  • 메모리를 할당받고
  • 네트워크를 사용하고
  • 프로세스를 생성할 수 있다.

4. glibc의 역할

4.1 glibc란 무엇인가

glibc는 GNU C Library의 약자이며,

사용자 공간에서 system call을 쉽게 사용할 수 있도록 감싸주는 표준 라이브러리

이다.

중요한 점:

  • system call은 커널 기능이다.
  • glibc는 사용자 공간 라이브러리다.
  • glibc 안의 함수들이 내부적으로 system call을 호출한다.

4.2 구조 흐름

전체 구조는 다음과 같다.

사용자 프로그램

→ glibc 함수

→ system call

→ 커널

→ 하드웨어

glibc는 system call을 “만드는” 것이 아니라,

system call을 “호출해주는” 중간 계층이다.

4.3 예시

C 코드:

printf(“hello”);

여기서:

  • printf는 glibc에 정의된 함수다.
  • printf 내부에서 write()라는 system call이 호출된다.
  • write는 커널 기능이다.

즉, 우리가 호출한 함수는 사용자 공간에 있지만

결국 하드웨어에 접근하는 것은 커널이다.

5. 핵심 개념 정리

커널

→ 하드웨어 관리자

사용자 프로그램

→ 커널 위에서 동작하는 일반 프로그램

System Call

→ 사용자 프로그램이 커널에게 요청하는 공식 통로

glibc

→ system call을 감싸서 쉽게 사용하게 해주는 사용자 공간 라이브러리

6. 최종 이해 문장

리눅스는 커널이며,

사용자 프로그램은 하드웨어를 직접 다룰 수 없고,

glibc를 통해 system call을 호출하여

커널에게 하드웨어 사용을 요청한다.

이 문서를 한 번 덮고 나서,

다시 열었을 때

“구조 그림”이 머릿속에 바로 떠오르면

이 파트는 제대로 이해한 것이다.

다음으로 갈 준비가 되면,

“쉘은 정확히 어떤 역할을 하는가?”를

같은 방식으로 정리해볼까?

네트워크 네임스페이스

네트워크 네임스페이스 진입과 식별 요약

진입 방법

sudo ip netns exec <네임스페이스 ID> bash

예:

sudo ip netns exec cni-9184fb6d-88fc-c73a-86d6-e9bd3ad8914a bash

→ 해당 네임스페이스 내부 쉘로 들어감.

네임스페이스 안에 들어와 있는지 확인

ip netns identify $$
  • 결과가 cni-xxxx-...로 나오면 → 지금 네임스페이스 안에 있음
  • 결과가 없으면 → 지금은 호스트 네임스페이스(기본)

네임스페이스 나가는 방법

exit

→ 빠져나와서 기본 네임스페이스로 복귀

실무 팁

쉘 프롬프트만 보면 안에서 작업 중인지 잘 모르니, 아래처럼 프롬프트를 변경하면 구분이 쉬움:

sudo ip netns exec <ns> bash --rcfile <(echo 'PS1="(netns) \u@\h:\w\$ "')

너의 질문:

"하나의 인터페이스가 여러 개의 IP를 가질 수 있지?"

정답: 그렇다, 가능하다.

리눅스에서는 하나의 인터페이스에 IP alias 또는 secondary IP를 붙여서 여러 개의 IP를 설정할 수 있어.

예시

ip addr add 192.168.0.100/24 dev eth0
ip addr add 192.168.0.101/24 dev eth0

위 명령을 실행하면, eth0이라는 하나의 인터페이스에 두 개의 IP가 붙어.

확인 방법:

ip addr show eth0

출력 예:

2: eth0: ...
    inet 192.168.0.100/24 ...
    inet 192.168.0.101/24 ...

용도

  • 하나의 NIC로 여러 IP를 응답하게 만들 수 있음
  • VIP(가상 IP) 설정할 때도 이 기능을 활용
  • 로드밸런서, keepalived, HA 구성 등에서 자주 씀

단점 (주의할 점)

  • 같은 서브넷 내 IP를 너무 많이 붙이면 ARP 충돌이 일어날 수 있음
  • 인터페이스 단위 트래픽 제어나 QoS에는 약점 있음 → 이럴 땐 veth나 SR-IOV, macvlan 등으로 분리함

즉,

네임스페이스가 "환경"의 격리라면,

인터페이스는 "선"이고,

IP는 그 선에 붙는 "주소표"야.

하나의 네트워크 인터페이스에 여러 IP 주소를 할당할 수 있다.

Shell 확장·파일 권한·Job control

명령을 읽을 때는 program에 전달된 argument만 보지 말고, 그 전에 Shell이 text를 어떻게 확장했는지 확인한다. Quote를 쓰지 않은 *, ?, 변수와 command substitution은 Shell 단계에서 결과 text로 바뀐 뒤 program에 전달된다.

printf '%s\n' "*.log"   # 별표 자체를 전달
printf '%s\n' *.log     # 일치하는 이름들로 확장
printf '%s\n' "$name"   # 한 argument로 보존
printf '%s\n' $name     # word splitting과 glob 확장 가능

Space·별표가 든 filename과 빈 변수를 안전하게 다루려면 variable expansion을 대체로 double quote로 감싼다. rm $target처럼 값과 확장 결과가 불명확한 destructive 명령은 실행 전에 대상 경로를 별도 확인한다.

Directory 권한은 파일 권한과 의미가 다르다

권한일반 파일Directory
r내용 읽기이름 목록 읽기
w내용 수정entry 생성·삭제·이름 변경
x실행경로를 통과하고 entry에 접근

Directory에 w만 있고 x가 없으면 내부 entry를 정상적으로 조작할 수 없다. 파일 삭제 가능 여부는 그 파일의 write bit보다 부모 directory의 w+x와 sticky bit 등에 더 직접적으로 좌우된다.

Job control은 Shell의 대화형 process 관리 기능이다

  • Ctrl-Z: foreground process group에 정지 signal을 보낸다.
  • jobs: 현재 Shell이 추적하는 job을 본다.
  • bg %1: 정지한 job을 background에서 계속한다.
  • fg %1: job을 foreground로 가져온다.
  • command &: 처음부터 background job으로 시작한다.

Terminal을 닫은 뒤에도 유지해야 하는 service를 단순 background job으로 운용하지 않는다. systemd, container orchestrator처럼 restart·log·lifecycle을 관리하는 도구를 사용한다.

편입 후 검증 메모

  • 원문 캡처 전사: 출처가 불명확한 강의 슬라이드는 공개하지 않았다. 그림의 고유 설명은 다음처럼 텍스트로 보존한다.
  • find: 지정한 경로부터 디렉터리 계층을 실시간 순회하며 이름·타입·수정 시각·크기·권한 같은 조건을 평가한다. 경로를 생략하면 현재 디렉터리에서 시작한다.
  • locate: 파일 경로 색인 DB를 검색하므로 대체로 빠르지만, DB 갱신 뒤 생긴 파일은 찾지 못할 수 있다. 시스템에 따라 updatedb나 정기 작업이 색인을 갱신한다.
  • namespace: 네트워크 네임스페이스마다 인터페이스·주소·라우팅 테이블이 분리된다. 프로세스 격리는 mount·PID·user 등 다른 namespace와 cgroup을 함께 봐야 한다.
