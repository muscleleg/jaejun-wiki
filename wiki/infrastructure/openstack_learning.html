1. OpenStack은 자원 Pool을 API로 나누어 쓰는 시스템이다

Compute, Network와 Storage를 중앙 API로 요청하고 Project·User·Policy 경계 안에서 할당한다. Dashboard는 이 API를 사용하는 화면이며 OpenStack 그 자체가 아니다.

범용 역량에서는 서비스 이름 자체를 외우는 데 그치지 않고, 자원 사용·내부 구조·설계·운영·장애 분석을 연결하는 공통 언어로 사용한다.

3. VM 생성 요청의 축약 흐름

  1. Client가 Keystone에서 인증하고 Service Endpoint를 확인한다.
  2. Nova API가 Image, Flavor, Network, Keypair 같은 요청 계약을 받는다.
  3. Nova Scheduler가 Placement의 Resource Inventory와 Allocation을 바탕으로 Compute 후보를 고른다.
  4. 선택된 Compute가 Glance Image를 사용해 Hypervisor에 VM을 만든다.
  5. Neutron이 VM Port를 Network와 Security Group에 연결한다.
  6. Volume을 요청했다면 Cinder가 Backend Volume을 만들고 Nova를 통해 VM에 연결한다.
중요: 실제 구현은 Message Queue, Database, Agent와 Driver를 더 거친다. 위 순서는 처음에 책임을 구분하기 위한 논리 흐름이다.

4. Control Plane과 Data Plane

평면흐름검증
Control PlaneAPI → Auth → Scheduler → DB·Message Queue → AgentService·Endpoint·Agent 상태, API 응답, Log
Data PlaneVM Packet → Port·Switch·Router → Provider NetworkNamespace·Route·ARP·Flow·Packet Capture
Storage Data PathVM Block I/O → Protocol·Driver → Cinder Backend게스트 Block Device, Backend Volume, 실제 쓰기·읽기

Dashboard가 열리고 API가 200을 반환해도 VM Packet과 Volume I/O가 끝까지 흐른다는 보장은 없다. 각 평면의 실제 산출물을 따로 확인해야 한다.

5. Kolla-Ansible은 OpenStack이 아니라 OpenStack을 배포하는 계층이다

kolla-ansible deploy를 실행하면 OpenStack API를 호출해 VM을 만드는 것이 아니다. Ansible Playbook이 호스트의 패키지·디렉터리·설정과 Docker 컨테이너를 원하는 상태로 만들고, 그 컨테이너 안에서 Keystone·Nova·Neutron·Cinder 같은 OpenStack 서비스가 실행된다.

5.1 VIP·HAProxy·Keystone은 API 입구에서 서로 다른 일을 한다

  • VIP는 클라이언트가 서비스에 접근할 때 사용하는 안정적인 대표 IP다. All-in-One에서도 서비스별 실제 컨테이너 주소를 직접 기억하지 않게 한다.
  • HAProxy는 VIP의 포트를 받아 알맞은 API backend로 전달한다. 싱글노드에서는 고가용성 이점보다 공통 진입점과 배포 구조의 일관성이 중요하다.
  • Keystone은 트래픽을 분배하는 Proxy가 아니다. 사용자·Project·Role을 확인하고 Token과 Service Catalog를 제공한다.
헷갈리기 쉬운 구분:
192.168.50.254 같은 Kolla VIP는 “OpenStack 서비스 API의 입구”이고, 172.24.4.x Floating IP는 “VM 데이터 트래픽이 OpenStack 바깥과 통신하는 주소”다.

6. Nova는 VM을 관리하고, libvirt·QEMU·KVM이 실제 실행을 나눠 맡는다

“Nova가 VM을 만든다”는 말은 책임을 요약한 표현이다. 실제로는 Nova가 수명주기와 배치를 결정하고, nova-compute가 libvirt API를 통해 QEMU 프로세스와 KVM 가속을 사용해 VM을 실행한다.

계층책임없거나 실패하면
Nova API·Scheduler요청 접수, 상태 관리, 실행할 Compute 선택VM 요청·배치 단계에서 실패
nova-compute선택된 호스트에서 VM 생성·삭제·연결 작업 수행해당 Compute의 VM spawn 실패
libvirtNova가 여러 Hypervisor를 일관된 API로 제어하게 함Nova와 실제 VM runtime 사이 제어 실패
QEMUVM 프로세스와 가상 디스크·NIC 등 장치 모델 제공게스트에 필요한 가상 하드웨어 실행 불가
KVMLinux kernel에서 CPU 가상화 확장을 사용해 vCPU 실행 가속하드웨어 가속 불가 또는 매우 제한적인 실행

7. 오류 메시지를 서비스 이름이 아니라 실패한 계층에 놓는다

관측한 현상먼저 볼 경계이유
CLI가 401 UnauthorizedKeystone Token·Project·Role·Endpoint자원 생성 이전의 인증/권한 단계에서 멈췄다.
No valid hostPlacement Inventory·Allocation, Nova Scheduler요청을 실행할 Compute 후보를 선택하지 못했다.
Scheduling 뒤 VM이 ERRORnova-compute·libvirt·KVM·Glance호스트는 골랐지만 실제 VM spawn 또는 image 준비가 실패했다.
VM은 ACTIVE지만 ping 실패Neutron port·Security Group·OVS·Router·NATControl Plane 생성은 끝났고 Network Data Plane을 확인해야 한다.
Volume은 available인데 게스트 장치가 없음Cinder Attachment·Nova·libvirt·iSCSIBackend 생성과 VM Attach는 서로 다른 단계다.
/dev/vdb는 있지만 파일이 안 보임게스트 Partition·Filesystem·Mount·I/OBlock Device 제공과 Filesystem 사용은 별개다.

이 표의 목적은 정답 명령을 외우는 것이 아니라, 마지막으로 성공한 경계 다음부터 조사 범위를 줄이는 것이다.

8. 작은 검증 과제

  1. “Image는 생성됐지만 VM Scheduling이 실패한다”에서 Glance와 Placement·Nova 중 어디부터 볼지 설명한다.
  2. Floating IP가 할당됐지만 외부 통신이 실패할 때 Control Plane 성공과 Data Plane 실패를 구분한다.
  3. Cinder API에서 Volume이 보이는 것과 게스트에서 쓰기가 되는 것 사이에 남은 경로를 적는다.
  4. kolla-ansible deploy와 openstack server create가 각각 어느 계층에 작용하는지 설명한다.
  5. Nova·libvirt·QEMU·KVM을 “결정 → 제어 → 장치 모델 → CPU 가속” 순서로 연결한다.
