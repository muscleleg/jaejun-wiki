1. File과 Block Device는 같은 추상화가 아니다

Application File
  ↓ Filesystem
Logical Block Address
  ↓ Block Device Driver
Physical or Virtual Storage

일반 파일은 이미 어떤 Filesystem이 관리하는 이름·Metadata·Block Mapping 안에 있다. 반면 Block Device는 번호가 붙은 Block을 읽고 쓰는 Interface를 제공하며, 그 위에 Filesystem이나 LVM을 올릴 수 있다.

2. loop 장치는 일반 파일에 Block Device 입구를 붙인다

Host Filesystem의 큰 File
        ↓ loop mapping
/dev/loopN처럼 보이는 Block Device
        ↓
Filesystem 또는 LVM이 사용

데이터가 RAM에 복제되는 것이 아니다. loop 장치에 쓴 Block은 뒤의 File Offset에 기록된다. 재부팅 뒤 같은 번호가 보장되지 않으므로 번호가 아니라 Backing File을 기준으로 연결과 복구를 설계해야 한다.

3. LVM은 Block Device를 유연한 Pool로 나눈다

계층역할
PVLVM이 관리할 Block Device 또는 Partition을 초기화한 단위
VG하나 이상의 PV 용량을 합친 Storage Pool
LVVG에서 잘라 애플리케이션이나 Filesystem에 제공하는 논리 Block Device
Thin Pool논리적으로 큰 LV를 만들되 실제로 쓴 Block만 Pool에서 소비하도록 관리

LVM 이름이 “Physical Volume”이라고 해서 반드시 물리 Disk 전체일 필요는 없다. 하지만 대상 장치를 잘못 고르면 기존 데이터가 손상될 수 있으므로 파괴적 초기화 전에 장치·크기·Backing 관계와 기존 Signature를 읽기 전용으로 확인해야 한다.

4. Cinder 요청이 게스트 Block Device가 되는 흐름

  1. 사용자가 Cinder API에 크기와 Type을 지정해 Volume을 요청한다.
  2. Cinder Scheduler가 조건에 맞는 Backend를 고른다.
  3. Volume Service와 Driver가 LVM Backend에 LV를 만든다.
  4. Nova가 Attach 요청을 받아 Host·Guest 연결을 조정한다.
  5. 게스트 OS에서 새 Block Device가 보인다.
  6. 사용자가 필요에 따라 Partition·Filesystem·Mount를 구성한다.
볼륨과 Filesystem은 다르다.
Cinder가 Block Device를 제공해도 그 안의 Filesystem과 Directory 구조를 자동으로 만들어 주는 것은 아니다.

5. File-backed LVM의 학습 가치와 한계

학습에 좋은 점운영에서 부족한 점
별도 Disk 없이 Volume 생성·Attach·Detach를 실습한다.Host Filesystem과 같은 장애 영역을 공유한다.
loop·LVM·Cinder 계층을 눈으로 확인할 수 있다.성능과 내구성이 전용 Block Storage나 분산 Storage와 다르다.
Backing File을 명확한 실습 경계로 삼는다.Boot 순서와 loop 재연결 자동화가 추가로 필요하다.

따라서 이 구성은 Cinder의 제어·데이터 흐름을 배우는 Lab Backend이지 Production 설계의 증거가 아니다.

6. API에서 실제 I/O까지 검증한다

  1. Cinder Service와 Backend가 활성 상태인지 확인한다.
  2. Volume이 생성되고 Backend에 대응하는 LV가 생겼는지 확인한다.
  3. Attach 뒤 Nova와 Cinder의 Attachment 정보가 일치하는지 확인한다.
  4. 게스트에서 예상 크기의 Block Device가 보이는지 확인한다.
  5. 전용 테스트 Volume에 Filesystem을 만들고 Mount한다.
  6. 파일 쓰기·동기화·읽기 후 Detach·Reattach에서도 데이터가 남는지 확인한다.
  7. 재부팅 뒤 loop·VG·Cinder Backend가 올바른 순서로 복구되는지 확인한다.
