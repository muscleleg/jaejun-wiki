kubectl 과정

Kubernetes에서 kubectl 명령어를 사용해 파드를 생성하는 전체 과정을 종합해서 설명해드리겠습니다.

1. kubectl 명령어로 파드 생성 요청

  • 사용자가 kubectl apply 혹은 kubectl create 명령을 사용하여 파드를 생성하면, 이 요청이 API 서버에 전달됩니다.
  • kubectl은 Kubernetes 클라이언트로서 사용자가 정의한 YAML 파일 등의 매니페스트를 API 서버에 전달하는 역할을 합니다.

2. API 서버가 파드 정의 저장

  • API 서버는 전달받은 파드 생성 요청을 etcd(Kubernetes의 key-value 저장소)에 저장합니다. 이때, 파드는 아직 어느 노드에서 실행될지 결정되지 않은 상태입니다.
  • API 서버는 파드의 정의를 저장한 후, 스케줄러가 이 정보를 확인할 수 있도록 준비합니다.

3. 스케줄러가 파드 배치 결정

  • 스케줄러는 API 서버로부터 대기 중인 파드 정의를 확인합니다.
  • 스케줄러는 클러스터의 상태, 각 노드의 리소스 사용량, 파드가 요구하는 리소스 등을 평가한 후, 파드를 실행할 적합한 노드를 결정합니다.
  • 스케줄러가 어느 노드에 파드를 배치할지 결정하면, 해당 노드의 이름을 파드 정의에 바인딩 정보로 추가하여 API 서버에 전달합니다.

4. API 서버가 kubelet에 배치 정보 전달

  • API 서버는 스케줄러로부터 받은 바인딩 정보를 저장합니다.
  • 이후, API 서버는 각 노드에서 실행 중인 kubelet에게 이 정보를 전달하고, 각 kubelet이 자신에게 할당된 파드의 정의를 가져갈 수 있도록 준비합니다.

5. kubelet이 파드 생성 및 관리

  • kubelet은 API 서버로부터 자신이 실행할 파드 정의를 가져와 해당 노드에서 파드를 생성하고 컨테이너를 실행합니다.
  • kubelet은 이후 주기적으로 파드의 상태를 모니터링하고, 파드가 정상적으로 실행되도록 관리합니다. 문제가 발생할 경우 재시작이나 리소스 할당 조정 등의 작업을 수행합니다.

6. 상태 정보 보고

  • kubelet은 노드와 파드의 상태 정보를 주기적으로 API 서버에 보고하여, API 서버가 클러스터 전체의 상태를 일관되게 파악할 수 있도록 합니다.
  • 이를 통해 관리자는 kubectl get pods 등의 명령어로 파드 상태를 조회하고 클러스터 상태를 모니터링할 수 있습니다.

요약

  • kubectl: 사용자가 명령어로 API 서버에 파드 생성 요청을 보냄.
  • API 서버: 요청을 저장하고 스케줄러와 kubelet이 정보를 가져갈 수 있도록 함.
  • 스케줄러: 파드를 실행할 노드를 결정하여 바인딩 정보(API 서버에 파드-노드 매칭 정보)를 저장.
  • kubelet: API 서버에서 정의된 파드 정보를 가져와 노드에서 파드를 생성하고 관리.
  • 상태 보고: kubelet은 파드와 노드 상태를 API 서버에 보고하여 클러스터 상태를 일관되게 유지.

이러한 프로세스를 통해 Kubernetes 클러스터는 사용자가 요청한 대로 파드를 자동으로 배치하고 관리합니다.

서비스 포트와 이미지에 명시된 포트는 동일해야함

쿠버네티스 환경에서 서비스(Service)는 파드들을 통해 실행되고 있는 애플리케이션을 네트워크에 노출(expose)시키는 가상의 컴포넌트다.

왜 서비스란 것이 필요하게 되었을까? 클러스터 안에서 애플리케이션을 구동시키는 데에 쓰이는 파드들의 반영속적인(ephemeral) 특성 때문이다. 파드를 소개했던 지난 글의 내용처럼, 쿠버네티스에서의 파드는 무언가가 구동 중인 상태를 유지하기 위해 동원되는 일회성 자원으로 언제든 다른 노드로 옮겨지거나 삭제될 수 있다. 또한 파드는 생성될 때마다 새로운 내부 IP를 받게 되므로, 이것만으로 클러스터 내/외부와 통신을 계속 유지하기는 어렵다.

FROM node:14-alpine

WORKDIR /app

COPY package.json .

RUN npm install

COPY . .

EXPOSE 8080

CMD [ "node", "app.js" ]
kubectl expose deployment first-app --type=LoadBalancer --port=8080

해당 값을 가진 이미지를 통해 만든 deployment를 서비스화 시킬때

이미지와 다른 포트로 하면 제대로 동작하지않음

kubectl expose deployment first-app --type=LoadBalancer --port=8081

8081로 서비스할시 제대로 동작하지않았음

전체 코드

import com.pulumi.Context;
import com.pulumi.openstack.compute.Instance;
import com.pulumi.openstack.compute.InstanceArgs;
import com.pulumi.openstack.compute.inputs.NetworkRefArgs;
import com.pulumi.automation.*;

import java.util.Map;

public class OpenStackVmMain {
    public static void main(String[] args) {
        try {
            // 1. 실행 환경에서 OpenStack 인증 정보 가져오기
            String authUrl  = System.getenv("OS_AUTH_URL");
            String username = System.getenv("OS_USERNAME");
            String password = System.getenv("OS_PASSWORD");
            String project  = System.getenv("OS_PROJECT_NAME");

            // 2. Pulumi 프로젝트 정의
            ProjectSettings projectSettings = ProjectSettings.builder()
                    .name("openstack-vm-project")
                    .runtime("java")
                    .description("Pulumi Automation API - OpenStack VM Example")
                    .build();

            // 3. Workspace 옵션 설정 (프로그램 정의 포함)
            LocalWorkspaceOptions options = LocalWorkspaceOptions.builder()
                    .projectSettings(projectSettings)
                    .program((Context ctx) -> {
                        Instance vm = new Instance("my-vm",
                                InstanceArgs.builder()
                                        .flavorName("m1.small")        // VM 스펙
                                        .imageName("ubuntu-20.04")     // 이미지 이름
                                        .network(NetworkRefArgs.builder()
                                                .name("private-net")   // 네트워크
                                                .build())
                                        .securityGroups("default")
                                        .metadata(Map.of("role", "pulumi-vm"))
                                        .build());

                        // ✅ 여러 출력값 등록
                        ctx.export("vm_id", vm.id());
                        ctx.export("vm_name", vm.name());
                        ctx.export("vm_ip", vm.accessIpV4());
                    })
                    .build();



            // 4. Stack 생성/선택
            Stack stack = LocalWorkspace.createOrSelectStack(
                    StackArgs.builder()
                            .stackName("dev")
                            .workDir(System.getProperty("user.dir"))
                            .opts(options)
                            .build()
            );

            System.out.println("✅ Stack initialized: " + stack.name());

            // 5. OpenStack 인증정보 Config 주입
            stack.setConfig("openstack:auth_url", ConfigValue.of(authUrl));
            stack.setConfig("openstack:user_name", ConfigValue.of(username));
            stack.setConfig("openstack:password", ConfigValue.secret(password));
            stack.setConfig("openstack:tenant_name", ConfigValue.of(project));
            stack.setConfig("openstack:domain_name", ConfigValue.of("Default"));

            // 6. 실행 (pulumi up)
            UpResult result = stack.up();

            // 7. 결과 출력
            System.out.println("🚀 OpenStack VM 생성 완료!");
            result.outputs().forEach((key, value) ->
                    System.out.printf("%s = %s%n", key, value.value())
            );

        } catch (Exception e) {
            e.printStackTrace();
        }
    }
}

Project vs Stack 관계

  • Project = 전체 설계도 (예: OpenStack VM 관리하는 코드 묶음)
  • Stack = 그 설계도를 기반으로 만들어진 하나의 환경 배포

예시:

  • Project: openstack-vm-project
  • Stack: dev → 개발 환경, 작은 VM
  • Stack: staging → 테스트 환경, 중간 VM
  • Stack: prod → 운영 환경, 대형 VM

Project = 소프트웨어 애플리케이션

Stack = 각기 다른 실행 인스턴스 (개발용 서버, 운영용 서버 등)

✅ 정리

Stack은 Pulumi Project의 실행 단위이고, 환경별로 다른 Config와 상태를 갖는 독립적인 배포 단위입니다.

우리 코드에서 stackName("dev") 로 지정했으니, 현재는 dev 환경에 맞는 VM을 관리하는 Stack을 쓰고 있는 거예요.

📖 Pulumi Automation API (OpenStack VM 생성 흐름)

1️⃣ 프로젝트 생성

ProjectSettings projectSettings = ProjectSettings.builder()
        .name("openstack-vm-project")
        .runtime("java")
        .build();
  • Pulumi의 최상위 단위 → 프로젝트 이름(openstack-vm-project)과 실행 언어(java)를 정의
  • CLI로 치면 Pulumi.yaml 파일 역할을 코드로 대신한 것

2️⃣ VM 스펙 정의

Instance vm = new Instance("my-vm",
        InstanceArgs.builder()
                .flavorName("m1.small")
                .imageName("ubuntu-20.04")
                .network(NetworkRefArgs.builder()
                        .name("private-net")
                        .build())
                .securityGroups("default")
                .metadata(Map.of("role", "pulumi-vm"))
                .build());
ctx.export("vm_ip", vm.accessIpV4());
  • Program 블록 안에서 VM 리소스를 정의
  • Flavor, Image, Network, Security Group → VM의 스펙

3️⃣ Stack 생성 (환경 단위)

Stack stack = LocalWorkspace.createOrSelectStack(
        StackArgs.builder()
                .stackName("dev")
                .workDir(System.getProperty("user.dir"))
                .opts(options)
                .build()
);
  • dev 라는 스택을 생성/선택
  • 한 Project 안에서 여러 Stack(dev, staging, prod)을 가질 수 있음
  • Stack = 특정 환경에서의 배포 단위 + 상태(State) 보관소

4️⃣ Stack Config 설정 (OpenStack 인증 정보 삽입)

stack.setConfig("openstack:auth_url", ConfigValue.of(authUrl));
stack.setConfig("openstack:user_name", ConfigValue.of(username));
stack.setConfig("openstack:password", ConfigValue.secret(password));
stack.setConfig("openstack:tenant_name", ConfigValue.of(project));
stack.setConfig("openstack:domain_name", ConfigValue.of("Default"));
  • OpenStack Provider가 API 호출할 때 필요한 값들을 Stack Config에 세팅
  • ConfigValue.secret(password) → 비밀번호 같은 민감 정보는 Pulumi state에 암호화 저장

5️⃣ Stack Up 실행

UpResult result = stack.up();
  • pulumi up 과 동일한 동작을 Automation API로 실행
  • 내부적으로:
  1. 현재 Stack State 로드
  2. Program 실행 (VM 정의)
  3. State와 Program 비교(Diff)
  4. 필요한 OpenStack API 호출 → VM 생성/수정/삭제

결과:

result.outputs().forEach((key, value) ->
        System.out.printf("%s = %s%n", key, value.value())
);
  • VM이 생성되고, ctx.export 로 등록한 출력값(IP 등)이 결과로 나옴

✅ 요약

  1. Project 생성 → openstack-vm-project 선언
  2. VM 스펙 정의 → Program 블록에서 Instance 선언
  3. Stack 생성 → dev 스택 (환경 단위, State 보관)
  4. Config 설정 → OpenStack 인증 정보 주입
  5. Stack Up 실행 → pulumi up 실행 → VM 생성

“Pulumi State 파일에 실제로 뭐가 기록되는지” 또는 “Stack마다 Config 값이 달라질 때 어떻게 여러 환경을 관리하는지”예요.

어떤 쪽이 더 궁금하세요?

코드에서 Output<String> 의 의미

예를 들어:

Output<String> vmId   = vm.id();
Output<String> vmName = vm.name();
Output<String> vmIp   = vm.accessIpV4();
  • vm.id() 같은 메서드는 리소스가 생성된 이후에만 알 수 있는 값 → Output<String> 으로 감싸짐
  • Pulumi는 이 Output 을 추적해서, 실제 값이 준비되면 export하거나 다른 리소스에 전달할 수 있음

코드 적용 예시

Program 부분을 이렇게 바꿀 수 있어요:

.program((Context ctx) -> {
    Instance vm = new Instance("my-vm",
            InstanceArgs.builder()
                    .flavorName("m1.small")
                    .imageName("ubuntu-20.04")
                    .network(NetworkRefArgs.builder()
                            .name("private-net")
                            .build())
                    .securityGroups("default")
                    .metadata(Map.of("role", "pulumi-vm"))
                    .build());

    // Pulumi 리소스 속성은 Output<String> 타입
    Output<String> vmId   = vm.id();
    Output<String> vmName = vm.name();
    Output<String> vmIp   = vm.accessIpV4();

    // export 해서 Stack Output으로 노출
    ctx.export("vm_id", vmId);
    ctx.export("vm_name", vmName);
    ctx.export("vm_ip", vmIp);
})

실행 결과 (변함 없음)

vm_id   = 12345678-90ab-cdef-1234-567890abcdef
vm_name = my-vm
vm_ip   = 10.0.0.25

정리

  • Pulumi 리소스 속성은 대부분 Output<T> 타입
  • 이유: 리소스 생성은 비동기적이고, 실제 값은 배포가 끝난 뒤에야 확정됨
  • ctx.export("name", output) 으로 내보내면 Pulumi가 알아서 추적하고, 결과에서는 “실제 값”으로 풀려서 보여짐

apply()

1. Output<T> 는 "나중에 알 수 있는 값"

Pulumi의 리소스 속성은 대부분 Output<T> 타입이에요.

예를 들어:

Output<String> networkOutput = vm.accessIpV4();

여기서 vm.accessIpV4() 는 단순 String 이 아니라 Output<String>.

왜냐면 VM이 실제로 생성된 뒤에야 IP를 알 수 있기 때문입니다.

즉, Output 은 미래에 값이 확정되는 비동기 컨테이너 라고 생각하면 됩니다.

2. apply 란?

apply 는 Output<T> 에 담긴 값을 실제로 쓸 때 사용하는 메서드입니다.

networkOutput.apply(ip -> {
    System.out.println("VM IP: " + ip);
    return ip;
});
  • ip 는 Pulumi가 VM 생성 후 얻어온 실제 값 (ex. "10.0.0.25")
  • apply 블록 안에서만 안전하게 접근할 수 있음
  • apply 의 리턴값은 다시 Output<U> 타입이 됨

3. 왜 그냥 get() 같은 게 없나?

Pulumi는 선언적 IaC라서, 값을 즉시 꺼내 쓰면 실행 순서가 꼬여요.

예:

  • “VM 만들고 → IP 가져오고 → 보안그룹에 넣는다” 같은 순서를 Pulumi가 자동으로 관리해야 함.
  • 그래서 Pulumi는 값을 강제로 꺼내는 대신, 의존 관계를 apply 로 연결하는 방식을 택함.

4. 실전 예시

예를 들어 VM IP를 보안그룹 규칙에 넣고 싶을 때:

Output<String> vmIp = vm.accessIpV4();

SecurityGroupRule rule = new SecurityGroupRule("allow-ssh",
        SecurityGroupRuleArgs.builder()
                .direction("ingress")
                .protocol("tcp")
                .portRangeMin(22)
                .portRangeMax(22)
                .remoteIpPrefix(vmIp.apply(ip -> ip + "/32")) // apply 사용
                .securityGroupId("default")
                .build());

여기서:

  • vmIp 값이 아직 없으니 → 그냥 String으로는 못 씀
  • apply 를 써서 VM이 생성된 뒤 IP를 받아서 보안 그룹 규칙에 넣음

5. 비유

  • Output<T> = “나중에 도착할 택배 상자”
  • apply = 택배가 도착하면 열어서 무언가 하는 행동

✅ 정리

networkOutput.apply(...) 는 Pulumi에서 리소스 속성이 확정된 후 그 값을 사용하거나 변환하기 위한 함수입니다.

즉, Output<T> 값에 안전하게 접근할 수 있는 유일한 방법이에요.
