쿠버네티스

istio에서 게이트웨이 → 가상 서비스 → 서비스 → 파드로 통신이 되는데 가상서비스가 왜 필요한지?

1. Ingress vs Istio Gateway의 차이

  • Kubernetes Ingress: 단순히 외부 트래픽을 내부의 특정 서비스로 라우팅하는 역할
  • Istio Gateway: Ingress와 비슷하지만, Istio의 서비스 메시 내부에서 트래픽을 세밀하게 제어할 수 있음 (예: 버전별 트래픽 분배, TLS, 리트라이, 페일오버 등)

2. Istio에서 가상서비스(VirtualService)가 필요한 이유

Ingress처럼 게이트웨이 → 서비스 → 파드 구조라면?

  • 게이트웨이가 트래픽을 서비스로 보내는 건 가능함
  • 하지만 서비스 내부에서 트래픽을 세부적으로 제어할 방법이 없음

그래서 가상서비스가 필요함.

가상서비스는 "어떤 요청이 어떤 서비스로, 어떤 조건으로 전달될지"를 정의하는 역할을 함.

3. 가상서비스가 없으면?

만약 게이트웨이 → 서비스 → 파드로 직접 라우팅한다면?

  • 트래픽을 A 서비스로 보낼 수는 있지만, 버전별 트래픽 분배(예: 80%는 v1, 20%는 v2) 같은 세밀한 제어는 불가능하다.
  • 서비스 간의 트래픽 정책(예: 특정 경로는 다른 서비스로 라우팅, 특정 요청은 다른 백엔드로 전달 등) 적용 불가능
  • Istio의 페일오버, 리트라이, 시간 초과 설정 등을 활용할 수 없음

4. 가상서비스의 역할

가상서비스는 아래와 같은 세부적인 트래픽 제어를 가능하게 함.

  • 호스트 기반 라우팅: foo.example.com 은 foo-service로, bar.example.com은 bar-service로
  • 경로 기반 라우팅: /api/v1 요청은 v1 서비스로, /api/v2 요청은 v2 서비스로
  • 가중치 기반 라우팅: 80%는 v1으로, 20%는 v2로
  • 페일오버 및 리트라이: 특정 서비스가 다운되면 다른 인스턴스로 자동으로 라우팅
  • 헤더 기반 라우팅: 특정 User-Agent 헤더가 포함된 요청만 특정 서비스로 전달

5. Istio 트래픽 흐름 (게이트웨이 포함)

  1. 외부 요청 발생
  2. 게이트웨이(Gateway)
  • 특정 도메인/포트를 받아들이는 역할
  1. 가상서비스(VirtualService)
  • 게이트웨이에서 들어온 트래픽을 내부 서비스로 라우팅
  • 서비스 메시 내부에서도 특정 서비스 간 트래픽을 조정
  1. 서비스(Kubernetes Service)
  • 트래픽을 실제 파드(Pod)로 전달

7. 결론

  • Kubernetes의 Ingress처럼 "단순 라우팅"만 필요하다면 게이트웨이 → 서비스 구조도 가능
  • 하지만 Istio의 고급 트래픽 관리 기능(버전별 트래픽, 리트라이, 페일오버 등) 을 쓰려면 가상서비스가 필수
  • 가상서비스는 "트래픽을 어떤 기준으로 어떻게 보낼지"를 제어하는 역할을 함

👉 그래서 Istio에서는 게이트웨이 - 가상서비스 - 서비스 - 파드 구조가 필요함.

게이트웨이가 단순히 트래픽을 받아들이는 역할이라면, 가상서비스는 그 트래픽을 "어떻게 보낼지"를 정의하는 중요한 역할을 해! 🚀

k8s의 서비스가 할 수 없는 부분

Kubernetes 서비스(Service)는 기본적으로 IP 기반의 L4(Transport Layer) 라우팅을 제공하고, Istio의 가상서비스(VirtualService)는 L7(Application Layer) 기반의 세밀한 트래픽 제어를 할 수 있어.

📌 Kubernetes 서비스(Service)와 Istio 가상서비스(VirtualService)의 차이

기능 Kubernetes Service Istio VirtualService
라우팅 기준 클러스터 내부 IP(L4) 호스트명, URI 경로, 헤더, 쿠키 등(L7)
트래픽 분배 라운드로빈, 세션 어피니티 버전별(가중치 기반), 지역별 트래픽 제어
리트라이/페일오버 없음 가능
타임아웃 설정 없음 가능
A/B 테스트 불가능 가능 (예: 90% v1, 10% v2)
mTLS 지원 불가능 가능
헤더/쿠키 기반 라우팅 불가능 가능

📍 왜 Kubernetes 서비스만으로는 부족할까?

  1. 호스트 기반 라우팅 불가능
  • Kubernetes 서비스는 IP 기반이기 때문에 foo.example.com을 foo-service로, bar.example.com을 bar-service로 보내는 게 불가능함.
  • Istio VirtualService를 사용하면 도메인(host)별로 트래픽을 다르게 보낼 수 있음.
  1. URI 경로 기반 라우팅 불가능
  • Kubernetes 서비스는 단순한 포트 포워딩 개념이라 /api/v1을 v1 서비스, /api/v2를 v2 서비스로 보내는 게 불가능함.
  • Istio VirtualService에서는 경로 기반 라우팅을 설정 가능.
  1. 버전별 트래픽 분배(A/B 테스트, Canary 배포) 불가능
  • Kubernetes 서비스는 트래픽을 단순히 파드(Pod)로 분배하지만, 특정 버전(v1, v2)으로 나누는 건 불가능.
  • Istio VirtualService는 80% v1, 20% v2 식으로 트래픽을 조정 가능.
  1. 리트라이 및 페일오버 지원 없음
  • Kubernetes 서비스는 기본적으로 트래픽이 실패하면 클라이언트가 다시 요청해야 함.
  • Istio VirtualService를 사용하면 자동으로 리트라이 및 다른 인스턴스로 페일오버 가능.
  1. mTLS 및 세부적인 보안 제어 없음
  • Kubernetes 서비스는 L4(Transport Layer) 수준에서만 동작해서 TLS 설정이나 인증 정책을 적용하기 어려움.
  • Istio VirtualService는 mTLS를 적용해서 내부 서비스 간 보안 강화 가능.

✅ 정리

  • Kubernetes 서비스는 기본적인 IP 기반 L4 라우팅만 가능하고, L7 기반의 세밀한 트래픽 제어는 불가능.
  • Istio VirtualService를 사용하면 도메인(host), URI 경로, 헤더, 쿠키, 버전별 트래픽 분배 같은 고급 트래픽 제어가 가능함.
  • 따라서, 서비스 메시가 필요한 환경(마이크로서비스, A/B 테스트, Canary 배포, 트래픽 정책 제어 등) 에서는 가상서비스가 필수!

👉 그래서 일반 Kubernetes 서비스만으로는 Istio의 고급 트래픽 제어 기능을 대체할 수 없음! 😃

인그레스로도 안되는지?

좋은 질문이야! Ingress와 Istio Gateway + VirtualService가 비슷해 보일 수도 있는데, 사실 기능적으로 큰 차이가 있어.

Ingress로 할 수 있는 것과 Istio VirtualService가 필요한 이유를 비교해볼게.

🚀 Ingress로 안 되는 것들 (Istio VirtualService가 필요한 이유)

1. 헤더 기반 라우팅 불가능

  • 예를 들어, User-Agent가 Mobile이면 mobile-service로, Desktop이면 desktop-service로 보내고 싶다면?
  • Ingress는 이런 헤더 기반 라우팅을 지원하지 않음.
  • Istio VirtualService는 가능 → match: headers["User-Agent"]

2. 버전별 트래픽 분배(A/B 테스트, Canary 배포) 불가능

  • 80%는 v1으로, 20%는 v2로 보내기 같은 가중치 트래픽 분배가 필요할 때?
  • Ingress는 무조건 하나의 서비스로만 보내야 함.
  • Istio VirtualService는 가능 → weight: 80, weight: 20

3. 리트라이 / 페일오버 기능 없음

  • Ingress는 단순 라우팅만 가능해서, 만약 서비스가 다운되면 클라이언트가 직접 다시 요청해야 함.
  • Istio VirtualService는 자동 리트라이 및 다른 인스턴스로 페일오버 가능.

4. mTLS 보안 기능 없음

  • Ingress는 서비스 간 암호화(mTLS)를 제공하지 않음.
  • Istio VirtualService는 서비스 간 통신을 자동으로 암호화(mTLS) 가능 → tls: ISTIO_MUTUAL

5. Rate Limiting(속도 제한) 설정 어려움

  • Ingress 자체적으로 Rate Limiting(속도 제한) 기능이 없음 → Nginx Ingress Controller 같은 추가 설정 필요.
  • Istio VirtualService는 기본적으로 지원 → maxRequestsPerConnection: 1

✅ 정리

  • Ingress는 기본적인 L7 라우팅(도메인, 경로 매칭)만 가능하고, 고급 트래픽 제어 기능은 없음.
  • Istio VirtualService는 A/B 테스트, Canary 배포, 헤더 기반 라우팅, 페일오버, 보안(mTLS)까지 지원.
  • 따라서 Ingress는 단순 외부 트래픽을 서비스로 라우팅하는 데 적합하지만, 서비스 메시 내에서 세밀한 트래픽 제어가 필요한 경우에는 Istio VirtualService가 필수!

👉 결론: Ingress로도 일부 기능은 가능하지만, Istio VirtualService 없이 Istio의 강력한 트래픽 제어 기능을 제대로 활용할 수 없음! 🚀

게이트웨이 → 인그레스도 가능 (추천하지 않음, 기존 인그레스를 유지해야한다면 사용가능)

Istio Gateway에서 Kubernetes Ingress로 트래픽을 보낼 수 있다.

즉, 게이트웨이 → 인그레스 → 서비스 → 파드 구조도 가능함. 하지만 몇 가지 고려해야 할 점이 있어.

📌 Istio Gateway → Ingress 흐름

  1. Istio Gateway
  • 외부에서 들어오는 트래픽을 수락
  1. Istio VirtualService
  • 특정 경로 또는 호스트에 따라 Ingress 서비스로 트래픽 전달
  1. Kubernetes Ingress
  • Ingress Controller(Nginx, Traefik 등)가 트래픽을 다시 Kubernetes 서비스로 전달
  1. Kubernetes 서비스 → 파드
  • Ingress가 연결된 서비스가 요청을 처리

💡 이렇게 하면 Istio의 고급 트래픽 제어 기능을 일부 활용하면서, 기존 Ingress 설정도 유지할 수 있음.

✅ Istio Gateway에서 Ingress로 트래픽 보내는 방법

만약 Ingress를 ingress-nginx로 설정했다고 가정하고, Istio Gateway에서 트래픽을 Ingress로 전달하려면 아래처럼 설정 가능함.

1️⃣ Ingress 서비스 생성

apiVersion: v1
kind: Service
metadata:
  name: ingress-nginx
  namespace: ingress-nginx
spec:
  selector:
    app.kubernetes.io/name: ingress-nginx
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: 80

💡 ingress-nginx의 서비스 이름을 istio VirtualService에서 사용할 예정

2️⃣ Istio Gateway 설정

apiVersion: networking.istio.io/v1alpha3
kind: Gateway
metadata:
  name: my-gateway
  namespace: istio-system
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "example.com"

💡 example.com 도메인으로 들어온 요청을 처리

3️⃣ Istio VirtualService 설정 (Ingress로 트래픽 전달)

apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: ingress-routing
  namespace: istio-system
spec:
  hosts:
    - "example.com"
  gateways:
    - my-gateway
  http:
    - match:
        - uri:
            prefix: /
      route:
        - destination:
            host: ingress-nginx.ingress-nginx.svc.cluster.local
            port:
              number: 80

💡 VirtualService가 Ingress 컨트롤러 서비스로 트래픽을 전달하도록 설정

⚠️ 주의할 점

  1. Ingress 컨트롤러가 Istio 트래픽을 받을 수 있도록 설정해야 함
  • ingress-nginx가 Istio Gateway에서 들어온 요청을 정상적으로 처리할 수 있도록 Ingress 리소스도 잘 설정해야 함.
  1. mTLS 적용 시 호환성 문제 발생 가능
  • Istio 내부 서비스 간 mTLS를 활성화한 경우, Ingress 컨트롤러가 Istio 내부 트래픽을 처리할 때 인증 문제가 발생할 수도 있음.
  1. 굳이 Ingress를 사용할 필요가 없을 수도 있음
  • Istio Gateway + VirtualService만으로 Ingress의 역할을 완전히 대체할 수 있음.
  • Ingress를 쓰는 이유가 없다면 Istio의 기능을 그대로 활용하는 것이 더 깔끔함.

🔥 결론

  • Istio Gateway에서 Ingress 컨트롤러로 트래픽을 전달하는 것 가능
  • 하지만 Istio VirtualService만으로도 충분한 기능 제공
  • 기존 Ingress 설정을 유지하고 싶을 때만 이 방식을 고려하는 것이 좋음 🚀

destination rule의 역할

✅ DestinationRule의 역할 정리

맞아! DestinationRule은 VirtualService가 도달할 목적지(destination)에 대한 트래픽 정책을 정의하는 역할을 해.

즉, VirtualService는 "어디로 보낼지", DestinationRule은 "보낸 후 어떻게 다룰지"를 정하는 거야.

🔹 하나의 DestinationRule이 여러 VirtualService에 적용될 수 있음

  • DestinationRule은 특정 host(서비스)에 대한 정책을 정의하기 때문에, 여러 개의 VirtualService에서 동일한 DestinationRule을 참조할 수 있음.
  • 예를 들어, my-service.default.svc.cluster.local에 대한 DestinationRule이 존재하면, 여러 VirtualService에서 이 DestinationRule을 사용할 수 있음.

✅ 예제: 여러 VirtualService가 하나의 DestinationRule을 공유하는 경우

🔹 첫 번째 VirtualService

apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: my-service-canary
spec:
  hosts:
    - my-service.default.svc.cluster.local
  http:
    - route:
        - destination:
            host: my-service
            subset: v1
          weight: 90
        - destination:
            host: my-service
            subset: v2
          weight: 10

🔹 두 번째 VirtualService

apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: my-service-rolling
spec:
  hosts:
    - my-service.default.svc.cluster.local
  http:
    - route:
        - destination:
            host: my-service
            subset: v1
          weight: 50
        - destination:
            host: my-service
            subset: v2
          weight: 50

🔹 DestinationRule (공통)

apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: my-service
spec:
  host: my-service.default.svc.cluster.local
  subsets:
    - name: v1
      labels:
        version: v1
    - name: v2
      labels:
        version: v2
  trafficPolicy:
    connectionPool:
      http:
        maxRequestsPerConnection: 10
    outlierDetection:
      consecutiveErrors: 5
      interval: 10s
      baseEjectionTime: 30s

🚀 설명

  • 두 개의 VirtualService (my-service-canary, my-service-rolling)가 같은 my-service를 대상으로 하지만, 다른 트래픽 정책을 가짐
  • DestinationRule은 my-service.default.svc.cluster.local에 대한 정책을 정의
  • 버전별 서브셋(subset) 정의 (v1, v2)
  • 연결 풀(connectionPool) 설정
  • 장애 감지(outlierDetection) 적용
  • 즉, VirtualService에서 subset: v1 또는 subset: v2로 지정하면 자동으로 이 DestinationRule을 따름.

🔹 VirtualService만 봐서는 어떤 DestinationRule이 적용되는지 모름

  • VirtualService는 "이 트래픽을 어디로 보낼지"만 정의하므로, 해당 서비스가 어떤 DestinationRule을 따르는지 명확하지 않음.
  • DestinationRule은 서비스(host) 단위로 설정되기 때문에, 여러 VirtualService가 하나의 DestinationRule을 공유할 수도 있음.
  • VirtualService에는 DestinationRule에 대한 직접적인 참조가 없음.
    → DestinationRule이 어떤 VirtualService에 영향을 주는지 확인하려면 istioctl get destinationrule 같은 명령어를 사용해야 함.

🔥 결론

✔️ DestinationRule은 특정 서비스(목적지)에 대한 트래픽 정책을 정의함.

✔️ 하나의 DestinationRule을 여러 VirtualService에서 사용할 수 있음.

✔️ VirtualService만 보면 어떤 DestinationRule이 적용되는지 알 수 없음!

✔️ 어떤 DestinationRule이 적용되었는지 확인하려면 kubectl get destinationrule 또는 istioctl get destinationrule을 사용해야 함. 🚀

재검토 대상 원문

이걸 왜 사용자가 수동으로 해야하는지?

📌 왜 kubeadm이 자동으로 k8s.conf 설정을 안 해줄까?

좋은 질문이야! 쿠버네티스를 설치할 때 필수적인 네트워크 설정이라면, 왜 kubeadm이 자동으로 해주지 않을까? 🤔

✅ 1. kubeadm은 최소한의 설정만 자동화함

  • kubeadm은 쿠버네티스 클러스터를 설정하는 도구일 뿐, OS 네트워크 설정까지 자동으로 구성하지 않아.
  • 쿠버네티스를 실행하는 환경(리눅스 배포판, 네트워크 구조, 방화벽 설정 등)은 사용자마다 다를 수 있어서, OS-level 설정을 강제하지 않음.
  • 쿠버네티스는 다양한 환경에서 실행될 수 있기 때문에, 운영체제(OS) 관련 설정은 사용자가 직접 설정하도록 설계됨.

💡 즉, kubeadm은 "쿠버네티스를 설치하는 도구"이지 "리눅스 환경을 자동 설정하는 도구"가 아님.

✅ 2. kubeadm이 sysctl 설정을 자동으로 바꾸지 않는 이유

쿠버네티스가 정상적으로 작동하려면 리눅스 커널에서 몇 가지 네트워크 설정이 필요해.

대표적으로 두 가지:

  1. net.bridge.bridge-nf-call-iptables=1
  • iptables가 브릿지 네트워크 트래픽을 필터링할 수 있도록 설정.
  • 만약 이 설정이 없으면, 쿠버네티스에서 네트워크 정책(NetworkPolicy)이 제대로 동작하지 않음.
  1. net.ipv4.ip_forward=1
  • 패킷이 다른 네트워크로 전달될 수 있도록 설정.
  • 이 설정이 없으면, Pod 간 통신이 불가능해질 수도 있음.

💡 하지만 이 값들은 쿠버네티스만 사용하는 설정이 아니고, 리눅스 시스템 전체에 영향을 줄 수 있기 때문에 kubeadm이 자동으로 변경하지 않음!

→ 만약 kubeadm이 임의로 이 설정을 바꿔버리면 다른 네트워크 애플리케이션이 오작동할 수도 있음.

→ 그래서 사용자가 직접 설정하도록 문서에서 안내하고 있음.

✅ 3. kubeadm은 특정 환경에서 실행될 수도 있기 때문

  • kubeadm은 Bare-metal 서버, 가상 머신, 클라우드(AWS, GCP, Azure) 등 다양한 환경에서 실행될 수 있어.
  • 하지만 각 환경마다 네트워크 설정이 다름.
  • 클라우드에서는 기본적으로 net.ipv4.ip_forward=1이 설정되어 있을 수도 있음.
  • 일부 보안이 중요한 환경에서는 브릿지 네트워크 트래픽 필터링(bridge-nf-call-iptables=1)을 허용하지 않을 수도 있음.

💡 즉, kubeadm이 임의로 설정을 변경하면 특정 환경에서 문제가 발생할 수 있기 때문에, 사용자가 직접 설정하도록 유도하는 거야.

✅ 4. 네트워크 플러그인(CNI)마다 필요한 설정이 다를 수 있음

  • 쿠버네티스에서 Pod 간 네트워크 통신을 담당하는 플러그인(CNI, Container Network Interface)이 여러 가지 있어.
  • 대표적인 CNI 플러그인:
  • Calico
  • Flannel
  • Cilium
  • Weave Net
  • 하지만 각 네트워크 플러그인마다 필요한 커널 설정이 다를 수도 있음.
  • kubeadm이 특정 설정을 강제해버리면 어떤 CNI에서는 불필요한 설정이 적용될 수도 있고, 다른 CNI에서는 설정이 부족할 수도 있어.

💡 그래서 네트워크 플러그인을 설치하기 전에 사용자가 직접 OS-level 설정을 해야 하는 거야!

✅ 5. kubeadm 문서에서도 사용자가 직접 설정하라고 안내함

쿠버네티스 공식 문서에서도 kubeadm을 실행하기 전에 사용자가 직접 sysctl 설정을 해야 한다고 설명하고 있어.

📌 쿠버네티스 공식 문서에서 요구하는 sysctl 설정 예시 (출처: Kubernetes 공식 문서)

cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF

sudo modprobe overlay
sudo modprobe br_netfilter

cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF

sudo sysctl --system

📌 이 파일을 직접 설정해야 하는 이유

  1. OS 설정은 사용자의 책임이므로, kubeadm이 자동으로 하지 않음.
  2. 시스템마다 기본값이 다를 수 있어서, 사용자가 직접 확인하고 적용해야 함.
  3. 쿠버네티스가 네트워크를 제대로 관리할 수 있도록 보장하기 위함.

📌 결론

✅ kubeadm은 쿠버네티스를 설치하는 도구일 뿐, OS-level 설정을 자동으로 변경하지 않음.

✅ net.bridge.bridge-nf-call-iptables=1과 net.ipv4.ip_forward=1 설정은 쿠버네티스 네트워크 정책과 Pod 간 통신에 필요하지만, OS 전체에 영향을 줄 수 있어서 사용자가 직접 설정해야 함.

✅ 다양한 환경(Bare-metal, 클라우드, VM 등)에서 실행되기 때문에, 자동으로 설정하면 오히려 문제가 발생할 수 있음.

✅ 네트워크 플러그인(CNI)마다 필요한 설정이 다를 수 있어서, kubeadm이 강제하지 않고 사용자가 직접 설정하도록 유도함.

✅ 쿠버네티스 공식 문서에서도 sysctl 설정을 수동으로 하라고 안내하고 있음.

api group

Kubernetes에서 API 그룹(API Group)은 리소스의 집합을 정의하고, 해당 리소스에 대한 작업을 수행하는 데 사용되는 엔드포인트의 논리적인 그룹입니다. API 그룹은 Kubernetes API의 일부이며, 다음과 같은 목적을 가집니다:

  1. 리소스 그룹화: API 그룹은 특정 유형의 리소스를 함께 그룹화하여 조직화합니다. 예를 들어, pods, services, deployments와 같은 리소스들은 모두 Kubernetes의 core API 그룹에 속합니다.
  2. 버전 관리: API 그룹은 특정 버전의 Kubernetes API에 대한 엔드포인트를 식별합니다. 예를 들어, v1, v1beta1과 같은 버전은 특정 API 그룹 내에서 사용됩니다.
  3. 권한 관리: RBAC(Role-Based Access Control)과 같은 Kubernetes 보안 메커니즘에서는 API 그룹을 사용하여 리소스에 대한 권한을 할당합니다. 권한은 특정 API 그룹 내에서 정의되고 관리됩니다.

API 그룹은 Kubernetes API에 대한 RESTful 엔드포인트의 일부를 나타내며, 일반적으로 /apis/{api-group}/{version}와 같은 형식으로 구성됩니다.

예를 들어, core API 그룹의 버전 v1은 다음과 같은 엔드포인트로 표현됩니다: /api/v1. 또한, extensions API 그룹의 v1beta1 버전은 다음과 같이 표현됩니다: /apis/extensions/v1beta1.

API 그룹은 Kubernetes의 확장성과 유연성을 높이는 데 중요한 역할을 합니다. 새로운 리소스를 추가하거나 새로운 버전을 도입할 때, 적절한 API 그룹을 선택하여 기능을 구성할 수 있습니다.

api group 만들 수 있나?

Kubernetes에서는 API 그룹을 직접 만들거나 정의할 수는 없습니다. API 그룹은 Kubernetes 자체에서 미리 정의된 그룹이며, Kubernetes의 코드베이스에 하드코딩되어 있습니다. 새로운 API 그룹을 만들거나 기존 API 그룹을 변경하는 것은 일반적으로 Kubernetes 개발 및 컨트리뷰션 프로세스의 일부이며, 커뮤니티의 결정과 프로젝트의 진행에 따라 이루어집니다.

그러나 사용자가 Kubernetes 환경에서 새로운 리소스 유형을 정의하고 사용할 수는 있습니다. 이를 위해 Custom Resource Definitions (CRDs)를 사용할 수 있습니다. CRDs를 통해 사용자 정의 리소스와 해당 리소스를 다루기 위한 컨트롤러를 정의할 수 있습니다. 이를 통해 사용자는 Kubernetes API에 새로운 리소스 유형을 추가할 수 있습니다. 그러나 이러한 사용자 정의 리소스는 Kubernetes의 기본 API 그룹이 아닌 사용자 정의 그룹 내에서 정의되고 사용됩니다.

따라서 사용자는 Kubernetes의 API 그룹을 확장하는 것은 아니지만, CRDs를 사용하여 사용자 정의 리소스를 만들어 Kubernetes의 확장성을 높일 수 있습니다.

api group을 ""으로주면?

Kubernetes에서 API 그룹을 ""(빈 문자열)으로 지정하는 것은 기본적으로 "core" API 그룹을 나타냅니다. 즉, 리소스에 대한 API 그룹이 명시적으로 지정되지 않았을 때는 "core" 그룹을 사용하는 것으로 간주됩니다.

예를 들어, 다음과 같은 API 경로는 "core" API 그룹의 v1 버전을 나타냅니다:

/api/v1

따라서 API 그룹을 ""로 지정하는 것은 Kubernetes에서 기본적으로 제공되는 "core" API 그룹을 사용하도록 하는 것과 같습니다.

쿠버네티스에서 사용되는 주요 API 그룹 중 일부는 다음과 같습니다:

  1. core:
  • 가장 기본적인 API 그룹으로, 쿠버네티스의 핵심 기능을 포함합니다.

Kubernetes Statefulset

Statefulset은 application의 상태를 관리해주는 API 오브젝트

Deployment와 비슷하게 container spec에 기반을 두지만, Pod간 독자성을 제공

즉, persistent한 식별자를 제공해주며 네트워크, 스토리지, 순서등의 기능이 있다는 뜻

말 그대로 stateless한 서비스에는 지금까지 공부한 다른 것들을 이용해도 되지만, stateful한 서비스 (ex. DB, network)등에 대해서는 Statefulset을 사용하여 서비스해야함

Deployment에서 Replicas를 1로 고정하여 사용해도 되긴 하지만, 기능과 의미를 완벽히 보장하지 않기에 권장하지 않음

간단하게 정리하자면

  • Deployment(Replicaset) -> 동일하고 교체 가능한 서버
  • Statefulset -> 개별 관리가 필요하고 대체가 불가능한 서버

로 이해하면 된다.

1. StatefulSet 이해하기

쿠버네티스 클러스터상에서 돌아가는 애플리케이션을 애완동물(pets)이나 가축(cattle)으로 생각해봅시다.

개발자는 각 인스턴스에 이름을 부여하고 개별적으로 관리한다는 점에서 애플리케이션을 애완동물처럼 대하는 경향이 있는데, 그러한 각별한 주의를 기울일 필요 없이 가축처럼 취급하는 편이 더 나을 수 있습니다. 그러면 농부가 병든 가축을 교체하는 것 처럼 비정상적인 인스턴스를 주저없이 교체할 수 있기 때문입니다.

스테이트리스(stateless) 애플리케이션의 인스턴스는 가축과 같이 동작합니다. 인스턴스가 죽더라도 새로운 인스턴스를 만들 수 있고 사람들은 그 차이를 눈치채지 못할 것이기 떄문에 인스턴스가 죽는 것은 아무런 문제가 되지 않습니다.

그러나 스테이트풀(stateful) 애플리케이션은 애완동물과 같습니다. 애완동물이 죽었을 때 새 애완동물을 바로 살 수 없고, 주변 사람들도 금방 알아차릴 것이기 때문입니다. 잃어버린 애완동물을 대체하기 위해선 이전 애완동물과 생김새나 행동이 완전히 똑같은 새로운 애완동물을 찾아야 하는데, 이는 *애플리케이션의 경우 새 인스턴스가 이전 인스턴스와 완전히 같은 상태와 아이덴티티를 가져야 함을 의미합니다.*

레플리카셋이나 레플리케이션 컨트롤러로 관리되는 파드는 가축과 같습니다. 이 파드들은 stateless로 언제든지 새로운 파드로 교체될 수 있습니다. 반면 스테이트풀셋으로 관리되는 파드는 stateful해서 새로운 파드로 교체될 때 동일한 이름, 네트워크 아이덴티티, 상태 그대로 다음 노드에서 되살아납니다.

Stateful 애플리케이션은 쿠버네티스에서 삭제/생성 시 역할에 따라 다르게 애플리케이션을 생성해야합니다. 위의 그림에서 Arbiter 역할을 하는 애플리케이션이 다운될 경우 Arbier 애플리케이션을 생성해야합니다.

5. StatefulSet의 주의사항

스테이트풀셋을 사용할 때 주의사항이 있습니다.

  • 파드에 사용할 스토리지는 PVC를 통해서만 가능합니다.
  • 미리 PV를 생성해놓거나
  • StorageClass를 사용해 동적 프로비저닝 사용
  • 스테이트풀셋을 삭제하거나 파드를 삭제하더라도 볼륨은 삭제되지 않습니다
  • 데이터의 안전을 보장하기 위함
  • 헤드리스 서비스가 필요합니다.
  • 파드의 고유한 네트워크 신원을 제공하기 위함
  • 예를 들어 일반적인 서비스라면, 서비스는 기본적으로 레이블 셀렉터가 일치하는 랜덤한 포드를 선택해 트래픽을 전달하기 때문에 스테이트풀셋의 랜덤한 포드들에게 요청을 분산될 것입니다.
  • 하지만, 이것은 스테이트풀셋이 원하는 동작이 아닙니다. 스테이트풀셋의 각 포드는 고유하게 식별되야하며, 포드에 접근할 때에도 '랜덤한 포드'가 아닌 '개별 포드'에 접근해야 합니다.
  • 이런 경우 헤드리스 서비스는 서비스의 이름으로 포드의 접근 위치를 알아내기 위해 사용되며, 서비스의 이름과 포드의 이름을 통해서 포드에 직접 접근할 수 있습니다.

Pod 생성과정(controllerManager, scheduler, kubelet)

Deployment를 생성하는 과정은 Kubernetes에서 ReplicaSet을 생성하고, 이를 통해 실제 파드를 관리하는 일련의 흐름을 포함합니다. 아래는 Deployment가 생성될 때 ReplicaSet Controller가 어떻게 작동하는지를 포함한 자세한 설명입니다.

1. Deployment 생성 요청: kubectl과 API 서버의 역할

  • 사용자가 kubectl apply -f deployment.yaml 명령을 실행하면, 이 명령은 API 서버에 전달됩니다.
  • API 서버는 Deployment 리소스를 저장하고, 그 내부에 원하는 파드 수(예: replicas), 템플릿(파드의 스펙), 업데이트 전략 등을 포함한 정보를 기록합니다. 이 상태는 클러스터의 중앙 데이터 저장소인 etcd에 저장됩니다.

2. ReplicaSet Controller의 생성 및 관리

  • Controller Manager는 API 서버에 새롭게 생성된 Deployment를 감지합니다. 이때 Deployment의 메타데이터와 스펙을 확인합니다.
  • Deployment가 생성되면, ReplicaSet Controller는 이를 기반으로 ReplicaSet을 생성할 필요가 있는지 확인합니다. ReplicaSet은 Deployment의 파드 복제본 수를 관리하는 역할을 합니다.
  • ReplicaSet Controller는 API 서버에 ReplicaSet 리소스를 생성하는 요청을 보냅니다. 이 요청에는 Deployment의 스펙을 기반으로 한 파드 템플릿(사양)과 함께 원하는 복제본 수가 포함됩니다.

3. ReplicaSet의 생성

  • API 서버는 ReplicaSet 리소스를 생성하고 이를 클러스터의 상태로 저장합니다. ReplicaSet은 Deployment에 의해 관리되며, 특정한 레이블을 가진 파드를 생성하기 위한 템플릿을 포함합니다.
  • 이 시점에서 ReplicaSet은 "n개의 파드를 만들어야 한다"는 목표를 가지고, 이를 통해 Deployment의 복제본 수를 유지할 책임을 맡습니다.

4. Scheduler의 역할: 파드 바인딩

  • ReplicaSet이 생성되면, ReplicaSet Controller는 필요한 수의 파드를 생성할 수 있도록 파드를 생성하기 위한 요청을 API 서버에 보냅니다.
  • 이때 Scheduler는 API 서버에서 생성된 ReplicaSet을 감지하고, ReplicaSet에 지정된 파드 템플릿을 바탕으로 아직 바인딩되지 않은 파드를 감지합니다.
  • Scheduler는 클러스터의 노드 상태를 평가하여 적절한 노드를 선택하고, 해당 파드를 선택한 노드에 바인딩합니다. 이 바인딩 정보는 API 서버에 업데이트됩니다.

5. Kubelet의 역할: 파드 실행

  • Scheduler가 바인딩한 정보를 기반으로 해당 노드의 kubelet이 API 서버에 요청하여 자신에게 할당된 파드 스펙을 가져옵니다.
  • kubelet은 이 스펙을 사용하여 파드를 생성하고, 내부 컨테이너를 실행합니다.
  • kubelet은 파드의 상태를 지속적으로 모니터링하며, 문제가 발생하면 이를 API 서버에 보고합니다.

6. 상태 유지 및 자동 복구

  • 만약 파드가 종료되거나 장애가 발생하면, ReplicaSet Controller는 이를 감지하고, 필요한 경우 API 서버에 새로운 파드를 생성하도록 요청합니다.
  • 이 과정은 Scheduler와 kubelet을 통해 반복되어, 항상 설정된 복제본 수를 유지할 수 있도록 합니다.

요약 흐름도

  1. kubectl apply -f deployment.yaml → API 서버에 Deployment 생성 요청.
  2. API 서버가 Deployment 리소스를 저장하고 Controller Manager가 이를 감지.
  3. ReplicaSet Controller가 ReplicaSet 생성 요청을 API 서버에 전송.
  4. API 서버가 ReplicaSet 리소스를 생성.
  5. ReplicaSet이 필요한 수의 파드를 생성하기 위해 Scheduler에 요청.
  6. Scheduler가 바인딩되지 않은 파드를 감지하고 적절한 노드에 바인딩.
  7. 해당 노드의 kubelet이 API 서버에서 파드 스펙을 가져와 파드를 생성하고 관리.
  8. ReplicaSet Controller가 상태를 지속적으로 모니터링하여 복제본 수 유지.

이렇게 Kubernetes는 Deployment를 통해 복제본 수를 자동으로 관리하고, 파드의 상태를 유지하여 고가용성과 안정성을 보장합니다.

Controller 종류

Controller Manager는 여러 컨트롤러를 포함하며, 각 컨트롤러는 Kubernetes 클러스터의 특정 리소스나 기능을 관리한다. 주요 컨트롤러는 다음과 같다.

1. Replication Controller

  • 파드의 복제본 수를 관리하여, 설정된 수의 파드가 항상 실행되도록 보장합니다. ReplicaSet은 Replication Controller의 발전된 형태로, 레이블 셀렉터를 더 정교하게 지원합니다.

2. Node Controller

  • 클러스터 내 노드의 상태를 감시하고, 노드가 실패했을 때 적절한 조치를 취합니다. 예를 들어, 노드가 정상적으로 작동하지 않으면, 그에 따른 파드의 상태를 업데이트하거나 재배치하는 작업을 수행합니다.

3. Job Controller

  • 일회성 작업(Job)을 관리합니다. 주어진 작업을 성공적으로 완료해야 하며, 실패할 경우 재시도하는 등의 로직을 담당합니다.

4. DaemonSet Controller

  • 각 노드에 특정 파드를 배포하여 모든 노드에서 실행되도록 보장합니다. 예를 들어, 로그 수집기나 모니터링 도구를 모든 노드에 배포할 때 사용됩니다.

5. Service Controller

  • 클라우드 공급자의 서비스와의 통신을 관리하며, Kubernetes의 서비스 리소스와 클라우드 제공자의 로드 밸런서를 연동합니다.

6. EndPoint Controller

  • 서비스와 파드 간의 연결을 관리하여, 서비스가 파드의 IP 주소 및 포트를 올바르게 인식하도록 합니다.

7. Namespace Controller

  • 네임스페이스 리소스를 관리하며, 네임스페이스가 생성되거나 삭제될 때 필요한 작업을 수행합니다.

이 외에도 Kubernetes는 다양한 상황과 요구 사항에 따라 여러 컨트롤러를 추가할 수 있습니다. 각 컨트롤러는 API 서버에서 발생하는 변경 사항을 감지하고, 이를 기반으로 클러스터 상태를 원하는 상태로 조정하는 역할을 합니다.

즉, Controller Manager는 이러한 여러 컨트롤러를 통해 Kubernetes 클러스터의 다양한 리소스를 지속적으로 관리하고, 상태를 유지하는 핵심 컴포넌트입니다.

여전히 자동으로 관리됩니다.

따라서 deployment는 외부에 있는 모든 pod를 지속적으로 감시하며,

제어해야 하는 pod가 있는지 살핍니다.

그리고 selector로 제어할 pod를 선택합니다.

쿠버네티스에서 거의 모든 리소스와 작동하는 selector를 보게 될 겁니다.

예를 들어 Azure 서비스 처럼요.

deployment를 위한 다양한 유형의 selector가 있는데,

두 가지 다른 유형의 선택을 사용할 수 있습니다.

matchLabels로 레이블을 일치시킬 수 있고,

matchExpressions로 표현을 일치시킬 수 있습니다.

cgroup

cgroup(Control Group)은 리눅스 커널의 기능으로, 프로세스 그룹의 시스템 자원 사용을 제어하고 모니터링하는 메커니즘입니다. 주요 특징은 다음과 같습니다:

  1. 자원 관리: CPU, 메모리, 디스크 I/O, 네트워크 등의 컴퓨팅 자원 사용을 제한하고 할당할 수 있습니다[1][3].
  2. 프로세스 그룹화: 여러 프로세스를 하나의 그룹으로 묶어 관리할 수 있습니다[1].
  3. 계층 구조: cgroup은 계층적 구조를 가지며, 상위 그룹의 제한은 하위 그룹에도 적용됩니다[5].
  4. 서브시스템: CPU, 메모리, 블록 I/O 등 다양한 리소스를 제어하는 서브시스템으로 구성됩니다[1][2].
  5. 컨테이너 기술 지원: 주로 컨테이너의 리소스 제어를 위해 사용됩니다[3].
  6. 버전: 현재 cgroup v1과 v2 두 가지 버전이 존재하며, v2는 v1의 문제점을 개선한 버전입니다[1][5].
  7. 파일시스템 인터페이스: cgroup은 cgroupfs라는 가상 파일시스템을 통해 관리됩니다[5].

cgroup은 시스템 관리자가 프로세스 그룹의 리소스 사용을 효과적으로 제어하고 모니터링할 수 있게 해주는 강력한 도구입니다.

원문 보존 단위

하나의 파드에는 하나의 GPU, 컨테이너가 여러개가 있을때에도 마찬가지

gpu 설정은 컨테이너 한개만 하고 4개가 있더라도 알아서 공유해서 쓴다는거네 ?

정확히 이해하셨습니다. ✅

🔑 핵심 정리:

  • GPU 리소스는 Pod 단위로 할당됩니다.
  • Pod에 컨테이너가 1개든 2개든 4개든 상관없이, 그 Pod에 할당된 GPU(MIG 포함)는 모든 컨테이너가 공유해서 사용할 수 있습니다.
  • 단, GPU를 "요청(limits)"하는 컨테이너는 반드시 1개만 있어야 합니다.

나머지 컨테이너는 GPU를 사용하더라도 요청은 하지 않습니다.

📌 예를 들어:

spec:
  containers:
    - name: main
      image: my-deep-learning-app
      resources:
        limits:
          nvidia.com/mig-1g.5gb: "1"  # ✅ GPU 리소스 요청

    - name: sidecar-1
      image: my-logger  # ✅ GPU 접근 가능 (요청은 안 함)

    - name: sidecar-2
      image: my-monitor  # ✅ GPU 접근 가능 (요청은 안 함)

    - name: sidecar-3
      image: my-gpu-tool  # ✅ GPU 접근 가능 (요청은 안 함)

이 구조는 다음과 같다고 보면 됩니다:

[POD]
 ├─ Container: main (GPU 요청 O, 사용 O)
 ├─ Container: sidecar-1 (GPU 요청 X, 사용 O)
 ├─ Container: sidecar-2 (GPU 요청 X, 사용 O)
 └─ Container: sidecar-3 (GPU 요청 X, 사용 O)
        ↓
   GPU 디바이스 1개를 공유해서 사용

추가로, 각 컨테이너가 GPU 디바이스에 접근하려면 해당 노드에 nvidia-container-runtime이 설정돼 있어야 하며, 컨테이너 이미지에 CUDA 또는 NVIDIA 도구(nvidia-smi 등)가 포함되어 있어야 합니다.

각 컨테이너에 필요한 CUDA 버전과 도구가 다르면 이미지 구성도 함께 조정해야 한다.

KServe

1. 모델 학습과 모델 서빙

1-1. 모델 학습이란?

모델 학습은 쉽게 말해:

  • 데이터를 모으고
  • 알고리즘을 적용해서
  • 파라미터를 계산하고
  • 결과물을 “모델 파일”로 만드는 과정
  • sklearn 모델 (.pkl)
  • PyTorch 모델 (.pt)
  • LLM 가중치

→ 학습의 결과는 “파일”이다.

1-2. 그런데 파일만 있으면 서비스가 되나?

→ 아니다.

모델 파일은 그냥 파일일 뿐이다.

실제 서비스가 되려면:

  • 외부 요청을 받아야 하고
  • 요청을 모델 입력으로 변환해야 하고
  • 추론을 실행해야 하고
  • 결과를 응답으로 반환해야 한다.

→ 이 모든 걸 담당하는 것이 “서빙 서버”다.

2. 모델 서빙이 어려운 이유

“FastAPI로 API 하나 만들면 되는 거 아니야?”

맞는 말이지만, 운영에서는 그렇지 않다.

2-1. 진짜 운영에서 필요한 것들

→ FastAPI 하나로는 부족하다.

실제 운영에서 필요한 항목:

  • 트래픽이 늘면 자동 확장돼야 함
  • 요청이 없으면 자원을 줄여야 함
  • 서버가 죽으면 자동 복구돼야 함
  • GPU/CPU 자원 관리가 필요함
  • 버전 관리가 필요함
  • 배포 방식이 표준화돼야 함

→ 이걸 매번 직접 만들면 운영 난이도가 폭발한다.

3. 그래서 등장한 개념: “모델 서빙 플랫폼”

“모델 서빙을 공통된 방식으로 운영할 수 없을까?”

이 질문에 대한 답 중 하나가 바로

→ KServe

4. KServe의 정확한 정의 (아주 중요)

KServe 한 줄 정의

→ KServe는 모델을 서빙하기 위한 “운영 플랫폼”이다.

KServe는

서빙 서버를 직접 구현하는 도구가 아니라, 이미 존재하는 서빙 서버를 Kubernetes 위에 YAML 하나로 쉽게 배포·확장·관리하게 해주는 도구다.

5. KServe가 “해주는 것”과 “안 해주는 것”

5-1. KServe가 해주는 것

KServe는 운영을 담당한다.

  • Kubernetes 리소스 생성
  • Deployment
  • Service
  • Route
  • 오토스케일
  • scale-out
  • scale-to-zero
  • 장애 복구
  • 트래픽 라우팅
  • 배포 표준화

→ 운영 관점의 모든 것

5-2. KServe가 안 해주는 것

KServe는 추론 로직을 만들지 않는다.

  • 모델 학습
  • 추론 알고리즘
  • LLM API 구현

→ KServe는 “머리”가 아니라 “포장과 운영”이다.

6. 그럼 서빙 서버는 누가 만드나?

6-1. 서빙 서버란 무엇인가?

서빙 서버는:

  • HTTP 요청을 받고
  • 모델 추론을 실행하고
  • 응답을 돌려주는 실행체

6-2. LLM 시대의 표준 서빙 서버: vLLM

요즘 LLM 서빙에서 가장 많이 쓰이는 것이 vLLM이다.

vLLM의 특징:

  • GPU 기반 LLM 추론 엔진
  • 성능 최적화에 집중
  • 이미 API 서버를 포함
  • OpenAI 호환 API 제공

vLLM을 실행하면

“모델 + 추론 엔진 + API 서버”가 한 번에 뜬다.

7. 여기서 많은 사람들이 헷갈리는 포인트

“KServe가 LLM API 서버를 만들어주는 거 아니야?”

→ 아니다. 대부분의 경우 KServe는 이미 만들어진 서빙 서버를 띄운다.

  • vLLM이 API 서버를 만든다
  • KServe는 그 서버를 운영 환경에 올려준다

8. KServe + vLLM 조합의 역할 분담

역할 담당
모델 추론 vLLM
API 서버 vLLM
GPU 사용 vLLM
Kubernetes 배포 KServe
오토스케일 KServe
장애 복구 KServe

→ 이 조합이 실무에서 가장 흔하다.

9. FastAPI로 직접 만들었을때 문제점

FastAPI로

  • API 만들고
  • 모델 로딩하고
  • 추론하고
  • 응답해도 된다.

하지만 실무에서는 문제가 된다

FastAPI만 쓰면:

  • Deployment 직접 작성
  • Service 직접 작성
  • Autoscaling 직접 설정
  • GPU 스케줄링 직접 고려
  • 장애 대응 직접 구현

→ 운영 복잡도가 급격히 증가한다.

KServe의 핵심 가치

KServe의 진짜 가치는

“서빙 서버의 성능”이 아니라

“운영 복잡도를 YAML 하나로 줄이는 것”이다.

→ KServe는 서빙계의 Helm이다.

10. InferenceService란 무엇인가?

KServe에서 사용하는 핵심 리소스가 바로

→ InferenceService (ISVC)

Deployment도 아니고Service도 아니고Route도 아닌

→ 서빙 서버 하나를 표현하는 상위 개념 CRD다.

11. YAML 하나로 서빙 서버를 띄운다는 의미

KServe + vLLM 최소 예제

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: mistral-vllm
  namespace: ml
spec:
  predictor:
    containers:
      - name: vllm
        image: vllm/vllm-openai:latest
        args:
          - serve
          - mistralai/Mistral-7B-Instruct-v0.2
        resources:
          limits:
            nvidia.com/gpu: 1

이 YAML 하나로:

  • vLLM 실행
  • 모델 다운로드
  • API 서버 기동
  • Service 생성
  • Route 생성
  • 필요 시 오토스케일

→ 운영 관점에서 엄청난 단순화다.

12. KServe가 “서빙 서버를 만들어주는” 경우도 있다

완전히 안 만드는 건 아니다.

12.1 sklearn, xgboost 같은 단순 모델

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: iris
spec:
  predictor:
    sklearn:
      storageUri: s3://models/iris/

이 경우:

  • KServe가 내부 런타임 사용
  • API 서버 자동 생성

→ 하지만 실무의 대부분은 LLM + vLLM 케이스다.

13. KServe는 GPU 전용인가?

→ 아니다.

  • CPU 모델도 가능
  • GPU 모델도 가능

14. KServe 최종 정리

KServe의 목적은 모델 서빙을 운영 가능한 형태로 만드는 것

15. 최종 요약

KServe는 모델 서빙을 위한 Kubernetes 운영 플랫폼이다.

대부분의 경우 KServe는 서빙 서버를 직접 만들지 않고,

vLLM 같은 이미 완성된 서빙 서버를

YAML 하나로 쉽게 배포·확장·관리하게 해준다.

이를 통해 모델 서빙의 운영 복잡도를 크게 줄일 수 있다.

vLLM

1. LLM이란 무엇인가 (아주 기초)

1-1. LLM이란?

LLM(Large Language Model)은

사람의 언어를 이해하고, 그 다음에 올 말을 예측해서

토큰(token) 단위로 문장을 만들어내는 모델이다.

예를 들어,
사용자: “오늘 날씨가”
이 입력이 들어오면 LLM은 “가”, “좋”, “겠”, “습”, “니”, “다”
같은 다음 토큰들을 하나씩 예측해서 문장을 완성한다.

중요한 점은:

  • LLM은 한 번에 문장을 만드는 게 아니라
  • 토큰을 하나씩 순서대로 생성한다는 것이다.

2. LLM이 응답을 만들 때 내부에서 일어나는 일

2-1. 토큰을 하나 만들 때마다 필요한 정보

LLM은 다음 토큰을 예측할 때:

  • 지금까지 등장한 모든 토큰들을 참고한다
  • “이전 문맥(context)”을 기반으로 다음 토큰을 계산한다

이때 사용하는 구조가 Transformer이고,

Transformer에서 핵심이 되는 메커니즘이 Attention이다.

2-2. KV Cache란 무엇인가

Attention 계산을 할 때 매번

이전 토큰 전체를 다시 계산하면 너무 느리다.

그래서 LLM은 다음과 같은 최적화를 한다.

  • 이전 토큰들의 계산 결과 중
  • Key / Value 값을
  • GPU 메모리에 저장해 둔다

이 저장 공간을 KV Cache라고 부른다.

정리하면:

KV Cache =지금까지 생성된 토큰들의 “문맥 상태”를 담고 있는 GPU 메모리

3. 왜 KV Cache가 문제가 되는가

3-1. 요청 하나 = KV Cache 하나

LLM 서버에 요청이 들어오면:

  • 요청 A는 요청 A만의 대화 문맥을 가진다
  • 요청 B는 요청 B만의 대화 문맥을 가진다

그래서:

  • 요청 A → KV Cache A
  • 요청 B → KV Cache B

👉 요청 수만큼 KV Cache가 필요하다

3-2. KV Cache는 계속 커진다

토큰이 하나 생성될 때마다:

  • KV Cache에 새로운 정보가 추가된다
  • 즉, 응답이 길어질수록 KV Cache도 커진다

그래서 GPU 메모리 사용량은 대략 이렇게 된다.

GPU 메모리 사용량 ≈
모델 파라미터 +
(동시 요청 수 × 요청당 KV Cache 크기)

이 방식은 간단하고 이해하기 쉽다.

하지만 실무에서는 치명적인 문제가 있다.

4-2. GPU 메모리는 CPU와 다르다

CPU 메모리는:

  • 가상 메모리
  • 스왑
  • 느려지더라도 버팀

GPU 메모리는:

  • 스왑 없음
  • 가상 메모리 없음
  • 연속된 물리 메모리 공간이 필요
  • 못 잡으면 즉시 OOM (Out Of Memory)

4-3. 연속 메모리 할당 문제

FastAPI + PyTorch 기본 추론에서는:

  • 요청 하나가 들어오면
  • KV Cache를 큰 연속된 GPU 메모리 덩어리로 할당한다

문제는 이거다.

  • 요청이 늘어나면
  • GPU 메모리 여기저기에 작은 빈 공간이 생긴다
  • 하지만 연속된 큰 공간이 없으면
  • 새 KV Cache를 할당할 수 없다

즉,

전체 메모리는 남아 있는데연속 공간이 부족해서 OOM이 나는 상황

이걸 메모리 파편화(fragmentation)라고 부른다.

5-1. 문제의 본질

LLM 서빙 문제의 본질은:

  • GPU 메모리 관리 + 스케줄링 ⭕

그래서 vLLM은 이렇게 생각했다.

“KV Cache를 꼭 연속된 공간에 둬야 하나?”

“잘게 쪼개서 써도 되지 않나?”

  • 메모리 공간만 재사용된다

7. vLLM의 두 번째 핵심: 토큰 단위 스케줄링

7-1. 기존 방식: 요청 단위 처리

기존 서버는 이렇게 처리한다.

요청 B 처리

문제:

  • 나머지는 대기
  • UX 나쁨

  • 요청 A의 다음 토큰 1개

7-3. 스텝(step)의 개념

vLLM에서 한 스텝이란:

여러 요청의 “다음 토큰”을 모아

한 번의 GPU 연산으로 처리하는 단위

예시:

Step 1: A1, B2, C4
Step 2: A2, B3, C5
Step 3: A3, B4, C6
  • 토큰 번호는 요청마다 다르다
  • 하지만 스텝은 동기화되어 있다

8. 동적 batching과 트레이드오프

8-1. 동적 batching이란

vLLM은:

  • 요청을 모아서 기다리지 않는다
  • 매 스텝마다 지금 처리 가능한 토큰들을 자동으로 묶는다

이걸 동적 batching이라고 한다.

8-2. throughput vs latency

  • 토큰을 많이 묶을수록
  • GPU 활용률 ↑
  • throughput ↑
  • 하지만
  • 한 스텝 계산 시간은 조금 늘어남
  • 단일 요청 완료 시간은 약간 느려질 수 있음

👉 명확한 트레이드오프

8-3. 왜 이 구조가 실무에서 맞는 선택인가

만약 한 요청이 GPU를 독점하면:

  • 뒤에 온 사용자는 아무 반응도 못 보고 기다림
  • 서비스가 멈춘 것처럼 느껴짐

vLLM 구조에서는:

  • 모든 사용자가 빠르게 첫 토큰을 받는다
  • 스트리밍으로 응답이 계속 나온다
  • UX가 훨씬 좋다

그래서 대부분의 챗봇은:

  • 토큰 단위 처리
  • 스트리밍 응답

을 사용한다.

9-1. 이 옵션의 의미

  • 요청 개수 ❌
  • 토큰 개수 ⭕

9-2. 왜 중요한가

이 값 하나로:

  • GPU 메모리 사용량
  • throughput
  • latency
  • 안정성(OOM 여부)

이 전부가 결정된다.

그래서 실무에서 가장 중요한 옵션이다.

10. vLLM은 무엇인가 (최종 정의)

이제 모든 걸 합치면, vLLM은 이렇게 정의할 수 있다.

vLLM은KV Cache를 페이지 단위로 관리하고,요청을 토큰 단위로 스케줄링하여,GPU 메모리를 효율적으로 사용하면서다수의 LLM 요청을 안정적으로 처리하는LLM 전용 추론 서버다.

그리고 그 결과로:

  • OpenAI 호환 API 제공
  • FastAPI 없이 바로 사용 가능
  • 실무 운영이 가능해진다

vLLM - 이해를 위한 트랜스포머 모델 이해

트랜스포머(Transformer) 모델 완전 정리

― “LLM은 어떻게 다음 단어를 만들어내는가”

0. 왜 이걸 알아야 하나?

요즘 LLM(ChatGPT 같은 것들)은

  • 말을 너무 자연스럽게 하고
  • 질문을 잘 이해하는 것처럼 보이고
  • 긴 문맥도 기억하는 것처럼 느껴진다

그래서 많은 사람들이 이렇게 생각한다.

“뭔가 의미를 이해해서 답하는 것 같다”

하지만 실제로 내부에서는 의미를 ‘이해’하지 않는다.

LLM은 단 하나의 일을 반복한다.

“지금까지 나온 내용을 바탕으로다음에 나올 토큰 하나를 고른다”

이 글의 목표는 단 하나다.

이 말이 왜 진짜인지,그리고 그게 어떻게 가능한지처음부터 끝까지 설명하는 것

1. LLM은 문장을 만들지 않는다. “토큰”을 만든다

1-1. 토큰이란?

우리가 보는 문장:

나는 사과를 먹었다.

LLM 내부에서는 이렇게 쪼개진다:

[나는] [사과를] [먹었다] [.]

이 각각을 토큰(token)이라고 부른다.

중요한 점:

  • 토큰은 단어일 수도 있고
  • 단어의 일부일 수도 있고
  • 조사, 기호, 공백일 수도 있다

LLM의 세계에서는:

❌ 문장

⭕ 토큰들의 나열

2. LLM의 유일한 임무

LLM은 항상 이 문제만 푼다.

P(다음 토큰 | 지금까지 나온 모든 토큰)

즉,

“지금까지 이 토큰들이 나왔을 때

다음 토큰으로 가장 그럴듯한 건 뭐지?”

이걸 한 번만 하는 게 아니라:

  • 다음 토큰 생성
  • 그 토큰을 다시 입력에 붙임
  • 또 다음 토큰 생성
  • …
  • 종료 토큰(EOS)이 나오면 멈춤

그래서 결과적으로 문장처럼 보일 뿐,

실제로는 토큰을 하나씩 이어 붙인 결과다.

3. 토큰은 숫자 벡터로 바뀐다 (임베딩)

LLM은 글자를 그대로 계산하지 않는다.

각 토큰은 내부적으로 이런 형태다:

[0.13, -0.72, 1.04, ..., 0.55]

이걸 임베딩 벡터라고 한다.

의미:

  • 숫자 덩어리
  • 의미, 성질, 용도 같은 것이 좌표로 표현됨

4. 순서는 어디에 들어가나? (Position Embedding)

중요한 질문:

“트랜스포머는 순서를 모른다던데

그럼 ‘마지막 토큰’은 어떻게 아는 거지?”

답은 이거다.

토큰 벡터는 실제로 이렇게 만들어진다.

최종 입력 벡터 = 단어 임베딩 + 위치 임베딩

예:

나는   = E(나는)   + P(1)
사과를 = E(사과를) + P(2)
먹었다 = E(먹었다) + P(3)

그래서 Q, K, V를 만들 때부터 이미:

  • “몇 번째 토큰인지”
  • “앞인지, 뒤인지”

정보가 벡터 안에 녹아 있다.

5. Transformer의 핵심: Attention

5-1. 왜 Attention이 필요할까?

다음 문장을 보자.

나는 사과를 먹었다.

“먹었다”라는 말은:

  • 나는 → 누가 먹었는지
  • 사과를 → 무엇을 먹었는지

이 관계를 알아야 의미가 생긴다.

Attention은 이걸 계산한다.

“이 토큰이다른 토큰들을 얼마나 참고해야 하지?”

6. Q, K, V는 뭐냐?

각 토큰 벡터는 세 가지로 변환된다.

  • Query (Q): 지금 내가 찾고 싶은 것
  • Key (K): 내가 가진 정보의 라벨
  • Value (V): 실제 정보 내용

비유하면:

  • Q: 질문
  • K: 목차
  • V: 본문

7. Self-Attention이 실제로 하는 일

문장:

나는 사과를 먹었다

토큰:

[나는] [사과를] [먹었다]

각 토큰은 자기 자신을 Query로 삼아

다른 토큰들의 Key와 비교한다.

예를 들어 “먹었다” 토큰은:

Q_먹었다 · K_나는
Q_먹었다 · K_사과를
Q_먹었다 · K_먹었다

이걸로 이런 가중치를 얻는다:

[0.2, 0.4, 0.4]

의미:

  • 나는 → 20% 참고
  • 사과를 → 40% 참고
  • 먹었다 → 40% 참고

8. Attention Output은 뭐냐?

이 가중치를 Value에 곱해서 더한다.

Attention_output(먹었다)
= 0.2×V_나는 + 0.4×V_사과를 + 0.4×V_먹었다

결과는 하나의 벡터다.

[0.43, 0.22, 0.55]

이 벡터의 의미는:

“문장 전체를 고려했을 때의 ‘먹었다’”

9. 왜 모든 토큰의 Attention Output을 만드나?

중요한 질문이었다.

“어차피 다음 단어는 마지막 토큰으로 예측하는데

왜 나는, 사과의 attention output도 만들지?”

이유는 두 가지다.

  1. 모델 구조상 Self-Attention은입력 토큰 수만큼 출력을 만든다
  2. 학습할 때는 모든 위치가다음 단어 예측 대상이 된다

하지만 추론 시에는:

  • 실제로 다음 토큰 예측에 쓰는 건
  • 마지막 토큰의 output 하나뿐

10. Causal Mask — 왜 마지막 토큰이 중요한가

Attention에는 규칙이 하나 있다.

미래 토큰은 절대 보면 안 된다

그래서:

  • 첫 번째 토큰 → 자기 자신만 봄
  • 두 번째 토큰 → 앞 두 개만 봄
  • 마지막 토큰 → 앞의 모든 토큰을 봄

즉,

마지막 토큰만이지금까지의 모든 문맥을 알고 있다

그래서:

  • 마지막 토큰의 벡터 = 현재 문장의 요약 상태

11. Add & LayerNorm — 관계를 “적용”하는 단계

Attention은 관계 정보를 만든다.

하지만 그걸 바로 쓰지 않는다.

Y = LayerNorm(X + Attention(X))

의미:

  • X: 원래 토큰 의미
  • Attention(X): 관계 정보
  • Add: 관계를 기존 의미에 반영
  • LayerNorm: 값 안정화

중요한 포인트:

  • ❌ LayerNorm이 관계를 넣는 게 아니다
  • ⭕ Add가 관계를 실제로 적용한다

12. FFN (Feed Forward Network)은 뭐냐?

FFN은 각 토큰 벡터를 혼자서 다시 가공한다.

  • 토큰끼리는 섞지 않는다
  • 각 토큰을 “혼자 생각하게” 만든다

비유하면:

  • Attention: 회의
  • FFN: 회의 끝나고 혼자 정리

역할:

  • 중요한 특징은 강조
  • 불필요한 특징은 약화

13. Transformer 블록의 전체 구조

한 블록은 항상 이 순서다.

Self-Attention
→ Add & LayerNorm
→ FFN
→ Add & LayerNorm

이 블록을 수십 번 반복한다.

14. 그럼 다음 토큰은 어떻게 고르나?

마지막 블록까지 지나면 이런 게 있다.

h = 마지막 토큰의 최종 벡터

이 벡터는:

  • 순서 정보 포함
  • 문맥 정보 포함
  • 의미 요약 상태

모델은 이걸로 이렇게 한다.

h · w_단어1
h · w_단어2
h · w_단어3
...

즉,

  • 모든 단어 후보 벡터와 내적
  • 점수 계산
  • 확률로 변환
  • 하나 선택

이게 다음 토큰 예측이다.

15. 문장은 왜 한 번에 안 나오나?

LLM은:

  • 문장을 예측하지 않는다
  • 항상 다음 토큰 하나만 예측한다

그래서:

  • 토큰 → 출력
  • 토큰 → 출력
  • …
  • EOS 토큰 → 종료

문장은 그 결과를 사람이 보는 방식일 뿐이다.

16. EOS 토큰과 토큰 한도

EOS는:

  • 특별한 로직 ❌
  • 그냥 “종료를 의미하는 토큰” ⭕
  • 학습 데이터에서 자주 등장한 패턴

토큰 한도(max_tokens)는:

  • 모델 내부가 아는 게 아니다
  • 외부 시스템이 강제로 멈추는 장치

그래서:

  • 문장이 안 끝났는데 잘릴 수 있다
  • 이건 버그가 아니라 정상 동작

17. 왜 대부분의 답변은 토큰 한도보다 훨씬 짧을까?

이게 신기했던 부분이지.

이유는 단순하다.

  1. 학습 데이터의 대부분이 짧다
  2. 질문–답변 구조가 많다
  3. EOS가 자연스럽게 나오는 분포를 학습했다
  4. RLHF로 “적당히 말하고 끝내기”가 강화되었다

즉,

LLM은 ‘끝내는 알고리즘’을 가진 게 아니라‘사람이 보통 끝내는 타이밍’을 통계적으로 배웠다

18. KV Cache는 왜 필요한가?

토큰을 하나 만들 때마다:

  • 이전 모든 토큰의 K/V가 필요하다

하지만:

  • 매번 다시 계산하면 너무 느리다

그래서:

  • 이전 토큰의 Key/Value를 GPU 메모리에 저장
  • 다음 토큰 생성 시 재사용

이게 KV Cache다.

핵심:

  • 토큰 step 수는 줄일 수 없다
  • 하지만 중복 계산은 제거할 수 있다

19. 최종 한 문장 요약

트랜스포머 기반 LLM은문맥을 요약한 상태 벡터를 계속 갱신하면서그 상태와 가장 잘 어울리는다음 토큰 하나를 반복적으로 선택하는 모델이다.

여기까지 이해했다면,

너는 이제 LLM을 “마법”으로 보는 단계는 완전히 끝났고,

다음 단계는 딱 하나다.

“이 과정을 수백 개 요청이 동시에 들어올 때GPU에서 어떻게 효율적으로 굴리느냐?”

→ 그 답이 바로 vLLM이다.

핵심 개념 보강

명령형 생성과 선언형 YAML의 경계

kubectl run은 기본적으로 Pod 하나를 만들고, kubectl create deployment는 Deployment를 만든다. 같은 image를 써도 controller가 Pod를 재생성하고 replica를 조정하는지는 생성한 resource kind에 따라 달라진다.

kubectl run demo --image=nginx:1.27
kubectl create deployment demo --image=nginx:1.27
kubectl create deployment demo --image=nginx:1.27 \
  --dry-run=client -o yaml

--dry-run=client -o yaml은 server에 만들기 전에 시작 YAML을 확인하는 도구다. 생성된 YAML을 그대로 완성된 운영 manifest로 보지는 않는다. label·selector, resource request/limit, probe, security context, Service, volume과 rollout 조건을 목적에 맞게 보강한다.

YAML(YAML Ain't Markup Language: 사람이 읽기 쉬운 data 직렬화 형식)에서 list는 -로 표현되고 indentation이 부모·자식 구조를 결정한다. Syntax가 유효하더라도 Kubernetes schema와 field 의미가 맞는지는 kubectl apply --dry-run=server, kubectl explain과 실제 상태로 검증한다.

실행 완료 기준
apply 성공 → resource가 저장됨
controller 조정 → Pod 생성·교체
readiness 통과 → traffic을 받을 준비 완료

참고 자료

  • 기존 학습 기록: kubectl 명령형 생성
  • 기존 학습 기록: Kubernetes YAML
  • Kubernetes 공식 문서: kubectl run

편입 후 검증 메모

  • 선언적 조정: controller는 원하는 상태와 현재 상태의 차이를 반복적으로 조정한다. YAML 적용 한 번이 곧 실행 완료라는 뜻은 아니다.
  • 워크로드: DaemonSet·Deployment·StatefulSet은 Pod를 만드는 목적과 identity·placement·storage 요구가 다르다. 이름만으로 선택하지 않는다.
  • Probe: liveness 실패는 컨테이너 재시작을 유발할 수 있다. startup·readiness와 목적을 분리하고 장애 시나리오로 검증한다.
  • GPU: 일반적으로 device plugin과 extended resource 요청이 필요하다. 한 Pod의 여러 컨테이너가 GPU를 자동 공유한다고 가정하지 않는다.
