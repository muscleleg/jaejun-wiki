[B]
[C]
[D]

처럼.

FIFO라면?

그럼:

  • B
  • C
  • D

순으로 실행됨.

근데 현실은 더 복잡함

왜냐면 운영체제 목표는 단순 공정성이 아니야.

목표:

  • 응답 속도
  • CPU 효율
  • 사용자 체감
  • 기아(starvation) 방지

등이 있음.

그래서 실제 OS는 다양한 스케줄링 전략 사용

대표적으로:

  • FIFO
  • Round Robin
  • Priority Scheduling
  • Multilevel Queue
  • CFS(Linux)

등.

가장 중요한 개념

Ready Queue ≠ 무조건 단순 FIFO

야.

예를 들어 우선순위(priority)가 있으면

Ready Queue 내부가 사실상:

우선순위 기준 정렬

될 수 있음.

예:

우선순위 높은 D
우선순위 낮은 B
우선순위 낮은 C

그러면 D 먼저 실행 가능.

Linux는 더 복잡함

현대 Linux는 완전 단순 Queue가 아니라:

CFS(Completely Fair Scheduler)

라는 걸 사용함.

얘는 단순 FIFO가 아니라:

“CPU를 최대한 공평하게 분배”

하려고 함.

즉:

  • 오래 못 돌린 애
  • 인터랙티브 작업
  • 우선순위 높은 애

등을 고려함.

그럼 waiting queue에서 돌아온 애는 불리할까?

오히려 반대인 경우도 많아.

예:

  • 마우스 입력 처리
  • 키보드 입력
  • UI 이벤트

같은 건 빠르게 반응해야 함.

그래서 OS는:

I/O 끝난 작업 우대

하는 경우도 많음.

왜냐면:

사용자 체감 응답성

이 중요하니까.

예시

크롬 클릭했는데:

"앞에 batch 작업 많으니까 10초 기다리셈"

이면 미치겠지.

그래서 현대 OS는 보통:

  • CPU만 오래 쓰는 작업
  • 짧게 자주 깨는 작업

을 다르게 취급함.

아주 중요한 관점

운영체제 스케줄링은:

“큐 자료구조 공부”

가 아니라,

“한정된 CPU를 어떻게 효율적으로 나눌까”

문제야.

그래서 Queue도 단순 자료구조가 아님

실제로는:

  • 우선순위 큐
  • Red-Black Tree
  • Time Slice 관리
  • 가상 실행 시간(vruntime)

같은 복잡한 방식 사용.

네 질문으로 연결하면

질문:

waiting queue에서 돌아온 애는 앞에 있는 애 다 끝날 때까지 기다리냐?

답:

“OS 정책에 따라 다름”

이 정확해.

단순 FIFO면 기다릴 수도 있음.

하지만 현대 OS는 보통:

  • 우선순위
  • 응답성
  • 공정성

등을 고려해서 더 빨리 실행시킬 수도 있음.

그리고 여기서 진짜 중요한 개념 등장.

선점(preemption)

이야.

왜냐면 이제 질문이 생김:

“실행 중인 애를 강제로 끌어내릴 수도 있나?”

정답은:

가능하다.

그리고 현대 OS 핵심 기능 중 하나야.

편입 후 검증 메모

  • Queue의 의미: Ready Queue와 Waiting Queue라는 이름이 FIFO 정책을 보장하지 않는다. 실제 선택 순서는 우선순위, time slice, fairness와 스케줄러 구현에 따라 달라진다.
  • Blocked의 복귀: I/O 완료나 이벤트가 발생하면 대기 중 실행 주체가 곧바로 CPU를 얻는 것이 아니라 보통 Ready 상태로 이동해 다시 스케줄링된다.
  • Context switch: 레지스터와 실행 상태 저장·복원뿐 아니라 캐시·TLB 영향도 비용에 포함될 수 있다. “동시에 보임”과 여러 코어에서 실제 병렬 실행을 구분한다.
  • Deadlock: 상호배제·점유대기·비선점·순환대기의 네 조건은 교착상태의 필요조건이다. 예방·회피·탐지/복구 중 어떤 전략을 쓰는지 시스템 맥락과 함께 판단한다.
