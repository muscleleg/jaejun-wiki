+-------------------+

1. 코드 영역(Code Segment)

여기에는:

  • 실행할 코드

가 들어감.

예:

    return a + b;
}

이런 기계어 코드가 저장됨.

CPU는 여기서 명령을 읽음.

2. 데이터 영역(Data Segment)

전역 변수 같은 것 저장.

예:

프로그램 시작부터 종료까지 살아있음.

예:

함수 호출 정보를 저장.

이게 핵심 중 핵심이야.

함수 호출은 어떻게 동작할까?

예:

    int result = add(10, 20);

static int add(int a, int b) {
    int sum = a + b;

1. main 실행

3. add 함수 작업
4. add 종료
5. main으로 복귀

근데 CPU는 어디서 명령을 가져올까?

바로:

메모리(RAM)

에서 가져와.

프로그램 실행의 진짜 의미

우리가:

크롬 실행
게임 실행
자바 실행

이라고 말하잖아?

사실은:

“프로그램 코드가 메모리에 올라간 상태”

를 의미해.

예를 들어:

int c = a + b;

이 코드도 실제로는 메모리에 들어감.

그리고 CPU가 그걸 읽어 실행하는 거야.

CPU는 사람 언어를 못 읽는다

CPU는:

  • Java 모름
  • Python 모름
  • JavaScript 모름

오직:

기계어(machine code)

만 이해 가능해.

예를 들어 CPU 입장에서는:

10110000

같은 형태의 명령만 이해 가능해.

그래서 컴파일이 필요함

우리가 작성한:

int a = 10;

같은 코드는 사람이 읽기 쉬운 언어야.

CPU는 못 읽어.

그래서:

Java 코드
→ 바이트코드
→ JVM
→ 기계어

이런 변환 과정이 필요해.

C언어는:

C 코드
→ 기계어

로 바로 컴파일됨

  • 안 흐른다

그래서:

  • 0
  • 1

GC는 대체 어떻게 객체를 찾을까?

먼저 문제 상황

Python이나 Java는:

user = User()

처럼 객체를 생성해도,

우리가 직접:

free(user)

같은 걸 하지 않아.

그러면 문제가 생겨.

예를 들어:

while True:
    user = User()

이런 코드가 있으면 객체가 계속 생성됨.

근데 사용 안 하는 객체를 계속 메모리에 남겨두면:

메모리 부족(OOM)

이 발생함.

그래서 등장한 게:

GC(Garbage Collection)

이야.

GC 목표는:

“사용하지 않는 객체를 자동으로 제거”

하는 것.

그런데 어려운 문제

GC는 어떻게:

"이 객체 이제 안 쓰네?"

를 알 수 있을까?

핵심 아이디어

GC는 사실:

“살아있는 객체”를 찾는다

그리고 나머지를 제거함.

예시

class User:
    pass

user = User()

메모리 느낌으로 보면:

Stack(Frame):
user ----+

Heap:     |
          v
       User 객체

여기서 중요한 건:

user 변수가 객체를 가리키고 있음

즉 객체에:

참조(reference)

가 존재함.

그런데

user = None

하면?

구조:

Stack(Frame):
user = None

Heap:
User 객체

이제 아무도 User 객체를 가리키지 않음.

즉:

도달 불가능(Unreachable)

상태.

GC는 이런 객체를 제거함.

그런데 어디서부터 검사할까?

여기서 등장:

GC Root

GC Root는:

“살아있는 객체 탐색 시작점”

이야.

대표적인 GC Root:

  • 함수 지역변수
  • 전역 변수
  • 현재 실행 중인 스레드
  • static 변수(Java)

등.

Python 예시

class Address:
    pass

class User:
    def __init__(self):
        self.address = Address()

user = User()

구조 느낌:

GC Root(user 변수)
      ↓
    User 객체
      ↓
   Address 객체

GC는:

GC Root에서 시작해서
참조를 따라감

즉:

  • User 살아있음
  • Address도 살아있음

판단.

이걸 객체 그래프(Object Graph)

라고 생각하면 쉬움.

GC 실제 흐름

1단계 — Root 찾기

예:

지역변수
전역변수
실행중 스레드

2단계 — 참조 따라가기

user → User → Address

3단계 — 살아있는 객체 표시(Mark)

4단계 — 표시 안 된 객체 제거(Sweep)

이걸:

Mark & Sweep

방식이라고 함.

그림으로 보면

GC Root
   ↓
[A] → [B]

[C]

A, B는 살아있음.

C는 아무도 참조 안 함.

즉 제거 대상.

중요한 포인트

GC는:

객체를 하나씩 검사하는 게 아니라
참조 관계를 탐색

하는 거야.

순환 참조는?

예:

a = {}

b["a"] = a

구조:

A ↔ B

서로 참조 중.

근데 만약:

a = None

하면?

이제 GC Root에서 접근 불가능.

즉:

순환 참조여도 제거 가능

왜 GC가 비쌀까?

GC는 힙 객체를 추적해야 함.

즉:

  • 객체 많을수록
  • 참조 많을수록

비용 증가.

그래서 Java는 GC 중에:

Stop-The-World(STW)

가 발생 가능.

즉:

잠깐 모든 스레드 멈춤

그래서 GC 튜닝 중요

실무에서:

  • 메모리 사용량
  • 객체 생성량
  • GC pause

핵심 요약

GC Root에서 시작해서
참조 가능한 객체를 탐색

하는 것.

그리고:

도달 불가능한 객체 제거

하는 시스템이야.

편입 후 검증 메모

  • 스택과 힙: “스택은 빠르고 힙은 느리다”는 배치·할당 비용을 설명하는 단순화다. 실제 접근 성능은 캐시 지역성, 할당기, 객체 배치와 접근 패턴에도 좌우된다.
  • malloc: 호출 즉시 요청량만큼 물리 RAM이 배정된다고 단정할 수 없다. 프로세스 가상 주소 공간과 allocator가 먼저 관리하고, 실제 페이지는 접근 시 page fault를 거쳐 연결될 수 있다.
  • 인터럽트와 시스템 콜: 하드웨어 인터럽트, 예외, 소프트웨어가 의도적으로 진입하는 시스템 콜은 커널로 제어권이 이동한다는 공통점이 있지만 발생 원인과 처리 경로가 다르다.
  • GC: 객체 추적과 회수 방식은 런타임마다 다르다. Python의 참조 카운팅·세대별 순환 GC와 Java의 tracing collector를 하나의 방식으로 섞지 않는다.
