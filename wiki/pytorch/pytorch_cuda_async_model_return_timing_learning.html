CUDA 비동기 실행에서 Python 호출 반환과 GPU 계산 완료를 비교하기

Python의 모델 호출이 반환되는 시점과 GPU가 등록된 작업을 실제로 모두 완료하는 시점을 따로 측정하고, 두 시간이 무엇을 포함하는지 구분합니다.

비동기 실행 Warm-up 비교 시점 전체 실습 코드 실행 결과 반환 시간이 긴 이유 두 시간의 해석 blocking D2H 연결 결론

PyTorch에서 CUDA를 사용하면 CPU와 GPU는 서로 다른 역할을 수행합니다.

CPU는 Python 코드와 PyTorch 연산을 실행하면서 GPU가 수행할 CUDA Kernel을 준비하고 등록합니다. GPU는 등록된 Kernel을 받아 실제 Tensor 연산을 수행합니다.

이 때문에 다음 두 시점은 반드시 같지 않습니다.

Python의 model(...) 호출이 반환된 시점
GPU가 model(...)의 실제 계산을 완료한 시점

이번 실습에서는 두 시점 사이에 실제 차이가 발생하는지 직접 측정했습니다.

1. CUDA 연산은 비동기적으로 실행될 수 있습니다

GPU 모델을 호출하면 CPU는 모델의 모든 계산을 직접 수행하지 않습니다.

gpu_outputs = gpu_model(
    input_ids=gpu_input_ids,
)

개념적으로 CPU와 GPU는 다음과 같이 역할을 나눕니다.

CPU
→ Python 코드 실행
→ PyTorch 연산 준비
→ Tensor와 출력 객체 준비
→ CUDA Kernel을 GPU 작업 Queue에 등록

GPU
→ 등록된 CUDA Kernel 실행
→ Attention·MLP·LM Head 계산
→ Logit 생성

CPU는 GPU에 작업을 등록한 뒤 GPU의 모든 계산이 끝나기 전에 다음 Python 코드로 이동할 수 있습니다. 이것이 CUDA의 비동기 실행입니다.

그러므로 다음 두 사건은 서로 다릅니다.

gpu_model(...)이 Python에서 반환됨
≠
GPU가 Forward 계산을 물리적으로 완료함

2. 왜 Warm-up을 먼저 실행하는가

GPU 연산 시간을 측정하기 전에 같은 모델을 여러 번 미리 실행했습니다.

warmup_count: int = 10

with torch.inference_mode():
    for _ in range(warmup_count):
        gpu_model(
            input_ids=gpu_input_ids,
            use_cache=False,
        )

GPU에서 모델을 처음 실행할 때는 실제 추론 외에도 일회성 준비 비용이 발생할 수 있습니다.

  • CUDA Context 준비
  • 필요한 CUDA Kernel과 라이브러리 준비
  • GPU 메모리 할당
  • PyTorch 메모리 캐시 준비
  • 연산에 필요한 내부 자료 구조 준비

Warm-up은 이러한 초기화 비용을 없애거나 아끼는 작업이 아닙니다. 측정 전에 미리 지불해 실제 측정 구간에서 제외하는 작업입니다.

Warm-up 없이 측정

측정 시작
→ 일회성 초기화
→ 실제 Forward
→ 측정 종료

이 경우 평소의 Forward 실행 시간에 최초 준비 비용이 섞입니다.

Warm-up을 사용하면 다음과 같은 경계를 만들 수 있습니다.

Warm-up 실행
→ 최초 준비 비용 발생
→ Warm-up GPU 작업 완료 대기
→ 측정 시작
→ 반복 Forward 실행

Warm-up 역시 CUDA에 비동기적으로 등록될 수 있으므로, 측정 직전에 동기화합니다.

torch.cuda.synchronize()
start_time = time.perf_counter()

이렇게 해야 Warm-up에서 남은 GPU 작업이 실제 측정 구간에 섞이지 않습니다.

3. 실습에서 비교하려는 두 시점

이번 실습에서는 tiny GPT-2의 GPU Forward를 200번 실행했습니다.

repeat_count: int = 200

확인하려는 첫 번째 시점은 200번의 gpu_model(...) 호출이 모두 Python으로 반환된 시점입니다.

model_calls_returned_time: float = time.perf_counter()

두 번째 시점은 앞에서 등록한 GPU 작업이 실제로 모두 끝난 시점입니다.

torch.cuda.synchronize()
gpu_work_completed_time: float = time.perf_counter()

torch.cuda.synchronize()는 지금까지 GPU에 등록한 작업이 모두 끝날 때까지 CPU를 기다리게 합니다.

4. 전체 실습 코드

import time
import torch

repeat_count: int = 200
warmup_count: int = 10

gpu_model.eval()

# 최초 실행의 일회성 준비 비용을 측정 전에 지불
with torch.inference_mode():
    for _ in range(warmup_count):
        gpu_model(
            input_ids=gpu_input_ids,
            use_cache=False,
        )

# Warm-up GPU 작업이 측정 구간에 들어오지 않도록 대기
torch.cuda.synchronize()

start_time: float = time.perf_counter()

with torch.inference_mode():
    for _ in range(repeat_count):
        gpu_model(
            input_ids=gpu_input_ids,
            use_cache=False,
        )

# 200번의 Python model() 호출이 모두 반환된 시점
model_calls_returned_time: float = time.perf_counter()

# 등록된 GPU 작업이 실제로 모두 끝날 때까지 대기
torch.cuda.synchronize()

gpu_work_completed_time: float = time.perf_counter()

model_calls_returned_ms: float = (
    model_calls_returned_time - start_time
) * 1000

gpu_work_completed_ms: float = (
    gpu_work_completed_time - start_time
) * 1000

remaining_gpu_wait_ms: float = (
    gpu_work_completed_time - model_calls_returned_time
) * 1000

print(
    "모든 model() 호출이 반환되기까지:",
    f"{model_calls_returned_ms:.3f} ms",
)
print(
    "GPU 계산이 실제로 완료되기까지:",
    f"{gpu_work_completed_ms:.3f} ms",
)
print(
    "호출 반환 후 추가로 기다린 시간:",
    f"{remaining_gpu_wait_ms:.3f} ms",
)

5. 실제 실행 결과

실습에서는 다음 결과가 나왔습니다.

모든 model() 호출이 반환되기까지: 1335.146 ms
GPU 계산이 실제로 완료되기까지: 1335.274 ms
호출 반환 후 추가로 기다린 시간: 0.128 ms

200번의 model() 호출이 모두 반환된 뒤에도 GPU 작업이 완전히 끝난 것은 아니었습니다.

마지막 torch.cuda.synchronize()에서 약 0.128ms를 추가로 기다렸습니다.

따라서 다음 사실을 확인할 수 있습니다.

Python의 model() 호출 반환
≠
GPU의 실제 계산 완료

다만 예상과 달리 두 시간의 차이는 매우 작았습니다.

6. 비동기 실행인데 호출 반환 시간은 왜 길었는가

비동기 실행이라는 말은 gpu_model(...) 호출이 아무 작업도 하지 않고 즉시 반환한다는 뜻이 아닙니다.

gpu_model(...) 한 번을 실행하는 동안 CPU도 여러 작업을 수행합니다.

Python Module 호출
→ PyTorch 연산 준비
→ Tensor Shape와 장치 확인
→ 출력 Tensor 메모리 준비
→ 여러 CUDA Kernel 등록
→ 결과 Tensor 객체 반환

또한 GPT-2의 Forward는 하나의 CUDA Kernel로 구성되지 않습니다. Embedding, Attention, MLP, LM Head 등에 필요한 여러 연산과 Kernel을 차례대로 등록합니다.

이번 실습에서는 이 과정을 200번 반복했습니다.

for _ in range(200):
    gpu_model(...)

CPU와 GPU는 다음과 같이 서로 겹쳐서 실행됩니다.

CPU: Forward 1 등록 → Forward 2 등록 → Forward 3 등록 → … → Forward 200 등록
GPU:      Forward 1 실행 → Forward 2 실행 → Forward 3 실행 → … → 거의 완료

CPU가 다음 Forward에 필요한 작업을 준비하고 등록하는 동안 GPU는 앞서 등록된 Kernel을 계속 실행합니다.

이번 입력은 [Batch=1, Token=3]이고 모델도 tiny GPT-2이므로 GPU가 처리해야 하는 계산량이 매우 작았습니다. CPU가 200번째 호출을 마쳤을 때 GPU도 앞선 작업을 거의 모두 처리한 상태였습니다.

그래서 마지막에 기다린 시간이 0.128ms밖에 남지 않았습니다.

7. 두 시간을 어떻게 해석해야 하는가

다음 값은 순수한 CPU 시간이라고 볼 수 없습니다.

model_calls_returned_ms

이 값에는 다음 작업이 포함됩니다.

  • Python 반복문 실행
  • PyTorch Module 호출
  • Tensor와 출력 객체 준비
  • CUDA Kernel 등록
  • 그동안 CPU와 겹쳐 진행된 GPU 계산

마찬가지로 다음 값도 순수 GPU Kernel 실행 시간은 아닙니다.

gpu_work_completed_ms

이 값은 측정 시작부터 CPU의 작업 등록과 GPU의 실제 계산이 모두 끝날 때까지 걸린 전체 벽시계 시간입니다.

측정 시작
│
├─ CPU: PyTorch 작업 준비·CUDA Kernel 등록 ─┐
│                                           │ 서로 겹쳐 실행
└─ GPU: 등록된 CUDA Kernel 실제 계산 ───────┘
                                            ↓
                                      모든 작업 완료

따라서 이번 결과는 다음처럼 해석해야 합니다.

CPU가 200번의 호출을 모두 반환하기까지    1335.146ms
CPU·GPU 작업이 모두 완료되기까지          1335.274ms
호출 반환 후 남아 있던 GPU 작업              0.128ms

변수 이름도 다음 의미에 가깝습니다.

all_model_calls_returned_ms
all_gpu_work_completed_ms

8. 왜 .to("cpu") 실습에서는 별도 동기화가 필요 없었는가

앞선 CPU·GPU Logit 비교에서는 GPU 결과를 CPU로 이동했습니다.

gpu_logits_on_cpu = gpu_outputs.logits.to("cpu")

CPU 메모리로 Logit을 복사하려면 GPU에서 Logit 계산이 먼저 완료되어야 합니다.

일반적인 blocking D2H 복사에서는 다음 순서가 필요합니다.

GPU Forward 작업 등록
→ GPU에서 Logit 계산
→ 필요한 GPU 작업 완료까지 대기
→ GPU Logit을 CPU 메모리로 복사
→ CPU에서 Logit 사용

따라서 .to("cpu")가 끝난 뒤에는 CPU가 완성된 Logit을 사용할 수 있었습니다.

torch.allclose(
    cpu_logits,
    gpu_logits_on_cpu,
)

이 비교는 결과의 정확성 측면에서 안전했습니다.

그러나 GPU 연산 시간만 측정할 때는 결과를 CPU로 가져오지 않을 수 있습니다. 이때는 암묵적인 대기 지점이 없으므로 torch.cuda.synchronize() 같은 명시적인 측정 경계가 필요합니다.

9. 이번 실습의 결론

이번 실습에서 확인한 핵심은 다음과 같습니다.

CPU
→ Python과 PyTorch 코드 실행
→ GPU 작업 준비
→ CUDA Kernel 등록

GPU
→ 등록된 Kernel을 실제로 실행
→ Tensor 결과 계산

CPU와 GPU의 작업은 서로 겹쳐서 진행될 수 있습니다.

따라서 model() 호출이 Python에서 반환됐다고 해서 GPU 계산까지 모두 끝났다고 단정할 수 없습니다.

이번에는 작은 모델과 짧은 입력을 사용해 CPU가 200번의 Forward를 등록하는 동안 GPU가 작업을 거의 따라잡았습니다. 그 결과 마지막 동기화에서 기다린 시간은 0.128ms에 불과했습니다.

하지만 그 작은 차이를 통해서도 Python 호출 반환과 GPU 계산 완료가 서로 다른 시점이라는 사실을 확인했습니다.

CUDA의 비동기 실행은 CPU 호출이 무조건 즉시 끝난다는 뜻이 아닙니다. CPU는 작업을 준비하고 등록하며, GPU는 등록된 작업을 실제로 계산합니다. 정확한 GPU 측정을 위해서는 두 역할이 겹쳐 실행된다는 점과 동기화 경계를 함께 고려해야 합니다.

이 동기화 경계를 실제 No-cache·KV Cache × Batch 1·4 Benchmark에 적용했을 때, RTX 2000 Ada의 tiny GPT-2에서 두 Batch 모두 출력이 일치했고 KV Cache의 평균 전체 Latency가 약 11% 감소했습니다. 이는 순수 GPU Kernel 시간이 아니라 동기화된 생성 함수 전체의 벽시계 결과이며, 상세 조건과 한계는 PyTorch 추론 Baseline 통합 실습 기록에 남겼습니다.
