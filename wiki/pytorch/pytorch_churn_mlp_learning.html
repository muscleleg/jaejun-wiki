회원 이탈 데이터에서 MLP와 BCE까지

작은 숫자 Tensor에서 시작했던 학습 흐름을 실제 표 데이터로 확장해, Pandas 정리부터 NumPy·Tensor·DataLoader·MLP의 Logit과 첫 BCE Loss까지 연결합니다.

데이터 준비, Batch Shape, MLP Forward와 초기 BCE 값에 이어 SGD로 같은 Batch를 한 번 수정해 Loss가 0.6564000844955444 → 0.6511512994766235로 내려가는 것까지 실행했다. 이는 전체 Train 루프나 한 Batch 과적합 완료가 아니다. Validation Accuracy·Yes Recall, 저장·복원·추론은 아직 실행하지 않았고, BCE 세부 계산과 다차원 Linear의 파라미터·Shape도 다시 설명하는 확인이 남아 있다.

2. 실제 표 데이터를 같은 Train 기준으로 전처리한다

공개 회원 이탈 데이터는 (7043,21)이었다. 식별자 customerID와 정답 Churn을 입력에서 빼고, 정답의 의미를 직접 숫자로 정했다.

Feature와 Label 분리
X = df.drop(columns=["customerID", "Churn"])
y = df["Churn"].map({"No": 0, "Yes": 1})

이 매핑 때문에 이후 숫자 1은 이탈, 0은 비이탈을 뜻한다. 반대로 매핑하면 모델 출력의 해석도 반대로 바뀐다. 분리 결과는 X (7043,19), y (7043,)이고 Label 수는 0: 5174, 1: 1869였다.

TotalCharges 숫자 변환

공백을 NaN으로 바꾼 뒤 0으로 채우기
X["TotalCharges"] = pd.to_numeric(
    X["TotalCharges"],
    errors="coerce",
).fillna(0)

변환 뒤 dtype은 float64, 남은 결측치는 0개였다. 공백 11개가 가입 기간 0인 행이라는 앞선 품질 점검 근거를 사용해 0으로 처리했다.

Stratified Train·Validation Split

test_size=0.2, random_state=42, stratify=y로 나눈 결과는 Train (5634,19), Validation (1409,19)였다. 1 비율은 각각 약 0.26535, 0.26544로 거의 같았다.

train_test_split()은 입력 자료형을 유지하므로 X_train·X_valid는 열 이름과 행 index가 있는 Pandas DataFrame이고, y_train·y_valid는 1차원 Pandas Series다. 여기서 Pandas의 행·열 label은 머신러닝 정답 Label인 y와 다른 의미다. NumPy ndarray는 이후 전처리 결과에서 처음 만들어진다.

열 선택과 전처리 기준

숫자형 4개SeniorCitizen, tenure, MonthlyCharges, TotalCharges에 StandardScaler를 적용했다.
범주형 15개OneHotEncoder(sparse_output=False, handle_unknown="ignore")를 적용했다.

preprocessor.fit_transform(X_train)은 Train에서 범주 자리·평균·표준편차를 배우면서 변환하고, preprocessor.transform(X_valid)은 그 기준을 Validation에 그대로 적용한다. Validation에서 다시 fit하지 않는 이유는 평가 데이터 정보가 섞이는 누수와 Feature 자리 불일치를 막기 위해서다.

결과는 열 이름을 가진 Pandas DataFrame에서 숫자만 가진 NumPy 배열로 바뀌었다.

Train: Pandas (5634,19) → NumPy (5634,45) · Validation: Pandas (1409,19) → NumPy (1409,45)

3. NumPy 배열을 float32 Tensor와 Batch로 옮긴다

입력은 이미 [고객 수,45개 Feature]이므로 Shape을 유지한다. 정답은 Pandas Series를 NumPy로 바꾼 뒤 reshape(-1,1)로 모델 출력과 같은 2차원 Shape을 만든다.

Pandas·NumPy → Tensor
X_train_tensor = torch.tensor(X_train_processed, dtype=torch.float32)
X_valid_tensor = torch.tensor(X_valid_processed, dtype=torch.float32)

y_train_tensor = torch.tensor(
    y_train.to_numpy(),
    dtype=torch.float32,
).reshape(-1, 1)

reshape(-1,1)에서 1은 열을 하나로 고정하고, -1은 전체 원소 수에 맞춰 행 수를 자동 계산하라는 뜻이다. 그래서 (5634,)가 (5634,1)이 된다.

Train 정답[5634,1]float32

TensorDataset과 타입 오류

모델이 계산할 Tensor로 바꾸는 작업은 앞의 torch.tensor()에서 끝났다. TensorDataset은 새 숫자 형식으로 변환하는 객체가 아니라, 이미 만든 입력 Tensor와 정답 Tensor를 같은 인덱스끼리 짝짓는 객체다. 처음에는 Validation 입력 자리에 NumPy 배열 X_valid_processed를 넣어 TypeError: 'int' object is not callable가 발생했다. NumPy의 .size는 정수 속성인데 TensorDataset은 Tensor의 .size(0) 메서드를 호출하기 때문이다. X_valid_tensor로 바꿔 Train 5,634개와 Validation 1,409개의 짝을 만들었다.

DataLoader가 Batch 행을 공급한다

Train과 Validation DataLoader
train_loader = DataLoader(
    train_dataset,
    batch_size=64,
    shuffle=True,
)

valid_loader = DataLoader(
    valid_dataset,
    batch_size=64,

Train은 Epoch마다 순서를 섞고, Validation은 고정한다. iter(train_loader)는 Batch 반복기를 만들고 next(...)는 그중 한 Batch를 꺼낸다. 첫 Batch는 입력 [64,45], 정답 [64,1]이었다. Train은 89개 Batch(64 × 88 + 2), Validation은 23개 Batch다. 64는 바뀔 수 있는 고객 수이고 45는 모델 입력 계약이라 고정된다.

4. MLP는 각 고객의 45개 값을 16개 중간값과 Logit 하나로 바꾼다

ChurnMLP Forward
class ChurnMLP(nn.Module):
    def __init__(self):
        super().__init__()
        self.hidden = nn.Linear(45, 16)
        self.output = nn.Linear(16, 1)

    def forward(self, x):
        hidden = self.hidden(x)
        activated = torch.relu(hidden)
        logits = self.output(activated)
        return logits
[batch,45] → [batch,16] → [batch,1]

45 → 16은 고객 한 명의 Feature 45개를 학습 가능한 조합 16개로 바꾸고, 16 → 1은 그 16개를 고객별 Logit 하나로 합친다는 뜻이다. Batch가 64명이어서 출력이 [64,1]이지만 모델이 64명 전용이라는 뜻은 아니다. [1,45], [32,45], 마지막 [2,45]도 각각 앞 차원을 유지해 처리한다.

ReLU와 마지막 Linear 구분
ReLU는 음수를 0에 가깝게 만드는 것이 아니라 정확히 0으로 만들고, 양수에는 상한 1을 두지 않는다. ReLU(10)=10이다. ReLU는 중간값에만 적용되므로 마지막 Linear(16,1)의 가중치와 bias에 따라 Logit은 -100, -0.2608, 10처럼 어떤 실수도 될 수 있다.

5. 현재 질문 · Linear의 숫자와 파라미터 Shape

이해 진행 중이며 완료 표시하지 않는다.
아래 내용은 현재 코드가 실제로 가진 구조를 정리한 기술 기준이다. 사용자가 파라미터 수와 3차원 입력의 출력 Shape을 다시 예측하거나 자기 말로 설명하는 확인은 아직 남아 있다.

nn.Linear(45,16)의 두 숫자는 입력값 45개와 출력값 16개를 뜻한다. 실제 weight는 [out_features,in_features]=[16,45]인 2차원 행렬이고, 출력값마다 bias 하나가 있어 bias Shape은 [16]이다.

계층WeightBias파라미터 수
Linear(45,16)[16,45] · 45 × 16 = 720[16] · 16개736개
Linear(16,1)[1,16] · 16개[1] · 1개17개
전체ReLU에는 학습 파라미터가 없음753개

Linear의 weight는 2차원이지만 입력 Tensor는 3차원 이상일 수 있다. Linear는 앞 차원을 유지하고 마지막 Feature 축만 바꾼다.

[32,10,45] → Linear(45,16) → [32,10,16]

nn.Linear(45,33,16)은 45 → 33 → 16을 뜻하지 않는다. 세 번째 위치 인자는 새 출력 차원이 아니라 bias 자리다. 현재 PyTorch에서는 정수 16이 참으로 취급되어 Linear(45,33,bias=True)처럼 만들어질 수 있지만, 의도가 불분명하므로 쓰지 않는다. 45 → 33 → 16을 만들려면 Linear(45,33)과 Linear(33,16) 두 계층을 따로 선언해야 한다.

6. Sigmoid는 제한 없는 Logit을 0과 1 사이로 압축한다

첫 고객의 학습 전 Logit은 z=-0.2608이었다. Sigmoid 계산은 다음과 같다.

11 + e−z = 11 + e0.2608 ≈ 11 + 1.298 ≈ 0.4352

현재 단계에서는 이 값을 과하게 해석하지 않고 학습 전 sigmoid 출력값이라고 기록한다. Sigmoid 자체는 각 실수를 독립적으로 0~1 사이로 압축할 뿐이며, MinMaxScaler처럼 데이터 전체의 최솟값·최댓값을 사용하는 정규화는 아니다.

0.5 Threshold는 sigmoid 출력값을 최종 0/1 판정으로 바꿀 때 쓰는 별도 규칙이다. 현재 셀은 아직 Threshold로 판정하지 않았고, BCE가 연속적인 sigmoid 출력값을 채점하는 단계다.

표현상 주의
학습 전 출력에는 단순히 “확률”이라고 쓰지 않고 학습 전 sigmoid 출력값이라고 쓴다. BCE 학습 뒤에도 이는 모델이 추정한 값이며 현실의 빈도와 맞는지는 별도의 Calibration 검증이 필요하다.

7. BCE는 실제 정답 쪽 sigmoid 출력값에 -log를 적용한다

p를 sigmoid 출력값, y를 실제 정답 0 또는 1이라고 두면 고객 한 명의 BCE는 다음 두 경우로 읽을 수 있다.

실제 정답 y=1개별 Loss = -log(p)
실제 정답 y=0개별 Loss = -log(1-p)

두 경우를 한 식으로 합치면 다음과 같다.

L = -[y log(p) + (1-y) log(1-p)]

첫 고객 실제 숫자로 계산

z = -0.2608, p = 0.4352, y = 0
L
= -[0 × log(0.4352) + (1 - 0) × log(1 - 0.4352)]
= -log(0.5648)
≈ 0.571

첫 고객의 실제 정답이 0이므로 p가 아니라 1-p=0.5648을 선택해 벌점을 계산한다. 같은 출력에서 정답이 1이었다면 -log(0.4352) ≈ 0.832가 된다.

정답 방향 벌점의 크기는 별도 예제로도 예측했다. sigmoid 출력값이 0.8일 때 실제 정답이 1이면 -log(0.8), 실제 정답이 0이면 -log(0.2)이므로 두 번째 벌점이 더 크다. e-x가 0.8보다 작은 0.2가 되려면 x가 더 커야 한다는 관계로도 설명했다. 이는 같은 모델 출력이라도 실제 정답 쪽에 남긴 값이 0.8인지 0.2인지에 따라 BCE가 달라진다는 확인이다.

고객별 Loss 64개를 하나로 합치기

nn.BCEWithLogitsLoss()의 기본값은 reduction="mean"이다. 따라서 고객별 Loss 64개를 모두 더한 뒤 64로 나눈다.

Batch Loss = 고객 1 Loss + 고객 2 Loss + ⋯ + 고객 64 Loss64 = 0.6564000844955444

화면에는 logits[:3]으로 앞 3명만 출력했지만, 실제 Loss 계산에는 logits [64,1]과 batch_y [64,1] 전체가 들어갔다. 고객별 값을 보고 싶을 때만 reduction="none"을 사용한다.

MSE·분산·BCE 구분

계산비교 기준현재 의미
분산각 값 − 그 값들의 평균데이터가 평균에서 얼마나 퍼졌는지
MSE Loss예측값 − 실제 정답을 제곱한 평균앞선 선형회귀에서 사용한 Loss
BCE Loss정답 쪽 sigmoid 출력값에 -log현재 0/1 이진분류에서 선택한 Loss

(sigmoid 출력값 - 실제 정답)²을 평균내는 방식도 가능한 다른 Loss이며 MSE라고 부른다. 현재 코드는 이 방식 대신 BCE를 선택했다.

WithLogits의 뜻
개념상 Logit → Sigmoid → BCE지만 BCEWithLogitsLoss는 수치적으로 안전하게 계산하려고 원본 Logit에서 두 단계를 함께 처리한다. 따라서 Loss에는 loss_fn(logits, batch_y)를 넣고, torch.sigmoid(logits)를 다시 넣어 sigmoid를 중복 적용하지 않는다.

8. SGD로 같은 Batch를 한 번 수정했다

저장된 노트북의 한 Step
optimizer = torch.optim.SGD(model.parameters(), lr=0.1)

optimizer.zero_grad()
logits = model(batch_x)
loss_before = loss_fn(logits, batch_y)
loss_before.backward()
optimizer.step()

SGD는 model.parameters()에 등록된 753개 weight·bias 각각에 대해 새 값 = 기존 값 - learning rate × Gradient를 적용한다. 저장된 실행에서는 같은 Batch의 Loss가 0.6564000844955444에서 0.6511512994766235로 내려갔다.

실행 증거와 이해 증거를 구분한다.
사용자는 optimizer.step() 한 번마다 Gradient와 learning rate를 기준으로 weight·bias가 조금 조정되고, 그 결과 Loss가 0.6564000844955444 → 0.6511512994766235로 소폭 감소했다고 자기 말로 설명했다. SGD 한 Step의 원리는 확인했지만, 전체 753개 파라미터 계산과 다차원 Linear의 마지막 축 Shape은 다시 설명하는 확인이 남아 있다. 같은 Batch를 충분히 과적합하거나 전체 Train 루프를 만든 상태도 아니다.

9. 다음에 확인할 완료 조건

  • 고객별 BCE를 reduction="none"으로 출력하고 첫 값과 Batch 평균을 다시 계산한다.
  • Linear(45,16)·Linear(16,1)의 파라미터 수와 3차원 입력의 출력 Shape을 자료 없이 다시 설명한다.
  • 이미 확인한 한 번의 SGD Step을 반복해 같은 Batch를 충분히 과적합한다.
  • 전체 Train 루프와 가중치를 바꾸지 않는 Validation 루프를 분리한다.
  • Validation Accuracy와 Yes Recall을 기존 Logistic Regression 결과와 같은 Split에서 비교한다.
  • 모델과 전처리·Label 매핑을 저장하고 다시 불러와 한 고객을 추론한다.

이 항목을 실행·설명·재실행하기 전에는 Dataset·DataLoader와 학습 루프 챕터를 완료로 표시하지 않는다.
