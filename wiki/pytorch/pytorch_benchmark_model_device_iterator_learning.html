PyTorch · Benchmark Function & Model Device

Benchmark 함수에서 모델 장치를 직접 확인하고 next(model.parameters()) 이해하기

전역 모델·장치에 의존하던 생성 Benchmark를 명시적인 함수 입력으로 바꾸고, 실제 전달된 모델의 Parameter 장치와 입력 Tensor 장치를 Forward 전에 검증합니다.

← CUDA 비동기 Timing 실습모델·Tensor 장치 일치
전역 상태 문제 함수 입력 리팩터링 실제 모델 장치 next() 오해 Iterator 커서 장치 불일치 검사 전체 함수 코드 적용 범위 결론

1. 전역 model과 device에 의존하면 Benchmark 대상을 혼동할 수 있습니다

기존 generate_for_benchmark()와 measure_generation()은 함수 밖의 전역 model과 device를 사용했습니다.

generated_ids = model.generate(...)

if device.type == "cuda":
    torch.cuda.synchronize()

이 구조에서는 CPU 모델과 GPU 모델을 함께 만든 뒤에도 함수가 실제로 어느 모델을 사용하는지 호출부만 보고 알기 어렵습니다. prompt_ids는 GPU에 있는데 전역 model은 CPU 모델을 가리키거나, 실제 모델은 CPU인데 전역 device가 CUDA를 가리키는 식으로 상태가 어긋날 수도 있습니다.

전역 model  → 무엇을 가리키는지 함수 밖 상태에 의존
전역 device → 실제 전달된 모델의 장치와 다를 수 있음

Benchmark에서는 비교할 대상을 명확하게 고정해야 하므로, 모델과 장치를 함수 밖의 암묵적인 상태에 맡기지 않는 편이 안전합니다.

2. 측정할 모델을 함수 인자로 직접 받습니다

리팩터링한 함수는 model: GPT2LMHeadModel을 직접 입력받습니다.

def generate_for_benchmark(
    model: GPT2LMHeadModel,
    prompt_ids: Int64[
        Tensor,
        "batch prompt_token",
    ],
    max_new_tokens: int,
    use_cache: bool,
) -> Int64[
    Tensor,
    "batch generated_token",
]:

이제 호출부에 CPU 모델을 넣으면 CPU 모델을 측정하고, GPU 모델을 넣으면 GPU 모델을 측정합니다.

generate_for_benchmark(
    model=cpu_model,
    prompt_ids=cpu_prompt_ids,
    ...
)

generate_for_benchmark(
    model=gpu_model,
    prompt_ids=gpu_prompt_ids,
    ...
)

함수 입력과 출력의 역할은 다음과 같습니다.

  • model: 이번 호출에서 실제로 생성에 사용할 모델입니다.
  • prompt_ids [Batch,Prompt Token]: 같은 장치에 있어야 하는 입력 Token ID입니다.
  • max_new_tokens: 새로 생성할 Token 수입니다.
  • use_cache: KV Cache 사용 여부입니다.
  • 반환값 [Batch,Generated Token]: Prompt와 새 Token을 포함한 생성 ID입니다.

3. 함수 안에서 실제 전달된 모델의 장치를 구합니다

model_device: torch.device = (
    next(model.parameters()).device
)

model.parameters()는 모델이 가진 Parameter를 차례대로 꺼낼 수 있는 Iterator를 반환합니다. next(...)로 그중 첫 번째 Parameter를 꺼내고, 그 Parameter의 .device를 읽습니다.

cpu_model 전체를 .to("cpu")
→ 첫 Parameter Device: cpu

gpu_model 전체를 .to(cuda_device)
→ 첫 Parameter Device: cuda:0

현재 실습은 모델 전체를 하나의 장치로 옮긴 단일 GPU 구성입니다. 따라서 첫 Parameter의 장치를 현재 모델의 대표 장치로 사용할 수 있습니다.

4. 처음에는 next()가 두 번째 Parameter를 꺼낸다고 생각했습니다

next(model.parameters())를 처음 보았을 때, 이름이 next이므로 현재 Parameter 다음에 있는 두 번째 Parameter를 꺼내는 것처럼 느껴졌습니다.

하지만 model.parameters()를 방금 호출해 만든 Iterator는 아직 어떤 Parameter도 꺼내지 않은 상태입니다. Iterator의 커서는 첫 원소 위가 아니라 첫 원소 앞에 있습니다.

Iterator 생성 직후

커서
 ↓
[첫 Parameter] [두 번째 Parameter] [세 번째 Parameter] ...

따라서 최초의 next()는 커서를 첫 Parameter로 이동시키면서 그 값을 반환합니다.

5. JDBC ResultSet처럼 커서는 첫 원소 앞에서 시작하지만, Python은 값을 함께 반환합니다

이 동작은 과거 JSP·JDBC에서 사용했던 ResultSet의 커서와 연결해서 이해할 수 있습니다. JDBC ResultSet도 처음에는 커서가 첫 행 바깥, 즉 첫 행 앞에 있습니다.

ResultSet 생성 직후

커서
 ↓
[첫 번째 행] [두 번째 행] [세 번째 행] ...

JDBC에서는 resultSet.next()가 커서를 다음 행으로 이동시키고, 이동에 성공했는지를 boolean으로 반환합니다. 실제 열 값은 그 뒤 getString() 같은 메서드로 별도로 읽습니다.

if (resultSet.next()) {
    String name = resultSet.getString("name");
}

Python Iterator의 next(iterator)도 첫 호출에서 커서를 첫 원소로 이동시킨다는 점은 같습니다. 차이는 이동 성공 여부만 반환하는 것이 아니라, 이동한 위치의 값을 동시에 반환한다는 점입니다.

parameter_iterator = model.parameters()

first_parameter = next(parameter_iterator)
# 첫 Parameter로 이동하면서 첫 Parameter 자체를 반환

두 번째 Parameter를 얻으려면 같은 Iterator에 next()를 두 번 호출해야 합니다.

parameter_iterator = model.parameters()

first_parameter = next(parameter_iterator)
second_parameter = next(parameter_iterator)

반면 다음 코드는 호출할 때마다 model.parameters()가 새 Iterator를 만듭니다.

next(model.parameters())
next(model.parameters())

두 Iterator 모두 커서가 첫 원소 앞에서 시작하므로, 두 호출은 각각 첫 Parameter를 반환합니다.

6. 모델과 입력 Tensor의 장치가 다르면 Forward 전에 중단합니다

if prompt_ids.device != model_device:
    raise ValueError(
        "모델과 prompt_ids의 장치가 다릅니다: "
        f"model={model_device}, "
        f"prompt_ids={prompt_ids.device}"
    )

모델 Weight와 입력 Tensor가 다른 장치에 있으면 모델 Forward는 정상적으로 계산될 수 없습니다. 이 검사는 깊은 모델 호출 안에서 장치 오류가 발생하기 전에, 무엇이 어긋났는지를 이해할 수 있는 메시지로 알려 줍니다.

model_device      cuda:0
prompt_ids.device cpu
→ ValueError: 모델과 prompt_ids의 장치가 다릅니다

model_device      cuda:0
prompt_ids.device cuda:0
→ Forward 실행 가능

torch.ones_like(prompt_ids)로 만드는 Attention Mask는 prompt_ids와 같은 장치에 생성됩니다. 따라서 입력 장치 검사가 통과하면 Mask도 모델과 같은 장치에서 사용할 수 있습니다.

7. 리팩터링한 Benchmark 함수

import time
import torch

from torch import Tensor
from jaxtyping import Int64
from transformers import GPT2LMHeadModel


def generate_for_benchmark(
    model: GPT2LMHeadModel,
    prompt_ids: Int64[
        Tensor,
        "batch prompt_token",
    ],
    max_new_tokens: int,
    use_cache: bool,
) -> Int64[
    Tensor,
    "batch generated_token",
]:
    model_device: torch.device = (
        next(model.parameters()).device
    )

    if prompt_ids.device != model_device:
        raise ValueError(
            "모델과 prompt_ids의 장치가 다릅니다: "
            f"model={model_device}, "
            f"prompt_ids={prompt_ids.device}"
        )

    attention_mask: Int64[
        Tensor,
        "batch prompt_token",
    ] = torch.ones_like(prompt_ids)

    with torch.inference_mode():
        generated_ids: Int64[
            Tensor,
            "batch generated_token",
        ] = model.generate(
            input_ids=prompt_ids,
            attention_mask=attention_mask,
            max_new_tokens=max_new_tokens,
            do_sample=False,
            use_cache=use_cache,
            pad_token_id=tokenizer.pad_token_id,
        )

    return generated_ids


def measure_generation(
    model: GPT2LMHeadModel,
    prompt_ids: Int64[
        Tensor,
        "batch prompt_token",
    ],
    max_new_tokens: int,
    use_cache: bool,
    warmup_runs: int,
    measurement_runs: int,
) -> tuple[
    float,
    float,
    Int64[
        Tensor,
        "batch generated_token",
    ],
]:
    model_device: torch.device = (
        next(model.parameters()).device
    )

    generated_ids: Int64[
        Tensor,
        "batch generated_token",
    ]

    for _ in range(warmup_runs):
        generated_ids = generate_for_benchmark(
            model=model,
            prompt_ids=prompt_ids,
            max_new_tokens=max_new_tokens,
            use_cache=use_cache,
        )

    if model_device.type == "cuda":
        torch.cuda.synchronize()

    start_time: float = time.perf_counter()

    for _ in range(measurement_runs):
        generated_ids = generate_for_benchmark(
            model=model,
            prompt_ids=prompt_ids,
            max_new_tokens=max_new_tokens,
            use_cache=use_cache,
        )

    if model_device.type == "cuda":
        torch.cuda.synchronize()

    elapsed_seconds: float = (
        time.perf_counter() - start_time
    )

    average_seconds: float = (
        elapsed_seconds / measurement_runs
    )

    generated_token_count: int = (
        prompt_ids.shape[0] * max_new_tokens
    )

    tokens_per_second: float = (
        generated_token_count / average_seconds
    )

    return (
        average_seconds,
        tokens_per_second,
        generated_ids,
    )

measure_generation()도 전달받은 model을 매번 생성 함수에 넘기고, 그 모델의 실제 장치가 CUDA일 때만 측정 전후에 동기화합니다. 전역 device가 아니라 측정 대상 모델의 장치를 기준으로 Timing 경계를 결정합니다.

8. 첫 Parameter의 장치를 모델 전체의 장치로 볼 수 있는 범위

이번 실습에서는 다음처럼 모델 전체를 하나의 장치로 옮겼습니다.

cpu_model.to("cpu")
gpu_model.to(cuda_device)

모든 Parameter가 같은 장치에 있으므로 첫 Parameter의 .device를 모델의 대표 장치로 사용해도 됩니다.

하지만 Model Parallel이나 device_map을 사용해 Parameter가 여러 GPU 또는 CPU·GPU에 나뉘어 있다면, 첫 Parameter의 장치만으로 모델 전체의 배치를 대표할 수 없습니다.

첫 Parameter   cuda:0
중간 Layer     cuda:1
마지막 Layer   cuda:1

next(model.parameters()).device
→ cuda:0만 알려 줌
→ 모델 전체의 장치 배치를 설명하지 못함

따라서 next(model.parameters()).device는 현재처럼 모델 전체가 한 장치에 있는 단일 장치 실습의 검증 방법입니다. 여러 장치에 나뉜 모델에서는 해당 Framework의 입력 장치 계약과 Device Map을 별도로 확인해야 합니다.

9. 결론

Benchmark 함수가 전역 model과 device를 암묵적으로 사용하면 CPU·GPU 비교에서 실제 측정 대상을 혼동할 수 있습니다. 모델을 함수 인자로 직접 받고, 전달된 모델의 실제 Parameter 장치와 입력 Tensor 장치를 확인하면 호출 자체가 측정 조건을 설명하게 됩니다.

model을 명시적으로 전달
→ 첫 Parameter에서 현재 단일 장치 확인
→ prompt_ids.device와 비교
→ 불일치하면 Forward 전에 ValueError
→ 실제 모델 장치를 기준으로 CUDA 동기화

next(model.parameters())는 두 번째 Parameter를 고르는 코드가 아닙니다. 새 Iterator의 커서가 첫 원소 앞에서 시작하므로 최초 next()가 첫 Parameter로 이동하면서 그 값을 반환합니다. 두 번째 Parameter는 같은 Iterator에 next()를 한 번 더 호출해야 얻을 수 있습니다.
