1. DB의 실제 데이터는 Page 단위로 저장된다

DB는 Row 하나하나를 독립적으로 디스크에서 읽고 쓰는 것이 아니라, Page라는 고정 크기 묶음 단위로 데이터를 관리한다. PostgreSQL은 기본적으로 8KB Page를 사용한다.

Table

Page 0                 Page 1
┌──────────────┐       ┌──────────────┐
│ Row          │       │ Row          │
│ Row          │       │ Row          │
│ Row          │       └──────────────┘
└──────────────┘

Page 단위로 읽는다는 말은 Page 0 → Page 1 → Page 2 순서로 무조건 읽는다는 뜻이 아니다.

필요한 Page 번호를 안다면 그 Page를 바로 요청할 수 있다.

Page 812 필요
    ↓
메모리에 있나?
    ├─ 있음 → 바로 사용
    └─ 없음 → 디스크에서 Page 812를 메모리로 가져옴

즉 Page는 FIFO Queue가 아니라 저장·관리 단위다.

2. Heap이란 무엇인가

PostgreSQL의 일반적인 Table은 Heap-organized table이다. 여기서 Heap은 Min Heap이나 Max Heap이 아니라, Row를 특정 컬럼 값에 따라 정렬해서 배치하지 않는 테이블 저장 방식을 뜻한다.

입력: id=10, id=3, id=500, id=7

Heap Page 0       Heap Page 1
10                7
3
500

id=7이면 몇 번 Page에 있다는 값 기반 배치 규칙이 Heap 자체에는 없다.

Table
  ↓
Heap 방식으로 조직됨
  ↓
여러 Heap Page
  ↓
각 Heap Page 안에 Row(Tuple)
  • Heap: Table 전체의 저장 조직 방식
  • Heap Page: Heap을 구성하는 실제 Page
  • Row/Tuple: Page 안의 실제 데이터

3. 인덱스가 없다면: Sequential Scan

Heap은 특정 컬럼 기준으로 정렬되어 있지 않다.

Page 0: age=31, 45, 22
Page 1: age=18, 67, 45
Page 2: age=52, 29, 40

WHERE age = 45를 실행해도 Heap만 가지고는 45가 어느 Page에 있는지 알 수 없다. 따라서 Page 0, Page 1, Page 2…를 읽으며 Row를 검사해야 한다. 이것이 Sequential Scan이다.

4. 인덱스는 별도의 빠른 탐색 구조다

인덱스는 Table과 별도로 만들어지며, 개념적으로 검색 값 → 실제 Row 위치를 연결한다.

조건
↓
Index
↓
Row 위치
↓
Heap Page
↓
실제 Row

SQL에서 보통 사용할 인덱스를 직접 지정하지 않는다. 예를 들어 SELECT * FROM users WHERE age = 45;를 실행하면 Optimizer가 Sequential Scan과 Index Scan 중 더 저렴하다고 판단한 방법을 선택한다.

5. 일반적으로 말하는 Index는 B-Tree다

PostgreSQL에서 별도 방식을 지정하지 않고 CREATE INDEX idx_age ON users(age);라고 만들면 기본적으로 B-Tree Index가 생성된다.

Index
├─ B-Tree
├─ Hash
├─ GIN
├─ GiST
└─ ...

B-Tree는 컬럼 값을 정렬하고 범위를 여러 갈래로 나누어 원하는 위치까지 빠르게 내려가는 Tree다.

            [30 | 60]
           /    |    \
       <30    30~60   >60

45는 30보다 크고 60보다 작음
→ 가운데 범위로 이동

처음부터 값을 하나씩 찾는 대신 필요 없는 범위를 계속 버린다.

6. B-Tree의 Root, Internal, Leaf와 Page

Root
 ↓
Internal
 ↓
Leaf

Root / Internal Page

어느 Page로 내려갈지 결정하는 길 안내 역할을 한다.

[20 | 40 | 70]

<20      → Page A
20~40    → Page B
40~70    → Page C
>=70     → Page D

Leaf Page

마지막 검색 대상인 인덱스 엔트리가 있다.

age=40 → TID
age=42 → TID
age=45 → TID
age=47 → TID

Root/Internal은 어디로 갈지 안내하고, Leaf는 실제 key와 Row 위치를 제공한다.

Tree에서 더 이상 자식이 없는 마지막 Node를 나무의 잎에 빗대어 Leaf라고 한다. Leaf가 수천 개라면 원하는 값이 어느 Leaf에 있는지 처음에는 모르므로 Root → Internal → Leaf 순서로 찾아간다. Root Page는 자주 쓰이기 때문에 메모리에 있을 가능성이 높다.

B-Tree Node와 Page의 관계

B-Tree의 Node는 실제 DB에서 대체로 Index Page 하나에 대응한다고 생각할 수 있다. Page 하나에는 key 하나가 아니라 여러 key와 pointer가 함께 들어간다.

Index Page
┌──────────────────────┐
│ 20 → child Page      │
│ 40 → child Page      │
│ 70 → child Page      │
│ ...                  │
└──────────────────────┘

DB가 Page 단위로 읽으므로 Page 하나에 많은 key를 넣는 편이 효율적이다. 한 Node에서 많은 자식 Page로 분기하면 Tree 높이가 낮아지고 Root에서 Leaf까지 읽을 Page 수도 줄어든다. 그래서 B-Tree는 DB의 Page 단위 저장과 I/O 방식에 잘 맞는다.

= 검색 흐름

Root Page
↓ 45가 속한 범위 선택
Internal Page
↓ 범위를 더 좁힘
Leaf Page
↓ age=45 발견
TID 획득
↓
실제 Heap Row로 이동

7. 중복, UNIQUE와 범위 검색

중복 값

인덱스 컬럼이 UNIQUE가 아니면 같은 key를 가진 여러 엔트리가 존재할 수 있다. WHERE age = 30이면 첫 30을 찾은 뒤 같은 값이 이어지는 부분을 읽는다.

29
30 ← 시작
30
30
30
31 ← 종료

UNIQUE Index

UNIQUE라면 동일한 key를 가진 Row가 둘 이상 존재할 수 없다. id=123을 하나 찾으면 같은 값을 더 찾을 필요 없이 종료한다. 즉 중복을 검색하며 제거해서 빠른 것이 아니라, 애초에 중복이 없다는 보장을 이용한다.

범위 검색

B-Tree는 정렬되어 있어 =, >, <, BETWEEN 검색에 사용할 수 있다. age BETWEEN 30 AND 50이면 Tree로 30이 있는 Leaf까지 빠르게 간 뒤, 범위를 벗어날 때까지 인접 엔트리를 순서대로 읽는다.

Tree → 범위 시작점까지 빠르게 이동

Leaf → 30, 35, 40, 45, 50
                         51에서 종료

B-Tree 전체를 처음부터 순차 탐색하는 것이 아니라, 시작 위치까지 빠르게 이동한 후 필요한 구간만 순차적으로 읽는 것이다.

8. Hash Index

B-Tree가 “이 값은 어느 범위에 있지?”를 묻는다면 Hash는 “이 값을 계산하면 어느 Bucket이지?”를 묻는다.

값
↓
hash 함수
↓
hash code
↓
Bucket 결정
↓
해당 Bucket Page

Hash 값은 메모리 주소가 아니다

hash("kim") → 837291에서 837291은 RAM 주소가 아니다. 이 값으로 논리적인 Bucket 번호를 정하고, 인덱스의 메타정보와 배치 규칙으로 그 Bucket이 사용하는 Index Page를 찾는다.

hash → Bucket → Index Page

Bucket과 Page

  • Bucket: Hash Index가 해시값을 묶는 논리적 분류 단위
  • Page: 내용이 저장되는 실제 단위
Bucket 42
↓
Primary Page
↓ 필요하면
Overflow Page

저장한 위치를 다시 찾는 원리

인덱스 생성: "kim" → hash("kim") → Bucket 42 → 엔트리 저장
나중의 조회: "kim" → 같은 hash() → 같은 Bucket 42

저장과 조회에 같은 Hash 함수를 쓰기 때문에 같은 논리적 위치를 다시 계산할 수 있다.

Bucket Page 안에서도 비교한다

Bucket Page에는 여러 엔트리가 들어간다. 따라서 Page까지 도착한 뒤 원하는 hash code와 일치하는 엔트리를 검사한다.

전체 수백만 건
↓ hash
특정 Bucket
↓
Page 내부의 소수 엔트리 검사

Hash Collision

서로 다른 값이 같은 hash 결과를 가질 수 있다. 같은 hash code 후보가 여러 개라면 실제 Heap Row로 가서 원래 조건이 맞는지 다시 확인할 수 있다. Hash Index도 정답을 즉시 확정하기보다는 검사할 후보를 아주 적게 줄이는 역할을 한다.

B-Tree와 Hash의 차이

B-Tree                         Hash
값의 순서를 유지              값을 hash code로 변환
=, >, <, BETWEEN             주로 = 검색
범위 탐색 가능                원래 값의 순서가 사라짐

예를 들어 20, 21, 22가 전혀 다른 순서의 Bucket에 들어갈 수 있으므로 Hash는 BETWEEN 20 AND 30 같은 범위 검색에 적합하지 않다.

9. GIN의 기본 개념

GIN은 역색인(Inverted Index) 계열이며, 한 Column 안에 여러 요소가 들어 있는 경우에 적합하다.

Row 1 → [python, ai]
Row 2 → [java, spring]
Row 3 → [python, django]

GIN
python → Row 1, Row 3
ai     → Row 1
java   → Row 2
spring → Row 2
django → Row 3

“이 Row의 값은 무엇인가?”가 아니라 “이 요소가 들어 있는 Row들은 어디인가?”를 빠르게 찾는다.

배열, JSONB, 전문 검색 등에 사용할 수 있다.

핵심 한 문장
DB의 실제 데이터는 Page에 저장되고, 일반 Table은 특정 key 순서가 없는 Heap 구조로 Page를 사용한다. 인덱스는 Heap 전체를 뒤지지 않도록 별도 탐색 구조를 만들며, B-Tree는 정렬과 범위 분할로 원하는 Leaf Page를 찾아가고 Hash는 값을 계산해 원하는 Bucket Page의 후보로 바로 좁힌다.
