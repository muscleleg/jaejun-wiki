sqlite3 기본 명령어 정리

sqlite3 기본 명령어 정리입니다:

DB 접속

sqlite3 ai-memory.db

자주 쓰는 명령어 (접속 후)

명령어 설명
.tables 테이블 목록 보기
.schema 전체 테이블 구조(DDL) 보기
.schema 테이블명 특정 테이블 구조 보기
.headers on 컬럼명 표시 켜기
.mode column 보기 좋게 컬럼 정렬
.quit 종료

SQL 쿼리

-- 전체 데이터 조회
SELECT * FROM agent_sessions;
SELECT * FROM agent_messages;

-- 조건 조회
SELECT * FROM agent_messages WHERE session_id = 'user_1';

-- 최근 메시지만
SELECT * FROM agent_messages ORDER BY id DESC LIMIT 5;

-- 삭제
DELETE FROM agent_messages;
DELETE FROM agent_sessions;

접속 없이 한 줄로 실행

sqlite3 ai-memory.db ".tables"
sqlite3 ai-memory.db "SELECT * FROM agent_messages;"

보기 좋게 출력하는 조합

sqlite3 -header -column ai-memory.db "SELECT * FROM agent_messages;"
  • header는 컬럼명 표시, column은 정렬된 표 형태로 출력합니다.

명령어 정리

PostgreSQL에서 데이터베이스 변경과 스키마 지정은 다음과 같이 하면 됩니다:

✅ 1. 데이터베이스 변경

PostgreSQL은 USE 명령어가 없기 때문에, 다른 데이터베이스로 변경하려면 새로 접속해야 합니다.

📌 방법

  • CLI에서:
\c 데이터베이스명

예:

\c mydatabase
  • 또는 psql 처음 접속할 때:
psql -U 사용자명 -d 데이터베이스명

✅ 2. 스키마 지정

PostgreSQL에서 스키마는 논리적인 데이터베이스 안의 구분 영역입니다. 테이블, 뷰 등을 스키마.객체명으로 관리합니다.

📌 스키마 지정 (쿼리에서 명시적 사용)

SELECT * FROM my_schema.my_table;

📌 스키마 우선순위 설정 (검색 경로 지정)

SET search_path TO my_schema;

이렇게 하면 이후에는 my_table처럼 쓸 수 있음.

💡 확인 명령어

  • 현재 접속한 데이터베이스 확인:
SELECT current_database();
  • 현재 search_path 확인:
SHOW search_path;
  • 존재하는 스키마 확인:
SELECT schema_name FROM information_schema.schemata;

후속 항목은 스키마 생성·삭제와 권한 부여다.

✅ search_path는 어떤 종류의 설정인가?

  • ✔️ 세션 단위 설정

→ SET search_path TO ... 하면 현재 접속한 세션에만 적용돼요.

다음 접속 때는 초기화됨.

  • ✔️ 사용자별 기본값 설정도 가능함
    → 영구적으로 설정하고 싶으면 사용자나 데이터베이스 레벨에 지정해야 함.

✅ 예시: 세션에서 변경

SET search_path TO my_schema;

→ 이후 이 세션에서는 모든 쿼리에서 my_schema 우선 참조됨.

✅ 예시: 사용자 레벨로 영구 설정

ALTER ROLE my_user SET search_path TO my_schema;

→ my_user가 접속하면 자동으로 search_path = my_schema가 적용됨.

✅ 예시: 데이터베이스 레벨 설정 (덜 일반적)

ALTER DATABASE my_db SET search_path TO my_schema;

💡 요약

설정 대상 명령어 적용 범위
세션 SET search_path TO ... 현재 연결된 세션에만
사용자 ALTER ROLE ... SET 해당 유저가 로그인할 때 자동 적용
데이터베이스 ALTER DATABASE ... SET 해당 DB에 접속할 때 기본값

보안 요구가 높다면 public 스키마의 기본 권한도 함께 검토한다.

LIKE, ILIKE 차이

LIKE 와 ILIKE 의 차이는 대소문자를 구분하느냐입니다.

✅ 차이 요약

구문 대소문자 구분 예시 결과
LIKE 구분함 'Apple' LIKE 'a%' ❌ false (대소문자 다름)
ILIKE 구분 안 함 'Apple' ILIKE 'a%' ✅ true (대소문자 무시함)

✅ 와일드카드 문법

기호 의미
% 0개 이상의 문자
_ 정확히 1개의 문자

✅ 예제

-- 대소문자 구분
SELECT 'Hello' LIKE 'h%';     -- false
SELECT 'Hello' ILIKE 'h%';    -- true

-- 와일드카드 예제
SELECT 'abc' LIKE 'a_c';      -- true
SELECT 'abc' LIKE 'a__';      -- true
SELECT 'abc' LIKE 'a%';       -- true

✅ 실제 사용 예

SELECT * FROM users WHERE name ILIKE '%kim%';
-- 이름에 'kim', 'Kim', 'KIM' 등 포함된 모든 레코드 검색

정리:

  • LIKE → 민감한 검색
  • ILIKE → 민감하지 않은 검색 (대소문자 무시)

→ 일반 사용자는 ILIKE을 더 자주 씀.

예제

-- first_name이 'J'로 시작하는 모든 고객 조회
SELECT * FROM customer WHERE first_name LIKE 'J%';

-- first_name이 'J'로 시작하는 고객 수를 조회
SELECT COUNT(*) FROM customer WHERE first_name LIKE 'J%';

-- first_name이 'J'로 시작하고, last_name이 'S'로 시작하는 고객 조회
SELECT * FROM customer WHERE first_name LIKE 'J%' AND last_name LIKE 'S%';

-- first_name이 'j' 또는 'J'로 시작하고, last_name이 's' 또는 'S'로 시작하는 고객 조회 (대소문자 구분 없음)
SELECT * FROM customer WHERE first_name ILIKE 'j%' AND last_name ILIKE 's%';

-- first_name이 'er'로 끝나는 고객 조회 (예: 'Tyler', 'Jennifer' 등)
SELECT * FROM customer WHERE first_name LIKE '%er';

-- 첫 글자가 아무 문자이고, 그 뒤에 'her'로 시작하는 first_name을 가진 고객 조회 (예: 'Sheri', 'Theresa' 등)
SELECT * FROM customer WHERE first_name LIKE '_her%';

-- 첫 글자가 아무 문자이고, 그 뒤에 'her'로 시작하지 않는 고객을 조회
-- 즉, 'Sheri', 'Theresa' 같은 이름은 제외됨
SELECT * FROM customer WHERE first_name NOT LIKE '_her%';

-- first_name이 'A'로 시작하는 고객을 last_name 오름차순으로 정렬하여 조회
SELECT * FROM customer WHERE first_name LIKE 'A%' ORDER BY last_name;

-- first_name이 'A'로 시작하고, last_name이 'B'로 시작하지 않는 고객을 last_name 기준으로 정렬하여 조회
SELECT * FROM customer WHERE first_name LIKE 'A%' AND last_name NOT LIKE 'B%' ORDER BY last_name;

-- 결제 금액이 5.00보다 큰 payment 레코드 개수 조회
SELECT COUNT(*) FROM payment WHERE 5.00 < amount;

-- first_name이 'P'로 시작하는 배우(actor) 수를 조회
SELECT COUNT(*) FROM actor WHERE first_name LIKE 'P%';

-- 중복 없이 district의 개수를 조회
SELECT COUNT(DISTINCT district) FROM address;

-- 모든 고유한(different) district 값을 조회
SELECT DISTINCT district FROM address;

-- 등급이 'R'이고, 교체 비용이 5 이상 15 이하인 영화 수를 조회
SELECT COUNT(*) FROM film WHERE rating = 'R' AND replacement_cost BETWEEN 5 AND 15;

-- 제목에 'Truman'이라는 단어가 포함된 영화 수를 조회
SELECT COUNT(*) FROM film WHERE title LIKE '%Truman%';

-- film 테이블에서 replacement_cost의 최솟값을 조회
-- ⚠️ 이 쿼리에서는 집계 함수(MIN)를 쓰기 때문에, 다른 컬럼(ex: title)을 같이 SELECT 하려면 GROUP BY가 필요함
-- 예: SELECT title, MIN(replacement_cost) FROM film; → 오류 발생 (title은 집계되지 않았기 때문)
SELECT MIN(replacement_cost) FROM film;

-- replacement_cost의 최솟값과 최댓값을 함께 조회
SELECT MIN(replacement_cost), MAX(replacement_cost) FROM film;

-- replacement_cost의 평균값을 조회
SELECT AVG(replacement_cost) FROM film;

-- replacement_cost의 평균값을 소수점 둘째 자리까지 반올림해서 조회
SELECT ROUND(AVG(replacement_cost), 2) FROM film;

-- replacement_cost의 총합을 조회
SELECT SUM(replacement_cost) FROM film;
-- 고객 ID별로 중복 없이 한 번씩만 조회 (고유한 customer_id 목록)
SELECT customer_id FROM payment GROUP BY customer_id;

-- 고객 ID별로 결제 금액 합계를 조회
SELECT customer_id, SUM(amount) FROM payment GROUP BY customer_id;

-- 고객 ID별 결제 금액 합계를 오름차순 정렬하여 조회
SELECT customer_id, SUM(amount) FROM payment GROUP BY customer_id ORDER BY SUM(amount);

-- 고객 ID별 결제 금액 합계를 내림차순 정렬하여 조회
SELECT customer_id, SUM(amount) FROM payment GROUP BY customer_id ORDER BY SUM(amount) DESC;

-- 고객 ID와 직원 ID 조합별로 결제 금액 합계를 조회
SELECT customer_id, staff_id, SUM(amount) FROM payment GROUP BY customer_id, staff_id;

-- 전체 결제 일시(payment_date)를 그대로 조회
SELECT payment_date FROM payment;

-- 결제 일시에서 날짜만 추출하여 조회 (시간 제거)
SELECT DATE(payment_date) FROM payment;

-- 날짜별로 결제 금액의 총합을 조회
SELECT DATE(payment_date), SUM(amount) FROM payment GROUP BY DATE(payment_date);

-- 날짜별 결제 금액 합계를 조회하고, 가장 높은 금액 순으로 정렬
SELECT DATE(payment_date), SUM(amount) FROM payment GROUP BY DATE(payment_date) ORDER BY SUM(amount) DESC;

-- 직원 ID(staff_id)별 결제 건수(count)를 조회
SELECT staff_id, COUNT(amount) FROM payment GROUP BY staff_id;

-- 영화 등급(rating)별로 교체 비용의 평균을 소수점 둘째 자리까지 반올림하여 조회
SELECT rating, ROUND(AVG(replacement_cost), 2) FROM film GROUP BY rating;

-- 고객 ID별 결제 금액 총합을 구하고, 가장 많이 결제한 상위 5명의 고객을 조회 (내림차순 정렬 + 제한)
SELECT customer_id, SUM(amount) FROM payment GROUP BY customer_id ORDER BY SUM(amount) DESC LIMIT 5;

스키마

1. 기본 스키마의 정체 (왜 있나요?)

PostgreSQL을 설치하면 기본적으로 보이는 스키마들은 시스템 관리와 표준 준수를 위한 용도입니다.

스키마 이름 역할 비유
public 사용자가 별도 지정 없이 테이블을 만들면 들어가는 기본 폴더 공용 거실
information_schema DB 내 모든 정보(테이블 목록, 컬럼명 등)를 조회하는 표준 뷰 도서관 인덱스
pg_catalog DB의 심장부(내장 함수, 시스템 데이터)가 담긴 곳 운영체제(OS) 시스템 폴더

2. 스키마를 새로 만들어 쓰는 이유 (실무 방식)

공부할 때는 public만 써도 충분하지만, 실무에서는 보통 서비스 목적에 따라 스키마를 새로 만들어 사용합니다.

  • 정리 정돈: 테이블이 많아질 때 기능별(결제, 회원, 주문 등)로 묶어 관리하기 편합니다.
  • 보안: 특정 사용자에게 특정 스키마만 접근하도록 권한을 쪼개어 부여할 수 있습니다.
  • 이름 충돌 방지: 여러 팀이 협업할 때 각자 스키마를 쓰면 테이블 이름이 겹쳐도 문제가 생기지 않습니다.

3. 한눈에 보는 요약 가이드

  1. 초보 단계: public 스키마에 바로 테이블을 만들어 연습해도 무방합니다.
  2. 중수 단계: CREATE SCHEMA [이름] 명령어로 나만의 공간을 만들어 관리하기 시작합니다.
  3. 주의사항: pg_catalog나 information_schema는 시스템 운영용이므로 절대 삭제하거나 수정하지 마세요.

직접 스키마를 생성하고 그 안에 테이블을 만드는 실습 SQL 문법을 알려드릴까요, 아니면 지금 만든 my_table을 다른 스키마로 옮기는 방법을 알려드릴까요?

아키텍처

  1. 핵심 구성 요소
  • Shared Buffers (RAM 🧠): 데이터 페이지(8KB 단위)를 보관하는 공유 메모리 공간입니다. 자주 쓰는 '인기 데이터'가 머무는 곳이며, 디스크 I/O를 최소화하여 성능을 끌어올립니다.
  • WAL (Write Ahead Log, Disk 📝): 모든 변경 사항을 실제 데이터 파일에 적기 전, 가장 먼저 기록하는 로그 파일입니다. 데이터의 안전(무결성)을 보장하는 최후의 보루입니다.
  • Data Files (Heap, Disk 💾): 실제 테이블 데이터가 영구적으로 저장되는 본진입니다.

2. 데이터가 처리되는 흐름 (The Lifecycle)

A. 데이터를 읽을 때 (SELECT)

  1. 메모리 우선: 요청된 데이터 페이지가 Shared Buffers에 있는지 확인합니다.
  2. 디스크 로드: 메모리에 없다면(Cold Data), 디스크에서 8KB 페이지를 읽어 Shared Buffers에 올립니다.
  3. 반환: 이후 메모리에 있는 데이터를 사용자에게 전달합니다. (이제 이 데이터는 '인기 후보'가 됩니다.)

B. 데이터를 수정할 때 (UPDATE / INSERT)

  1. 메모리 수정: Shared Buffers에 있는 해당 페이지의 내용을 바꿉니다. (이 상태를 Dirty Page라고 합니다.)
  2. WAL 기록 (Commit): 수정 즉시 변경 이력을 WAL 파일에 순차적으로 기록합니다. 이 단계가 끝나야 사용자는 "성공" 응답을 받습니다.
  3. 비동기 반영 (Checkpoint): 실제 데이터 파일(.dbf)은 당장 수정되지 않습니다. 나중에 여유가 있을 때(체크포인트) Shared Buffers의 내용이 디스크로 한꺼번에 옮겨 적힙니다.

3. 장애 복구와 일관성 (Reliability)

  • Crash Recovery: DB가 갑자기 꺼져서 메모리(Shared Buffers)가 날아가도 걱정 없습니다. 다시 켜질 때 WAL 로그를 읽어 마지막 체크포인트 이후의 작업을 재현(Redo)하여 최신 상태로 복구합니다.
  • 복제 (Replication): Master 서버의 WAL이 Slave 서버로 전달됩니다. Slave는 이 로그를 읽어 자신의 Shared Buffers를 최신 상태로 유지하며, 필요한 경우에만 디스크에서 데이터를 읽어와 수정합니다.

연습환경 구성

관례(Convention)를 기준으로 PostgreSQL 연결 설정과 애플리케이션 구성을 정리한다. 실제 환경에서는 사용 중인 드라이버와 배포 방식에 맞춰 각 설정을 재검증해야 한다.

☁️ 1. 왜 외부 DB(Neon)를 쓰는가?

  • 실무 지향: 내 컴퓨터 안이 아닌, 실제 원격 서버와 통신하는 로직을 그대로 연습할 수 있습니다.
  • 클린 환경: PostgreSQL 소프트웨어를 로컬에 설치하지 않아도 되므로 PC 환경이 꼬일 염려가 없습니다.
  • 배포 준비: 나중에 FastAPI 서비스를 클라우드에 올릴 때, DB 주소만 입력하면 바로 연동되는 구조를 미리 익힙니다.

⚙️ 2. Neon 클라우드 설정 (1분 컷)

  1. Project 생성: postgres-practice (이름 자유)
  2. Region: Asia Pacific (Tokyo) 또는 Singapore (속도가 가장 빠름)
  3. 핵심 설정: Connection pooling 스위치를 OFF로 끄세요.
  4. 주소 복사: Show password를 눌러 비밀번호를 확인한 뒤, postgres://example_user:[REDACTED_PASSWORD]@db.example.invalid:5432/example_db 형태의 주소를 복사합니다.

📦 3. 가상환경 세팅 (표준 관례)

가상환경 이름은 프로젝트마다 이름을 바꾸지 않고 .venv로 통일하는 것이 업계 표준입니다.

  1. 생성: 터미널에서 python -m venv .venv 입력
  2. 활성화:
  • Windows: .venv\Scripts\activate
  • Mac/Linux: source .venv/bin/activate
  1. 패키지 설치: 활성화 상태에서 pip install sqlalchemy asyncpg greenlet 입력

💻 4. SQLAlchemy 통합 코드 (main.py)

이 코드는 설계 → 연결 → 생성을 한 번에 처리합니다.

import asyncio
from sqlalchemy.ext.asyncio import create_async_engine
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column
from sqlalchemy import String, Integer

# [1] 주소 설정: 'postgres://'를 'postgresql+asyncpg://'로 반드시 변경
RAW_URL = "복사한_주소_붙여넣기"
DATABASE_URL = RAW_URL.replace("postgres://", "postgresql+asyncpg://")

# [2] 테이블 설계 (Blue Print)
class Base(DeclarativeBase):
    pass

class Course(Base):
    __tablename__ = "courses"
    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    title: Mapped[str] = mapped_column(String(100), nullable=False)
    price: Mapped[int] = mapped_column(Integer, default=0)

# [3] 비동기 엔진 생성 (echo=True로 SQL 로그 확인)
engine = create_async_engine(DATABASE_URL, echo=True)

# [4] 실행: 파이썬 설계를 Neon DB에 물리적으로 생성
async def init_db():
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
    print("🚀 Neon DB에 'courses' 테이블 생성이 완료되었습니다!")

if __name__ == "__main__":
    asyncio.run(init_db())
여러 번 실행해도 에러가 발생하지 않는 이유

그 질문이야말로 SQLAlchemy가 왜 단순한 쿼리 생성기가 아니라 "ORM 프레임워크"인지를 보여주는 핵심입니다.

metadata.create_all이 여러 번 실행되어도 안전한 이유는 내부적으로 "Idempotency(멱등성)"라는 원칙을 지키기 때문입니다.

재검증 메모
기본 checkfirst=True에서 SQLAlchemy가 테이블 존재 여부를 확인해 누락된 테이블을 만들지만, 모든 dialect가 문자 그대로 IF NOT EXISTS를 보낸다고 단정할 수 없다. 기존 컬럼 변경은 migration 도구로 관리한다.

🧐 왜 에러가 나지 않고 멀쩡할까?

SQLAlchemy는 단순히 CREATE TABLE... 명령을 DB에 무조건 던지는 게 아니라, 실행될 때 다음과 같은 사전 체크 단계를 거칩니다.

  1. DB 스캔 (Reflection): create_all이 호출되면, 먼저 DB에 접속해서 현재 어떤 테이블들이 있는지 목록을 훑어봅니다.
  2. 존재 여부 대조: 우리가 파이썬 코드에 정의한 Course 클래스의 이름(__tablename__ = "courses")이 실제 DB 테이블 목록에 있는지 비교합니다.
  3. 조건부 실행 (IF NOT EXISTS): * 테이블이 없다면: CREATE TABLE courses... 쿼리를 실행합니다.
  • 테이블이 이미 있다면: 아무 작업도 하지 않고 조용히 넘어갑니다.

💡 실무에서 이게 왜 중요할까?

만약 테이블이 있을 때마다 에러가 난다면, 우리는 매번 서버를 켤 때마다 "테이블이 있나 없나?"를 체크하는 코드를 직접 짜야 했을 겁니다.

하지만 SQLAlchemy가 이 과정을 자동화해 주기 때문에:

  • 안정성: 앱을 재시작해도 DB 데이터가 날아가거나 충돌이 나지 않습니다.
  • 편의성: 새로운 기능이 추가되어 User라는 클래스를 새로 만들었다면, main.py를 다시 실행하는 것만으로 기존 Course는 건드리지 않고 User 테이블만 싹 만들어줍니다.

⚠️ 주의할 점 (수정은 안 돼요!)

여기서 많은 초보 개발자가 오해하는 부분이 있습니다.

  • 생성(Create)은 해주지만, 수정(Alter)은 안 해줍니다.
  • 예를 들어, 이미 생성된 Course 클래스에서 price 컬럼의 이름을 cost로 바꾸고 다시 실행하면?
  • SQLAlchemy는 "어? courses 테이블은 이미 있네? 통과!"라고 생각하고 이름 변경을 무시해버립니다.

그래서: 실무에서는 테이블 구조가 바뀔 때마다 Alembic 같은 마이그레이션 도구를 써서 "어떤 컬럼이 어떻게 바뀌었는지" 기록하고 적용하는 과정을 거치게 됩니다.

🏗️ SQL 테이블 정의 공식

하나의 컬럼(Column)을 만들 때는 반드시 아래 순서를 지켜야 합니다.

순서 요소 역할 예시
1 컬럼 이름 데이터의 이름 (명사) id, name, price
2 데이터 타입 저장할 데이터의 종류 (정체성) SERIAL, VARCHAR(100), INTEGER
3 제약 조건 데이터가 지켜야 할 규칙 (성격) PRIMARY KEY, NOT NULL, DEFAULT 0

💡 기억해두면 좋은 포인트

  1. 타입이 먼저!: "이름이 username이고 성격은 필수인데 종류는 글자야" 라고 말하지 않고, "이름은 username, 종류는 글자, 성격은 필수야" 순으로 말해야 컴퓨터가 알아듣습니다.
  2. 제약 조건의 유연함: NOT NULL UNIQUE라고 쓰든 UNIQUE NOT NULL이라고 쓰든 제약 조건들끼리의 순서는 상관없습니다. 하지만 이들은 항상 타입 뒤에 와야 합니다.

✍️ 직접 쿼리 완성해보기

이제 이 공식을 활용해서 아까 기획했던 products 테이블을 직접 만드는 SQL을 작성해 볼 차례입니다.

[복습용 조건]

  • 테이블 이름: products
  • id: 자동 증가 정수, 기본 키
  • name: 최대 100자 문자열, 필수 값
  • price: 정수형, 필수 값
  • stock: 정수형, 기본값 0

편입 후 검증 메모

  • 스키마 계층: PostgreSQL의 schema는 database 안의 namespace다. 서로 다른 database를 schema처럼 직접 참조하는 구조로 이해하지 않는다.
  • LIKE/ILIKE: ILIKE는 PostgreSQL의 대소문자 무시 패턴 연산자다. 결과는 locale·collation과 문자 데이터에 영향을 받을 수 있다.
  • 연결 정보: 공개본의 사용자·비밀번호·호스트·database 이름은 모두 예시값이다. 실제 값은 환경 변수나 비밀 관리 도구에서 주입하고 로그·문서·Git에 남기지 않는다.
  • 연습 환경: 관리형 DB나 특정 GUI의 화면 절차는 바뀔 수 있다. 핵심 검증은 SSL 요구, 연결 제한, 트랜잭션, migration과 최소 권한 계정이다.
  • SQLite 비교: SQLite CLI 메모는 단일 파일 DB의 점검 도구로 보존했지만 PostgreSQL의 서버 프로세스·권한·동시성 모델과 동일하지 않다.
