SQL·JDBC 실행 흐름과 안전한 Query

SQL 문자열을 만드는 데서 끝내지 않고, Java application이 connection을 얻어 값을 binding하고 결과 cursor를 읽고 transaction을 닫는 전 과정을 이해합니다.

전체 흐름자원값 bindingResultSettransactionpaginationView동적 연결진단결론

1. JDBC는 Java 호출을 database protocol로 연결한다

JDBC(Java Database Connectivity: 자바 데이터베이스 연결)는 Java에서 관계형 database에 접속하고 SQL을 실행하는 표준 API(응용 프로그램 인터페이스)입니다.

대표 흐름
Driver → Connection → PreparedStatement → execute → ResultSet 또는 update count → commit/rollback → 자원 close

Driver가 Java 호출을 database 제품의 protocol로 변환하고, Connection이 한 database session과 transaction context를 나타냅니다. Framework가 이를 추상화해도 connection pool, transaction, cursor라는 실제 자원은 남습니다.

2. Connection·Statement·ResultSet은 닫아야 하는 자원이다

String sql = "select id, name from member where active = ? order by id";

try (Connection connection = dataSource.getConnection();
     PreparedStatement statement = connection.prepareStatement(sql)) {
    statement.setBoolean(1, true);
    try (ResultSet rows = statement.executeQuery()) {
        while (rows.next()) {
            long id = rows.getLong("id");
            String name = rows.getString("name");
        }
    }
}

try-with-resources는 정상·예외 경로 모두에서 자원을 역순으로 닫습니다. 운영 application은 매 요청마다 새 물리 연결을 만들기보다 pool에서 Connection을 빌리고 반환합니다.

3. placeholder는 값을 위한 자리이며 SQL 구조를 위한 자리가 아니다

PreparedStatement의 ?에는 문자열·숫자·날짜 같은 값을 binding합니다. 값과 SQL 문법을 분리하므로 quote escaping 오류와 SQL injection 위험을 줄입니다.

String sql = "select id, name from member where email = ?";
statement.setString(1, email);
식별자는 binding할 수 없습니다
table 이름, column 이름, ASC/DESC 같은 SQL 구조를 사용자 입력으로 직접 이어 붙이지 않습니다. 동적 정렬이 필요하면 허용 목록에서 안전한 SQL 조각으로 mapping합니다.
String orderBy = switch (sortKey) {
    case "name" -> "name";
    case "created" -> "created_at";
    default -> "id";
};
String sql = "select id, name from member order by " + orderBy;

4. ResultSet cursor는 첫 row 앞에서 시작한다

executeQuery 직후 cursor는 before-first 위치입니다. 먼저 next()를 호출해야 첫 row로 이동합니다. 한 건만 예상해도 0건과 여러 건을 어떻게 처리할지 계약을 정합니다.

if (!rows.next()) return Optional.empty();
Member member = mapMember(rows);
if (rows.next()) throw new IllegalStateException("unique 제약 위반");
return Optional.of(member);

Column label을 사용하면 순서 변경에 덜 취약하지만 SQL alias와 Java mapping이 일치해야 합니다. SQL NULL을 primitive getter로 읽을 때 기본값과 실제 0을 구분하려면 wasNull() 또는 nullable type mapping을 고려합니다.

5. 여러 SQL이 하나의 업무라면 transaction으로 묶는다

connection.setAutoCommit(false);
try {
    updateBalance(connection, fromId, -amount);
    updateBalance(connection, toId, amount);
    connection.commit();
} catch (Exception error) {
    connection.rollback();
    throw error;
}

commit 전에 일부 SQL만 성공한 상태에서 오류가 나면 rollback해야 원자성을 지킬 수 있습니다. Connection을 pool에 반환하기 전에 auto-commit, read-only, isolation 같은 상태가 framework나 pool에 의해 초기화되는지도 확인합니다.

7. View는 저장된 query이고 materialized view는 결과를 저장한다

  • View: 이름을 붙인 query입니다. 기초 table을 기준으로 실행되며 권한과 반복 query를 단순화할 수 있습니다.
  • Materialized view: query 결과를 물리적으로 저장해 읽기를 빠르게 할 수 있지만 refresh 전략과 stale data를 관리해야 합니다.

View가 있다고 자동으로 빠른 것은 아닙니다. index 사용과 실행 계획을 실제 database에서 확인합니다. 같은 이름의 view를 중복 생성하거나 다른 계정 schema에 만들어 놓고 찾지 못하는 문제도 흔합니다.

8. 외부 database 연결 정보는 코드와 공개 문서에서 분리한다

URL(통합 자원 위치), 사용자 이름, 비밀번호, 인증서는 environment variable이나 secret manager에서 주입하고 log에 출력하지 않습니다. Runtime에 임의 driver와 URL을 받아 접속하는 기능은 allowlist, network egress, timeout, read-only 계정, query 제한 없이는 data 유출 경계가 될 수 있습니다.

개발 도구에서 접속이 된다는 사실과 application server에서 접속이 된다는 사실도 다릅니다. DNS(도메인 이름 시스템), route, firewall, TLS(전송 계층 보안), driver version과 계정 권한을 application 실행 환경에서 검증합니다.

9. 실패는 계층별로 분리해 진단한다

  1. Driver를 load할 수 있는가?
  2. DNS와 port에 도달하는가?
  3. TLS와 인증이 성공하는가?
  4. Schema·table·column 이름과 권한이 맞는가?
  5. SQL syntax와 parameter 수·type이 맞는가?
  6. ResultSet mapping과 NULL 처리가 맞는가?
  7. commit 또는 rollback이 실행됐는가?

SQL 문자열 조립 때 단어 사이 공백이 빠지는 단순 오류도 최종 SQL을 parameter와 분리해 log하면 금방 찾을 수 있습니다. 다만 민감한 값은 masking합니다.

10. 결론

JDBC 문제는 연결 → 값 binding → 실행 → cursor 이동 → mapping → transaction 확정 → 자원 반환 순서로 추적합니다. SQL 문법만 맞아도 이 경계 중 하나가 깨지면 application은 올바르게 동작하지 않습니다.
