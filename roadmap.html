    Hidden State `[1,2,4]`에서 Token별 Feature 평균을 `dim=-1, keepdim=True`로 구하면 평균을 낸 마지막 축이 길이 `1`로 남아 `[1,2,1]`이 되고, 이 평균을 원래 Tensor에서 뺄 때 크기 `1`인 축이 Feature 길이 `4`에 맞춰 Broadcasting된다고 자기 말로 설명했다. Broadcasting은 오른쪽 축부터 크기를 비교하며, 크기가 같거나 한쪽이 `1`이면 계산할 수 있고, 차원이 짧은 `[4]`는 부족한 Batch·Token 축이 왼쪽에 생략된 것으로 보아 `[1,2,4]`의 Feature 축에 대응한다고 이해했다. 반면 같은 위치의 축이 `4`와 `2`처럼 다르고 어느 쪽도 `1`이 아니면 연산할 수 없다는 경계도 구분했다. KV Cache Benchmark의 `[1000,128]`을 다시 해석해, Batch 1000은 문맥을 공유하는 문장 1000개가 아니라 서로 독립적인 Sequence 1000개이고 각 행 안에서만 128 Token이 Attention한다는 점을 정리했다. Attention Score는 개념적으로 `[Batch,Head,Query Token,Key Token]`이므로 행별 행렬이 분리되고, KV Cache `[Batch,KV Head,과거 Token,Head Dimension]`도 같은 Tensor에 묶여 있을 뿐 행끼리 과거 문맥을 공유하지 않는다. 서로 이어지는 문장이라면 한 행의 긴 Sequence로 연결해야 뒤 문장이 앞 문장을 참조할 수 있으며, 독립 요청이라면 하나의 Batch 안의 서로 다른 행으로 둔다. Batch의 각 행을 서로 다른 클라이언트 요청처럼 이해할 수 있지만 정확한 단위는 독립적인 요청 또는 Sequence라고 구분했다. 같은 tiny GPT-2와 `I study.` 입력을 CPU와 RunPod CUDA GPU에서 각각 실행하고, 양쪽 Logit dtype이 `float32`임을 확인했다. GPU Logit을 CPU로 옮겨 비교한 결과 `torch.equal(...)=False`, `torch.allclose(rtol=1e-5, atol=1e-5)=True`였고, 전체 `[1,3,50257]` Logit의 최대 절댓값 차이는 `1.4901161193847656e-08`이었다. `(cpu_logits-gpu_logits).abs().max().item()`을 부호 제거, 전체 원소 중 최대 차이 Scalar Tensor 선택, Python `float` 변환의 순서로 설명했으며 Shape이 `[1,3,50257] → [] → float`로 바뀐다고 정리했다. CPU와 GPU의 다음 Token ID는 모두 `5087`이어서, 미세한 부동소수점 차이가 이번 입력의 `argmax` 선택에는 영향을 주지 않았음을 검증했다. 진행률 표시 비활성화는 계산에 영향 없는 UI 제어이고, 여러 줄 괄호는 Tuple이 아니며 쉼표가 Tuple을 만든다는 Python 문법도 함께 확인했다. 또한 `gpu_model(...)`의 Python 반환과 GPU 물리 계산 완료는 같은 시점이 아닐 수 있지만, 이번 기본 `.to("cpu")` D2H 복사는 선행 CUDA 작업을 기다린 뒤 완성된 CPU 값을 반환하므로 직후 정확성 비교는 안전하다고 구분했다. 반면 `perf_counter()`로 호출만 감싸면 GPU 완료 전에 종료 시각이 기록될 수 있어, GPU Timing에는 `torch.cuda.synchronize()` 또는 CUDA Event 같은 명시적 측정 경계가 필요하다고 정리했다. 이어서 입력 `[1,3]`인 tiny GPT-2를 Warm-up 10회 뒤 200회 실행해, 모든 Python `model()` 호출 반환까지 `1335.146ms`, 동기화로 GPU 작업이 모두 끝날 때까지 `1335.274ms`, 반환 뒤 남은 대기는 `0.128ms`임을 측정했다. `model_calls_returned_ms`는 순수 CPU 시간이 아니고 `gpu_work_completed_ms`도 순수 Kernel 시간이 아니라, CPU의 준비·등록과 GPU 계산이 겹친 전체 벽시계 구간이라고 교정해 해석했다. Benchmark 함수는 전역 `model`·`device` 대신 `model: GPT2LMHeadModel`을 직접 받고, `next(model.parameters()).device`와 `prompt_ids.device`가 다르면 Forward 전에 `ValueError`를 내도록 리팩터링했다. 처음에는 `next()`가 두 번째 Parameter를 꺼낸다고 생각했지만, 새 Iterator의 커서가 첫 원소 앞에 있어 최초 호출이 첫 Parameter로 이동하며 값을 반환한다고 JDBC ResultSet 경험과 연결해 교정했다. 같은 Iterator에 두 번 호출해야 두 번째 Parameter가 나오며, 호출마다 새 Iterator를 만드는 `next(model.parameters())`는 항상 첫 Parameter라는 점과 이 검사가 단일 장치 모델에만 대표성을 가진다는 범위까지 확인했다. 최종적으로 PAD Token `<|endoftext|>`·ID `50256`를 설정하고 RTX 2000 Ada에서 tiny GPT-2, Prompt 2 Token, 새 Token 20개, Warm-up 3회, 동기화된 20회 측정으로 No-cache·KV Cache × Batch 1·4를 비교했다. 두 Batch 모두 출력이 `torch.equal=True`였고, Batch 1은 `48.395ms/413.26 tokens/sec → 42.857ms/466.66 tokens/sec`, Batch 4는 `49.180ms/1626.66 tokens/sec → 43.671ms/1831.89 tokens/sec`로 Cache 사용 시 Latency가 각각 약 `11.44%`·`11.20%` 줄었다. No-cache의 개념적 Token-position `230`과 Cache의 `21` 차이보다 시간 차이가 작았던 이유를 tiny 모델·짧은 Sequence에서 Python 생성 반복·Kernel Launch·argmax·Tensor 연결 같은 고정 비용의 비중이 크기 때문이라고 한정했으며, 다른 로컬 CPU 수치와 직접 우열을 비교하지 않았다. 이 단계 뒤에 Peak VRAM과 Profiler 분석을 이어서 수행했다. Batch와 Sequence를 의도적으로 키워 Cache 효과를 다시 확인했다. `tokenizer(["I study"]*1000)`으로 만든 `[1000,2]` 입력을 Sequence 축으로 64번 반복해 실제 CUDA Tensor `[1000,128]`을 사용했다. 새 Token 20개·Warm-up 3회·동기화된 20회 조건에서 No-cache와 KV Cache의 출력은 `torch.equal=True`였고, `838.082ms/23864.01 tokens/sec` 대비 `151.391ms/132108.06 tokens/sec`로 KV Cache가 약 `5.536배` 빠르고 Latency는 `81.94%` 줄었다. 문장당 Token-position은 `2750→147`, Batch 전체는 `2,750,000→147,000`으로 약 `18.71배` 줄었지만, 최초 Prefill과 Python 반복·Kernel Launch·argmax·Tensor 연결·Cache 관리 비용 때문에 시간 향상은 약 5.54배에 그쳤다고 해석했다. 반복 Token ID는 의미 있는 자연어가 아니라 Shape·성능 조건 변경용 합성 입력이다. 최초 저장 셀에 남아 있던 Batch 4 기준의 변수명·축 표기·출력 Label은 실제 `Batch 1000 · Prompt 128` 조건과 일치하도록 교정했다. 짧은 `I study` 입력의 Batch 1·4에서는 Cache의 Latency 감소가 약 11%였지만, 문장 수만 3000으로 늘린 `[3000,2]`에서는 `372.289ms/161164.97 tokens/sec → 275.249ms/217984.06 tokens/sec`로 차이가 커졌음을 비교했다. 이어 `[1000,128]` 합성 입력에서 각 Step은 1000개 문장을 함께 처리하지만 Autoregressive Step 20회는 순차로 진행되고, 수동 Loop의 `max_new_tokens=20`은 문장당 정확히 20회의 생성 Step이므로 Batch 전체 생성 Token은 `1000×20=20,000`개라고 정리했다. 일반 `model.generate()`에서 이 값은 EOS 조기 종료가 가능한 상한이며 모델의 최대 Context 길이와는 다르다고 구분했다. 이번 Stress Test는 Batch와 Prompt 길이를 동시에 바꿔 원인을 분리할 수 없으므로, 다음에는 Batch 1000을 고정하고 Sequence 2와 128만 비교하는 통제 실험이 필요하다고 결론 내렸다. `torch.cuda.memory_allocated()`는 측정 시작 시점의 메모리 크기 Baseline을 저장하고, `reset_peak_memory_stats()`는 현재 메모리를 0으로 만들거나 자동 차감하는 함수가 아니라 호출 시점부터 Peak의 High-water mark를 다시 추적하는 시간 경계라고 구분했다. 따라서 `max_memory_allocated()`가 반환한 측정 구간의 전체 Peak에서 Baseline을 직접 빼 생성으로 추가된 최대 메모리를 계산한다. 첫 번째 측정의 GPU 생성 결과가 다음 Baseline에 남지 않도록 비교용 결과는 CPU 복사본으로 보존하고 `del generated_ids_on_gpu`로 GPU Tensor 변수의 참조를 제거하며, `del` 자체는 메모리를 직접 지우는 명령이 아니라는 점도 정리했다. RTX 2000 Ada·tiny GPT-2·Batch 1·Prompt 2 Token·새 Token 20개 조건에서 출력 Token ID는 일치했고, 추가 Peak VRAM은 No-cache `1.202 MiB`, KV Cache `1.204 MiB`로 차이가 `0.002 MiB`에 그쳤다. 같은 측정 구조를 `[1000,128]` 합성 입력에 적용하자 출력은 다시 일치했고, No-cache `583.125 MiB`와 KV Cache `587.061 MiB`로 Cache 경로의 Peak가 `3.936 MiB` 증가했다. Prompt Cache의 이론 규모 약 `3.906 MiB`와 비슷했지만, 측정값은 개별 Cache Tensor가 아니라 전체 생성 경로의 Peak 차이라는 한계를 유지했다. RunPod에서 tiny GPT-2에 `I study`를 넣은 한 번의 GPU Forward를 PyTorch Profiler로 기록했다. `key_averages()` 표의 `Self`는 해당 연산 자체, `Total`은 하위 연산을 포함한 비용이고, `# of Calls`와 평균 시간·CPU/CUDA 비율·연산별 메모리의 계산 기준을 실제 수치로 읽었다. `aten::mm`의 `Self CUDA 18.655us`와 `ampere_sgemm_128x32_tn`의 `18.655us`는 두 번의 계산이 아니라 같은 행렬 곱셈을 PyTorch ATen 연산과 실제 CUDA Kernel이라는 서로 다른 계층에서 본 결과라고 설명했다. ATen은 Attention이 아니라 Tensor 연산의 공통 표현이며, CPU Tensor면 CPU 구현이 계산하고 CUDA Tensor면 CPU가 CUDA Kernel 실행을 등록해 GPU가 계산한다고 자기 말로 정리했다. `aten::mm`의 CUDA 메모리 `393KB`가 Logit Shape `[1,2,50257]`와 float32 4Byte 계산값 약 `393KiB`에 대응함을 확인했고, 전체 `Self CPU 6.267ms`와 `Self CUDA 137.439us` 차이는 작은 모델·Batch 1·Prompt 2의 Kernel 계산이 짧고 CPU 준비·등록 비용 비중이 컸던 결과이지 CPU가 모델 계산 대부분을 대신했다는 뜻은 아니라고 구분했다. Tokenizer가 만든 CPU 입력 `[1,2]`를 `.to("cuda")`로 옮기고, tiny GPT-2 Forward로 GPU Logit `[1,2,50257]`을 만든 뒤 `.to("cpu")`로 되가져오는 전체 구간을 PyTorch Profiler로 기록했다. H2D는 Host인 CPU 메모리에서 Device인 GPU 메모리로, D2H는 그 반대 방향으로 복사한다는 뜻이며, `.to()`가 원본 Tensor를 변신시키는 것이 아니라 대상 장치에 복사본을 만든다는 점을 연결했다. 장치 이동은 `aten::to → aten::_to_copy → aten::copy_`와 `cudaMemcpyAsync`로, GPU 계산은 `aten::embedding`·`aten::native_layer_norm`·`aten::addmm`·`aten::bmm`·`aten::mm`과 실제 CUDA Kernel로 나타났다. `non_blocking=False`여도 내부에서 비동기 복사 API로 등록한 뒤 `cudaStreamSynchronize`로 완료를 기다릴 수 있다고 구분했다. 최신 실행에서 `Memcpy DtoH (Device -> Pageable) 31.424us`, `ampere_sgemm_128x32_tn 18.432us`, 전체 `Self CUDA time total 187.968us`를 확인했다. H2D 입력은 `int64` 2개인 16Byte라 CUDA 시간 상위 40행에서 `Memcpy HtoD` 장치 이벤트가 보이지 않았고, Kernel 재시작 직후의 Lazy Loading 가능성과 작은 단일 Forward 조건 때문에 이 수치를 일반 성능 Benchmark로 해석하지 않는 한계를 남겼다.
